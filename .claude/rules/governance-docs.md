# ガバナンス文書の参照と命名のルール

文書へ書き足すとき・書き換えるときは、次の書く約束を守る（文書の量についての第一の規範である。`ADR-doc-promise-over-area-ratchet`）。(1) かぶりなく書く。同じ主張が別の場所に無いかを grep で確かめ、あれば正本の 1 か所に寄せて、他の場所からはそこを参照する。(2) 必要なことだけを書く。推論でたどり着ける事柄と、その場限りの事情は書かない。(3) 古い情報を残さない。触った節の近くにある主張が、今も正しいかを確かめる。文書の量には合否の基準も測る仕組みも無い。書いてよいかは、この約束だけで判断する。

`AGENTS.md` / ルート `CLAUDE.md` / `docs/adr/` / `governance:check` は互いに参照し合う。他の文書を指すときは、正準形 `` `<対象>`「<見出し>」 `` で書く。対象として認める綴りの正本は `scripts/governance/lib.mjs` の `isRefTargetSpelling` である（ここへ写さない）。参照がどこへ着地するかも、同じ doc に書いてある。この形の参照だけが `governance:check` の G-heading-refs で照合される。見出しを改名したり消したりすると、CI が参照元を名指しして落ちる。照合の対象は `.md` だけではない。コード（`.rs`）とスクリプト（コメント記法を持つファイル）のコメントに書いた参照も、同じ検査で照合される（#925・#1138）。

- **序数で他を指してはならない。** 対象は見出しの序数だけでなく、ファイル名の連番・検査 ID・その他の引用される識別子すべてである。番号を使うと、構造を変えにくくなる。また、少なくとも散文に書いた序数と検査 ID の引用は、ずれても `governance:check` が通してしまう（実在しない Step を序数で指す参照と、存在しない検査 ID の引用を注入して確かめた）。連番は並行作業で衝突もする。値が決まるのはマージのときなので、2 本の PR が同じ値を使ってしまう（ADR の連番で 3 回起きた。#812）。
- **機構の実装の詳細（述語の種類・件数・分岐の列挙）を散文へ写さない。**連番と同じ理由が、値だけでなく記述にも当てはまる。記述が正しいかどうかも、マージのときに決まる。#984 は `governance-check.mjs` を読み、「判定する識別子の形は camelCase と SCREAMING_SNAKE だけ」と正確に書いた。しかし並行して入った #989 が 3 つ目の述語を足し（照合の件数が 70 件から 285 件に増えた）、squash で両方が同じツリーに載った時点で、この記述は偽になった。自分のブランチの CI も main の CI も緑で、どちらもこの誤りを検出していない。書くのは帰結（「型で修飾したトークンには当たらない」）だけにし、仕組みは正本を指す。
- **名前は、テーマや目的が決まった時点で、何を指すか分かる形で付ける。**「いま空いている最大値 + 1」を取る操作を持たない名前は、衝突しない。ADR は `docs/adr/ADR-<slug>.md`（引用するときは `ADR-<slug>`）とし、`governance:check` の検査は `G-<name>` とする（#812）。ADR はすべて移行済みで、連番に戻すと G-adr-file-names が落ちる。
- **見出しを移動・圧縮・分割したら、旧版から別の手順で導き直して、すべての主張が新版のどこかにあることを確かめる。**文言を保ったまま組み直すだけ（箇条書きにする・太字を整理する）なら、先に旧版と新版のバッククォート語・issue 番号・ADR 名・エラーコードを、集合の差で突き合わせる。`git show HEAD:<file>` と作業ファイルから `grep -oE` で抽出し、`comm` で比べれば、落とした識別子と足した識別子が 1 行ずつ出る（#1230 で 4 段落 1.8 万字の組み直しに使い、落ちた 1 語が ADR へ移したものだと確かめた）。それでも、完全かどうかは機構では確かめられない。`/plan-review`「Step 2b」に相当する確認（旧内容を SSOT にして、作者とは別の枠組みで確認する）を行う。G-heading-refs が照合するのは正準形だけで、しかも 1 物理行に収まったものだけである。散文の形（「ルート `CLAUDE.md` のフック節」）や、節を移動したときの意味の変化は検出されない。本文を別の場所へ移したら、旧所在を散文で名指している箇所（「〜の行」「〜節」）を `git grep` で数える。根拠のある場所として指しているものは、新しい所在の正準形へ直す。集合の差は、移した本文の内側しか見ない（#1315 で 1 件が偽になった）。助詞が挟まった近い形について G-near-heading-refs が正準形へ直すよう促すのは、それが見出しへ着地したときだけである（改名で着地しなくなると、指摘は何も出さずに消える）。物理改行をまたいだ参照は、照合の候補にすら上がらない。G-folded-heading-refs がこれを別に赤にするが、その適用範囲と見落とす範囲の正本は同検査のヘッダである（ここで数え上げると古くなる）。
- **ADR を消すときは、現役の文書にある引用を散文に直してから消す。**ADR 本文の中の参照は照合されない。ADR は凍結された歴史であり、古くなるままにする（`ADR-adr-frozen-history`）。G-adr-citations は役に立つが、すべての経路を見るわけではない。照合する母集団の外に残った引用は、何も出さずに壊れる（母集団の正本は同検査の `adrCitationDocs` である。2026-08-09 に実測した。#1008）。
- **既に消滅した節の名前を正準形で書かない。**正準形は今ある場所を指すためのもので、過去の名前の記録ではない（G-heading-refs を導入したときに、`PERFORMANCE.md` で 1 件あった）。歴史を書くなら、バッククォートを外して散文にする。
- **これらの編集で自動で走る検査は無い。**G-heading-refs を含む決定的な検査は、PR の CI の governance-check job が後から走らせる（#587）。`.rs` のコメントに書いた見出し参照も同じで、fmt / clippy / test は参照の着地先を確かめない（#925）。
