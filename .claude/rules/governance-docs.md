# ガバナンス文書の参照と命名のルール

文書へ書き足すとき・書き換えるときは、次の書く約束を守る（文書の量についての第一の規範である。`ADR-doc-promise-over-area-ratchet`）。(1) かぶりなく書く。同じ主張が別の場所に無いかを grep で確かめ、あれば正本の 1 か所に寄せて、他の場所からはそこを参照する。(2) 必要なことだけを書く。推論でたどり着ける事柄と、その場限りの事情は書かない。(3) 古い情報を残さない。触った節の近くにある主張が、今も正しいかを確かめる。文書の量には合否の基準も測る仕組みも無い。書いてよいかは、この約束だけで判断する。

他の文書を指すときは、ファイル名を書き、節は見出し名を添えて示す（`` `<対象>`「<見出し>」 `` の形）。見出し名は読み手の手がかりであり、検査は照合しない。見出しは自由に直してよい。直したら旧名で `git grep` し、見つかった参照を同じ変更で直す。`governance:check` が照合するのは、`/` を含むパスの実在（G-references）と、ADR の短縮引用（G-adr-citations）である。

- 序数で他を指してはならない。 対象は見出しの序数だけでなく、ファイル名の連番・検査 ID・その他の引用される識別子すべてである。番号を使うと、構造を変えにくくなる。また、少なくとも散文に書いた序数と検査 ID の引用は、ずれても `governance:check` が通してしまう（実在しない Step を序数で指す参照と、存在しない検査 ID の引用を注入して確かめた）。連番は並行作業で衝突もする。値が決まるのはマージのときなので、2 本の PR が同じ値を使ってしまう（ADR の連番で 3 回起きた。#812）。
- 機構の実装の詳細（述語の種類・件数・分岐の列挙）を散文へ写さない。連番と同じ理由が、値だけでなく記述にも当てはまる。記述が正しいかどうかも、マージのときに決まる。#984 は `governance-check.mjs` を読み、「判定する識別子の形は camelCase と SCREAMING_SNAKE だけ」と正確に書いた。しかし並行して入った #989 が 3 つ目の述語を足し（照合の件数が 70 件から 285 件に増えた）、squash で両方が同じツリーに載った時点で、この記述は偽になった。自分のブランチの CI も main の CI も緑で、どちらもこの誤りを検出していない。書くのは帰結（「型で修飾したトークンには当たらない」）だけにし、仕組みは正本を指す。
- 名前は、テーマや目的が決まった時点で、何を指すか分かる形で付ける。「いま空いている最大値 + 1」を取る操作を持たない名前は、衝突しない。ADR は `docs/adr/ADR-<slug>.md`（引用するときは `ADR-<slug>`）とし、`governance:check` の検査は `G-<name>` とする（#812）。ADR はすべて移行済みで、連番に戻すと G-adr-file-names が落ちる。
- 見出しを移動・圧縮・分割したら、旧版から別の手順で導き直して、すべての主張が新版のどこかにあることを確かめる。文言を保ったまま組み直すだけ（箇条書きにする・太字を整理する）なら、先に旧版と新版のバッククォート語・issue 番号・ADR 名・エラーコードを、集合の差で突き合わせる。`git show HEAD:<file>` と作業ファイルから `grep -oE` で抽出し、`comm` で比べれば、落とした識別子と足した識別子が 1 行ずつ出る（#1230）。それでも、完全かどうかは機構では確かめられない。`/plan-review`「Step 2b」に相当する確認（旧内容を SSOT にして、作者とは別の枠組みで確認する）を行う。本文を別の場所へ移したら、旧所在を名指している箇所（「〜節」「〜の行」）を `git grep` で数え、新しい所在へ直す。集合の差は、移した本文の内側しか見ない（#1315）。
- ADR を消すときは、現役の文書にある引用を散文に直してから消す。ADR 本文の中の参照は照合されない。ADR は凍結された歴史であり、古くなるままにする（`ADR-adr-frozen-history`）。G-adr-citations は役に立つが、すべての経路を見るわけではない。照合する母集団の外に残った引用は、何も出さずに壊れる（母集団の正本は同検査の `adrCitationDocs` である。2026-08-09 に実測した。#1008）。

## 消す・移す・書き換えるとき

- **消す変更の中で「新しく書いた 1 文」は、削除ではなく新規記述である。** 削除の diff では消したことに注意が向き、書き足した主張の検算が抜ける。**残す記述に手を入れたら、その一文は測る対象になる**（#660）。引用位置は行番号ではなくシンボル名・見出し名で書く——行番号は書いた時点で既にずれていることがある
- **移設は削除ではなく差し引きである。** 削減幅を見積もるなら、移設先への追記と跡に残すポインタを引いてから言う（#827/#830 は −28% 見積もりに対し実測 −19.7%。同一サイクルで 2 度、書き足しを引かずに数字を出した）。機構化（散文 → スクリプト）でも呼び出し 1 行と契約への参照は残る
- **自分の変更が偽にした記述・作った矛盾は「範囲外」に置けない。** 判定は「存在しなくなるものへ読者を送るか」「現在形の主張が偽になるか」であり、歴史を述べて真のままの記述は残す（#660）
- **「これは X が持つから消す」と書くときは、X の母集団が元の観点を覆っているかを読んで確かめる。** 覆っていなければ、その差分は**どの検査にも属さなくなる**（#764）。移送先が**実施の有無を観測できる形**を持つかも見る——持たない場所へ移した責務は沈黙する
- **責務の「所在」を書いた散文は、移設で偽になる。しかもシンボル名の grep では届かない。** 消す変更では compile-fail が呼び出し元を挙げるが、移設では**コードは全部通る**まま散文だけが古くなり、所在は略記・概念ラベルで書かれているため関数名では引けない（#749 は 4 箇所を直して実際は 6 箇所だった）。**探し方は概念語の grep である。** あわせて 3 点:
  - **新しく書いた所在の主張は、根拠となる関数の現在地で検算する**（#749 の新設 `//!` は自らの主張を反証していた・`docs/adr/ADR-window-coordinator-split-rule.md` 却下 5）
  - **移設で書き直す `//!` は、引き取った項目だけでなく手放した項目も引き直す**（#666 は**残った側**が出ていった項目を自分のものとして数えた）
  - **訂正した段落は、diff ではなく現物を読み直す**——1 つのラベルを潰すと同じ段落の別のラベルが context 行に沈み、差分だけを見るレビューは「訂正済み」と判定する（#755/#801 の 4 例目はそれで 1 ラウンド生き延びた）
- **規範に条項を足す前に、その節が律する対象範囲（スコープ）が宣言されているか確かめる。** 検算の母集団は、自分が見ていた範囲ではなく**規範が示す範囲**である。スコープの無い規範では、既存条項が既に偽でありうる（#654 は `SPEC.md` §11 に宣言が無いため適用範囲が `snotra-settings` へ及び、既存条項の時点で偽だった）。**スコープ宣言を先に置くと、新条項が真になると同時に既存の偽も消える**
- **全称・不在断定・数え上げは、確定の前に反証プローブを回す。**「何が増えたら/変わったらこの文は偽になるか」を 1 つ挙げる——挙がるなら、暗黙に数えているか前提を隠している。処置は 3 択: 挙がった条件を前提として書き添える／下限の主張（「少なくとも」「〜だけではない」）へ弱める／書かない。**想起や引用をプローブの実行の代わりにしない**——本則を引きながら書いた文書が偽の全称だった先例（#977）と、偽の全称を直した文が再び全称で偽になる連鎖（#1091 で 3 回）がある。検査を書く側の同型（∀ 条件に ∃ 条件を組にする）は `docs/development-principles.md`「構造的設計原則と強制の階梯」に正本がある
- **規範を適用する側に立ったときも、その規範の述語が何を数えているかを検算する——精密に数えることは、何を数えているかを問わない言い訳になる。** #1222 では「連続 2 サイクル 0 件で撤去」という規則を適用し、行数ではなくサイクル境界（`RETROSPECTIVE.md` の更新）まで突き合わせて「条件成立」と結論した。**数え方は正しかったが、「0 件」が何を意味するかを一度も問わなかった**——その 0 件は「露出があって鳴らなかった」ではなく「鳴りようがなかった」で、情報を持たなかった。利用者の指摘（「細かい修正ばかりの局面ではいくら数を重ねても見直しにならない」）で発覚し、規則の側を直した。**適用の丁寧さは検算の代わりにならない。** 規範が数える対象を導出しているなら、その導出をここでも 1 度当てる
- **規則を具体化するとき、閉じた形を開いた禁止の列挙へ替えない。**「読みへ渡すのは純 CPU だけにする」は閉じており、「`engine.lock()` を呼ぶな・I/O を取るな」は開いている——後者は「列挙にないものは書いてよい」と読める。#1123 のレビュー対応で実際にこの置き換えを行い、名指ししなかった他の錠を規則が禁じなくなった。**具体例は規則の下へ「とくに」として置く**（規則を例で置き換えない）。**委譲側が正本より広い契約を宣言していたら、狭めたのは正本の側である**——この退行はそこで露見した
