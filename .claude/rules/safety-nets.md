# セーフティネット（hook / CI / githooks / 規範）を新設・変更するときのルール

セーフティネット（対象はフロントマターの `paths`）に触ると、このファイルが自動で配送される。規範文書（ルート `CLAUDE.md` / `AGENTS.md`）は配送されないので、必要なときに手で読む。設計の考え方は `docs/development-principles.md`「構造的設計原則と強制の階梯」と「検査・検出器を置くときの作法」にある。ここには、セーフティネットが本当に効いているかを確かめる手順を置く。

## 効いていることは、フォールトインジェクションで一度は実測する

- 「hook が自動実行する」「CI が担保する」を理由に手順を省く前に、故意に壊して検出されることを 1 度確かめる（#471）
- 機構そのものの配置を変えたら（判定ファイルの移動・母集団の切り出し方の変更・走査元の追加）、その母集団を入力にする述語を測り直す。一度測った結果は、将来の母集団について何も保証しない（#1143）
- 赤になったことを検出の証拠にする前に、変異が「実際に起きた回帰の姿」と同じ強さかを確かめる（#872）。姿の正本は、その回帰を直したときの実測コメントである。コンパイルエラーは検出ではない。赤の理由が検査の assert かコンパイラかを、毎回出力で確かめる（#1201）

## フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる

- 変異は複製（worktree・一時ディレクトリ・メモリ上のコピー）に当てる。ライブの hook を無効にしない（#504）。git 操作の手本は `.githooks/githooks.test.mjs` にある
- 変異の対象には、他の場所から逐語で名指されていないものを選ぶ。名指されていると別の理由で赤になり、確かめたいことを観測できない（#1094）
- 本体リポジトリの内側の worktree では、`node_modules` を張らない。外へ置いた複製では junction を張る。モジュール解決の失敗は、検出と同じ exit 1 になる。そのため、どのモジュールが解決できなかったかを必ず読む
- 結果を読む前に、測定ハーネスそのものが壊れていないかを疑う（自前で組んだ母集団・finding を絞るキーの取り違え・独立でない対照）（#1214）
- Windows で変異の実行に timeout を掛けるなら、`spawnSync` の timeout に任せない。timeout が止めるのは、`shell: true` や `npx.cmd` が挟む直下の `cmd.exe` だけで、その下は孤児として残る。timeout の後はルートプロセスが既に死んでいるので、taskkill も効かない。代わりに `spawn`（`npx` を呼ぶなら `shell: true` のまま）と自前のタイマーを使う。止める前に `Get-CimInstance Win32_Process` のスナップショットを 1 回取り、`child.pid` から `ParentProcessId` でたどった子孫の `(ProcessId, CreationDate)` を控える。`taskkill /PID <child.pid> /T /F` で止め、数秒おいて、控えた組が 1 つも残っていないことを確かめる。PID は再利用されるので、PID だけでなく組で照合する（#1352・Node v24 で実測。却下した確認方法は `ADR-mutation-timeout-process-tree`）

## 規範（ドキュメント・スキル・チェックリスト）を足すとき

- 規範へフォールトインジェクションを当てる専用の手順は置かない（`docs/adr/ADR-retire-norm-review.md`）。規範が妥当かどうかは、条項を使う作業と独立したレビューが後から明らかにする
- モデルの癖に合わせた調整を規範へ入れるときは、どのモデルのどの癖への対処かを条項に添える。次のモデルで逆向きに働いても、何への対処かが書かれていなければ、誰もそれを外さない（#1230）
- check 系スキルを新設するときは、母集団と費用対称性を書く（`docs/check-skill-skeleton-design.md`）

## 検査の入力集合を、具体対象で検算する

- 「全部」「一致した」と言うときは、守りたい対象を 1 件名指しして、それが入力に現れることを示す。判定の対象外が混じらないことも示す（#488・#482）。母集団は、派生した参照集合からではなく、起きた事実から取る

## 検出器のカバー範囲は、欠落のパターンごとに検算する

- 「既存の機構が検出するから要らない」と言う前に、守る対象の条件ごとに壊して測る（#858）
- テストも条件ごとに書く。同じ結果（終了コード・`ok: false`）になる理由が複数ある関数では、理由ごとに、その理由だけに当たる入力を置き、理由（メッセージ）まで assert する。結果だけを見るテストでは、fail-closed の分岐や、どの例外も同じ終了コードにする catch-all が同じ結果を出す。そのため、理由の 1 つを消す変異も、関数を壊す変異も検出されずに残る（#1319）
- 新設する検出器は、設計を確定する前に、注入する変異を先に書く。その配置では発火しないことが、計画の段階で見つかる（#878）
- CI での実測は、計画ではなく PR 本文のチェックリストに書く（PR が在って初めて測れる）。`workflow_dispatch` だけの workflow は、一時的に `push:` を足して測り、測った後に外す
- 回復機構（fail-safe・リトライ）を足したら、それが隠す退行を誰が見るかを同時に決める。故障注入は、回復機構の追加を巻き戻した状態で行う（#755/#801）

## 検出器を置く・動かすとき

- **新設する検査の期待値は、SPEC・契約と照合してから書く。** 実装より強い期待を書いた検査は設計どおりの挙動を FAIL と判定し、赤の信用を落とす（#749・#757 は受容済みのはみ出しを FAIL 条件にした）。受容残余を持つ挙動では、**残余の境界そのものを判定条件にする**。照合先は必ず現在の SPEC である——引いた条文自体が後の変更で消えることがある（当該条文は #835 で消え、境界は `SPEC.md`「4.5 最大列挙数」へ移った）
- **変異は 2 方向へ入れる。** 「検査が狙う対象」を壊す向きと、**「検査が対象を見ているか」を壊す向き**（依存を素通しへ差し替える）。入力集合が空になる経路だけでなく**退化する経路**も疑う——非空のキャッシュに空のツリーを渡すと、ツリーを引く実装と引かない実装が同じ答えを返し、母集団ゼロの検算では見えない（#872 反復 12。後者の変異で既存 222 本が緑のまま新設 1 本だけが落ちた）
- **注入が赤くならなかったことは、検査が縛れている証拠にも、その事故が起きえない証拠にもならない。** 系が構造的に故障を防いでいれば正しい姿の変異でも発火しない（#1004 H7 は 2 度失敗した: 消費して捨てる変異が coalescing と同じ結果になり、次に debounce 幅と検索時間が拮抗して追い越さなかった。worker へ人工遅延を入れて初めて発火した）。**「めったに起きないが起きたら深刻」を見張る検知器は、人工的にでも一度発火させるまで、発火しうるかが分からない**
- **検知器を足す前に、その検知器が単独で検出する経路を数える。** 既存の検査が検出する経路を除いて残るものが無ければ、それは検知力ではなく**保守の対象**である（#872 反復 12 は検知器の破綻を 3 回続けて指摘され、毎回その検知器を直して新しい未検証の装置を投入していた。発火経路を数えたら守っていたのは 1 経路で、2 行の断言で刺せた）。「検知器が足りない」と読むのは誤診でありうる
- **拒否する機構の誤爆は一様でない——「拒否メッセージの復帰手順が適用できない誤爆」を別枠で探す。** 真陽性と誤爆の件数だけでなく、**誤爆した相手が示された手順で回復できるか**を問う。回復手段のない拒否は、規範を機構へ移した設計そのものへの信頼を落とす（#768。同型の非対称は自分の機構同士にも生じ、PostToolUse が出す再現コマンドを PreToolUse が拒んだ）
- **既存の検知器へ「移設」するときも、移設先で発火するかを測る**（移設は新設と同じ検算を要する）。#1056 は余剰容量の検査を `capacity == n` の組からアリーナ用の組へ移したが、移設先の経路は確保が寸法ぴったりで**構成上つねに 0** になり、`shrink_to_fit` を外しても緑のままだった（伸長に任せる別経路の索引を fixture へ足して初めて発火した）
- **「測ったが動かなかったので採らなかった」と残余へ記録するときは、0 を保証していたのが対象の性質か判定の構成かを書き分ける。** 前者なら記録は持つが、後者は**判定が広がった瞬間に黙って反転する**（#1095: G-stale-identifiers の「Rust のテストコードが語彙を寄付する穴は全セルで 0 件」は #885 当時の実測だが、0 を作っていたのは穴の性質ではなく**述語が lowercase snake_case を見ていなかったこと**で、#989 が述語を足した時点で 9 件へ反転していた。誰も測り直さないまま 5 か月緑だった）。**結論が正しいままでも理由づけだけが偽になる**——反転しても赤くならないので、気づく契機はその残余を読み直したときしかない

## これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する

- 「無出力 = 合格」のような意味づけをすると、タイムアウト・起動失敗・出力溢れが誤って合格になる。その意味が成り立たない経路をすべて塞ぐ（#471）。分類を 1 つ足したら、隣の分類へ到達する経路も列挙し直す（#489）
