# セーフティネット（hook / CI / githooks / 規範）を新設・変更するときのルール

セーフティネット（対象はフロントマターの `paths`）を触ると自動配送される。規範文書（ルート `CLAUDE.md` / `AGENTS.md`）は配送されないので必要時に手で読む。設計哲学は `docs/development-principles.md`「構造的設計原則と強制の階梯」が持つ。ここに置くのは、セーフティネットが**本当に効いているか**を確かめる手順である。

## 効いていることは、フォールトインジェクションで一度は実測する

- 「hook が自動実行する」「CI が担保する」に依拠して手順を省く前に、故意に壊して検知されることを 1 度確かめる（#471）
- 機構自身の配置を変えたら（判定ファイルの移動・母集団の切り出しの変更・走査元の追加）、その母集団を食う述語を測り直す。一度測ったことは将来の母集団を保証しない（#1143）
- 赤くなったことを検出の証拠にする前に、変異が「実際に起きた回帰の姿」と同じ強さかを確かめる（#872）。**コンパイルエラーは検知ではない**——赤の理由が検査の assert かコンパイラかを毎回出力で確かめる（#1201）

## フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる

- 変異は複製（worktree・一時ディレクトリ・メモリ上のコピー）に当てる。ライブの hook を無害化しない（#504）。git 操作の手本は `.githooks/githooks.test.mjs`
- 変異対象は、他所から逐語で名指されていないものを選ぶ。名指されていると別の理由で赤くなり、当の観測ができない（#1094）
- 本体リポジトリの内側の worktree では `node_modules` を張らない。外へ置いた複製では junction を張る。モジュール解決の失敗は検知と同じ exit 1 になるので、どのモジュールが解決できなかったかを必ず読む
- 結果を読む前に、測定ハーネス自身が壊れる形（自前で組んだ母集団・finding を絞る鍵の取り違え・独立でない対照）を疑う（#1214）

## 規範（ドキュメント・スキル・チェックリスト）を足すとき

- 規範へフォールトインジェクションを当てる専用手順は置かない（`docs/adr/ADR-retire-norm-review.md`）。妥当性は条項を使う作業と独立レビューが事後に暴く
- モデルの癖への較正を規範へ入れるときは、どのモデルのどの癖への栓かを条項に添える。次のモデルで逆向きに効いても、名乗らない栓は誰も外さない（#1230）
- check 系スキルを新設するときは、母集団と費用対称性を書く（`docs/check-skill-skeleton-design.md`）

## 検査の入力集合を、具体対象で検算する

- 「全部」「一致した」と言うときは、守りたい対象を 1 件名指しして入力に現れることを示し、判定対象外が混じらないことも示す（#488・#482）。母集団は派生した参照集合ではなく、起きた事実から取る

## 検出器のカバー範囲は、欠落のパターンごとに検算する

- 「既存の機構が捕まえるから要らない」と言う前に、守る対象の足ごとに壊して測る（#858）
- 新設する検出器は、設計を確定する前に「注入する変異」を先に書く。その配置では発火しないことが計画段階で見つかる（#878）
- CI の実測は計画ではなく PR 本文のチェックリストへ送る（PR が在って初めて測れる）。`workflow_dispatch` だけの workflow は、一時的な `push:` で測ってから外す
- 回復機構（fail-safe・リトライ）を足したら、それが隠す退行を誰が見るかを同時に決める。故障注入は回復機構ごと巻き戻して行う（#755/#801）

## これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する

- 「無出力 = 合格」のような意味づけは、タイムアウト・起動失敗・出力溢れを誤った合格に変える。意味が成り立たない経路をすべて塞ぐ（#471）。分類を 1 つ足したら隣接分類への到達経路も再列挙する（#489）
