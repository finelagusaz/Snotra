# セーフティネット（hook / CI / githooks / 規範）を新設・変更するときのルール

このファイルは、セーフティネットそのもの（対象は上の `paths` が SSOT）を触ると自動配送される——**rules 自身を含むため、本ファイルの編集でも配送される**（この手順は自分自身にも適用される）。規範文書（ルート `CLAUDE.md` / `AGENTS.md` 等）もセーフティネットだが `paths` 外＝自動配送されない（誤配送を避けるため。必要時に手動参照する）。**設計哲学**（検出は構造化信号で行い、fail-closed を既定値に埋める）は `docs/development-principles.md`「構造的設計原則と強制の階梯」が SSOT。ここに置くのは、そのセーフティネットが**本当に効いているか**を確かめる運用手順である。

## 効いていることは、フォールトインジェクションで一度は実測する

- **「hook が自動実行する」「CI が担保する」は書かれた時点の期待であって、測定結果ではない**。それに依拠して手順を省く前に、故意に壊して検知されることを 1 度確かめる（#471: hook の出力が一度も届いていないのに「届く」という記述の上に PR が積まれていた）。

## フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる

- 判定がソース述語でも実 git 操作でも規則は同じで、**変わるのは複製の作り方だけ**である。述語はメモリ上へコピーして変異させ、git 操作は hook を一時ディレクトリへコピーして使い捨て repo の `core.hooksPath` をそこへ向ける（手本は `.githooks/githooks.test.mjs`）。「判定が〜なら」のような条件節を免除と読んではならない（#504: 条件節を免除と読み、ライブの `pre-commit` を無害化して main 保護が数十秒消えた）。意図的に規則違反となる操作を行い、拒否されることを確認する類はガードの**行使**であり、弱めていないので対象外（#482）。

## セーフティネットが「規範」（ドキュメント・スキル・チェックリスト）の場合、フォールトインジェクションとは「回避しようとする読者」である

- 規範は機構ではないので実行して測れない——想定読者の観点で文言だけを読ませ、抜け道を探させる。**手順は `/norm-review` が持つ**（停止条件の決め方・2 クラスの読者・塞ぎの分量予算）。パスに属する規範（`.claude/rules/` `.claude/skills/` および規範文書）を新設・変更したら起動する。
- **check 系スキル（`*-check`）は 4 スロット（母集団・証拠・停止・接続）と費用対称性を満たす**——定義は `docs/check-skill-skeleton-design.md`

- 条項を足す前にその節のスコープ宣言を見る（検算の母集団は規範が名乗る範囲）: `docs/development-principles.md`「構造的設計原則と強制の階梯」

## 検査の入力集合を、具体対象で検算する

- 一覧・索引・サブエージェントの報告を根拠に「全部」「一致した」と言うときは、(1) 守りたい対象を 1 件名指しし、それが実際に読む入力に現れることを示し、(2) 判定対象外が同じ入力に混じらないことを示す（両方向）。**正常時に一覧へ出ない対象は、その一覧だけを見る検査からは永遠に見えず**（#488, #489）、余計なものが入れば誤爆する（#482）。母集団は**派生した参照集合ではなく、起きた事実**から取り（`closingIssuesReferences` ではなく `gh issue list --search "closed:>=<mergedAt>"`）、派生集合（`description` 等の要約）で関連性を判断しない。

## これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する

- 「無出力 = 合格」「空 = 未設定」のような意味づけは、同じ状態を無害なノイズから**誤った合格判定の原因**に変える——意味が成り立たない経路をすべて塞ぐ（#471: hook の沈黙に「合格」を与えたとき、タイムアウト・起動失敗・出力溢れが沈黙経路として残っていた）。**分類を 1 つ足したときは、隣接分類への到達経路も再列挙する**——逃げ道は塞いだ扉の隣に現れる（#489）。
