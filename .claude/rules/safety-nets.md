# セーフティネット（hook / CI / githooks / 規範）を新設・変更するときのルール

このファイルは、セーフティネットそのもの（対象は上の `paths` が SSOT）を触ると自動配送される——**rules 自身を含むため、本ファイルの編集でも配送される**（この手順は自分自身にも適用される）。規範文書（ルート `CLAUDE.md` / `AGENTS.md` 等）もセーフティネットだが `paths` 外＝自動配送されない（誤配送を避けるため。必要時に手動参照する）。**設計哲学**（検出は構造化信号で行い、fail-closed を既定値に埋める）は `docs/development-principles.md`「構造的設計原則と強制の階梯」が SSOT。ここに置くのは、そのセーフティネットが**本当に効いているか**を確かめる運用手順である。

## 効いていることは、フォールトインジェクションで一度は実測する

- **「hook が自動実行する」「CI が担保する」は書かれた時点の期待であって、測定結果ではない**。それに依拠して手順を省く前に、故意に壊して検知されることを 1 度確かめる（#471: hook の出力が一度も届いていないのに「届く」という記述の上に PR が積まれていた）。
- **注入したことと、注入が正しい強さであることは別である**——変異が本来の回帰より強いと、検査が縛れていなくても赤くなる。**赤くなったことを「検出できる証拠」として扱う前に**、変異が「実際に起きた回帰の姿」と同じかを確かめる（#872 で同じ型を 3 回）。**発火しないときも同じである**（#1004）。**どちらの向きも本文は `docs/development-principles.md`「構造的設計原則と強制の階梯」が持つ。**

## フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる

- 判定がソース述語でも実 git 操作でも規則は同じで、**変わるのは複製の作り方だけ**である。述語はメモリ上へコピーして変異させ、git 操作は hook を一時ディレクトリへコピーして使い捨て repo の `core.hooksPath` をそこへ向ける（手本は `.githooks/githooks.test.mjs`）。「判定が〜なら」のような条件節を免除と読んではならない（#504: 条件節を免除と読み、ライブの `pre-commit` を無害化して main 保護が数十秒消えた）。意図的に規則違反となる操作を行い、拒否されることを確認する類はガードの**行使**であり、弱めていないので対象外（#482）。

## 規範（ドキュメント・スキル・チェックリスト）を足すとき

- **規範そのものへフォールトインジェクションを当てる専用手順は置かない。** かつて `/norm-review` が担ったが、判別力がゼロと測れたため 2026-08-07 に廃止した（経緯と却下案は `docs/adr/ADR-retire-norm-review.md`）。規範の妥当性は、条項を実際に使う作業と独立レビュー（`code-reviewer`・`/plan-review`「Step 2b — 独立導出による網羅性レビュー」）が事後に暴くものとして扱う。
- **check 系スキルに必須なのは母集団と費用対称性の 2 つだけである**（証拠・停止・接続は書けるなら 1 文で）——定義と、必須を 4 つから 2 つへ減らした実測は `docs/check-skill-skeleton-design.md`

- 条項を足す前にその節のスコープ宣言を見る（検算の母集団は規範が名乗る範囲）: `docs/development-principles.md`「構造的設計原則と強制の階梯」

## 検査の入力集合を、具体対象で検算する

- 一覧・索引・サブエージェントの報告を根拠に「全部」「一致した」と言うときは、(1) 守りたい対象を 1 件名指しし、それが実際に読む入力に現れることを示し、(2) 判定対象外が同じ入力に混じらないことを示す（両方向）。**正常時に一覧へ出ない対象は、その一覧だけを見る検査からは永遠に見えず**（#488, #489）、余計なものが入れば誤爆する（#482）。母集団は**派生した参照集合ではなく、起きた事実**から取り（`gh pr view <PR> --json closingIssuesReferences` ではなく `gh issue list --search "closed:>=<mergedAt>"`）、派生集合（`description` 等の要約）で関連性を判断しない。

## 検出器のカバー範囲は、欠落のパターンごとに検算する

- **「既存の機構が捕まえるから新しい検査は要らない」は、それ自体が検査を書かない理由として使われる**。検出器が守る対象が複数の足を持つとき（id → 予算 → 実装 の組など）、どの足が欠けても赤くなるとは限らない（#858: カナリアが捕まえるのは 3 本中 1 本だけで、残りは手書きの列挙が唯一の検知点だった）。足ごとに壊して測り、捕まらない足は機構へ載せる。
- **CI の実測は PR が在って初めて行える**——`ci.yml` は `pull_request` でのみ起動し、`gh pr create` は `workspace/plan.md` の未チェック `- [ ]` で block される（#749）。計画に検証項目として置くと循環して閉じられないので、**PR 本文のチェックリストへ送る**（#858）。
- **新設した workflow が `workflow_dispatch` だけを持つ場合、main へ入る前に実測する手段が無い**——dispatch は既定ブランチに在るものしか起動できない（実測）。PR 本文のチェックリストは「PR ができてから走る `ci.yml`」には効くが、**起動手段そのものが無い workflow には届かない**。実験用の枝接頭辞へ `push:` を一時的に張って測り、役目を終えたら workflow ごと外す（#872 の pester-flake-repro.yml が先例。撤去済み）。
- **回復機構（fail-safe・自己修復・リトライ）を足したら、その機構が隠す退行を誰が見るかを同時に決める**。#755/#801 では、show の導出が退行しても次のフレームが 1 フレームで補正するため、**外から窓を測る検査は緑のまま通る**（観測できる差は約 16ms の過渡だけで、200ms ポーリング + 100ms 間隔のサンプリングには写らない）。**故障注入は回復機構ごと巻き戻して行う**——実測では、導出をバグらせても外部の矩形測定は正しい値を返し、in-process の信号だけが発火した。外から見えない退行には、プロセス内で不変条件を突き合わせる信号を用意する（形は「起きてはならないことが起きていないか」・`src-tauri/CLAUDE.md`「モジュール構成」）。

## これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する

- 「無出力 = 合格」「空 = 未設定」のような意味づけは、同じ状態を無害なノイズから**誤った合格判定の原因**に変える——意味が成り立たない経路をすべて塞ぐ（#471: hook の沈黙に「合格」を与えたとき、タイムアウト・起動失敗・出力溢れが沈黙経路として残っていた）。**分類を 1 つ足したときは、隣接分類への到達経路も再列挙する**——逃げ道は塞いだ扉の隣に現れる（#489）。
