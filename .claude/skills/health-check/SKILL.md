コードベースとドキュメントの状態を検証する。発見事項を報告し、修正はしない。

決定的検査の正本は `npm run governance:check`（`scripts/governance-check.mjs`・#587）である。旧 Check 2・3・4・6・8・9 は、すべてそこで機械検査するようになった。対応表は `references/mechanized-checks.md` にある。Check 番号は振り直さない（序数で参照している箇所が古くならないようにするため）。下の欠番の理由はその表が説明する。Check 1・5・10 は一部だけが機械化されており、意味の判断が要る残りの部分を下に書く。このスキルで実行するのは次である。

1. `npm run governance:check` を実行する。赤なら、その全件を発見事項（Critical）として報告する
2. 機械化できない検査を、従来どおり実施する。対象は Check 5 の残りの部分（コマンド直書き grep）と Check 7（メモリ整合）である

## Check 1 — CLAUDE.md モジュール構成の乖離

→ `npm run governance:check`（G-module-index・#587）が機械検査する。ここでは実行しない。

ただし、`governance:check` が照合するのは `MODULE_INDEX_CRATES` に載っている crate だけである。crate を新設して同表へ足し忘れると、その `CLAUDE.md` のモジュール構成はまったく照合されないまま緑になる（2026-08-09 実測・#1008）。

足し忘れそのものは別の層が検出する。`scripts/governance-check.test.mjs` の母集団カナリア（#701）が、実 `Cargo.toml` の `[workspace] members` を読む。そして `CLAUDE.md` を持つ member が `MODULE_INDEX_CRATES` と `governanceDocs()` の両方に載ることを、`npm test` で固定する。

テストファイルの除外（正本: `vitest.config.ts` の include）と basename 照合の意味は、スクリプト（`scripts/governance/checks/G-module-index.mjs`）とそのテスト（`G-module-index.test.mjs`）が固定する（検査ごとのファイル分割・#1088 でここへ移った）。facade（`scripts/governance-check.mjs`）は `checks/` から何も再輸出しない。そのため import 元は `checks/` 側である（#1094）。

責務記述の内容が正しいか（索引があるかではなく、記述が実態と合っているか）は機械化できない。気づいた乖離があれば、発見事項として報告する。

## Check 5 — docs/build-commands.md コマンドの整合（SSOT）

コマンドが実在するかの照合（`npm run XXX` → `package.json` scripts、`cargo test -p <crate>` → workspace members の package name）は、`npm run governance:check`（G-build-commands・#587）が機械検査する。ここでは実行しない。

この Check に残るのは、意味の判断が要る部分だけである。

- `AGENTS.md`「開発ワークフロー」の「変更後の検証を実行する」や `.claude/skills/*/SKILL.md` に、コマンド本体（`cargo XXX` / `npm XXX` / `npx XXX` の具体的な引数を含む実行コマンド）が直書きされていないかを grep する。`docs/build-commands.md` の正本を経由していない箇所を報告する（コマンド名への言及や参照リンクは許容する）。

## Check 7 — MEMORY.md 参照の実在性

`MEMORY.md` はリポジトリに存在しない。harness のユーザー領域（`~/.claude/projects/<project-slug>/memory/`）にある。その絶対パスは、メインエージェントの system prompt に与えられる。スラグの導出規則をここに書かない（harness 内部の仕様であり、表記も揺れる）。

- リポジトリ内を Glob して見つからないことは、発見事項ではない。
- `Read` / `Glob` / `Grep` は、絶対パスを渡せばリポジトリ外へ届く（実測）。ツールが届くかどうかは問題にならない
- このチェックを委譲するときは、メモリ領域の絶対パスをサブエージェントのプロンプトに明記する。サブエージェントは system prompt を継承しないので、パスを知らない。渡し忘れると、サブエージェントは見えないものを「無いもの」として報告する（#489 で実測）

検証内容（7a〜7c は機械的な検査である。7d はレビューであり、自動では判定できない）:

1. 7a — 索引 → ファイルの実在: `MEMORY.md` を読み、リンク先のメモリファイルが実在するかを確認する。存在しないファイルへの参照を報告する
2. 7b — 索引 ↔ 本文の一致: 各メモリファイルの `description` が内容と合っているかを簡易にチェックする（ファイルを読んで比べる）
3. 7c — ファイル → 索引の実在（逆方向）: メモリ領域を `Glob` ですべて列挙し、`MEMORY.md` に載っていない孤児ファイルが無いかを確認する。索引だけを母集団にすると、ディスク上にあって索引に無いメモリはいつまでも見えない（#492）
4. 7d — 事実が古くなっていないかのレビュー: 今サイクルで実測により覆した前提・変更した設定・仕様変更があるなら、そのキーワードと概念名でメモリ本文を grep する。該当する主張は更新するか削除する。索引の `description` で関連性を判断しない。`description` は本文から作った要約であり、覆された一文がそこに現れるとは限らない（#488: `push-before-pr-create` の `description` は正確なままで、本文は既に無くなった機構を述べていた）。実施は `/retrospective`「Step 6」が担う

Check 7 が保証するのは索引の整合であって、全メモリの事実が今も正しいことではない。7d は、ある主張が今も真かを読んで考えるしかなく、機械では判定できない。そのため「全メモリが現在の事実と一致する」と報告しない。書けない全称の主張は、検査していないのに緑と見える結果を作る（`AGENTS.md`「検証の作法（全タスク共通）」の、何が増えたら偽になるかを問う手順）。

結論には根拠を添える。「発見事項なし」も同じである。7a はリンク先ごとに実在するかどうかを、7c は `Glob` の全列挙と索引の突き合わせを、一覧で示す。`/plan-review` と同じ決まりである。根拠のない「確認済み」は、確認したことにならない。証跡の無い「発見事項ゼロ」は、実施していないのと区別が付かない。

判定は三値である。「異常あり」「異常なし」「見ていない」を同じ記号で書かない。

- パスが与えられており、リンク切れか `description` の不一致がある → 発見事項として報告する
- パスが与えられており、メモリ領域が空（`MEMORY.md` 未作成） → 正常（メモリ未初期化）である。発見事項ではない。ただし「空」は列挙の結果として示す（`Glob` の出力を根拠に添える）。実行方式を問わず、「空だった」と自己申告しない。誤ったパスも空に見える。そのため、委譲先が空を観測したときは、渡したパスが正しいかを委譲元が確認する
- パスが与えられていない（実行者がパスを持たない） → `[Skipped] 検証不能` と報告する。「不在」と報告しない（存在しない欠陥を作り出すことになる）

`[Skipped]` は「実行者がパスを持たない」という状態を表す。検査を省く口実ではない。

- インライン実行のメインエージェントは、system prompt から絶対パスを得られる。そのため Skip は正当化されない
- 委譲先が `[Skipped]` を返したら、パスを持つ委譲元がパスを渡して再委譲する。`[Skipped]` をそのまま最終報告へ載せない
- したがって、最終報告に Check 7 の `[Skipped]` が残るのは、実行環境そのものにメモリ領域が与えられていない場合だけである

これは規範であって機構ではない（受容する性質である）。実行者が「パスを持たない」「読んだが整合していた」と偽っても、文書はそれを反証できない。防御は 2 つだけである。1 つは根拠を要求すること（偽る手間を増やす）。もう 1 つは `Skipped` を見える形で出すこと（黙って消えられなくする）。`--no-verify` と同じく best-effort として扱う。

## Check 10 — docs/build-commands.md ↔ .github/workflows/\* の対応

「CI/CD メモ」の対応表とワークフローの機械照合は、`npm run governance:check`（G-ci-table・#587）が担う。照合するのは、表のコマンドと wrapper スクリプトのパスが、表に書いた workflow の `run:` に現れるか、および workflow ファイルが実在するかである。ここでは実行しない。

残るのは意味の判断だけである。次を見る。

- 表のトリガー記述（「PR 自動」「対象 paths を含む PR」等）が、実際の `on:`/`paths` 設定と合っているか
- 逆方向に、「workflow で実行されているが表に無いコマンド」が無いか
- カテゴリ A〜C の必須コマンドが対応表から漏れていないか（G-ci-table は表の行を起点に照合する。そのため、表に載っていない必須コマンドは機構の母集団に入らない）

気づいたずれは Warning で報告する。

## 出力

```markdown
# Health Check Report

## 発見事項

### [Critical / Warning / Info] <カテゴリ>
- <具体的な乖離の説明>

## 実施できなかったチェック

### [Skipped] Check 7 — メモリ領域の絶対パスが与えられていない

## サマリー
- チェック項目数: N（実施: M / Skipped: K）
- 発見事項: N件（Critical: N / Warning: N / Info: N）
- 根拠 — governance:check の出力（検査の本数行）と exit code、Check 7 の実在列挙
```

- `Critical` / `Warning` / `Info` は発見事項である（コードベースに乖離がある）。`[Skipped]` は発見事項ではない（前提が満たされず、検査そのものが走らなかった）。「異常なし」と「見ていない」を同じ記号で書かない。
- `[Skipped]` が正当なのは、文書化された前提を満たせない場合に限る。現状、その前提を持つのは Check 7 だけである（メモリ領域の絶対パスが与えられていない）。`governance:check` の実行と Check 5 の残りの部分は、前提が常に満たされる。そのため、それらが `Skipped` になったこと自体を発見事項（検査基盤の異常）として報告する。この限定が無いと、「面倒な検査は `Skipped` にしておけば楽」という抜け道ができる
- 「All checks passed.」と書けるのは、発見事項がゼロで、かつ `Skipped` もゼロのときだけである。`Skipped` が 1 つでもあれば「M passed, K skipped」と書く（M = 実施数）
- 「根拠」行は実行の証跡であって、発見事項ではない。`Critical`/`Warning`/`Info`（乖離あり）とも `[Skipped]`（未実行）とも別の、3 つ目の分類である。発見事項の件数にも、「All checks passed」の判定にも数えない。この行は、検査が母集団を絞るとき（現状は Check 1 の test 除外）に、「何をどれだけ照合したか」を具体的に示す。省くと、「差分ゼロ」と「照合していない」を区別できなくなる（Check 7 の証跡の決まりと、`AGENTS.md`「検証の作法（全タスク共通）」の「照合は SSOT に対して行う」を、一般の形にしたもの）。将来、ほかの検査が根拠を出せる余地は残しておく
- 該当が無いセクション（発見事項ゼロ / `Skipped` ゼロ）は省いてよい。サマリーは常に出す（根拠行を含む）
