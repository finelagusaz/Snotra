自律的にフルサイクル開発を行う。実装判断はコードとドキュメントから自律的に行い、要求判断が必要な場合のみ確認する。**着手時に何をするかを 1 行で述べ、Step の切り替わり・発見・方針転換のたびに短く報せる**——読者は tool の出力を見ていない（この条項はモデルの癖への較正である。対象は Fable 5.1 以降に見られる、tool 呼び出しの合間の報せが減る癖で、Opus 5.5 も同じ向き・#1230）。最後の報告の形は「出力」節が定める。

タスク: $ARGUMENTS

## Step 1 — 入口判定

このスキルは**計画を所有しない**。動くのは「**未確定がゼロで、人間が承認済みの計画**がある」か「計画が要らない」かのどちらかのときだけである。

### 1a. workspace/plan.md の由来を確かめる

`/start-issue` は中断（セッション断・放棄）しても `workspace/` を残すため、別タスクの残骸や、承認前で止まった計画が残っていることがある。`workspace/plan.md` があれば、**別々の性質である次の 3 つ**を確かめる。

- **同一性** — `plan.md` とコミットメッセージ（あれば）の issue 番号・目的が**与えられたタスク**と噛み合う。`/implement` は単独起動が日常的な経路であり、**このブランチの issue が今のタスクとは限らない**
- **未確定ゼロ**（機械判定）— `## 未確定（実装前に潰す）` で始まる見出し行が**存在し**、かつ**その節の中**（次の同レベル見出しまで）に `- [ ]` が 1 つも無い。**節の中に限る**——フェーズ配下の作業項目は着手前なら当然すべて `- [ ]` であり、ファイル全体で数えると常に不成立になる。**見出しの存在を確かめる側も落とせない**——欄を書かなかった計画が件数ゼロで素通りし、判定が fail-open へ退化する（#821）
- **人間承認**（機械判定）— `## 人間レビュー` 見出しが存在し、その節に `- [x] 承認済み — <日付> / 問い: "<承認を求めた問いの逐語引用>" / 回答: "<ユーザー発言の逐語引用>"` が 1 件ある。問いと回答は会話へ逆引きできる逐語引用にする。エージェント自身の判断や、コミット済みであることを承認の代用にしない

**既定は fail-closed である**——確かめられなければ、あるものとして扱わない。古い計画や未レビューの計画を有効と誤れば**違うものを実装し**、検証を全部通ってコミットまで気づけない。無効と誤っても聞き直すだけで済む。

### 1b. 分岐（行き先を決めるのはこの表だけである）

| 状況 | 動き |
|---|---|
| 3 つすべて立つ | それを実装の指示として読み Step 2 へ（`/start-issue`「出力」の引き渡し契約）。調査はやり直さない |
| 同一性は立つが、未確定ゼロか人間承認が立たない | 計画は在るが引き渡し条件を満たさない。**止める**（1c-B）。コミット済みかどうかは無関係——コミットは計画内容または人間承認の証拠ではない |
| main から到達できる／別ブランチのもの／このブランチ上でも与えられたタスクと噛み合わない＝**別タスクの残骸** | **消さずに**何の残骸かを報告し、削除か退避かをユーザーに確認したうえで、「計画が無い」ものとして下の「計画が無く…」の 2 行のどちらかへ進む |
| 由来の判断がつかない | **止める**（1c-C） |
| 計画が無く、計画を書かずに直せる | 下の調査を行ってから Step 2 へ |
| 計画が無く、計画が要ると判明した（**実装の途中で判明した場合も同じ**） | **止める**（1c-A） |

計画なしの経路でだけ行う調査:

- `SPEC.md` と関連する `CLAUDE.md` を読み、意図とアーキテクチャを理解する
- `$ARGUMENTS` からエントリポイントと関連モジュールを特定する
- 要求された機能と重複する既存コードを検索する
- 3層モデルの制約（意図は `SPEC.md`、実装はコード）に留意する
- **要求の曖昧さを判定する** — 「何を作るか」がコードとドキュメントから一意に決まらない場合（UI の見た目、対象範囲、既存動作を変えるか追加するか等）、最も影響の大きい 1〜2 点に絞って質問し、回答を得てから進む

**計画が要るサイン**（網羅ではなく徴候である）:

- 複数ファイルにまたがり、変更の順序に依存する
- 新しい状態・プロセス・ウィンドウ・永続形式を導入する
- `SPEC.md` に書かれた挙動を変える
- どう直すかが一つに決まらず、代替案の比較が要る

### 1c. 止まったときの引き渡し

**実装を始めない。** 停止は 3 種で、それぞれ渡し方が違う:

- **1c-A（計画が無く、要ると判明した）**: 何が計画を要求したかを報告し、**issue 本文の草案を出して起票を打診する**。承認されたら `gh issue create` を実行し、`/start-issue <N>` へ渡す
- **1c-B（計画はあるが引き渡し条件を満たさない）**: **新規 issue は起票しない。** 未確定が残るなら `/start-issue`「5a. check スキルによる計画検証」へ、人間承認が無いなら `/start-issue`「5c. 人間の注釈と承認」へ戻す。`/implement` が未確定を潰したり、承認を自己記録したりしてはならない
- **1c-C（由来の判断がつかない）**: 何を確かめられなかったかを示して問う。答えを得るまで進まない

## Step 2 — 実装

- **純粋核（crate を問わず egui/Win32 非依存でテスト可能なロジック）の追加・変更: テストが主張する性質を、その性質をまだ持たない実装に当てて実際に落としてから（Red）通す（Green）**。既存コードを直すなら、現状のコードがその実装である。新しい型・関数を導入するなら、シグネチャだけ置いて中身を `todo!()` か no-op にする——テストだけ先に書いても得られるのはコンパイルエラーであり、**実装に当てて落ちたことにならない**（#745）。`snotra-core` に限らず `src-tauri` 等の純粋モジュール（`lifecycle.rs`・`search_state.rs` 等）も対象（`view`/Win32 依存はテスト前提にしない）
- 計画がある場合は、計画に沿って変更を行う
- **plan.md のチェックリストを消し込みながら進める**: 完了した項目はその都度 `- [x]` へ更新し、フェーズのコミットに含める（チェック状態を git に残し、中断・再開時の「どこまでやったか」を接地させる）。実装中に判明した計画外の作業は、その場で `- [ ]` として plan.md へ追記する——途中発見のタスクも PR 前ゲートに乗せる
- 新しい純ロジックには、それが属する crate に `#[cfg(test)]` ユニットテストを追加する
- **既存テストを改名・転用するとき、元のテストが証明していた不変条件を孤立させない**: 改名は内容ではなく「どの命題を証明していたか」も追跡する。転用で失われる不変条件は別テストで補う
- **ソースファイル（`.rs`）を新規追加・削除したら、同じ変更で該当 `CLAUDE.md` のモジュール構成節の索引（ファイル名）を更新する**（責務散文は各ファイルの `//!` が正本・#562。索引漏れは `governance:check` が捕捉する——**ただし `MODULE_INDEX_CRATES` に載っている crate に限る**。また、**同名のファイルが同じ節で既に言及されていれば緑のまま通る**。射程と死角の正本は `scripts/governance/checks/G-module-index.mjs` と `ADR-module-index-reverse-scope`）
- `SPEC.md` に記載された挙動に影響する変更の場合、`SPEC.md` も更新する（`AGENTS.md`「3層分担」に従う）

## Step 3 — 検証とレビュー（委譲・最大5サイクル）

**カテゴリ A〜F の検証もレビューも、主エージェントの作業ツリーでは行わない。** コミットを 1 つ作り、その sha に対して、**権威ある A〜F は道具（`npm run verify:tree`）が道具の木で、レビューと変異注入は worktree のサブエージェントが自分の木で**行う。

**対象を不変オブジェクトにすることが、この形の要点である。** 委譲した検査が対象を読む時刻は制御できない（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）ので、**動かないものを渡す**。**検証とレビューを別の木で走らせても 2 つの報告が別の版へ向かないのは、道具の要約と委譲先の `align` の出力が、どちらも sha を機械可読で名乗るからである。** 動く対象を渡していた頃の経緯は `docs/adr/ADR-implement-verification-delegated-to-worktree.md`、委譲先を道具の木へ入れない理由と却下した形は `docs/adr/ADR-implement-verification-tool-tree.md` が持つ。

**主エージェントがビルドを回さなくなるわけではない**——編集中の速い確認（変更した crate の fmt / clippy / test）は主ツリーで手で回す。道具が回すのは**権威ある一式**である（`cargo doc` と `npm run governance:check` を含む）。

### 3a. 委譲の前に

- **`git status --porcelain` が空であることを確認する。** worktree はコミットから切られるので、**コミットし忘れた変更は検証の対象に入らない**——しかも緑で返る（対象ゼロで自明に green を返す形・#922）。道具はこの形を exit 2 で拒むが、委譲先の木は道具を通らずに切られるので、ここで確かめる
- `git branch --show-current` で現在のブランチを確認し、`main` 上にいる場合は feature ブランチ（`feat/` / `fix/` / `chore/` 等）を作成する（`main` 直コミットは禁止・`.githooks/pre-commit` に弾かれる。`/start-issue` を経ていない単体起動時に該当しやすい）
- このタスクで変更したファイルのみをステージし、conventional commit を作成する（例: `feat:`, `fix:`, `refactor:`）。何を実装し、なぜ実装したかの簡潔な説明を含める
- **`plan.md` の消し込みを同じコミットへ含める**（Step 2 が「その都度 `- [x]`」を求めている。含めないと未コミットの実行記録が溜まり、Step 4 の `workspace/` 撤去がそれを抱えたまま消す対象になる）
- **check スキルはここで主エージェント自身が実行する** — 変更の種類に応じた check スキル（`/symmetric-check`・`/dry-check`・`/race-check`・`/persistence-check`・`/state-check`）を、**`AGENTS.md`「条件別チェック（トリガー → 参照先）」表に従って**実行する（トリガー→検査のマッピングの SSOT はその表。二重管理を避けるためここに再掲しない。**この列挙は写しであり、表と同期している間だけ「出力」の母集団が一致する**——受容の理由は `docs/adr/ADR-implement-step4-report-slot.md`）。ビルドを伴わない読む仕事なので委譲先と競合しない。`/symmetric-check` はコードパス変更・バグ修正でほぼ常に該当。**同じ check が `/start-issue` の計画段階で走っていても、ここで実行する**——対象が計画と実装で別だからである（計画に無い変更は実装中に必ず生じる）。発見事項は修正し、コミットへ含めてから委ねる

### 3b. 委譲へ渡すもの

**まず道具を回す**: `npm run verify:tree -- run --sha <sha> --categories <該当カテゴリ>`。コマンドは `docs/build-commands.md`「変更後の検証チェックリスト」の各カテゴリのフェンスを道具が読む（コマンド文字列はこの SKILL に書かない）。

- **該当の判定は拡張子ではなく、変更が触れるコードパスの意味で行う**（`.claude/rules/src-tauri.md`・#558）——カテゴリ C・D はファイルの種類ではなく変更が何をするかで決まるため、拡張子でマッピングすると一度も到達しない。**E と F は道具が常に回す**ので渡さなくてよい。散文に条件が書かれた単発のコマンド（E の `scripts/lib/**` → `test:powershell` 等）は `--also <npm script>` で足す
- 完走まで分単位で掛かるので、バックグラウンドで回して完了の通知を待つ。**C を要求する巡は、道具の完走を待ってから委譲を起動する**——smoke は Snotra が既に起動していると throw するため（`scripts/lib/SnotraSmoke.psm1`）、木を分けても並走できない。それ以外の巡は並走してよい
- **exit 2 は「検査が走らなかった」であって赤ではない**（未コミットの変更・sha ≠ HEAD・コマンド 0 件・木の失敗）。メッセージに従って前提を直し、回し直す

次に `Agent` を `isolation: "worktree"` で 1 体起動する。**`name` を付ける**——3c の `SendMessage` による再開がそれを宛先にする。次をすべて渡す。

- **アンカーの sha**と、「作業ツリーと食い違ったら `git show <sha>:<path>` が正本である」こと
- **委譲先の最初の操作は `node <本体のルート>/scripts/verify-tree.mjs align --sha <sha>` である**（ルートは主が解決した絶対パスを `/` 区切りで渡す——委譲はコンテキストを継承しない）。harness の木はセッション開始時点のコミットで切られ、アンカーと一致しない。そのコミットには道具が無いことがあるので、`npm run` ではなく本体のスクリプトを絶対パスで呼ぶ。**exit 2 なら止まって報告させる。巡ごとに最初に打たせる**——前巡の変異が巻き戻されていなければ、ここで止まる
- **カテゴリ A〜F は渡さない**——道具が回す。委譲先が自分の木で回すテストは、変異注入の検知を測るためのものに限る
- **レビュー**（`code-reviewer` の観点）。Critical または High の発見事項は修正してから次へ進む
- **変異注入**——検知器が効くことを測り、巻き戻しを**内容ハッシュ**で照合させる（mtime は「変わった」を偽陽性で出す）。**赤の理由が検査の assert であることを出力で確かめさせる**——timeout とモジュール解決の失敗は検知に数えない（道具との並走に加え、委譲先自身のテストの並走でも CPU 競合で timeout の赤が出る・#1154・#1179）。**注入するのはこのエージェントだけである**: 主エージェントは同じ木へ注入しない
- **意図的に分けた構造**を根拠の所在つきで先に渡す（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）
- **⚠️（確信の持てない所見）も返り値の列挙に含めさせる**
- **報告は委譲先の木の中の `.delegate/` へ書かせる**（`align` が出す `delegate_dir`）。**木の外へ書かせない**——木が「変更なし」のまま止まると harness が片づけ、`SendMessage` で再開した委譲先は本体の作業ツリーで動く（#1298）。`.delegate/` はどのコミットにも現れないので、次の巡の checkout とも衝突しない。**報告の名前を `report*.md` にしない**（Write が拒否される）。直列の巡では道具の要約のパスも渡す

**このスキルが `Agent` を起動してよいのは、この1体だけである。** 計画レビューをここで再実行しない。レビュー対象は計画ではなく、コミットした具体的な diff である。

カテゴリ D のうち **`scripts/manual-smoke.ps1` の目視判定はエージェントが完了できない**（対話入力を要する）ため、`-PostToPr` か出力ファイルの貼り付けで人間へ委ねる。一方、キー注入・ウィンドウキャプチャ・ピクセル判定のように決定的な自動検査として実装された部分は実行し、目視項目と一括して「実行不能」にしない。

### 3c. 報告を受けてから

**道具の要約と委譲の報告が両方届くまで、作業ツリーに触らず HEAD を進めない。** どちらもアンカーの sha を名乗るので、届く前に HEAD を進めると「報告の sha == HEAD」が崩れ、その指摘がまだ生きているかの照合が毎回入る（`docs/adr/ADR-implement-verification-delegated-to-worktree.md`）。

- **道具の要約を読む**（パスは道具が標準出力の JSON の `summary` に出す）。`status` と各コマンドの `exit` だけでなく、**`categories_run` とコマンドの一覧を、変更が触れたコードパスと突き合わせる**——緑は、走ったコマンドが変更を見ていることまでは示さない。`warnings` があれば根拠欄に書く
- **並走した巡で道具が赤なら、委譲の報告が届いたあとに同じ `run` を単独で 1 回だけ回し直してから確定する**（委譲先との CPU 競合で timeout の赤が出うる）
- **報告を記録する**: 道具の要約と、委譲先の `.delegate/` の報告を `workspace/` へ写し、次のコミットに含める
- 修正を当てたらコミットし、**道具を同じ形で回し直し、同じエージェントへ新しい sha を `SendMessage` で渡して再実行させる**。**上の「1体だけ」に反しない**——`SendMessage` は起動ではなく再開である。新しく起動しないのは、**自分が出した指摘の解消と、前の巡で ⚠（確信の持てない所見）として残した争点を、同じエージェントが追えるから**である（#934）
- **この Step を出るのは、いま HEAD にある差分が、その差分の内容がトリガーする検査をすべて通ったときである。** 指摘を直したら、直した内容をトリガー判定（`AGENTS.md`「条件別チェック（トリガー → 参照先）」）へ当て直し、3a の check スキル、3b の道具と委譲のうち該当するものを再実行する。**再実行時の母集団は各検査が自分で定めるアンカーのままである**——修正した分だけを切り出さない（`/race-check` の母集団は `--base` 起点の累積差分であり、縮まない）
- **「解消した」の判定は、報告の結論を受け取るのではなく、指摘を見つけた道具で自分で測る**
- 状態でゲートされた挙動（分岐表示・エラー経路・cold path）は build/test が通っても検証済みとは限らない——その状態を実際に発生させて確認する（`docs/development-principles.md` デバッグ節）

5サイクル後も収束しない場合、中止して診断サマリーを書く:
- 試みた内容
- 残存するエラー・指摘
- 根本原因の推定

## Step 4 — 仕上げ

実装差分は Step 3 で既にコミットされている。ここに残るのは、`workspace/` を畳む前の回収と、道具の回し直しと、木の片づけと、その撤去コミットだけである。**この順序で行う**——PR 前ゲート（`.claude/hooks/pre-bash.mjs`）は、道具の要約の sha から HEAD までに `workspace/` の外の変更が無いことを照合し、**その照合に例外は無い**（#1299）。ADR の回収コミットは `workspace/` の外に載るので、道具の最後の実行より後に積むと PR が止まる。

- **`workspace/` を削除する前に、否定の知識を ADR へ回収する**（#593）: `plan.md`・本サイクルの検討に「代替案 B を検討して却下した」判断があれば、削除で失う前に `docs/adr/ADR-<slug>.md` を起こす（形式は `docs/adr/ADR-doc-minimization-cap-enforcement.md` に倣う。**連番を振らない**——slug はテーマが決まった時点で決める・#812）。**トリガーは否定の知識が生じたときだけ** — 自明な実装・一本道の選択では作らない。無ければ何もしない。ADR に書くのは**却下した代替案と、却下の理由**である——採用案の再説明を書かない（採用案はコードと `SPEC.md` が持つ）。**「やらないと決めた作業項目」は代替案の却下ではないので、同じ節の `workspace/` 削除条件が挙げる ADR / issue の 2 択のうち issue 側へ送る**
- **最後の要約から `workspace/` の外が動いたら、道具を回し直す**（ADR を起こした場合など）: `npm run verify:tree -- run --sha HEAD --categories <該当カテゴリ>`。木は warm なので、E と F だけなら数十秒で済む。green でなければ Step 3 へ戻る
- **木を片づける**: `npm run verify:tree -- remove --delegate-tree <align が出した worktree>`。道具の木と委譲先の木（`.delegate/` だけが残るもの）とそのブランチを消す。**要約は残る**（PR 前ゲートが読む）。委譲先の木は `.delegate/` で意図的に dirty に保ってあるので、`npm run clean:worktrees` は `--force` なしでは拾わない。**exit 1 で止まったら出力を読む**——`.delegate/` 以外の変更が残っていれば中身を確かめ、「ロックされている」なら委譲先がまだ動いているので停止を待って打ち直し（ロックは `--force` 1 回では外れない）、ディレクトリだけが残ったなら `git worktree list` で他のセッションの `agent-*` が無いことを確かめてから `npm run clean:worktrees -- --force` で消す（`--force` は dirty な木をすべて消す）
- `workspace/` ディレクトリが存在する場合、**`plan.md` の全項目が `- [x]` であることを確認してから**削除してステージに含める（`/start-issue` の引き継ぎバッファは実装完了で役目を終える）。未チェックの項目が残っているなら削除しない——完了させるか、やらないと決めた項目は計画から外して理由を ADR か issue へ記録する。**未チェックを残したままの削除は、PR 前ゲート（PreToolUse hook）の視界から計画を消す**
- **削除より先に `plan.md` の最終状態をコミットする。** 未コミットの実行記録（測定値・変異注入のログ・レビュー対応）は削除で失われ、**git 履歴から戻せるのはコミット済みの版だけである**。Step 2・3a のとおり消し込みをフェーズのコミットへ含めていれば、ここで残るのは最後の巡の分だけで済む。`git rm -r workspace/` は独立したコミットにする（squash マージで畳まれるので運用コストは無い）
- **`git rm` が `error: … has local modifications` で止まったら、それは保護であって障害ではない。** 次を守る（#934・経緯は PR #958）:
  - **まず何が未コミットかを見て、順序が逆であることを疑う**
  - **`-f` を付けない。** git 自身が `use … -f to force removal` と勧めてきても従わない
  - **`checkout` 系（`git checkout` / `git checkout-index` / `git restore`）で「戻す」をしない。** `-f` と同じく未コミットの記録を破棄する
  - ステージだけ取り消すなら `git reset` で止め、**作業ツリーへ触るコマンドを続けて打たない**
