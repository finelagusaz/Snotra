自律的にフルサイクル開発を行う。実装の判断は、コードとドキュメントから自分で行う。要求の判断が要るときだけ確認する。着手時に、何をするかを 1 行で述べる。Step の切り替わり・発見・方針転換のたびにも、短く報せる（読者は tool の出力を見ていない）。この条項は、モデルの癖に合わせた調整である。対象は Fable 5.1 以降に見られる、tool 呼び出しの合間の報せが減る癖である。Opus 5.5 も同じ向きである（#1230）。最後の報告の形は「出力」節が定める。

タスク: $ARGUMENTS

## Step 1 — 入口判定

このスキルは計画を所有しない。動くのは、「未確定がゼロで、人間が承認済みの計画がある」か「計画が要らない」かのどちらかのときだけである。

### 1a. workspace/plan.md の由来を確かめる

`/start-issue` は中断（セッション断・放棄）しても `workspace/` を残す。そのため、別タスクの残骸や、承認前で止まった計画が残っていることがある。`workspace/plan.md` があれば、次の 3 つを確かめる（3 つは別々の性質である）。

- 同一性 — `plan.md` とコミットメッセージ（あれば）の issue 番号・目的が、与えられたタスクと噛み合う。`/implement` は単独で起動するのが日常の経路である。このブランチの issue が、今のタスクとは限らない
- 未確定ゼロ（機械判定）— `## 未確定（実装前に潰す）` で始まる見出し行が存在する。かつ、その節の中（次の同レベル見出しまで）に `- [ ]` が 1 つも無い。数えるのは節の中に限る（フェーズ配下の作業項目は、着手前ならすべて `- [ ]` である。ファイル全体で数えると、常に不成立になる）。見出しが存在することも確かめる。これを落とすと、欄を書かなかった計画が件数ゼロとして通り、判定が fail-open になる（#821）
- 人間承認（機械判定）— `## 人間レビュー` 見出しが存在し、その節に `- [x] 承認済み — <日付> / 問い: "<承認を求めた問いの逐語引用>" / 回答: "<ユーザー発言の逐語引用>"` が 1 件ある。問いと回答は、会話へ逆にたどれる逐語引用にする。エージェント自身の判断や、コミット済みであることを、承認の代わりにしない

既定は fail-closed である。確かめられなければ、あるものとして扱わない。古い計画や未レビューの計画を有効と誤ると、違うものを実装する。その誤りは検証を全部通り、コミットまで気づけない。無効と誤っても、聞き直すだけで済む。

### 1b. 分岐（行き先を決めるのはこの表だけである）

| 状況 | 動き |
|---|---|
| 3 つすべて立つ | それを実装の指示として読み、Step 2 へ進む（`/start-issue`「出力」の引き渡し契約）。調査はやり直さない |
| 同一性は立つが、未確定ゼロか人間承認が立たない | 計画は在るが、引き渡し条件を満たさない。止める（1c-B）。コミット済みかどうかは関係しない（コミットは、計画内容の証拠にも人間承認の証拠にもならない） |
| main から到達できる／別ブランチのもの／このブランチ上でも与えられたタスクと噛み合わない＝別タスクの残骸 | 消さない。何の残骸かを報告し、削除か退避かをユーザーに確認する。そのうえで「計画が無い」ものとして扱い、下の「計画が無く…」の 2 行のどちらかへ進む |
| 由来の判断がつかない | 止める（1c-C） |
| 計画が無く、計画を書かずに直せる | 下の調査を行ってから Step 2 へ進む |
| 計画が無く、計画が要ると判明した（実装の途中で判明した場合も同じ） | 止める（1c-A） |

計画なしの経路でだけ行う調査:

- `SPEC.md` と関連する `CLAUDE.md` を読み、意図とアーキテクチャを理解する
- `$ARGUMENTS` からエントリポイントと関連モジュールを特定する
- 要求された機能と重複する既存コードを検索する
- 3層モデルの制約（意図は `SPEC.md`、実装はコード）に留意する
- 要求の曖昧さを判定する — 「何を作るか」が、コードとドキュメントから一意に決まらないことがある（UI の見た目、対象範囲、既存動作を変えるか追加するか等）。その場合は、最も影響の大きい 1〜2 点に絞って質問し、回答を得てから進む

計画が要るサイン（網羅ではなく、徴候である）:

- 複数ファイルにまたがり、変更の順序に依存する
- 新しい状態・プロセス・ウィンドウ・永続形式を導入する
- `SPEC.md` に書かれた挙動を変える
- どう直すかが一つに決まらず、代替案の比較が要る

### 1c. 止まったときの引き渡し

実装を始めない。停止は 3 種あり、それぞれ渡し方が違う:

- 1c-A（計画が無く、要ると判明した）: 何が計画を要求したかを報告する。issue 本文の草案を出し、起票を打診する。承認されたら `gh issue create` を実行し、`/start-issue <N>` へ渡す
- 1c-B（計画はあるが引き渡し条件を満たさない）: 新規 issue は起票しない。未確定が残るなら、`/start-issue`「5a. check スキルによる計画検証」へ戻す。人間承認が無いなら、`/start-issue`「5c. 人間の注釈と承認」へ戻す。`/implement` が未確定を潰したり、承認を自分で記録したりしてはならない
- 1c-C（由来の判断がつかない）: 何を確かめられなかったかを示して問う。答えを得るまで進まない

## Step 2 — 実装

- 純粋核（crate を問わず、egui/Win32 に依存せずテストできるロジック）を追加・変更するときは、テストが主張する性質を、その性質をまだ持たない実装に当てて実際に落とす（Red）。それから通す（Green）。既存コードを直すなら、現状のコードがその実装である。新しい型・関数を導入するなら、シグネチャだけ置き、中身を `todo!()` か no-op にする（テストだけ先に書いても、得られるのはコンパイルエラーである。それは実装に当てて落ちたことにならない・#745）。対象は `snotra-core` に限らない。`src-tauri` 等の純粋モジュール（`lifecycle.rs`・`search_state.rs` 等）も含む（`view`/Win32 に依存するものはテストの前提にしない）
- 計画がある場合は、計画に沿って変更を行う
- plan.md のチェックリストを消し込みながら進める。完了した項目は、その都度 `- [x]` へ更新し、フェーズのコミットに含める（チェック状態を git に残し、中断・再開時に「どこまでやったか」を確かめられるようにするため）。実装中に判明した計画外の作業は、その場で `- [ ]` として plan.md へ追記する（途中で見つけたタスクも、PR 前ゲートに乗せるため）
- 新しい純ロジックには、それが属する crate に `#[cfg(test)]` ユニットテストを追加する
- 既存テストを改名・転用するときは、元のテストが証明していた不変条件を孤立させない。改名では、内容だけでなく「どの命題を証明していたか」も追跡する。転用で失われる不変条件は、別テストで補う
- ソースファイル（`.rs`）を新規追加・削除したら、同じ変更で、該当 `CLAUDE.md` のモジュール構成節の索引（ファイル名）を更新する（責務の散文は各ファイルの `//!` が正本である・#562）。索引漏れは `governance:check` が捕捉する。ただし、対象は `MODULE_INDEX_CRATES` に載っている crate に限る。また、同名のファイルが同じ節で既に言及されていれば、緑のまま通る。適用範囲と死角の正本は、`scripts/governance/checks/G-module-index.mjs` と `ADR-module-index-reverse-scope` である
- `SPEC.md` に記載された挙動に影響する変更の場合、`SPEC.md` も更新する（`AGENTS.md`「3層分担」に従う）

## Step 3 — 検証とレビュー（委譲・最大5サイクル）

カテゴリ A〜F の検証も、レビューも、主エージェントの作業ツリーでは行わない。コミットを 1 つ作り、その sha に対して行う。権威ある A〜F は、ツール（`npm run verify:tree`）がツールの worktree で回す。レビューと変異注入は、worktree のサブエージェントが自分の worktree で行う。

この形の要点は、対象を不変オブジェクトにすることである。委譲した検査が対象を読む時刻は、制御できない（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）。だから、動かないものを渡す。検証とレビューを別の worktree で走らせても、2 つの報告は別の版へ向かない。ツールの要約と委譲先の `align` の出力が、どちらも sha を機械可読な形で示すからである。動く対象を渡していた頃の経緯は、`docs/adr/ADR-implement-verification-delegated-to-worktree.md` にある。委譲先をツールの worktree へ入れない理由と、却下した形は、`docs/adr/ADR-implement-verification-tool-tree.md` にある。

主エージェントがビルドを回さなくなるわけではない。編集中の速い確認（変更した crate の fmt / clippy / test）は、主ツリーで手で回す。ツールが回すのは、権威ある一式である（`cargo doc` と `npm run governance:check` を含む）。

### 3a. 委譲の前に

- `git status --porcelain` が空であることを確認する。worktree はコミットから切られるので、コミットし忘れた変更は検証の対象に入らない。しかも、結果は緑で返る（対象ゼロで自明に green を返す形・#922）。ツールはこの形を exit 2 で拒む。しかし、委譲先の worktree はツールを通らずに切られるので、ここで確かめる
- `git branch --show-current` で現在のブランチを確認する。`main` 上にいる場合は、feature ブランチ（`feat/` / `fix/` / `chore/` 等）を作成する（`main` への直コミットは禁止であり、`.githooks/pre-commit` に弾かれる。`/start-issue` を経ずに単体で起動したときに起きやすい）
- このタスクで変更したファイルだけをステージし、conventional commit を作成する（例: `feat:`, `fix:`, `refactor:`）。何を実装したか、なぜ実装したかの簡潔な説明を含める
- `plan.md` の消し込みを、同じコミットへ含める（Step 2 が「その都度 `- [x]`」を求めている。含めないと、未コミットの実行記録が溜まる。すると、Step 4 の `workspace/` 撤去が、それを抱えたまま消すことになる）
- check スキルは、ここで主エージェント自身が実行する。変更の種類に応じた check スキル（`/symmetric-check`・`/dry-check`・`/race-check`・`/persistence-check`・`/state-check`）を、`AGENTS.md`「条件別チェック（トリガー → 参照先）」表に従って実行する。トリガーから検査への対応の SSOT は、その表である（二重管理を避けるため、ここに再掲しない）。この列挙は写しである。表と同期している間だけ、「出力」の母集団が一致する（これを受け入れた理由は `docs/adr/ADR-implement-step4-report-slot.md`）。ビルドを伴わない読む仕事なので、委譲先と競合しない。`/symmetric-check` は、コードパスの変更・バグ修正でほぼ常に該当する。同じ check が `/start-issue` の計画段階で走っていても、ここで実行する。対象が、計画と実装で別だからである（計画に無い変更は、実装中に必ず生じる）。発見事項は修正し、コミットへ含めてから委ねる

### 3b. 委譲へ渡すもの

まずツールを回す: `npm run verify:tree -- run --sha <sha> --categories <該当カテゴリ>`。各カテゴリのコマンドは、ツールが `docs/build-commands.md`「変更後の検証チェックリスト」のフェンスから読む（コマンド文字列はこの SKILL に書かない）。

- 該当するかの判定は、拡張子ではなく、変更が触れるコードパスの意味で行う（`.claude/rules/src-tauri.md`・#558）。カテゴリ C・D は、ファイルの種類ではなく、変更が何をするかで決まる。拡張子で対応づけると、一度も該当しない。C に当たる変更では、smoke を CI に任せず、ここでローカルに回す。修正のたびに、結果をその場で見るためである（修正のループを持たない `/deps-update` は、CI に任せる）。E と F はツールが常に回すので、渡さなくてよい。散文に条件が書かれた単発のコマンド（E の `scripts/lib/**` → `test:powershell` 等）は、`--also <npm script>` で足す
- 完走まで分単位で掛かる。バックグラウンドで回し、完了の通知を待つ。C を要求するラウンドでは、ツールの完走を待ってから委譲を起動する。smoke は、Snotra が既に起動していると throw する（`scripts/lib/SnotraSmoke.psm1`）。そのため、worktree を分けても並走できない。それ以外のラウンドは並走してよい
- exit 2 は「検査が走らなかった」であり、赤ではない（未コミットの変更・sha ≠ HEAD・コマンド 0 件・worktree の失敗）。メッセージに従って前提を直し、回し直す

次に、`Agent` を `isolation: "worktree"` で 1 体起動する。`name` を付ける（3c の `SendMessage` による再開が、それを宛先にする）。次をすべて渡す。

- アンカーの sha。あわせて、「作業ツリーと食い違ったら `git show <sha>:<path>` が正本である」こと
- 委譲先の最初の操作は `node <本体のルート>/scripts/verify-tree.mjs align --sha <sha>` である。ルートは、主が解決した絶対パスを `/` 区切りで渡す（委譲はコンテキストを継承しない）。harness の worktree はセッション開始時点のコミットで切られるので、アンカーと一致しない。そのコミットにはツールが無いことがある。そのため、`npm run` ではなく、本体のスクリプトを絶対パスで呼ぶ。exit 2 なら、止まって報告させる。これは、ラウンドごとに最初に打たせる（前のラウンドの変異が巻き戻されていなければ、ここで止まる）
- git は `cd … &&` や `;` で繋がず、自分の worktree の cwd で単発に打たせる（worktree の隔離は、複合形を拒む。複合形では、worktree の中に留まるかを検証できないため・#1324）
- カテゴリ A〜F は渡さない（ツールが回す）。委譲先が自分の worktree で回すテストは、変異注入の検知を測るためのものに限る
- レビュー（`code-reviewer` の観点）。`.claude/agents/code-reviewer.md` を全文読ませる（観点の名前だけを渡すと、委譲先は手元の一般的なレビュー観点で代用する。すると、訳語の点検のような、このリポジトリ固有の項目が黙って落ちる）。Critical または High の発見事項は、修正してから次へ進む
- 変異注入。検知器が効くことを測らせ、巻き戻しを内容ハッシュで照合させる（mtime は「変わった」を偽陽性で出す）。赤の理由が検査の assert であることを、出力で確かめさせる。timeout とモジュール解決の失敗は、検知に数えない（ツールとの並走でも、委譲先自身の並走でも、CPU 競合で timeout の赤が出る・#1154・#1179）。注入するのは、このエージェントだけである。主エージェントは、同じ worktree へ注入しない。timeout を掛けて回すなら、後始末は `.claude/rules/safety-nets.md`「フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる」に従わせる（#1352）
- 意図的に分けた構造を、根拠の所在つきで先に渡す（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）
- ⚠️（確信の持てない所見）も、返り値の列挙に含めさせる
- 報告は、委譲先の worktree の中の `.delegate/` へ書かせる（`align` が出す `delegate_dir`）。worktree の外へ書かせない。worktree が「変更なし」のまま止まると、harness がそれを片づける。すると、`SendMessage` で再開した委譲先は、本体の作業ツリーで動く（#1298）。`.delegate/` はどのコミットにも現れないので、次のラウンドの checkout とも衝突しない。報告の名前を `report*.md` にしない（Write が拒否される）。直列のラウンドでは、ツールの要約のパスも渡す

このスキルが `Agent` を起動してよいのは、この1体だけである。計画レビューを、ここで再実行しない。レビュー対象は計画ではなく、コミットした具体的な diff である。

カテゴリ D のうち、`scripts/manual-smoke.ps1` の目視判定は、エージェントが完了できない（対話入力を要する）。そのため、`-PostToPr` か出力ファイルの貼り付けで、人間へ委ねる。一方、キー注入・ウィンドウキャプチャ・ピクセル判定のように、決定的な自動検査として実装された部分は実行する。目視項目と一括して「実行不能」にしない。

### 3c. 報告を受けてから

ツールの要約と委譲の報告が両方届くまで、作業ツリーに触らず、HEAD を進めない。どちらも、アンカーの sha を示す。届く前に HEAD を進めると、「報告の sha == HEAD」が崩れる。すると、その指摘がまだ生きているかの照合が、毎回入る（`docs/adr/ADR-implement-verification-delegated-to-worktree.md`）。

- ツールの判定の内訳を読む。標準出力の JSON が、要約ファイルの `status`・`categories_run`・各コマンドの `exit`・`warnings` をそのまま載せる（ファイルのパスは、同じ JSON の `summary`）。`status` と各コマンドの `exit` だけでなく、`categories_run` とコマンドの一覧を、変更が触れたコードパスと突き合わせる（緑は、走ったコマンドが変更を見ていることまでは示さない）。`warnings` があれば、根拠欄に書く
- 並走したラウンドでツールが赤なら、委譲の報告が届いたあとに、同じ `run` を単独で 1 回だけ回し直してから確定する（委譲先との CPU 競合で、timeout の赤が出うる）
- ラウンドの結果を、`plan.md` の消し込みへ 1 行で書く。書くのは、アンカーの sha・ツールの判定・指摘の件数・生き残った変異の数である。報告の本文は写さない（`workspace/` へ写しても、撤去コミットで消える。本文は Step 4 の回収が `.delegate/` から読む・#1317）
- 修正を当てたら、コミットする。ツールを同じ形で回し直す。同じエージェントへ新しい sha を `SendMessage` で渡し、再実行させる。これは上の「1体だけ」に反しない（`SendMessage` は起動ではなく、再開である）。新しく起動しないのは、同じエージェントなら、自分が出した指摘の解消と、前のラウンドで ⚠（確信の持てない所見）として残した争点を追えるからである（#934）
- この Step を出るのは、いま HEAD にある差分が、その差分の内容がトリガーする検査をすべて通ったときである。指摘を直したら、直した内容をトリガー判定（`AGENTS.md`「条件別チェック（トリガー → 参照先）」）へ当て直す。そして、3a の check スキルと、3b のツールと委譲のうち、該当するものを再実行する。再実行時の母集団は、各検査が自分で定めるアンカーのままである。修正した分だけを切り出さない（`/race-check` の母集団は `--base` 起点の累積差分であり、縮まない）
- 「解消した」の判定は、報告の結論を受け取って済ませない。指摘を見つけたツールで、自分で測る
- 状態でゲートされた挙動（分岐表示・エラー経路・cold path）は、build/test が通っても検証済みとは限らない。その状態を実際に発生させて確認する（`docs/development-principles.md`「確かめるときの落とし穴」）

5サイクル後も収束しない場合は、中止して診断サマリーを書く:
- 試みた内容
- 残存するエラー・指摘
- 根本原因の推定

## Step 4 — 仕上げ

実装差分は、Step 3 で既にコミットされている。ここに残るのは、`workspace/` を畳む前の回収と、ツールの回し直しと、worktree の片づけと、その撤去コミットだけである。これらは、この順序で行う。PR 前ゲート（`.claude/hooks/pre-bash.mjs`）は、ツールの要約の sha から HEAD までに、`workspace/` の外の変更が無いことを照合する。その照合に例外は無い（#1299）。ADR の回収コミットは `workspace/` の外に載る。そのため、ツールの最後の実行より後に積むと、PR が止まる。

- `workspace/` を削除する前に、否定の知識を ADR へ回収する（#593）。`plan.md`・委譲先の `.delegate/` の報告・本サイクルの検討に「代替案 B を検討して却下した」判断があれば、削除で失う前に `docs/adr/ADR-<slug>.md` を起こす。形式は `docs/adr/ADR-doc-minimization-cap-enforcement.md` に倣う。連番は振らない（slug はテーマが決まった時点で決める・#812）。起こすのは、否定の知識が生じたときだけである。自明な実装・一本道の選択では作らない。無ければ何もしない。ADR に書くのは、却下した代替案と、却下の理由である。採用案の再説明は書かない（採用案はコードと `SPEC.md` が持つ）。「やらないと決めた作業項目」は、代替案の却下ではない。そのため、同じ節の `workspace/` 削除条件が挙げる ADR / issue の 2 択のうち、issue 側へ送る
- 最後の要約から `workspace/` の外が動いたら（ADR を起こした場合など）、ツールを回し直す: `npm run verify:tree -- run --sha HEAD --categories <該当カテゴリ>`。worktree は warm なので、E と F だけなら数十秒で済む。green でなければ、Step 3 へ戻る
- worktree を片づける: `npm run verify:tree -- remove --delegate-tree <align が出した worktree>`。これは、ツールの worktree と、委譲先の worktree（`.delegate/` だけが残るもの）と、そのブランチを消す。要約は残る（PR 前ゲートが読む。マージの後は `merge:pr` が消す）。委譲先の worktree は、`.delegate/` で意図的に dirty に保ってある。そのため、`npm run clean:worktrees` は `--force` なしでは拾わない。exit 1 で止まったら、出力を読む。`.delegate/` 以外の変更が残っていれば、中身を確かめる。「ロックされている」なら、委譲先がまだ動いている。停止を待って打ち直す（ロックは `--force` 1 回では外れない）。ディレクトリだけが残ったなら、`git worktree list` で他のセッションの `agent-*` が無いことを確かめる。それから、`npm run clean:worktrees -- --force` で消す（`--force` は dirty な worktree をすべて消す）
- `workspace/` ディレクトリが存在する場合は、`plan.md` の全項目が `- [x]` であることを確認してから削除し、ステージに含める（`/start-issue` の引き継ぎバッファは、実装の完了で役目を終える）。未チェックの項目が残っているなら、削除しない。完了させるか、やらないと決めた項目を計画から外し、理由を ADR か issue へ記録する。未チェックを残したまま削除すると、PR 前ゲート（PreToolUse hook）が計画を見られなくなる
- 削除より先に、`plan.md` の最終状態をコミットする。未コミットの実行記録（測定値・変異注入のログ・レビュー対応）は、削除で失われる。git 履歴から戻せるのは、コミット済みの版だけである。Step 2・3a のとおり消し込みをフェーズのコミットへ含めていれば、ここで残るのは最後のラウンドの分だけで済む。`git rm -r workspace/` は、独立したコミットにする（squash マージで 1 つに畳まれるので、運用の手間は増えない）
- `git rm` が `error: … has local modifications` で止まったら、それは保護であり、障害ではない。次を守る（#934・経緯は PR #958）:
  - まず、何が未コミットかを見る。順序が逆になっていないかを疑う
  - `-f` を付けない。git 自身が `use … -f to force removal` と勧めてきても、従わない
  - `checkout` 系（`git checkout` / `git checkout-index` / `git restore`）で「戻す」をしない。これらは `-f` と同じく、未コミットの記録を破棄する
  - ステージだけ取り消すなら、`git reset` で止める。作業ツリーへ触るコマンドを、続けて打たない

## 出力

次の形で報告する。到達しなかった Step の欄には、「未到達」と書く（生成物が存在しないので、埋めれば捏造になる）。検証の母集団は、`docs/build-commands.md`「変更後の検証チェックリスト」のカテゴリ A〜F 全件である。レビューの母集団は、3a の check スキル全件と 3b の委譲である。

```markdown
## 実装結果

- 入口: 計画あり — <同一性/未確定ゼロ/人間承認の根拠> | 計画なし — <理由>
- 停止: なし | <Step> で停止 — <1c-A/B/C の引き渡し先、または診断サマリー>

### 検証（カテゴリ A〜F 全件）

| カテゴリ | 実行 / 該当なし / 実行不能 | 根拠（実行ならツールの要約の exit code と、要約が示す sha） |
|---|---|---|

### レビュー（3a の check スキル全件 + 3b の委譲）

| 検査 | 実施（ラウンド数・件数・修正の有無） / 該当なし / 未実施 | 根拠 |
|---|---|---|

### テスト

- <テスト名> — <検証した不変条件>（追加・更新が無ければ「なし — <理由>」）

### コミット

- <hash> <message>
```

- 「実行不能」に入れてよいのは、実行者がエージェントであること、または実行環境がどこであるかに由来するものだけである。具体的には、`scripts/manual-smoke.ps1` が要求する対話的な目視判定と、実行環境が Windows でないときの Windows 専用コマンド（`docs/build-commands.md`「Windows のみ実行可能（`windows` クレートや Win32 API・実行バイナリに依存）」）に限る。人間へ引き渡す項目を、根拠欄に書く
- どの値であれ、時間・手間を理由に選んではならない。レビューでは、それは「未実施（理由: 省いた）」である。検証では、そもそも Step 3 を終えていない（停止側に居り、この表を書く地点に無い）
- レビューは、1 検査 1 行とする。Step 3 を複数周した検査は、ラウンド数を書く（出口条件により、2 周以上は正常に起きる）
- レビューの母集団は、3a の列挙と一致する。`AGENTS.md`「条件別チェック（トリガー → 参照先）」表へ check スキルを足すときは、3a の列挙も同じ変更で直す
- 委譲の行には、アンカーにした sha と変異注入の結果を書く（沈黙は「実施しなかった」と区別できない。委譲先が報告を返さないことは起こりうる）
