自律的にフルサイクル開発を行う。実装判断はコードとドキュメントから自律的に行い、要求判断が必要な場合のみ確認する。**作業中の実況は、発見があったときと方針を変えたときに限る**——これは実況に掛かる制限であって、「出力」節が求める報告を免除しない。

タスク: $ARGUMENTS

## Step 1 — 入口判定

このスキルは**計画を所有しない**。動くのは「**未確定がゼロで、人間が承認済みの計画**がある」か「計画が要らない」かのどちらかのときだけである。

### 1a. workspace/plan.md の由来を確かめる

`/start-issue` は中断（セッション断・放棄）しても `workspace/` を残すため、別タスクの残骸や、承認前で止まった計画が残っていることがある。`workspace/plan.md` があれば、**別々の性質である次の 3 つ**を確かめる。

- **同一性** — `plan.md` とコミットメッセージ（あれば）の issue 番号・目的が**与えられたタスク**と噛み合う。`/implement` は単独起動が日常的な経路であり、**このブランチの issue が今のタスクとは限らない**
- **未確定ゼロ**（機械判定）— `## 未確定（実装前に潰す）` で始まる見出し行が**存在し**、かつ**その節の中**（次の同レベル見出しまで）に `- [ ]` が 1 つも無い。**節の中に限る**——フェーズ配下の作業項目は着手前なら当然すべて `- [ ]` であり、ファイル全体で数えると常に不成立になる。**見出しの存在を確かめる側も落とせない**——欄を書かなかった計画（＝自覚なき書き手の産物）が件数ゼロで素通りし、判定が fail-open へ退化する（#821）
- **人間承認**（機械判定）— `## 人間レビュー` 見出しが存在し、その節に `- [x] 承認済み — <日付> / 問い: "<承認を求めた問いの逐語引用>" / 回答: "<ユーザー発言の逐語引用>"` が 1 件ある。問いと回答は会話へ逆引きできる逐語引用にする。エージェント自身の判断や、コミット済みであることを承認の代用にしない

**既定は fail-closed である**——確かめられなければ、あるものとして扱わない。倒す向きに非対称があるためで、古い計画や未レビューの計画を有効と誤れば**違うものを実装し**、検証を全部通ってコミットまで気づけない。逆に有効な計画を無効と誤っても、止まって聞き直すだけで回復できる。

### 1b. 分岐（行き先を決めるのはこの表だけである）

| 状況 | 動き |
|---|---|
| 3 つすべて立つ | それを実装の指示として読み Step 2 へ（`/start-issue`「出力」の引き渡し契約）。調査はやり直さない |
| 同一性は立つが、未確定ゼロか人間承認が立たない | 計画は在るが引き渡し条件を満たさない。**止める**（1c-B）。コミット済みかどうかは無関係——コミットは計画内容または人間承認の証拠ではない |
| main から到達できる／別ブランチのもの／このブランチ上でも与えられたタスクと噛み合わない＝**別タスクの残骸** | **消さずに**何の残骸かを報告し、削除か退避かをユーザーに確認したうえで、「計画が無い」ものとして下の「計画が無く…」の 2 行のどちらかへ進む |
| 由来の判断がつかない | **止める**（1c-C） |
| 計画が無く、計画を書かずに直せる | 下の調査を行ってから Step 2 へ |
| 計画が無く、計画が要ると判明した（**実装の途中で判明した場合も同じ**） | **止める**（1c-A） |

計画なしの経路でだけ行う調査:

- `SPEC.md` と関連する `CLAUDE.md` を読み、意図とアーキテクチャを理解する
- `$ARGUMENTS` からエントリポイントと関連モジュールを特定する
- 要求された機能と重複する既存コードを検索する
- 3層モデルの制約（意図は `SPEC.md`、実装はコード）に留意する
- **要求の曖昧さを判定する** — 「何を作るか」がコードとドキュメントから一意に決まらない場合（UI の見た目、対象範囲、既存動作を変えるか追加するか等）、最も影響の大きい 1〜2 点に絞って質問し、回答を得てから進む

**計画が要るサイン**（網羅ではなく徴候である）:

- 複数ファイルにまたがり、変更の順序に依存する
- 新しい状態・プロセス・ウィンドウ・永続形式を導入する
- `SPEC.md` に書かれた挙動を変える
- どう直すかが一つに決まらず、代替案の比較が要る

### 1c. 止まったときの引き渡し

**実装を始めない。** 停止は 3 種で、それぞれ渡し方が違う:

- **1c-A（計画が無く、要ると判明した）**: 何が計画を要求したかを報告し、**issue 本文の草案を出して起票を打診する**。承認されたら `gh issue create` を実行し、`/start-issue <N>` へ渡す
- **1c-B（計画はあるが引き渡し条件を満たさない）**: **新規 issue は起票しない。** 未確定が残るなら `/start-issue`「5a. check スキルによる計画検証」へ、人間承認が無いなら `/start-issue`「5c. 人間の注釈と承認」へ戻す。`/implement` が未確定を潰したり、承認を自己記録したりしてはならない
- **1c-C（由来の判断がつかない）**: 何を確かめられなかったかを示して問う。答えを得るまで進まない

## Step 2 — 実装

- **純粋核（crate を問わず egui/Win32 非依存でテスト可能なロジック）の追加・変更: テストが主張する性質を、その性質をまだ持たない実装に当てて実際に落としてから（Red）通す（Green）**。既存コードを直すなら、現状のコードがその実装である。新しい型・関数を導入するなら、シグネチャだけ置いて中身を `todo!()` か no-op にする——テストだけ先に書いても得られるのはコンパイルエラーであり、**実装に当てて落ちたことにならない**（#745 実測）。`snotra-core` に限らず `src-tauri` 等の純粋モジュール（`lifecycle.rs`・`search_state.rs` 等）も対象（`view`/Win32 依存はテスト前提にしない）
- 計画がある場合は、計画に沿って変更を行う
- **plan.md のチェックリストを消し込みながら進める**: 完了した項目はその都度 `- [x]` へ更新し、フェーズのコミットに含める（チェック状態を git に残し、中断・再開時の「どこまでやったか」を接地させる）。実装中に判明した計画外の作業は、その場で `- [ ]` として plan.md へ追記する——途中発見のタスクも PR 前ゲートに乗せる
- 新しい純ロジックには、それが属する crate に `#[cfg(test)]` ユニットテストを追加する
- **既存テストを改名・転用するとき、元のテストが証明していた不変条件を孤立させない**: 改名は内容ではなく「どの命題を証明していたか」も追跡する。転用で失われる不変条件は別テストで補う
- **ソースファイル（`.rs`）を新規追加・削除したら、同じ変更で該当 `CLAUDE.md` のモジュール構成節の索引（ファイル名）を更新する**（責務散文は各ファイルの `//!` が正本・#562。索引漏れは `governance:check` が捕捉するが PR まで漏らさない）
- `SPEC.md` に記載された挙動に影響する変更の場合、`SPEC.md` も更新する（`AGENTS.md`「3層分担」に従う）

## Step 3 — 検証（最大5サイクル）

`docs/build-commands.md`「変更後の検証チェックリスト」を SSOT として、該当するカテゴリ A〜F をすべて実行する。失敗した場合、修正して失敗したステップから再実行する。**該当の判定は拡張子ではなく、変更が触れるコードパスの意味で行う**（`.claude/rules/src-tauri.md`・#558）——カテゴリ C・D はファイルの種類ではなく変更が何をするかで決まるため、拡張子で写像すると一度も到達しない。カテゴリ D のうち **`scripts/manual-smoke.ps1` の目視判定はエージェントが完了できない**（対話入力を要する）ため、`-PostToPr` か出力ファイルの貼り付けで人間へ委ねる。一方、キー注入・窓キャプチャ・ピクセル判定のように決定的な自動検査として実装された部分はエージェントが実行し、目視項目と一括して「実行不能」にしない。

- カテゴリ A（Rust 変更）の clippy・`snotra-core` のテストも SSOT 上「必須」（最初の失敗で停止するチェーン実行を推奨）
- **ソースファイルを追加/削除した場合、カテゴリ F（`npm run governance:check`）も実行する**（モジュール索引・参照・スキル表の整合。#629/#630 で索引更新漏れが CI まで再発した）。**この行はカテゴリ F の発火条件を狭めない**——発火条件の SSOT は `docs/build-commands.md`「F. ガバナンス文書（`*.md`・`.claude/rules/`・`.claude/skills/`・workflow）を変更した場合」の見出しであり、`*.md` の編集だけでも該当する
- 状態でゲートされた挙動（分岐表示・エラー経路・cold path）は build/test が通っても検証済みとは限らない——その状態を実際に発生させて確認する（`docs/development-principles.md` デバッグ節）
- 具体的なコマンド文字列は `docs/build-commands.md` を参照（二重メンテを避けるためこの SKILL に書かない）

5サイクル後もエラーが残る場合、中止して診断サマリーを書く:
- 試みた内容
- 残存するエラー
- 根本原因の推定

## Step 4 — レビュー

**この Step を出るのは、いま手元にある差分が、その差分の内容がトリガーする検査をすべて通ったときである。** 指摘を直したら、直した内容をトリガー判定（`AGENTS.md`「条件別チェック（トリガー → 参照先）」）へ当て直し、4a・4b・Step 3 のうち該当するものを再実行する。**再実行時の母集団は各検査が自分で定めるアンカーのままである**——修正した分だけを切り出さない（`/race-check` の母集団は `--base` 起点の累積差分であり、縮まない）。**Step 3 の 5 サイクルは、この往復をまたいで共有する予算である。** 尽きたら診断サマリーを書いて止まる。

### 4a. check スキルの実行

変更の種類に応じた check スキル（`/symmetric-check`・`/dry-check`・`/race-check`・`/persistence-check`・`/state-check`）を、**`AGENTS.md`「条件別チェック（トリガー → 参照先）」表に従って**実行する（トリガー→検査の写像の SSOT はその表。二重管理を避けるためここに再掲しない）。`/symmetric-check` はコードパス変更・バグ修正でほぼ常に該当。発見事項があれば修正してから 4b に進む。**同じ check が `/start-issue` の計画段階で走っていても、ここで実行する**——対象が計画と実装で別だからである（計画に無い変更は実装中に必ず生じる）。

### 4b. code-reviewer エージェント

`code-reviewer` エージェントを変更に対して実行する。Critical または High の発見事項は修正してから次に進む。

**このスキルが `Agent` を起動してよいのは、この1種だけである。** 計画レビューをここで再実行しない。レビュー対象は計画ではなく、テスト後の具体的なdiffである。

**指摘へ修正（fix-forward）を当てた後の 2 巡目は、新しく起動せず同じエージェントを `SendMessage` で継続する**（`AGENTS.md`「条件別チェック（トリガー → 参照先）」表の「レビュー指摘へ修正（fix-forward）を当てた」行が要求する再実行の実体）。**上の「1体だけ」に反しない**——`SendMessage` は起動ではなく再開である。継続する利点は 2 つで、(1) **自分が出した指摘の解消をそのエージェント自身が検算でき**、(2) round 1 で ⚠（確信の持てない所見）として残した争点を追える（#934 で実測: 2 巡目が ⚠ 1 件を独立検証して真と決着させ、修正周辺の所見を別に 7 件挙げた）。

## Step 5 — コミット

- **`git branch --show-current` で現在のブランチを確認し、`main` 上にいる場合は feature ブランチ（`feat/` / `fix/` / `chore/` 等）を作成してからコミットする**（`main` 直コミットは禁止・`.githooks/pre-commit` に弾かれる。`/start-issue` を経ていない単体起動時に該当しやすい）
- このタスクで変更したファイルのみをステージする
- **`workspace/` を削除する前に、否定の知識を ADR へ回収する**（#593）: `plan.md`・本サイクルの検討に「代替案 B を検討して却下した」判断があれば、削除で失う前に `docs/adr/ADR-<slug>.md` を起こす（形式は `docs/adr/ADR-doc-minimization-cap-enforcement.md` に倣う。**連番を振らない**——slug はテーマが決まった時点で決める・#812）。**トリガーは否定の知識が生じたときだけ** — 自明な実装・一本道の選択では作らない。無ければ何もしない。ADR に書くのは**却下した代替案と、却下の理由**である——採用案の再説明を書かない（採用案はコードと `SPEC.md` が持つ）。**「やらないと決めた作業項目」は代替案の却下ではないので、同じ節の `workspace/` 削除条件が挙げる ADR / issue の 2 択のうち issue 側へ送る**
- `workspace/` ディレクトリが存在する場合、**`plan.md` の全項目が `- [x]` であることを確認してから**削除してステージに含める（`/start-issue` の引き継ぎバッファは実装完了で役目を終える）。未チェックの項目が残っているなら削除しない——完了させるか、やらないと決めた項目は計画から外して理由を ADR か issue へ記録する。**未チェックを残したままの削除は、PR 前ゲート（PreToolUse hook）の視界から計画を消す**
- **削除より先に `plan.md` の最終状態をコミットする。** Step 2 が「消し込みをその都度 `- [x]` へ更新し、**フェーズのコミットに含める**」を求めているので、それを守っていれば損失はせいぜい最後のフェーズ分に留まる。**守らず最後に一括更新した場合、削除の対象は未コミットの実行記録（測定値・故障注入のログ・レビュー対応）を丸ごと抱えている**——「git 履歴から復元可能」が成り立つのはコミット済みの版だけである。実装差分と `plan.md` を 1 コミットにし、`git rm -r workspace/` を次のコミットへ分ける（squash マージで畳まれるので運用コストは無い）
- **`git rm` が `error: … has local modifications` で止まったら、それは保護であって障害ではない。** `-f` で押し通すのも（**git 自身が `use … -f to force removal` と勧めてくるが従わない**）、`checkout` 系（`git checkout` / `git checkout-index` / `git restore`）で「戻す」のも、**未コミットの記録を破棄する**（2026-08-07 の #934 サイクルで、`git reset` の直後に `checkout-index -f` を打って実行記録を全損した。控えは無く、会話の一次出力から再構成した）。止まったら**まず何が未コミットかを見て、順序が逆であることを疑う**。ステージだけ取り消すなら `git reset` で止め、**作業ツリーへ触るコマンドを続けて打たない**
- conventional commit を作成する（例: `feat:`, `fix:`, `refactor:`）
- 何を実装し、なぜ実装したかの簡潔な説明を含める

## 出力

次の形で報告する。**到達しなかった Step の欄には「未到達」と書く**——生成物が存在しないため、埋めれば捏造になる。検証の母集団は `docs/build-commands.md`「変更後の検証チェックリスト」のカテゴリ A〜F 全件、レビューの母集団は 4a の check スキル全件と 4b の `code-reviewer` である。

```markdown
## 実装結果

- 入口: 計画あり — <同一性/未確定ゼロ/人間承認の根拠> | 計画なし — <理由>
- 停止: なし | <Step> で停止 — <1c-A/B/C の引き渡し先、または診断サマリー>

### 検証（カテゴリ A〜F 全件）

| カテゴリ | 実行 / 該当なし / 実行不能 | 根拠（実行ならコマンド出力と exit code） |
|---|---|---|

### レビュー（4a 全件 + 4b）

| 検査 | 実施（ラウンド数・件数・修正の有無） / 該当なし / 未実施 | 根拠 |
|---|---|---|

### テスト

- <テスト名> — <検証した不変条件>（追加・更新が無ければ「なし — <理由>」）

### コミット

- <hash> <message>
```

- **「実行不能」に入れてよいのは、実行者がエージェントであること・実行環境がどこであるかに由来するものだけである**——`scripts/manual-smoke.ps1` が要求する対話的な目視判定と、実行環境が Windows でないときの Windows 専用コマンド（`docs/build-commands.md`「Windows のみ実行可能（`windows` クレートや Win32 API・実行バイナリに依存）」）に限る。人間へ引き渡す項目を根拠欄に書く
- **どの値であれ、時間・手間を理由に選んではならない**——レビューでそれは「未実施（理由: 省いた）」であり、検証では**そもそも Step 3 を終えていない**（＝停止側に居り、この表を書く地点に無い）
- レビューは**1 検査 1 行**とし、Step 4 を複数周した検査はラウンド数を書く（出口条件により 2 周以上は正常に起きる）
- レビューの母集団は 4a の列挙と一致する——`AGENTS.md`「条件別チェック（トリガー → 参照先）」表へ check スキルを足すときは、4a の列挙も同じ変更で直す
