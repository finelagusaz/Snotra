規範は機構ではないが、測り方は機構と同じでよい——**種を蒔いて、捕まえるかを見る**。`.githooks/githooks.test.mjs` が hook を複製して変異を当てるのと同じ操作を、文書へ当てる。

対象: $ARGUMENTS

## Step 1 — 母集団と種

母集団は**この変更で足した／書き換えた条項**である。変更していない条項は母集団の外にあり、そこで見つけた欠陥は issue へ回す。

条項ごとに種を 1 件書く:

> **種**: `<どんな作業状況で>` / `<どの欠陥が紛れ込むか>` / `<条項が効けば何が起きるか>`

種は起きた事実から取る——issue・`RETROSPECTIVE.md`・`docs/adr/`。想像で作った種は、自分が捕まえられると分かっているものに寄る。

**種が書けない条項は、捕まえるものを持たない。** 削除候補として Step 4 に記録し、その条項の検査はそこで終わる。母集団が空になる変更（索引の追随・ファイル名の更新のような、判定を足さないもの）では、起動そのものに仕事が無い。

## Step 2 — 対照（規範なし）

文書を複製して当該条項を削り、その複製を読む状態で、通常のエージェントに通常の作業をさせる。稼働中の規範は弱めない（`.claude/rules/safety-nets.md`「フォールトインジェクションでは、稼働中のガードを弱めない——複製に変異を当てる」）。

**削ったつもりの答えが対照に残っていないか確かめる。** 条項が別の条項と同じ結論を運んでいると、対照が正解を出して「条項不要」に見える——**母集団の切り出しに失敗した run を「対照も捕まえた」と読むと、効いている条項を削除候補にする**。迷ったら対照は変更前の版そのもの（`git show HEAD:<path>`）にする（#812 で射程の条項だけを削ったが命名の条項が同じ答えを残しており、再走して判定が覆った）。

**対照が欠陥を捕まえたなら、その条項に仕事は無い。** 「条項不要」として Step 4 に記録し、削除を提案する——この種の検査はそこで終わる。

## Step 3 — 本番（規範あり）

同じ種・同じ作業を、規範ありで走らせる。対照とは別のサブエージェントへ渡す（同じ文脈で続けると対照の結論が漏れる）。

各ランの成果物は、呼び出し側が指定した絶対パスへ書かせる（委譲の規律は `CLAUDE.md`「サブエージェント委譲と worktree」が正本。返り値に依存させない）。パスは種ごと・対照/本番ごとに別にする。不着なら同じ指示で 1 度だけ再起動し、それでも不着ならそのランは**不成立**と書く（件数ではなく不成立）。

## Step 4 — 記録と、素通りした種の修正

種ごとに三値を割り当てる: **捕まえた** / **素通りした** / **対照も捕まえた（条項不要）**。

素通りした種だけが修正の対象である。**修正そのものは呼び出し側が行う**——このスキルは `Edit` を持たない（`/plan-review` が `Write` を外しているのと同じ理由で、測る側が測られる文書を書き換えないため）。形は素通りの様態に合わせる:

| 素通りの様態 | 採る形 |
|---|---|
| 従ったが、出力の形が違う | 出力が何であるかを順序つきで述べる（recipe） |
| 要る要素が落ちた | 埋める枠を、既に埋めている様式の中へ置く |
| 条件で振る舞いが変わるべきだった | 観測可能な述語に紐づけた条件分岐 |
| 知っていて破った | 種蒔きの射程外。`pressure-scenario.md` へ |

**免除条項は射程を持たない**——「この制限は code block には適用しない」と書いても code block は抑制される（`superpowers:writing-skills`「Match the Form to the Failure」の実測）。一部を除外したいなら、規則が届かない構造へ変える。ただし書きを 1 つ足すだけで、そこから交渉が再開する。

修正したら**同じ種で Step 2 から再走**する。捕まえたら止まる。**2 度目の修正でも素通りするなら `BLOCKED` として人へ返す**——予算を超える修正を要する種は、対象の設計そのものに欠陥がある徴候である（`docs/adr/ADR-race-check-simplification.md` で実際にそう機能し、2 モード同居という設計欠陥が特定された）。

修正 1 件あたりの分量は **1 文**を目安にする。塞ぎは文書を増やす方向にしか働かないためである（#764: 2 巡で `code-reviewer` Phase 1 が 3.4 倍になり、圧縮という目的が反転した）。

## 出力

```markdown
## norm-review — <対象>

### 母集団
足した／書き換えた条項 <N> 件。種を書けたもの <K> 件 / 書けなかったもの <N−K> 件（＝削除候補）

### 種ごとの結果
- 種 1 <一行要約>: 捕まえた ／ 素通りした → <採った形と修正 1 文> ／ 対照も捕まえた（条項不要）
- ...

### 受容する残余
- **網羅性**: 検査したのは種が通った経路だけである。文書全体を走査していないため、経路外の論理衝突は残る
- <不成立だったラン／削除候補のまま残した条項／`BLOCKED` として返した種>
```

**三値は種ごとに全件書く。** `K = 捕まえた + 素通りした + 対照も捕まえた + 不成立` が立たない報告は、落ちた種と「種が無かった」を見分けられない（`/plan-review`「Step 3 — 結果の統合と報告」の配送台帳と同じ理由）。
