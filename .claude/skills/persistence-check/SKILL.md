$ARGUMENTS のシリアライズ／永続化ロジックについて、後方互換とデータ保全が安全かを検証する。
$ARGUMENTS が空の場合は、会話の直近の変更内容から対象を推定する。

実装後のコードレビューだけでなく、`workspace/plan.md` の計画レビューにも使える。計画の段階で「この永続化変更は既存ユーザーのデータを壊さないか？」を検証する。見落としがあれば、計画を更新してから実装に進む。

## 背景

このリポジトリで高リスクの問題が最も多く出る領域は、on-disk 永続化（`index.bin` / `config.toml` / `history.bin` / `window.bin`）である。#338・#343・#394・#461 で繰り返し問題が起きてきた。規則（編集時に守る命令）の正本は `snotra-core/CLAUDE.md`「データ永続化の注意」であり、ここには写さない。このスキルが正本として持つのは 2 つである。1 つはその規則を満たしたかを検証する方法、もう 1 つは規則の根拠になった失敗の型（下の典型パターンと、各 Step のアンチパターン）である。

永続化バグの典型パターン:
1. 形式を変えたのに version をバンプしない → 旧データを新スキーマで読んで破損するか、デシリアライズに失敗する
2. セマンティクスを変えたのに version をバンプしない → バイト列は同じでも値の解釈が変わり、データが壊れる（例: 絶対座標→モニター相対。出典は `snotra-core/src/window_data.rs` の `//!`）
3. 後方互換テストが「新形式往復」だけ → 旧形式が読めなくてもテストは緑になる（新形式を書いて新形式で読むテストは、旧形式が壊れても通る）
4. デコードに失敗した直後に上書き保存する → 学習データ（history 等）を空で上書きして失う
5. `match` の兄弟分岐で保全方針がそろっていない → 1 つの分岐だけ直しても、別の分岐にデータを壊すフォールバックが残る（`Config::load` 型）

## Step 1 — 変更の分類

$ARGUMENTS から対象の永続化構造を特定し、ソースコードを読む。変更を分類する:

```
対象: <struct 名 / ファイル>
変更種別:
  [ ] フィールド追加/削除/型変更（バイト形式が変わる）
  [ ] セマンティクス変更（バイト形式は同一だが値の解釈が変わる）
  [ ] シリアライザ切替（bincode↔postcard 等）
  [ ] リファクタ（バイト形式不変を主張・例: owned/borrowed struct の Cow 統合）
  [ ] 読み込み失敗ハンドリングの変更（load / fallback）
```

## Step 2 — version バンプの要否判定

```
形式が変わる or セマンティクスが変わる → version バンプ必須
  - 該当 version 定数（INDEX_CACHE_VERSION / magic+version ヘッダー / 各 struct の version）をバンプしたか
  - 旧バージョン用フォールバック構造体（IndexCacheVN / Legacy variant 等）を残したか
  - load 経路に「新 → 旧」のフォールバックチェーンを追加したか
バイト形式もセマンティクスも不変（純リファクタ）→ バンプ不要
  - ただし「不変」の主張を Step 3 のテストで証明すること
```

## Step 3 — 後方互換テストの検証（最重要）

後方互換は、旧形式を新コードで読めることで証明する。次を確認する:

```
[ ] 旧オンディスク形式（凍結バイト列 or 旧 struct でシリアライズした bytes）を入力に、
    新コードで deserialize できるテストがあるか
[ ] そのテストは「新形式の往復」とは別に存在するか
    （新形式往復だけでは旧形式の読込失敗を検出できず false-green）
```

```
[ ] 実データと突き合わせる接地テストについて、**その期待値が「いま変えた表現」を 1 度も
    通っていないか**を 1 行で書き出したか（通っていれば不動点＝assert は原理的に落ちない）
```

- アンチパターン: 新コードの出力を golden 化するだけにする。これは forward-stability（今後の形式が安定していること）しか保証しない。「新出力＝旧形式」であることを独立には証明しない。形式が既に壊れていても、新しい golden がその壊れた形を固定してしまい、検出されない（#461）
- アンチパターン（不動点）: 形式変更によって、期待値の元になる原文の出どころが「導出結果」へ入れ替わる。テスト本体は 1 行も変わらないので、差分を読んでも気づかない。壊れていても緑のままで、しかも件数つきの成功メッセージが出る（反復 10 の実例: `target_path` をディスクから消したとき、`load_cached_entries` が「ディスクの原文」ではなく「ツリーから組み直した結果」を返すようになった。その結果、312,691 件の忠実性テストが「組み直し対組み直し」の比較になった）。永続化から消した値を期待値に使っているテストは、すべてこれを疑う。残る唯一の原文は、そのデータを最初に生んだ経路（走査・入力）である。そのテストのコストが上がって `#[ignore]` になっても、不動点のままよりはよい
- 正しい向き: 「旧形式の凍結バイト列 → 新コードで load 成功」を検証する。凍結バイト列は、旧ビルドかリファクタ前のコードから採取するのが最も厳密である
- serde 表現の変更（enum variant / untagged / flatten / tag）: 旧オンディスク形式の deserialize が失敗すると、全設定がリセットされてデータを失う（#394）。旧形式の受理の仕方は `snotra-core/CLAUDE.md`「データ永続化の注意」にある。受理した旧形式を `apply_migrations()` で現行の形へ移しているかも見る（例: `snotra-core/src/config/migrate.rs` の `migrate_instant_legacy_commands`）
- field-level の `#[serde(default = ...)]` を検証するなら、その field が属するセクションを fixture に置く。セクションごと省いた TOML は、親側の `#[serde(default)]`（例 `Config.visual`）によって struct 全体が既定値になる。そのため field の属性は一度も実行されない。属性を消してもテストが通り、壊れていても緑になる。正しい形は「セクションは書く・新キーだけ書かない」である。加えて、既存キーを 1 つ sentinel として入れ、その値が反映されること（＝struct の既定値になっていないこと）を同じテストで示す（#646 PR2 で、PR1 から残っていた穴として検出）

## Step 4 — デコード失敗時のデータ保全

```
[ ] deserialize 失敗時に空データを即時 save() で上書きしていないか（学習データ喪失・#338）
[ ] 読み込み失敗を種類で扱い分けているか（Config::load 型）
[ ] 同じ match の全兄弟分岐で保全方針が揃っているか
    （1 分岐だけ直しても別分岐に破壊的フォールバックが残る・#343）
```

区分の正本は `snotra-core/src/config/io.rs` の `LoadOutcome` である。各分岐の保全の正本は、同じファイルの `Config::load_from_dir_reporting` の doc である。

## Step 5 — 派生・移行経路の整合

- IndexCache 系: `snotra-core/CLAUDE.md`「IndexCache バージョン変更チェックリスト」の全項目を満たすか
- history 系: `snotra-core/CLAUDE.md`「history.rs のキー正規化に関するチェックリスト」の全項目がそろうか
- Config をデシリアライズする新しい経路を追加したなら、`snotra-core/CLAUDE.md`「Config のデシリアライズ経路」に従ったか
- TOML フィールドを別の struct へ移したなら、`snotra-core/CLAUDE.md`「データ永続化の注意」の移し方に従ったか

## Step 6 — 境界条件テストの確認

次に対応するテストが存在するかを grep で確認する:

| 境界条件 | テストの内容 |
|---------|-----------|
| 旧形式の読込 | 旧 version / 旧 struct の凍結バイト列を新コードで deserialize |
| 新形式の往復 | 現行 struct の serialize → deserialize が一致 |
| デコード失敗 | 破損バイト列で既定値フォールバック・実データを潰さない |
| バイト安定 | 固定 fixture の serialize が golden bytes と一致（形式ドリフト検出） |

不足していれば、具体的なテストケースを提案する。

## 出力

根拠の決まり: すべての判定に根拠（`file:line` または grep 結果）を付ける。コード・テストを確認せずに下した判定は「満たす」とせず、「要確認」として報告する。

- version バンプ要否の判定と根拠
- 後方互換テストの有無と、旧形式の読込を証明できているか（forward-stability の保証で止まっていないか）
- デコード失敗時にデータを保全できるか
- 問題があれば修正案（version バンプ / 旧形式 fallback / 凍結バイト列テスト追加 / 保全方針の統一）
- すべて安全な場合は「version 判定・後方互換・データ保全すべて満たしており、永続化変更は安全」と明示する
