`workspace/plan.md` を、実装のときに追加の判断が要らない状態へ近づける。判定するのはレビューの回数ではなく、要件への適合と、未確定事項が解消されたかどうかである。

## Step 1 — plan.md の読み込み

issue・`workspace/plan.md`・必要なコードと規範を読む。そのうえで、次を主エージェント自身が照合する。

1. issue の各要件に、対応する作業項目がある
2. 変更するファイル・シンボル・インターフェースが実在する
3. 不変条件、異常系、テストの期待値が具体的に書かれている
4. `SPEC.md` と関連文書を更新するかどうかの判断が正しい
5. `## 未確定（実装前に潰す）` に未チェックの項目が残っていない
6. タスク分割の境界が、`AGENTS.md`「条件別チェック（トリガー → 参照先）」の既存のトリガーをまたいでいない（とくに「新 API の導入と呼び出し点の移行は 1 タスクに束ねる」。分割すると、`-D warnings` の下で中間状態が `dead_code` で落ちる）
7. 変更によって偽になる散文（doc comment・`CLAUDE.md`・`SPEC.md` の記述）を含むファイルが、変更ファイルの一覧に載っている。確かめ方は次のとおり。変更する識別子と、その変更を指す概念ラベル（概念 1 つにつき 1 語に限る）を、Bash ツールで `npm run prose:sweep -- --plan workspace/plan.md <語>...` へ渡す。出力の `★未掲載`（計画が一度も名指していないファイル）を 1 件ずつ判定する（PowerShell からの打ち方は `docs/build-commands.md`「Windows/macOS/Linux で実行可能」）。手で打つ grep で代えない。出力の切り詰め（`head` / `--include`）が漏れの原因として記録されている（#1142・#1182）。0 件の語は、言い換えて打ち直す（ラベルが外れている場合や、物理改行をまたいでいる場合にも 0 件になる）。見出し行の件数を `/start-issue`「5b. セルフレビュー（plan-review 固有の補完）」の欄へ渡す

不一致は、答えが決まっていれば計画を修正する。調査や裁定が要るなら、未確定欄へ追加する。

### リスク判定

次のいずれかに当たれば高リスク、それ以外は通常リスクとする。

- 永続形式・設定キー・公開 API・状態遷移を変更する
- worker、channel、listener、共有状態、非同期処理を変更する
- hook、CI、rules、skills、ガバナンス文書を変更する
- 網羅性そのものが要件である
- 複数モジュール間のインターフェースを新設・変更する
- ユーザーが `--deep` または独立レビューを明示した

通常リスクでは、Step 1 の自己レビューだけで Step 3 へ進む。高リスクでは、既定で Step 2b を実行する。Step 2 を使うのは、issue に書かれていない人間の裁定（会話・モック・`AskUserQuestion` で決まった要求）が計画の前提にあるときだけである。Step 2b は issue の WHAT だけを渡すので、委譲先はその裁定を知らず、逆の導出を返すからである。どちらの場合も、実行するのは一方だけである。この既定は #1300 の試行である。記録欄は `/start-issue`「5b. セルフレビュー（plan-review 固有の補完）」にある。

## Step 2 — 計画準拠の独立レビュー

高リスクのうち、issue に書かれていない人間の裁定が計画の前提にある場合に使う（「リスク判定」）。`general-purpose`・`model: sonnet` の1体へ、該当するリスク観点だけを渡す。全観点を一律に渡さない。

指示に含めるもの:

- issue と `workspace/plan.md` のパス
- 対象のファイルと、今回検証する1〜2個のリスク観点
- 関連する `AGENTS.md` / `CLAUDE.md` / `.claude/rules/` のパス
- 根拠を `file:line` または grep 結果で示すこと
- 出力を「要対処」「軽微」「未検証」の3分類にすること
- 呼び出し側が指定した絶対パス `<repo-root>/workspace/plan-review-<slug>.md` へ結果を書き出すこと

呼び出し側は、既存のファイルと衝突しない slug を決める。リポジトリルートを解決した絶対パスを渡す。成果物が無い場合、または対象の issue と3分類のいずれかが欠けている場合は、同じ指示で1度だけ起動し直す。再び届かなければ、独立レビュー不成立として Step 3 に記録する。

## Step 2b — 独立導出による網羅性レビュー

issue の WHAT だけを渡す。`workspace/plan.md` と `workspace/research.md` は読ませない。必要な変更ファイルとシンボルを、委譲先にコードから独立に導出させる。型は `general-purpose`、モデルは親を継承する。

Step 2 と同じく、呼び出し側が今回固有の slug を決め、リポジトリルートを解決した絶対パス `<repo-root>/workspace/plan-review-<slug>.md` を渡す。成果物が無い場合、または対象の issue・導出したファイル・シンボルが欠けている場合は、1度だけ起動し直す。再び届かなければ、独立レビュー不成立として Step 3 に記録する。

主エージェントが次を比較する。

- 導出 ∖ plan: 漏れの候補
- plan ∖ 導出: スコープ過剰の候補
- 判断の不一致: 根拠を突き合わせる

独立導出は1回で終える。再実行するのは、issue の要件、または変更対象のファイル・シンボルの集合が変わった場合だけである。説明文だけを直した場合は再実行しない。

## Step 3 — 結果の統合と報告

要対処の根拠だけを、主エージェントが照合し直す。根拠が成り立たなければ軽微へ下げ、下げた事実を残す。

```markdown
## plan-review 結果

- リスク: 通常 / 高
- レビュー方式: 自己レビューのみ / 計画準拠レビュー1体 / 独立導出1体
- エージェント数: 0 / 1

### 要対処
- <項目> — <計画の修正 | 未確定欄への追加> — <再照合した根拠>

### 軽微
- <項目または「なし」>

### 未検証
- <観点と理由、または「なし」>

### 判断
- 実装着手: 可 / 要修正 / 人間の裁定待ち
```

レビューを自動で繰り返さない。計画の修正後に再レビューするのは、要件・対象ファイル/シンボル・インターフェース・不変条件・テストの期待値のいずれかが変わった高リスクの計画だけである。それ以外は、主エージェントが照合し直した後、人間の承認へ渡す。
