## 背景

このプロダクトのレースコンディションは「**送信してから適用されるまでの間に世界が変わりうる**」という 1 点に帰着する。`await` を数える検査は当たらない——UI 層の並行性は worker スレッド + channel + フレーム drain にある。

前提となる土台が 3 つある（要点のみ再掲する。正本は `src-tauri/CLAUDE.md`「イベント駆動 wake の不変条件」節と `snotra-egui-runtime/CLAUDE.md` の不変条件で、内容が食い違ったら正本が正しい）:

1. **view-local の UI 状態（各 view の `&mut self`）を直接触ってよいのはイベントループスレッドだけ**である。両窓の `update()` は同一スレッドで走る。**窓 API・managed state はこの限りでない**——別スレッドからも触られる（→ 種別 ⑤ と、① のうち送信を持たないもの）。
2. **フレームは勝手に回らない**（イベント駆動ランタイム）。状態を変えても、誰かが次フレームを起こさなければ画面に出ない。**wake 漏れそのものを裁くのは Step 4a である**——Step 1 が拾うのは種別 ⑧（paint より後に走るもの）で、wake 漏れの主要経路はそこを通る。
3. **`listen` のコールバックは emit した呼び出し元スレッド上で同期実行される**——別スレッドへ dispatch されない（正本は `src-tauri/CLAUDE.md`「Win32 メッセージ配送の注意」節）。ゆえに listener の追加は、**emit 元のスレッドから UI 状態を触るコードの追加**になりうる（emit 元の例: Win32 メッセージループ・config 監視・index build。**例示であって網羅ではない**）。UI 状態を触らない listener もありうるが、**触るかどうかは Step 2 以降で判定する**——Step 1 では並行境界として拾う。これは反直観であり、最も見落とされる境界である。

## Step 1 — 並行境界の列挙

母集団は 3 段で作る。**段 (3) 以降の母集団は候補集合であって、差分ではない。**

### 段 (1) — 対象を決定的に取得する

```
git diff $(git merge-base main HEAD)    # 追跡ファイルの、分岐点からの全変更
git status --short                       # 新規ファイル（未追跡は git diff に一切現れない）
```

**素の `git diff` も `main...HEAD` も使わない**——前者はコミット済み分を、**後者は未コミット分**を落とす（同一の作業ツリーで実測 183 行 vs 139 行）。この検査は `/implement`「4a. check スキルの実行」から**コミットより前**に呼ばれるため、`main...HEAD` はいちばん新しい変更をまるごと落とす。`main` 以外から分岐しているなら `main` を分岐元のブランチ名へ置き換える。そのうえで、**2 コマンドの出力が両方とも空なら、それは「変更が無い」ではなく「基準が誤っている」と読む**——`git merge-base` が `HEAD` そのものを返していないかを確かめ、返しているなら基準を取り直す（`main` 上で実行している・分岐元が既に自分のコミットを含む、のいずれか）。**空の母集団のまま先へ進んではならない。** ここを禁止 ref の列挙で守らないのは、列挙の外側（`HEAD` を含む別の ref）へ逃げ道が移るからである。

**`git status --short` が挙げたファイルは、パスではなく中身が対象である**——未追跡ファイルは差分を持たないので、ファイル全体を段 (2) の入力にする。

**廃止・移行を検査するなら、起点は作業ツリーに無い。** 消えた記号を現在から探すと構造的に 0 件が返る。基準リビジョンから取る:

```
git show $(git merge-base main HEAD):<path>
```

### 段 (2) — 候補を列挙する

**候補**とは、段 (1) で得た対象に現れるシンボルのうち、下の種別表のいずれかに当たるものである。

**候補集合は種別表の全行の手がかりを 1 度ずつ走らせて作る**——1 件見つけた時点で打ち切らず、境界を宣言できるかは走らせ終えてから決まる（打ち切れる形にすると、①で 1 件当てるのが最短経路になり ②〜⑧ は永久に読まれない）。

**grep はシンボル名で行う。行番号で位置を断定しない**——挿入でずれる。

| # | 種別 | 手がかり |
|---|---|---|
| ① | worker の spawn | `thread::spawn`, `async_runtime::spawn` |
| ② | channel への send | `\.send\(`, `Sender`, `channel\(` |
| ③ | フレームでの drain | `try_recv`, `Receiver` |
| ④ | managed state の読み書き | `try_state`, `Mutex`, `Atomic`, `\.lock\(` |
| ⑤ | **Tauri listener / emit** | `\.listen\(`, `\.emit\(`, `events::` |
| ⑥ | **channel を経由しない worker**（managed state や窓 API を直接叩く監視・再スキャン系スレッド） | **独立した grep は無い**——① のヒットを送信の有無で分類し、送信を持たないものがこれである |
| ⑦ | `.await` 地点（少数だが実在する） | `\.await` |
| ⑧ | **paint より後に走るもの**（遅延 dispatch・期限つき再描画の処理）。**クリックは、ハンドラが遅延 dispatch で戻るときにここへ入る**——同フレームで閉じる局所ハンドラは、どこへも渡らないので境界ではない | `request_repaint_after`, `dispatch` |

**手がかりは入口であって網羅ではない。** 別名 import・再エクスポート・マクロ生成・`Builder::new().spawn` は当たらない。**0 件は「この手がかりでは見つからなかった」であって「無い」ではない**——だから 0 件の報告には打ったコマンドを添える（段 (3) の証拠形式 (iii)）。

**④ の対象外はロック取得順序・保持区間だけである**（正本は `snotra-core/CLAUDE.md`「engine.rs のロック最小化パターン」）。**④ 全体が対象外なのではない**——④ として見るのは「その状態を別スレッドが読み書きするか」である。

**1 つの worker が複数の種別を持つなら、種別ごとに別の候補を立てる**——spawn した本体の中で send もし managed state へも直書きするのは 3 候補である。1 つにまとめると、そのうち 1 つ（多くは channel）の staleness だけ見て満足する。**worker 本体の中での実行順序も 4d の対象**である。分割したかの検算は、**Step 1 の候補数と Step 5 の行数の一致**で行う。

### 段 (3) — 母集団を確定する

**以降の母集団は候補集合である。** 差分でもファイルでもない。**ただし段 (2)・段 (3) で grep を打つ相手は常にパスである**——段 (1) の対象ファイルと、下の「辿る範囲」が加えたファイル。候補集合は grep の**結果**であって、grep の対象ではない。**この限定は母集団の列挙に掛かるのであって、Step 3 の経路探索には掛からない**（そちらは共有状態を変えうる経路を探すので、対象は変更ファイルの外にも及ぶ）。

**母集団の外にあるもの**: **同じファイルに居るだけの既存ヒット**（`update()` を持つファイルは `Mutex` だけで数十件ヒットする）。外したヒットは、**どれをなぜ外したかを 1 行で書く**（証拠形式 (ii)）。

**辿る範囲**（費用の上限を決める）:

- **候補が読み書きする状態**: 候補が直接読み書きするものまで（**1 段**）。推移的に辿らない
- **呼び出し元（上流）**: **1 ホップ**。この規模のアプリでは辿り続ければ必ず `update()` に着くが、`update()` 自体はどの種別でもない。**呼び出し元が多数あるときは全件を個別に裁定せず、呼び出し元の集合に対して種別の grep を 1 回打つ**——費用が呼び出し元の件数に比例しないようにする
- **呼び出し先（下流）**: **1 段**。候補が新しく呼ぶヘルパが種別のいずれかに当たるなら、それは候補が持ち込んだ境界である

呼び出し元を辿るのは、**定義ファイルの grep が空振りすることと、並行性に無関係であることが別だから**である。純粋関数であっても、それが **staleness 判定・可視性/表示ゲート述語・世代の照合**のいずれかに使われているなら境界の要石である。

### 証拠 — 候補ごとに 1 つ

**次の 3 群のそれぞれの要素に、対応する形式を 1 つずつ書く**——候補集合の各要素に (i)、母集団外と裁定した各ヒットに (ii)、**候補を 1 件も生まなかった各種別に (iii)**。

| 形式 | いつ | 書くもの |
|---|---|---|
| **(i) 境界** | 並行境界である | 種別・シンボル・何が誰へ渡るか |
| **(ii) 母集団外** | ヒットしたが候補ではない | シンボルと、外した理由 1 行 |
| **(iii) 候補なし** | その種別に候補が 1 件も無い | **打ったコマンドとその出力**（**⑥ は独立の grep を持たないので、① のヒットを送信の有無で分類した結果を置く**——⑥ に (iii) を書けないことは、⑥ の行を省いてよい理由にならない） |

```
候補 1: <種別> — <シンボル> — <何が誰へ渡るか>       ← (i)
候補 2: <シンボル> — 母集団外（<理由>）              ← (ii)
種別 ⑦: 候補なし — `rg '\.await' <対象>` → 0 件      ← (iii)
```

**`[要確認]` は終端になれない。** 確認手段が無いなら、その候補を **(i) 境界として Step 2 へ送る**（安全側へ倒す）——報告を閉じられないまま止まらない。

**境界を 1 件見つけても、残りの候補の裁定も、候補を生まなかった種別の (iii) も免除されない。仕事量は上の 3 群の大きさで決まり、結論の向きでは変わらない。** (iii) を「非該当と結論するときだけ」の義務にすると、①で 1 件当てて抜ける経路が**走らせた痕跡を何も残さない**——これは義務の追加ではなく、**条件つき免除の除去**である（費用対称性が最初から要求していた形）。

### 「並行境界なし」と結論してよいとき

**全種別について (iii) を示し、かつ辿る範囲（上の 3 つ）を実行したとき**だけである。

- **一部の種別だけを見た確認は成立しない**——⑤（listener）と ⑥（① のうち送信を持たない分類）が最も見落とされる（→「背景」の土台 3）

**候補が 0 件であること自体は正当な結論である**——「この変更にはこの検査の対象が無い」。**捕まえるべきは 0 件ではなく、0 件を生んだ手順の不定性**であり、それを閉じるのは段 (1) の空判定である（2 コマンドがともに空なら、母集団ではなく基準を疑う）。

## Step 2 — 各境界の staleness 機構の同定

送信と適用の間に世界が変わったとき、**古い結果をどう落とすか**。現行の代表的な 4 型（**網羅ではない。5 型目以降を見つけたらそう報告する**）:

| 型 | 成立条件 | 例（2026-07 時点） |
|---|---|---|
| **世代 token** | channel が **view 寿命の共有**。メッセージに token を載せ、drain で現行世代と照合して捨てる | folder ナビ（`accept_folder_result`） |
| **チャネル所有権** | channel が **per-request**。受信側の構造体が `Receiver` を所有し、破棄すると遅着 send は `Err` で自然消滅する | 起動（`LaunchInFlight`） |
| **重複 spawn ガード** | 結果がキーで冪等。staleness は無害で、代わりに in-flight 集合で同一対象の多重 spawn を防ぐ | アイコン抽出（`icon_pending`） |
| **level-triggered 状態** | 値を共有スロットへ直書きし、読み側が毎フレーム現在値を読む | updater の phase |

**判定軸は「送信路が view 寿命の共有か、per-request か」である**（送信路は channel とは限らない——managed state の共有スロットも同じ役を果たす）。共有なら token が要り、per-request なら所有権の破棄で足りる。**この 2 つを混ぜてはならない**（per-request に token を足すのは冗長、共有から token を落とすのは破れ）。

**世代 token は channel 専用の機構ではない**——共有スロットへ直書きする level-triggered 型が、その値の一部として世代を運ぶこともある。「channel が無いから世代の話ではない」と読まないこと。

**窓をまたぐ共有スロットは、運ぶ値が世代を持つかを個別に問う**——同じ構造体の中でも、世代を運ぶフィールドと運ばないフィールドが同居しうる。裸の index・裸の添字は「受け側フレームで対象集合が入れ替わっていない」ことを暗黙に仮定している。境界チェック（`.get()`）は**存在の確認であって同一性の確認ではない**。

## Step 3 — 窓の間に到達しうる事象の列挙

各境界について、**送信〜適用の間に**共有状態を変えうる経路を grep で探す。主な経路:

| 経路 | トリガー | 影響 |
|---|---|---|
| 打鍵 → 検索/フィルタ | ユーザー入力（毎フレーム受け付ける） | クエリ・結果・選択・世代 |
| Enter / クリック → 起動 | ユーザー操作（クリックは別窓から遅延 dispatch で戻る） | in-flight 状態・結果クリア |
| Escape / ← → モード離脱 | ユーザー操作 | view 種別・世代の失効 |
| hide / show | ホットキー・blur・起動完了（**emit 元は別スレッドでありうる**） | reset-on-show による全 view-local の一掃 |
| config 適用 | ファイル監視スレッド | テーマ・フォント・言語・幅・index 再構築 |
| index build 完了 | build スレッド | 世代 bump → 再検索 |
| 他 worker の到着 | 別の spawn | 結果の総入れ替え |

**この表は例示であって網羅ではない。** 対象コードに現れる入力ハンドラ・イベント名を grep し、表に無い経路が無いことを示す（表の 7 行を裁定して終えるのは、模範解答を網羅と取り違えている）。

各経路が**その窓の間に実際に到達可能か**を判定する（ガードの有無を確認する）。到達不能と結論するなら、何が塞いでいるかを名指しし、**そのガードの条件式（`if` / `match` / 早期 return）を `file:シンボル` か grep 結果で示す**——名前を挙げるだけでは、そのガードが当の経路を実際に止めている確認になっていない。

## Step 4 — 5観点での検証

**全面適用は差分が新設・変更した境界に限る。** 既存のまま触っていない境界は 1 行の理由（「この差分は触れていない」）で足りる——**この免除は 4a〜4e にだけ掛かり、Step 2・Step 3 は全候補に走る**。段 (3) の**呼び出し元（上流）**が引き込んだ境界もこの 1 行でよく、**それは `[要確認]` ではない**（ゆえに出力表で `[要修正]` へ倒す対象でもない）。**ただし呼び出し先（下流）は免除されない**——段 (3) がそれを「候補が持ち込んだ境界」と呼ぶとおり、差分が新しく呼んだ以上それは差分が新設した境界である。境界数 × 観点数 × 証拠 2 種の積は容易に破綻し、破綻した検査は「大半が `[要確認]`」という行動不能な報告を生む。

### 4a. wake 義務

状態を変えた後、**次フレームを起こす者がいるか**（回数ではなく到達性を問う。送信が 1 バーストで完結し、**最後の送信より後に** repaint が来るなら 1 回で足りる。逐次 send が長時間続くなら、最後の 1 回では途中の到着が見えない）。

- 自窓の `egui::Context` を持つ場所（`update()` 内・worker へ渡した clone）は `ctx.request_repaint()`
- 外部スレッド・別窓・listener からは wake handle（`WindowWaker`）を使う
- **managed state や外部へ渡すハンドルに `egui::Context` の clone を置いていないか**——clone は repaint callback ごと複製し、worker の停止・join を妨げる（`snotra-egui-runtime/CLAUDE.md` の不変条件）
- hidden 窓への wake は実効 no-op でよい（次の show で live-read が拾う）が、**それを前提にしてよいのは値を運ばない wake だけ**である
- **listener が自ら起こさない設計は、それ自体では問題ではない**——別のイベントへ wake を委譲していることがある。その場合は**委譲先のイベントが全終端で無条件に伴走することを emit 側の制御フローで確認する**。コメントの記述を根拠にしない

### 4b. staleness 適用

Step 2 で同定した機構が、実際に適用されているか。

- 共有 channel: drain で token を照合して捨てているか。滞留を全部 drain して最新を採っているか
- per-request channel: 受信側の破棄が「捨てる」全経路（成功・timeout・異常終了・リセット）に置かれているか。**enum の全アームを尽くしたか**
- 世代カウンタ: **書き側の全サイト**が進めているか
- 重複 spawn ガード: in-flight への insert と、全終端での remove が対になっているか
- single-flight（再入拒否）: 拒否のフラグを**戻す経路が全終端にあるか**——1 つ欠けると永久に拒否し続ける
- **level-triggered 状態**: 書き手が複数（worker・UI スレッド・別 listener）いるとき、**後着の書き込みが先着の意味のある遷移を黙って上書きしないか**

### 4c. 窓の間に届く事象への耐性

Step 3 で到達可能とした事象それぞれについて。

- **ユーザー操作**: ロード未確定・in-flight 中の古い対象に対する操作を弾いているか（弾かないなら、古い対象に作用しても無害である根拠を**コードで**示す——対象キーの比較・冪等性を保証する条件式を `file:シンボル` で）
- **hide / show を跨ぐか**: hidden 中は `update()` が走らないため、期限つき再描画による時限処理は**可視中しか効かない**。hide を跨ぐ in-flight 状態は reset-on-show の backstop とセットで設計する（正本は `src-tauri/CLAUDE.md`「イベント駆動 wake の不変条件」節）
- 判定は「**クリアされるか**」ではなく「**クリアされるか、されない理由が書かれているか**」である——意図的に show を跨がせる状態が実在するため、クリアを一律の要件にすると誤検出になる
- **クリア対象の列挙は view-local だけで閉じない**——managed state 側に置かれた共有スロットは reset の視野に入っていないことがある

### 4d. 順序不変条件

**この処理を別の位置へ動かすと壊れるか。** 壊れるなら、その順序はコメントで明文化されているか。

**`update()` の中だけの話ではない**——listener / emit ハンドラ・show/hide の同期関数・worker 本体の中の逐次処理も、すべて順序不変条件を持ちうる。

既知の型（正本は各コメント）: 消費は初期化・リセットの後／格納は表示・wake の前／**主窓の可視フラグと従属窓の show/hide は、show と hide で逆向き**。

**「壊れない」と判定する場合も根拠が要る**——その処理が読み書きする状態と、前後の処理が読み書きする状態に重なりが無いことを grep で示す。

### 4e. 同一フレーム内の live-read 規律

- 同じ設定値をフレーム冒頭で読んだら、**後段で読み直さない**（間に適用が挟まると同一フレーム内で新旧が混ざる）
- 読み取り結果を `self.` へ保持しない（毎フレーム live-read が設定変更の反映経路そのもの）
- **逆に、フレームを跨いでキャッシュして hot-reload を殺していないか**も見る

## Step 5 — 各境界の判定

```
境界 1: <種別> — <シンボル> — <説明>
  4a wake 義務:     [OK] / [問題] <内容>
  4b staleness:     [OK] / [問題] <内容>
  4c 窓の間の事象:  [OK] / [問題] <内容>
  4d 順序:          [OK] / [問題] <内容>
  4e live-read:     [OK] / [問題] <内容>
  総合判定: [安全] / [要修正: <具体的な修正内容>] / [要確認: <未確認の項目>]
```

**`[要確認]` が 1 つでも残る境界は `[安全]` にしてはならない。** `[問題]` が 1 つも無いことは、`[安全]` の条件ではない——確認していない項目があるなら、その境界の総合判定は `[要確認]` である。「面倒な観点を `[要確認]` に倒し、`[問題]` が無いので安全」は、この検査を無効化する最短経路である。

**Step 1 の候補数と Step 5 のマトリクスの行数は一致させる。** 統合・除外したなら、その理由を Step 5 に書く——正直に列挙したあと途中で 1 行落とすのは、入口ではなく出口での取りこぼしである。

## 出力 — 判定と、次に何が起きるか

**根拠の規律**: 全判定に、**`file:シンボル` と、その判定を支える実際のコード片（該当行）の両方**を付ける。場所の名前だけでは、そこに何が書かれているかを確認した証拠にならない。**行番号で位置を断定しない**——挿入でずれる。

全境界の判定をマトリクス形式でまとめ、Step 1 の証拠（形式 (i)(ii)(iii)）を添える。

| 総合判定 | 次の動作 | 停止権 |
|---|---|---|
| **[安全]** | 「全境界で状態競合リスクなし」と明示して終わる | — |
| **[要修正]** | 修正案を提示する。**修正するかどうかは呼び出し元が決める**（`/implement`「4a. check スキルの実行」は「発見事項があれば修正してから 4b に進む」と定める） | **呼び出し元** |
| **[要確認]** | 終端にできない。安全側へ倒し `[要修正]` として扱う | **呼び出し元** |
| **[非該当]** | 「並行境界なし（候補 0 件）」と明示して終わる。**`[安全]` と同じ記号を使わない**——検査を実行したことと、検査対象があったことは別である | — |

**`[非該当]` にも証拠が要る**——全種別ぶんの (iii) は結論に関わらず要求されている（→「証拠 — 候補ごとに 1 つ」）ので、そこで書いたものをそのまま添える。
