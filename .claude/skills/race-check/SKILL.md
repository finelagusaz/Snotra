$ARGUMENTS の変更が、**別スレッド・別フレーム・別窓へ何かを渡しているか**を見る。渡っていれば、送信してから適用されるまでの間に世界が変わりうる——このプロダクトの状態競合はその 1 点に帰着する。`await` を数える検査は当たらない。

**計画段階では起動しない。** 計画の記述に対する並行境界の検査は本スキルの守備範囲になく、`/plan-review` も引き継がない（経緯と選択肢は `#784`）。

**`$ARGUMENTS` は対象の説明であって母集団の定義ではない。** 食い違ったら差分の側を採る——`$ARGUMENTS` で絞り込むと、波及した他ファイルが俎上から落ちる。

## 知っておくこと

正本は `src-tauri/CLAUDE.md`「イベント駆動 wake の不変条件」節と `snotra-egui-runtime/CLAUDE.md` の不変条件。食い違ったら正本が正しい。

1. **view-local の UI 状態（各 view の `&mut self`）を直接触ってよいのはイベントループスレッドだけ**である。両窓の `update()` は同一スレッドで走る。**窓 API・managed state はこの限りでない**——別スレッドからも触られる。
2. **フレームは勝手に回らない**（イベント駆動ランタイム）。状態を変えても、誰かが次フレームを起こさなければ画面に出ない。
3. **`listen` のコールバックは emit した呼び出し元スレッド上で同期実行される**——別スレッドへ dispatch されない（正本は `src-tauri/CLAUDE.md`「Win32 メッセージ配送の注意」節）。ゆえに listener の追加は、**emit 元のスレッドから UI 状態を触るコードの追加**になりうる（emit 元の例: Win32 メッセージループ・config 監視・index build。例示であって網羅ではない）。**これは反直観であり、最も見落とされる境界である。**

## 1. 対象を取る

```
git diff $(git merge-base main HEAD)    # 追跡ファイルの、分岐点からの全変更
git status --short                       # 新規ファイル（未追跡は git diff に一切現れない）
```

**素の `git diff` も `main...HEAD` も使わない**——前者はコミット済み分を、後者は未コミット分を落とす（同一の作業ツリーで実測 183 行 vs 139 行）。この検査は `/implement`「4a. check スキルの実行」から**コミットより前**に呼ばれる。`main` 以外から分岐しているなら `main` を分岐元のブランチ名へ置き換える。

**2 コマンドの出力が両方とも空なら、それは「変更が無い」ではなく「基準が誤っている」と読む**——`git merge-base` が `HEAD` そのものを返していないかを確かめ、返しているなら基準を取り直す。空の母集団のまま先へ進まない。

**`git status --short` が挙げたファイルは、パスではなく中身が対象である**（未追跡ファイルは差分を持たない）。

**廃止・移行を検査するなら、起点は作業ツリーに無い**——消えた記号を現在から探すと構造的に 0 件が返る。`git show $(git merge-base main HEAD):<path>` で基準リビジョンから取る。

## 2. 渡っているものを挙げる

**grep はシンボル名で行う。行番号で位置を断定しない**——挿入でずれる。

| # | 種別 | 手がかり |
|---|---|---|
| ① | worker の spawn | `thread::spawn`, `async_runtime::spawn` |
| ② | channel への send | `\.send\(`, `Sender`, `channel\(` |
| ③ | フレームでの drain | `try_recv`, `Receiver` |
| ④ | managed state の読み書き | `try_state`, `Mutex`, `Atomic`, `\.lock\(` |
| ⑤ | **Tauri listener / emit** | `\.listen\(`, `\.emit\(`, `events::` |
| ⑥ | **channel を経由しない worker**（managed state や窓 API を直接叩く監視・再スキャン系スレッド） | 独立した grep は無い——① のヒットを送信の有無で分類し、送信を持たないものがこれである |
| ⑦ | `.await` 地点（少数だが実在する） | `\.await` |
| ⑧ | **paint より後に走るもの**（遅延 dispatch・期限つき再描画の処理）。クリックは、ハンドラが遅延 dispatch で戻るときにここへ入る——同フレームで閉じる局所ハンドラはどこへも渡らない | `request_repaint_after`, `dispatch` |

**手がかりは入口であって網羅ではない。** 別名 import・再エクスポート・マクロ生成・`Builder::new().spawn` は当たらない。**0 件は「この手がかりでは見つからなかった」であって「無い」ではない**——だから 0 件で終えるときは打ったコマンドを添える。

**同じファイルに居るだけの既存ヒットは境界ではない**（`update()` を持つファイルは `Mutex` だけで数十件ヒットする）。見るのは差分が触れたものと、それが持ち込んだものである。

**④ の対象外はロック取得順序・保持区間だけである**（正本は `snotra-core/CLAUDE.md`「engine.rs のロック最小化パターン」）。④ として見るのは「その状態を別スレッドが読み書きするか」。

**1 つの worker が複数の種別を持つなら、種別ごとに別に立てる**——spawn した本体の中で send もし managed state へも直書きするのは 3 つである。1 つにまとめると、そのうち 1 つ（多くは channel）の staleness だけ見て満足する。

**どこまで辿るか**: 境界が読み書きする状態は 1 段（推移的に辿らない）。呼び出し元は 1 ホップ（多数あるなら個別に裁定せず、その集合へ種別の grep を 1 回打つ）。呼び出し先は 1 段——候補が新しく呼ぶヘルパが種別に当たるなら、それは差分が持ち込んだ境界である。純粋関数であっても、**staleness 判定・可視性/表示ゲート述語・世代の照合**に使われているなら境界の要石である。

**何も渡っていないなら、打ったコマンドを添えて「並行境界なし」で終わる。** これは正当な結論である（この変更にはこの検査の対象が無い）。

## 3. 境界ごとに 5 つ答える

**答えられない項目があるなら、それが指摘である。**

### a. 何が誰へ渡るか

種別・シンボル・渡る値。

### b. 送信〜適用の間に世界が変わったとき、古い結果はどう落ちるか

現行の代表的な 4 型（**網羅ではない。5 型目を見つけたらそう報告する**）:

| 型 | 成立条件 | 例（2026-07 時点） |
|---|---|---|
| **世代 token** | 送信路が **view 寿命の共有**。メッセージに token を載せ、drain で現行世代と照合して捨てる | folder ナビ（`accept_folder_result`） |
| **チャネル所有権** | 送信路が **per-request**。受信側の構造体が `Receiver` を所有し、破棄すると遅着 send は `Err` で自然消滅する | 起動（`LaunchInFlight`） |
| **重複 spawn ガード** | 結果がキーで冪等。staleness は無害で、代わりに in-flight 集合で同一対象の多重 spawn を防ぐ | アイコン抽出（`icon_pending`） |
| **level-triggered 状態** | 値を共有スロットへ直書きし、読み側が毎フレーム現在値を読む | updater の phase |

**判定軸は「送信路が view 寿命の共有か、per-request か」である**（送信路は channel とは限らない——managed state の共有スロットも同じ役を果たす）。共有なら token が要り、per-request なら所有権の破棄で足りる。**この 2 つを混ぜてはならない**（per-request に token を足すのは冗長、共有から token を落とすのは破れ）。

- **世代 token は channel 専用の機構ではない**——共有スロットへ直書きする level-triggered 型が、その値の一部として世代を運ぶこともある
- **窓をまたぐ共有スロットは、運ぶ値が世代を持つかを個別に問う**。裸の index・裸の添字は「受け側フレームで対象集合が入れ替わっていない」ことを暗黙に仮定している。境界チェック（`.get()`）は**存在の確認であって同一性の確認ではない**
- 同定した機構が**実際に適用されているか**を見る: 共有 channel は drain で token を照合し滞留を全部 drain しているか／per-request は受信側の破棄が全終端（成功・timeout・異常終了・リセット）にあるか（**enum の全アームを尽くしたか**）／世代カウンタは**書き側の全サイト**が進めているか／in-flight への insert と全終端での remove が対か／single-flight の拒否フラグを**戻す経路が全終端にあるか**（1 つ欠けると永久に拒否し続ける）／level-triggered は**後着の書き込みが先着の意味のある遷移を黙って上書きしないか**

### c. 状態を変えたあと、次フレームを起こす者はいるか

回数ではなく到達性を問う。送信が 1 バーストで完結し**最後の送信より後に** repaint が来るなら 1 回で足りるが、逐次 send が長時間続くなら最後の 1 回では途中の到着が見えない。

- 自窓の `egui::Context` を持つ場所（`update()` 内・worker へ渡した clone）は `ctx.request_repaint()`。外部スレッド・別窓・listener からは wake handle（`WindowWaker`）
- **managed state や外部へ渡すハンドルに `egui::Context` の clone を置いていないか**——clone は repaint callback ごと複製し、worker の停止・join を妨げる（`snotra-egui-runtime/CLAUDE.md` の不変条件）
- hidden 窓への wake は実効 no-op でよい（次の show で live-read が拾う）が、それを前提にしてよいのは**値を運ばない wake だけ**である
- **listener が自ら起こさない設計は、それ自体では問題ではない**——別のイベントへ委譲していることがある。その場合は委譲先が全終端で無条件に伴走することを **emit 側の制御フローで**確認する。コメントの記述を根拠にしない

### d. 送信〜適用の間に、何が届きうるか

| 経路 | トリガー | 影響 |
|---|---|---|
| 打鍵 → 検索/フィルタ | ユーザー入力（毎フレーム受け付ける） | クエリ・結果・選択・世代 |
| Enter / クリック → 起動 | ユーザー操作（クリックは別窓から遅延 dispatch で戻る） | in-flight 状態・結果クリア |
| Escape / ← → モード離脱 | ユーザー操作 | view 種別・世代の失効 |
| hide / show | ホットキー・blur・起動完了（**emit 元は別スレッドでありうる**） | reset-on-show による全 view-local の一掃 |
| config 適用 | ファイル監視スレッド | テーマ・フォント・言語・幅・index 再構築 |
| index build 完了 | build スレッド | 世代 bump → 再検索 |
| 他 worker の到着 | 別の spawn | 結果の総入れ替え |

**この表は例示であって網羅ではない。** 対象コードに現れる入力ハンドラ・イベント名も見る。到達不能と結論するなら、**そのガードの条件式（`if` / `match` / 早期 return）を `file:シンボル` か grep 結果で示す**——名前を挙げるだけでは、それが当の経路を止めている確認にならない。

耐性の側で見るもの:

- **ユーザー操作**: in-flight 中の古い対象への操作を弾いているか。弾かないなら、古い対象に作用しても無害である根拠を**コードで**示す（対象キーの比較・冪等性を保証する条件式）
- **hide / show を跨ぐか**: hidden 中は `update()` が走らないため、期限つき再描画による時限処理は**可視中しか効かない**。hide を跨ぐ in-flight 状態は reset-on-show の backstop とセットで設計する
- 問うのは「**クリアされるか**」ではなく「**クリアされるか、されない理由が書かれているか**」——意図的に show を跨がせる状態が実在するため、クリアを一律の要件にすると誤検出になる
- **クリア対象は view-local だけで閉じない**——managed state 側の共有スロットは reset の視野に入っていないことがある

### e. 順序と live-read

**この処理を別の位置へ動かすと壊れるか。** `update()` の中だけの話ではない——listener / emit ハンドラ・show/hide の同期関数・worker 本体の中の逐次処理も順序不変条件を持ちうる。既知の型: 消費は初期化・リセットの後／格納は表示・wake の前／**主窓の可視フラグと従属窓の show/hide は、show と hide で逆向き**。壊れるなら順序がコメントで明文化されているか。**「壊れない」と判定する場合も、読み書きする状態に重なりが無いことを示す。**

live-read は 3 点: 同じ設定値をフレーム冒頭で読んだら**後段で読み直さない**（間に適用が挟まると同一フレーム内で新旧が混ざる）／読み取り結果を `self.` へ保持しない（毎フレーム live-read が設定変更の反映経路そのもの）／**逆にフレームを跨いでキャッシュして hot-reload を殺していないか**。

## 出力

境界ごとに a〜e の答えと、**[安全]** か **[要修正]**。判定には `file:シンボル` と該当行を添える（場所の名前だけでは、そこに何が書かれているかを確認した証拠にならない）。**行番号で位置を断定しない。**

- **[要修正]** なら修正案を出す。**修正するかどうかは呼び出し元が決める**（`/implement`「4a. check スキルの実行」は「発見事項があれば修正してから 4b に進む」と定める）
- 境界が 1 つも無かったなら **[非該当]** と明示し、打ったコマンドを添える。**[安全] と書き分ける**——検査を実行したことと、検査対象があったことは別である

**仕事量は境界の数で決まる。** 境界が無ければ 1〜2 で終わり、あればその数だけ 5 問に答える——結論の向きで増減しない。
