開発サイクルの振り返りを行う。質問せず自律的に進めること。

対象: $ARGUMENTS

## Step 1 -- サイクルの全体像を把握

```bash
git log main..HEAD --oneline
git diff main..HEAD --stat
```

- 変更したファイル・コミット履歴からサイクルの全体像を把握する
- `workspace/plan.md` があれば読み、当初の計画と実際の実装を比較する
- PR のコメントやレビュー指摘があれば `gh pr view` で確認する

## Step 2 -- 振り返りの分析

以下の3観点で分析する:

### よかったこと
- 計画通りに進んだ点、うまくいった判断
- 効果的だったパターンや手法

### 伸びしろ
- 手戻り・追加修正が発生した箇所とその原因
- 見落としていた影響範囲やエッジケース
- 次回同じ状況で改善できる点

### 構造的パターンの抽出
- 「このバグは○○を確認していれば防げた」→ ワークフロールールの候補
- 「このパターンは今後も使える」→ CLAUDE.md の横断的実装パターン候補
- 「この判断基準は明文化すべき」→ 開発原則やデバッグ原則の候補
- 「このワークフローステップ自体が機能しなかった・足りなかった」→ スキルの更新候補（実際に更新するかはユーザーと相談する）

## Step 3 -- 教訓の CLAUDE.md 反映

Step 2 で抽出した構造的パターンのうち、今後のサイクルで繰り返し参照する価値があるものを特定し、適切な CLAUDE.md に反映する:

- 横断的なルール → `CLAUDE.md`（ルート）
- フロントエンド固有 → `ui/CLAUDE.md`
- Rust バックエンド固有 → `src-tauri/CLAUDE.md` または `snotra-core/CLAUDE.md`
- スキル・エージェントの改善 → 該当する `.claude/skills/` または `.claude/agents/`

**反映の判断基準**: 単発の出来事ではなく、再発しうるパターンのみ反映する。過剰な追記は CLAUDE.md の可読性を下げるため、既存ルールで包含できる場合は追記しない。

## Step 4 -- RETROSPECTIVE.md の上書き

Step 3 の反映が完了してから、`RETROSPECTIVE.md` を以下のフォーマットで**上書き**する:

```markdown
# Retrospective — <サイクルの概要>

## よかったこと

### <見出し>
<説明>

---

## 伸びしろ

### <見出し>
<説明>

---

## ネクストアクション

- [ ] <アクション項目>
```

- **ネクストアクション**: ドキュメント改善は Step 3 で既に反映済みなので含めない。実装タスクや手動確認など、実行が必要な項目のみ列挙する
- 前回の内容は上書きする（追記しない）

## Step 5 -- メモリの鮮度チェック

サイクルで変更した内容に関連するメモリが `MEMORY.md` に存在するか確認する。

1. `MEMORY.md` を読み、各メモリファイルの説明を確認する
2. サイクルの変更内容と関連するメモリがあれば、ファイルを読んで内容が現在のコードベースと矛盾していないか検証する
3. 矛盾するメモリは更新または削除する（MEMORY.md のインデックスも同期）
4. サイクルで得た知見のうち、将来の会話で有用なものがあればメモリに追加する

**判断基準**: メモリは「コードやドキュメントから読み取れない、セッション横断で有用な情報」のみ保持する。コードの構造やパターンは CLAUDE.md の責務。

## 出力

以下を報告:
1. サイクルの概要（1〜2行）
2. CLAUDE.md に反映した教訓（あれば、どのファイルに何を追加したか）
3. メモリの更新（あれば、追加/更新/削除したメモリ）
4. ネクストアクションの一覧
