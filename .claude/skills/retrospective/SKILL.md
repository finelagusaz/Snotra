開発サイクルの振り返りを行う。質問せずに自律的に進める。例外はスキル自体の更新である。その採否だけはユーザーに諮る（Step 2）。

対象: $ARGUMENTS

## Step 1 — サイクルの全体像を把握

```bash
git log main..HEAD --oneline
git diff main..HEAD --stat
```

- 変更したファイルとコミット履歴から、サイクルの全体像を把握する
- `workspace/plan.md` があれば読み、当初の計画と実際の実装を比較する
- PR のコメントやレビュー指摘があれば、`gh pr view` で確認する

## Step 2 — 振り返りの分析

次の 3 つの観点で分析する。

### よかったこと
- 計画どおりに進んだ点、うまくいった判断
- 効果があったパターンや手法

### 伸びしろ
- 手戻り・追加修正が起きた箇所と、その原因
- 見落としていた影響範囲やエッジケース
- 次回同じ状況で改善できる点

### 構造的パターンの抽出（「どのトリガーで必要になるか」で分類する）

教訓ごとに「これは何をした瞬間に必要になるか」を問う（実際の置き場所は Step 3 の順序で決める）。既定では `AGENTS.md` に足さない。トリガーを持つ教訓は、そのトリガーに紐づく文書へ置く。

- 機械判定できる違反（型・compile・出力形式の逸脱） → 機構（compile-fail・`#[must_use]`・hook・test）の候補
- 特定のファイル/パスを触るときの注意 → `.claude/rules/` の候補
- 特定の作業局面（対称ペアの変更・網羅列挙・状態の追加・永続形式の変更 等）の注意 → 該当スキルの候補
- 汎用の設計・デバッグの判断基準 → `docs/development-principles.md` の候補
- どのトリガーにも紐付かず、書く・判断するたびに効く横断原則 → `AGENTS.md`「検証の作法」の候補
- ワークフローのステップ自体が機能しなかった・足りなかった → スキルの更新候補（実際に更新するかはユーザーと相談する）

## Step 3 — 教訓の配置（トリガーに括り付ける）

Step 2 で抽出した構造的パターンのうち、今後のサイクルで繰り返し参照する価値があるものを置く。置き先は、その教訓が必要になるトリガーに紐づく文書である。`AGENTS.md` の常時ロードへの追加は、既定でも第一候補でもない。最後の手段である。トリガーを持たない、本当に横断的な原則だけをそこに置く。単発の出来事は置かず、再発しうるパターンだけを置く。

上の段から順に検討する（`docs/development-principles.md`「構造的設計原則と強制の階梯」に対応する）。

1. 機構が吸収できるか（最上段）: compile-fail・`#[must_use]`・hook・テストで違反を検出できるなら、または構造で違反を起こせなくできるなら、教訓は「注意書きの追加」にしない。「機構の追加・強化」にする。`AGENTS.md`・各 `CLAUDE.md` に専用のチェックリストや注意書きが要る箇所は、「構造が規則を吸収できていない」ことを示す信号である。カナリアで守るのは、失敗しても何も出力しない経路だけでよい（放っておいても明示的に失敗するものに見張りは要らない）
2. 内容の種類で置き場所が決まるものを先に振り分ける（第二軸）: 手順（ステップ列として実行できる）→ スキル（規範文書に手順の本文を書かない）。否定の知識（なぜ B を却下したか）→ `docs/adr/ADR-<slug>.md`。失敗の一次証跡（何が起きたか）→ GitHub issue（`RETROSPECTIVE.md` は上書きで消えてよい）。意図（仕様） → `SPEC.md`
3. 特定のファイル/パスを触ると効くか → `.claude/rules/<X>.md`（対象を読むと自動で配送される）。既存の rule の `paths:` に該当するなら本文へ追記する。該当しなければ新設する（新設するときはカナリアの要否を判断する）
4. 特定の局面・作業で効くか → 該当スキル（`/symmetric-check`・`/plan-review`・`/state-check`・`/persistence-check`・`/dry-check`・`/race-check` 等）の本文へ置く。`AGENTS.md`「条件別チェック」表には「トリガー → 参照先」の 1 行だけを足す（本文の SSOT はスキルの側である）
5. 汎用の設計・デバッグの原則か → `docs/development-principles.md`
6. モジュール固有 → 各サブディレクトリの `CLAUDE.md`（`src-tauri/`・`snotra-core/`・`snotra-settings/`・`snotra-egui-runtime/`）／Claude Code 固有（コミュニケーション原則・スキル表・委譲/worktree の運用） → ルート `CLAUDE.md`
7. どのトリガーにも紐付かず、書く・判断するたびに効く横断原則だけ → `AGENTS.md`「検証の作法」の中心部。常時ロードに置く価値があるのはここだけである

不変条件: 常時ロード面（ルート `CLAUDE.md` / `AGENTS.md`）に置いてよいのは「トリガー＋参照＋根拠 issue 番号」までである。手順の本文を置いてはならない。手順はスキルへ置く（#488 の 4 手順を `/merge-pr` へ移した検算が先例である）。

検収条件: `AGENTS.md` を重くする方向の変更は、設計が悪い兆候として扱う。ドキュメントが軽くなることを、設計改善の検収条件にする（構造が規則を吸収したら、対応するチェックリストは削除する）。既存のルール・既存のトリガーで包含できるなら追記しない。同じ教訓の本文を 2 箇所に書かない。`AGENTS.md` はポインタにとどめ、本文はトリガーに紐づく文書に 1 つだけ置く（ドリフトを防ぐため）。

## Step 4 — 残タスクの振り分け（issue / PR）

`RETROSPECTIVE.md` は上書きするファイルである。サイクルを越えて残るタスクを置くと、次のサイクルの上書きで失われる。Step 2 で洗い出した「実行が必要な項目」のうち、Step 3 で教訓として置ききれなかったもの（ドキュメント化ではなく実行を要するもの）を、次の追跡先へ振り分ける（`RETROSPECTIVE.md` には残さない）。

- PR のライフサイクルの中で閉じるタスク（push・ラベル付与・CI のグリーン確認・手動マージ 等）→ 対象 PR の本文のチェックリストに追記する（`gh pr edit --body` 等）。PR が merge されれば、それで閉じる
- サイクル/PR を越えて残るタスク（follow-up・別のリファクタ・繰り越し・要設計）→ GitHub issue を起票する（`gh issue create`）。迷ったら、残る側である issue を選ぶ
  - 起票の前に、同じ「はい」で動き出すものを 1 件へ束ねる。判定するのは関連の強さではない。「人間が 1 度承認すれば束ねた全部が着手可能になるか」で判定する（#1112 と #1113 は 1 つの是非で code と規範の両方が動き、PR #1117 一本で閉じた。同じサイクルの #1114 は是非が別だったので、別の PR になった）。束ねたら、その 1 つの是非を issue のタイトルに置き、所見は個別の見出しとして本文へ残す。タイトルが違えば、人間はそこで分割できる。本文に残っていれば、片方が知られずに落ちることがない。迷ったら分ける（判断が重複しても人間の目に見えるが、束ね損なった所見は誰にも気づかれない）

既に完了したタスク（merge 済みの PR の手順など）は振り分けなくてよい。振り分けた issue 番号 / PR のチェックリストは出力に記録する。

## Step 5 — RETROSPECTIVE.md の上書き（教訓のみ）

Step 3・Step 4 が終わってから、`RETROSPECTIVE.md` を次の 2 セクションのフォーマットで上書きする。タスク（ネクストアクション）は Step 4 で振り分け済みなので含めない。

```markdown
# Retrospective — <サイクルの概要>

## よかったこと

### <見出し>
<説明>

---

## 伸びしろ

### <見出し>
<説明>
```

- 各節（`###` 配下）には「次のサイクルで効く一点」だけを書く。`RETROSPECTIVE.md` は次のサイクルで上書きされるので、どれだけ読んだかの証明や経緯の説明は要らない。ただし、節を短く保つことは、Step 3 の教訓の配置を省く理由にならない（上書きで消えるのはここの記述であって、トリガーに括り付けた教訓ではない。節を短くするために教訓の抽出そのものを 1 件へ絞ると、`AGENTS.md`「RETROSPECTIVE.md の運用」の不変条件が防ごうとした失敗に戻る）
- 前回の内容は上書きする（追記しない）
- 実行タスク・未完了の項目は書かない（Step 4 で issue / PR へ振り分け済みである）
- 他の文書の見出しを引くときは、正準形 `` `<対象>`「<見出し>」 `` で書く（`.claude/rules/governance-docs.md`）。`RETROSPECTIVE.md` は G-heading-refs の母集団に入っている。上書きのたびに、参照の書き方が新しく決まる。ここで散文の形に戻すと、着地の照合が毎サイクル失われる

## Step 6 — メモリの鮮度チェック

サイクルで変更した内容に関連するメモリが `MEMORY.md` にあるかを確認する。

`MEMORY.md` はリポジトリの外にある（所在と委譲の決まりは、`.claude/skills/health-check/SKILL.md` の Check 7 を SSOT とする）。

1. `MEMORY.md` を読み、各メモリファイルの説明を確認する
2. サイクルの変更内容と関連するメモリを探す。索引の `description` で関連性を判断してはならない。今サイクルで覆した前提・変更した設定・仕様変更のキーワードと概念名で、メモリの本文を grep する（`description` は本文から作った要約であり、古くなった一文がそこに現れるとは限らない。手順の SSOT は health-check の Check 7d である）
3. 該当したメモリはファイルを読み、内容が現在のコードベース・ドキュメントと矛盾していないかを確かめる
4. 矛盾するメモリは更新または削除する（`MEMORY.md` のインデックスも合わせて直す）
5. サイクルで得た知見のうち、将来の会話で役に立つものがあれば、メモリに追加する

判断基準: メモリには「コードやドキュメントから読み取れない、セッションをまたいで役に立つ情報」だけを置く。コードの構造やパターンは、AGENTS.md / 各 CLAUDE.md の責務である。

## Step 7 — サイクル末の health-check

サイクル末の衛生チェックを行う（実行の責任は `/retrospective` が負う）。`/health-check` は user 起動専用（`disable-model-invocation`）なので、スキルからは起動できない。そこで、その定義 `.claude/skills/health-check/SKILL.md` に従い、同スキルの冒頭が「本スキルで実行するのは」として挙げる項目をすべて、本スキルの責任で行う（一覧の正本はそこであり、ここへ写さない）。つまり `/health-check` は起動しない。実行の方式は、インラインでもサブエージェントへの委譲でもよい。

サブエージェントへ委譲する場合は、Check 7 のためにメモリ領域の絶対パスをプロンプトへ明示して渡す（サブエージェントは system prompt を継承しないので、渡さなければ `MEMORY.md` を見つけられない）。渡さないなら Check 7 は `[Skipped]` である。`Skipped` が残ったまま「All checks passed」と報告しない（#489）。

health-check は「報告のみ・修正しない」と定義されている。そのため、見つかった事項の処理は本スキルが受け持ち、Step 3・Step 4 の方針に従って振り分ける。

- doc のドリフト（CLAUDE.md のモジュール構成・参照リンク・SPEC.md の番号・スキル表 等）→ その場で該当ドキュメントを直す（Step 3 と同じ方針）
- 実装・大規模な対応が要るもの → GitHub issue を起票する（Step 4 の振り分け）
- PR の中で閉じられるもの → 対象 PR の本文へ追記する（Step 4 の振り分け）

## 出力

次を報告する。
1. サイクルの概要（1〜2 行）
2. ドキュメントに反映した教訓（あれば、どのファイルに何を追加したか）
3. 振り分けたタスク（起票した issue 番号 / 追記した PR 本文のチェックリスト）
4. メモリの更新（あれば、追加/更新/削除したメモリ）
5. health-check の結果のまとめ（発見事項・`Skipped` とその処理・根拠）。カテゴリの定義は health-check の出力形式（`.claude/skills/health-check/SKILL.md`）を SSOT とする。根拠とは、発見事項でも `Skipped` でもない、実行した証跡である。governance:check の出力（検査の本数の行）・Check 7 の実在列挙などが当たる（発見事項の数や `All checks passed` の判定には数えない）
