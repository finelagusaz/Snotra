# Snotra Architecture Boundaries

## 目的

Snotra のレビューでは、まず「どの責務境界をまたいだ変更か」を判定する。
境界違反は局所修正に見えても回帰範囲が広い。

## 1. `snotra-core`

- 純ロジック層として扱う
- UI 表示文字列を持たない
- 検索、設定値、履歴、インデックスなどの意味論を持つ
- Win32 や Tauri の都合で API を歪めない

確認質問:
- この変更は表示文言やウィンドウ都合を `snotra-core` に持ち込んでいないか
- エラー意味はフラグや構造で返し、表示は UI 側に委ねているか

## 2. `src-tauri`

- Tauri IPC、ウィンドウ、トレイ、ホットキー、IME、子プロセスの責務を持つ
- Windows 固有機能を集約する
- 初期化順とライフサイクルの不変条件を守る

確認質問:
- リスナー登録前に機能を有効化していないか
- Win32/Tauri の制約を `ui` へ漏らしていないか

## 3. `ui`

- 表示、入力、リアクティブ状態、結果レンダリングの責務を持つ
- 表示文字列、通知文言、テーマ反映を持つ
- Rust 側の契約を前提に描画するが、検索意味論の本体は持たない

確認質問:
- 表示都合のロジックが検索の真実源になっていないか
- ライフサイクルを持つ購読や timer を単一管理しているか

## 4. `snotra-settings`

- 設定 GUI を別プロセスで持つ
- 本体との連携は `config.toml` を真実源にする
- 本体との直接 IPC を増やさない

確認質問:
- 設定反映がファイル経由の契約を壊していないか
- 子プロセス spawn と終了処理が対になっているか

## 5. API 境界のレビュー原則

- 呼び出し側パッチと API 側完結案を比較し、後者を優先する
- 境界をまたぐ不変条件は、できるだけ下位層で完結させる
- 片側だけ直してもう片側の呼び出し忘れを生む設計を避ける

確認質問:
- この不変条件は API の内側で守れるか
- 呼び出し側全員に同じ修正を要求していないか

## 6. 変更が危険な境界

- 検索結果の意味論と UI 表示条件の境界
- 初期化順とイベント購読順の境界
- 本体と設定 GUI のプロセス境界
- 履歴/インデックス/アイコンキャッシュの永続化境界
- Tauri/WebView と native window の観測境界
