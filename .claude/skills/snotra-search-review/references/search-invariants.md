# Search Invariants

## 最初に固定する不変条件

- 増分検索を使ってよいのは、今回の一致条件が前回条件の部分集合であるときだけ
- 候補集合を広げうる変化が起きたら、前回候補ではなく全件から再検索する
- `snotra-core` は検索結果の意味だけを返し、表示文言は返さない

## 一致条件の整理

レビューではフラグ名ではなく、実際に有効な検索述語の集合として考える。

典型的な述語:
- ASCII 前方一致
- ASCII 部分一致
- kana 変換後一致
- migemo 一致
- slash command 判定
- instant command 判定

確認質問:
- 今回、新しい述語が前回から追加されていないか
- その追加で候補集合は広がりうるか
- 広がるなら full scan へ落ちるか

## 増分検索が安全なケース

- クエリが前回クエリの prefix extension である
- 有効な検索モードが変わっていない
- kana / migemo の有効値が前回から新規出現していない
- 設定変更で active predicate が変わっていない

## 増分検索が危険なケース

- `migemo_min_chars` を跨いで migemo が無効 -> 有効になる
- 前回は `kana_query = None`、今回は `Some(...)` になる
- 通常検索から slash command / instant command へ切り替わる
- 履歴や設定変更で ranking predicate の意味が変わる
- query parser の結果が前回と別モードになる

## 典型的な壊れ方

### 1. 述語の新規出現

前回候補には「前回時点の述語でヒットした要素」しか含まれない。
今回初めて有効になった述語だけでヒットする要素は欠落する。

### 2. 値の非単調変化

bool では「前回も有効だった」ことしか分からない。
だが実際には、前回値と今回値の関係が prefix でないと安全ではない。

確認質問:
- `prev_migemo_enabled` のような代理指標だけで判定していないか
- 実際に比較すべきなのは `prev_kana_query` や変換後 query ではないか

## 安全側の原則

- 迷ったら full scan に倒す
- 性能劣化より false negative 防止を優先する
- キャッシュ再利用の条件は bool の組み合わせで済ませず、述語の意味で説明できるようにする
