Issue #$ARGUMENTS の調査と計画を行う。ユーザーへ確認するのは要求の判断だけである。実装の判断はコードと文書から行う。明示的な人間の承認を得るまで、実装へ渡さない。

## Step 1 — ISSUE 読み込み & 要求の曖昧さ判定

```bash
gh issue view $ARGUMENTS
```

タイトル・本文・ラベル・コメントを読む。

- 「どう作るか」が不明: コードと文書を調査して決める
- 「何を作るか」が不明: 影響の大きい 1〜2 点を質問し、回答を得てから進む

## Step 2 — main 最新化 & ブランチ作成

作業ツリーに未保存の変更が無いことを確かめてから実行する。

```bash
git checkout main
git pull --ff-only
git checkout -b <feat|fix|chore>/<short-name>
```

## Step 3 — 調査（workspace/research.md）

### 3a. 調査を書く

前のサイクルの `workspace/` の成果物は、今回の事実として再利用しない。`workspace/research.md` と `workspace/plan.md` は、今回の issue 用に書き直す。

`RETROSPECTIVE.md`、`SPEC.md`、関連する `CLAUDE.md`、コードを読み、`workspace/research.md` に次だけを書く。

- issue の要約
- 関連するファイル・モジュール・関数
- 再利用できる既存のパターン
- 技術的な制約
- 未解決の疑問

書いたファイルとシンボルは、grep で実在を確かめる。外部仕様や上流の issue を根拠にする場合は、最後の maintainer の回答と、ローカルで使っているバージョンまで確かめる。

### 3b. 敵対的調査（サブエージェント 1 体・sonnet）

`research.md` を書き終えたら、その主張を反証しにいく枠を 1 体だけ走らせる。求めるのは同意ではなく反証である。

母集団は `research.md` の全主張である。事実・関連ファイル/シンボル・技術的な制約・未解決の疑問のすべてを対象にする。「壊せた項目」と「壊せなかった項目」を両方宣言させる。後者を省くと、報告が無い項目について「見ていない」のか「壊せなかった」のかが分からなくなる（前者だけを求めると、報告の手間は壊せた項目にしかかからず、報告しない項目には手間がかからない）。

`Agent` を `subagent_type: general-purpose` / `model: sonnet` で 1 体起動し、プロンプトに次をすべて含める。

1. 争点を 5 つ前後の箇条書きで渡す。散文の要約ではなく、偽にできる形の命題として渡す。「逐語追認するな」と明記する
2. `workspace/research.md` の絶対パスと、根拠にした一次資料（issue 番号・ファイルパス）
3. 測定環境そのものを疑う指示。疑うべき形として「計測コードが測る分岐と、変更が触る分岐が違う」を名指しする。実 `config.toml` / 実 `index.bin` / env の値が調査の前提と一致するかを、実際に読みに行かせる（#1057 では 4 枠のうちこの枠だけが `normal_mode` の違いを突き止めた。その結果、「効果なし」という測定が何も測っていなかったと分かった。他の枠は計画とコードだけを見ていたので、原理的にここへ届かない）
4. 所見ごとに「この所見を偽にする手順」を書かせる
5. 確信の持てない所見（⚠️）も、返り値の列挙に含めさせる。返り値の仕様から外れた所見はファイルにしか残らず、会話に載らない
6. 出力先は呼び出し側が指定する: `workspace/adversarial-<issue番号>.txt`。名前を `report*.md` にしてはならない（Write が拒否される・実測）

委譲はコンテキストを継承しない。メインエージェントの system prompt にしか無い事実（絶対パス等）は、明示して渡す。issue に添付された画像はサブエージェントには読めない。そのため、一次証拠に画像を含む論点は、この枠で決着させない。

所見は `research.md` へ反映し、採否と理由を残す。採るのは所見であって、添えられた機序の説明ではない。機序は一次証拠を使って自分で裁定する。

## Step 4 — 実装計画（workspace/plan.md）

計画は、実装者が追加の判断をせずに実行できる粒度で書く。

- 目的と受け入れ条件
- 変更するファイルの一覧と対象シンボル
- 実装の順序
- 不変条件と異常系
- テスト方針と検証コマンド（変異注入は `/implement`「3b. 委譲へ渡すもの」の委譲先が行う。主エージェントの作業項目にはしない。主は同じ worktree へ注入しないので、主に割り当てると、実装時に計画と手順が食い違う・#1026）
- `SPEC.md`・関連文書の更新の要否
- 新しく導入する用語（仕組み・概念・状態に付ける日本語の名前）と、その語に `docs/comment-guidelines.md`「言語（日英）」の判定 (A)/(B) を当てた結果。標準の語で言えない語は、初めて書く箇所で括弧に原語か一言の説明を添える。ほかのファイルに既にある語を書くなら、`docs/glossary.md` に足すことも作業項目に入れる。用語を導入しないなら、この項目は省く（直訳語の多くは、新しい仕組みに名前を付けた時点で生まれ、その後は写されて広まった。#1376 までの整備で実測した。「道具の木」は verify:tree の導入時に生まれた）
- フェーズごとの `- [ ]` 作業項目

さらに、次の 2 節を必ず置く。

```markdown
## 未確定（実装前に潰す）

- [ ] <未確定事項> — <測る・決める・裏取りする方法>

## 人間レビュー

- [ ] 承認待ち
```

未確定事項を解消したら `- [x]` にする。測定値・判断・却下の理由を残し、計画の本文にも反映する。作業項目と未確定事項を混ぜない。

判定で分岐する作業は、作業項目に置かない。未確定欄の潰し方として書く。「勝ったら実装 / 負けたらクローズ」のように片方しか実行されない分岐を作業項目にすると、どちらへ転んでも、もう片方が `- [ ]` のまま残る。これは引き渡し契約（未確定欄が空）と、`gh pr create` の未チェックガード（#749）の両方に引っかかる。作業項目は、勝敗のどちらでも実行するものだけで組む。分岐の中身は、未確定事項の「測る・決める」側へ書く。判定が出たら計画を書き換え、消えた分岐は削除する（#1059 では「先に最小実装で単価を測り、勝たなければクローズする」を issue 自身が課しており、この形で閉じた）。

作業項目に置くのは、計画が受け持つ作業だけである。コミット以降（コミット・push・PR 作成・マージ）は置かない。境界は「コミットより手前か」で決める。語が一致するかでは決めない。`/implement` のコミットと `workspace/` の撤去、そのあとの push・PR 作成・マージはすべて該当する。「実装差分を確定させる」のように、コミットの前に真になる状態なら置いてよい。コミット以降を置くと、必ず次のどちらかになる。実施の前に `- [x]` を付ければ、まだ起きていない行為を完了と主張することになる。同時に `gh pr create` の未チェックガード（#749）も解除してしまう。実施の後に付ければ、そのチェックを含むコミットが未チェックのまま残る（#922 では前者になり、実装を 1 行も含まない PR を立てられる状態になっていた）。

## Step 5 — 計画検証と人間レビュー

### 5a. check スキルによる計画検証

#### 収束判定に要る状態はすべて `plan.md` に置く

別の台帳・スナップショット・会話履歴を、未確定ゼロやレビュー完了の判定根拠にしない。

最初に、主エージェント自身が次を照合する。

1. issue の全要件に作業項目が対応している
2. 境界条件を列挙し、各条件に検証がある
3. 新しい状態・リソース・プロセスに、正常/失敗/破棄の経路がある
4. より単純な既存のパターンで置き換えられないか
5. 壊してはならない不変条件に、検知の手段がある

その後、`AGENTS.md`「条件別チェック（トリガー → 参照先）」に該当する check スキルだけを実行する。

`/plan-review` は常には実行しない。`/plan-review`「リスク判定」の高リスク条件に該当する場合だけ、1 回実行する。

網羅性が要件のとき、またはガバナンス文書を移動・圧縮・分割するときは、`/plan-review --deep` を使う。それ以外は `/plan-review` を使う。結果のうち対処が要るものを計画へ反映し、未確定欄を空にする。

### 5b. セルフレビュー（plan-review 固有の補完）

`/plan-review` を実行しなかった場合も、5a の自己レビューの結果を `workspace/plan.md` の末尾へ記録する。

```markdown
## セルフレビュー

- リスク: 通常 / 高
- plan-review: 未実施（通常リスク） / 自己レビューのみ / 独立レビュー1体
- エージェント数: 0 / 1
- 要対処: <件数と反映内容>
- 未検証: <なし、または理由>
- 散文の全件列挙: 語 <n> / 総件数 <x> 行 / ★未掲載 <m>（計画へ足した <k>） / 未実施（通常リスク）
- 試行（#1300・高リスクのみ・独立レビュー 1 回ごとに 1 行）: 方式 Step 2 / Step 2b / 設計変更 <n> / 主の見落とし <n>
```

「散文の全件列挙」は、`/plan-review`「Step 1 — plan.md の読み込み」が実行する `prose:sweep` の見出し行から写す。高リスクでこの欄が空なら、変更で偽になる散文の照合は行われていない。「試行」の行は、#1300 の試行のための足場である。列の意味は、#1300 の本文の表に従う。この行は、5c の承認のあとに #1300 へコメントする（承認の前に計画が変わると、古い行が残るため）。#1300 が閉じたら、`.claude/skills` で #1300 に触れる箇所をすべて、試行の結論に合わせて消すか直す（`git grep '#1300' .claude/skills` で数える）。

### 5c. 人間の注釈と承認

計画の草案を示し、ユーザーへ次のどちらかを依頼して停止する。

1. `workspace/plan.md` へ注釈を追加する
2. 計画を明示的に承認する

注釈があれば、すべて反映する。そのうえで、実装を変える差分かどうかを判定する。要件・対象ファイル/シンボル・インターフェース・不変条件・テストの期待値が変わった高リスクの計画だけ、`/plan-review` を追加で 1 回実行する。説明文だけの訂正では再実行しない。

承認を得たら、次の形へ更新する。

```markdown
## 人間レビュー

- [x] 承認済み — <YYYY-MM-DD> / 問い: "<承認を求めた問いの逐語引用>" / 回答: "<ユーザー発言の逐語引用>"
```

高リスクなら、承認を記録したあとに、5b の「試行」の行を issue 番号つきで #1300 へコメントする。5c で `/plan-review` を再実行したなら、その回の分を 2 行目として足し、両方の行をコメントする。置き換えも合算もしない（#1300 の表の「回数」は、独立レビューの回数である）。`workspace/` は PR の前に撤去され、main に残らない。そのため、記録の正本は #1300 のコメントである。

明示的な承認が無ければ、Step 6 へ進まない。

## Step 6 — workspace をコミット & プッシュ

未確定欄に `- [ ]` がなく、人間レビューが承認済みであることを確かめてから実行する。

```bash
git add workspace/
git commit -m "chore: workspace 調査・計画 (issue #$ARGUMENTS)"
git push -u origin HEAD
```

## 出力

1. issue の要約
2. ブランチ名
3. 敵対的調査（3b）の所見。壊せた項目と壊せなかった項目の両方と、その採否と理由
4. 計画の変更ファイル数・フェーズ数
5. リスク判定、plan-review の方式、起動したエージェント数（3b の 1 体を含む）
6. 人間レビューの承認記録（高リスクなら、#1300 へ書いた試行のコメントの URL も）
7. 次のアクション: `/implement` で実装できること

引き渡し契約: `workspace/plan.md` は、未確定欄が空で、人間レビューが明示的に承認済みである。高リスクの計画で、独立レビューの後に実装を変える差分が入った場合は、その差分だけ追加のレビューを済ませている。
