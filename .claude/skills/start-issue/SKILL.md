Issue #$ARGUMENTS の調査と計画を行う。要求判断だけをユーザーへ確認し、実装判断はコードと文書から行う。**明示的な人間の承認を得るまで実装へ渡さない。**

## Step 1 — ISSUE 読み込み & 要求の曖昧さ判定

```bash
gh issue view $ARGUMENTS
```

タイトル・本文・ラベル・コメントを読む。

- 「どう作るか」が不明: コードと文書を調査して決める
- 「何を作るか」が不明: 影響の大きい1〜2点を質問し、回答後に進む

## Step 2 — main 最新化 & ブランチ作成

作業ツリーに未保存の変更が無いことを確認してから実行する。

```bash
git checkout main
git pull --ff-only
git checkout -b <feat|fix|chore>/<short-name>
```

## Step 3 — 調査（workspace/research.md）

前サイクルの `workspace/` 成果物は今回の事実として再利用しない。`workspace/research.md` と `workspace/plan.md` を今回のissue用に書き直す。

`RETROSPECTIVE.md`、`SPEC.md`、関連する `CLAUDE.md`、コードを読み、`workspace/research.md` に次だけを書く。

- issue の要約
- 関連ファイル・モジュール・関数
- 再利用できる既存パターン
- 技術的制約
- 未解決の疑問

記載したファイルとシンボルは grep で実在を確認する。外部仕様や上流issueを根拠にする場合は、最終maintainer回答とローカルで使用中のバージョンまで確認する。

## Step 4 — 実装計画（workspace/plan.md）

計画は、実装者が追加判断せず実行できる粒度で書く。

- 目的と受け入れ条件
- 変更ファイル一覧と対象シンボル
- 実装順序
- 不変条件と異常系
- テスト方針と検証コマンド
- `SPEC.md`・関連文書の更新要否
- フェーズごとの `- [ ]` 作業項目

さらに次の2節を必ず置く。

```markdown
## 未確定（実装前に潰す）

- [ ] <未確定事項> — <測る・決める・裏取りする方法>

## 人間レビュー

- [ ] 承認待ち
```

未確定事項を解消したら `- [x]` にし、測定値・判断・却下理由を残して計画本文にも反映する。作業項目と未確定事項を混ぜない。

## Step 5 — 計画検証と人間レビュー

### 5a. check スキルによる計画検証

#### 収束判定に要る状態はすべて `plan.md` に置く

別の台帳・スナップショット・会話履歴を、未確定ゼロやレビュー完了の判定根拠にしない。

最初に主エージェント自身が次を照合する。

1. issue の全要件に作業項目が対応する
2. 境界条件を列挙し、各条件に検証がある
3. 新しい状態・リソース・プロセスに正常/失敗/破棄経路がある
4. より単純な既存パターンで置き換えられないか
5. 壊してはならない不変条件に検知手段がある

その後、`AGENTS.md`「条件別チェック（トリガー → 参照先）」に該当するcheckスキルだけを実行する。

`/plan-review` は常時実行しない。次のいずれかなら1回だけ実行する。

- 永続形式・設定キー・公開API・状態遷移の変更
- worker・channel・listener・共有状態・非同期処理の変更
- hook・CI・rules・skills・ガバナンス文書の変更
- 網羅性が要件、またはガバナンス文書を移動・圧縮・分割する
- 複数モジュール間のインターフェース変更
- ユーザーが独立レビューを要求

網羅性が要件、またはガバナンス文書を移動・圧縮・分割するなら `/plan-review --deep`、それ以外は `/plan-review` を使う。結果の要対処を計画へ反映し、未確定欄を空にする。

### 5b. セルフレビュー（plan-review 固有の補完）

`/plan-review` を実行しなかった場合も、5aの自己レビュー結果を `workspace/plan.md` 末尾へ記録する。

```markdown
## セルフレビュー

- リスク: 通常 / 高
- plan-review: 未実施（通常リスク） / 自己レビューのみ / 独立レビュー1体
- エージェント数: 0 / 1
- 要対処: <件数と反映内容>
- 未検証: <なし、または理由>
```

### 5c. 人間の注釈と承認

計画草案を提示し、ユーザーへ次のどちらかを依頼して**停止する**。

1. `workspace/plan.md` へ注釈を追加する
2. 計画を明示的に承認する

注釈があればすべて反映し、実装を変える差分か判定する。要件・対象ファイル/シンボル・インターフェース・不変条件・テスト期待値が変わった高リスク計画だけ、`/plan-review` を追加で1回実行する。説明文だけの訂正では再実行しない。

承認後、次の形へ更新する。

```markdown
## 人間レビュー

- [x] 承認済み — <YYYY-MM-DD、承認したユーザー発言の短い引用>
```

明示的な承認が無ければ Step 6 へ進まない。

## Step 6 — workspace をコミット & プッシュ

未確定欄に `- [ ]` がなく、人間レビューが承認済みであることを確認してから実行する。

```bash
git add workspace/
git commit -m "chore: workspace 調査・計画 (issue #$ARGUMENTS)"
git push -u origin HEAD
```

## 出力

1. issue の要約
2. ブランチ名
3. 計画の変更ファイル数・フェーズ数
4. リスク判定、plan-review方式、起動したエージェント数
5. 人間レビューの承認記録
6. 次のアクション: `/implement` で実装できること

**引き渡し契約**: `workspace/plan.md` は、未確定欄が空で、人間レビューが明示的に承認済みである。高リスク計画で独立レビュー後に実装を変える差分が入った場合は、その差分だけ追加レビュー済みである。
