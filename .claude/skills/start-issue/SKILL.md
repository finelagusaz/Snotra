Issue #$ARGUMENTS の調査と計画を行う。要求判断だけをユーザーへ確認し、実装判断はコードと文書から行う。**明示的な人間の承認を得るまで実装へ渡さない。**

## Step 1 — ISSUE 読み込み & 要求の曖昧さ判定

```bash
gh issue view $ARGUMENTS
```

タイトル・本文・ラベル・コメントを読む。

- 「どう作るか」が不明: コードと文書を調査して決める
- 「何を作るか」が不明: 影響の大きい1〜2点を質問し、回答後に進む

## Step 2 — main 最新化 & ブランチ作成

作業ツリーに未保存の変更が無いことを確認してから実行する。

```bash
git checkout main
git pull --ff-only
git checkout -b <feat|fix|chore>/<short-name>
```

## Step 3 — 調査（workspace/research.md）

### 3a. 調査を書く

前サイクルの `workspace/` 成果物は今回の事実として再利用しない。`workspace/research.md` と `workspace/plan.md` を今回のissue用に書き直す。

`RETROSPECTIVE.md`、`SPEC.md`、関連する `CLAUDE.md`、コードを読み、`workspace/research.md` に次だけを書く。

- issue の要約
- 関連ファイル・モジュール・関数
- 再利用できる既存パターン
- 技術的制約
- 未解決の疑問

記載したファイルとシンボルは grep で実在を確認する。外部仕様や上流issueを根拠にする場合は、最終maintainer回答とローカルで使用中のバージョンまで確認する。

### 3b. 敵対的調査（サブエージェント 1 体・sonnet）

`research.md` を書き終えたら、**その主張を壊しにいく**枠を 1 体だけ走らせる。同意でなく反証を求める。

**母集団は `research.md` の全主張である**——事実・関連ファイル/シンボル・技術的制約・未解決の疑問のすべてを対象にし、**「壊せた項目」と「壊せなかった項目」を両方宣言させる**。後者を省くと、沈黙が「見ていない」と「壊せなかった」のどちらか分からなくなる（前者だけを求めると、費用が見つけた側にしか掛からない）。

`Agent` を `subagent_type: general-purpose` / `model: sonnet` で 1 体起動し、プロンプトに次をすべて含める。

1. **争点を 5 つ前後の箇条書きで渡す**——散文の要約ではなく、**偽にできる形の命題**として。「逐語追認するな」と明記する
2. **`workspace/research.md` の絶対パス**と、根拠にした一次資料（issue 番号・ファイルパス）
3. **測定環境そのものを疑う指示。** 「計器が測る枝と、変更が触る枝が違う」を疑うべき形として名指しし、実 `config.toml` / 実 `index.bin` / env の値が調査の前提と一致するかを**読みに行かせる**（#1057 では 4 枠のうちこの枠だけが `normal_mode` の違いを突き止め、「効果なし」という測定が何も測っていなかったと判明した——他の枠は計画とコードだけを見ており原理的に到達できない）
4. **所見ごとに「この所見を偽にする手順」を書かせる**
5. **確信の持てない所見（⚠️）も返り値の列挙に含めさせる**——返り値仕様から外れた所見はファイルにしか残らず会話に載らない
6. **出力先は呼び出し側が指定する**: `workspace/adversarial-<issue番号>.txt`。**`report*.md` にしてはならない**（Write が拒否される・実測）

**委譲はコンテキストを継承しない。** メインエージェントの system prompt にしか無い事実（絶対パス等）は明示的に渡す。**issue 添付の画像はサブエージェントに読めない**ので、一次証拠に画像を含む論点はこの枠で決着させない（`CLAUDE.md`「サブエージェント委譲と worktree」）。

所見は `research.md` へ反映し、**採否と理由を残す**。**採るのは所見であって、添えられた機序の説明ではない**——機序は一次証拠で自分で裁定する。

## Step 4 — 実装計画（workspace/plan.md）

計画は、実装者が追加判断せず実行できる粒度で書く。

- 目的と受け入れ条件
- 変更ファイル一覧と対象シンボル
- 実装順序
- 不変条件と異常系
- テスト方針と検証コマンド
- `SPEC.md`・関連文書の更新要否
- フェーズごとの `- [ ]` 作業項目

さらに次の2節を必ず置く。

```markdown
## 未確定（実装前に潰す）

- [ ] <未確定事項> — <測る・決める・裏取りする方法>

## 人間レビュー

- [ ] 承認待ち
```

未確定事項を解消したら `- [x]` にし、測定値・判断・却下理由を残して計画本文にも反映する。作業項目と未確定事項を混ぜない。

**判定で分岐する作業を作業項目に置かない——未確定欄の潰し方として書く。** 「勝ったら実装 / 負けたらクローズ」のように片方しか実行されない枝を作業項目にすると、**どちらへ転んでも他方が `- [ ]` のまま残り**、引き渡し契約（未確定欄が空）と `gh pr create` の未チェックガード（#749）の両方に触れる。作業項目は**勝敗のどちらでも実行するもの**だけで構成し、分岐の中身は未確定事項の「測る・決める」側へ書く。判定が出たら計画を書き換え、消えた枝は削除する（#1059 は「先に最小実装で単価を測り、勝たなければクローズする」を issue 自身が課しており、この形で閉じた）。

**作業項目に置くのは計画が所有する作業だけである——コミット以降（コミット・push・PR 作成・マージ）を置かない。** 境界は「コミットより手前か」であって語の一致ではない: `/implement` Step 5 以降の手順はすべて該当し、「実装差分を確定させる」のように**コミット前に真になる状態**なら置いてよい。置くと必ずどちらかへ転ぶ: 実施**前**に `- [x]` を付ければ、まだ起きていない行為を完了として主張し、同時に `gh pr create` の未チェックガード（#749）を解除する。実施**後**に付ければ、そのチェックを含むコミットが未チェックのまま残る（#922 で前者を踏み、実装を 1 行も含まない PR を立てられる状態になっていた）。

## Step 5 — 計画検証と人間レビュー

### 5a. check スキルによる計画検証

#### 収束判定に要る状態はすべて `plan.md` に置く

別の台帳・スナップショット・会話履歴を、未確定ゼロやレビュー完了の判定根拠にしない。

最初に主エージェント自身が次を照合する。

1. issue の全要件に作業項目が対応する
2. 境界条件を列挙し、各条件に検証がある
3. 新しい状態・リソース・プロセスに正常/失敗/破棄経路がある
4. より単純な既存パターンで置き換えられないか
5. 壊してはならない不変条件に検知手段がある

その後、`AGENTS.md`「条件別チェック（トリガー → 参照先）」に該当するcheckスキルだけを実行する。

`/plan-review` は常時実行しない。`/plan-review`「リスク判定」の高リスク条件に該当する場合だけ1回実行する。

網羅性が要件、またはガバナンス文書を移動・圧縮・分割するなら `/plan-review --deep`、それ以外は `/plan-review` を使う。結果の要対処を計画へ反映し、未確定欄を空にする。

### 5b. セルフレビュー（plan-review 固有の補完）

`/plan-review` を実行しなかった場合も、5aの自己レビュー結果を `workspace/plan.md` 末尾へ記録する。

```markdown
## セルフレビュー

- リスク: 通常 / 高
- plan-review: 未実施（通常リスク） / 自己レビューのみ / 独立レビュー1体
- エージェント数: 0 / 1
- 要対処: <件数と反映内容>
- 未検証: <なし、または理由>
```

### 5c. 人間の注釈と承認

計画草案を提示し、ユーザーへ次のどちらかを依頼して**停止する**。

1. `workspace/plan.md` へ注釈を追加する
2. 計画を明示的に承認する

注釈があればすべて反映し、実装を変える差分か判定する。要件・対象ファイル/シンボル・インターフェース・不変条件・テスト期待値が変わった高リスク計画だけ、`/plan-review` を追加で1回実行する。説明文だけの訂正では再実行しない。

承認後、次の形へ更新する。

```markdown
## 人間レビュー

- [x] 承認済み — <YYYY-MM-DD> / 問い: "<承認を求めた問いの逐語引用>" / 回答: "<ユーザー発言の逐語引用>"
```

明示的な承認が無ければ Step 6 へ進まない。

## Step 6 — workspace をコミット & プッシュ

未確定欄に `- [ ]` がなく、人間レビューが承認済みであることを確認してから実行する。

```bash
git add workspace/
git commit -m "chore: workspace 調査・計画 (issue #$ARGUMENTS)"
git push -u origin HEAD
```

## 出力

1. issue の要約
2. ブランチ名
3. 敵対的調査（3b）の所見——**壊せた項目と壊せなかった項目の両方**、および採否と理由
4. 計画の変更ファイル数・フェーズ数
5. リスク判定、plan-review方式、起動したエージェント数（3b の 1 体を含む）
6. 人間レビューの承認記録
7. 次のアクション: `/implement` で実装できること

**引き渡し契約**: `workspace/plan.md` は、未確定欄が空で、人間レビューが明示的に承認済みである。高リスク計画で独立レビュー後に実装を変える差分が入った場合は、その差分だけ追加レビュー済みである。
