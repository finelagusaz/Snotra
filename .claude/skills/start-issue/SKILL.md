Issue #$ARGUMENTS の作業を開始する。実装判断は自律的に行い、要求判断が必要な場合のみ確認する（後述）。

## Step 1 — ISSUE 読み込み & 要求の曖昧さ判定

```bash
gh issue view $ARGUMENTS
```

issue の内容（タイトル・本文・ラベル・コメント）を把握し、**要求が一意に解釈できるか判定する**:

- **実装の曖昧さ**（「どう作るか」が不明）→ コードとドキュメントから解決できる → そのまま進む
- **要求の曖昧さ**（「何を作るか」が不明）→ コードをいくら読んでも答えが出ない → 質問してから進む

要求の曖昧さがある場合、最も影響の大きい1〜2点に絞って質問する。例:
- UI の見た目・操作フロー
- 既存動作を変えるのか、追加するのか
- 対象範囲（全項目か、特定条件のみか）

回答を得てから Step 2 に進む。

## Step 2 — main 最新化 & ブランチ作成

以下を順に実行する:

```bash
git checkout main
```

```bash
git pull --ff-only
```

issue の内容から適切なブランチ名を決める:
- 機能追加: `feat/<短い説明>`
- バグ修正: `fix/<短い説明>`
- その他: `chore/<短い説明>`

```bash
git checkout -b <branch-name>
```

## Step 3 — 調査と分析（workspace/research.md）

`workspace/research.md`・`workspace/plan.md`・`workspace/plan-snapshot.md`（`/start-issue`「5a. check スキルによる計画検証」がラウンドごとに取る `plan.md` の複製）・`workspace/plan-review/`（ディレクトリごと。`/plan-review`「Step 2 — 並列サブエージェントで検証」のスカウトと「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」の成果物。ファイル名が毎回変わるため列挙せず、**新鮮性は「上書き」ではなく `/plan-review` Step 2 が起動前に行う削除が保証する**——上書きは書き手が落ちた回には起きない）が既に存在する場合は上書きする（前回の作業成果物）。**このサイクルで書き直すファイルはここに列挙されたものだけである**——列挙から漏れたものは前サイクルの内容のまま残り、次に読む人が今回の成果物と誤読する（`workspace/measurement.md` が #628 のまま取り残されている実例がある）。

`SPEC.md`、関連する `CLAUDE.md`、ソースコードを読み、issue の要求を分析する。

`workspace/research.md` に以下を出力:

- **issue の要約**: 何を解決/実現するか
- **関連コード**: 影響を受けるファイル・モジュール・関数の列挙
- **既存パターン**: 類似の実装が既にあるか、再利用できるか
- **技術的制約**: Win32 依存、IPC 境界、イベントループのメッセージポンプ制約（`src-tauri/CLAUDE.md`「ウィンドウ生成の制約」）など。Win32 API を使う場合、`SendInput`/`SetForegroundWindow`/`ShowWindow` 等の入力・ウィンドウ系 API は部分的に非同期な場合がある。計画時に MSDN で同期性を確認し、技術的制約に記録する
- **未解決の疑問**: 調査で判明しなかった点（あれば）

**書くのは調査で判明した事実だけである。** 読んだが計画に影響しなかったファイルの要約・前置き・一般論を書かない——`research.md` は次に `plan.md` を書くための入力であって、読んだ量の証明ではない。**ただしこれは出力の制限であって、調査範囲の制限ではない**——「影響しなかった」と判定できるのは読んだ範囲だけであり、読まなかったファイルはこの判定にすら現れない。

**列挙の事実確認**: 「関連コード」に挙げたファイル・関数が実在し、説明が正確かを grep で確認してから Step 4 へ進む。研究の前提誤りは plan へ伝播する——`/plan-review`「Step 2b」 の独立再導出が伝播後に拾うが、前提はここで正すのが最も安い。

**外部ソースが根拠のときの追加確認**（外部 issue・上流バグ・外部仕様を根本原因の根拠にする場合のみ発火。使わない issue では不要）: issue 本文冒頭の説明を確定事実とせず、timeline を**最終 maintainer 回答**まで辿って現在の結論（fixed / reverted / 未修正）を掴んでから前提として扱う。上流の記述とローカル実装（使用中バージョン・設定者→中間層→実 consumer の実行経路）が食い違うときは、どちらを採用したかを理由付きで `research.md` に記す。上の実在確認が内部前提を、`/plan-review`「Step 2b」 がコードベースを覆うのに対し、**外部の事実だけはどの下流検査も再導出できない**——ここで正さなければ後段で拾えない（#565。内部前提=能力・根本原因診断の裏取りは `docs/development-principles.md`「デバッグ・バグ修正」節）。

## Step 4 — 実装計画（workspace/plan.md）

`workspace/research.md` の分析結果をもとに、`workspace/plan.md` に実装計画を作成する。

計画には以下を含める:

- **変更ファイル一覧**: 各ファイルで何を変更するか
- **実装順序**: 依存関係を考慮したフェーズ分け
- **不変条件**: 各変更が守るべき不変条件。新たな状態フラグ・プロセス・ウィンドウ・リソースを導入する場合は「失敗・異常終了・予期しない順序で呼ばれたときにどうなるか」も含めて記述する
- **テスト方針**: 追加・更新するテストと検証コマンド
- **サンプルコードを載せるなら構造の理由を付記する**: リソース管理・非同期処理の配置が問われる箇所に「なぜこの構造か」をコメントする（配置だけを写すと、実装が理由を知らないまま形を崩す）
- **SPEC.md 更新要否**: 挙動変更を伴う場合は更新内容を記載
- **未確定（実装前に潰す）**: 下記の専用節。**計画の完成とは、この欄が空になることである**

### 「未確定（実装前に潰す）」節

計画が目指すのは網羅的な記述ではなく、**実装時に判断が要らない状態**である。まだ決まっていないものを隠さず 1 か所へ集める。

- 見出しは `## 未確定（実装前に潰す）— ラウンド N` とする。**照合は固定接頭辞への前方一致**（`## 未確定（実装前に潰す）` で始まる行）で行い、完全一致で探さない——ラウンド番号が付くため見失う
- `- [ ]` で列挙し、各項目は 2 つを持つ: **(a) 何が決まっていないか / (b) どう確定させるか**（測る・決める・裏取りする）
- **フェーズ配下の作業項目とは別のリストである**（作業項目は「何を実装するか」、未確定は「何が決まっていないか」。後者だけが着手の可否を決める）
- 確定したら `- [x]` にし、**確定させた結果**（測定値・裁定・却下した代替案）を残す。**さらにその結果を計画本文（変更ファイル一覧・実装順序・不変条件・テスト方針）へ畳み込む**——欄の中だけで完結した差分は、次ラウンドのレビュー範囲の判定に乗らない
- **裁定によって受容した項目には、裁定の出所（ユーザー発言の引用と日付）を書く。** `- [x]` へ倒す手順は脱出レシピでもあり、機構は止めない。事後に監査できる形だけを残す
- **最初に埋めるのはレビューではなく、計画を書いた当人である。** ここで先に埋めて潰せるものを潰すほど、5a のラウンドが減る。埋める観点は 5 つ——判定ロジック・値が実データで確定しているか / 選択が決着しているか / 事実の裏取りが済んでいるか / 境界と異常系を列挙したか / 完了の判定を書いたか

例:

```markdown
## 未確定（実装前に潰す）— ラウンド 1

- [ ] 述語が「非空かつ全エントリ deny」で足りるか — **測る**: 必須要素が 1 つ消えた
      入力を作り、実データを含む代表ケースで両案を実行して比べる
- [ ] `members` の glob 要素を展開するか — **決める**: 現在 0 件。展開器は YAGNI か
```

**作業項目はチェックリストで列挙する**: 実行を要する作業項目は、すべてフェーズ配下の `- [ ]` 行として列挙する。散文は説明であり、**散文にだけ書かれた作業は存在しない扱いになる**。フェーズごとの「完了条件」を別に書かない——チェックボックス列そのものが唯一の作業列挙 = 完了条件である（#749: 本文に書いた作業が完了条件に写らず実行から落ちた）。未チェックの `- [ ]` が残ったままの `gh pr create` は PreToolUse hook が拒否する（`CLAUDE.md`「フック」）。**この段落が言う散文は、作業項目としての散文である——各チェック項目の判断根拠に限る。上の 5 セクション（変更ファイル一覧・実装順序・不変条件・テスト方針・SPEC.md 更新要否）はこの制限の対象外である**（不変条件とテスト方針は `.claude/agents/code-reviewer.md`「2a. plan.md 不変条件との照合」と `/plan-review`「Step 1 — plan.md の読み込み」が読む入力であり、削ると照合対象ゼロのまま「違反なし」に見える）。

`docs/development-principles.md` の開発原則（KISS/DRY/YAGNI）と `AGENTS.md`「開発ワークフロー」の実装着手前（判定・要件確定・影響範囲・事前調査）に従うこと。

## Step 5 — セルフレビュー & 計画更新

### 5a. check スキルによる計画検証

計画の内容に応じて該当する check スキルを実行し、計画の見落としを検出する。発見事項があれば計画を更新する。

- `/plan-review` は**常に実行**する（サブエージェントで影響範囲・不変条件・スコープを並列検証）。**1 回では終わらない——下記のループを回す。**
- ほかの check スキルは、**`AGENTS.md`「条件別チェック（トリガー → 参照先）」表に従って**選ぶ（トリガー→検査の写像の SSOT はその表。二重管理を避けるためここに再掲しない）。判定対象は**計画が記述する設計上の操作**であって、既存コードの grep 結果ではない。

#### レビューのループ（上限 3 ラウンド）

```
ラウンド N:
  0. 先に未確定欄の見出しのラウンド番号を N へ繰り上げ、その後で plan.md を
     workspace/plan-snapshot.md へ複製する（このラウンドで計画が動いたかの基準）
  1. /plan-review を回す
  2. 指摘を必ずどちらかへ落とす:
       (a) 計画の修正       — 答えが決まっているもの
       (b) 未確定欄への追加 — 測る・決める・裏取りするまで答えが出ないもの
  3. 未確定欄を潰す（実測・裁定・裏取り）。潰せた項目を - [x] にし、結果を計画本文へ
     畳み込む。潰す作業が新しい疑問を生んだら、それも欄へ足す
  4. 収束判定（2 条件の AND）:
       (i)  未確定欄に - [ ] が残っていない
       (ii) plan-snapshot.md と plan.md の差分が空（このラウンドで計画が動かなかった）
       両方成立 → 収束。ループを抜ける
       いずれか不成立 → ラウンド N+1 へ
```

- **手順 0 の順序を守る。** 繰り上げを複製の後に行うと、繰り上げそのものが差分になって **(ii) が恒偽**になり、全サイクルが上限 3 の打ち切りへ落ちる。複製先を `workspace/plan-review/` の中に置いてもいけない（`/plan-review`「Step 2 — 並列サブエージェントで検証」の削除で消える）
- **条件 (ii) を落とさない。** (i) だけだと、**最終ラウンドで未確定を潰した結果が誰のレビューも受けずに収束する**。(i) は「実装へ渡れるか」、(ii) は「再レビューが要るか」で、**別の問いを 1 つの判定器に畳んではならない**（#821）
- **不着（独立レビュー不成立）が残るラウンドは収束と判定しない。** そのレイヤーは検証されていないのであって、問題が無かったのではない。次ラウンドで必ず起動し直す
- **収束を保証するのは上限 3 である。**「レビューが疑問を増やし、実測が減らす」という非対称は成り立たない——実測こそ新しい疑問を生む（#713 では述語を実データへ当てた実測が欠陥を出した）
- **3 ラウンドで収束しなければ止めてユーザーへ返す。** 残っている未確定項目と、それを潰せなかった理由を添える。無言で 4 ラウンド目に入らない。人が「受容して進む」と裁定したら、`- [x]` へ倒して受容する残余・理由・裁定の出所を書く（`- [ ]` のまま残さない——PreToolUse hook が `gh pr create` を拒むため受容して進む経路が塞がり、さらに残留した `workspace/plan.md` が次サイクルの無関係な PR まで拒む）
- **収束したら `workspace/plan-snapshot.md` を削除する。** 判定に使い終えた複製であり、残すと Step 6 のコミットに `plan.md` のほぼ写しが入る。途中でセッションが切れた場合は残るが、次ラウンドの手順 0 が上書きする
- **収束判定に要る状態はすべて `plan.md` に置く。** 持続する面はそれだけである（`workspace/plan-review/` は毎ラウンド削除され、セルフレビュー節への記録は収束後、会話コンテキストは中断で巻き戻る）。ラウンド番号を見出しへ、確定結果を本文へ畳み込むのはこの原則の系である

### 5b. セルフレビュー（plan-review 固有の補完）

Step 5a の `/plan-review` が **①対称コードパス ②影響範囲の網羅性（呼び出し元 grep）③リソース管理（生成/破棄ペア・`false` に戻さない `AtomicBool`／`join()` の無い `thread::spawn`／`kill(` の無い子プロセス）④既存パターンとの整合 ⑤YAGNI** を検証済みである（`/plan-review`「Step 2」の観点＋ `/plan-review`「Step 2b」の独立再導出）。**5b でこれらを再実行しない**——同一 plan.md への二度手間を避ける。plan-review の「要対処」を確認し、あれば `workspace/plan.md` を更新する。

**ただしこの免除は、plan-review が「独立レビュー不成立」と報告したエントリには及ばない**——そのレイヤーの ①〜⑤ は検証されていない。5b で自ら確認する（**`/plan-review` の再実行は `workspace/plan-review/` を作り直すため、届いていた他エントリの成果物も消える**——当該レイヤーだけを 5b で見る方が安い）。**不成立が残るならその事実と代替検証を `workspace/plan.md` 末尾の「セルフレビュー」セクションに記す**（本ファイル末尾の引き渡し契約「未確定がゼロの計画」が偽になるのを防ぐ）。**ループでは次ラウンドが当該レイヤーを起動し直す方が確実である**——不成立のエントリは「当ラウンド対象外」を名乗れない（`/plan-review`「Step 2 — 並列サブエージェントで検証」）。5b の自力確認はそれより安い代替であって、上位互換ではない。

5b は**各ラウンドの中で**適用する（5a の手順 2〜3 の一部である）。ラウンドをまたいで 1 度だけ行うものではない。

5b では **plan-review が扱わない次の3観点だけ**を追加で確認し、問題があれば計画を修正する:

1. **境界条件**: エッジケースの検証ケースが計画に含まれているか（境界を列挙し最低1件ずつ・`AGENTS.md`「事前調査（レビュー未然防止）」）
2. **シンプル化の挑戦**: 「この設計、本当にこの複雑さが必要か」— 新たな状態（`AtomicBool`・`Mutex`・子プロセス等）・汎用インターフェース・暗黙の前提を導入する箇所について、より単純な代替がないか問い直す。「この操作が失敗したらどうなるか」を設計段階で書けているか
3. **破壊不変条件 + 検知手段**: この変更で「壊れたら即アウト」なシステム不変条件を列挙し、**検知手段（テスト・スモーク・手動確認手順）とセットで** plan.md に記述したか。特に Win32 フック・ホットキー・プロセス間通信など「戻ってこない」系のリスク。plan-review は「失敗時どうなるか」までは見るが、検知手段の有無はここで確認する

plan-review の結果（要対処の解消）と 5b の3観点を、`workspace/plan.md` 末尾の「セルフレビュー」セクションに記録する。**記録は収束（または打ち切り）の後に 1 度だけ書く**——ラウンドの途中で書くと、その記述自体が差分になって収束条件 (ii) が成立しなくなる。書く内容は、回したラウンド数・最終ラウンドの結果・不成立エントリの有無・打ち切った場合はその事実である。

## Step 6 — workspace をコミット & プッシュ

セッション断絶・別マシン継続に備え、`workspace/` を必ずコミットしてプッシュする。以下を順に実行する:

```bash
git add workspace/
```

```bash
git commit -m "chore: workspace 調査・計画 (issue #$ARGUMENTS)"
```

```bash
git push -u origin HEAD
```

## 出力

最後に以下を報告:

1. issue の要約（1〜2行）
2. 作成したブランチ名
3. 計画の概要（変更ファイル数・フェーズ数）
4. 回したラウンド数と、収束したか打ち切ったか
5. セルフレビューで修正した点（あれば）
6. 次のアクション: `/implement` で実装に進めること

**引き渡し契約**: ここで渡す `workspace/plan.md` は**未確定がゼロの計画**である——未確定欄が在り、そこに `- [ ]` が 1 つも残っておらず、その最終形が `/plan-review` を通っている。`/implement` はこの前提で計画を読み、調査をやり直さない。**「レビューを 1 度通した」では足りない**——レビュー後に育った部分は、どのレビューも受けていない（#821）。打ち切って渡す場合は、受容した未確定と裁定の出所が `plan.md` に残っている。
