$ARGUMENTS に関連する対称性を、2つの軸（コードパスの対称・リソースのライフサイクルの対称）で検証する。
$ARGUMENTS が空の場合は、会話の直近の変更内容から対象を推定する。

実装後のコードレビューだけでなく、`workspace/plan.md` の計画レビューにも使える。計画の段階で対称性を検証する。見落としがあれば、計画を更新してから実装に進む。

## 背景

対称性の見落としは3種類ある:

1. コードパスの対称ペア: `show` を変更したら、`hide` も確認する。片方だけを変更すると、不変条件が壊れる
2. リソースのライフサイクルの対称ペア: リソースの「生成 → 登録 → 破棄」の各ステップの間に早期リターンがあると、生成済みで未登録のリソースがリークする。とくに追跡機構（Set/Map/配列）を廃止・移行するときは、旧機構が保護していたパスが、新機構では保護されなくなりやすい
3. 同型ペアの取り違え（swap）: 対称な 2 つの対象（main/results ウィンドウ、送信/受信、前景/背景）へ、同じ型の値を配線することがある。このとき、対応が「順序」や「フィールド名」でしか決まっていないと、取り違えても型・テスト・スモークがすべて通る。1・2 は「片方が抜ける」漏れである。これに対して 3 は、「両方あるが入れ替わっている」誤りである

## Step 1 — パターンの特定

$ARGUMENTS から以下を抽出する:
- 影響を受ける関数 / イベント名 / 不変条件のキーワード
- 変更の種類（呼び出しの追加、呼び出しの削除、処理順序の変更、追跡機構の廃止・移行 等）

## Step 2a — コードパスの対称ペア検索

コードベースを grep し、以下のようなペアを探す:

| 変更対象 | 確認対象 |
|---------|---------|
| `show` / `open` | `hide` / `close` |
| `enter*` | `exit*` |
| `expand` | `collapse` |
| `mount` / `setup` | `unmount` / `teardown` |
| `register` | `unregister` |

同じ関数やキーワードの他の呼び出し箇所も検索する。元の変更に含まれなかったコードパスを見つける。

## Step 2b — リソースライフサイクルの対称性検索

変更がリソース管理に関わる場合（worker スレッド、listener、Child プロセス、状態フラグ等）は、以下を検索する:

| 確認項目 | 検索方法 |
|---------|---------|
| 生成箇所 | `thread::spawn` / `listen(` / `Command::new` / `request_repaint_after` 等を grep |
| 登録箇所 | `.insert(` / 変数への代入 / `store(true` |
| 破棄箇所 | `join()` / `kill(` / `store(false` / 受信側の drop 等を grep |

とくに以下のパターンに注意する:
- 生成→登録の間の早期リターン: 生成した後、登録する前に `if (...) return` があるパスでは、生成済みのリソースが破棄されない
- 追跡機構の廃止・移行: 旧 Set/Map に `.add`/`.set` していた全箇所を grep する。新機構に同等の保護があるかを確認する

## Step 2c — 同型ペアの取り違えの検査

同じ型の値を、対称な 2 つの対象へ配線している箇所を列挙する（`main` / `results`、`tx` / `rx`、`from` / `to` 等）。newtype で分けても防げないことがある。分かれ目が「どちらの生成呼び出しの戻り値か」であれば、newtype で包む時点では、まだ両方が同じ型だからである（#671 PR D の実例: `attach(results, ..)` と `attach(window, ..)` が同じ型の wake handle を返す。そのため newtype を使っても、取り違えたまま compile が通る）。

| 確認項目 | 方法 |
|---|---|
| 配線の起点 | 同じ型の値を作る呼び出しを列挙する。「どちらの対象か」を、変数名ではなく引数で確認する |
| 中継の各段 | 構造体リテラルのフィールド短縮記法（`Foo { a, b }`）は取り違えを隠す。段ごとに読む |
| 区別できる観測 | 取り違えたときに、どちらか一方だけが壊れる観測を 1 つ特定する。無ければ「この誤りは検出手段が無い」と報告する |

判定に「型で守られている」と書くときは、守っている箇所が起点かどうかを明示する。起点で同じ型なら、型は守っていない。

## Step 3 — 各候補の評価

候補ごとに十分な前後のコードを読み、すべての実行ケースを列挙する:

```
候補: <file>:<line> — <説明>
  ケース A: <シナリオ> → <影響> → OK / 問題: <説明>
  ケース B: <シナリオ> → <影響> → OK / 問題: <説明>
  判定: [適用] 同じ変更が必要
        [不要] 理由: <ケースごとの明示的な根拠>
```

ケースごとの根拠が無い「不要」の判定は、レッドフラグである。根拠の無い除外は、未検証として扱う。

## 出力

根拠の規律: すべての判定に根拠（`file:line` または grep 結果）を付ける。コードを確認せずに下した判定は [適用]/[不要] とせず、[要確認] として報告する。

全候補を、判定と根拠を付けて列挙する。
対称ペアが見つからなかった場合は、その旨を明示する（Step 2 で実行した grep パターンを添える）。
