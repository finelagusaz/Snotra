# ADR-0003: race-check のトリガー述語を機構カテゴリで書き、規範の硬化には母集団の限定を伴わせる

## 文脈

#663 で `/race-check` を全面改訂した。旧版は #532 SU7 で撤去された SolidJS フロント（`dispatchQueryInput`・`searchLane`・`latestRun.isStale()`）を前提としており、**陳腐化ではなく構造的に機能停止していた**——Step 1 が「`await` 地点の列挙」から始まるが、`src-tauri` 全体の `.await` は 2 箇所（updater のみ・実測）しかなく、UI 層の並行性は `std::thread::spawn` + `mpsc` + フレーム drain + Tauri listener にある。空集合を返した Step 1 の後、Step 2〜5 は一度も発火しない。

決めるべきことが 2 つあった。**(1) トリガー述語をどう書くか**（発火しない述語を残せば改訂の意味が無い）。**(2) 規範文書をフォールトインジェクションで硬くする手続きをどう回すか**（`.claude/rules/safety-nets.md` が「回避しようとする読者」による検証を要求する）。

## 決定

1. **述語は実体の機構カテゴリで書く** — 「worker spawn・channel・フレーム drain・Tauri listener・スレッド/窓をまたぐ共有状態・フレーム内 live-read、または async 関数を追加/変更」。`.await` 軸は削除ではなく**降格して残す**。
2. **スキル本文は機構カテゴリに錨を打ち、現行シンボルは 1 カテゴリ 1 件の例示ラベル付きに留める**。位置は `file:line` で書かず、シンボル名と grep レシピで書く。
3. **義務を足す方向の修正は、母集団の限定とセットにする**（下記「却下 4」）。

## 検討した代替案と却下理由

### 却下 1: 述語から async 節を落とし、worker/channel だけにする

短くなるが、`spawn_update_check` / `spawn_install` の 2 経路がスキルの視界から落ちる。**「消滅した」と「少数になった」は別である**——実測 2 箇所は 0 ではない。撤去された技術の残骸を消す作業で、**残っているものまで一緒に消す**のは、旧版が死んだのと対称の失敗になる。

### 却下 2: 述語を「窓をまたぐ共有状態」に留める

改訂の初稿はこう書いた。code-reviewer が計画自身の不変条件（「述語は直近サイクルの実変更に当てて発火を確認してから確定する」）に照らして検算し、**#673（同一フレーム内の config 新旧混在）が発火しない**ことを検出した——スキルは 4e として観点を持つのに、述語が呼ばない。同様に `index_generation` のような**スレッドをまたぐが単一窓**の共有状態も落ちる。**述語 ⊊ Step 1 の境界集合**という不等号が残っていた。

教訓は「述語は観点の集合から導く」であり、直感で列挙して後から観点を足すと不等号が開く。

### 却下 3: 現行シンボル（`folder_rx` / `icon_pending` / `LaunchInFlight` / `snapshot_generation`）を Step 表に書く

読みやすさは上がるが、**旧版が死んだ原因そのものを再生産する**。`.claude/rules/src-tauri.md` が #588 で既に採った答え（見出し名・シンボル名で grep し、行で断定しない）をスキルにも適用する。事実（wake 義務・hidden 中 `update()` 不走行）はスキルに写さず `src-tauri/CLAUDE.md` の節名で参照する。

### 却下 4: フォールトインジェクションの指摘を、母集団を限定せずに義務追加だけで塞ぐ

**これが本サイクルで最も価値のある否定の知識である。**

第 1 巡（手を抜く読者）は「①②③だけ grep して非該当で終える」「grep を 1 件だけ貼る」という逃げ道を挙げた。素直な対処は義務を足すこと——「全 7 種の grep を示せ」「総ヒット件数を明記し全件判定せよ」。そう直した。

第 2 巡（規則を全部守る読者）が、その修正が生んだ**実行不能**を実測で示した: `view.rs` の 1 関数を変更しただけで、母集団がファイル全体のため `Mutex` 系だけで 51 件、7 種合計 70 件を 1 件ずつ裁定する義務が生じる。**これはサボりではなく、手順どおりに実行した結果**である。さらに「呼び出し元も辿れ」の打ち切り規則が無いため、この規模のアプリでは辿り続ければ必ず `update()` に着き、純粋核の変更でも「非該当」を出せなくなる。

**手を抜く読者の逃げ道を塞ぐ修正は、忠実な読者の実行可能性を削る方向に働く。** ゆえに義務を足すときは同時に母集団を絞る（変更 hunk + 変更シンボルが読み書きする状態 + 呼び出し元 1 ホップ）。片方だけでは、緩すぎる検査か実行できない検査のどちらかになる。

**読者 2 クラスが両方要る理由もここにある**——この破れは手を抜く読者からは永久に見えない。片方だけ回していたら、第 1 巡の修正は「硬くなった」と評価されたまま残った。

### 却下 5: 「staleness 機構は 4 型である」と網羅的に書く

初稿はそう書いた。plan-review の実測が 5 型目（アプリ全体スコープの単調カウンタをフレーム毎に diff する型）を見つけた。**全称表現は前提条件とセットで書く**（`AGENTS.md`「検証の作法」）を分類にも適用し、「代表 4 型・網羅ではない。5 型目を見つけたらそう報告する」と書く。

## 帰結

- 述語は 5 箇所（SKILL.md frontmatter / `AGENTS.md` / ルート `CLAUDE.md` / `start-issue` / `.claude/rules/{src-tauri,snotra-settings}.md`）で同期する。**`governance:check` はこの一致を検査しない**（G8 は存在照合のみ）ため、人手照合が唯一の防御である。
- 常時ロード規範（ルート `CLAUDE.md` + `AGENTS.md`）は 216/216 で余裕ゼロ。述語の更新は**行数を増やさない置換**に限られる。
- 受容する残余: 呼び出し元の遡行を 1 ホップで打ち切るため、2 ホップ以上先でゲート述語に効く純粋関数の変更は捕捉されない（実測: `layout::path_size` → `results_should_show` は 3 ホップ）。無限遡行と恣意的打ち切りを避けるための意図的な射程外である。
