# ADR-0006: 計画の所有を /start-issue に一本化する

## 文脈

`/start-issue` と `/implement` の両方が「計画」を所有していた。`/start-issue` は調査の後に `workspace/plan.md` を書き `/plan-review` でレビューする一方、`/implement` にも計画フェーズ（旧 Step 2）が残っており、`plan.md` の有無を見て分岐する判定が両スキルに独立に存在した。

この二重所有は3つの食い違いを生んでいた。

- **F1（到達不能な分岐と破れた出力契約）**: `/implement` の入口判定は `plan.md` があれば実装 Step へ直行するよう書かれており、旧 Step 2 の `plan.md` 分岐は正常系では二度と評価されない到達不能コードになっていた。にもかかわらず出力契約は「変更計画（Step 2）」の提示を要求しており、指示と契約が食い違ったまま残っていた。`/start-issue` からの引き渡しは正常系そのものであり、この矛盾は毎回踏む経路だった。
- **F3（検証水準が入口で変わる）**: `/start-issue` 経由なら計画は必ず `/plan-review` を通るが、`/implement` を単独起動すると計画は無検証のまま実装に入れた。`/implement` 単独起動は日常的な経路であり（利用者確認済み）、まれな迂回路ではなく主要な使われ方の一つでこの差が生じていた。
- **F5（重複の理由が書けない）**: 同じ check スキルが計画段階と実装段階の2度走る構成になっていたが、対象が別であるという正当化がどちらのスキルにも書かれていなかった。

F1 と F5 は根が同じで、両スキルが「計画」という概念を所有しているために判定が2箇所に生まれ、重複の理由を誰も書けなくなっていた。

## 決定

計画の所有を `/start-issue` に一本化する。`/implement` は「レビュー済みの計画がある」か「計画が要らない」かのどちらかでのみ動き、計画が要ると判明した時点で実装を始めずに止まる（`/implement`「Step 1 — 入口判定」・`/implement`「1b. 分岐」）。止まったあとどう乗り換えるかは `/implement`「1c. 止まったときの引き渡し」が扱う。

`plan.md` の同一性確認（`/implement`「1a. workspace/plan.md の同一性確認」）は、今のタスクのものと確認できないかぎり fail-closed に倒す——判断がつかなければ「あるものとして」進まず、止めて問う。

## 検討した代替案と却下理由

1. **`/implement` の中に計画フェーズを昇格させる**（自分で `plan.md` を書き `/plan-review` を回してから実装する）: 却下。単独起動での中断が起きにくくなる利点はあるが、計画フェーズが `/start-issue` と `/implement` の2箇所に実装されることになり、直したい F1・F5 をそのまま再生産する。今回消したい構造そのものが残る。

2. **計画フェーズを独立スキルへ切り出し両方から呼ぶ**: 却下。二重管理という構造は消えるが、今回の重複の原因は「共通部品が無いこと」ではなく「概念の所有が曖昧であること」だった。原因が所有の分散にあるとき、部品を追加する解は問題の形に対して過剰である。

3. **`/start-issue` を issue 無しでも回せるようにする**（`/implement` の乗り換え先として）: 却下。issue 読解・ブランチ作成に条件分岐が増え、F1 と同型の「分岐が2箇所に生まれる」構造を新設してしまう。直した箇所の隣に同じ形の欠陥を作ることになる。

4. **単独起動でも常に `/plan-review` を回す**: 却下。入口によらず検証水準は揃うが、小さな修正1つのたびにサブエージェントが走り、コストと待ち時間が毎回かかる。境界を定義して必要な場合だけサブエージェントを回す方が安い。

5. **規模（触るファイル数など）で自動分岐させる**: 却下。閾値の妥当性を誰も検算できない判定が新たに増える。「計画が要るか」という、実装者がどのみち行っている判断をそのまま使う方が、判断の総数を増やさずに済む。

6. **`plan.md` の同一性が不明なとき、あるものとして進む**: 却下。**本 ADR で最も価値のある否定の知識である。** 誤りの代償に非対称がある——古い `plan.md` を有効と誤れば「違うものを実装する」結果になり、検証（テスト・レビュー）を全部通過してコミットするまで気づけない。逆に、有効な計画を古いと誤っても、止まって聞き直すだけで回復できる。倒す向きが明らかに非対称なので、判断がつかない場合の既定を fail-closed に定めた。

## 帰結

`/implement` は入口判定・実装・検証・レビュー・コミットの5段になる（`/implement`「Step 1 — 入口判定」から始まる構成。旧 Step 2「計画」は削除され、以降が繰り上がった）。

**この設計の中身——手順どうしの整合性は機構では守れない。** `governance:check` が機械的に守るのは参照の着地・面積・スキル表の存在だけであり、「入口判定の分岐が実装 Step と両立するか」「出力契約が実際の Step 構成と食い違っていないか」は検査の対象外である。これは `docs/adr/0004-canonical-heading-references.md`「帰結」が明記した残余と同じクラスであり、F1 と同型の欠陥（指示と契約の食い違い）は将来また再発しうる。

同一性確認（`/implement`「1a. workspace/plan.md の同一性確認」）は、未コミットの `plan.md` に対しては弱い。`/start-issue` が最終ステップに到達せず中断した場合、git の証跡が無いため内容の一致だけが判断材料になり、判断がつかなければ止める——安全側に倒れるが、中断復帰の体験としては摩擦が残る。
