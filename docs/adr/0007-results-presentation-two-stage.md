# ADR-0007: results 窓の導出は 2 段に割り、`main_size` と `results_origin` を導出の外に置く

#752（段 2）で「窓をどう見せるか」を決める純粋関数群を 1 つの導出へ束ねた。issue が素描した単一の `WindowPresentation { main_size, results_visible, results_size, results_origin }` は**構成可能だったが採らなかった**。ここに残すのは、その却下理由である。

## 文脈

`egui_shell` には「results 窓を出すか・どの大きさで・どこへ」を決める純粋または準純粋な関数が散在していた（`results_should_show` / `results_window_height` / `clamp_results_height` / `main_window_height` / `position_results_below_main` / `results_available_height`）。#752 の目的は、`SPEC.md` §8.6 の 4 連言をユニットテストで固定できるようにすることである。

素直に読むと「1 フレーム分の入力を 1 か所で読み、1 つの値を導く」形になる。しかしその形は、フレーム内の読み点・第 2 の消費者・最頻フレームの費用という 3 つの事実と衝突する。

## 決定

- 導出は **results の（可視性・クランプ前の高さ）** で止める（`ResultsInputs` → `ResultsPresentation`）
- 幾何は**純粋な算術 2 本**（`results_top_y` / `available_below`）へ切り出し、Win32 を読む側は薄いラッパーのまま残す
- **`main_size` と `results_origin` は導出に入れない**
- **クランプは導出の外**（driver が `clamp_results_height` で行う）
- 連言③（`plain_hidden`）は**クリック逆流の消費前**に 1 回だけ読み、連言②の材料（件数）は**消費後**に読む。この非対称は意図であり、`present_results` の doc に記録する

## 検討した代替案と却下理由

### 1. issue が素描した単一 `WindowPresentation` をそのまま作る

**構成は可能である**（幾何の算出と適用を割れば `SetWindowPos` は飛ばない）。3 つの独立した理由で却下した。

- **`results_origin` はフレームに閉じない。** 第 2 の消費者が `Moved` リスナー（ネイティブ移動ループ中はフレームが回る保証が無いためイベント駆動で直接動かす・#646 PR2 決定 10）であり、1 フレーム分の入力を持たない。`window_gap` が `VisualSnapshot` から意図的に外されているのと同じ構造（#673）
- **最頻フレームで幾何 5 読みが純増する。** クランプ後のサイズを同じ値に持つと、results を出さないフレーム（空クエリ・0 件・indexing carve-out）でも main の position/size/scale・作業領域・results の scale を毎回読む。現状は早期 return が位置決めより前にあるため**何も読まない**。対価が無い
- **`main_size` は幅と「意図的な 2 導出」を巻き込む。** 幅は `window_width()`（config の live-read）で `layout.rs` を一切通らない。かつ main の高さは `show_egui_main` の `bar_height` collapse と毎フレームの `main_window_height` の**意図的な 2 導出**であり（位置クランプの順序制約）、束ねると片方が消える

### 2. 融合済みの `show_results: bool` を受け取り続ける（関数の移設だけで済ませる）

受け入れ条件を**原理的に**満たせない。連言②「結果が空でない」と③「通常結果を隠していない」が呼び出し前に 1 つの bool へ潰れているため、テストが「0 件で隠れた」と「carve-out で隠れた」を区別できない。移設だけの再編はこの issue の目的を達成しない。

### 3. 「`show_results` の構成を導出へ畳むことは**禁止**である」と結論する

**一度この結論を計画に書き、誤りだった。** 記録として残す。

連言②③と①④が同一フレーム内の別の時刻に読まれている（間にクリック逆流の消費が挟まり、`start_launch` が結果を空にする）という事実から、「読み点を前へ寄せれば視覚回帰、後ろへ寄せれば `#699` の publish 順序違反」という二分法を立て、ゆえに畳み込みは恒久的に禁止だと結論した。

**二分法が網羅的でなかった。** 第三案がある——pre-click で `plain_results_hidden` を 1 回だけ評価して publish 用に保持し、post-click では件数だけを再評価する。これなら `#699` の順序を保ったまま 4 連言を一体で導出できる。採用したのはこの形である。

事実（読み点が違う）から導けるのは「**publish と窓判定で同一の単一時刻の値を共有してはならない**」までであって、「畳んではならない」ではなかった。`AGENTS.md`「検証の作法」の「全称表現は前提条件とセットで書く。書けないなら書かない」を、禁止の側で踏んだ実例である。**誤った禁止を doc へ恒久化していれば、実在する選択肢を将来の実装者から隠していた。**

### 4. `available` を遅延クロージャで渡し、無理に 1 関数へ束ねる

早期 return と単一値導出を両立させる技術的な手はある。しかしそのクロージャの中身は `set_position` という副作用を持つ関数である。副作用を「純粋な導出」の引数の内側へ隠すと、`EscapeOutcome` が成功例として持つ性質——純粋な決定を値で返し、副作用は driver が実行する——が名前だけになる。2 段に割るほうが因果順序が読み手に見える。

### 5. `window_gap` を `VisualSnapshot` へ入れて導出の入力を揃える

`visual.rs` と `src-tauri/CLAUDE.md` が明示的に除外している（#673）。`Moved` リスナーと共用するためフレームに閉じない。却下 1 の第 1 理由と同じ構造の問題である。

### 6. `show_egui_main` の `bar_height` collapse を `main_window_height` へ統合する

`show_egui_main` は「高さリセット → 位置決め → show」の順序制約を持ち、位置クランプが展開時の高さで効くのを防ぐために**意図的に** `bar_height` だけへ畳んでいる。毎フレームの導出とは目的が違う。統合すると show 直後に位置がずれる。

### 7. `max_results = 0` をついでに直す

**挙動変更**であり「挙動は変えない」に違反する。かつ `max_results = 0` が到達可能であること（本体の config 適用経路は `Config::validate()` を通らない）は、**連言④を②から独立に動かせる唯一の梃子**であり、受け入れ条件を満たすために使っている。直すなら別 issue で、そのとき「④は②に含意される」という新しい事実をテストに反映する。

## 帰結

- 導出は 2 段（可視性 + クランプ前高さ → クランプ）に割れた。`main_size` と `results_origin` は外に残る
- 読み点の非対称は**恒久的な制約**として `present_results` の doc に記録した。読み点を前へ寄せると、行クリック起動フレームで古い行が 1 フレーム描かれる（`cargo test` では落ちない）
- 等価グリッドが固定するのは「pre-click 件数 == post-click 件数」のフレームに限られる。クリック起動フレームの等価性は論証とカテゴリ D の目視が担う
- 却下 3 の教訓は一般則である: **禁止を恒久文書へ書く前に、その禁止が依存している前提を明示できるか確かめる。** 明示できない禁止は、選択肢を隠す
