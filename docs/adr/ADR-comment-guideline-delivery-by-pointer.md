# ADR-comment-guideline-delivery-by-pointer: コメント規約を配送される rule 本体へ統合する案と、条項に機械検査を付ける案を却下した

2026-08-08、#732 で `docs/comment-guidelines.md` の配送穴を塞いだ（策定済みの規約が `.rs` を編集する者へ届いていなかった）。**この ADR が残すのは、そのとき却下した案である**——採用後の姿は `.claude/rules/comments.md`（ポインタだけの router）と `docs/comment-guidelines.md`（正本）が持つ。

## 却下 1: 正本を rule 本体へ統合し、`.rs` 編集時に全文が届くようにする

「ポインタでは正本を開かない読者が居る」という懸念に対する最も直接的な案であり、利用者から明示的に問われた（「既存のコメントガイドラインは comments.md に統合する？」）。**測って却下した。**

- **機構が拒む。** 正本は 5264 字で、rules 面は 10470 / 12000 字だった。統合すると **15734 / 12000（上限の 131%・超過 3734 字）** となり `G-area-budget` が赤になる。上限を上げれば通るが、それは火災報知器そのものの無効化である。
- **先例が真逆を向いている。** `governance-docs.md`（当時 1677 字）を `.rs` の書き手へ届けることは、2026-08-04 に「全 Rust 編集へこの rule 1 本ぶんを配送する費用を避けた」として**見送られている**（`docs/adr/ADR-canonical-heading-references.md`「受容する残余」）。5264 字はその 3.1 倍を、`.rs` を触るたび毎回課税する。
- **登ってほしい階梯を逆走する。** `docs` が `G-area-budget` の母集団外なのは意図的で、「『その作業に入った者だけが読む面』への退去は #593 が推奨する経路であり、課税すれば登ってほしい階梯を登る側が罰せられる」（`scripts/governance-check.mjs` の同検査のコメント）。統合は正本を退去先から常時課税面へ引き戻す。
- **人間向けの入口が壊れる。** `CONTRIBUTING.md` は寄稿者へ `docs/comment-guidelines.md` を示し、`docs/development-principles.md` は「コメント自体の書式・粒度・定型ラベルは `docs/comment-guidelines.md` を SSOT とする」と宣言している。統合すると案内先がエージェント設定（`.claude/`）配下になる。

**懸念自体には別の答えがある**——router は 4 つの節を名指しするので開く先が一意に定まり、既存 router 3 枚も同じ賭けで運用されている。正本側の読みやすさが問題なら、面積を使わない手（破られやすい条項を先頭へ寄せる・死んだ `## TSDoc の様式` 節を整理する）が残っている。

## 却下 2: crate 別の既存 router へ 1 行ずつ足す

一見こちらが既存の分割規律に沿う。**2 つの理由で却下した。**

- **`snotra-egui-runtime` に rule が 1 枚も無い**（`.rs` 12 ファイル）。既存 3 枚へ足すだけでは覆えず、新設を含めて **5 か所**に同じポインタを置くことになる。`AGENTS.md`「条件別チェック（トリガー → 参照先）」の写しの行——「同じ事実を 2 か所以上へ書こうとしている時点で、それが写しである」——に正面から反する。
- **単一 rule で足りることは実測で分かった。** harness の rules 配送は**重なる**（glob が一致した rule はすべて同時に配送され、既存 router を隠さない）。この挙動は `G-rules-globs` からは分からない——当の検査が自ら「harness の配送判定の再現ではなく『マッチ 0 件の検知』に限定した近似」と宣言している。ゆえに新鮮な context のサブエージェントで測り、4 glob すべてで新 rule と既存 router の**同時配送**を確認した。**重複排除はファイル単位で 1 セッション 1 回なので、1 つの context で測れる glob は 1 本だけである**（4 本を閉じるのに新鮮な context を 4 つ要した）。

bare `**/*.rs` の 1 枚で全 `.rs` を覆う案も検討したが、**その glob 形の配送を測っていない**ため採らなかった——外していれば rule が 1 度も届かない静かな失敗になる。採ったのは既存 rule と字面が同型の crate 名始まり glob を 4 本並べる形である。

## 却下 3: 行またぎコードスパンの検知器を `governance:check` へ新設する

折返し条項が禁じる「コードスパンを行またぎさせない」は決定的に測れる（コメント行のバッククォートの偶奇 + コードフェンス状態）。**実装前に発火しうることも測った**——当時 5 件で発火し、修正後は 0 件で将来を守る形になる。それでも利用者の裁定で見送った: **5 件は `.rs` のコメント 8030 行に対する事故率であり、規範 1 行と現存違反の修正で足りる**という判断である。

## 却下 4: 散文の数え上げを検出する検知器

「経路の数・分岐の列挙」を禁じる条項に機械検査を付ける案。**語彙依存の regex を実データへ当てて却下した**——`.rs` 全体で 10 件ヒットし、分類すると本物は 3 件で **7 件が偽陽性**（「経路が 1 つでもあれば」型の条件節、「一箇所に保つ」型の規範、一意性の宣言）。しかも「N 枝」のように語を変えれば容易にすり抜ける（実際に `font_stack.rs` の「3 枝」をこの regex は拾えず、同じ段落を別の理由で編集したときに初めて見つかった）。**機械化に向かないと測れた**ので、条項側に「一意性の宣言は対象ではない」「過去の変化量は対象外」の線引きを書いて受容した。

## 受容する残余

- **新しい crate を追加したとき、`.claude/rules/comments.md` の `paths` に足す必要がある。** `G-rules-globs` は「パターンが 1 件以上にマッチするか」だけを見て逆向き（全 `.rs` が覆われているか）を見ない。却下 2 のとおり bare glob は配送を測っていないため採れず、この取りこぼしは検知されない。
- **行またぎスパンの再発は誰も検知しない**（却下 3 の帰結）。次に誰かが grep で辿れないコメントを踏むまで分からない。
- **折返し・訳語の条項は 100% 規範であって機構ではない。** 規範そのものへフォールトインジェクションを当てる手順は置かない（`docs/adr/ADR-retire-norm-review.md`）ので、妥当性は条項を実際に使う作業と独立レビューが事後に暴くものとして扱う。実際このサイクルでは、**新設した条項 2 つが自分自身に適用したときに破れているのを code-reviewer が捕まえた**（条項本文が自分の禁じた数え上げを含んでいた／訳語の射程規則が実際の判定を導けなかった）。
- **配送実測 4 本のうち 1 本（`snotra-settings/**/*.rs`）は孫エージェントの報告であり、主エージェントの一次証拠が手元に無い。** 重複排除ゆえ同一セッションからは再測できない。
