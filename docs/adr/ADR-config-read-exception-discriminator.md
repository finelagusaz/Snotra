# ADR-config-read-exception-discriminator: config の live-read 規範の例外を、走るスレッドで切る

## 文脈

#1032 は「config の live-read は `egui_shell::read_config` を通す。`engine.lock()` を経てはならない」を定め、例外を「`commands/` の操作時の読み」と**場所**で切っていた。理由として (A) 毎フレームではないこと、(B) `resolve_opener` のように別目的で同じ錠を既に取るものがあることを挙げていた。

#1076 は `instant_prefix` がこの規範の射程に入るかを問うた。呼び出し元を全件辿った結果、**例外の切り方そのものが実際の害の代理として精度を欠いていた**ことが分かった。規範が挙げる害は「フレームが走査の完了まで返らない」であり、害はディレクトリにも頻度にも結びついていない。`commands/` で正しく切れていたのは、4 件のうち 3 件がたまたま egui フレームの外（icon worker・tray スレッド）に居たためであって、残る `get_instant_commands` は `commands/` に在りながら UI フレームの中で毎打鍵走っていた。

決めるべきは、**例外を何で切るか**である。

## 決定

**弁別子は「その読みがイベントループスレッドで走るか」とする。** 動機は「ユーザーがその読みの完了を待っているか」だが、**判定には動機を使わない**——両者を規範の文面で分けて書く。どこで走るかは呼び出し元を辿って決め、非自明な 2 つ（`on_event_loop` へ渡したクロージャの本体はインラインでも post でもイベントループスレッドで走ること・tao の window-event リスナーもそこで走ること）を明示したうえで、正本は `snotra-egui-runtime` の `proof.rs` を指す。

条項の全文は `src-tauri/CLAUDE.md`「モジュール構成」が正本とする。

## 検討した代替案と却下理由

- **案 A: 「毎フレームでない読みは engine lock のままでよい」**（#1076 自身が提案した文言）: 却下。移す当の対象（`instant_prefix`）が毎フレームではないため、**移行した対象を免除する例外**になり、決定と正面から矛盾する。
- **案 B: 字面（`commands/` の）を維持する**: 却下。`commands/instant.rs` の `get_instant_commands` は `commands/` に在りながら `run_search_with` の Instant 枝から毎打鍵 UI フレームの中で走る。**字面は穴を持つ**。場所での切り分けが機能して見えたのは偶然（他の 3 件がフレームの外に居た）であり、偶然に依拠した規範は次の 1 件で破れる。
- **案 C: 事由 (B)「別目的で同じ錠を既に取る」を判定に使う**: 却下。**「別目的」がそれ自体ただの config 読みなら循環する**——config 読み 2 つが互いを正当化することはできない。`commands/icon.rs` も `commands/instant.rs` も `execute_instant_selected` も成立しなかった（instant 起動は履歴を記録しないので後続の engine lock が存在しない）。**(B) には 2 通りの読みがあり、ここでは緩い読みを採って評価した**——厳密な読み（錠の取得そのものを共有する）なら `resolve_opener` でも成立しない（履歴の錠は `record_and_save` が別に取り直す）。緩い読み（起動という操作がどのみち engine の錠を取るので新しく待つ面が増えない）でようやく `launch_item_with_state` の経路で成立する——**そして `resolve_all_openers` は `record_and_save` を伴わないので、緩い読みでも成立しない**。どちらの読みでも判定基準としては使えない。
- **案 D: 「その読みの完了をユーザーが待つか」を判定基準にする**: 却下。**ユーザーはアイコンの出現も、`→` を押した先のフォルダ一覧の表示も待っている**。字面どおり適用すると icon worker と folder worker まで `read_config` へ移すべきだと結論でき、**規範が自分の挙げる例外を否定する**。動機としては正しいので、動機と判定を分けたうえで動機の側に残した。
- **案 E: 「egui フレームの外か中か」で切る**: 却下。show 経路はフレームの外だが、窓が出るまでを止めるため非例外にする必要がある。**規則が自分で自分を反証する**形になり、`docs/architecture.md` に置いた言い換えは but 節も無く端的に偽だった。
- **案 F: イベントループスレッドで走るものを列挙して外延を書く**（「フレームの中・show / hide・`on_event_loop` がインラインへ倒れる listener の本体」）: 却下。`on_event_loop` は**インラインでも post でも**クロージャをイベントループスレッドで走らせる（インラインか post かは**いつ**走るかであって**どこで**走るかではない）。ゆえに条項が 2 文あとで先例として挙げる hotkey の読み（platform スレッドからの emit ＝ post 側）が自分の規則から漏れ、条項が自分と矛盾した。tao の window-event リスナー（`Moved` → `position_results_below_main` の `window_gap` の読み）も同じ理由で漏れる。**列挙は外延を固定するので、非自明な経路を 1 つ落とすだけで規範が偽になる。**
- **案 G: 規範を型・構造で強制する（表現不能にする）**: 却下。**弁別子が否定形の述語だからである**——「イベントループスレッドを止め**ない**場所」を型で表すには、「ここはイベントループ上ではない」というトークンを worker と platform の全経路へ通す必要がある。この crate が持つ証人型 `EventLoopProof`（`snotra-egui-runtime` の `proof.rs`・`!Send + !Sync`・crate 外で構築不能）は**肯定側の存在を証明できるが不在を証明できない**。残り 2 つの構造的な手も塞がっている: `Engine` から config を外へ出すのは**既に限界まで済んでおり**（`AppState.config` は同じ `Arc` で `read_config` は engine に触れない。書きだけが `Mutex<Engine>` の内側に残るのは `complete_index_drain` の原子性のため）、`Engine::config()` の可視性を狭めるのは `src-tauri` に正当な呼び出しが残るため不可である。
- **案 G′: lint で守る（`clippy.toml` の `disallowed-methods` に `Engine::config` を載せる）**: **却下ではなく、本サイクルでは決めない。** 型では表せない（案 G）が lint なら表せ、`sorted_by_path`（#1067）という同型の前例もある。ただし (1) `clippy.toml` と `G-clippy-disallowed` はセーフティネットであり、ルート `CLAUDE.md`「最重要ルール 2」が単独判断を禁じる、(2) 正当な実使用が 4 件あり `#[allow]` を打鍵させる形になるため、それを「抑制」ではなく「分類の記録」と見なせるかの裁定が要る。**「#1032 が受容残余と書いたから」を理由にはしない**——#1032 の判断の入力は本サイクルで変わった（条項の射程が `commands/` まで広がった）。**別 issue とする。**
- **案 H: 実害を測ってから決める**: 却下。#1032 / #1036 の計装は撤去済みで、入れ直す費用が移行そのもの（読み口を替えるだけ）より大きい。#1076 は「規範との関係を裁定する」ことを求めており測定を要求していない。**ゆえにこのサイクルは性能を測っておらず、速くなったとも主張していない。**
- **案 I: `ADR-blur-grace-single-field-state-machine` の本文を訂正する**: 却下。同 ADR は `auto_hide_enabled` を毎フレーム無条件で読む判断を記録し、その却下理由に「engine lock は既に毎フレーム 2 回（`read_visual` / `lang()`）走っており 2 → 3 に増えるだけ」という費用評価を置いている。**この前提は 6 日後の #1036 で偽になった**（両者が `read_config` へ移り、実際の値は 0 → 1 だった）。しかし ADR は凍結された歴史であり腐るに任せる（`ADR-adr-frozen-history`）。**生きた層**——`auto_hide_enabled` の doc——へ事実を書いた。

## 検討していない代替（この記録は網羅ではない）

**「例外を置かない」——残る例外 3 か所（`commands/launch.rs` の 2 つと `commands/icon.rs`）も `read_config` へ移す**案は、本サイクルで一度も俎上に載せていない。3 か所とも engine の錠を config 読みのためだけに取っており（実測）、`AppState.config` はスレッドを問わないので移すこと自体は可能である。移せば規範は「config の live-read は engine 錠を経ない」だけになり、**弁別子という装置ごと不要になる**（本 ADR の案 A〜F がすべて無意味になる）。得るのは統治だけで性能は変わらず、`resolve_opener` は錠を替える変更なので `/race-check` の対象になる。**却下したのではなく評価していない。** 別 issue とする。

## 帰結

- 例外は場所ではなくスレッドで決まるので、**同じ関数が両方から呼ばれるようになれば分類が変わる**。条項は「呼び出し元を辿って判定すること」を要求する。
- 動機と判定を分けたことで、「ユーザーが待っているか」を根拠に worker の読みまで移そうとする誤りが規範の側で止まる。
- 外延を列挙しないので、イベントループスレッドで走る経路が増えても条項は偽にならない。代わりに**どこで走るかを一次証拠で確かめる責務が読者に移る**——非自明な 2 つは条項が名指し、正本は `proof.rs` が持つ。
