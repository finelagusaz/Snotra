# ADR-declared-colors-over-modal-color: 窓が「見せねばならない色」を宣言し、最頻色では判定しない

## 文脈

`check:colors` の判定は「窓全体の**最頻色**が期待色と一致するか」だった。その前提——スクリプト自身が
「背景は窓で最も広い色なので」と書いていた——は **main 窓で偽**である。実測（#949 の前後 2 回とも同一）:

```
main 窓 752x56   入力欄 43.1% / 背景 33.3% / 入力欄の縁 11.3%
results 窓        背景 76.1%（最頻・正しく動く）
```

ゆえに main はどんな背景色を指定しても赤で、`$succeeded` は常に false だった。**永久に赤いゲートは
ゲートが無いのと機能的に同じ**であり、読み手が exit code を無視するようになれば、**正しく動いている
results 側の判定まで道連れになる**。

## 決定

**各窓が「見せねばならない色」を宣言し、宣言色がそれぞれ下限占有率以上あるかを判定する。**
下限は宣言ごとに持つ（main は背景 15% / 入力欄 15%、results は背景 50%）。判定述語は純関数として
`scripts/lib/SnotraWindowColors.psm1` に置き、Pester が論理を測る。

## 検討した代替案と却下理由

- **ランキングで判定する**（「上位 2 色の集合 == {背景, 入力欄}」）: 却下。**ランキングは presence の
  proxy** であり、判定を 2 つの独立した量の**相対**面積へ結びつける。`bar_padding` / `window_width` /
  status 行の有無 / `font_size` は順位を覆しうるが、**そのとき両色は完全に届いている**——レイアウトを
  変えるたびに偽陽性が出る。捕まえたい失敗（色が届かない）は「順位が下がる」ではなく**不在（0 px）**
  として現れる。`docs/development-principles.md`「構造的設計原則と強制の階梯」の「**守りたい要素は
  名指しする**」に従う。
- **下限をグローバル固定にする**（当初案の一律 5%）: 却下。旧述語「最頻である」は「下限以上」を
  **含意する**が、**逆は成り立たない**。results で背景が 10% しか届かない状態は**旧判定では赤・
  一律 5% では緑**になり、**現に動いている検出器を弱める**——本 ADR が直そうとしている欠陥の
  ちょうど裏返しである。下限を宣言へ載せれば、データ駆動のまま窓ごとの強度を保てる。
- **判定を位置に紐付ける**（入力欄の矩形の中だけで入力欄色を測る）: 却下。矩形を検査側で得るには
  `bar_padding` / `bar_inset` / `font_size` から導く必要があり、**製品のレイアウト計算の写しを検査側に
  作る**ことになる（式が 2 箇所になり、片方だけ腐る）。代価として**クロス配線を検出できない**残余が
  残る（下記）。
- **赤の理由を分類する検出器を置く**（「色が届いていない」/「レイアウトが崩れた」）: 却下。失敗
  メッセージが**実測占有率**を持てば `0.0%` = 不在 / `3%` = 在るが下限未満として読み分けられる。
  分類器は同じ情報を二重に表現し、射程を膨らませる。
- **判定を `visual-check-colors.ps1` の中に残す**（モジュールへ出さない）: 却下。素のスクリプト内
  関数は Pester から呼べず、**欠陥が在るまさにその述語だけがテストを持てない**状態が続く。
  Bitmap→ヒストグラムの I/O はスクリプトに残し、**純粋な半分だけ**を出す。

## 帰結

- main の判定が**史上初めて緑になった**（`exit 0` を実測）。それまで「main が緑」は未証明の状態だった
- **入力欄背景色（`input_background_color`）の到達が自動で測られるようになった。** seed も非既定色へ
  変えたので、「egui の既定と偶然違うから通る」という経路に頼らない。**上の測定値は seed 変更前
  （入力欄が config 既定 `#383838` だった頃）のものである**——変更後にこの道具が印字するのは
  `background 33.3% / input_bg 37.6%`（main）と `background 76.1%`（results）で、下限の根拠は
  そちらを使う（`Get-SnotraDeclaredColors` の doc が正本）
- 故障注入を**宣言色ごとに 1 本ずつ**置く必要が生まれた——`frame.set_clear_color` を落としても
  `input_bg` は `ui.visuals_mut()` という別経路で無傷のまま届く（実測）。1 本では新しい宣言が
  飾りでも気づけない（`.claude/rules/safety-nets.md`「検出器のカバー範囲は、欠落のパターンごとに検算する」）

## 受容する残余

- **クロス配線（値の取り違え）を検出できない。** 位置に紐付かない存在検査ゆえ、背景領域に入力欄色・
  入力欄領域に背景色が出ても**両色とも下限を超えて緑になる**。この失敗は「不在」ではなく
  「**別の場所に存在**」として現れ、述語の前提の外にある。位置判定を却下した代価である
- **同じ限界の第 2 例: 宣言が測るのは「色の存在」であって「その要素の存在」ではない。**
  `input_bg` は入力欄以外にも出うる——status 行が同じ `input_background_color` を **raw painter へ
  直接渡して**描く（`SPEC.md` の as-built・`view.rs` の適用点とは無関係な経路）。入力欄の塗りが
  消えても status 行が出ていれば宣言は満たされる。**今は鳴らない**（main を撮る時点で status 行の
  述語が常に偽——indexing でも launching でも通知中でもない）が、それは構造ではなく状況である
- **このゲートは人間が起動したときだけ走る**（`ci.yml` にも `e2e.yml` にも無い・GUI 依存）。
  直しても「誰も起動しなければ黙る」性質は残り、**それがこの修正の価値の上限である**
- 選択色・hint 色は測らない。hint は文字のアンチエイリアスで周囲色と混ざるため、判定に閾値と
  許容距離の 2 つのマジックナンバーを要する
