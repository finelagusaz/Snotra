# ADR-error-row-icon-key-in-derivation: 列挙失敗行がアイコンを持たないことを、消費者ではなくキーの導出で担保する

## 文脈

#1134。フォルダ列挙に失敗した行（`is_error`）に、前の世代で通常のフォルダ行として抽出したテクスチャが残って描かれる経路があった。`SPEC.md`「3.4 アイコン」は「列挙失敗行は抽出せず placeholder も描かない」を既に定めており、直すのは実装の側である。

キーの消費者は 3 つある——要求（`wanted_icon_keys`）・保持（`visible_icon_keys` → `retain_visible`）・引き（`icon_for_row`）。不変条件を守っていたのは要求側の `if r.is_error { continue }` だけで、保持側が前の世代のキーを残し、引き側がそれを返していた。どこへ条件を置くかを決める必要があった。

## 決定

`SearchResult::icon_key` が `is_error` のとき `None` を返す。要求側の条件は撤去する。

## 検討した代替案と却下理由

- **描画側（`draw_result_row`）の `Some(tex)` 枝に `is_error` ガードを 1 行足す**: 却下。差分は最小だが、**検知器を単体テストとして置けない**——「テクスチャが既に在る状態から連鎖を通す」という #1134 の核心が描画層でしか観測できず、kittest 相当の器を要する。加えて不変条件が要求側と描画側の 2 か所に分かれたままになる。
- **`icon_for_row`（引き側）で `is_error` を見る**: 却下。単体で測れる利点は採用案と同じだが、不変条件が要求側と引き側の 2 か所に残り、保持側は使われないテクスチャを持ち続ける。
- **`folder::error_result` が `IconSource::Skip` を入れる**: 却下。データの出所で決まる点は良いが、**規約であって構造ではない**——`is_error: true` を作る別の生成点が将来 `FromPath` で書けば破れる。採用案があれば同じ事実の 2 つ目の表現になり、#1133 が定めた「キーを導くのは `icon_key` ただ 1 つ」に反する。
- **保持側（`visible_icon_keys`）を `is_error` で絞る**: 却下。#1133 が意図的に広く取った判断（狭いと、抽出した直後の世代交代でテクスチャを落として積み直す往復になる）を覆すことになる。**採用案でも保持側は結果として狭まるが、それは「行の性質で絞る条件」を足したのではなく、エラー行がキーを持たなくなった帰結である**——通常行の往復は起きない。

## 受容した費用

採用案では、列挙に失敗したフォルダのテクスチャが 1 件落ちる（エラー行の世代は 1 行だけである）。そこから離脱したときの再抽出は、`commands/icon.rs` の `load_icon_pngs` が `IconCache` を先に引くため**シェル呼び出しにはならない**。

`icon_key` が `IconSource` に加えて `is_error` も見るようになり、「キーの導出」と「行の性質」が同居する。**`icon_key` の意味は「この行のアイコンをどこから取るか」であり、「取らない」は既に `Skip` として語彙の中にある**という理由でこれを受容した（2026-08-19 の人間裁定）。

## 帰結

- 要求・保持・引きの消費者は、それぞれ個別に `is_error` を見る必要がなくなる。
- 検知器は 2 段になる——導出そのもの（`snotra-core`）と、テクスチャが既に在る状態からの連鎖（`src-tauri` の純粋核）。**その間の隙間**（`icon_for_row` が返した `None` が描画の `None` 枝へ届くこと）に検知器は置いていない（受容する残余）。
- 「エラー行に placeholder を描かない」は別の不変条件であり、描画側の `None if !result.is_error` が引き続き担う。
