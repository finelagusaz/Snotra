# ADR-folder-location-display-surface: フォルダ展開中の現在地を、入力欄のプレースホルダ 1 面だけに出す

**日付**: 2026-07-29 / **関連**: #836・#743（誤読の実例）・#700（描画面を 2 つ持たない教訓）・#532 SU3 M2 Task 3（見送りの経緯）

## 文脈

フォルダ展開中、画面のどこにも現在のディレクトリが出ていなかった。受け入れ条件は「(1) 現在のディレクトリが画面から分かる (2) 他モードの表示を壊さない（**同じ情報に描画面を 2 つ持たない**）」であり、この 2 つは素朴には両立しない——(1) を「常に見える」と読むと、どの候補面も条件付きでしか満たさないからである。

以下は**却下した案とその理由**の記録である。採用案（入力欄の `hint_text` に `<フルパス> 内を検索...`）は `SPEC.md`「6.7 フォルダ展開中の現在地表示」とコードが持つので、ここには書かない。

## 却下 1: status 行に出す

`overlay_kind`（`notify.rs`）の排他ラダーへ folder 文脈を第 4 の種別として足す案。

- **`overlay_kind` は排他ラダー（indexing > 起動中 > 一時通知）である。** folder 文脈をそこへ入れると、indexing 中や起動中に現在地が**黙って消える**。これは #700 が是正した失敗様態そのもの（案内が局面によって別の面へ飛ぶ／消える）を、別の入口から再導入することになる
- **`main_window_height` が 1 行伸びる。** フォルダ展開中ずっと status 行が立つため、フォルダに出入りするたびに main 窓が伸縮し、`position_results_below_main` 経由で results 窓も上下する
- **「常に見える」という利点自体が偽だった**——上の 1 点目により、status 行案も無条件には受け入れ条件 (1) を満たさない。**採用案との差は「いつ消えるか」だけであり、消えない案は候補に無かった**

## 却下 2: results 窓のヘッダ行に出す

結果リストの先頭に現在地の行を置く案。

- **0 件・空フォルダでは `present_results` が非表示を返して results 窓ごと消える。** 現在地をいちばん知りたい局面（空のフォルダに入ってしまった・列挙に失敗した）でちょうど出ない
- `RowsSnapshot` の行インデックスに現在地行が混ざり、クリック逆流（`take_clicked_for`）の照合に手が入る

## 却下 3: 長いパスを自前で中間省略する → **2026-08-01 に採用へ転じた（#870）**

`results_view::truncate_middle`（`pub(crate)`・テスト済み）を、書式へ埋める前の `dir` に当てる案。egui 既定の**末尾**省略では、深い階層でいま居るフォルダ名（＝パスの末尾）が削られるため。

2026-07-29 に次の理由で却下した:

- `truncate_middle` は `per_char_px`（呼び出し側が渡す推定値）で幅を測る API で、CJK を過小評価する既知の粗さを持つ。接尾辞「 内を検索...」の実幅も別途推定が要る
- 既定幅 600px でのパス予算は概ね ASCII 55〜60 字で、**実運用のパスはたいてい収まる**（溢れは端の事例）
- 撤去済み WebView2 版は CSS クリップで `…` すら付かなかった。egui 既定は parity より既に良い
- **観測点を残して受容した**: #836 のカテゴリ D 目視表（この PR 限りの表として PR 本文に置いたもので、`scripts/manual-smoke.ps1` の常設 13 項目とは別物である——却下 6 がその区別の理由）の項目 7・10。そこで受容できないと判明したらこの案を follow-up として起こす

### 覆したもの（#870）

**その観測点が答えを返した。** 2026-08-01 のカテゴリ D 実測（英語 UI・既定幅 600px・128 字の fixture）で、第 3 階層と LEAF 到達の main 窓キャプチャが **SHA256 で 1 バイトも違わなかった**。想定していた失敗は「いま居るフォルダ名が読めなくなる」だったが、実際の失敗は**異なる 2 つのディレクトリが同一表示になる**ことだった。この機能は #743 の**誤読**を防ぐために入ったので、目的そのものが深い階層で成立していない。

さらに、**却下理由 1・2 は当時すでにリポジトリ内で解かれていた**:

- 理由 1 —— `truncate_middle` の唯一の呼び出し点（`results_view.rs`）は `per_char_px` を**実 galley から実測している**（`layout_no_wrap` で 1 回組んで平均を割り出す・#632 の方針）。**呼び出し点を見ずに API のシグネチャだけで書いていた**
- 理由 2 —— 接尾辞の実幅を別に推定する必要は無い。「候補を書式へ埋めた文字列の実幅」を測る関数を注入すれば、固定部の推定が設計から消える

理由 3（実運用のパスはたいてい収まる）は今も正しい。**変わったのは頻度ではなく、溢れたときの質である。**

**教訓**: 却下理由に「既存 API が粗い」と書くときは、その API の**呼び出し点**を開いてから書く。粗さが呼び出し側で既に埋められていることがある。

**採用にあたって却下した実装案は、番号順を保つため末尾の却下 7・8 に置いた。**

## 却下 4: hint の 3 分岐を純粋核へ切り出す

`overlay_kind` に倣って `hint_kind(view_kind, dir, lang)` のような純粋関数を作り、テストで固定する案。

- **hint の分岐は `view_kind()` の優先度ラダー（tool > folder > results）そのものであり、切り出すと `view_kind()` の 2 重導出になる。** `overlay_kind` が正当なのは、それが `view_kind` と**独立な** 3 入力（indexing / launching / notice）を畳む関数だからで、この形とは違う
- `strings.rs` の依存が `Language` だけで済まなくなる（`ViewKind` を UI 文言テーブルへ持ち込む）
- 受け入れ条件 (2) は構造で閉じており、テストの口を作る動機が弱い——instant / slash コマンドは軸 2（`QueryIntent`）で `ViewKind::Results` に落ち、既存 2 腕の値は 1 文字も変わらない

## 却下 5: `view_kind()` の 2 回読みを 1 回へ束ねる

`in_tool` / `in_folder` が隣接行で `view_kind()` を 2 回呼んでいるのを 1 回にする案。

- 2 回の間に `&mut self.controller` が入らないため値は同一で、直す不整合が無い（YAGNI）
- **落としてはならないのは読み点の「位置」の方だった。** そちらは不変条件として計画とコードコメントに残した——`update()` の冒頭からこの位置までに `view_kind()` と現在地を書き換える `&mut` 呼び出しが挟まっており、前寄せすると hint が遷移前のディレクトリを描く

## 却下 6: 常設の目視項目（`scripts/manual-smoke.ps1` の `$items`）へ足す

現在地表示は自動検出器を持たないため、常設の目視チェックリストへ項目を追加する案。

- 既存 13 項目はいずれも**横断不変条件**（フォーカス奪取・hide の順序・クリック逆流の読み点・位置復元・フォント hot-reload・キャレット・ベースライン・通知期限）＝**どの変更でも壊れうるもの**であり、機能単位の受け入れ確認ではない
- 新機能のために先回りで常設項目を足すと、以後すべての PR に恒久コストが乗る。この PR 限りの目視表（PR 本文）で足りる
- **足す条件を決めておく**: #836 の表示が実際に一度回帰したとき（#700 → 目視項目 11 と同じ経路）。先回りでは足さない

## 却下 7: 平均文字幅で 1 回割って `truncate_middle` を当てる（#870 の素案）

issue #870 本文が示した最短の実装。`folder_hint(l, "")` の実幅を固定部として引き、残りを平均文字幅で割って文字数を出す。

- **収まる保証を持たない。** 平均で割るので、残した head/tail がたまたま平均より広ければ溢れる。溢れれば egui が末尾を削り、leaf が消える＝ #870 の症状へ戻る——**静かに戻る**のが悪い
- 採った形（測定関数を注入して二分探索し、収まった候補だけを記録する）は、測定 8 回（128 字）と引き換えに「1 件でも収まる候補があれば返り値は必ず実測で収まっている」を得る。galley は egui がキャッシュするので定常フレームはハッシュ引きである

## 却下 8: `truncate_middle` を `layout.rs` へ丸ごと移す

中間省略の実装を純粋核へ集約する案。

- 共有できるのは「char 数だけ受ける中核」であって、px ベースの `truncate_middle(s, avail_px, per_char_px)` 本体ではない（用途が違う——結果行は 1 回の推定、hint は測定注入）。移しても DRY が閉じるのは中核 1 関数だけ
- 移動はテスト群も動かし、**#870 の diff に「結果行の省略ロジックが動いた」が混ざる**。カテゴリ D の証跡をレビューするとき、表示が変わった原因の切り分けが利かなくなる
- 採った形: `layout::truncate_middle_chars` を新設し、`results_view::truncate_middle` は**シグネチャ・挙動・テストを据え置いたまま本体だけ委譲**する。head/tail 分割の実装が 2 本並ぶことは避けられている

## 受容した残余

- **絞り込みを 1 文字打つとプレースホルダは消える。** 却下 1 で述べたとおり無条件に満たす候補が無く、かつ `enter_folder` / `navigate_folder` はどちらも絞り込みをクリアするので、`←` / `→` の直後は必ず表示される——#743 の誤読が起きた瞬間をちょうど覆う
- ~~**深い階層では末尾（いま居るフォルダ名）が削られる。**~~ **この受容は #870 で撤回した**（却下 3 の「覆したもの」）。当時の実測（2026-07-29・既定幅 600px・日本語 UI）は**パス 71 字なら全部見え、94 字で leaf も接尾辞も消える**で、**受容の裁定（ユーザー・2026-07-29）**は「必要だったらユーザーが幅を大きくすれば解決する」——`window_width` という逃げ道が利用者の側にあることが決め手だった。
  **撤回の理由は逃げ道の有無ではない**: 実際の失敗様態が「読めない」ではなく「**区別できない**」だったこと（2026-08-01 実測）。幅を広げれば解決する点は今も変わらないが、広げるまでのあいだ画面は**誤った情報を示していない**のではなく**現在地を示していない**——#743 の誤読を防ぐという目的そのものが立たない。**残った受容は「leaf が予算の半分を超えると leaf 自身も途中から削れる」ことだけである**（`SPEC.md`「6.7 フォルダ展開中の現在地表示」）
- **末尾 `\` の揺れを正規化しない**（`C:\ 内を検索...` と `C:\d\Cafe 内を検索...` が混ざる）。撤去済み WebView2 版も同じ値を出していた
