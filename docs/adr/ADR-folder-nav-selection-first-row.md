# ADR-folder-nav-selection-first-row: フォルダ遷移後の選択は 1 行目とし、遷移元の行を追わない

## 文脈

#743 は「フォルダ展開中の `←` が階層を上げず、選択だけが親フォルダ行へ動く」というバグ報告として起票された。実機の協働トレース計測（`←` 7 打鍵・列挙結果の受理と適用をトレース）で**症状は再現せず、階層は毎回正しく上がっていた**ことが確定した。行は毎回差し替わっており（1 行 → 133 行）、画面のスクリーンショットとも一致した。

観測が「選択だけが動いた」に見えた理由は 2 つの合流である。(1) 通常検索からの `←` は展開履歴を記録するため、親を列挙すると直前まで居たフォルダが並び順の先頭へ来やすく、遷移が選択を 1 行目へ戻す結果その行に載る。(2) 候補が少ないと結果ウィンドウが 1 行分まで縮み、戻ったときに直前の画面と見分けにくい（後者は #835 へ切り出した）。

そのうえで、issue 本文は期待として「直前まで居たフォルダの行が選択されるのが自然」と述べていた。展開後の選択位置は SPEC が定めておらず、**as-built を明文化するか、issue の期待どおりに実装するか**を決める必要があった。

## 決定

**遷移後の選択は 1 行目とする**（現行実装のまま）。この as-built を SPEC §6.1 に、**2 段の形**で明文化する——打鍵の時点で 1 行目へ移り、非同期に届く候補の到着では 1 行目へ戻さず件数の範囲内へ収めるだけである。

あわせて「直前まで居たフォルダの行が選ばれることは保証しない」を明記する。

## 検討した代替案と却下理由

- **遷移元のフォルダの行を選択する（issue が「自然」と述べた挙動）**: 却下。遷移元のディレクトリを持ち越し、**非同期に届いた列挙結果の中からその行を探して選ぶ**状態が要る。この状態は folder フィルタの打鍵・列挙失敗時のエラー行・結果が届かないままの窓・遅着した旧トークンの結果と相互作用し、いずれの組み合わせでも「どの行を選ぶか」を決めねばならない。得られるのは 1 段目の遷移でしか体感できない利便であり（`←` による上昇は展開履歴を記録しないため、2 段目以降は今でも遷移元が先頭に来ない）、費用に見合わない。
- **「置換後の選択は常に 1 行目である」と 1 文で書く**: 却下。**実装より強い主張**になる。候補の到着経路は選択を 1 行目へ戻さずクランプするだけで、ロード中の上下カーソルキーによる移動を抑止する仕組みも無い。1 文で書くと、規範を忠実に守る読者を誤りへ導く。
- **選択の規則を `←` の項にだけ書く**: 却下。`→` も同じ遷移を共有しており、片側だけに書くと `→` が仕様の外へ落ちる。

## 帰結

- SPEC §6.1 に選択の規則が 2 段で入る。`snotra-core` の並び順は書き写さず、「並び順が決める」とだけ述べる（正本は `folder.rs` の module doc）。
- `search_state.rs` の純粋核テスト 5 本が、階層上昇・ルート終端・遷移時の選択リセット・到着時のクランプ・0 件到着を固定する。**射程は状態核の合成であって driver の分岐ではない**——`←` の分岐を殺してもこの 5 本は緑のままであり（実測）、分岐の正しさを支える証拠は上記のトレース計測である。
- 「遷移元の行を選ぶ」を将来やりたくなったら、本 ADR の却下理由（相互作用する 4 つの状態）が出発点になる。
