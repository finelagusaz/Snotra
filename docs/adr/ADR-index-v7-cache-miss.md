# ADR-index-v7-cache-miss: 照合用の正規化を変えた版上げで、v7 の index.bin を cache-miss として扱う

照合用の正規化の入口を 1 つにしたことで（#1309）、`index.bin` の派生の列（`lower_names` / `lower_file_names`）とマスクの意味が変わり、`INDEX_CACHE_VERSION` を 7 から 8 へ上げた。**この ADR が残すのは、v7 を読んだときの扱いで却下した案である**——採った扱い（v7 は読まず、呼び出し側の全走査で 1 回だけ置き換える）はコード（`load_cache_in`）が持つ。

## 文脈

v2〜v6 の旧版枝は、読んだ走査結果 `entries` を手に持っているので、その場で導き直して現行版で書き戻せる（`upgrade_legacy_cache_in`）。**v7 は `entries` を持たず、木を直に読む。** 派生の導出（`derive_columns`）はファイル名を得るのに `target_path` のフルパスを要るので、v7 から導き直すには何らかの形で木を作り直すか、木から直接導出する経路が要る。

v7 は、版を上げた時点で全ユーザーの `index.bin` が置かれている版である。

## 決定

v7 は読まない。`load_cache_in` は v7 で `None` を返し、呼び出し側の cache-miss 枝が全走査して v8 で書く（更新後の初回起動で 1 回だけ、22〜30 秒）。内訳の計器（`cache_byte_breakdown_in`）だけは v7 を読み続ける。

## 検討した代替案と却下理由

- **A. 木を実体化して旧版枝と同じ昇格に乗せる**（`tree.materialize()` → `upgrade_legacy_cache_in`）: 却下。全走査を伴わず、費用は昇格する起動 1 回の実体化のピークだけで済み、**plan-review の独立導出はこちらを推奨した**。だが `snotra-core/CLAUDE.md`「indexer.rs の索引更新の契機」が「昇格をロード側に置いてはならない」の射程を v7 の枝と定め、木から作り直す複製の復活を戒めている。A はその規範を書き換える変更であり、ユーザーに諮った結果、規範を変えずに単純な形を採った（2026-10-31）。**費用の比較では A が勝つ**ので、全走査の 1 回が問題になったら、規範の書き換えと合わせて再検討する。
- **C. 木から直接導出する経路を足す**（非根は `name` と拡張子、根は `table` のフルパスの末尾からファイル名を復元する）: 却下。ファイル名を取り出す規則が `Path::file_name` と木の復元の 2 つになり、`search/build.rs` が戒める「木専用の導出を書き起こさない」に反する——規則が 2 つあると、片方の経路だけが静かにずれる。
- **派生の列だけを捨て、書き戻さずに毎起動導き直す**: 却下。明示的な再構築をしない利用者は毎起動 Wave 1 を払い続ける。「indexer.rs の索引更新の契機」が挙げる「新形式の削減を永久に受け取らない」と同じ形になる。
- **D. 版を上げず、毎起動 Wave 1 をやり直す**: 却下。キャッシュヒットの起動で Wave 1 を飛ばすという v4 以降の前提を壊す。
- **E. 版を上げず、旧い列を使い続ける**: 却下。`snotra-core/CLAUDE.md`「データ永続化の注意」の「データの意味を変える場合も版を上げる」に反する。索引の更新は明示操作だけなので、名前側の旧い意味は何か月でも残りうる。

## 帰結

- いちばん新しい v7 のユーザーだけが全走査を払い、v6 以前のユーザーは安く昇格する、という逆転を受容した。
- 次に派生の列の意味を変えるときも、その時点の現行版は同じ問いに当たる（木を直に読む版は `entries` を持たない）。
