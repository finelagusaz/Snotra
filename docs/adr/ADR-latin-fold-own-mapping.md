# ADR-latin-fold-own-mapping: nucleo-matcher 0.3.1 の壊れた折りたたみ表を、照合器を替えずに自前の写像で迂回する

## 文脈

照合用の正規化の 1 文字の写像（`query.rs` の `fold_char`）は、nucleo-matcher 0.3.1 の `chars::normalize` を呼んでいた。その表は壊れており、U+1D00 以降を誤った字へ写し（`ẗ`→`n`・`ḋ`→`e`・`ⁱ`→`a`）、結合文字を 2 つ持つ字（`ǘ` など 22 字）を畳まなかった（#1395）。照合器の内部も、`Config.normalize` が真なら同じ表を名前の側にだけ当て直していた。

上流（helix-editor/nucleo）の master は 2024-12 に表を作り直しているが、crates.io の最新は 0.3.1（2024-02）のままで、リリースを求める上流の issue（helix-editor/nucleo#86）にメンテナの返事は無い（2026-11 時点）。照合器の開発そのものは止まっていない（master には 2026-06 までコミットがある）。

## 決定

照合器は 0.3.1 のまま使い、折りたたみだけを自前の写像にする。照合器の折りたたみ（`Config.normalize`）は切る。写像の規則はコード（`query.rs` の `fold_latin`）が持つ。

## 検討した代替案と却下理由

- **上流の master を git 依存で固定する**: 却下。表の修正は入るが、未リリースの差分（大文字小文字を区別する前方一致の修正など）で検索順位が変わりうる。表の誤りのためだけに照合器の挙動の差分を抱えることになる。
- **既存のフォーク `ncp-matcher`（alexrutar/ncp-engine）へ切り替える**: 却下。crates.io にあり更新もされているが、README が自ら「Unstable fork」と書き、メンテナは 1 人である。`prefer_prefix` のスコアの変更を含み、順位が動く。
- **自分でフォークして保守する**: 却下。Snotra が使うのは 4 つの API（`Matcher::fuzzy_match`・`Utf32Str` / `Utf32String`・`chars::graphemes`・`chars::normalize`）だけだが、照合器の保守と上流の取り込みを抱える。壊れているのは折りたたみだけで、照合器は動いている。
- **別の照合器（`frizbee` など）へ移る**: 却下。算法が違い（SIMD の Smith-Waterman）、順位が大きく変わる。SPEC §4.1 の「nucleo-matcher 相当」も書き換えになる。
- **上流の修正版の表を写す**: 却下。nucleo-matcher は MPL-2.0 で、Snotra は MIT である。しかも上流の修正版にも誤りがある（`ḋ`→`e`・`ḣ`→`g`・`ẉ`→`j`・`⁹`→`0`）。Unicode の分解から導く規則なら、表のデータを写さずに済み、上流の誤りも持ち込まない。
- **範囲で区切り、U+1D00 以降だけ自前にする**: 却下。U+1D00 未満にも未折りたたみの字（`ǘ` など）がある。分解の規則は全範囲に当て、0.3.1 の写像は分解できない字の受け皿として U+1D00 未満だけに残す（範囲で区切るのは、0.3.1 に頼る側である）。

## 帰結

- U+1D00 未満の分解できない字（`ł`・`ø`・`ß` など）は、0.3.1 の写像をそのまま使い続ける。その範囲の写像は、`query.rs` のダイジェストの検知器が固定する。依存を上げて写像が動けば、検知器が落ちる（`index.bin` の版を上げてから値を更新する）。
- 上流がリリースを再開しても、この写像は自動では置き換わらない。照合器を上げるときは、照合器の折りたたみを切ったまま使えるかだけを確かめればよい。
