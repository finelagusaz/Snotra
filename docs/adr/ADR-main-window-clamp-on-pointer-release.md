# ADR-main-window-clamp-on-pointer-release: メインウィンドウの作業領域への復帰は「ポインタを離した時点」で行う

**状態**: 採用（2026-08-04・#738）

## 文脈

`main` 窓はドラッグで作業領域の外へ持ち出せた（#738・実機観測は #749 の目視）。直前の #904 が人間裁定として「**バーの位置はユーザーが決め、行の出没では動かさない**」を確定させており、復帰の設計はこの裁定を壊さない範囲で選ぶ必要があった。

採用したのは「**ポインタが押されていないフレームで、バー高ぶんの矩形を作業領域の内側へ戻す**」である。以下は却下した案とその理由——採用案の説明はコード（`window_coordinator::clamp_main_into_work_area`）と `SPEC.md` §8.2 が持つ。

## 却下 1 — `WM_MOVING` をフックして移動矩形そのものを拘束する

「ドラッグ中も作業領域から出られない」を真に保証できる唯一の手段である。却下した理由は 2 つ。

- `main` 窓の wndproc は tao の所有であり、サブクラス化が要る。`src-tauri/CLAUDE.md`「ある窓の show / hide / topmost のいずれか 1 つが tao を迂回したら、残り 2 つも必ず迂回側へ寄せる」が戒める混在と同じ性格の介入になる
- **得られるのは「ドラッグ中も出せない」だけである。** ユーザーの要求は「持っていこうとしても復帰する」であり、離した時点の復帰で満たされる（人間裁定・2026-08-04:「ユーザーがドラッグ操作を終えたら、戻るでOK」）

## 却下 2 — 毎フレーム無条件にクランプする

初版の計画はこの形で、「ドラッグ中に引き戻されるゴムバンド挙動でも受け入れ条件を満たす」と判定していた。**この判定は誤りである。**

横並びの作業領域 A=`0..1920`、B=`1920..3840`、窓幅 600px を考える。A から右へ運ぶとき、左端が `1320..1620` の区間では**まだ A との重なりが優勢**であり、毎フレームのクランプはそのつど `x=1320` へ引き戻す。**B が優勢になる `x>1620` へ到達できず、通常速度のモニター間移動が事実上封鎖される。**

これは #738 のコメント 1 でユーザーが挙げていた懸念（「ディスプレイ間移動で邪魔になったりしないか」）そのものだった。

## 却下 3 — 基準モニターを `MonitorFromWindow`（窓全体の矩形）で決める

既存の `monitor::window_monitor_work_area` を再利用する素直な形だが、**採用すると本 ADR の修正自身が #904 の裁定を破る。**

`MonitorFromWindow` はウィンドウ全体の矩形の重なりでモニターを選ぶ。上下に隣接するモニターでバーを上側の下端付近に置き、status 行 + toast 行が出て実ウィンドウの大部分が下側へ伸びると、基準モニターが下側へ切り替わる——**行が出ただけでバーが隣モニターへ飛ぶ**。

ゆえに `monitor::point_monitor_work_area` を新設し、**バー矩形の中心**から決める。バー矩形は行の出没で変わらないので基準も動かない。同じ理由で `read_placement_relative`（hide 時の保存）も同じ基準へ揃えた——揃えないと、保存座標の原点が「hide の瞬間に行が出ていたか」で変わり、次の show でバーが 1 枚ぶん飛ぶ。

**`results_available_height` だけは `MonitorFromWindow` のままにした。** results は main の**下**に置かれるため、main が下側モニターへ伸びている状況では伸びた先のモニターの `bottom` で高さを切るほうが意図に合う。揃えるべきなのは「バーの位置を決める／記録する」経路だけである。

## 却下 4 — 幅設定の変更フレームだけクランプを止める

計画段階では「画面端付近で幅を広げると重なりが隣モニター優勢になり、意図しない方向へ飛ぶ」ことを理由に、幅変更では位置を動かさない方針を SPEC へ書こうとした。**実装後の検証で撤回した。**

クランプは「ポインタ非押下の全フレーム」で働くため、幅変更フレームだけを除外していない。除外するには幅の変化を別に検出する仕組みが要り、得られるのは「隣モニターへ飛ばない」だけである。人間裁定 2（「ディスプレイまたぎで表示されるユースケースは想定しなくてOK」）と 3（「ユーザーが自力で作業領域内に戻せるなら問題なし」）により受容できると判断し、**SPEC を as-built へ直した**（`.claude/rules/spec.md`「as-built を記述する」）。

## 却下 5 — reset-on-show フレームではガードを外す（固着の backstop）

`code-reviewer` の指摘（Medium）に対する対処案で、**動機は正しい**。egui が押下フラグを落とすのは `Event::PointerButton{pressed:false}` を受けたときだけで、`PointerGone` でもフォーカス喪失でも落ちない（egui 0.35 の `input_state`）。press に対応する release が届かない経路が 1 つでもあれば `any_down()` はプロセス寿命のあいだ `true` に固着し、**クランプが黙って死ぬ**——しかも検知手段が無い。

`if was_reset_frame || !any_down()` とすれば show ごとに自己修復する、という案だった。**実測で却下した。**

| | ドラッグ中の top | 離した後 |
|---|---|---|
| backstop 無し | 1050（**外側のまま**＝正しい） | 956 |
| backstop 有り | **956（引き戻される）** | 956 |

**却下 2 の封鎖がそのまま現実になる。** 人間裁定「ドラッグ操作を終えたら戻る」を壊すため採らない。

**ゆえに押下フラグの固着は受容する残余である。** 根拠は、想定した「release が届かない」状況が実測では起きないこと（ドラッグ後に何も操作せず放置して 0.5s で復帰する。tao の `WM_EXITSIZEMOVE` が `WM_LBUTTONUP` を合成する経路がある）。届かない環境が見つかったときに、封鎖を起こさない形で改めて設計する。

**再測の手順**: 治具を書いて `SetCursorPos` + `mouse_event` でドラッグを注入し、押下したままの窓矩形と、離して 0.5s 後の窓矩形を `GetWindowRect` で比べる。押下中に窓が引き戻されていれば封鎖が起きている。

## 検討したが本 PR では動かさなかった構造側の選択肢（#878 継ぎ目 2）

**上の却下 1〜5 はすべて policy である**——「いつクランプするか」「どのモニターを基準にするか」の変奏であり、「**誰が窓の幾何を所有するか**」を問うていない。その問いは #878 が親 issue として整理しており、本 ADR がそれを閉じたわけではない。

#878 は継ぎ目 2 についてこう書いている——`position_on_target_monitor` が**高さを引数で受け取れば** `show_egui_main` の collapse（2 手 `set_size`）が不要になる。これを先に動かすと、本 PR が抱えた次の 2 つが**構造的に成立しなくなる**。

- show 経路（`set_size` → `outer_size()` の読み戻し）とクランプ経路（`bar_rect_height_phys` + 非クライアント分）で、**同じ物理バー高が 2 通りに導出されている**。一致は `dpi` crate の丸め規則に依存し、テストで固定できない（`layout::bar_rect_height_phys` の doc）
- OS の窓が高さを渡す唯一の経路である限り、`show_egui_main` の 2 手 `set_size` を退役させられない

**動かさなかった理由は、#801 の修正で「2 手 `set_size`」を決めた直後であり、その構造に触ると同じサイクル内で 2 度作り直すことになるためである。** #738 の症状（ドラッグでバーが画面外へ出る）は継ぎ目 2 に触らずに閉じられる。

**残っている代価**: 本 PR は OS の窓から幾何を読み戻す箇所を 1 つ増やし（`read_bar_anchor`）、`view.rs` を main の位置の第 2 の書き手にした。#878 が「分割の代価が毎回バグとして支払われている」と書いた集計に、本 PR も 1 行を加える側である。**#760（継ぎ目 4 の残り半分）に着手するときは、継ぎ目 2 を先に動かすほうが安いかを必ず量ること。**
