# ADR-modal-move-loop-clamp-suppression: モーダル移動ループ中のクランプ抑止を実装しない

**状態**: 採用（2026-08-27・#1194）

## 文脈

#1173 が「キーボードによる窓移動（`Alt+Space` → `M` → 矢印）とクランプの相互作用が未検証」と
提起し、PR #1193 が「移動中もクランプが発火し、外に留まれない」と実測して `SPEC.md` §8.2 と
`clamp_main_into_work_area` の rustdoc へ着地させた。#1194 はその修正——`any_down()` に代わる
「移動中である」の判定を入れてキーボード移動を拘束から外す——を実装するために起票された。

**実装前の計測で、修正の前提が再現しなかった。** 以下は却下した案とその理由である。採用した
挙動（＝現状のまま）の説明はコードと `SPEC.md` §8.2 が持つ。

## 却下 1 — `GetGUIThreadInfo` の `GUI_INMOVESIZE` でクランプを抑止する

#1194 の本命案であり、`clamp_main_into_work_area` の rustdoc が候補として名指していたものである。
**実装可能性まで確かめた上で却下した。**

実装可能性について確かめたこと（いずれも実測）:

- `GetGUIThreadInfo` / `GUITHREADINFO` / `GUI_INMOVESIZE` は `windows` 0.62.2 の
  `Win32_UI_WindowsAndMessaging` に在り、**`src-tauri` が既に有効にしている feature だけで揃う**
  （同じ feature 集合だけを持つ使い捨て crate でコンパイル・実行し、`Ok(())` と
  `flags`・`hwndMoveSize` の値まで確認した）
- スレッド id は `GetWindowThreadProcessId(main_hwnd, None)` で窓から引ける。
  **`GetGUIThreadInfo(0, …)` は「フォアグラウンドスレッド」であって呼び出しスレッドではない**
- ゆえに `ADR-main-window-clamp-on-pointer-release` 却下 1（tao の wndproc サブクラス化）には
  当たらない

**却下の理由は「効かない」である。** 3 条件 13 反復の計測で、**モーダル移動ループ中に egui の
フレームが 1 枚も回らない**ことが分かった（移動区間 3 秒に対し `egui_frame` は 0 枚、
フレーム間隔の最大は 5.9 秒）。クランプはフレームでしか走らないので、**抑止すべき発火が
そもそも存在しない**。述語を入れても挙動は 1 ビットも変わらず、可視中の毎フレームに Win32
呼び出しが 1 回増える費用だけが残る。

**副次的な理由**: この経路では述語の真の側を観測できない。読み手はクランプのフレームだけで、
そのフレームがループ中に走らないためである。`/symmetric-check` が求める「真偽が両向きに立つ」
ことを**実測で示せない**判定を、挙動を決める位置へ置くことになる。

**述語そのものは観測専用として残した**（`main_in_modal_move_loop`）。`egui_main:clamp` の
`in_move_size` 欄がそれで、**「フレームが回らない」という前提を後から偽にできる唯一の検知手段**
である。前提が崩れれば欄が真を出し、そのとき本 ADR を覆せばよい。

## 却下 2 — `WM_MOVING` をフックして移動矩形を拘束する

`ADR-main-window-clamp-on-pointer-release` 却下 1 と同じ案である。**同 ADR は凍結された歴史ゆえ
引用で退けず、却下理由が今も真かを測り直した**（`adr-rejection-reasons-can-go-stale`）。

**理由 1（tao 所有の wndproc へサブクラス化が要る）は今も真である。** tao 0.35.3 の
`WindowExtWindows` が公開するのは `hwnd` / `hinstance` / `set_enable` / `set_taskbar_icon` /
`set_overlay_icon` / `theme` / `reset_dead_keys` / `begin_resize_drag` であり、**wndproc フック・
サブクラス化の公開 API は無い**（`platform/windows.rs` を走査して 0 件）。`WM_MOVING` を
捕まえるには今も `hwnd()` から自前で `SetWindowSubclass` する必要がある。

**理由 2（「離した時点の復帰で満たされる」）は射程が狭かった**——キーボード移動に「離す」は
無い。だが #1194 の計測で拘束そのものが再現しなかったため、**この欠けは採否を変えない**。

## 却下 3 — モーダルループ中に `ctx.request_repaint()` で鎖を繋ぐ

却下 1 を採った場合に要る補助案だった。「確定後の最初のフレームで 1 度だけ戻る」を保証するには、
フラグが偽へ落ちた最初のフレームが要る——ループ中の各フレームで repaint を再要求して鎖を繋ぐ、
という形である。

**独立に実測で潰れた。** 一時通知（updater toast）を出した条件でも、モーダルループ中のフレームは
0 枚だった。toast は armed 期限を持ち毎フレーム残余を再要求する
（`src-tauri/CLAUDE.md`「期限を待つ状態（armed）は…」）にもかかわらず、**`request_repaint_after`
の鎖はモーダルループを越えない**。繋ぐ相手のフレームが来ない。

## `.claude/rules/src-tauri.md` の `PlatformBridge` 既定に逆らった点

同 rule は「Win32 を呼ぶ経路の新設は `PlatformBridge` 経由を既定とする」と定める。
`main_in_modal_move_loop` は**直呼びである**。理由は、問うているのが**その窓の所有スレッド自身の
状態**だからである——platform スレッドのメッセージループへ委ねると、答えるのは別スレッドに
なり、`GetGUIThreadInfo` が返す値の意味が変わる。委譲すると測りたいものが測れなくなる。

## 受容する残余

- **#1173 / PR #1193 の実測と本 ADR の実測が食い違ったままである。** どちらかが誤りとは
  判定していない——挙動はフレームの有無で分かれうるので、両方が別条件の真でありうる。
  あちらの記録に条件（arrow の cadence・クエリの有無・index build の進行中か・hide/show を
  挟んだか）が残っておらず、**再現できなかった**
- **多モニターでの封鎖は依然として未測定である**（開発機が単一モニター）。#1194 では
  人間裁定により単一モニターの代替判別子（作業領域の下端で止まるか、カーソル限界まで出られるか）
  で進めた
- **確定後に窓を動かす OS 側の経路は名指したが直していない**（#1194 Q2）。純平行移動であり、
  その後にクランプが 1 度だけ働いて作業領域の内側へ戻すため、最終位置は仕様どおりである
