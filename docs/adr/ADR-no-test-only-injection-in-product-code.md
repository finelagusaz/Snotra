# ADR-no-test-only-injection-in-product-code: 計測・検査のために製品コードへ注入点を足さない

- 状態: 採用
- 日付: 2026-08-09
- 文脈: #1000（起動の端から端までを刻む計器）の Phase 3

## 決定

**変異試験や計測のためだけに、製品コードへ失敗注入点・観測フックを足さない。**

## 却下した案

`startup.rs` の `StartupFailure` は 7 分類を持つが、実機で観測できるのは
`HotkeyRegistration`（`RegisterHotKey` の失敗）だけである。残る 6 つ——bridge の spawn 失敗・
Win32 初期化失敗・channel 切断・bridge state 不在・`Mutex` の poison・窓の生成失敗——は、
**外から起こす手段が無い**。

計画は変異試験 (m)〜(r) でこれらを模擬することにしており、そのために次の案が挙がっていた:

- **A. 既存のエスケープハッチを増やす** — `platform/mod.rs` には
  `SNOTRA_FAKE_INITIAL_HOTKEY_FAILURE` という前例がある（#652 の受け口検証用）。同じ流儀で
  `SNOTRA_FAKE_BRIDGE_SPAWN_FAILURE` 等を足す
- **B. テスト専用の注入点を作る** — `PlatformBridge::begin` に失敗を差し込める seam を開ける

## 却下の理由

**計測しきれないリスクは残るが、本来不要なコードがトラブルの原因を作り込む理由にはならない。**

- 注入点は**製品が実際に通る経路に分岐を増やす**。分岐は状態を増やし、状態は組み合わせを増やす
- ハッチは env で制御される以上、**製品の起動経路に env 読みが 1 つ増える**。#872 は
  「PowerShell の env 復元が空文字を作り、測定ハーネスの全反復が黙って計器つきで走っていた」
  という事故を記録している——ハッチ自体が事故の面になる
- 得られるのは「その経路で `startup:failed` が出ること」の確認だけであり、**その経路が
  本番で起きたときに正しく動く保証にはならない**（模擬した失敗と本物の失敗は別物である）

## 受容する残余

- 失敗経路 6 つは**実機で一度も観測していない**。守っているのは写像の網羅性
  （`StartupFailure::from` の網羅 match と `reason` の一意性）だけである
- `PlatformBridgePending::wait` の channel 切断が**本番でどう起きるか**は未特定のまま残る

この残余は `startup.rs` の `//!`「受容する残余」が正本として持つ。

## この決定が及ぶ範囲

**計測・検査のための注入に限る。** 製品の要件から必要な分岐（config による挙動の切り替え等）は
対象外である。また `SNOTRA_EGUI_FAKE_UPDATE` / `SNOTRA_FAKE_INITIAL_HOTKEY_FAILURE` のような
**既存のハッチを撤去する決定ではない**——それらは視覚スモークが他に手段を持たない箇所で、
費用と便益の勘定が別である（新設のハードルを上げるだけで、既存を否定しない）。
