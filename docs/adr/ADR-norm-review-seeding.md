# ADR-norm-review-seeding: `/norm-review` を 2 クラス読者から種蒔き（フォールトインジェクション）へ移した際に却下した案

`/norm-review` の測り方を「文言だけを渡した 2 クラスの読者に抜け道を探させる」から「**その条項が捕まえると自称する欠陥を種として蒔き、捕まえるかを見る**」へ移した。**この ADR が残すのは、そのとき却下した案である**——採った手順は `/norm-review` 自身と `pressure-scenario.md` が持つ。

## 文脈

`.claude/rules/safety-nets.md` 第一節は「効いていることはフォールトインジェクションで一度は実測する」と定める。規範に対しては「フォールトインジェクション ＝ 回避しようとする読者」と置き換えていた。**この置き換えが誤っていた**——フォールトインジェクションが測るのは「種を蒔いて検出器が捕まえるか」（結果に接地）であり、2 クラス読者が測るのは「文書が敵対的パーサに耐えるか」（文章に接地）である。`.githooks/githooks.test.mjs` は前者の形を持つが、規範だけが類推で代替されていた。

3 つの独立した測定が同じ方向を指していた:

| 出所 | 測定 |
|---|---|
| `docs/adr/ADR-two-class-reader-discrimination.md` | 素性の異なる 4 文書で規則を守る読者の件数が 17〜20（ばらつき 3 件）。件数は文書ではなく道具の署名 |
| `docs/check-skill-skeleton-design.md`「検証」 | 塞ぐほど忠実な読者の詰まる箇所が 18 → 21 件へ増え、手を抜く読者の突破は 5/5 → 4/5 とほぼ動かず |
| `#787` | 1 行のファイル索引更新に対して 13 件中 12 件を降格 |

加えて、`superpowers:writing-skills`「Match the Form to the Failure」が同じ現象を head-to-head の実測つきで記録していた——出力の形が違う／要素が落ちるクラスへ禁止形を当てると、**指示なしの対照より悪い**。同節は「Exemption clauses don't scope. If part of the output must be exempt, restructure so the rule can't reach it」とも述べており、これは骨格の検証節が独立に観測した「免除の射程を限定した隣に穴が空いた」と同一の現象である。**一般則は「構造を変えろ」と言い、こちらの対応は「射程をもっと丁寧に限定する」だった。**

本リポジトリの規範を否定終止（「〜ない」で終わる文）の割合で測ると、硬化の系譜と未硬化の世代がきれいに割れた: `health-check` 26% / `race-check` 16% / `plan-review` 15% / `implement` 14% / `norm-review` 10% に対し、`persistence-check` `symmetric-check` 4% / `cache-check` `state-check` `dry-check` 0%。`#788`（`/race-check` の簡素化）は字数を 9176 → 7381 へ 2 割削ったが、否定終止は 12% → 16%、太字密度は 9.0 → 10.6 へ**上がった**——削れたのは手順と例示の側であり、禁止は残渣として残る。

## 検討した代替案と却下理由

### 却下 1: 2 クラス読者を残し、種蒔きと併存させる（網羅性の保持）

忠実な読者は文書全体を走査するが、種蒔きは種が通った経路しか踏まない。網羅性は確かに落ちる——`docs/adr/ADR-two-class-reader-discrimination.md` 却下 4 が記録するとおり、規則を守る読者は 1 サイクルで 3 回、実際に手を止めさせた（循環参照・証跡要求による実行不能・要石と候補集合の論理衝突）。

しかし併存は費用を二重にしたうえで、**判別力の無い計器を残す**。`docs/adr/ADR-two-class-reader-discrimination.md` 却下 1・2 が既に「件数は品質の順序を与えない」と結論しており、残す根拠は「稀に本物を拾う」に留まる。**網羅性の喪失は受容する残余として引き受ける**（ユーザー裁定・2026-07-28）。**代替の受け皿は無い**——`/plan-review`「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」と `code-reviewer` は経路外の論理衝突を拾いうるが、`AGENTS.md`「条件別チェック（トリガー → 参照先）」表は規範のみの変更をどちらへも振り分けておらず、**現状そこへ到達する起動条件が存在しない**。委譲すると書けば、走らない検査を走るものとして数えることになる。振り分けを足すかどうかは規範の変更であり、別途の合意を要する。

### 却下 2: 手を抜く読者だけを残す（安価な側を残す）

指摘が真であることと判別することは別である（`docs/adr/ADR-two-class-reader-discrimination.md` は義務形密度の計測でこれを示した——「義務文が一つも無い」という指摘はリポジトリの規範すべてについて真だった）。加えて、その指摘を修理すると 4/4 で新しい欠陥が出る。**安い方を残すと、最も有害な方を残すことになる。**

### 却下 3: skill を改名する（`norm-fault-injection` 等）

`superpowers:writing-skills` の命名規約（動詞先行・現在分詞）には適うが、`ADR-command-shape-norms-in-hook` `0010` `0011` `0012` `0013` と `docs/check-skill-skeleton-design.md` が `/norm-review` を名指しで参照しており、**ADR は過去の事実の記録であるため書き換えられない**（書き換えれば当時そう呼んでいたという事実が消える）。名前の改善より参照の安定を採る。

### 却下 4: 起動条件を `paths` glob で絞る

`#787` は「起動条件を『条項を足す変更』に限定する」を選択肢に挙げていた。しかし `.claude/rules/safety-nets.md` の `paths` は**ファイル粒度**であり、「その変更が判定を足したか」を表現できない。glob をいじる代わりに、`safety-nets.md` の要求文へ「判定を足す変更で起動する」を書いた。

**実際にはこれは二重の防御である**——種蒔きは起動前に「この変更が捕まえるべき欠陥」を書くことを要求するので、索引の追随や改名では**母集団が空になって検査が自然に終わる**。要求文はそれを明示しているにすぎない。

### 却下 5: 規律型の失敗（`#504` 型）も種蒔きで測る

`#504`（条件節を免除と読み、ライブの `pre-commit` を無害化して main 保護が数十秒消えた）は「知っていて破る」クラスであり、通常の作業を走らせるだけでは現れない。種蒔きで測ろうとすると、種が事実上 pressure scenario になる。

`superpowers:writing-skills` は失敗様態ごとに別の道具を割り当てており（discipline には禁止 + 合理化表 + red flags、shaping には recipe）、**1 つの手順へ混ぜることが今回の病因そのものだった**。ゆえに `pressure-scenario.md` として別ファイルへ置き、`SKILL.md` Step 4 の表から 1 行で分岐させる。常時ロード面は増えない（skill 本文は `AREA_BUDGET.alwaysLoaded` の母集団外・`docs/adr/ADR-implement-step4-report-slot.md` 帰結）。

### 却下 6: `allowed-tools` へ `Edit` を足す（`#782` の選択肢 b）

`#782` A1 は「`allowed-tools` に書き込み手段が無いのに Step 3 が書き換えを要求する」を先行欠陥として挙げ、(a)「修正は呼び出し側が行う」の明記と (b) `Edit` の追加を選択肢に置いていた。種蒔きは RED-GREEN の往復（修正 → 同じ種で再走）を含むため (b) が素直に見えたが、**測る側が測られる文書を書き換える構図**は `/plan-review` が `Write` を意図的に外した理由（自作自演の防止）にそのまま当たる。(a) を採り、Step 4 へ 1 文を置いた。

なお本 PR での (b) の試行は、harness の権限分類器が権限拡大として遮断した——**設計判断の前に機構が同じ結論を出した**格好である。

## 帰結

- **対照（規範なし）のランが「この条項は不要」を出せるようになった。** 2 クラス読者は敵対的読者ゆえ必ず穴を見つけ、**規範が増える方向にしか出力しない計器**だった（`#764` の 3.4 倍がその帰結）。`docs/development-principles.md`「構造的設計原則と強制の階梯」は、構造が規則を吸収したらチェックリストを削除し、ドキュメントが軽くなることを設計改善の検収条件とすると定めていたが、それを満たす証拠を作る道具が無かった
- **停止条件が接地した。** 「上限 2 巡」という恣意的な上限から、「同じ種で捕まえるまで、2 度目の修正でも素通りするなら `BLOCKED`」へ。`BLOCKED` が機能した実績は `docs/adr/ADR-race-check-simplification.md` にある
- **指摘という中間生成物が消えたことで、その裁定にまつわる機構が不要になった。** `#775` が置いた等式（`N+M = K+L+R`）は「降格が沈黙する経路」を塞ぐものだったが、種蒔きの三値（捕まえた／素通りした／対照も捕まえた）には降格が無い

## 受容する残余

- **網羅性**（却下 1）。文書全体の走査は行われない
- **`docs/check-skill-skeleton-design.md`「検証」節の成功判定は 2 クラス読者を前提に書かれている**（「忠実に実行すると詰まる箇所が減ったこと」）。骨格の移行順序 4（`/symmetric-check` への適用）の時点で再評価が要る。本 PR では触れていない
- **本変更自身への自己適用は行っていない。** 新しい `/norm-review` を自分自身へ当てる（種を蒔く）のが筋だが、`/implement`「4b. code-reviewer エージェント」は `Agent` の起動を 1 体に限っており、種蒔きは対照/本番で複数体を要する。**`/implement` の外で別途実行する**——`docs/adr/ADR-check-skill-skeleton.md` が骨格自体に読者を当てたのと同じ位置づけの作業である
- **`pressure-scenario.md` は一度も実行されていない。** `.claude/rules/safety-nets.md`「効いていることは、フォールトインジェクションで一度は実測する」の対象であり、`#772` が `/norm-review` に対して行ったのと同じ初回実測が要る
