# ADR-path-query-forward-single-pass: パスクエリの走査を前向き 1 パスへ替えず、現行の並列走査を残した

2026-08-12、`#1059`（パスクエリの残り 6,944 µs はキー組み立てと `find`）の手段として
**逐次前向き 1 パス**——`IndexTree` が `parent < i` を保つことを使い、KMP の照合状態を添字の
昇順に親から子へ伝播して、フルパスを組み立てずに一致だけ判定する——を検討し、**最小実装で
単価を測って採らないことにした。** issue 本文が「先に最小実装で単価を測ること。勝たなければ
その実測を以てクローズする」と定めており、この ADR はその実測に基づく判断の記録である。

**実測値の正本は `PERFORMANCE.md`「却下: パスクエリの走査を前向き 1 パスへ替える」** であり、
ここには数字を写さない（判断と、なぜ再訪しないかだけを残す）。

## 前提（測って分かっていたこと）

- パスクエリは Fuzzy ビットマスク pre-filter をスキップするので、索引規模がそのまま毎打鍵に
  乗る唯一の経路である（`snotra-core/CLAUDE.md` の search.rs 節）
- `#1057` が name の Fuzzy スコアリングを飛ばして -3,824 µs を取った後も、正規化キーの組み立てと
  `find` が残る。`\zzz-no-such-path\` の p50 は 7,762〜8,731 µs（`#1059` 着手時の実測）
- **組み立て側は既にセグメント単位である。** `PathCursor` が祖先の鎖を持ち回り、大半のエントリは
  バッファを巻き戻して 1 段だけ書き足す（`search/path_store.rs` の `//!`）。
  `#1057` 本文が「フルパスを組み立て直す」と書いたのは誤りで、同 issue が訂正済み
- 現行の走査は rayon の fold/reduce で 16 並列。前向きパスは逐次になるので、
  「逐次 1 パス + 並列スコアリング」の 2 段構えになる

## 却下 1: 前向き 1 パスそのもの（**単価が削れなかった**）

**設計と最小実装は書き上がった**（`search/tests/performance.rs` に置いた spike。撤去条件
——本判定を記録した PR #1066 のマージ——が発火したので **#1067 のサイクルで撤去済みである**。
下の数字がその全成果で、コードはもう手元に無い）。
`state[i] = advance(state[parent[i]], 区切り + 自分のセグメント)` と
`matched[i] = matched[parent[i]] || 到達` を添字昇順に回す形である。

却下の理由は、**この spike 自身が明らかにした 1 つの数字**である——**逐次同士で比べたとき、
1 パスは現行走査の単価を 1.29 倍（0 件クエリ）/ 1.14 倍（全件マッチ）しか下げない。**

走査するバイト量は 1/6 になる（1 段あたり平均 20 B 対 フルパス平均 119.3 B）。それでも単価が
削れないのは 2 つの理由による:

- **`str::contains` は memchr の SIMD 実装で 1 サイクルに複数バイトを進む。** 素朴な KMP の遷移は
  1 バイトごとに分岐する。**バイト量の比は単価の比ではない**
- **組み立て側で省けるものが元から少ない。** 上の前提のとおり `PathCursor` は既に親の接頭辞を
  持ち回っており、1 パス案が新たに省くのは「巻き戻しと 1 段の書き足し」だけである

そのうえで並列度 16 → 1 の転落を払うので、実測は現行の 2.33〜3.34 倍遅い。
**しかも spike は `matched` のビット列を作るだけで、スコアも `byte_pos` も履歴照合も
載せていない**——測ったのは単価の**下限**であり、正しく作れば差は開く一方である。

## 却下 2: 前向きパスを並列化して救う案（**天井が 1.29 倍しかない**）

`C:\` 直下の部分木ごとに分割すれば、各チャンクの開始状態は親が先に確定しているので並列化自体は
可能である（**scan の根での分割は効かない**——実運用点の scan の根は 4 つで、そのうち `C:\` の
部分木が全件をほぼ占める）。

**それでも採らない。** 却下 1 で測った単価の比が上限を決めているからである:

- 並列化が完璧に効いたとしても、得られるのは**最大 1.29 倍**である。**この比は spike の実装で
  測った値**であり、KMP の内側（1 バイトごとの分岐）を詰める余地までは否定していない
  ——ただし spike は `matched` のビット列しか作らない**下限**の姿で既に負けており、
  内側をいくら速くしても下の 2 点は消えない
- その 1.29 倍は「マッチしたエントリのフルキーを作らない」ことで得た値である。実際には
  スコアの `byte_pos` と履歴照合がフルキーを要求するので、**マッチした件数ぶんの組み立てが
  後段で戻ってくる**。`c:\users\` は 96,482 件が該当し、そこでの単価差は 1.14 倍しか無い
- つまり**最良でも誤差、悪ければ退行**である。走査の形を 2 段構えへ作り替え、
  `/race-check` の対象になる並行の面を増やす対価に見合わない

## 却下 3: マッチ不能な部分木を丸ごと飛ばす案（**意味論から不可能**・測っていない）

**これは測定ではなく論証で落ちる。** パスマッチは**部分文字列**検索であり、親で照合状態が 0 に
戻っても、子孫は自分のセグメントの途中から新たに一致を開始できる。ゆえに「この部分木には
決して一致が現れない」と言える条件が存在しない。0 件ヒットのクエリでも全件ぶんの遷移を払う。

spike はこの前提（スキップ無し）で書いてあり、飛ばす最適化を入れても却下 1・2 の天井は動かない
——飛ばせる部分木が無いからである。

## 予測は結論だけ当たり、機序は 2 つとも外れていた（**この ADR で最も残す価値のある部分**）

着手前の見積もりは「バイト量が 6 倍減るが並列度で 16 倍損をするので負ける」だった。判定
（負け）は当たったが、**6× も 16× も実測と桁が違った**（単価 1.29× / 並列の利き 3.01×）。

- 見積もりを計画の「未確定」に置き、**spike で測ってから書いた**ことだけがこれを捕まえた。
  もし「16 倍の並列度を失うので割に合わない」と規範文書へ書いていたら、次の反復で
  「並列度さえ保てば勝てる」という誤った枝を生んでいた（実際の天井は 1.29 倍である）
- 並列度が 16 コアで 3 倍しか効かない**原因**は切り分けていない。メモリ帯域が支配的という推定と、
  rayon の chunk 境界ごとに worker の `PathCursor` の鎖が冷えるという対立仮説が残る。
  **比は測ったが、原因は推定である**——この区別を書かずに写すと、正しい所見の隣に未測定の
  主張が着地する

## 引き受けた残余

- **`c:\` のマッチ後コスト（約 11.4 ms・p50 15.5 ms のうち）はこの判断で 1 µs も減らない。**
  正体は 312,108 件ぶんの履歴照合・ヒープ push・tie-break であり、走査ではない。
  `#1059` の射程外として扱った
- **`c:\` の max は 1 フレームを超え続ける**（実測 18,642〜22,420 µs）。`#1059` の判定は p50 で
  行うとユーザーが決めており（2026-08-12）、p50 では 15.5 ms で内側に居る
