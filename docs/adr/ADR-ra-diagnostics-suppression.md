# ADR-ra-diagnostics-suppression: Claude Code の RA 診断を抑制せず、`mod` 宣言の書き忘れは検査で塞ぐ

#1085。`ADR-claude-code-ra-lsp-plugin-delivery`（#1083）が先送りにした「診断（diagnostics）をどう扱うか」の後始末である。先送りの条件は「まず実効設定を実測してから決める」だった。

## 文脈

抑制の機構は 2 層ある。

- **Claude Code 側の `.lsp.json` の `diagnostics: false`** — publishDiagnostics の**エージェント context への注入だけ**を止め、navigation は保つ
- **RA 側の `initializationOptions.diagnostics.enable = false`** — RA が診断を**計算しない**

判断基準は #1083 の承認時にユーザーが示したもので、エージェントが LSP から**過不足なく**情報を受け取ることにある。抑制は「過剰」の側の対処であり、過剰が実在するかが問いだった。

## 決定

**どちらの層も採らない。** `.lsp.json` に `diagnostics` キーを足さず、RA 側の `diagnostics.enable` も設定しない。

**あわせて `G-module-linkage`（`scripts/governance-check.mjs`）を新設した。** 先送りの根拠だった `unlinked-file` は抑制の採否に関わらず届いておらず、`mod` 宣言の書き忘れを見る機構が 1 つも無かったためである。

## 決定を支える実測

2026-08-14 の実測である。**この節が正本**で、他の文書はここを指す。測ったのは Claude Code が起動した RA インスタンスと、同じ `initializationOptions` で別途起動した RA である。CLI（`rust-analyzer diagnostics .`）は `cfg(test)` を立てず ratoml も読まないため測定手段に採らない。

- **量の問題は存在しない。** 実セッションで届く診断は**構文エラーだけ**だった。コメントの書き換え・改名・未リンクファイルの作成・構文エラー注入の 4 種の変異で測り、構文エラーの 2 例以外は 0 件である。改名は cargo から見れば `unresolved import` / `cannot find function` だが、ファイルを開いた状態で注入し直しても LSP 側は 0 件だった。
- **`ra-diagnostics-noise-is-baseline-not-edits` が言う底値 96 件は LSP に存在しない。** うち 94 件を占める `inactive-code` は `#[cfg(test)] mod tests` に由来し、CLI が `cfg(test)` を立てないことのアーティファクトである。LSP 側では当該ファイルを開いても 0 件だった。
- **抑制すると失うものが 1 つある。** cargo が見ないファイル（未リンクの `.rs`）の構文エラーが、LSP 側からは届く。PostToolUse hook の `fmt` / `clippy` / `test` はそこで沈黙した。小さいが、**不足の側に落ちる唯一の実測値**である。
- **`unlinked-file` は届かない。** 未リンクファイルを明示的に `didOpen` し、同じ publish 配列に構文エラーが 2 件入っている状況で、`unlinked-file` だけが不在だった。**原因は #1083 の設定ではない**——`initializationOptions` を空（RA 既定）にした対照でも結果は同一である。

測り方の詳細と、そこから外した対抗仮説は #1085 の PR 本文とレビュー記録が持つ。

## 検討した代替案と却下理由

- **Claude Code 側の `diagnostics: false` を採る**: 却下。減らせる量が無い（正常な編集で 0 件）一方、cargo が見ないファイルの構文エラーを失う。navigation が保たれるかも静的読解の傍証しか無く、確かめるにはセッション再起動を伴う実測が要る——**得るものが無い変更のために測定を積む**ことになる。
- **RA 側の `diagnostics.enable = false` を採る**: 却下。同じ理由に加え、RA が計算そのものをやめるため構文エラーも消える。CPU の節約は、正常な編集で 0 件という実測の下では対象がほぼ無い。
- **両方採る**: 却下。二重機構になり、片方を戻したときに効かない理由が分かりにくくなる。
- **`checkOnSave = false` を戻して rustc 診断を取り戻す**: 却下（本 issue の範囲外だが、実測の結果として選択肢に上がった）。rustc の診断は PostToolUse hook の `clippy` が同じものを、しかも**確定判定として**運んでいる。LSP 側に重ねると `docs/hooks.md`「Claude Code の RA インスタンスと hook の分担」が定めた分担——RA は semantic navigation の道具であり検証の権威ではない——が崩れる。
- **`unlinked-file` が出ない機序を突き止めてから決める**: 却下。RA の `ide-diagnostics` を読むと当該診断はモジュールに属さないファイルへ無条件に積まれるはずで、観測と合わない。**機序は未確定のまま残す**——分かっているのは「出ていない」ことと「我々の設定が原因ではない」ことの 2 つで、決定はその 2 つで足りる。推測を規範へ書かない。
- **`mod` 忘れの検知を別 issue へ送る**: 却下（ユーザー判断）。本 issue の実測が初めて穴の形を確定させており、同じ文脈のうちに塞ぐほうが安い。
- **`G-module-index` を拡張して `mod` 到達性も見る**: 却下。同検査は実ファイル ↔ `CLAUDE.md` の索引を双方向で照合するもので、`mod` の到達性とは見ているものが違う。1 つの検査に 2 つの命題を持たせると、どちらが落ちたのかが呼び出し側で分からなくなる。
- **新検査の母集団に `MODULE_INDEX_CRATES` を再利用する**: 却下。あれはルート `Cargo.toml` の `[workspace] members` の写しであり、その母集団カナリアが縛るのは **`CLAUDE.md` を持つ member だけ**である（実読で確認）。`CLAUDE.md` を持たない crate を新設すると黙って飛ばされる。リンク性は `CLAUDE.md` の有無と無関係なので、写しではなく導出の唯一の口（`workspaceMembers`）を使う。
- **検知を PostToolUse hook 側（編集ごと）に置く**: 却下。新しい検査 id は予算・コマンド・再現手順・発火一覧・代表編集の 5 点セットを同時に要求する一方、`mod` 忘れは編集の瞬間に直せなくても PR CI までに捕まれば実害が無い（未リンクのコードは動かないので、そのまま出荷されることがない）。

## 受容する残余

**足ごとに名指しする。**

1. **`unlinked-file` が publish されない機序は未確定である。** 決定には影響しないが、将来 RA を更新して届くようになれば、`mod` 忘れの検知が二重になる。そのとき `G-module-linkage` を畳むかは改めて測って決める。
2. **`workspace.symbol.search` の `limit = 512` は独立には証明できていない。** 効いていることの証拠は `kind = all_symbols` の側だけで、上限の違いが現れるクエリを投げていない（実測は 114 件で、既定の 128 を下回る）。
3. **`diagnostics: false` の下で navigation が生きるかは未実測である。** 抑制を採らない決定により不要になった。採る判断へ戻すなら、セッション再起動を伴う実測が先に要る。
4. **`G-module-linkage` は `#[cfg]` を評価せず和を取る。** 保証は「どれかの cfg で宣言されている」であって「ビルド構成でコンパイルされる」ではない。**決して有効化されない cfg / feature の下だけで宣言されたファイルは緑になる**——この検査が塞ぐと言った最悪の帰結（テストが黙って走らない）を、その形では取りこぼす。cfg を評価しないのは誤検出を避けるための選択である。
5. **`G-module-linkage` はインライン `mod x { ... }` の中の `mod y;`・`include!`・二重引用符と同一行から外れた属性の綴り（raw string・ディレクトリ指定・`#[cfg_attr]`・同一行の `#[cfg(...)] mod x;`）を追わない**（いずれも現在 0 件）。当該ファイルが未到達として**赤に倒れる**ので、向きは沈黙ではなく過検出である。**これは当初からそうだったのではない**——初版は先頭空白を許す行頭アンカーを持っており、インライン `mod` の中身を拾ったうえで基準ディレクトリを外し、**同名の兄弟ファイルへ誤って一致して孤児を緑にしていた**（レビューが実測）。列を固定し、判定前にコメントと複数行文字列を落とすことで、誤りの向きを赤側へ寄せた。
6. **`[lib] path = ...` で `src/` の外へソースを置く crate は母集団から外れる**（現在 0 件）。`src/bin/` は `src/` の内側だが cargo が自動発見する target なので、母集団から明示的に除外してある。
7. **緑のフィクスチャは検査を縛らない。** `checkModuleLinkage` を `return []` へ無力化すると、落ちるのは赤いフィクスチャだけである（実測）。緑の役割は誤検出の防止であり構造上正しいが、**カナリアの本数を検出力の量として読んではならない**。
