# ADR-rebuild-without-scan-ledger: 走査が要るかを engine の ledger で決め、キャッシュの照合だけには任せない

## 文脈

#1456 で、`include_path_env` / migemo の切り替えでは全走査をやめ、`index.bin` を読み直して建て直すことにした。`index.bin` の照合キー（`compute_config_hash`）は走査対象だけから作るので、この 2 つを切り替えても照合は当たり続ける。そこで「走査するかを何で決めるか」を選ぶ必要があった。

## 決定

走査するかは engine の ledger が決める。ledger は `/s`・初回構築の走査要求を世代で持ち、`index.bin` がいまの索引と同じ走査の結果か（`cache_in_sync`）も持つ。drain は、ledger が走査を要求していなければ `index.bin` を読み直し、読めなければ走査する。

## 検討した代替案と却下理由

- **キャッシュの照合だけで決める（当たれば読む・外れたら走査する）**: 却下。3 つの場合で崩れる。(1) `/s` は照合が当たっても走査しなければならない（ファイルシステムの最新を取り込む唯一の明示操作である）。(2) first-run は `config.toml` の有無だけで決まるので、古い `index.bin` が残っていると照合が当たり、初回構築がそれを採る。(3) 走査対象を A→B と変えて B の保存に失敗した後、B→A と戻すと、古い A の `index.bin` に照合が当たる。どれも結果は「古いが正しく見える」索引で、気づく手段が無い。
- **走査対象の変更を `config_watcher` で走査の要求（`Rescan`）に分類する**: 却下。走査対象が変わればハッシュが変わるので、照合に外れて走査へ落ちる。保存に失敗していれば `cache_in_sync` が偽で走査する。分類を足しても取りこぼしは塞がらず、`IndexInputs` の差分の向きを `config_watcher` に持たせる分だけ複雑になる。レビューでも取りこぼしの手順は組み立てられなかった。
- **`cache_in_sync` を起動時の cache-miss で一律に偽へ倒す**: 却下。cache-miss の分岐も保存を通るので、保存の成否をそのまま運べる。一律に偽へ倒すと、cache-miss で起動した直後の切り替えが 1 回余分に走査する。
- **走査要求を `bool` 1 本で持つ**: 却下。走査中（`begin` の後）に届いた `/s` を、その走査の完了で満たしたことにしてしまう。走査がそれより前のファイルシステムを見ているかもしれない。世代なら、`begin` の時点の要求だけを満たす。

## 帰結

- `start_index_build` は要求の種類（`BuildRequest::Rescan` / `Rebuild`）を取る。
- 「`/s` と初回構築が走査しなくなる」向きの退行は CI が守る（ledger のテスト・`material_without_scan` のテスト・ソーステキスト検査）。「毎回走査に戻る」向きは守らない（遅くなるだけで結果は正しい）。経緯と額は `PERFORMANCE.md`「採用: `include_path_env` / migemo の切り替えでは走査せず、`index.bin` から建て直す（#1456）」にある。
