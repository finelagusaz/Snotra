# ADR-rescan-explicit-only: 自動の背景再スキャンを間引くのではなく撤去し、索引の更新を明示操作だけにした

2026-08-10、#1001（背景再スキャンが起動のたびに `C:\` を全走査する）の対策として **`index.bin` の `built_at` を「前回完走した時刻」として使う間引き**を設計し、書き上げたうえで**採らないことにした**。採ったのは自動経路そのものの撤去である。**この ADR が残すのは、その間引き設計の中身と、撤去へ倒した根拠である。** 作るものは `docs/superpowers/specs/2026-08-10-explicit-scan-only-design.md` が正本。

## 前提（測って分かっていたこと）

- 実運用点の背景再スキャンは 22〜30 秒、1 コアを使い切る。同じ起動のキャッシュロードは 80 ms である（#1001 のコメント・実機トレース）
- **`rescan-log.jsonl` の実起動 2 標本はどちらも `Changed` で、2 本目の差分は 31 万件中 1 件だった。** その 1 件のために 22.7 秒走り、`Changed` ゆえアイコンキャッシュを毎起動捨てていた
- USN は単独の機構になりえない（32 MiB 上限・保持窓 6.1 時間・非昇格では拡大不可・`ENUM_USN_DATA` 不可）
- mtime 差分スキャンは天井 0.51 で棚上げ（`ADR-mtime-differential-scan-ceiling.md`）
- **`/s` はランチャーで 2 打鍵である**（SPEC §15.3: 完全一致した時点で debounce をキャンセルし Enter なしに即実行）

## 却下 1: 間引き（`built_at` を「前回完走した時刻」として使う）

**設計は書き上がっていた。** 中身を残す——同じ案が再提案されたときに、ここまで進んでいたことが分かるように。

- 判定は純関数 `full_scan_interval_elapsed(built_at, now, interval) -> bool`。`checked_sub` で「未来（時計の巻き戻し）」を期限切れ側へ倒し、u64 の wrap も塞ぐ
- 判定点は `try_background_rescan_in` の中・書き込みロック取得の前。`rescan_task: None` で消す形は採らない（記録の「行が無い」の意味が 3 つに増えるため）
- **`cached_version != INDEX_CACHE_VERSION` は間引きをバイパスする**（さもないと v4 残留の教訓が「N 日間だけ」再発する）
- 保存の条件（現在は `changed || stale_format`）を**無条件**へ単純化し、「**走ったら書く。書かなかったなら走っていない**」を不変条件にする。これにより `built_at` が「最後に完走した走査の時刻」と厳密に一致し、**「開始を完走として記録する」バグが構造的に表現不能になる**（`built_at` を進める唯一の手段が、完走した走査結果を引数に要求する `save_cache_sorted_in` だから）
- 間引かれた起動も記録に 2 行書く（`skip_reason="throttled"`）

**却下の理由は、この設計自身が明らかにしたことである。**

間隔を 7 日に決めた時点で「**索引は普段古い**」を受け入れている。新しく入れたアプリは最大 1 週間検索に出てこない。すると自動経路が残して届ける価値は「1 週間に 1 回、勝手に追いつく」だけになる。

**つまり間引き案と明示のみ案は、鮮度では大差がない。** 差はコストと複雑さにしか無く、その軸では明示のみが圧勝する——撤去できるのは日和見的な書き手・世代機構・digest 比較・走っているセッションへの索引差し替え（#1017）・計器一式であり、`/race-check` の対象になる並行の面がまるごと消える。

**そして `/s` が 2 打鍵であることが、この取引を成立させている。** 明示のコストがほぼゼロでなければ、この判断は逆になっていた。

### 間引き案が優っていた点（撤去側が引き受けた代価）

- 自動経路は「気づかないうちに追いつく」。撤去側にはそれが無く、**沈黙して古い**が残る。緩和として設定タブに最終構築日時を出すが、設定を開かないユーザーには届かない
- 実運用点では自動経路は**実際に働いていた**（2 標本とも完走し `Changed` で更新した）。動いているものを消す判断である

## 却下 2: 「セッションが走査より短いマシン」向けに、K 回連続で完走しなければ諦めて間引く

間引き案の残余（完走しないマシンには一度も効かない）を消す案。**却下**: 間引きの状態が「完走した事実」から「試行した回数」へ汚染される。「開始を完走として記録する」の変装であり、誤ると「永遠に間引かれて再スキャンが一度も走らない」が沈黙で起きる。`2026-08-09-rescan-in-situ-instrument-design.md` §8.2 が計器の兼用を却下したのと同じ理由である。

なお **12 秒セッションは `kill` で作った A/B の実験条件であって、野外の観測ではない**（#1001 のコメント）。実証されたのは「セッションが走査より短ければ成果は消える」という機構であり、そういうセッションの実運用での頻度は測られていない。

## 却下 3: 間引きの状態を専用ファイル（`rescan-state.*`）に置く

policy を resource から分ける既存の選好には合う。**却下**: 「権威的ビルドの直後に、間引きを知らないまま無駄な全走査が走る」を避けるには `rebuild_and_save` と cache-miss 枝の**全書き込み点**へ状態更新を足す必要があり、「`index.bin` を書いたら状態も更新せよ」という文書契約を新設することになる。加えて新しい永続形式なので版・欠損・破損の扱いを全部決めることになる。`built_at` 案はそのどちらも要求しない。

## 却下 4: `index.bin` のファイル mtime を触って完走を記録する

17 MiB の書き戻しを避けられる。**却下**: 読まれない事実（mtime）と読まれる事実（`built_at`）の二重化になる。避けようとしているコストは実測 `save_ms` = 458 / 683 ms である。

**この却下は表示にも同じ強さで効く。** 設定タブへ最終構築日時を出すために mtime を読むのも同じ二重化なので、`index.bin` の先頭から `built_at` を読む（`index_built_at_in`）。

## 却下 5: 壁時計スケジュール（Everything の Folder Index と同じ形）

Everything は索引を二本立てで持つ。NTFS index は MFT 直読み + USN 監視で**管理者権限を要し**（公式 FAQ: "Everything requires administrative privileges for low level read access to NTFS volumes for NTFS indexing"）、権限を買えない Folder Index の側は「監視 + 予定された再スキャン（毎日 hh:mm / 週次 / N 時間ごと / Never）+ rescan on full buffer」である。Snotra が居るのは Folder Index の側である（`ENUM_USN_DATA` が非昇格で拒否される・#1001 実測）。

**却下**: Everything は常駐プロセス前提でタイマーを持てる。Snotra もトレイ常駐だが、タイマーとスレッドが増えるうえ「予定時刻に PC が落ちていたらどうするか」を別途決める必要があり、結局「前回完走からの経過」の状態が要る。

**なお公式ドキュメントに Folder Index の既定間隔は書かれていない。** 「Everything の既定が N だから」という論法は使えない——参照できるのは粒度の語彙（日次・週次・時間・分・Never）と構造だけである。

## 却下 6: 間隔を config キーで可変にする

**却下（間引き案を採る場合の話として）**: 永続形式の変更であり、新規記録・既存移行・外部参照 API・設定 UI を同時に揃える必要がある。間引き自体を採らなかったので論点ごと消えた。

## 撤去が引き受けた 2 つの移設

**どちらも「無言で消す」のが最悪の形である。**

1. **形式昇格。** 旧版 `index.bin` を現行版へ書き戻せる唯一の場所が背景再スキャンだった。**移設できることは実測で確かめた**——`save_cache_sorted_in` の返り値が material そのもの（`(IndexTree, CachedMasks)`）であり、v2〜v6 の枝は `cache.entries` を手に持って `IndexTree::build` へ渡しているので、**その 1 行の置換で済み複製は発生しない**。「昇格をロード側に置いてはならない」の射程は v7 の枝（木を直読みするので `entries` が無く、作り直すと 62.5 MiB の複製が復活する）に限られる
2. **アイコンキャッシュの無効化。** #996 が再構築時の掃除を撤去したため、エントリ集合が変わったときの無効化は `RescanOutcome::Changed` が唯一の担い手だった。`start_index_build`（ビルド要求の単一入口）へ移し、判定なしで撃つ。**今日の機構は思われているより弱い**——キーはエントリの `target_path` であり、`.lnk` の張り替えやアプリ更新で**アイコンだけ**変わった場合は集合が同じなので今日も無効化されない。生き残ったキーの刷新は巻き添えである

## この ADR が偽にする先行判断

`ADR-mtime-differential-scan-ceiling.md` の「帰結」は**効く順を「全走査の間引き → 稼働中の watch →（必要なら）USN」**と書き、「受容する残余」は再測定の契機を「間引きが入ったあとに残る N 日に 1 回の代金」に置いていた。**間引きを採らないので、どちらも前提が消える。**

ただし当該 ADR の**結論（mtime 差分スキャンの棚上げ）は変わらない**。理由はむしろ強まる——残る走査は明示的な全再構築だけになり、そこは正しさが最も要求される場所で、mtime 差分が差し出すのはまさに正しさだからである（アーカイブ展開・属性を保持するコピーで mtime が過去へ動く）。

## 受容する残余

- **索引は明示的に再構築するまで古い。** 「沈黙して古い」という失敗の形は残る。緩和は設定タブの最終構築日時のみで、**ユーザーの判断で検索 0 件時の表示や status 行への常時表示は置かない**
- **`/s` の代金は 22〜30 秒のままである。** 走査そのものは速くなっていない（#1002 がそこへ効く）
- **#1001 の受け入れ 3 は文言どおりには満たさない。** 自動の変更検出そのものを撤去するので「取りこぼしの検知器」は対象を失う。頻度側（毎起動でなくなる）は満たす
- **`built_at` が全版で先頭フィールドであることは観測された性質であって契約ではない。** `index_built_at_in` はそこに依存するので、golden bytes テストへ assertion を 1 本足して固定する
