# ADR-results-fixed-height: results 窓は最大表示件数分の固定高とし、下端クランプを撤去する

#835 で `results` 窓の高さを実件数フィットから固定高へ変え、あわせて #675 の下端クランプ機構を撤去した。ここに残すのは、その過程で却下した 5 つの代替案と、理由である。

## 文脈

**この決定は往復である。** #646 PR2 以前の `SPEC.md` §4.5 は「結果ウィンドウの高さは最大表示件数に基づく固定高とする。ヒット数が最大表示件数未満でも高さは維持され…」であり、#646 PR2 決定 7 がそれを実件数フィットへ変えた。#835 は決定 7 を覆して元へ戻す。

戻す理由は #743 で得た。「フォルダ展開中の `←` が階層を上げない」という報告を実機トレースで調べたところ、**症状は不具合ではなく誤読**だった（7 打鍵で毎回親へ上昇）。誤読の実因は窓の伸縮である——通常検索（200 行）→ `←`（子が 1 つの親フォルダ・**1 行**）→ `←`（133 行）と操作すると窓が激しく伸縮し、1 行まで縮んだ状態から戻ると直前の画面と見分けが付かない。

## 決定

- 高さは `最大表示件数 × 行高 + 8px` の固定とし、算出関数から件数の入力を落とす
- 0 件の hide は連言②「結果が空でない」が直接担う（`SPEC.md` §8.6）
- **下端クランプ（#675）は機構ごと撤去する**——収まらない分は画面外へはみ出させる

## 検討した代替案と却下理由

### 1. 下端クランプを維持する（#675 をそのまま残す）

固定高と両立する。件数起因の伸縮だけが消え、画面下端に近いときは窓が作業領域に合わせて縮む——変更としては最小で、撤去に伴う 5 シンボルの削除も要らない。

**却下したのは「窓の大きさが変わらない」という利得が中途半端に終わるからである。** 件数で変わらなくなっても、位置で変わるなら「さっきと同じ画面か」を高さで判断できない状態は残る。#743 の誤読が起きたのは伸縮そのものであって、伸縮の原因が件数か位置かではない。人間裁定（2026-08-04）:「results が画面下部に数行消えてもサイズは変えない、でいいと思う。はみ出て不自由ならユーザーが好きに位置を動かす」。

### 2. 下端に収まらないときはメインウィンドウを上へ押し上げて確保する

**バーの位置はユーザーが決めるものであり、行の出没で動かしてはならない**（`SPEC.md` §4.7）。押し上げた位置は hide 時に `read_placement_relative` が保存するため、次回以降そこへ恒久化する——#755 / #801 で実際に踏んだ失敗と同じ経路である。

### 3. クランプは外すが「1 行分は必ず見える」床だけ残す

#675 の床（作業領域の残りが 1 行未満でも 1 行 + padding は確保する）を、上限クランプなしで生かす案。

**床を効かせる手段が「高さを詰める」か「位置を動かす」しかなく、どちらも却下 1・却下 2 に帰着する。** 「サイズは変えない」と両立する床は存在しない。撤去の帰結として、バーを作業領域の最下端へ置くと `results` が丸ごと画面外へ出て 1 行も見えなくなる——これは #675 が「メインウィンドウを画面下端へ置くと結果が一切出ない」として防いだ状態そのものだが、**位置を動かせば直るものとして受容する**（同裁定）。

### 4. 0 件でも最大表示件数分の空窓を出す

窓の出没そのものが無くなるので、伸縮の解消としては最も徹底している。

**却下した。** ヒットしない打鍵のあいだ黒い箱が残り続ける。加えて `SPEC.md` §8.6 の連言②「結果が空でない」を捨てることになり、4 連言が 3 つへ減る——#752 が②と④を区別できるようにした変更を無に帰す。

### 5. 最大表示件数が 0（`config.toml` の手編集で到達する）のとき 1 行を床にする

**却下した。** 「0 にしたら消える」という素直な読みから外れるうえ、床を置けば機構が 1 つ増える。高さ算出が 0.0 を返せば既存の「高さ 0 ⇒ hide」契約にそのまま乗るので、新しい規則を足さずに済む。

## 帰結

- 撤去は 5 シンボルに連鎖した——`clamp_results_height` / `available_below` / `results_available_height` に加え、呼び出し点を失った `monitor::window_monitor_work_area` と `ResultsWindow::scale_factor`。`position_results_below_main` は残るが、上端 y を返す理由（クランプが消費する）を失ったので戻り値を落とした
- **連言④（窓高さ > 0）と②（結果が空でない）が完全に独立になった。** `ADR-results-presentation-two-stage` の却下 7 は、④を②から独立に動かせる唯一の梃子が `max_results = 0` であると記し「直すなら別 issue で、そのとき『④は②に含意される』という新しい事実をテストに反映する」と送った。#835 はその逆方向で着地している——含意が強まるのではなく消えた。真理値表の到達不能 4 行（「②false ∧ ④true」）が構成可能になり、測る側へ足した
- **`results` 窓の scale factor を読む箇所が無くなった。** `layout::results_top_y` の doc が「`main_scale` と `results_scale` は型では区別できない——検出器は無く、守るのはラッパーの単一性とこの doc だけである」と記していた受容残余は、同型の値が 1 つになったことで構造的に消えた
- 手動スモークの項目 7（「作業領域の下端で高さがクランプされる」）は前提が消えたため書き換えた。トレース不変条件 H4 は**判定ロジックが変更後も真**（0 件なら hide するので `egui_results:show` の `rows` は必ず > 0）であり、契約の名指しだけを「件数 0 ⇒ hide」へ改めた
