# ADR-scan-progress-unit-and-log-fields: 構築中の進捗はフォルダ数で出し、記録に CPU 時間を持たせない

## 文脈

#1041 は、明示スキャン（`/s`）の所要を製品が記録しておらず、進捗も出ないことを扱った。記録の置き場所（`%APPDATA%\Snotra\scan-log.jsonl`）・進捗表示を含めること・残り時間を出さないことは、ユーザーの裁定である。作るものの正本は `SPEC.md` §3.3・§13.4 と `src-tauri/src/scan_log.rs` の `//!` にある。

## 却下 1: 進捗の単位を登録件数にする（分母は現在の索引の件数）

ユーザーが最初に選んだ形である（「128,000 / 約 312,000 件」）。分母はメモリにある索引の件数で読め、新しい記録を要さない。

**却下の理由**: 実運用点の構成では、最後の根 `C:\` が `extensions = []`・`include_folders = false` で、全体を再帰で走査しても 1 件も登録しない（`indexer/scan.rs` の `matches_extension` は空配列で偽を返す）。所要の大半を占める走査のあいだ、件数は止まったままになる。2026-11-15 の実機では、フォルダ 613,341 に対して登録は 23,869 件だった。**件数は仕事量の代理にならない。** 敵対的調査が実 `config.toml` を読んで見つけ、ユーザーの再裁定でフォルダ数へ替えた。

フォルダ数の分母は索引に無いので、記録の直近の完走行から読む。これは計測の記録を表示が読む形であり、撤去前の計測コードの設計（`docs/superpowers/specs/2026-08-09-rescan-in-situ-instrument-design.md` §8.2）が却下した「構築の振る舞いの入力に兼ねさせる」形とは区別する。誤っても欠けても、表示はフォルダ数だけへ落ちる。

## 却下 2: 残り時間（完了見込み）を出す

**却下の理由**: 所要はファイルシステムのキャッシュの状態で大きく揺れ（#977 で ±13 秒級、#1041 の標本で 2.8 倍）、見込みは外れる。2026-11-15 の実機でも、同じ走査対象で 85.2 秒（冷えた状態）と 27〜28 秒（温まった状態）が出た。見込みの元を記録の過去の所要に取ると、外れる見込みを表示することになる。

## 却下 3: 記録に構築スレッドの CPU 時間（`cpu_ms`）を持たせる

計画の当初案である。`GetThreadTimes` で構築スレッドの CPU 時間を測り、壁時計との差を「待たされた時間」（I/O 待ち・競合）として読む。2.8 倍の変動を 1 標本の中で説明できるはずだった。

**却下の理由**: snotra-core は `index_tree.rs`（`par_windows` / `into_par_iter`）と `search.rs` で rayon を使い、保存と構築の一部は別のスレッドで走る。構築スレッドの CPU 時間はその分を取りこぼすので、「壁時計との差 = 待ち」という読みが成り立たない。走査だけに絞って測るには、Win32 の呼び出しを core の `rebuild_and_save` へ入れることになり、得るものに見合わない。

**代わりに `dirs`（仕事量）を持たせた。** 同じ `scan_id` の行どうしで `scan_ms / dirs` を比べれば、仕事が増えたのか遅くなったのかを分けられる（上の実機の標本では、フォルダあたり 139 µs と 45 µs）。
