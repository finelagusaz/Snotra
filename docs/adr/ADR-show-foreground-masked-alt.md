# ADR-show-foreground-masked-alt: 表示時の前面化は tao の set_focus を置き換え、拒まれたら常にマスクした Alt で再試行する

## 文脈

#1470。tao 0.37.2 の `set_focus` は、`SetForegroundWindow` を拒まれるとマスクなしの Alt を注入して再試行する。まだ前面にいる元のアプリがその Alt を単独の Alt として受け、メニューを起動していた。前面化が拒まれるのは、Alt を離してから前面が移るまでの間に、打鍵が元のアプリへ落ちたときである（起動して最初の表示で起きやすい）。

## 決定

1. windows では `show_egui_main` の前面化を tao の `set_focus` から自前の関数へ**置き換える**。
2. 拒まれたら、vkE8 で包んだ Alt を注入して 1 回だけ再試行する。**修飾キーが押されていても注入を省かない。**

## 検討した代替案と却下理由

- **tao の `set_focus` を残し、その前に自前の前面化を置く**: 却下。自前の再試行も拒まれたとき、続く tao の `set_focus` がマスクなしの Alt を注入するので、直したいメニュー起動の経路が残る。
- **修飾キー（Alt・Ctrl・Shift・Win）の押下中は注入を省く**: 却下（実測による）。押下中に注入すると、注入した Alt up が押されている Alt を論理的に離し、Shift との組で入力言語の切替を踏みうる、という懸念から検討した。2026-11-17 に、Alt+Q を離して 5 ms 後に Shift と A を押し、Shift を押したまま前面化を拒ませて比べた（release・各 3 起動）。注入する版は 3/3 で前面化に成功し、元のアプリのメニュー起動も入力言語の切替要求（`WM_INPUTLANGCHANGEREQUEST`）も 0 だった。省く版は前面化を諦めるので、置き換えた後では「最前面に見えるのに前面でない」窓が残り、打鍵が元のアプリへ流れ続ける。そちらの害のほうが大きい。
- **Alt の押下中だけ注入を省く**: 却下。Alt を論理的に離す害（その後の打鍵が Alt なしになる）より、前面にならない窓が残る害のほうが大きい。置き換え前の tao の注入も同じ Alt up を送っていた。

## 帰結

- 置き換え後も、前面化より前に打った文字は元のアプリへ落ちる（Snotra は前面になる前に入力を受け取れない）。初回の表示が遅いことも残る。どちらも #1470 の範囲外である。
- マスクした Alt の down が、Word のキーヒントなど実在のアプリでどう見えるかは測っていない（試験窓のメニューでだけ測った）。
