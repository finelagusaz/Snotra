# ADR-show-path-derives-bar-rect: show がバー矩形を導出して位置決めへ引数で渡す（OS の読み戻しを外す）

## 文脈

#878 は「窓の幾何が、コードではなく OS のウィンドウオブジェクトを経由して部品間を渡っている」形を 4 つの継ぎ目に分解していた。症状（#755 / #801 / #738 / #760）は決着したが、継ぎ目 2 だけが残っていた——`position_on_target_monitor` が `main.outer_size()` を読み戻し、呼び出し側の `show_egui_main` は「位置計算へバー高を伝える」ためだけに `set_size(幅, バー高)` で窓を物理的に畳んでいた。

`ADR-show-path-derives-drawn-height` の**却下 2 がこの案そのもの**である。当時の却下理由は「同じ読み戻しは `position_results_below_main` にもあり、そちらはフレームに閉じない消費者を巻き込む」であった。**旧 ADR は編集しない**（`ADR-adr-frozen-history`）。反転はここに記録する。

## 決定

1. **show はバー矩形の物理サイズを導出し、`position_on_target_monitor` へ引数で渡す**。位置決めのためだけの `set_size` は撤去し、show の `set_size` は実高の 1 回だけになる。
2. **却下 2 の反転が成立するのは、`position_results_below_main` を巻き込まずに済むからである**。#878 の裁定則（窓の矩形から読んでよいのは、ユーザーが動かした位置・非クライアント差分・scale だけ）に照らすと、あちらは**呼び出し元に `Moved` リスナー（フレームの外で走る）を含む**ため読み戻しが正当であり、触る必要が無い。
3. **OS しか知らない量の読みは `read_frame_geom` の 1 か所に閉じる**。クランプ経路（`read_bar_anchor`）と show 経路（`derive_bar_rect_phys`）が同じ合成を通るので、`ADR-main-window-clamp-on-pointer-release`「残っている代価」が記録した「同じ物理バー高が 2 通りに導出されている」状態が解消する。丸め規則への依存は `layout::logical_to_phys` の doc 1 か所に集まる。
4. **退行の検出は `egui_main:bar_rect_mismatch`（in-process）で行う**。show が導いた矩形を残し、reset-on-show の消費フレームが自分で測った矩形と突き合わせる。smoke は可視区間にそれが**現れないこと**を断言する。

## 検討した代替案と却下理由

- **`position_results_below_main` も同時に塞ぐ（共有 atomic で main の直近の書き込み高さを渡す）**: 却下。(1) `outer_position()` はユーザーが動かした位置なのでどのみち読む——Win32 呼び出しの回数は減らない。(2) 物理 outer 高を atomic へ入れるには書き込み点で非クライアント分を読む必要があり、**読み戻しが移動するだけ**である。(3) 書き手が 2 人（show と毎フレーム）の memo をフレーム跨ぎで持つ形は #878 の継ぎ目 1 そのもので、`view.rs` と違い results 側には「次のフレームが直す」補正の相当物が無い。
- **`read_bar_anchor` を show からも呼ぶ**: 却下。あちらは `outer_position()` を読むが、show は位置をこれから**書く**側なので要らない読みが 1 つ増える。基準モニターの決め方も違う（show はカーソル/プライマリ、クランプはバー矩形の中心）。
- **退行の検出器を「show 直後にクランプが動いたか」にする**: 却下。**守りたい退行の足を捕まえない配置がある**——`WorkArea::clamp` は矩形が境界を越えたときしか座標を変えないため、窓が作業領域の内側にいる限り、show 側の導出が壊れていても沈黙する。この決定が持ち込む退行は**導出の誤り**（非クライアント分の落とし・scale の取り違え・丸め規則の食い違い）であり、それは矩形そのものを突き合わせないと見えない（`.claude/rules/safety-nets.md`「検出器のカバー範囲は、欠落のパターンごとに検算する」）。
- **外から窓の矩形を測る検査（DWM）に任せる**: 却下。導出が誤っても窓の実サイズは 2 手目の `set_size` が決めるので幅・高さは正しいままであり、位置のずれは可視中のクランプが次のフレームで戻す。**回復機構が外部の検出器を無力化する**形であり、#904 が `egui_main:height_mismatch` で踏んだのと同じである。
- **1 手目の `set_size` を残したまま、値も引数で渡す（二重に持つ）**: 却下。畳む手順が残る限り「畳む先の値」と「渡す値」が食い違う余地が残り、継ぎ目 2 は形として生き続ける。

## 帰結

- `ADR-results-presentation-two-stage` **却下 6**（`bar_height` collapse を `main_window_height` へ統合する）と `ADR-window-coordinator-split-rule` **決定 4** の括弧書きは、**collapse という手段そのものが消えた**ため描写として失効する。却下 6 の理由「位置クランプが展開時の高さで効くのを防ぐために意図的に畳んでいる」は、寸法を引数で渡せる以上もう成り立たない。**決定 4 の本体（main のサイズ適用が 2 か所に分かれたままであること）は真のまま**である。
- `ADR-main-window-clamp-on-pointer-release`「残っている代価」の申し送り（「#760 に着手するときは、継ぎ目 2 を先に動かすほうが安いかを必ず量ること」）に答えた。
- 挙動は変えない。`SPEC.md`「4.7 結果表示制御（2 窓構成）」「8.2 ウィンドウ位置」の「位置はバー高で決まる／伸びた高さでは再クランプしない」は不変である。**これは A/B で実測した**（下記）。

## 挙動不変の実測（A/B・2026-08-24）

作業領域 1920×1020 物理・DPI 125% の機体。`follow_cursor_monitor = false`（ターゲットをプライマリへ固定）・`window_width = 600`（既定）。観測点は 3 つで、いずれも `GetWindowRect` の物理座標である。

| 観測点 | 何を読むか |
|---|---|
| M1 | 初回 show（保存位置なし）= `WorkArea::center(win_w, win_h)` の出力 |
| M2 | 窓を作業領域の下端外へ押し出した後 = 可視中クランプの出力（**フレーム側 win_h の直読み**） |
| M3 | hide（保存）→ show = 保存位置 + **show 側**クランプの出力（**変更したのはここの導出である**） |

**A（`6638f7f9`・変更前）と B（`0a05b8ea`・変更後）は各 2 回とも完全に一致した**——M1 `(576,478)` / M2 `(576,956)` / M3 `(576,956)`、矩形はいずれも 768×64。`956 = 1020 − 64` で下端境界に貼り付いており、64 = `round(43 × 1.25)` + 非クライアント 10 である。

**一致したことを証拠にする前に、計器が差を出せることを対照で確かめた。**

| 変異 | M1 | M3 |
|---|---|---|
| 非クライアント分を落とす（#738 が名指す欠陥形） | **483**（+5 = `inset/2`） | 956（変わらず——show 側の矩形が縮むと `max_y` が広がり保存位置が束縛しない） |
| 非クライアント分を二重に足す | **473**（−5） | **946**（= 1020 − 74） |

すなわち M1 は両方向に、M3 は「show 側の矩形が伸びる」方向に感度を持つ。**A == B はこの感度の下での一致である。**
- **検出器の 2 軸は強さが違う**（`check_show_bar_rect` の doc が正本）。**幅軸だけが導出を実測と突き合わせており**、高さ軸は同じ `FrameGeom::bar_height_phys` を通る 2 つの呼び出し点の A/B である——共有した導出そのものの誤りは両側が同じだけずれて沈黙する。**死角を数え上げない**（config 変更・DPI 変更が窓に挟まる場合はその一例にすぎない）。
- **`derive_bar_rect_phys` の式は「`set_size` の後に窓が占める物理矩形」への依存を持つ**。tao の `set_inner_size` がその形を与えることは実装を読んで確かめたが、**上流の版で変わりうる依存であり、依存していること自体を検出器の幅軸が毎回の show で検算している**（これが幅軸を残す理由である）。
- **scale はこの窓が今いるモニターのものであって、show がこれから置く先のモニターのものではない**（旧経路も同じで退行ではない）。両者の DPI が違う配置では、検出器のどちらの軸も現実を測れない。
