# ADR-sorted-prefix-over-reflagging: 整列を真偽で測り直さず、範囲として保つことにした

2026-08-13、`#1067`（全件マッチのパスクエリに残るマッチ後コスト）の手段として
**PATH マージ後の整列の扱い**を決めた。採ったのは「整列している**範囲**を保つ」形である。
この ADR はそこで**却下した 4 案**と、その理由の記録である。

**実測値の正本は `PERFORMANCE.md`「採用: 整列している範囲を捨てない」および
「実運用点のパスクエリのフレームコストと、マッチ後の分解」** であり、ここには数字を写さない
（判断と、なぜ再訪しないかだけを残す）。

## 前提（測って分かっていたこと）

- 支配項は tie-break の `PathStore::cmp_paths` だった。マッチ後コストのうち 3 分の 2 を占める
  （ablation の 5 変異と過剰決定の検算で確定）
- その額は `IndexTree::extend_with_roots` が整列の旗を落とすことに由来する。要因分解と
  `M_cmp` の 2 経路が別々の手順で同じ額を指した
- **issue が第 1 に挙げた履歴照合は支配項ではなかった**——drift の帯の内側で 0 と区別できない

## 却下 1: マージ後に整列を測り直す（**測っても必ず偽になる**）

最初に検討した形。旗を無条件に落とすのをやめ、マージ後に改めて整列を測って真なら残す。

**実運用点で測ったところ、既存の最大パスは `C:\workspace\...`、追加の最小パスは
`C:\Users\...` だった。** PATH エントリはバイト順で必ず途中に入るので、測り直しても偽に
しかならない。**1 µs も改善しない。**

伸ばせる形の入力（追加ぶんが昇順で、かつ既存の最大より後ろ）は原理的には在りうるが、
そのために毎回「既存の最大」を組み立てる費用を全ユーザーへ課す価値は無い。

**再訪する条件**: PATH スキャンの結果が索引の末尾より後ろに来る構成が実在すると分かったとき。
現時点の実運用点は 1 件もそうなっていない。

## 却下 2: `result_limit` を下げる（**最適化ではなく機能変更である**）

設定の 36 構成を掃いた結果、`c:\` のコストを最も大きく動かす軸は `result_limit` だった
（200 → 8 の効きは整列の旗の反転より大きい）。しかし**これを下げることは最適化ではない。**

- 200 は絞り込みの閾値ではなく **top-k の器の大きさ**である。全件走査は器の大きさに依らず走る
- **200 行はすべて UI へ渡り、`ScrollArea` が全行ぶんを確保するのでスクロールで到達できる**。
  `visible_rows`（既定 8）が決めるのは同時に見える行数であって結果の件数ではない

ゆえに器を小さくすると 9 件目以降が消える。**性能の選択肢ではない。**

**`result_limit` が兼ねる 3 つの役割のうち、表示と無関係なのは履歴の剪定容量だけである。**
分けるならそこだが、剪定は保存時にしか走らないので**フレームコストは 1 µs も変わらない**。

## 却下 3: 履歴照合を top-k の通過後へ遅延する（**`c:\` では枝刈りが成立しない**）

issue が「着手前に潰すこと」として挙げた案。「boost が 0 になりうる件を先に弾く」形が
成立するかを、重みを読んで判定した。

**成立しない。** `c:\` は全件が同じ base score で並ぶため、`base + max_boost > worst` が
ほぼ常に真になり枝刈りが効かない。**`c:\` こそが本 issue の対象**なので、この案は
最初から候補から外れる。

## 却下 4: key だけで決まる履歴ブーストを疎な表に作り置く（**支配項ではなかった**）

却下 3 の代わりに挙げた案。履歴が変わるのは起動・実行時だけなので、検索のたびに全件ぶんの
ハッシュを払う理由が無い、という筋である。

**ablation が「履歴照合は drift の帯の内側」と測ったので採らない。** 削れる額が測定誤差と
区別できない対象に、索引の常駐と保守を足す取引にならない。

**再訪する条件**: 履歴の規模が桁で増えたとき（測定時の実 `history.bin` は global 17 件）。
そのときは `M_hist` を測り直すところから始める。

## 採った形が持つ性質

- **`index.bin` の形式は変わらない**（版バンプ無し）。ディスクは「全体が整列か」の `bool` の
  ままで、保存時に範囲から導き、読み戻しで復元する
- **旗は「契約ではなく実測」という既存の設計をそのまま引き継ぐ**（`sorted_prefix_len` の doc）。
  測れなかった経路は 0 を入れれば遅い経路を通るだけで、結果は変わらない
- **`extend_with_roots` は範囲に触れない。** 末尾へ足すだけなので範囲は構造的に壊れない
  ——「落とし忘れ」ではなく「落とす理由が無い」形である

## 残余

**max は依然 1 フレームを超える**（p50 は内側へ入った）。残るのは incremental cache 用の
全一致 index 収集と `ScoredEntry` 構築であり、そこへ踏み込むかは本 issue の外である。
