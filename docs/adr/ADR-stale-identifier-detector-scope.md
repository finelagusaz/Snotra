# ADR-stale-identifier-detector-scope: 腐り検出器 G-stale-identifiers の射程を決めたとき、#736 を閉じる案と除外リスト案を却下した

`.claude/**` の散文に残る「現行語彙に無い識別子」を検出する G-stale-identifiers を置いた（#736 の同クラスの再発防止）。**この ADR が残すのは、そのとき却下した案である**——採った述語と理由は `scripts/governance-check.mjs` の G-stale-identifiers 節が持つ。

## 文脈

#736 は「述語だけが書かれた間接参照であり、概念での再導出でしか拾えなかった」型の腐りを 10 件挙げ、すべて grep で 0 件と実測していた。G-references が見るのはパスの実在までで、**識別子の実在は誰も見ていない**。

着手前ゲートで述語を現行コーパスへ当てた実測（`AGENTS.md`「検証の作法」——判定の中核は自分で測る）:

| 述語 | finding | 真の腐り | 偽陽性 |
|---|---|---|---|
| バッククォート内の全識別子（camelCase / snake_case / kebab） | 53 | 13 | 40 |
| 同・camelCase（こぶ 1 つ以上）に限定 | 13 | 12 | 1 |
| 同 + `SPEC.md` を語彙へ + 外部コマンド行を除外 | **6** | **6** | **0** |

## 検討した代替案と却下理由

### 却下 1: G-stale-identifiers を「#736 を閉じる機構」として作る

計画のゲート条件 1 は「#736 の A/B 表の全件が finding に現れる」だった。**満たせなかった。**

#736 の 10 件の書かれ方を実際に読むと、バッククォートを持つのは 2 件だけである。残りは **frontmatter の `argument-hint` 文字列**（`dry-check` / `symmetric-check`）・**素の表テキスト**（`window-shown`）・**日本語散文**（「リアクティブ制約」「TypeScript 型チェック」「IPC ハンドラ」）で、識別子として書かれていない。

述語を広げて届かせる案は却下した——上表のとおり、バッククォートを外した瞬間に偽陽性が 40 件になる。**#736 は手作業で閉じ、G-stale-identifiers が引き受けるのは再発防止だけである。** この非対称は `scripts/governance-check.mjs` の G-stale-identifiers 節に自称スコープとして明記した（`AGENTS.md`「全称表現は前提条件とセットで書く」）。

### 却下 2: 偽陽性を除外リストで消す

camelCase 限定でも `closingIssuesReferences`（GitHub API のフィールド名）が 1 件残った。1 件なら定数へ書くのが速いが、`scripts/governance-check.mjs` 冒頭の契約は「**免除注記の機構は設けない**」と定める。除外リストは放置すると育ち、育った先で「なぜここに在るのか」を誰も言えなくなる。

**行の形で外した**——`gh` / `npm` / `cargo` / `git` 等のコマンドが同じ行に在るなら、その行の識別子はコマンドの引数である。実測で偽陽性 1 件が構造的に消え、真の腐り 6 件は残った（両方向で確認）。

### 却下 3: 単語 1 つの識別子も対象にする

`Glob` `Grep` `Agent` `Plan` `Explore` `Bash` は harness のツール名、`Critical` `Warning` `Info` `expand` `collapse` `mount` `plain` は散文の語彙である。いずれもリポジトリのソースに無いのは当然で、腐りではない。**こぶを 1 つ以上要求しないと、この 2 群が母集団の大半を占める**（53 件中 40 件弱）。単語 1 つの腐りは受容する残余とする。

### 却下 4: 現行語彙をソースだけから作る（`SPEC.md` を入れない）

ソースだけを語彙にすると、`folderState`（SPEC に 8 件）・`toolSelectionState`（4 件）・`resetForShow`（2 件）が finding になる。**しかしこれらは `SPEC.md` 自身が使っている語である**——`state-check/SKILL.md` はその忠実な写しであって、腐っているのは SSOT の側である。

写しだけを直すと、`AGENTS.md`「検証の作法」の「照合は SSOT に対して行う。派生コピー同士の一致を完全性の証拠にしない——SSOT を変えるときは写しを grep で数え上げてから直す」の**向きが逆転する**。SPEC 側の stale は `#735`（SPEC の WebView2 期 stale 記述を as-built へ畳む）の射程であり、そこで SSOT を直せば写しは G-stale-identifiers が捕まえる。

**ゆえに現行語彙の正本は「ソースの非コメント本文」と「`SPEC.md`」の 2 つとした。** 副作用として、G-stale-identifiers が #736 から引き取る件数は 2 → 0 になった（却下 1 の判断を強める側である）。

### 却下 5: ソースのコメントも語彙に入れる

`resetForShow` はソースに 11 件現れるが、**全件がコメント**である（「〜相当」「parity」という由来注記）。コメントを語彙に入れると由来注記が現行語彙に化け、腐りが原理的に検出できなくなる。G-config-reachability が同じ理由で `stripRustComments` を置いており、それを再利用した。

## 帰結

- **`resetForShow` / `folderState` / `toolSelectionState` は `state-check/SKILL.md` に残る。** SPEC 語彙ゆえ G-stale-identifiers は鳴らない。直すのは `#735` である
- **`docs/build-commands.md` を SSOT と宣言しながら写しを持っていた `deps-update`** は、写しを消して参照へ倒した。#736 が「単なる腐りより重い」と評した箇所である
- **`symmetric-check` の `*clicked*` / `*double-clicked*` 行は削除した。** `SPEC.md` §4.8 が「ダブルクリックは独立した挙動を持たない（as-built）」と決めており、この対称ペアは存在してはならない

## 受容する残余

- **単語 1 つの識別子**（却下 3）。`unlisten` のような 1 語の腐りは G-stale-identifiers が鳴らない（今回は手で直した）
- **frontmatter・素の表テキスト・日本語散文**（却下 1）。識別子として書かれていない腐りは対象外
- **`SPEC.md` 自身の腐り**（却下 4）。`#735` が担う

## その後（#735 完了後・射程を広げた）

**「現行語彙をソースだけから作る（`SPEC.md` を入れない）」として却下した案は失効した。** 却下の判断そのものは書き換えない——上の原文は当時の文脈として残す。ここに追記するのは、前提のどこが動いたかである。

**あれは暫定措置だった。** 却下理由は「SPEC 側の stale は `#735` の射程であり、そこで SSOT を直せば写しは G-stale-identifiers が捕まえる」であって、SPEC を語彙に置くこと自体を正当化してはいない。`#735` が完了した時点で、その前提は満期を迎えていた。

### 測定（射程の各軸を、リポジトリを変えずに proxy snapshot で測った）

軸は 3 つ。**A** = 語彙源から `SPEC.md` を外す / **B** = 検査対象に `SPEC.md` を加える / **C** = 語彙源から `*.test.mjs` を外す。

| 述語 | finding | 真の腐り | 偽陽性 |
|---|---|---|---|
| ベースライン | 0 | 0 | 0 |
| A 単独 | 0 | 0 | 0 |
| B 単独 | 0 | 0 | 0 |
| C 単独 | 1 | 0 | 1 |
| **A+B** | **5** | **5** | 0 |
| **A+B+C** | 6 | 5 | 1 |

**A 単独と B 単独が 0 なのは、件数が小さいのではなく理由が別々にある。**

- **A 単独が 0 なのは `#735` が写しごと片付けた後だからである。** 却下 4 が挙げた `folderState` / `toolSelectionState` / `resetForShow` は、`.claude/**` にも `SPEC.md` にもバッククォート付き camelCase としては残っていない。**ただし A を単独で採ってはならない**——却下 4 が守っていた向き（写しだけが鳴り SSOT は黙る）が、次に SPEC 語彙の写しが生まれた瞬間に復活する
- **B 単独が 0 なのは構造的である。** 語彙が `SPEC.md` 全文を含む限り、`SPEC.md` 内のあらゆる候補は自分自身に一致する——**SPEC が検査対象であると同時に自分の語彙源でもあり、自分で自分を免罪していた**

**A+B は却下 4 の懸念そのものを消す。** SPEC を語彙から外すと同時に検査対象へ入れれば、SSOT と写しは同時に鳴る。「どちらを先に直すか」という向きの問いが構造的に起こりえない。実効は測定のとおり——`#735` が名指しの一覧で狩ったため取りこぼした真の腐り 5 件（`alwaysOnTop` 2 箇所・`downloadAndInstall` 3 箇所）を機構が拾った。**棚卸しは `alwaysOnTop` を名指ししたのに、手作業の一巡は落とし、機構は拾った。**

### 「偽陽性を除外リストで消す」の却下で書いた効果は、1 行については成立していなかった

同案を却下したとき「行の形で偽陽性 1 件が構造的に消えた」と書いた。**`.claude/skills/merge-pr/SKILL.md` の手順 4 の行については、これは成立していなかった。** 同ファイルの手順 1・手順 4 の子項目は `gh pr view` を同じ行に持つので外れているが、手順 4 の冒頭行は語だけを書いていて外れない。その行が黙っていたのは、`scripts/governance-check.test.mjs` のフィクスチャ文字列が `closingIssuesReferences` を語彙へ寄付していたから——**偶然の免罪が上塗りしていた**（実測）。

**採った手当ては当時と同じである**——除外リストを置かず、その行に `gh pr view <PR> --json closingIssuesReferences` を書いた。行が語っているのはまさにそのコマンドの出力なので、これは回避ではなく記述の正確化である。

### 検出器のテストフィクスチャが、検出器の偽陰性を作っていた

軸 C を独立の論点として扱わなかったのは、フォールトインジェクションが決定的だったからである。`createObjectURL`——**この検査が「守りたい対象」として `scripts/governance-check.test.mjs` に名指しで書いた語**——は、同じファイルのフィクスチャに書かれているという理由だけで、実リポジトリでは永久に検出されなかった。`newValue` / `folderState` / `resetForShow()` も同じ経路で見逃されていた（いずれも A+B+C で検出されることを実測）。

`.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」を当てると、この検査は**自分の名指した対象に対して不成立**だった。ゆえに語彙の母集団は **production のソース**で揃える。

### 新しい射程

- **現行語彙の正本は「production のソースの非コメント本文」ただ 1 つ**（コメント除去 + テストコード除外）
- **検査対象は `.claude/**` の散文 + `SPEC.md`**
- 空母集団の fail-closed は `.claude/**` 側だけで判ずる（`SPEC.md` が長さを埋めると、`.claude/**` が 1 枚残らず消えても検知が沈黙する）

### 残る残余

- **述語は camelCase しか見ない。** snake_case・PascalCase・ドット区切り・式で書かれた腐りは今も対象外である。**「SPEC の腐りが機構で捕まるようになった」とは言えない**——言えるのは**「camelCase で書かれた再発は捕まる」**までである
- **Rust のテストコードは今も語彙を寄付しうる。** 除外はファイル名の `.test.<ext>` という形だけを見るので、Rust 側の 3 つの形——`#[cfg(test)] mod` の中身・`<crate>/tests/*.rs` の統合テスト・`src/**/tests/*.rs` へ分けたテストファイル——はどれも外れる。`stripRustComments` の隣にある `productionOnly` を通しても落ちるのは 1 つ目だけで、残る 2 つには述語が要る。全セルで測って finding を 1 件も動かさなかったため採らなかった——**穴が無いのではなく、まだ何も落ちていない**
- 「単語 1 つの識別子」「frontmatter・素の表テキスト・日本語散文」は上の受容する残余のまま
- **上の帰結が「`resetForShow` / `folderState` / `toolSelectionState` は state-check のスキル文書に残る」と書いた状態は、既に解消している**（当該スキルは `consume_reset_pending` という as-built の形に直っている）。歴史としてそのまま残す
