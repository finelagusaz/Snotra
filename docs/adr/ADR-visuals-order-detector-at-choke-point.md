# ADR-visuals-order-detector-at-choke-point: テーマ 3 値の適用を入力欄の関数へ吸収し、順序に検知手段を与える

## 文脈

`ADR-visuals-application-target` は適用先を `ctx.set_visuals` から `ui.visuals_mut()` へ移し、
**禁止**（`Context` 経由で global style を書かない）と**順序**（適用は visuals を読む最初の操作
より前）の 2 つの不変条件を残した。前者は #900 が `src-tauri/clippy.toml` の `disallowed-methods`
で機構化した。後者は同 ADR が**「新設した順序不変条件に検知器を置く」を見送っていた**（受容残余）
——「検知器を作るには『visuals を読む操作』を**静的に定義**する必要があり、egui の内部実装に
依存した脆い判定になる」が理由である。

**本 ADR はその却下を覆す。** 静的定義は要らなかった——実際に 1 pass 走らせて子 `Ui` の値を
読めばよい。#900 のマルチパースペクティブレビューで codex が提示し、構造の実在を確認した。

## 決定

**3 値の適用を `SearchWindowView::update` から `search_input_ui`（3 値の唯一の消費者である
`TextEdit` を描く関数）の入口へ移し、`hint` クロージャが受け取る子 `Ui` を実コードのまま
観測する検査を置く。**

`docs/development-principles.md`「構造的設計原則と強制の階梯」の **(a) 責務を検査可能な層へ移す**
の適用である（先例は #654）。機序と、どの検査が何を縛るかは `search_input_ui` の doc が正本。

## 検討した代替案と却下理由

- **「visuals を読む操作」を静的に定義する検知器**（`ADR-visuals-application-target` が
  「検知器を置く」の**見送り理由**として想定していた形）: 却下。egui の内部実装に依存する。
  **静的定義を要さない**ことが本決定の要点で、
  同じ結論を別の道具で得た以上、脆い方を選ぶ理由が無い。
- **`ctx.set_visuals` が当該 pass に届かないことを固定する対のテスト**: 却下（先行決定を維持）。
  egui の**現在の制限**を固定する主張であり、上流が直した日に緑のビルドが赤くなる。本決定が
  測るのは**製品関数の同一 pass 出力**なので、上流が直しても壊れない。
- **適用位置を規範（コメントと `CLAUDE.md`）で守り続ける**: 却下。#751 から本決定までの間、
  その規範を検算する機構は 1 つも存在しなかった。**規範は破れても沈黙する。**
- **`InputVisuals` を既存の `SearchInputParams` へ吸収する**: 却下。あちらは `TextEdit` へ
  **渡す**値、こちらは `ui` へ**適用する**値であり、順序の不変条件を負うのは後者だけである。
  分けたことで**適用漏れが `dead_code` でも捕まる**という副次的な検知が得られた（実測。
  吸収していても同じ効果は得られるが、責務の違いが型に現れない）。

## 帰結

- 3 値が届く範囲は「`search_input_ui` の入口以降」に縮む。**main 窓へ新しい egui コンテナを
  足すなら、その `Ui` へ自分で visuals を渡すこと**——`ADR-visuals-application-target` の帰結 2 が、
  より広い範囲へ当てはまるようになった。
- 適用漏れ・移設の巻き戻し・適用を子 `Ui` の生成より後ろへ動かす退行は、**テストで赤くなる**
  （5 変異で実測）。うち適用漏れと巻き戻しは `dead_code` でも二重に赤くなる。

## 受容する残余

- **`update()` 側の未適用区間が広がった。** 「テーマ未適用のまま `update()` が走る区間」は
  `ui.interact` 1 か所から `search_input_ui` の呼び出しまでの全域になった。**新設した検査は
  この区間を見ない**——`search_input_ui` を単独で駆動するためである。受けるのは呼び出し直前の
  in-code 警告と `src-tauri/CLAUDE.md` の規範であり、**自動検査は無い**（残る砦は
  `docs/build-commands.md`「`[visual]` の色を変える変更は、**非既定色で**目視する」だけである）。
- **観測点を `hint` クロージャに置いた代価。** 本来必要な「子 `Ui` の生成より前」より 1 段強い
  「`hint` の呼び出しより前」まで縛る。適用を関数の入口に置く限り偽陽性は出ない。
- **`InputVisuals` の構築点（`VisualSnapshot` から 3 値を手写しする箇所）の取り違えは検知ゼロである。**
  3 フィールドとも `Color32` ゆえ型は通り、新設した検査は `search_input_ui` の**中**しか見ない。
  `InputVisuals` を `visual.rs` 側へ寄せて手写しの点を 1 つ減らす案は、費用対効果が低いので
  **今回は見送った**（次に `VisualSnapshot` を触るときの候補）。現状の砦は非既定色の目視だけである。
- **移設の巻き戻しは、観測結果としては 3 値の同時適用漏れと区別が付かない。** 当てる編集の姿が
  違うので別の変異として測ったが、検査の判別力は 5 種類ではなく 4 種類である。
