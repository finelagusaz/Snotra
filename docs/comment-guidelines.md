# コメントガイドライン

コードコメント（rustdoc / TSDoc / インラインコメント）の書き方・粒度・配置を定める。エージェントにも人間にも適用する。

- 配送: `.rs` を編集すると、`.claude/rules/comments.md`（節を名指すだけの router）から届く
- 規約から外した否定の知識と、却下した案: `docs/adr/ADR-comment-guidelines-one-question.md`
- 適用範囲: 新しく書くコメントと、変更で触った段落。既存コメントの一括書き直しは求めない。ただし「日本語の折返し」の 2 形と、「言語（日英）」の訳語の判定は既存のコメントにも当てる

## 第一原則: コメントは理由を書く

**コードから読み取れないことだけを書く。** 書くかどうかと、どこに書くかは、次の問いで決める。

> **この行を単純にされたら、何が壊れるか。**

| 答え | 置き場 |
|---|---|
| テストが落ちる | **テスト名**に、壊れる性質を書く。テスト名で伝わらない検証意図だけをコメントに書く（「テストコードのコメント」） |
| テストは落ちないが、壊れる | **その行の直上**に、いま成り立つべき前提・不変条件として短く書く |
| 何も壊れない | 書かない |

この形に至った経緯は、**コミットメッセージと PR 本文**に書く。コメントには `#NNN` だけを残す。

**理由と精密事実は、置き方が違う。**

- **理由**は、それが守る行の隣に書く。「理由は `X` の doc」と遠くを指すだけで済ませない。呼び出し側の読者は、定義へジャンプすれば理由を読める
- **精密事実**（1 か所にしか置けない値・契約・式）は、正本を 1 つ決め、`` [`X`] `` か、ファイル名と見出し名で指す（「名指しと正本の指名」）。写しを 2 つ置くと、いずれ片方だけが直される

書かないもの:

- **コードの逐語訳**（「i をインクリメントする」型）
- **コードが決めている構造の事実**: 経路の**数**、分岐の**列挙**、**呼び出し元**、**到達可能性**。「なぜ」に見えるが、コードの写しである。分岐を 1 本足すたびに、散文だけが古くなる
  - 禁じるのは、今の姿の数え上げである。過去の変更（分岐を足した・消した）はこの項の対象ではない。ただし過去の変更は経緯なので、経緯そのものは書かず、`#NNN` で辿れる形にする（「歴史メモの様式」）
  - 名指しは書いてよい。古くなるのは数であって、名前ではない。名指しは原則として `` [`Type::method`] `` の形で書く。素の散文名は、誰も確かめないからである。素のバッククォートで書く面と、面ごとの保証は「名指しと正本の指名」にある
- **他のコードの現在の状態を主張する根拠**: 振る舞いの同一性（「旧実装と挙動は同じ」）と、頻度（「通常は空」）
  - 根拠は、古くならない形で書く。過去の行為（「〜した」）・日付つきの実測・正本への参照のどれかにする
  - 「同じ〜を通る」と書いてよいのは、実際に同じ 1 か所を通るときだけである。書き写したなら、書き写したと書く
  - 頻度は、数を添えられないなら根拠に使わない
- **変更履歴・レビュー向けの説明・未実装の計画**（git log と PR が持つ）

**書いてよい例外**（「書かないもの」に見えて、書く側に属するもの）:

- **一意性の宣言**: 「保存先を導く経路はここ 1 つだけである」は、今の姿の数え上げではない。崩れたら事故になる不変条件である
- **誤読の予防として名指しする列挙**: その列挙が無いと誤読される証拠があるなら残し、**その理由を同じ doc に書く**（実例: `snotra-core/src/search.rs` の `SearchEngine::recent_history`）。理由が隣に無い列挙は、正本の代わりの写しである

**コメントは、実装と同じ PR で直す。** 「なぜ」が変わる変更なら、同じコミットで直す。理由と不変条件だけを書いていれば、振る舞いを保つリファクタでコメントを直す必要は生じない。

## 短く保つ

**長いコメントは、たいてい複数の面の内容を 1 か所に積んでいる。** 長さを削るのではなく、面を分ける。行数・文字数の上限は置かない。

| 面 | 書くもの | 降ろす先 |
|---|---|---|
| `//!`（module doc） | モジュールの責務・依存方向・モジュール全体の不変条件 | 実装の詳細 → `///` |
| `///`（item doc） | 契約・保証・パニック条件・局所的な理由・寄せ先の無い測定値の正本 | 経緯 → `#NNN`、却下案の比較 → ADR |
| `//`（inline） | その行・ブロックだけに効く理由 | 保証の要る参照 → doc コメント（「名指しと正本の指名」） |
| ADR（`docs/adr/`） | 却下した代替案と、却下の理由 | 採用案の再説明 → コードと `SPEC.md` |
| `docs/` の散文 | 横断パターン・複数モジュールにまたがる設計 | 精密事実 → doc コメントを正本に指名する（`docs/development-principles.md`「文書に書くこと、コードに任せること」） |

- 同じ精密事実が別の面に既にあるなら、写さずに指す
- `//!` を短くするために責務を削らない。削った責務の受け皿が `CLAUDE.md` 側に無い

### 測定値の置き場

決定は `docs/adr/ADR-measurement-canon-in-code-doc.md` と `PERFORMANCE.md`「この文書へ記録するときの規約」にある。要点は次の 3 つである。

- **`PERFORMANCE.md` に節がある値**: コメントはその節をファイル名と見出し名で指し、値を写さない
- **寄せ先の無い値**: コードの doc を正本にしてよい
- **判断を支えていない経緯の値**（「反復 N で〜した」型の変化量）: `#NNN` へ委ねて外す

「実測値はコメントに書かない」と読み替えない。規模感そのものが「なぜそうしたか」の説得力になる場合がある。

## 名指しと正本の指名

**`` [`X`] `` は、「ここには書かない。正本はあちらである」を、読者と機械の双方へ宣言する記法である。** 精密事実を写さずに済ませるための、第一の道具である。その名前を誰が確かめるかは、書いた面で決まる。

| 面 | rustdoc が描く | 着地を検査する | rust-analyzer が定義へ飛ぶ |
|---|---|---|---|
| production の `///` `//!` | ○ | **○** | ○ |
| `#[cfg(test)]` の中の `///` | × | **×** | ○ |
| `//` のインラインコメント | × | **×** | × |

- 着地は `cargo doc` が検査する（`broken_intra_doc_links` は workspace で deny。発火するのは CI だけ）。**保証が要る参照は、production の doc コメント側へ置く。** ほかの面でも記法は無駄にならない。失うのは保証だけで、指名は残る
- `//` の行では、rust-analyzer も名前を解決しない。角括弧が残すのは、読み手への宣言だけである。名前が同じブロックの実行コードに現れるなら、読み手はそこから辿れる
- production の doc から `#[cfg(test)]` の項目へリンクすると、rustdoc がその項目を見ないので、検査が赤にする。その場合は素のバッククォートで書く（実例: `snotra-core/src/history.rs` の `HistoryStore::load` の doc）
- 定義から参照を列挙する向きには、どの面の名指しも現れない。findReferences が返すのはコード側だけで、rename も doc コメントを書き換えない。改名したときに doc コメントの名指しを赤にするのは、表で「検査する」が ○ の面だけである
- 開きが ASCII の `[` で、閉じが全角のとき、rustdoc はリンクと認識せず、リテラルとして出す。壊れたリンクではないので、`cargo doc` は何も言わない。この形は、`governance:check` の `G-fullwidth-doc-link-bracket` が `///` / `//!` で赤にする（適用範囲は同検査のヘッダが正本）

## rustdoc の様式

- **`///` には契約を書く。** 要約 1 行（何であるか）を置き、必要なら空行を挟んで詳細（保証・パニック条件・呼び出し前提・ロック規律）を書く。すべての pub アイテムへ機械的に付けることは求めない
- **既存アイテムの隣へ新しいアイテムを挿入したら、`///` の帰属が動いていないかを目で確かめる。** `///` は直後のアイテムに付く。既存の doc ブロックの末尾へ書き足す形で挿入すると、その doc ごと新しいアイテムのものになる。この誤りは、どの機械検査も見ない。挿入位置を既存アイテムの**後ろ**に取れば、構造的に起きない
- **`//!` には、モジュールの責務を宣言する。** 役割と設計方針を数行で書く
  - `CLAUDE.md` のモジュール責務は、原則として `//!` を正本とする。`CLAUDE.md` のモジュール構成節は、ファイル名の索引と、`//!` に収まらない横断不変条件に留める
  - 例外: 薄いラッパーの集約群や、宣言だけの `mod.rs` は、責務を `CLAUDE.md` に書く
  - 模範例: `snotra-core/src/search.rs`・`src-tauri/src/working_set.rs`・`snotra-settings/src/style.rs`
- **doc コメント内の、リンクでない角括弧はバッククォートで包む。** `/// [今すぐ更新] を描く` のような UI ラベルの `[...]` を、rustdoc は intra-doc link として解釈する。解決できなければ `cargo doc` が警告し、deny 設定の crate では CI が赤になる。`` `[今すぐ更新]` `` と包めば、リテラルとして描かれる
- **設計判断の長文は、`# Why ...` 見出しで構造化する**（模範例: `snotra-core/src/search.rs` の `SearchEngine` struct doc）。倣うのは見出しで構造化する形である。却下案の詳細をコメントへ置いてよい根拠にはならない（却下案の比較は ADR に置く）

## TSDoc の様式

「第一原則」と「短く保つ」は、`scripts/` の `.mjs` にもそのまま当てる。TS / JS に固有の規則は、次の 1 つだけである。

- **`@param` / `@returns` を必須にしない。** 型シグネチャと重複する。引数の**意味**（正規化済みか、どちらの座標系か）に補足が要るときだけ書く

## 日本語の折返し

**素の散文の折返しは禁じない。** 禁じるのは、実測された害を持つ次の 1 形だけである。

- **コードスパン（バッククォートで囲んだ識別子・コマンド）を行またぎさせない。** 見出し名やシンボル名で grep して辿れなくなる。rustdoc は soft line break を跨いで正しく描画するので、壊れるのは検索だけであり、気づかれにくい。2026-08-08 の実測では、`current_thread().id() == context.main_thread_id` を丸ごと分断していて、grep が 0 件を返した例があった

この規範は全ツリーへ掛かる。行末のインラインコメントも、`docs/adr/` も含む。除外するのは、構造行そのもの（表の行・箇条書きの行頭記号・コードフェンス）だけで、箇条書きの項の中身には当たる。検査は無いので、書く人とレビューが守る。

## 定型ラベル（既存慣習の様式化）

同じ意図には次のラベルを使い、同義のラベルを新しく増やさない。書式は厳密には強制せず、部分一致の変種を許す。

| ラベル | 意味 | 実例 |
|---|---|---|
| `保守注意:` | 将来の変更時に反映・確認すべき条件 | `snotra-core/src/config.rs`（icon_cache_cap 派生値） |
| `不変条件:` | 崩すと壊れる前提（変種「核心不変条件:」も可） | `snotra-settings/src/tabs/common.rs` |
| `実装メモ:` | 設計判断・テスト設計の補足 | `snotra-settings/src/app.rs` |
| `検出マーカー:` | 回帰をどう検知するかの仕掛けの説明 | `snotra-settings/src/app.rs` |
| `回帰テスト:` | テストが守る性質と、出自の `#NNN` | `src-tauri/src/icon.rs`、`src-tauri/src/egui_shell/view.rs` |

## 歴史メモの様式

経緯そのものはコメントに書かず、`#NNN` で辿れる形にする。コメントに残すのは、その経緯が**現在の形へ課している制約**だけである。

- **issue / PR 番号を `#NNN` で参照する**（例: `(#535)`）。経緯の全文は書かない
- **実測値には条件を添える（日付・エントリ数・試行回数など）。** 例: 「実測 17/2000 回」「2026-07-17 実測」。条件のない数値は再検証できない
- **却下した代替案の比較は `docs/adr/` へ置く。** コメントに残すのは、その却下が現在の形へ課している制約である。`SearchEngine` の doc は、比較がコメント側に残っている先例である。新しく書くなら、その分量は ADR に置く

## 言語（日英）

- **日本語を既定とする。** プラットフォームの低レベル部（Win32 API まわり）や、英語圏の API・用語が支配的な文脈では、英語でもよい
- **1 つのコメントブロックの中で、日本語と英語を混ぜることは避ける**（新しく書く分から適用する。既存は書き直さない）
- 技術用語・識別子・API 名は翻訳せず、原語のまま書く
- **訳語は、「その分野の日本語話者が実際に使う語」を選ぶ。** 誤りは例外なく「原語の字面をそのまま日本語へ置き換える」方向で起きる。漢語化（coverage → 被覆）も和語直訳も同じ誤りであり、名詞に限らず、比喩を述語へ活用させる形でも起きる。判定は 2 つある
  - **(A) 誤配属**: その訳語が標準語である分野を名指せて、それが今書いている分野でなければ誤り（名指した分野が今の分野なら正しい）
  - **(B) 造語**: その語で日本語検索して、同じ文脈の技術文書が出ないなら誤り。どの分野の標準語でもない思いつきは、(A) では拾えない
  - **迷ったら訳さない側を選ぶ**（カタカナか原語のまま書く）
  - **語ではなく語義ごとに判定する。** 同じ語が、文脈によって正しくも誤りにもなる。語の一覧を作って一括置換してはならない
- **適用範囲**: (A)/(B) は、新しく選ぶ訳語にも、既に書かれた訳語にも当てる
  - `SPEC.md` や各 `CLAUDE.md` で使われていることは、その訳語を残す理由にならない
  - 判定に当たらない語は、漢語でも書き換えない（例: 「正本」「母集団」は普通の日本語として通じる）
  - 既存の語を直すときも、**同じファイルの中で語を混在させない**（実例: フォントが字を持つかの語義は「カバー」へ揃えた。両者を結ぶ識別子は `font_covers_cjk` である）
- **ADR への適用**: 既存の訳語を直す整備は、`docs/adr/` にも及ぶ。ADR は凍結された歴史（`ADR-adr-frozen-history`）であり、この整備はその例外である
  - **直すのは語の置き換えに限る。決定の内容・文の組み立て・見出しは変えない**
  - 例外にする理由: ADR は判断の根拠として今も読まれ、その言い回しが新しく書く文へ写りうる
  - `docs/superpowers/` は対象外のまま

## テストコードのコメント

- **何を証明するテストかを書く。** とくに、「他のテストと重複しない理由」や race window の説明など、テスト名だけでは伝わらない検証意図を書く。回帰テストには `回帰テスト:` ラベルを付け、守る性質と出自の `#NNN` を書く
- **「この入力がこの誤りを弾く」と書くなら、その誤った規則で当の入力を実際に評価してから書く。** 主張がずれていてもテストは緑のままで、機構は何も言わない。「このテストは X を検出する」と書くときも同じで、X を実際に起こして落ちることを確かめる（#745 は、呼び出しを消しても全数が通るテストの doc が「守られている」と誤信させた）
- 同じ assert の並びに役割の違うものが混ざるなら、行ごとに書き分ける
- Given/When/Then などの BDD 定型は使わない（構造はコードで表す）
