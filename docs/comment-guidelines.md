# コメントガイドライン

コードコメント（rustdoc / TSDoc / インラインコメント）の書き方・粒度・配置の規約。エージェント・人間を問わず適用される。

本書は `.rs` を編集したとき `.claude/rules/comments.md` 経由で配送される（ポインタだけの router）。**本書を rule 本体へ統合しない理由と、条項に機械検査を付けない理由は `docs/adr/ADR-comment-guideline-delivery-by-pointer.md`** が持つ。

本書は**既存の優良慣習の追認・様式化**である。模範例はすべて実在のコードを参照する（新規ルールの発明は最小限に留める）。既存コメントの一括書き直しは本書のスコープ外——既存コメントは通常の変更でそのコードに触れたときに本書へ寄せれば足りる。

## 第一原則: コメントは理由を書く

**コードから読み取れないことだけを書く。** コードが「何をするか」を語り、コメントは「なぜそうしたか」を語る。

書く価値があるもの:

- **設計判断の理由**（なぜこの形でなければならないか。**却下案の詳細な比較は ADR へ**——「配置基準（3 層）」）
- **不変条件**（何が常に成り立つべきか、崩すと何が壊れるか）
- **過去の事故が残した制約**——**現在の形の理由**として書く。**経緯そのものは `#NNN` で辿れる形にする**（#1185。知見を捨てるのではなく、置き場を分ける）
- **呼び出し前提・契約**（同期性・再入・失敗時の挙動）

書かないもの:

- **コードの逐語訳**（「i をインクリメントする」型。リファクタで即座に嘘になる）
- **コードが決めている構造の事実**——経路の**数**、分岐の**列挙**、**呼び出し元**、**到達可能性**。**これは「なぜ」型に見えるが写しである**（正本はコード自身であり、分岐を 1 本足すたびに散文だけが腐る）。#977 で腐った 3 件はすべてこの型だった（「通る経路は 3 つ」「`None` になるのは保存先が引けなかったときだけ」「キャッシュヒット時に使用するコンストラクタ」）。模範例は `snotra-core/src/engine.rs` の `Engine::from_material`——「**版の番号を書かない。** 番号を書くと版を上げるたびにこの散文だけが腐る」と自ら宣言し、正本（`indexer::save_cache_sorted` と `load_cache_in` の分岐）を名指ししている。**この項の射程はコードコメントである**——散文ドキュメント側の同型は `AGENTS.md`「条件別チェック（トリガー → 参照先）」の写しの行が覆う。**腐るのは数であって名指しではない**ので、次のとおり区別する:
  - **数は書かない**（「経路は 2 つ」「呼び出し元は 3 箇所」）——分岐を 1 本足すたびに散文だけが嘘になり、しかも**誰も検査しない**（腐りやすい形が、ちょうど機械化されていない形と一致する）。**過去の変化量は対象外である**——「#689 が 1 枝を足した」のような経緯は現在の姿の数え上げではなく、「歴史メモの様式」の側に属する
  - **名指しは書いてよい。ただし `` [`Type::method`] `` の形で書く**——素の散文名は誰も確かめず、`` [`X`] `` は「正本はあちら」の宣言として読者にも機械にも届く。**どの面で何が確かめられるかは「名指しと正本の指名」の表が正本である**——保証の要る参照は、そこを見て置き場を決める
  - **列挙が「正本の代わり」なら書かない。列挙が「それが無いと誤読される」ための証拠なら残す**——実例は `snotra-core/src/search.rs` の `SearchEngine::recent_history`。「全件走査が毎回の窓表示に乗る」という誤読を 2 度招いたため、頻度を推測させず呼び出し元を名指しし、**その理由を同じ doc に書いている**。名指しの根拠が隣に無いものは前者（正本の代わり）である
  - **一意性の宣言はこの項の対象ではない**——「保存先を導く経路はここ 1 つだけである」「規則の定義はこの関数 1 つである」は今の姿の数え上げではなく、**崩れたら事故になる不変条件**であり「書く価値があるもの」の側に属する
  - **この条項は自分自身で腐り、その直しがまた腐った。** 模範例が指していた関数を #984 が削除したとき**機構は緑で、見つけたのはレビューであって機構ではない**（射程を広げた経緯は `ADR-stale-identifier-detector-scope`）。直しに書いた機構の述語は #989 の並行マージで偽になった（機序と一般形は `.claude/rules/governance-docs.md`「機構の実装の詳細（述語の種類・件数・分岐の列挙）を散文へ写さない」）。**ゆえにここへ機構の述語も照合件数もこの箇条の段数も書かない**（段数は #732 の初稿が書いて腐った）
- **「なぜ」に添える根拠のうち、他のコードの現在の状態を主張するもの**——**振る舞いの同一性**（「製品の規則をそのまま通す」「旧実装と挙動は同じ」）と**頻度**（「通常は空」「ほぼ毎回走る」）。前項が「数・列挙」を対象にするのに対し、こちらは**関係と割合**を対象にする（#995）。動機文は「**X のために** Y する。**なぜなら Z だから**」の形で書かれ、X（決定）は腐らないが **Z が他の現在形だと腐り、しかも読み手には動機ごと信用できなくなる**。
  - **「同じ〜を通る」と書けるのは、実際に同じ 1 か所を通るときだけである。** `window_coordinator.rs` の `read_bar_anchor`（クランプと hide 保存が同じ 1 つの関数を通る）や `search/tests/build.rs` が `IndexMaterial::extend_with_path_entries` そのものを通す形は、**構造が同一性を担保しているので要石**であり対象外。**別々に書いたものが「同じ規則」だと言うのは誰も検算しない**ので、書き写したなら**書き写したと書く**（「`indexer` の規則を書き写している——SSOT の関数が無いため」のように自ら名乗る形。模範例だった test fixture は #996 で対象ごと消えた）
  - **頻度は数を添えられないなら根拠に使わない。** 添えられる形の模範例は `snotra-core/src/index_tree.rs` の `IndexTree::file_key_into` の「実データで根は約 200 件（0.06%）——ほとんど通らない腕ゆえ、壊れても静かである」
  - 直すときは、根拠を腐らない形へ移す: **過去の行為**（「〜する」→「〜した」）・**過去の観測**（日付つきの実測）・**参照**（正本を指す）。**訂正のたびに新しい現在形を書けば、次の指摘を生む**——#995 のレビューが繰り返し当てたのはこの型だけである（例: 「片づく契機は次の drain だけ」→「片づけの保証は置かなかった」）
- **未実装計画**（YAGNI。「実装しない機能のコメントは書かない」——旧 ui/CLAUDE.md 由来の規範を全域に一般化したもの）
- **変更履歴の再現**（git log / PR が持つ。コメントは「現在の形の理由」だけを書く）
- **レビュー向けの一時的説明**（「この変更が正しい理由」は PR 本文に書く。マージ後の読者にはノイズ）

## 配置基準（3 層）

どこに書くかは `docs/development-principles.md`「ドキュメントとコードの分担（陳腐化の予防）」の判定基準——**「この一文は、振る舞いを保つリファクタを生き延びるか？」**——に従う。本書はコメント側の細分だけを追加する:

| 層 | 書くもの | 例 |
|---|---|---|
| 散文ドキュメント（`SPEC.md` / `docs/` / 各 `CLAUDE.md`） | intent・全体構造・横断パターン | アーキテクチャ、状態遷移の意図 |
| **doc コメント**（`///` `//!` `/** */`） | 公開アイテムの契約・精密事実の SSOT（正本コメント） | 保証・パニック条件・設計判断 |
| **インラインコメント**（`//`） | その行・ブロックに局所的な why | 「この順序でないと X が壊れる」 |

散文ドキュメントから精密事実（式・バイト形式・機構名）を参照するときは、参照先の doc コメントを正本コメントとして指名する（詳細は development-principles.md 同節）。

**層の中の分担**（#1185）。同じ層でも面によって置き場が違う:

| 面 | 書くもの | 書かないもの（降ろす先） |
|---|---|---|
| `//!`（module doc） | モジュールの責務・依存方向・モジュール全体に効く不変条件。**`CLAUDE.md` が責務の正本に指名している面である**（#562） | 実装の詳細（アルゴリズムの選択・記憶域の配置）→ `///` |
| `///`（item doc） | 契約・保証・パニック条件・局所的な理由・**寄せ先の無い測定値の正本**（下の「測定値の置き場」） | 経緯・却下案の詳細比較 → `#NNN` / ADR |
| `//`（inline） | その行・ブロックだけに効く理由 | 保証の要る参照（着地を検査されない面ゆえ →「名指しと正本の指名」の表） |
| ADR（`docs/adr/`） | **却下した代替案と、却下の理由**（否定の知識） | 採用案の再説明（コードと `SPEC.md` が持つ） |
| `docs/` の散文 | 横断パターン・複数モジュールにまたがる設計比較 | 精密事実（doc コメントを正本に指名する） |

**module doc が複数の設計論点を抱え始めたら、長さを削るのではなく層を分ける。** 責務は `//!` に残し、
実装の詳細は item doc へ降ろす——`//!` を短くするために責務を削ると、`CLAUDE.md` 側に受け皿が無い。

## 短く保つ

**行数や文字数の上限は置かない**（#1185 の非目標）。短さは長さの問題ではなく**層の問題**である——長いコメントは、たいてい**複数の層の内容が 1 か所に積まれている**。次の 3 つを順に問う:

1. **この一文はどの面のものか。** 責務なら `//!`、契約なら `///`、その行だけの理由なら `//`、却下案なら ADR、経緯なら `#NNN`（「配置基準（3 層）」の層の中の分担）
2. **同じ主張が別の面に既に在るか。** 在るなら**指す**（`` [`X`] `` か正準形参照）。写しを 2 つ置くと、片方だけが直る日が来る
3. **この一文は、振る舞いを保つリファクタを生き延びるか。** 生き延びないなら「第一原則」の「書かないもの」に当たる

### 測定値の置き場

**この判断はここで新しく決めない。** `docs/adr/ADR-measurement-canon-in-code-doc.md` と `PERFORMANCE.md`「この文書へ記録するときの規約」が既に決めている。要点だけ:

- **`PERFORMANCE.md` に節が在る値**——コメントはその節を正準形で指し、値を写さない
- **寄せ先の無い値**——**コードの doc が正本でよい。** `PERFORMANCE.md` へ新設して寄せると、出所が既存の写しそのものになる
- **判断を支えていない経緯の値**（「反復 N で〜した」型の変化量）——`#NNN` へ委ねて外す

**「実測値はコメントに書かない」と読み替えないこと**——規模感が「なぜそうしたか」の説得力そのものである場合があり、数値ではなく寄せ先が問題である。

## 名指しと正本の指名

**`` [`X`] `` は「ここには書かない、正本はあちらである」を読者と機械の双方へ宣言する記法である。** 「第一原則」が禁じる写し——数・列挙・他所の現在形——を書かずに済ませるための第一の道具であり、素の散文名との違いは装飾ではなく、**この宣言が届くかどうか**にある。

**同じ記法でも、その名前を誰が確かめるかは書いた面で決まる。**

| 面 | rustdoc が描く | 着地を検査する | rust-analyzer が定義へ飛ぶ |
|---|---|---|---|
| production の `///` `//!` | ○ | **○** | ○ |
| `#[cfg(test)]` の中の `///` | × | **×** | ○ |
| `//` のインラインコメント | × | **×** | × |

着地の検査は `cargo doc` が行う（`broken_intra_doc_links` は workspace で deny・発火は CI のみ）。**保証が要る参照は production の doc コメント側へ置く。** それ以外の面でも記法は無駄にならない——**失うのは保証だけで、指名は残る。**

**ただし `//` の行で失うのは保証だけではない。** 表のとおり rust-analyzer も解決しないので、この面で角括弧が残しているのは**読み手への宣言だけ**である。ゆえに問うのは「この名前は、このコメントが効いているブロックの実行コードにも現れるか」——現れるなら、読み手はそこから辿れる。角括弧が最も効くのは、名前がコードに無い側である。

**成否は「書いた面」だけでなく「指す先」でも決まる。** production の doc から `#[cfg(test)]` の項目へリンクすると、rustdoc がその項目を見ないので**検査が正しく赤にする**——そこは素のバッククォートで書く（実例と理由は `snotra-core/src/history.rs` の `HistoryStore::load` の doc）。

**逆向き（定義から参照の列挙）には、どの面の名指しも現れない。** findReferences が返すのはコード側だけで、rename も doc コメントを書き換えない（2026-08-25 実測）。ゆえに改名では、LSP が挙げた呼び出し元を直しても doc コメントは残る——それを赤にするのは、上の表で「検査する」と書いた面だけである。

**表の「○」が嘘になる形が 1 つある。** 開きが ASCII の `[` で閉じが全角のとき、rustdoc はリンクと認識せず**リテラルとして出す**——壊れたリンクは赤くなるが、リンクですらないものには何も言わない（#1172）。

**「×」の側は受容している。** `#[cfg(test)]` の中で失うのは「参照が生きている」という保証だけで、製品には影響しない（#1116）。

## rustdoc の様式

- **`///` は公開アイテムの契約を書く**: 要約 1 行（何であるか）＋必要なら空行を挟んで詳細（保証・パニック条件・呼び出し前提・ロック規律）。全 pub アイテムへの機械的な付与は求めない——**契約や非自明な前提を持つものに書く**
- **既存アイテムの隣へ新しいアイテムを挿入したら、`///` の帰属が動いていないか目で確かめる。** `///` は直後のアイテムに付くので、**既存の doc ブロックの末尾へ書き足す形で挿入すると、その doc ごと新しいアイテムのものになり、元のアイテムが doc を失う**。#1106 で `results_window_height` がこれを踏み、「`0.0` は hide の契約値である……ここが正本である」という**正本の宣言**が別の関数へ移って 4 つの参照が宙に浮いた。**どの機械検査も見ない**——リンク切れではないので `cargo doc` は緑、fmt / clippy / test も無関係で、doc の欠落そのものを lint で deny 化する案も workspace 全体で 305 件が該当する（2026-08-16 実測）ため採れない。挿入位置を「既存アイテムの**後ろ**」に取れば構造的に起きない
- **`//!` はモジュール冒頭の責務宣言**: モジュールの役割と設計方針を数行で。**#562 で責務を持つ個別モジュールへ展開し、`CLAUDE.md` のモジュール責務は原則 `//!` を正本とする**（`src-tauri` の `commands/`・`platform/` のような薄いラッパー集約群や宣言のみの `mod.rs` は責務を `CLAUDE.md` に記す例外）——`CLAUDE.md` のモジュール構成節はファイル名の索引と、`//!` に収まらない横断不変条件・チェックリストに留める（`//!` はコード側で改名に追従し、`cargo doc` の intra-doc link 検査が相互参照の腐敗を捕まえる）。模範例は `snotra-core/src/search.rs`（`SearchEngine`）/ `opener.rs`、`src-tauri/src` の `working_set.rs` / `state.rs`、`snotra-settings/src` の `style.rs`
- **doc コメント内の非リンク角括弧は backtick で包む**: `/// [今すぐ更新] を描く` のような UI ラベル・リテラル表記の `[...]` を rustdoc は intra-doc link として解釈し、解決できないと `cargo doc` が警告する（`snotra`/`snotra-core` は deny 設定ゆえ **CI rust-check が赤**になる。SU5 で 4 箇所踏んだ・PR #647）。`` `[今すぐ更新]` `` と backtick で包めばリテラルになる。この検査は PostToolUse hook にも task review にも含まれず **CI でのみ発火する**——doc コメントを書く時点で様式として守るのが唯一の早期防御
- **設計判断の長文は `# Why ...` 見出しで構造化する**（**引くのは見出しで構造化するという形であって、却下案の詳細をコメントへ置く根拠ではない**——置き場は「歴史メモの様式」が定める）: 模範例は `snotra-core/src/search.rs` の `SearchEngine` struct doc——`# Why parallel Vecs instead of a single Vec<CachedEntry> struct?` 見出しの下に、試作ブランチ・issue 番号・ベンチ結果の表・根本原因・「意図的であり技術的負債ではない」の明言、を置く。**長さ自体は問題ではない**（→「歴史メモの様式」）

## 日本語の折返し

**素の散文の折返しは禁じない。折るなという条項は、実測された害を持つ 2 形にだけ掛かる**（下の 2 つ。**3 つ目の害が実測されれば増える**）。

かつて本節は「文途中で物理改行を入れない（1 段落 1 行）」を一般則として課していた。**実測すると規範として機能しておらず**（機構を書く側自身が守っておらず、折返しの大半は下の 2 形に当たらなかった）、#992 で縮めた。**戻すなら、まずその数を測り直すこと**——値と測り方は `ADR-folded-code-span-detector`「文脈」が正本である（**ここへ写さない**。並行マージで片方だけが古びる）。

**規範としてのこの 2 形は、機構の射程と無関係に全ツリーへ掛かる**——行末のインラインコメントも、`docs/adr/` も、機構が走らない面も含む。**機構が見ない場所で守るのは人である**（機構の母集団は下記。そこは「赤で気づける範囲」であって「規範が及ぶ範囲」ではない）。**この 2 形については既存・新規を問わない**——それ以外の書き方の条項は、本書冒頭のとおり新規に書くコメントと、その変更で触った段落だけに適用する。**この節だけ射程が違うのは、機構が大部分を支えているからである。****規範としての除外は構造行そのものだけ**（表の行・箇条書きの行頭記号・コードフェンス）であり、**箇条書きの項の中身の散文には 2 形とも当たる**。

**射程は `.rs` を越えるが、全ツリーではない。** 機構が見るのは `.md` とコメント記法を持つスクリプト（`.ps1` / `.psm1` / `.mjs` 等）を含む一方、**`.md` は大半が母集団の外にある**（`docs/adr/` と `docs/superpowers/` が落ちるため。`.rs` とスクリプトは今日すべて入る）。**母集団の正本は各検査が導く `allHeadingRefDocs` であり、ここに枚数も除外の一覧も写さない**——腕が増えれば偽になる。赤を受け取った側が射程を知りたければ、各検査のヘッダが正本である。

**本書の配送は 4 crate の `.rs` だけである。** ゆえに `.ps1` / `.psm1` のように**規範が一言も無い面で機構だけが赤を出す**——赤を受け取ったら各検査のヘッダの射程宣言を読むこと（それが唯一の拠り所になる）。

禁じる 2 形と、その実測された害:

- **コードスパン（バッククォートで囲んだ識別子・コマンド）を行またぎさせない**。`.claude/rules/` が #588 で規範化した「見出し名・シンボル名で grep して辿る」が、行をまたいだコードスパンでは効かない——2026-08-08 の実測で 5 件あり、うち 1 件は `current_thread().id() == context.main_thread_id` を丸ごと分断していて grep が 0 件を返した。rustdoc の描画は soft line break を跨げるので壊れず、壊れるのは検索だけである（だから気づかれない）。**この形は機構が見る**（`G-folded-code-spans`。射程と死角は同検査のヘッダが正本）。#992 の時点で実在し、**そのうち 2 件は本節が入った 2026-08-08 より後に生まれていた**——規範 1 行では足りなかったことの一次証拠であり、件数と `git blame` は `ADR-folded-code-span-detector` が持つ
- **正準形の見出し参照 `` `<対象>`「<見出し>」 `` を物理改行で折らない**。折れると `governance:check` の照合はその参照を**一致として生成すらしない**——`checked` にも `findings` にも現れないので、「照合していない」と「差分ゼロ」を分ける証跡が残らない。**この形も機構が見る**（`G-folded-heading-refs`。射程と死角は同検査のヘッダが正本）。2026-08-20 の実測で 33 件在り、うち 1 件は折れが本物の腐りを隠していた

**整形器は持たないが、検査は持つ。** rustfmt はコメントを折り返さない（wrap_comments は既定 false かつ nightly 限定で、リポジトリは設定ファイルを置いていない。2026-08-22 に固定版で実測——stable は警告を出して無視し、折れは 1 文字も直らない。nightly でも向きは逆で、指定幅へ**折り込む**側の機能である）。clippy も**同じ固定版・同じ日に**doc lint を全部有効にして 0 件だった（新しい doc lint が入れば変わりうる）。**折れたスパンは正しい CommonMark だからであって、道具の欠落ではない**（`ADR-folded-code-span-detector`）。**折る側にも折らない側にも二次的な費用がある**——手で折れば一文直すたび段落全体が再折返しになって diff が膨らみ、折らなければ行が長くなる。**どちらも測っていない**ので、素の散文をどちらへ倒すかの根拠にしていない（縮めた根拠は上の実測であって、この費用ではない）。

**禁則処理の規則は置かない。** `.rs` のコメント 8030 行を走査して禁則違反候補は 0 件だった（2026-08-08 実測。行末の開き括弧・行頭の閉じ括弧や句読点で判定）。既に守られているものへ規範を足すと、面積だけ増えて読者の注意を奪う。

## TSDoc の様式

現行リポジトリの TS は `vitest.config.ts` のみ（フロントは #532 SU7 で撤去）。**書く機会がほぼ無いので、規範も最小で残す**（#1185）。

- 上の「第一原則」「配置基準（3 層）」「短く保つ」はそのまま当たる（**`scripts/` の `.mjs` にも**）。TS 固有なのは次の 1 点だけである
- **`@param` / `@returns` を必須にしない**——型シグネチャの重複になる。引数の**意味**（正規化済みか、どちらの座標系か）に補足が要るときだけ書く

## 定型ラベル（既存慣習の様式化）

以下のラベルが自然発生している（件数は少ないものもあるが、同義ラベルの分裂を防ぐため一覧化する）。同じ意図にはこれらを使い、新しい同義ラベルを増やさない:

| ラベル | 意味 | 実例 |
|---|---|---|
| `保守注意:` | 将来の変更時に反映・確認すべき条件 | `snotra-core/src/config.rs`（icon_cache_cap 派生値） |
| `不変条件:` | 崩すと壊れる前提（変種「核心不変条件:」も可） | `snotra-settings/src/tabs/common.rs` |
| `実装メモ:` | 設計判断・テスト設計の補足 | `snotra-settings/src/app.rs` |
| `検出マーカー:` | 回帰をどう検知するかの仕掛けの説明 | `snotra-settings/src/app.rs` |
| `回帰テスト:` | テストの由来・設計意図（どの事故・指摘から生まれたか、なぜこの形か） | `src-tauri/src/icon.rs`（#522 由来）、`src-tauri/src/egui_shell/view.rs`（#840 / #872 由来） |

ラベルの書式を厳密には強制しない（部分一致の変種を許容）。**意図が同じなら既存ラベルに寄せる**ことだけを守る。

## 歴史メモの様式

**粒度の判定基準: 「この情報が消えたら、将来の変更者が同じ失敗を繰り返すか？」**——繰り返すなら書く価値があり、繰り返さない（コードや型が防いでいる）なら書かない。

**長さを許すのはこの節の射程——歴史メモ——に限る**（#1185）。item doc の契約部は短く保つ（「短く保つ」）。**判定基準を通った情報でも、置き場は面によって違う**——経緯そのものは `#NNN` で辿れる形にし、コメントには**現在の形の理由**だけを残す（「配置基準（3 層）」の層の中の分担）。

書くときの様式:

- **issue / PR 番号を `#NNN` で参照する**（例: `(#535)`）。経緯の全文を書かず、番号で辿れるようにする
- **実測値には条件を添える**（日付・エントリ数・試行回数など。例: 「実測 17/2000 回」「2026-07-17 実測」）。条件のない数値は再検証できない
- **却下した代替案の詳細な比較は `docs/adr/` へ置く**（#1185）。コメントに残すのは、その却下が**現在の形へ課している制約**である。ADR へ書くときの順は「試した → 結果 → 採用理由」（`SearchEngine` doc が**コメント側に残っている先例**——試作 → ベンチ表 → 根本原因 → 意図の明言。**新しく書くならこの分量は ADR 側である**）
- 関連する `CLAUDE.md` / `.claude/rules/` に対応する規則があるなら相互参照する

## 言語（日英）

- **日本語を既定とする**（現状の主流を追認）
- **英語も可**: プラットフォーム低レベル部（Win32 API まわり）や、英語圏の API・用語が支配的な文脈では英語の方が自然なことがある
- **同一コメントブロック内の日英混在は避ける**（新規分から適用。既存は書き直さない。本書の模範例に英語コメントがあっても、倣うべきは構造であって言語ではない）
- 技術用語・識別子・API 名は翻訳せず原語のまま書く
- **訳語は「その分野の日本語話者が実際に使う語」を選ぶ。** 誤りは例外なく「原語の字面をそのまま日本語へ置き換える」方向で起きる——漢語化（coverage → 被覆）も和語直訳も同じ誤りであり、名詞に限らず比喩を述語へ活用させる形でも起きる。判定は 2 つある。**(A) 誤配属**: その訳語が標準語である分野を名指せて、それが今書いている分野でなければ誤り（名指した分野が今の分野なら正しい）。**(B) 造語**: その語で日本語検索して同じ文脈の技術文書が出ないなら誤り——どの分野の標準語でもない思いつきは (A) では捕まらない。**迷ったら訳さない側へ倒す**（カタカナか原語のまま書く）。**語ではなく語義ごとに判定する**——同じ語が文脈によって正しくも誤りにもなるので、語の一覧を作って一括置換してはならない
  - **射程**: 本条項は**新しく訳語を選ぶときの判定**であり、既存の定着語を置き換える指示ではない。**定着の判定は「その語がこのリポジトリの `SPEC.md` か各 `CLAUDE.md` で既に使われているか」**とし、使われているならそれがこのリポジトリの語である（例: 「窓」は `src-tauri/CLAUDE.md` や `snotra-egui-runtime/CLAUDE.md` が使うのでこのリポジトリの語であり、カタカナへ寄せ直さない）。適用は新規分と、その変更で触った箇所に限る。定着語について守るのは**同一ファイル内で語を混在させないこと**だけである。**訳語が複数定着している語義では、この定着テストは解を返さない**——そのときは「迷ったら訳さない側へ倒す」が決める（実例: フォントが字を持つかの語義は `SPEC.md` が「被覆」・`snotra-settings/CLAUDE.md` が「カバー」で、どちらも定着しているため後者へ倒した。`SPEC.md` 側は今回の変更で触っていないので上の適用範囲どおり射程外であり、両者の共通の錨は `font_covers_cjk` である）

## コメントと実装の同期

**コメントは実装と同じ場所・同じ PR で更新する。** 挙動を変える変更でコメントの「なぜ」が変わるなら、同じコミットで直す（「fix でも文書化された挙動を変えたら仕様変更」——`AGENTS.md`「バグか仕様変更かを判定する」——のコメント版)。

同期コストを下げるのは様式ではなく**内容の選び方**である: 「何を」型コメントは実装変更のたびに書き換えが要るが、「なぜ」型（設計判断・不変条件）は振る舞いを保つリファクタを生き延びる。第一原則を守ること自体が同期コストの根治になる。

## テストコードのコメント

- **テストの由来を書く**: 回帰テストは `回帰テスト:` ラベルで出自（どの事故・指摘から）や設計意図を明記する（既存ラベルの様式化）
- **何を証明するテストかを書く**: 特に「他のテストと重複しない理由」（例: 「純ロジックテスト済みのため重複させない」）や race window の説明など、テスト名だけでは伝わらない検証意図
- **「この入力がこの誤りを弾く」と書くなら、その誤った規則で当の入力を実際に評価してから書く。** 主張がずれていても**テストは緑のまま**で、機構は何も言わない——読者は「ここは守られている」という誤った安心だけを得る（#878: `logical_to_phys(43.6, 1.0) == 44` へ「`.5` ちょうど・銀行家丸めでも落ちる」と書いたが、43.6 は境界ではなく銀行家丸めでも 44 になる。弾いていたのは `trunc` だけで、銀行家丸めを弾くのは続く 3 行だった）。**同じ assert の並びに役割の違うものが混ざるなら、行ごとに書き分ける**——「何を弾くか」は行の性質であって、まとめて 1 行のコメントに括ると必ずどれかが嘘になる
- Given/When/Then 等の BDD 定型は使わない（現状不使用の追認。構造はコードで表す）
