# 開発原則

このプロジェクトで共有する設計・実装の原則。エージェント・人間を問わず適用される。

## KISS

- `main.rs` に業務ロジックを増やさない
- 責務を跨ぐ実装をしない
- 新規コードは既存のファイル構成・命名規則・スタイルパターンに合わせる。独自パターンを導入する前に既存パターンの利用を検討する

## DRY

- 責務の集約先は各サブディレクトリのドキュメント（`snotra-core/CLAUDE.md`, `src-tauri/CLAUDE.md`, `ui/CLAUDE.md`, `snotra-settings/CLAUDE.md`）に記載
- 同一ロジックの繰り返しは2回まで許容し、3回目で抽出を検討する（無理な抽象化よりも多少の重複を許容）
- **ドキュメント間でも DRY**: 同じ事実（モジュール一覧・コマンド・契約等）を複数の `.md` に書かない。SSOT を1つ決め、他は参照する。二重管理は片方の更新漏れで必ずドリフトする — 「同期を頑張る」のではなく「重複を排除する」のが根治

## YAGNI

- 使う予定だけの抽象化（不要な trait/generics/レイヤー）を導入しない
- 現在の要求範囲を超える機能追加を行わない
- 拡張性より、現要件での単純さと可読性を優先する

## 設定由来の派生状態（キャッシュとして扱う）

config から導出する派生状態は「キャッシュ」とみなす（#347/#348 の教訓）。

- **既定は live-read**（毎操作で config から計算）。**計測して高価なものだけキャッシュ化**（長命オブジェクトに焼き込む）する。安いものを焼き込むと設定変更が反映されないドリフトを生むだけ
- キャッシュ化（焼き込み）するなら、その**無効化（設定変更時の再構築）の所有者を必ず決める**。所有者不在は設定変更の取りこぼし・データ損失の温床（例: `HistoryStore.top_n` の焼き込みドリフト、index の lost-update 窓）
- 「setter を足して追従させる」より「そもそも焼き込まず live-read にする」方が、desync を構造的に発生不能にできる場合が多い（例: `HistoryStore.top_n` を live-read 化してフィールド自体を削除）
- 詳細設計は `docs/design/2026-05-31-coherence-staleset.md`（config↔派生状態コヒーレンシ / StaleSet 契約）

## デバッグ・バグ修正

- バグ修正時は、コードを書く前に根本原因を一文で明示する
- 根本原因の説明には「壊れた不変条件（何が常に成り立つべきだったか）」を必ず1つ含める
- 最初の修正案が失敗した場合、同じ深さで別の推測を試みるのではなく、より深い調査に切り替える
- バグ修正時は、修正対象のパターンをコードベース全体で検索し、同一パターンが他の箇所にも存在しないか確認してから完了とする
- `tauri.conf.json` や platform 固有ファイルに設定を追加する際は、その設定が Windows でサポートされているか事前に確認する（例: `backgroundThrottlingPolicy` は Windows 非対応でビルドエラーになる）
- 修正案が API 境界をまたぐとき、「呼び出し側パッチ」と「API 側で責務を完結させる修正」の両案を比較し、後者を優先する
- 競合しやすい一時状態（通知・ローディング・遅延処理）を導入する場合は、タイマー/購読のライフサイクルを単一管理し、再実行時に必ず前回ハンドルを破棄する
- ガード（ロック・フラグ・CAS）を追加するときは「どの*関数*を守るか」ではなく「どの*リソース*を守るか」で設計する。同じリソース（ファイル・共有状態）を触る経路が複数あれば、全経路が同じガードを通すこと。関数単位のガードは別経路の追加で素通りされる
- テストや挙動の「赤」を自分の変更による回帰と断定する前に、変更前のベースライン（`main` 等）で同じ条件を実行して A/B 比較する。両者が一致すれば、その差分は原因ではない（既存バグ・環境要因）。検索・索引など自分が触った領域の失敗ほど、思い込みを排してベースラインと突き合わせる。性能評価も同様に、同一マシンでの A/B でのみ退行を判定する（別環境の記録値との比較で判断しない）
- 層をまたぐ不具合は、上位層（UI）の症状から推測せず最下層を直接観測して切り分ける（backend IPC を直接呼ぶ・アプリにロード済み状態をダンプさせる等）。release ビルドはフロントの `trace()` がデッドコード除去されるため、上位層のログに頼らない観測手段を用意する
