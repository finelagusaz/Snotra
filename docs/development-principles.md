# 開発原則

このプロジェクトで共有する設計・実装の原則。エージェント・人間を問わず適用される。

## KISS

- `main.rs` に業務ロジックを増やさない
- 責務を跨ぐ実装をしない
- 新規コードは既存のファイル構成・命名規則・スタイルパターンに合わせる。独自パターンを導入する前に、既存パターンの利用を検討する

## DRY

- 責務の集約先は各サブディレクトリのドキュメント（`snotra-core/CLAUDE.md`, `src-tauri/CLAUDE.md`, `ui/CLAUDE.md`, `snotra-settings/CLAUDE.md`）に記載している
- 同一ロジックの繰り返しは2回まで許容し、3回目で抽出を検討する。無理な抽象化よりも多少の重複を許容する
- **ドキュメント間でも DRY を守る。** 同じ事実（モジュール一覧・コマンド・契約など）を複数の `.md` に書かない。SSOT を1箇所に決め、他からは参照する。二重管理は片方の更新漏れで必ずドリフトする。「同期を頑張る」のではなく「重複を排除する」のが根治である

## YAGNI

- 使う予定だけの抽象化（不要な trait / generics / レイヤー）を導入しない
- 現在の要求範囲を超える機能追加を行わない
- 拡張性よりも、現要件での単純さと可読性を優先する

## ドキュメントとコードの分担（陳腐化の予防）

散文ドキュメント（`SPEC.md` / `docs/architecture.md` 等）の陳腐化は、コードの精密な事実（式・バイト形式・フィールド列挙・実装機構名）を散文へ写経した箇所から生じる。#404 / #410 で是正したドリフトの大半がこのパターンだった。「ドキュメント間でも DRY」の原則をコード↔ドキュメント間にも広げ、そもそも写経しないことが根治となる。

- **ドキュメントには「なぜ・何を・全体構造（intent）」を書き、精密な事実はコードを SSOT として参照する。** ドキュメントの役割は意図・目的・全体像のオリエンテーションである。式・ワイヤーフォーマット・列挙・機構名は再記述せず、それを担うコード（`icon.rs::encode_batch_binary` の doc-comment、`TabId::ALL` など）を参照先にする。`architecture.md` が既に実践している「各 `CLAUDE.md` を SSOT とし、自身には重複を持たない」方式を、精密事実にも拡張する
- **参照が成立するには、参照先に正本コメントが必要である。** インラインコードしかない箇所（例: `shouldShowResults` memo）を参照するなら、その場所へ「intent と式」を記した正本コメントを置き、SSOT として指名する。精密事実とその理由がコードの同じ場所に同居する形になる
- **生成（doc-gen）より参照を既定にする。** コードコメントからのドキュメント生成は、ツール固定費が便益を上回る規模（横断ドキュメント中の精密事実は十数件程度）では割に合わない。参照を既定とし、対象が大量化して初めて生成やマーカー同期を検討する
- **判定基準: 「この一文は、振る舞いを保つリファクタを生き延びるか？」** 生き延びるもの（intent・why・構造）はドキュメントに書く。生き延びないもの（機構名・バイト形式・式）はコード内コメントに置くか参照にする。一文の中に残す部分と移す部分が混在することもある。例えば「indexing 中は隠す。ただし tool / folder / instant は除く」は intent なのでドキュメントに残し、`results().length > 0 && …` のような式はコードに移す
- **やむを得ず再記述する精密事実は、機械検査で保護する。** 列挙のように再記述が避けられないものは、ドキュメントとコード（`TabId::ALL` 等）の一致をアサートするテストを書き、サイレントドリフトを CI の red で検出する
- コメント自体の書式・粒度・定型ラベルは `docs/comment-guidelines.md` を SSOT とする（本節は「ドキュメント ↔ コードの分担」の SSOT）

## 設定由来の派生状態（キャッシュとして扱う）

config から導出する派生状態は「キャッシュ」とみなす。#347 / #348 の教訓に基づく。

- **既定は live-read とする。** 毎操作で config から計算し直す。計測して高コストだと判明したものだけをキャッシュ化（長命オブジェクトへの焼き込み）する。安価なものを焼き込むと、設定変更が反映されないドリフトを生むだけになる
- **キャッシュ化するなら、その無効化の所有者を必ず決める。** 設定変更時に誰が再構築を責任もって行うかを明確にする。所有者不在は設定変更の取りこぼし・データ損失の温床になる（例: `HistoryStore.top_n` の焼き込みドリフト、index の lost-update 窓）
- **「setter で追従」より「そもそも焼き込まない」を優先する。** live-read にすれば desync を構造的に発生不能にできる場合が多い（例: `HistoryStore.top_n` を live-read 化し、フィールド自体を削除した）
- 詳細設計は `docs/design/2026-05-31-coherence-staleset.md`（config↔派生状態コヒーレンシ / StaleSet 契約）を参照

## 状態を散在フラグで表さない（単一の導出源に集約する）

複数の boolean / nullable フラグの組み合わせで「モード」や状態を暗黙に表すと、排他律・優先順位・各状態での振る舞いがコード中の複数ガードに散らばる。各ガードが優先度を再導出するため、状態を1つ追加したときに全ガードの更新を忘れると、不変条件が気付かれないまま破れる。

この教訓は、検索モードの `folder` / `tool` / `instant` / `indexing` を散在する `if (toolSelectionState() || instantCommandMode())` 群から `viewKind()` / `interpKind()` の二軸導出へ集約した経験から得た。

- **散在ガードを見たら問う:** これは単一の概念か（→ 1つの判別子・導出メモ / 関数に集約する）、それとも直交する複数軸か（→ 各軸を名前付きで分離する）。フラグの組み合わせは、本来 discriminated kind か直交軸であることが多い
- **優先度・排他律は導出源の一箇所だけに書く。** 各ガードはその導出を消費するだけにする。更新箇所を一点に集約すれば、網羅 switch と `assertNever` で「状態追加時の分岐漏れ」をコンパイラに検出させられる
- **オーバーレイ状態を軸に混ぜない。** 相互排他なモードは discriminated kind にし、どのモードにも重なりうる状態は独立フラグのまま分けておく
- **仕様との一対一対応を保つ。** 仕様側に優先順位・状態遷移が記されているなら、実装の導出源がそれと対応するようにする（例: SPEC §8.6 状態図・§18.5 優先度 ↔ `viewKind()` の射影順）。整合検証は `/state-check` で行う
- **SSOT を担う状態を削除するときは、その役割の移管先を明示する。** ある状態（特に複数箇所から読まれる派生の源）は、値だけでなく「ある判定の唯一の評価点」という SSOT 役割を暗黙に担っていることがある。これを消すと、判定述語が消費側に再び散在しうる。削除前に「この状態が単一情報源だった判定は何か、削除後は誰が担うか」を問い、必要なら述語を共有ヘルパへ抽出して SSOT を移管する（例: instant 検出ラッチを廃止したとき、検出述語を `isInstantPrefix` へ抽出し、`interpKind` と query effect の SSOT にした）

## 構造的設計原則と強制の階梯

2026-07-05 の構成調査で挙がった課題群（#426〜#442）を抽象化すると、5つの構造的原因に還元された。既存の原則（DRY・設定由来の派生状態・散在フラグ）を補完する横断原則としてここに明文化する。

前提として、不変条件・規則を守らせる手段には強さの序列（強制の階梯）がある:

> 構造で不可能にする（型・導出・単一通過点） ＞ コンパイルで検出（compile-fail・`#[must_use]`） ＞ テスト・CI で検出 ＞ チェックリスト・レビューで検出 ＞ 書き手の記憶

設計・レビューでは「この規則はいまどの段で守られており、1段上げるコストは見合うか」を問う。

- **1. Derive, don't duplicate — 同じ知識の第2表現を手書きで並行維持しない。** タブ対応表・デフォルト値・派生 Vec 群・翻訳テーブル・バージョン表記のように、1つの知識が複数の表現を持つ場合は、1つを正として他を導出（builder 集約・テーブル駆動・宣言的マップ）する。手書きの並行維持は追加時の更新漏れを必然にする。DRY 原則の「ロジックの重複」から「表現の並行維持」への拡張（#436, #437, #438, #439, #441）
- **2. 不変条件は単一の通過点（choke point）に閉じ込める。** 「世代カウンタは必ず更新する」「通知→世代→クリアの順で行う」のような規則が複数コードパスに散在すると、正しさが書き手の記憶に依存する。規則を1つの関数・型（世代更新ヘルパ・ライフサイクル高階関数・正規化済み型）に閉じ、違反をそもそも書けなくする。「散在フラグ」原則の状態版に対する、操作・手続き版（#428, #431, #435, #439）
- **3. 純ロジックと副作用の分離をフラクタルに適用する。** crate 境界（snotra-core / src-tauri）で成立している functional core / imperative shell を、ファイル・関数のレベルにも同じ形で適用する（`working_set.rs` の純関数抽出が成功例）。判断（純粋・テスト可能）と実行（副作用）が1関数に混在して肥大したら分割の合図（#431, #433, #435, #436）
- **4. テスト可能性は機能ではなく横断アーキテクチャ要件である。** 検証の死角は「テストが書かれていない」箇所ではなく「テストが書けない/回らない構造」の箇所に生まれる。永続化経路は dir 注入可能に、全 crate のテストは CI で実行、全 UI 層に最低1つの検証ハーネス——を構造の受け入れ条件とする（#426, #427, #429, #432, #440）
- **5. 境界を跨ぐ契約は1箇所で規約として定義する。** IPC 返り値・翻訳カタログ形式・プロセス間ファイルプロトコルのような境界契約が「各実装の集積」として暗黙に存在すると、表現の系統が分裂する。契約を規約として1箇所に書き、実装はそれに従う（#434, #438, #442）
- **6. 検出は構造化された信号で行い、テキストは証拠に留める。** 「成功したか」を判定するのに出力テキストを使うと、切り詰め・書式変更・ロケールで検出が壊れる。判定には exit code・型・戻り値のような構造化された信号を使い、テキストは人間/エージェントが読む証拠として添える。**どこで切っても取りこぼすものを検出手段にしてはならない。** PostToolUse hook は `cargo test 2>&1 | tail -5` の出力有無で合否を伝えようとしていたが、成功時にも 5 行出るうえパイプ終端の `tail` が exit code を握り潰していた。検出を exit code へ移し、テキストは切り捨て可能な証拠に降格した結果、切り捨て通知も件数カウントも不要になった（#471）。**さらに、判定単位は「文字列が現れたか」ではなく「どの構文的位置に現れたか」で定義する。** 「言及」と「実行」を区別しない検出器は必ず誤爆する——PreToolUse hook は payload 全体を grep していたため `description` や `grep "gh pr create" f` の引数文字列で発火し、バグを説明する行為そのものを妨げた。判定を「コマンド位置に現れる呼び出し」へ移して根治した（#482）。同型の誤爆は `config-warn` がファイル内容中の `config.toml` に反応した件（#471）にもあり、この hook を守るために書いたカナリアテスト自身も、コメント中の `process.exit()` に反応して赤くなった
- **7. 失敗方向は、個別のハンドリングではなく既定値に埋め込む。** 「異常時にどちらへ倒れるか」を経路ごとの `if` で書くと、経路を 1 本足したときに倒れる向きが変わる。**安全側を既定値そのものに置き、安全と積極的に確認できた経路だけがそれを覆す**構造にすれば、未知の経路・将来の経路・例外経路がすべて自動的に安全側へ倒れる。PreToolUse hook は `exit 2` だけがツールをブロックし、`exit 0` は許可、それ以外の非ゼロ（Node が未捕捉例外で返す **1** を含む）はコマンドをそのまま実行する。ゆえに `pre-bash.mjs` は既定の `process.exitCode` を 2 に置き、許可が確定した経路だけが 0 を書く（#482）。これは階梯でいえば「構造で不可能にする」段であり、「全経路で fail-closed を忘れない」というチェックリスト段より 2 段上にある。**冗長に見える既定値は、冗長でなくなる日のために存在する**ため、その除去・反転を検知するテストを併せて置く
- **チェックリストは「構造が規則を吸収できていない」ことの診断信号である。** AGENTS.md・各 CLAUDE.md に専用チェックリストや注意書きが必要な箇所は、階梯の下段で守られている箇所の正確な地図になっている。構造が規則を吸収したら（例: 派生 Vec 生成の builder 集約後）、対応するチェックリストを削除する——ドキュメントが軽くなることを設計改善の検収条件とする
- **やりすぎの境界（YAGNI）:** 原則の教条的適用（trait 化・proc-macro 生成・既存契約の一斉移行）より、choke point 関数1つ・テーブル1枚・新規分からの規約化で 80% を取る。「無理な抽象化よりも多少の重複を許容する」は本節にも適用される

## デバッグ・バグ修正

- バグ修正時は、コードを書く前に根本原因を一文で明示する
- 根本原因の説明には「壊れた不変条件（何が常に成り立つべきだったか）」を必ず1つ含める
- 最初の修正案が失敗した場合、同じ深さで別の推測を試みるのではなく、より深い調査に切り替える
- バグ修正時は、修正対象のパターンをコードベース全体で検索し、同一パターンが他にも存在しないことを確認してから完了とする（計画時の影響列挙版は `AGENTS.md` ステップ 2「同一パターン全コードパス検索」）
- `tauri.conf.json` や platform 固有ファイルに設定を追加する際は、その設定が Windows でサポートされているか事前に確認する（例: `backgroundThrottlingPolicy` は Windows 非対応でビルドエラーになる）
- 修正案が API 境界をまたぐとき、「呼び出し側パッチ」と「API 側で責務を完結させる修正」の両案を比較し、後者を優先する
- issue や plan.md の前提——特に **能力**（何を受け付けるか）・**セキュリティ防御**・**根本原因診断**——は、実装前に「対応する実行コード」と「兄弟機能の既存挙動」で裏取りする。issue 作者がユーザー本人でも前提は誤りうる。例:「instant の exe を `.exe` 限定にすれば防御になる」は実際には `Command::new` が `.bat`/`.cmd`/`cmd.exe` を受理して誤り（#395）。「footer 赤枠は id 重複」という診断も真因は id 不安定性で `push_id` は効かず（#456）。`/plan-review` のサブエージェントは作者の枠組みに anchor しやすいため、盲点の是正には実証が要る。外部 issue・上流仕様を根拠にするときの時系列・最終 maintainer 回答の確認は `start-issue`（#565）が担う
- 乖離（実装とドキュメント・二つのコードパス等の食い違い）を解消するときは、issue が提示する「片方に揃える」二択を鵜呑みにせず、まずコードで前提を裏取りする——一方が呼び出し元の無い死蔵コードなら、**削除**が乖離の根本を断つ最小解になりうる（#409。選択肢空間は前提の裏取りで広がる）。削除の安全性は静的 grep + 独立再導出 + **compile/typecheck を「死蔵検出器」として使う**（live import が残れば module-not-found で落ちる）の独立経路で裏付ける
- 競合しやすい一時状態（通知・ローディング・遅延処理）を導入する場合は、タイマーや購読のライフサイクルを単一管理し、再実行時に必ず前回のハンドルを破棄する
- ガード（ロック・フラグ・CAS）を追加するときは「どの関数を守るか」ではなく「どのリソースを守るか」で設計する。同じリソース（ファイル・共有状態）を触る経路が複数あれば、全経路が同じガードを通るようにする。関数単位のガードは別経路の追加時に素通りされる
- テストや挙動の red を自分の変更による回帰と断定する前に、変更前のベースライン（`main` 等）で同じ条件を実行して A/B 比較する。両者が一致すれば、その差分は原因ではない（既存バグまたは環境要因）。検索・索引など自分が触った領域の失敗ほど、思い込みを排してベースラインと突き合わせる。性能評価も同様で、同一マシンでの A/B でのみ退行を判定する（異なる環境の記録値との比較で判断しない）
- 層をまたぐ不具合は、上位層（UI）の症状から推測せず、最下層を直接観測して切り分ける（backend IPC を直接呼ぶ、アプリにロード済み状態をダンプさせる等）。release ビルドではフロントの `trace()` がデッドコード除去されるため、上位層のログに頼らない観測手段を用意する
