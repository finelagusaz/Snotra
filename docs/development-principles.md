# 開発原則

このプロジェクトで共有する設計・実装の原則。エージェント・人間を問わず適用される。

**条項は「命令 1 文 ＋ 観点」で書き、経緯・数値・物語は `#NNN` の issue へ置く**——issue が事例集である。ただし**前提と境界条件は条項の側に残す**（落とせば、本書自身が戒める偽の全称になる）。

## 局面 → 立てる問い

節を読む前に問いを立てる。答えが対応する節にある。

| この局面に来たら | 立てる問い | 節 |
|---|---|---|
| 何かを消す・移す | 消す差分の中で**新しく書いた一文**はどれか | `docs/development-principles.md`「撤去（消す変更）の作法」 |
| 散文に精密な事実を書く | この一文は、振る舞いを保つリファクタを生き延びるか | `docs/development-principles.md`「ドキュメントとコードの分担（陳腐化の予防）」 |
| config から状態を導いて持つ | 既定の live-read で足りないか。キャッシュ化するなら無効化の所有者は誰か | `docs/development-principles.md`「設定由来の派生状態（キャッシュとして扱う）」 |
| config を足す・既定値を書く | この値の消費者は誰か。導出は 1 経路か | `docs/development-principles.md`「config の値は到達性の検出器を持たない」 |
| フラグ・モードを足す | 単一の概念か、直交する複数軸か | `docs/development-principles.md`「状態を散在フラグで表さない（単一の導出源に集約する）」 |
| 規範に条項を足す・書き換える | この面の役割は読者に行動を求めるか。リードを読んだだけで次の動作が決まるか | `docs/development-principles.md`「規範の書式は文書の役割から選ぶ」 |
| 規則を守らせたい | いまどの段で守られており、1 段上げる費用は見合うか | `docs/development-principles.md`「構造的設計原則と強制の階梯」 |
| 「検知手段が無い」と書きかけた | 検知可能になる設計へ変えられないか | `docs/development-principles.md`「構造的設計原則と強制の階梯」 |
| 検査・検証手段を新設する | その手段は何を見ていないか。出力は消費する層まで届いているか | `docs/development-principles.md`「検証の層と、層と層の隙間」 |
| 網羅性が要件 | その一覧の母集団を誰が知っているか | `docs/development-principles.md`「列挙の完全性」 |
| バグを直す | 壊れた不変条件は何か。この修正は何を持ち込んだか | `docs/development-principles.md`「デバッグ・バグ修正」 |
| 案の採否・欠陥の有無を実測で決める | 対照列は在るか（勝敗の比を分解する／陰性を読めるようにする） | `docs/development-principles.md`「デバッグ・バグ修正」 |

「主張は代理でなく対象そのもので測ったか」は全タスクに効くため `AGENTS.md`「検証の作法（全タスク共通）」が持つ。

## KISS

- `main.rs` に業務ロジックを増やさない
- 責務を跨ぐ実装をしない
- 新規コードは既存のファイル構成・命名規則・スタイルパターンに合わせる。独自パターンを導入する前に、既存パターンの利用を検討する

## DRY

- 責務の集約先は各サブディレクトリのドキュメント（`snotra-core/CLAUDE.md`, `snotra-egui-runtime/CLAUDE.md`, `src-tauri/CLAUDE.md`, `snotra-settings/CLAUDE.md`）に記載している
- 同一ロジックの繰り返しは 2 回まで許容し、3 回目で抽出を検討する。無理な抽象化よりも多少の重複を許容する
- **ドキュメント間でも DRY を守る。** 同じ事実を複数の `.md` に書かない。SSOT を 1 箇所に決め、他からは参照する。「同期を頑張る」のではなく「重複を排除する」のが根治である

## YAGNI

- 使う予定だけの抽象化（不要な trait / generics / レイヤー）を導入しない
- 現在の要求範囲を超える機能追加を行わない
- 拡張性よりも、現要件での単純さと可読性を優先する

## 撤去（消す変更）の作法

YAGNI の実行面。**被依存ゼロの対象ではコンパイラが盲になる**ため、拾えるのは手の列挙と最終 grep だけである。

- **消す変更の中で「新しく書いた 1 文」は、削除ではなく新規記述である。** 削除の diff では消したことに注意が向き、書き足した主張の検算が抜ける。**残す記述に手を入れたら、その一文は測る対象になる**（#660）。引用位置は行番号ではなくシンボル名・見出し名で書く——行番号は書いた時点で既にずれていることがある
- **移設は削除ではなく差し引きである。** 削減幅を見積もるなら、移設先への追記と跡に残すポインタを引いてから言う（#827/#830 は −28% 見積もりに対し実測 −19.7%。同一サイクルで 2 度、書き足しを引かずに数字を出した）。機構化（散文 → スクリプト）でも呼び出し 1 行と契約への参照は残る
- **移設は貼り付けではなく差分の抽出である。** 移す前に既存の正本を grep し、既にある事実は参照へ落として「その場所にしか無い部分」だけを移す（#660 で同一事実の 4 箇所目を作った）
- **自分の変更が偽にした記述・作った矛盾は「範囲外」に置けない。** 判定は「存在しなくなるものへ読者を送るか」「現在形の主張が偽になるか」であり、歴史を述べて真のままの記述は残す（#660）
- **旧 API を消すとき、compile-fail が名指しするのは「コード参照」だけである。** 被依存があっても盲点は残る（#752 はコンパイラが 5 箇所、grep 実測は 16 箇所）。**名前で参照する文書は grep で数え、「歴史的言及として残すもの」と「現在形で腐るもの」を仕分ける**——ADR と設計書は当時の決定文脈ゆえ旧名のままでよく、生きた文書は「旧 X は Y へ吸収」と書けば真のまま残る
- **公開面を狭めるときは、狭めた後に残る呼び手を数える。** 製品の呼び手がゼロでテストだけが残るなら `pub(crate)` では足りない——非テストのターゲットで `dead_code` が立ち、`-D warnings` の下では**狭める変更そのものが通らない**。**`#[cfg(test)]` で閉じるほうが強くもある**（製品ビルドにシンボルが存在しないので、可視性の違反ですらなく未定義メソッドになる）。#1123 では機構自身が書き残していた撤去手順が `pub(crate)` を指定しており、そのままでは実装が止まった——**撤去条件は書いた時点の想定であって、実行してみた結果ではない**
- **「これは X が持つから消す」と書くときは、X の母集団が元の観点を覆っているかを読んで確かめる。** 覆っていなければ、その差分は**どの検査にも属さなくなる**（#764）。移送先が**実施の有無を観測できる形**を持つかも見る——持たない場所へ移した責務は沈黙する

## ドキュメントとコードの分担（陳腐化の予防）

散文ドキュメントの陳腐化は、コードの精密な事実（式・バイト形式・フィールド列挙・実装機構名）を散文へ写経した箇所から生じる（#404 / #410 で是正したドリフトの大半）。「ドキュメント間でも DRY」をコード ↔ ドキュメント間へ広げ、そもそも写経しないことが根治となる。

- **ドキュメントには「なぜ・何を・全体構造（intent）」を書き、精密な事実はコードを SSOT として参照する。** 式・ワイヤーフォーマット・列挙・機構名は再記述せず、それを担うコード（`TabId::ALL` など）の doc コメントを参照先にする
- **参照が成立するには、参照先に正本コメントが必要である。** インラインコードしかない箇所を参照するなら、その場所へ「intent と式」を記した正本コメントを置き、SSOT として指名する
- **生成（doc-gen）より参照を既定にする。** 横断ドキュメント中の精密事実が十数件程度の規模では、ツール固定費が便益を上回る。対象が大量化して初めて生成やマーカー同期を検討する
- **判定基準:「この一文は、振る舞いを保つリファクタを生き延びるか？」** 生き延びるもの（intent・why・構造）はドキュメントへ、生き延びないもの（機構名・バイト形式・式）はコード内コメントか参照へ。一文の中に残す部分と移す部分が混在することもある
- **やむを得ず再記述する精密事実は、機械検査で保護する。** 列挙のように再記述が避けられないものは一致をアサートするテストを書き、サイレントドリフトを CI の red で検出する
- **責務の「所在」を書いた散文は、移設で偽になる。しかもシンボル名の grep では届かない。** 消す変更では compile-fail が呼び出し元を挙げるが、移設では**コードは全部通る**まま散文だけが腐り、所在は略記・概念ラベルで書かれているため関数名では引けない（#749 は 4 箇所を直して実際は 6 箇所だった）。**探し方は概念語の grep である。** あわせて 3 点:
  - **新しく書いた所在の主張は、根拠となる関数の現在地で検算する**（#749 の新設 `//!` は自らの主張を反証していた・`docs/adr/ADR-window-coordinator-split-rule.md` 却下 5）
  - **移設で書き直す `//!` は、引き取った項目だけでなく手放した項目も引き直す**（#666 は**残った側**が出ていった項目を自分のものとして数えた）
  - **訂正した段落は、diff ではなく現物を読み直す**——1 つのラベルを潰すと同じ段落の別のラベルが context 行に沈み、差分だけを見るレビューは「訂正済み」と判定する（#755/#801 の 4 例目はそれで 1 ラウンド生き延びた）
- **規律の宛先（どの錠か・どの層か）を移すとき、その規律が挙げる「なぜ」も測り直す。** 宛先が変われば**害の種類が変わりうる**——#1123 は config の読みを engine の `Mutex` から `RwLock` へ移し、規律の文（「read guard を握ったまま `engine.lock()` を要求するな」）は真のままだったが、理由は「待ちが両方に乗る」＝加算的な遅延から**逆順のデッドロック**へ変わっていた。**遅延なら読者は天秤にかけ、デッドロックなら絶対に避ける**——文が真でも拘束力が違う。しかもこの文言は移設の 3 サイクル前から在り、**契約を 1 か所へ集約した当の改稿で据え置かれた**（集約は「書き直す機会」に見えて、実際には「写す作業」になりやすい）
- コメント自体の書式・粒度・定型ラベルは `docs/comment-guidelines.md` を SSOT とする（本節は「ドキュメント ↔ コードの分担」の SSOT）

## 規範の書式は文書の役割から選ぶ

**行動形**は読者が次に取る動作で終わる形（`config の読みは read_config を通す`）、**事実形**は断定の繋辞で終わる形（`Layer 1 は best-effort である`）。読んで次の一手が出るのは前者だけである。

- **書式は候補であって規則ではない**——役割から書式は一意に決まらない。反例が実在する: 「実装契約」の `docs/hooks.md` に完全な行動形の条項があり、「運用ガイド」の `AGENTS.md` は表だけでなく順序付きのワークフローを持つ。**条項ごとに裁定する**（面ごとに決めない）
- **裁定は分類ではなく操作で行う（書き換えテスト）**——条項を `A のときは B する。C が起きたため（#NNN 実測）` の形へ実際に書き換えてみる。**これが判定するのは「書き換えられるか」であって「書き換えるべきか」ではない**（ほとんどの事実形は変換できてしまう）ので、併せて 2 つを問う: (1) その面の役割が読者に行動を求めるものか、(2) 書き換えると失われる保証があるか——射程宣言のように「逸脱の明記と対で初めて真になる」形は、片方だけ書き換えると全称が実装より強くなる
- **書き換えは参照を壊す**——条項の太字リードは `G-heading-refs` のアンカーであり、照合は前方一致である。頭を変える書き換えは着地していた参照を落とす（`97796aa` がリード 1 本の書き換えで参照 1 件を壊した実例）。**同じ変更の中で随伴修正する**。ただし同検査は正準形しか見ないので、散文形と意味依存は `.claude/rules/governance-docs.md`「ガバナンス文書の参照と命名のルール」が要求する独立再導出で拾う

| 役割 | 書式の候補 |
|---|---|
| 運用ガイド・開発プロセス（常時ロード） | トリガー → 行動／参照先 |
| 編集の瞬間の手助け（`.claude/rules/`） | `A のときは B する。C が起きたため（#NNN 実測）` |
| 開発原則・判断の型（本書） | 局面 → 立てる問い |
| モジュール固有の不変条件 | 行動形 + 射程の明示 |
| プロダクト知識（地図） | 構造を記述する。**行動形にしない**（#326 が二重管理をドリフトの根治として撤去した面である） |
| 改修者向けの実装契約（`docs/hooks.md`） | 射程の宣言と、その逸脱の明記の**対**。片方だけ書き換えない（当該行は #768 を名乗り、入れたコミットは #774） |
| コマンドリファレンス | 索引 + 行動形 |
| 様式規約 | 様式を規定する |

**役割の出所は 1 か所ではない。** `AGENTS.md`「ドキュメント参照」が大半を持つが、常時ロード面自身と `docs/hooks.md` の役割は同節に行が無い（後者はルート `CLAUDE.md`「フック」が持つ）。

**行動形／事実形のずれを見るゲートは無い。** 語形では割れないため作れない（否定形の「禁止」と「事実」は末尾の形が同じで、独立に書いた 4 本の述語がいずれも一点に収束しなかった・2026-08-22 実測）。計器を置くかは未決である。経緯と、この節が直そうとしている到達性の実測は `docs/superpowers/specs/2026-08-22-norm-format-by-role-design.md`。

## 設定由来の派生状態（キャッシュとして扱う）

config から導出する派生状態は「キャッシュ」とみなす（#347 / #348）。

- **既定は live-read とする。** 毎操作で config から計算し直し、計測して高コストだと判明したものだけをキャッシュ化する。安価なものを焼き込むと、設定変更が反映されないドリフトを生むだけになる
- **キャッシュ化するなら、その無効化の所有者を必ず決める。** 所有者不在は設定変更の取りこぼし・データ損失の温床になる
- **「setter で追従」より「そもそも焼き込まない」を優先する。** live-read にすれば desync を構造的に発生不能にできる場合が多い
- 詳細設計は `docs/design/2026-05-31-coherence-staleset.md`（config ↔ 派生状態コヒーレンシ / StaleSet 契約）

## config の値は到達性の検出器を持たない

コードの他の面には「届いていないと壊れる」機構がある——private / `pub(crate)` の関数は呼ばなければ `dead_code`、型は変えれば下流が compile-fail、モジュール索引と文書参照は `governance:check` が照合する。**config のフィールドは、定義しても誰も読まなくてもコンパイルが通る。**

（関数の検出器にも穴はある——lib crate の `pub` 項目に `dead_code` は出ないため、`snotra-core` の `pub fn` は呼ばれなくても `-D warnings` を通る。config が特異なのは、**穴ではなく検出器そのものが無い**ことである。）

欠如は 3 つの形で現れる。いずれも「値が参照ではなく**写し**として流れる」ことの帰結である。

- **消費者ゼロ** — 写しがどこにも届いていない
- **導出が 2 経路** — 写しが 2 つあり、片方だけが変わりうる
- **既定値の偶然の一致** — 写しが 2 箇所にあり、たまたま等しい

**休眠を支えているのは、自動で回る検証が既定値の下でしか走らないことである。** 乖離を露出させる入力——ユーザーが既定と違う値を設定すること——は、放っておいて回る検証には現れない（`[visual].background_color` は描画経路の消費者がゼロだったが、既定 `#282828` が `CLEAR_COLOR` と一致するため正常に見え続けた・#802 で解消）。

**規範では止まらない。** 規範が効くのは変更者がその場所を通るときだけで、**config の写しは通らない場所に散る**——既定値を変える人は、それを写した先のファイルを開かない（#794 のホットキーは config 側の競合判定と platform 側の登録に別 parser があり、コメントで一致を要求してもなお乖離した。core の意味型を両方が消費する機構へ移して解いた）。ゆえに機構へ移す:

- **新しい config フィールドには、追加と同じ変更で消費者を与える**（作ることと使うことは別判断）。読まないなら理由をフィールドの doc コメントへ書く。機械検査（旧 G-config-reachability）は捕捉 0 件のまま検査側の表だけが腐ったため #894 で廃止した——**この規範だけが頼りである**
- **既定値のリテラルを写さない。** フォールバックの正本は各セクションの `Default` 実装であり、`.unwrap_or(600.0)` のような再手打ちは今日たまたま一致しているだけである（#680 / #795）。**ただし「同じ数」と「同じ概念」は別である**——読み元が違えば写しではなく、参照へ寄せると存在しない結合を主張することになる（`docs/adr/ADR-config-default-fallback-references.md`）
- **`Default` 実装自身も既定関数を呼ぶ形に揃える。** serde は「セクション欠落 → `Section::default()`」と「キー欠落 → `#[serde(default = "default_X")]`」の 2 経路を持ち、食い違うと**同じ既定が TOML の書き方によって変わる**（`config.rs` の `empty_section_deserializes_to_default_*` が一致を固定する）

同じ構造は config 以外でも起きる——値の**定義側**の機構と規範を扱うのが本節、同じ穴を**検証の地図**の上に置くのが「検証の層と、層と層の隙間」である。

## 状態を散在フラグで表さない（単一の導出源に集約する）

複数の boolean / nullable フラグの組み合わせで「モード」を暗黙に表すと、排他律・優先順位・振る舞いがコード中の複数ガードに散らばる。各ガードが優先度を再導出するため、状態を 1 つ追加したときに更新を忘れると不変条件が気づかれないまま破れる。実体は `src-tauri/src/egui_shell/search_state.rs` の `ViewKind`（軸1: ビュースタック頂点）と `QueryIntent`（軸2: 入力の意味）の二軸導出である。

- **散在ガードを見たら問う:** これは単一の概念か（→ 1 つの判別子・導出関数に集約する）、それとも直交する複数軸か（→ 各軸を名前付きで分離する）
- **優先度・排他律は導出源の一箇所だけに書く。** 各ガードはその導出を消費するだけにする。更新箇所を一点に集約すれば、網羅 `match` で「状態追加時の分岐漏れ」をコンパイラに検出させられる
- **オーバーレイ状態を軸に混ぜない。** 相互排他なモードは discriminated kind にし、どのモードにも重なりうる状態は独立フラグのまま分けておく
- **仕様との一対一対応を保つ。** 仕様側に優先順位・状態遷移が記されているなら、実装の導出源がそれと対応するようにする（`SPEC.md` §8.6 状態図・§18.5 優先度 ↔ `view_kind()` の射影順）。整合検証は `/state-check`
- **SSOT を担う状態を削除するときは、その役割の移管先を明示する。** ある状態は値だけでなく「ある判定の唯一の評価点」という役割を暗黙に担っていることがあり、消すと判定述語が消費側へ再び散在する。削除前に「この状態が単一情報源だった判定は何か、削除後は誰が担うか」を問い、必要なら述語を共有ヘルパへ抽出する

## 構造的設計原則と強制の階梯

不変条件・規則を守らせる手段には強さの序列がある:

> 構造で不可能にする（型・導出・単一通過点） ＞ コンパイルで検出（compile-fail・`#[must_use]`） ＞ テスト・CI で検出 ＞ チェックリスト・レビューで検出 ＞ 書き手の記憶

設計・レビューでは「この規則はいまどの段で守られており、1 段上げるコストは見合うか」を問う。以下は #426〜#442 の課題群を抽象化した構造的原因である。

- **1. Derive, don't duplicate — 同じ知識の第2表現を手書きで並行維持しない。** 1 つの知識が複数の表現を持つ場合は、1 つを正として他を導出（builder 集約・テーブル駆動・宣言的マップ）する。DRY 原則の「ロジックの重複」から「表現の並行維持」への拡張
- **2. 不変条件は単一の通過点（choke point）に閉じ込める。** 「世代カウンタは必ず更新する」のような規則が複数コードパスに散在すると、正しさが書き手の記憶に依存する。規則を 1 つの関数・型に閉じ、違反をそもそも書けなくする。「散在フラグ」原則の操作・手続き版
- **3. 純ロジックと副作用の分離をフラクタルに適用する。** crate 境界で成立している functional core / imperative shell を、ファイル・関数のレベルにも同じ形で適用する。判断（純粋・テスト可能）と実行（副作用）が 1 関数に混在して肥大したら分割の合図
- **4. テスト可能性は機能ではなく横断アーキテクチャ要件である。** 検証の死角は「テストが書かれていない」箇所ではなく「テストが書けない/回らない構造」の箇所に生まれる。永続化経路は dir 注入可能に、全 crate のテストは CI で実行、全 UI 層に最低 1 つの検証ハーネス——を構造の受け入れ条件とする
- **5. 境界を跨ぐ契約は1箇所で規約として定義する。** 境界契約が「各実装の集積」として暗黙に存在すると、表現の系統が分裂する。契約を規約として 1 箇所に書き、実装はそれに従う
- **6. 検出は構造化された信号で行い、テキストは証拠に留める。** 判定には exit code・型・戻り値を使い、テキストは人間/エージェントが読む証拠として添える。**どこで切っても取りこぼすものを検出手段にしてはならない**（#471）。派生する 2 つの具体則:
  - **パイプは exit code をパイプ末尾のコマンドのものへ置き換える**——`cmd | tail && next` は `cmd` が赤でも先へ進む（#812）。**禁止ではなく安全形を使う**（#858 で再発したのは代わりの手段を書いていなかったためである。規範は復帰手順とセットで書く）: 出力を絞りたいなら `set -o pipefail` を先に置く（`(exit 3) | tail -1` は 0 を返すが、pipefail 下では 3 を返す。成功時は素通りするので既存の形を壊さない）。**そもそも出力が数行のコマンドを絞らない。** この危険は Bash 固有で、PowerShell の `$LASTEXITCODE` は cmdlet を挟んでも保たれる
  - **判定単位は「文字列が現れたか」ではなく「どの構文的位置に現れたか」で定義する**——「言及」と「実行」を区別しない検出器は必ず誤爆する（#482 の PreToolUse は payload 全体を grep してバグの説明そのものを妨げた。判定をコマンド位置へ移して根治）
- **7. 失敗方向は、個別のハンドリングではなく既定値に埋め込む。** 経路ごとの `if` で倒れる向きを書くと、経路を 1 本足したときに向きが変わる。**安全側を既定値そのものに置き、安全と積極的に確認できた経路だけがそれを覆す**構造にすれば、未知・将来・例外の経路がすべて自動的に安全側へ倒れる（`pre-bash.mjs` は既定の `process.exitCode` を 2 に置く・#482）。これは「構造で不可能にする」段であり、「全経路で fail-closed を忘れない」というチェックリスト段より 2 段上にある。**冗長に見える既定値は、冗長でなくなる日のために存在する**ため、その除去・反転を検知するテストを併せて置く
- **8. 全称条件だけの検査は、集合が縮んだときに空振りする。守りたい要素は名指しする。** 「全エントリが deny」のような ∀ 条件は**要素が消えた形**に対して真のまま通る。ゆえに ∀ 条件には「非空」だけでなく**「守りたい要素が在る」という ∃ 条件を組にする**（#713 の `G-workspace-lints` は 1 行消えた形を緑で通した）。**カナリアが「消えたら困る識別子」そのものを持つのは写しではなく設計である**（`.claude/hooks/post-edit.test.mjs` の member 名ハードコードが先例）

### 検査・検出器を置くときの作法

- **「検知手段が無い」と書きかけたら、検知可能になる設計へ変えられないか先に問う。** 動かし方は 2 種——(a) 責務を検査可能な層へ移す（#654 は失敗文言の区切りをテスト不能な呼び出し側から文言テーブルの関数内へ移した）、(b) 観測点そのものを作る（同 #654 の env ハッチ `SNOTRA_EGUI_FAKE_UPDATE_FAILED`）。**残余の記録は最後の手段である**
- **新設する検査の期待値は、SPEC・契約と照合してから書く。** 実装より強い期待を書いた検査は設計どおりの挙動を FAIL と判定し、赤の信用を落とす（#749・#757 は受容済みのはみ出しを FAIL 条件にした）。受容残余を持つ挙動では、**残余の境界そのものを判定条件にする**。照合先は必ず現在の SPEC である——引いた条文自体が後の変更で消えることがある（当該条文は #835 で消え、境界は `SPEC.md`「4.5 最大列挙数」へ移った）
- **故障注入は、本来の回帰より強い変異にしてはならない。** 変異が本来の故障より強いと、縛れていない検査でも赤くなり「縛れている」と記録してしまう。**変異は「実際に起きた回帰の姿」に合わせる**——姿の正本は、その回帰を直したときの実測コメントである（#872 で同型を 3 回踏んだ）
- **変異は 2 方向へ入れる。** 「検査が狙う対象」を壊す向きと、**「検査が対象を見ているか」を壊す向き**（依存を素通しへ差し替える）。入力集合が空になる経路だけでなく**退化する経路**も疑う——非空のキャッシュに空の木を渡すと、木を引く実装と引かない実装が同じ答えを返し、母集団ゼロの検算では見えない（#872 反復 12。後者の変異で既存 222 本が緑のまま新設 1 本だけが落ちた）
- **逆向きも同じ強さである——注入が赤くならなかったことは、検査が縛れている証拠にも、その事故が起きえない証拠にもならない。** 系が構造的に故障を防いでいれば正しい姿の変異でも発火しない（#1004 H7 は 2 度失敗した: 消費して捨てる変異が coalescing と同じ結果になり、次に debounce 幅と検索時間が拮抗して追い越さなかった。worker へ人工遅延を入れて初めて発火した）。**「めったに起きないが起きたら深刻」を見張る検知器は、人工的にでも一度発火させるまで、発火しうるかが分からない**
- **検知器を足す前に、その検知器が単独で捕まえる経路を数える。** 既存の検査が捕まえる経路を除いて残るものが無ければ、それは検知力ではなく**保守の対象**である（#872 反復 12 は検知器の破綻を 3 巡続けて指摘され、毎回その検知器を直して新しい未検証の装置を投入していた。発火経路を数えたら守っていたのは 1 経路で、2 行の断言で刺せた）。「検知器が足りない」と読むのは誤診でありうる
- **拒否する機構の誤爆は一様でない——「拒否メッセージの復帰手順が適用できない誤爆」を別枠で探す。** 真陽性と誤爆の件数だけでなく、**誤爆した相手が示された手順で回復できるか**を問う。回復手段のない拒否は、規範を機構へ移した設計そのものへの信頼を落とす（#768。同型の非対称は自分の機構同士にも生じ、PostToolUse が出す再現コマンドを PreToolUse が拒んだ）
- **定数で分岐する実装では、fixture がその定数を跨いでいるかを測る。** 到達しているかだけでは足りない——塊の大きさ・バッファ長・閾値で分かれる実装は、跨がない fixture では片側が一度も走らない（#1056 は `KANA_CHUNK = 4096` に対し fixture が数件で、塊併合の順序保存も底上げも検証されないまま「A/B 突き合わせが捕まえる」と 4 か所へ書いていた）。**「到達していない」と「到達したが分岐を見ていない」は、塊が 1 つでも効く対照の変異が赤くなるかで切り分ける。** 跨ぐ fixture を置いたら、**定数はテストから参照させて値を写さない**——写すと定数を増やした日にテストが黙って射程を失う
- **既存の検知器へ「移設」するときも、移設先で発火するかを測る**（移設は新設と同じ検算を要する）。同 #1056 は余剰容量の検査を `capacity == n` の組からアリーナ用の組へ移したが、移設先の経路は確保が寸法ぴったりで**構成上つねに 0** になり、`shrink_to_fit` を外しても緑のままだった（伸長に任せる別経路の索引を fixture へ足して初めて発火した）
- **テストのために可視性を広げる弁明を doc に書いたら、切り口が対象と合っていない兆候である。** 代償は 3 つ——テストがファイルシステムを巻き込む・**型に無い契約**の観客が広がり新しい呼び出し自身がその規範の反例になる・doc が弁明を抱える。**純粋な導出（I/O 無し）を切り出してそちらを公開する**と 3 つとも同時に消える（#977）
- **「測ったが動かなかったので採らなかった」と残余へ記録するときは、0 を保証していたのが対象の性質か判定の構成かを書き分ける。** 前者なら記録は持つが、後者は**判定が広がった瞬間に沈黙で反転する**（#1095: G-stale-identifiers の「Rust のテストコードが語彙を寄付する穴は全セルで 0 件」は #885 当時の実測だが、0 を作っていたのは穴の性質ではなく**述語が lowercase snake_case を見ていなかったこと**で、#989 が述語を足した時点で 9 件へ反転していた。誰も測り直さないまま 5 か月緑だった）。**結論が正しいままでも理由づけだけが偽になる**——反転しても赤くならないので、気づく契機はその残余を読み直したときしかない

### 規範を書くときの作法

- **規範に条項を足す前に、その節が律する対象範囲（スコープ）が宣言されているか確かめる。** 検算の母集団は、自分が見ていた範囲ではなく**規範が名乗る範囲**である。スコープの無い規範では、既存条項が既に偽でありうる（#654 は `SPEC.md` §11 に宣言が無いため射程が `snotra-settings` へ及び、既存条項の時点で偽だった）。**スコープ宣言を先に置くと、新条項が真になると同時に既存の偽も消える**
- **全称・不在断定・数え上げは、確定の前に反証プローブを回す。**「何が増えたら/変わったらこの文は偽になるか」を 1 つ挙げる——挙がるなら、暗黙に数えているか前提を隠している。処置は 3 択: 挙がった条件を前提として書き添える／下限の主張（「少なくとも」「〜だけではない」）へ弱める／書かない。**想起や引用をプローブの実行の代わりにしない**——本則を引きながら書いた文書が偽の全称だった先例（#977）と、偽の全称を直した文が再び全称で偽になる連鎖（#1091 で 3 回）がある。検査を書く側の同型（∀ 条件に ∃ 条件を組にする）は「構造的設計原則と強制の階梯」に正本がある
- **チェックリストは「構造が規則を吸収できていない」ことの診断信号である。** 専用チェックリストや注意書きが必要な箇所は、階梯の下段で守られている箇所の正確な地図になっている。構造が規則を吸収したら対応するチェックリストを削除する——**ドキュメントが軽くなることを設計改善の検収条件とする**
- **規則を具体化するとき、閉じた形を開いた禁止の列挙へ替えない。**「読みへ渡すのは純 CPU だけにする」は閉じており、「`engine.lock()` を呼ぶな・I/O を取るな」は開いている——後者は「列挙にないものは書いてよい」と読める。#1123 のレビュー対応で実際にこの置き換えを行い、名指ししなかった他の錠を規則が禁じなくなった。**具体例は規則の下へ「とくに」として置く**（規則を例で置き換えない）。**委譲側が正本より広い契約を宣言していたら、狭めたのは正本の側である**——この退行はそこで露見した
- **やりすぎの境界（YAGNI）:** 原則の教条的適用（trait 化・proc-macro 生成・既存契約の一斉移行）より、choke point 関数 1 つ・テーブル 1 枚・新規分からの規約化で 80% を取る

## 検証の層と、層と層の隙間

階梯が「規則を**どの強さ**で守るか」を問うのに対し、ここは「その手段が**何を見ていないか**」を並べる。**コマンド・実行条件・どの変更でどれを回すかは `docs/build-commands.md`「変更後の検証チェックリスト（必須・スキップ不可）」が正本**である（ここに写しを置かない）。並べるのは**実行される検証**であり、型・`#[must_use]`・hook のような「走らせるまでもなく効くもの」は階梯が扱う。

| 層 | 手段 | 保証するもの | **見ないもの** |
|---|---|---|---|
| 純粋核のロジック | `cargo test`（`snotra-core` / `layout.rs` / `ime.rs` 等） | 入力 → 出力の変換 | **その出力が消費されているか** |
| egui の論理座標 | `cargo test`（`view.rs` の kittest・`run_pass`） | widget の構成・順序・論理位置 | **実ピクセルへの丸め・実フォント・DPI** |
| node の純関数 | `npm test`（vitest） | `scripts/` と hook の判定ロジック | それが実際に配線されているか |
| PowerShell の純関数 | `test:powershell` | 判定ロジック（色・幾何・trace 不変条件） | 実際の窓 |
| 起動と配線 | `smoke:startup` / `smoke:egui` | 起動・hotkey 登録・show/hide・trace 不変条件 | 見た目 |
| 実ピクセルの色 | `check:colors`（判定あり） | 宣言色が届いているか | 位置に紐付かない（クロス配線） |
| 実ピクセルの幾何 | `check:input-metrics`（**判定を持たない**） | 入力欄の縦位置の実測値 | 合否——読むのは人間 |
| 人間の目視 | `smoke:manual` | 総合的な違和感 | 実施の記録（残さないと未実施と区別できない） |
| 文書の整合 | `governance:check` | 参照・索引・命名の着地 | 意味の側（責務の妥当性等・受容する残余） |
| 文書の整合（編集時） | PostToolUse の reminder（**判定を持つが合否を持たない**・#1139） | 編集した 1 ファイルに帰属する索引漏れ・参照の不在を、**直せる時点で**知らせる | 削除・`governanceDocs` の外・`mod` 宣言・他文書からその文書を指す参照。**上の層の代わりにはならない** |

**穴は層の内側ではなく境界に空く。** 各層は自分の担当を保証するので、抜けるのは「層 A の出力が層 B へ届いているか」である。2026-08-11 に 2 つ実測した。

- **純粋核 → 描画**: `ime::active_range_chars` は変換の正しさをテストで固定しながら、egui が `legacy_visuals` の下でその値を参照せず、**検査 2 本が緑のまま機能が丸ごと死んでいた**
- **論理座標 → 実ピクセル**: 入力欄の縦中央寄せは論理座標では 8 フォントすべて対称と測れたのに、**実機では 4 種で 1px ずれていた**（`raster.rs` がカバレッジ AA を持たないため・`snotra-egui-runtime/CLAUDE.md`「不変条件」）。**人間の目が唯一の検出器だった**

**ゆえに層を選ぶときは 2 つ問う。** (1) この変更は何を変えるか（値の計算・widget の構成・窓のライフサイクル・色・縦位置） (2) **その出力を消費する層まで届いているか**。(2) を飛ばすと「全部緑なのに動いていない」へ落ちる。

**判定を持たない道具を層に数えてよい。** `check:input-metrics` は合否を言わないが、**その層が無ければ差分は誰にも見えない**。フォント依存の 1px のように残余が構造的なとき、閾値を置けば「常に緑」か「常に赤」へ倒れる——**永久に赤いゲートはゲートが無いのと機能的に同じである**（`docs/adr/ADR-declared-colors-over-modal-color.md`）。合否を人間へ残す判断は、層を持たないことと同じではない。

**母集団を持つ検査では、母集団そのものが壊れる。** ソーステキスト検査（自分の属する production のソースを読み、目的の呼び出しが在ることを assert する形。テスト席を作れない型の呼び出し点を守る唯一の手段になる）が典型である。**母集団の取り方は 1 ファイル（`include_str!`）とディレクトリ（実行時の `read_dir`）の両方が実在する**（後者は #1201）。**どちら向きの壊れ方で沈黙するかを決めるのは、切り出し器ではなく切り出した結果を食う述語である**——広がる側で沈黙する述語と、狭まる側で沈黙する述語がある。ゆえに切り出しの正しさを述語と切り離して問うことはできない。**この裏返りは Rust と `.mjs` の双方で観測した**——母集団を切り出して述語へ渡す形であることが共通点で、言語ではない（2 実例からそれ以上は言えない）。

切り出した母集団 P と、本来見るべき本体 B を分けて書くと、要求は述語の向きで裏返る。**以下は観測された実例であって、述語の形はこれで尽きない**——新しい形を足すときは「どちら向きの誤りで、この述語は真へ倒れるか」を自分で問う。

- **存在形（`P.contains(x)`）は `P ⊆ B` を要求する。** P が B を越えて広がると他所の文字列で真になり沈黙する。**探す綴りが同じファイルに逐語で実在する**（assert のリテラルがまさにそれである）ことに加えて、**その綴りが飲み込まれる側に在る**という位置の前提が要る——アンカーより後ろに `mod tests` が在る現在の並びがそれで、テストモジュールを前へ置けば、**本体の呼び出しが消えた状態で** EOF まで伸びても綴りは飲み込まれず赤になる（呼び出しが在るうちは、どちらの並びでも真であってよい）。**上界を縛る assert がこれを塞ぐ**: 終端が実際に見つかったこと・アンカーが期待どおりの字下げから始まっていること
- **否定形（`!P.contains(x)`）は逆に `P ⊇ B` を要求する。** 切り捨てた領域に禁止語が在っても真になるので、**狭まる側で沈黙する**。**目印（canary）はこの下界のごく弱い版（`|P| > 0`）にすぎず、「P が途中で切れていない」は言わない**——2026-08-17 に rustc で対照を取り、canary の後・禁止語の前で切断した母集団に対して否定形は緑、同じ切り方で存在形は赤だった（#1112）
- **一致形（数え上げが宣言側と一致すること）は、広がった領域が要素を 1 つでも足せば赤になる。** 沈黙が残るのは増減が釣り合うときである——`egui_shell/view.rs` の `assert_read_once_in_this_file` は母集団がファイル全体なので、production の読みが消えることと doc コメントに綴りが現れることが釣り合えば緑が成立する（正本は同関数の doc。いまその側を支えているのは rustc の束縛であってこの検査ではない）

**ゆえに否定形からは切り出しを取り除ける。** 要求が `P ⊇ B` である以上、**守りたい本体が母集団に入るファイルのどれかに在るなら、母集団全体は B の上位集合である**——切らなければ下界は構成から満たされ、切り詰めという事象そのものが無くなる（**本体が母集団の外へ移りうる検査ではこの前提が外れる**）。**この但し書きは弱まったが消えていない**——#1201 が母集団を 1 ファイルからディレクトリへ広げたことで「隣の子モジュールへ移る」形では外れなくなったが、ディレクトリの外（親モジュール・サブディレクトリ）へ移る形では今も外れる。**下界の根拠がファイル単位から母集団単位へ移っただけである。**#1112 はこの形で `owners_of`（出現をファイル全体から列挙し、直前の字下げ 4 の `fn` ヘッダへ帰属させる）へ移した。**代わりに引き受けるものがある**——母集団が広い分「対象が 1 つも認識されていない」は起こりうるので、canary の役はアンカーがヘッダとして実在することを名指す assert が引き継ぐ。

**ただし「切らなければ安全」ではない。** 切り出しを外しただけの `!src.contains("禁止語")` は、**同じファイルにその綴りの正当な出現が在れば永久に赤くなる**——#1112 の当該ファイルには `read_config(` が対象外の経路（`lang()`）で、`self.indexing()` が起動の入口の外で在り、加えて**検査自身が禁止語をリテラルで綴る**。永久に赤いゲートはゲートが無いのと機能的に同じである（上の「判定を持たない道具」と同じ帰結）。**ゆえに切り出しを外すなら、代わりに濾過層が要る**——#1112 が置いたのは帰属（出現ごとに「どの関数の中に在るか」を決め、守りたい関数へ帰属するものだけを述語へ渡す）である。**そしてこの濾過層は、切り出しの除去と違って下界を構成では満たさない**——帰属を決めるのは行の形を読む述語であり、偽のヘッダがそれを横取りすれば禁止語は対象外へ落ちて緑になる。**残余の内訳と反証の実測は `src-tauri/src/egui_shell/launcher_controller/activation/tests.rs` の `owners_of` の doc を正本とする**（ここへ写せば、あちらを直したときこの行だけが腐る）。

**かつ、切り出しを持つ形は checkout の改行コードに依存する。** 終端を `find("\n    }\n")` のような部分文字列で探すと CRLF に一致せず、母集団が EOF まで伸びる（＝上の存在形が沈黙する側へ倒れる）。行の走査は `str::lines`（`\n` で分割し末尾の `\r` を落とす）で行い、**切り出しの helper 自身を LF / CRLF 両方の fixture で測る**——`include_str!` も `fs::read_to_string` も読むのは checkout された実ファイル（どちらも改行を変換しない）なので、作業ツリーの改行コードによらず固定する必要がある。同じ非対称（手元 `core.autocrlf=input` と CI の既定 `true`）は `.gitattributes` の冒頭コメントが `.githooks/**` について既に記録している。

2026-08-16 実測（#1077）: 検知器 2 本のうち 1 本が CI でだけ落ち、**もう 1 本は同じ理由で「空虚に緑」だった**——ガードを消しても通る状態で、**落ちた側を追わなければ気づけなかった**。手元は 3 度の全件実行がすべて緑である。

**切り出しの helper は、同じ母集団の形を共有する検査群の単位で 1 つに閉じる。** 検査ごとに書き写すと母集団の壊れ方が**検査ごとに独立に起きる**——#1077 で 2 本が別々の状態になったのはそれが原因である。#1106 は 2 本目を書くときに写し、`/simplify` の指摘で 1 つへ畳んだ（母集団を production 側へ限る理由も、書き写せば同じだけ複製される）。**crate 全域で 1 つにはならない**——切り出しはサイトの形ごとに別概念で、トップレベル関数（列 0 の `}`）・メソッド（4 スペースの `}`）・enum 宣言の走査は互いに置き換えられない。**同じ検査群に複数が同居することもある**: `egui_shell/launcher_controller/activation/tests.rs` は存在形が使う `method_body` と否定形が使う `owners_of` を並べて持つ——**極性が違えば要る不変条件が違い、道具も分かれる**。禁じているのは写しであって数ではない。判断と反転条件は `docs/adr/ADR-source-text-probe-helper-locality.md`。

## 列挙の完全性

**網羅性そのものが要件**のタスクでは、単一の分解枠組みは自身の盲点を構造的に継承する（#404）。第一の手段は独立再導出（`/plan-review`「Step 2b — 独立導出による網羅性レビュー」）であり、加えて次が取りこぼしやすい。**手作業のスイープ・改名監査・規範文書の移動でも同じ形で踏む。**

- **その一覧の母集団を誰が知っているかを先に答える。** 正本は 4 通りしかない——コンパイラ（enum variant・trait impl）／ソーステキスト（`const` の集合・モジュール内の関数）／ファイルシステム（対象文書・glob）／外部設定（CI job・npm script）。「網羅を守ると主張しているか」は意味の問いで判定がぶれるが、「母集団を誰が知っているか」は構造の問いで一意に決まり、分類が決まれば足し忘れを捕まえる変異の形も倒し先も決まる（#1011）。**文言の読みは篩、変異の実測は確定**（#1000）
- **列挙の SSOT はツール自身に問う（glob の意味論はツールごとに違う）。** `git` pathspec の `**/` は 1 段以上を要求し、`git ls-files` はブレース `{ts,tsx}` を展開しない（#471 はこれで深さ 0 の実在ファイルを落とした）。**そのうえで出力を切るオプション（`head` / `Select-Object -First` / Grep ツールの head_limit）を列挙に使わない**——切った時点で母集団は自分の推測に戻る（#666）
- **検索パターンは「概念」ではなく「自分が想定した書き方」を列挙する。** 同じ概念が複数の綴りで書かれていると、具体的なパターンは他の綴りを静かに落とす——出るのは 0 件ではなく**少なすぎる件数**なので、「1 箇所にしかない」という誤った結論がそのまま設計判断になる（#843 で 2 回）。緩いパターンで全件を出してから目で分類するか、別の綴りを想定した第 2 のパターンで件数を突き合わせる。日本語の散文では書式そのものが綴りを割るため（`**` は語中に挿入されうる）、**語幹の最短形で引く**（`可視性を**変える**` は `可視性を変える` に当たらない）
- **除外句（`grep -v` 等）は「意図した対象」ではなく「当たったもの全部」を落とす。除外あり／なしの両方を走らせて差を見る。** 差がゼロなら除外は no-op であり、落としているのはパターンの側である——そのとき散文が落ちる理由を除外へ帰属させていると、**説明が実装を指していない**。除外を付ける根拠（「〜だから除いてよい」）の側も観測で裏取りする: #1094 は「テストの import は隣（sibling）だけ」という**未検証の前提**で `grep -v '\.test\.mjs:'` を付け、兄弟でないテストが持つ静的 import を母集団から丸ごと落とした（誤った数え上げが調査から PR 本文まで伝播した）。**母集団を散文で名乗るときは、同時に「この母集団に入らないもの」を 1 つ名指す**——名指せないなら測っていない
- **順序に依存する参照は、削除・挿入で気づかれないまま不整合になる。** 章番号・ルール番号のような**序数**で参照されているものを削除・挿入するときは、参照側を全部数え上げる——概念ラベルで参照している箇所には当の語の grep では到達しない（#482）。**直すときは番号ではなく名前で参照し直す**（命名の規約は `.claude/rules/governance-docs.md`）
- **列挙から列挙への転記は機械で差集合を取る。** 手で写すと件数が数十を超えたあたりで 1 件落ち、落ちた 1 件は転記先だけを見る後工程からは見えない（#884）。転記の完了は「写し終えた」ではなく、転記元と転記先を機械で突き合わせた差分ゼロで宣言する
- **コンパイラを持たない機構（CI トリガー・GitHub ラベル・スキル/ドキュメントの規約）を廃止・変更するとき**は、定義だけでなく依存側を機構名で grep + 独立再導出して数え上げる——漏れた消費者は **false green で気づかれないまま残る**。**「コンパイルが通る＝消費者の漏れ無し」はコンパイラのある領域でしか成り立たない**（#145）

## デバッグ・バグ修正

### 根本原因の同定

- コードを書く前に根本原因を一文で明示し、**壊れた不変条件（何が常に成り立つべきだったか）を必ず 1 つ含める**
- 最初の修正案が失敗した場合、同じ深さで別の推測を試みるのではなく、より深い調査に切り替える
- 修正対象のパターンをコードベース全体で検索し、同一パターンが他に存在しないことを確認してから完了とする（計画時の影響列挙版は `AGENTS.md`「バグ発見時は同一パターン全コードパス検索を行う」）
- **「値を渡していない」と「渡したが受け手に無視される」は別の欠陥様態であり、呼び出し側の grep では後者に到達しない。** 前者を探す検索は、**引数が書かれている箇所を全部「対処済み」に見せる**。1 件見つけたら、同種の値を渡している他の箇所について**受け手のソースで**「実際にその値を使うか」を確かめる（#654: hint は色を渡していたが egui 0.35 の `TextEdit` が `weak_text_color` で無条件上書きしていた）。**受け手のソースを読むまでは、渡した値が届いたことにならない**
- **issue や plan の前提——特に能力（何を受け付けるか）・セキュリティ防御・根本原因診断——は、実装前に「対応する実行コード」と「兄弟機能の既存挙動」で裏取りする。** issue 作者がユーザー本人でも前提は誤りうる（#395 の `.exe` 限定は `Command::new` が `.bat`/`.cmd` を受理して誤り、#456 の「id 重複」は真因が id 不安定性だった）。`/plan-review` のサブエージェントは作者の枠組みに anchor しやすいため、盲点の是正には実証が要る。外部 issue・上流仕様を根拠にするときの時系列・最終 maintainer 回答の確認は `/start-issue`（#565）が担う
- **乖離を解消するときは、issue が提示する「片方に揃える」二択を鵜呑みにしない。** 一方が呼び出し元の無い死蔵コードなら、**削除**が乖離の根本を断つ最小解になりうる（#409。選択肢空間は前提の裏取りで広がる）。削除の安全性は静的 grep + 独立再導出 + **compile/typecheck を「死蔵検出器」として使う**の独立経路で裏付ける
- **層をまたぐ不具合は、上位層（UI）の症状から推測せず、最下層を直接観測して切り分ける。** 観測点は `SNOTRA_TRACE`（`crate::trace_main`）のように、release ビルドでも残り最下層から直接読めるものを用意する
- **性能の訴え（もたつき・入力遅延）は、まず debug ビルドを疑う。** 未最適化の CPU 密ループは release の 10-50× 遅い（#532 SU1 の「秒単位の IME 遅延」は debug の全画面塗りで、release で 8× 改善した）。あわせて**症状の出所を先に切り分ける**——全 UI に及ぶなら renderer 性能、特定入力だけなら経路固有
- **周期の理論値から負荷を見積もらない——増幅段は理論値に現れない。** 機構を正しく同定しても、その周期がそのまま負荷になるとは限らない（#628 はキャレット点滅から「2fps・CPU 1% 未満」と見積もったが実測 **11.5fps・5.1%**。`predicted_dt` が短い repaint 予約を即時再描画へ飽和させる増幅段が間にあった）。**見積りを選択肢の比較表に載せるなら、それが実測か理論値かを明示する**
- **原因は推測せず、名乗らせる手段を先に探す。** ライブラリが原因を報告する API を持つなら計器化を優先する（egui の `Context::repaint_causes()` は `file:line` を返す）。ただし**cause 名だけでは足りず、時間構造（バーストの長さ・間隔の分布）が要る**——「毎フレーム積まれる常在項」は cause 欄に必ず現れるため（#628 の引き金は 480ms の待ちと 26ms のバーストという構造が示した）

### 観測と計装

- **人手の観測時間には、観測条件を変える確認作業を混ぜない。** #628 の再測はカーソル挙動の目視のためホバーを同じ run に含め、`ScrollArea` のフェードが混入して計測が無効になった。目視確認は計測を止めてから行う。あわせて**ログのフラッシュ経路を手順に含める**——PowerShell の `Tee-Object` はパイプが閉じるまで書き出さないため、プロセスを終了させるまでログは 0 バイトに見える
- **観測条件が揃わない可能性に備え、プロトコル非依存の判別指標を用意する。** 総フレーム数や平均 fps はセッション長・操作量に汚染されるが、**局所構造**（#628 では「点滅待ちの直後に何フレーム続くか」）は汚染された run からでも結論を出せる（修正前 0% / 修正後 100%）
- **サブエージェントの報告が届かないとき、エージェントが死んだと決めない——`name:` を渡したかを見る。** `name:` 付きは最終テキストが呼び出し元へ配送されず（`SendMessage` が要る）、名前なしは完了時に自動配送される。**成果は消えていない**——`~/.claude/projects/<project>/<session>/subagents/` の `.jsonl` に全文が残る。督促で回復できるため 9 回中 8 回で機序を測らなかった: **安い回復手段は、根本原因を探す動機を奪う**。規範側の対処は `CLAUDE.md`「サブエージェント委譲と worktree」

### 修正の当て方

- 修正案が API 境界をまたぐとき、「呼び出し側パッチ」と「API 側で責務を完結させる修正」の両案を比較し、後者を優先する
- 競合しやすい一時状態（通知・ローディング・遅延処理）を導入する場合は、タイマーや購読のライフサイクルを単一管理し、再実行時に必ず前回のハンドルを破棄する
- **ガードを追加するときは「どの関数を守るか」ではなく「どのリソースを守るか」で設計する。** 同じリソースを触る経路が複数あれば全経路が同じガードを通るようにする。関数単位のガードは別経路の追加時に素通りされる
- **修正は、それ自体が新しい欠陥の生成過程である——「指摘は解消されたか」と「この修正が何を持ち込んだか」を別々に問う。** 片側だけを見て直すと反対側へ倒れる: 狭すぎる全称を広げれば広げすぎになり、2 軸を 1 事実へ畳めば前提が落ち、落ちた前提を段落で補えば同じ事実が 2 か所になる（#725 で同型を 4 度踏み、3 件目を捕まえたのは後者の設問を明示的に置いたレビューだけである）。**足す前に「その事実はすでにどこかに書かれていないか」を問う**——追加は常に重複の候補であり、書く側からは補強に見える
- **対処が「人間が裁定した仕様」や「実測で確かめた挙動」に触るなら、採用の前に測り直す。** レビュー指摘の動機が一次資料に照らして正しくても、その対処が正しいとは限らない（#738: `any_down()` の固着という指摘は正しく対処案も筋が通っていたが、実測するとドラッグ中も毎フレームクランプが走り「ドラッグを終えたら戻る」という人間裁定を壊した。ユニットテストも smoke も緑のまま、**対照実験だけが差を示した**）
- `tauri.conf.json` や platform 固有ファイルに設定を追加する際は、その設定が Windows でサポートされているか事前に確認する（例: backgroundThrottlingPolicy は Windows 非対応でビルドエラーになる。**現行の等価物が在ってはならない語**なので、識別子として書くと「現行語彙に無い」検査に当たる——素のテキストで書き、検索性だけ残す）

### 検証の落とし穴

- **red を自分の変更による回帰と断定する前に、変更前のベースライン（`main` 等）で同じ条件を実行して A/B 比較する。** 両者が一致すれば、その差分は原因ではない（既存バグまたは環境要因）。性能評価も同様で、**同一マシンでの A/B でのみ**退行を判定する
- **案の採否を実測で決めるときは、勝敗の比だけでなく、それを分解する対照列も同じセッションで測る。** 判定が正しくても、添えた機序は独立に誤りうる（#1059: 「バイト量 6 倍削減 対 並列度 16 倍損失」という予測は却下という結論に達したが、A 側を**単スレッドでも測る 1 列**を足すと実測は 1.29 倍 / 3.01 倍で機序は 2 つとも外れていた）。**誤った機序を書けば、次の反復が「条件を変えれば勝てる」という枝を生む**——あの件の真の天井は 1.29 倍で、並列化しても救えない。対照列は「片方の条件だけを外した列」であり、並列 対 逐次なら現行を逐次で回した列がそれに当たる
- **欠陥の再現を測るときも対照列が要る。用途が違う——あちらは機序を分解し、こちらは陰性を読めるようにする。** 症状の条件そのものが計器を黙らせる形では、単独の測定で「起きなかった」と「そもそも観測できない」が区別できない。#1106 は「`visible_rows = 0` で results 窓が出ないまま Enter が起動する」の再現で、④偽では `egui_results:show` が**原理的に出ない**——B 単独では「行が空で空振りした」と読む余地が残るため、`visible_rows = 8` の A を同じ打鍵列で並べた（行が非空だったことは `egui_launch` 自身が示す。起動の入口はその手前で空判定を通る）。**修正後も同じ 2 列を測る**と、片方が消えて片方が残ることが挙動の変化を挟み撃ちにする
- **その差分が触っていないコードでも「検証済み」ではない。** 移行で無改変のまま持ち越した経路が、新アーキで一度も実行されていなければ未検証である——受け入れで能動的に動かして確かめる（#532 SU1 の IME 経路は無改変だが人間の初検証で二重表示が露見した）
- **検査が緑になったことと、その検査が正しい対象を見たことは別である。** 件数は「参照が生き残った」ことしか示さない。**「何件通った」を根拠に「正しい」と言わず、正しさは別の観測で裏付ける**（指した先を直接読む・fixture で両方向を押さえる。#725）
- **「このテストは X を検出する」と doc に書いたら、X を実際に起こして落ちることを確かめる。** #745 は「対照テスト 2 本が reset の呼び出しを消す変更を落とす」と書いたが、実測では呼び出しを削除しても全数が通った。危険なのは向きである——同じ差分の 4 か所が正しく「検知手段は無い」と書いているなか、**テストの doc だけが「守られている」と誤信させた**。`.claude/rules/safety-nets.md`「効いていることは、フォールトインジェクションで一度は実測する」を、対象がセーフティネットでなくてもユニットテストの doc へ当てる
- **他者の指摘を自分で測り直すとき、「測って出なかった」を不在の証拠にしない——再現には入力の形が要り、その形は指摘者が持っている。** #768 は正規表現の指数爆発をバックトラックがそもそも起きない入力で測って 0.0ms を得、成立する指摘を棄却しかけた（条件を満たす入力では 747ms）。**再現しないときは自分の入力が指摘の条件を満たしているかを先に疑う**（報告に入力が書かれていなければ、聞くのが最短である）
- **レビュー通過・実行できた ≠ 実行時リソース挙動が検証済み。** 価値の中核が実行時プロパティ（メモリ常駐量・アイドル CPU/再描画・レイテンシ）である変更は、コードレビューがそれを見ない——受け入れで**計測**して初めて確かめられる（#532 SU6.5: 「Ready to merge」まで来た hide 経路が hidden でも 43MiB のままだった gap を、計測ゲートだけが暴いた）。「設計を決める前に測る」（#634 の SU4 プローブ）と対を成す「マージする前に測る」であり、計測ゲートはレビューと冗長でなく別クラス（実行時挙動）を捕える
- 実機シナリオの書き方（人間の反応時間より短い時限を要求しない等）は `docs/build-commands.md`「エージェントが目視項目を自分で実施するとき」が持つ
