# 開発原則

このプロジェクトで共有する設計・実装の原則。エージェント・人間を問わず適用される。

## KISS

- `main.rs` に業務ロジックを増やさない
- 責務を跨ぐ実装をしない
- 新規コードは既存のファイル構成・命名規則・スタイルパターンに合わせる。独自パターンを導入する前に、既存パターンの利用を検討する

## DRY

- 責務の集約先は各サブディレクトリのドキュメント（`snotra-core/CLAUDE.md`, `snotra-egui-runtime/CLAUDE.md`, `src-tauri/CLAUDE.md`, `snotra-settings/CLAUDE.md`）に記載している
- 同一ロジックの繰り返しは2回まで許容し、3回目で抽出を検討する。無理な抽象化よりも多少の重複を許容する
- **ドキュメント間でも DRY を守る。** 同じ事実（モジュール一覧・コマンド・契約など）を複数の `.md` に書かない。SSOT を1箇所に決め、他からは参照する。二重管理は片方の更新漏れで必ずドリフトする。「同期を頑張る」のではなく「重複を排除する」のが根治である

## YAGNI

- 使う予定だけの抽象化（不要な trait / generics / レイヤー）を導入しない
- 現在の要求範囲を超える機能追加を行わない
- 拡張性よりも、現要件での単純さと可読性を優先する

## 撤去（消す変更）の作法

YAGNI の実行面。crate・API・記述を消す変更は「減らすだけ」に見えて、次の点が抜けやすい（#660 の crate 撤去では最初の 3 つを実際に踏んだ）。**被依存ゼロの対象ではコンパイラが盲になる**ため、これらを拾うのは手の列挙と最終 grep だけである。

- **消す変更の中で「新しく書いた 1 文」は、削除ではなく新規記述である。** 削除の diff では消したことに注意が向き、書き足した主張の検算が抜ける。#660 では crate 撤去に合わせて「`cargo run`（`-p` 欠落）は別 bin を起動しうる」と補ったが、実測はルートで exit 101 のエラー（何も起動しない）だった。**残す記述に手を入れたら、その一文は測る対象になる**（引用位置も同様に、行番号ではなくシンボル名・見出し名で書く——行番号は書いた時点で既にずれていることがある）
- **移設は削除ではなく差し引きである——削減幅を見積もるなら、移設先への追記と跡に残すポインタを引いてから言う。** 「N 字を別ファイルへ移す」は N 字の削減にならない: 移設先では文脈を補う必要があり、元の場所にはポインタが残り、参照が正準形（`.claude/rules/governance-docs.md`）になると参照元も伸びる。#827/#830 は −28% と見積もって実測 −19.7% で、その前の見積もりは −30〜45% だった——**同一サイクルで 2 度、移設に伴う書き足しを引かずに数字を出した**。機構化（散文 → スクリプト）でも同じで、呼び出し 1 行と契約への参照は残る。
- **教訓・記述の移設は貼り付けではなく差分の抽出である。** 移す前に既存の正本を grep し、既にある事実は参照へ落として「その場所にしか無い部分」だけを移す。#660 の移設先は #399 の原型と受容残余を語り直し、同一事実の 4 箇所目を作った（計画段階で警告されていたのに実装で踏んだ）
- **自分の変更が偽にした記述・作った矛盾は「範囲外」に置けない。** 判定は「存在しなくなるものへ読者を送るか」「現在形の主張が偽になるか」で、歴史を述べて真のままの記述は残す。#660 では runtime 自身を「MVP runtime」と自称するログと、`docs/architecture.md` を正した結果 `docs/build-commands.md` に残った矛盾（実装に存在しない「Device 復旧」）を当初範囲外に置き、2 度覆した
- **旧 API を消すとき、compile-fail が名指しするのは「コード参照」だけである。** 被依存がある対象でもこの盲点は残る。#752 で layout の results_should_show を消したとき、コンパイラは呼び出し 1 箇所とテスト 4 行を正確に挙げたが、doc コメント・`src-tauri/CLAUDE.md`・ADR・設計書に散った名前依存 **10 箇所は視界の外**だった（grep 実測で全 16 箇所）。しかも数を grep に問わなかった 3 者（計画・独立再導出・レビュア）が全員 3〜4 箇所と過小に見積もった。**名前で参照する文書は grep で数え、そのうえで「歴史的言及として残すもの」と「現在形で腐るもの」を仕分ける**——ADR と設計書は当時の決定文脈ゆえ旧名のままでよく、生きた文書は「旧 X は Y へ吸収」と書けば真のまま残る
- **「これは X が持つから消す」と書くときは、X の母集団が元の観点を覆っているかを読んで確かめる。** 覆っていなければ、その差分は**どの検査にも属さなくなる**（#764: `code-reviewer` の Phase 1 から DRY とパフォーマンスを削り「Phase 2c と Phase 3 が持つ」と書いたが、2c は関数を起点に外向きへ探す手順、Phase 3 は「性能に敏感な箇所に触れる場合」の条件付きで、外側が宙に浮いた）。移送先が**実施の有無を観測できる形**（記録テンプレート等）を持つかも見る——持たない場所へ移した責務は沈黙する

## ドキュメントとコードの分担（陳腐化の予防）

散文ドキュメント（`SPEC.md` / `docs/architecture.md` 等）の陳腐化は、コードの精密な事実（式・バイト形式・フィールド列挙・実装機構名）を散文へ写経した箇所から生じる。#404 / #410 で是正したドリフトの大半がこのパターンだった。「ドキュメント間でも DRY」の原則をコード↔ドキュメント間にも広げ、そもそも写経しないことが根治となる。

- **ドキュメントには「なぜ・何を・全体構造（intent）」を書き、精密な事実はコードを SSOT として参照する。** ドキュメントの役割は意図・目的・全体像のオリエンテーションである。式・ワイヤーフォーマット・列挙・機構名は再記述せず、それを担うコード（`TabId::ALL` など）の doc コメントを参照先にする。`architecture.md` が既に実践している「各 `CLAUDE.md` を SSOT とし、自身には重複を持たない」方式を、精密事実にも拡張する
- **参照が成立するには、参照先に正本コメントが必要である。** インラインコードしかない箇所（かつての SolidJS フロントの shouldShowResults memo が実例。現行の等価物は無く、`layout.rs` が「0 件で隠れた」と「carve-out で隠れた」へ分解した）を参照するなら、その場所へ「intent と式」を記した正本コメントを置き、SSOT として指名する。精密事実とその理由がコードの同じ場所に同居する形になる
- **生成（doc-gen）より参照を既定にする。** コードコメントからのドキュメント生成は、ツール固定費が便益を上回る規模（横断ドキュメント中の精密事実は十数件程度）では割に合わない。参照を既定とし、対象が大量化して初めて生成やマーカー同期を検討する
- **判定基準: 「この一文は、振る舞いを保つリファクタを生き延びるか？」** 生き延びるもの（intent・why・構造）はドキュメントに書く。生き延びないもの（機構名・バイト形式・式）はコード内コメントに置くか参照にする。一文の中に残す部分と移す部分が混在することもある。例えば「indexing 中は隠す。ただし tool / folder / instant は除く」は intent なのでドキュメントに残し、`results().length > 0 && …` のような式はコードに移す
- **やむを得ず再記述する精密事実は、機械検査で保護する。** 列挙のように再記述が避けられないものは、ドキュメントとコード（`TabId::ALL` 等）の一致をアサートするテストを書き、サイレントドリフトを CI の red で検出する
- **責務の「所在」を書いた散文は、移設で偽になる。しかもシンボル名の grep では届かない。** 消す変更（上節）では compile-fail が呼び出し元を挙げるが、移設では**コードは全部通る**まま散文だけが腐る。#749 で `drive_results_window` を `view.rs` から移したとき、当の関数名で grep して 4 箇所を直したが、実際は 6 箇所あった——`mod.rs` の 2 箇所が「`view.rs`（drive）」「`view.rs` の drive」と**略記**しており、シンボル名の grep に掛からなかった。加えて新設した `//!` 自身が「main のサイズ適用は `view.rs` にある」と書き、その根拠に挙げた関数を同じ変更で自分のファイルへ引き取っていた（**説明が自らの主張を反証していた**）。**移設したら、所在を語る散文を「概念ラベル」でも数え上げ、新しく書いた所在の主張は根拠となる関数の現在地で検算する**（`docs/adr/ADR-window-coordinator-split-rule.md` 却下 5）。**この罠は両方向にある**——#666 では**残った側**（`view.rs`）の新しい `//!` が、同じ変更で自分から出ていった `ctx.set_fonts` を「本ファイルが個別に持つ 3 つ」の 1 つに数えていた。移設で書き直す `//!` は、**引き取った項目だけでなく手放した項目も**現在地で引き直す。**この罠は移設に限らない**——#755/#801 では前提を反転させる変更で同じ形が 4 例出た（「意図的な 2 導出」「目的が違う」「バー高への collapse」といった概念ラベルで書かれた**根拠**が偽になり、結論は真のまま残った）。**探し方は概念語の grep である**（`クランプ|畳む先|実表示の高さ` で 3 か所を追加で拾えた）。**かつ、1 つのラベルを潰すと同じ段落の別のラベルが diff の context 行に沈み、差分だけを見るレビューは「訂正済み」と判定する**——4 例目はそれで 1 ラウンド生き延びた。ゆえに**訂正した段落は、diff ではなく現物を読み直す**
- コメント自体の書式・粒度・定型ラベルは `docs/comment-guidelines.md` を SSOT とする（本節は「ドキュメント ↔ コードの分担」の SSOT）

## 設定由来の派生状態（キャッシュとして扱う）

config から導出する派生状態は「キャッシュ」とみなす。#347 / #348 の教訓に基づく。

- **既定は live-read とする。** 毎操作で config から計算し直す。計測して高コストだと判明したものだけをキャッシュ化（長命オブジェクトへの焼き込み）する。安価なものを焼き込むと、設定変更が反映されないドリフトを生むだけになる
- **キャッシュ化するなら、その無効化の所有者を必ず決める。** 設定変更時に誰が再構築を責任もって行うかを明確にする。所有者不在は設定変更の取りこぼし・データ損失の温床になる（例: `HistoryStore.top_n` の焼き込みドリフト、index の lost-update 窓）
- **「setter で追従」より「そもそも焼き込まない」を優先する。** live-read にすれば desync を構造的に発生不能にできる場合が多い（例: `HistoryStore.top_n` を live-read 化し、フィールド自体を削除した）
- 詳細設計は `docs/design/2026-05-31-coherence-staleset.md`（config↔派生状態コヒーレンシ / StaleSet 契約）を参照

## config の値は到達性の検出器を持たない

コードの他の面には「届いていないと壊れる」機構がある——private / `pub(crate)` の関数は呼ばなければ `dead_code`、型は変えれば下流が compile-fail（`AGENTS.md`「条件別チェック（トリガー → 参照先）」がこれを「移行漏れ検出器」として使う）、モジュール索引と文書参照は `governance:check` が照合する。**config のフィールドは、定義しても誰も読まなくてもコンパイルが通る。**

（関数の検出器にも穴はある——lib crate の `pub` 項目に `dead_code` は出ないため、`snotra-core` の `pub fn` は呼ばれなくても `-D warnings` を通る。config が特異なのは、**穴ではなく検出器そのものが無い**ことである。）

この欠如は 3 つの形で現れる。いずれも「値が参照ではなく**写し**として流れる」ことの帰結である。**同じ構造は config 以外でも起きる**——純粋核が計算した値を描画層が参照しなくなる形を 2026-08-11 に実測した（「検証の層と、層と層の隙間」）。本節は**値の定義側**の機構と規範を扱い、あちらは**検証の地図**の上に同じ穴を置く。

- **消費者ゼロ** — 写しがどこにも届いていない
- **導出が 2 経路** — 写しが 2 つあり、片方だけが変わりうる
- **既定値の偶然の一致** — 写しが 2 箇所にあり、たまたま等しい

**休眠を支えているのは、自動で回る検証が既定値の下でしか走らないことである。** 非既定の config を組むテストは在るが（`engine.rs` の検索系）、**見た目に効く値は既定の下でしか描かれない**——色を変えて描画を検証する経路は `npm run check:colors` の 1 本だけで、GUI と非ロック画面を要するため **CI には無く、明示的に起動したときだけ動く**（`docs/build-commands.md`「`[visual]` の色を変える変更は、**非既定色で**目視する」）。乖離を露出させる入力——ユーザーが既定と違う値を設定すること——は、放っておいて回る検証には現れない。**この形で実際に休眠していたのが #802 以前の `[visual].background_color` である**: 描画経路の消費者がゼロだったが、既定 `#282828` が `snotra-egui-runtime` の `CLEAR_COLOR` と一致するため既定のままでは正常に見え続けた（#802 で解消）。

**規範では止まらない。** 該当箇所にはたいてい既に注意書きがある。たとえば #794 以前のホットキーは config 側の競合判定と platform 側の登録に別 parser があり、コメントで一致を要求しても `del` と未知 modifier の扱いが乖離した。#794 では core の意味型を両方が消費する機構へ移した。しかし規範が効くのは変更者がその場所を通るときだけで、**config の写しは通らない場所に散る**——既定値を変える人は、それを写した先のファイルを開かない。ゆえに機構へ移す:

- **新しい config フィールドには、追加と同じ変更で消費者を与える**（作ることと使うことは別判断）。読まないなら理由をフィールドの doc コメントへ書く。機械検査（旧 G-config-reachability）は導入以来捕捉 0 件のまま検査側の表だけが腐ったため #894 で廃止した——**この規範だけが頼りである**
- **既定値のリテラルを写さない。** フォールバックの正本は各セクションの `Default` 実装（`AppearanceConfig::default()` 等）であり、`.unwrap_or(600.0)` のような再手打ちは今日たまたま一致しているだけである（#680 の 2。src-tauri の fallback を参照へ寄せた実例は #795）。**ただし「同じ数」と「同じ概念」は別である**——同じリテラルでも読み元が違えば写しではなく、参照へ寄せると存在しない結合を主張することになる（`AGENTS.md`「検証の作法（全タスク共通）」の「消す/共通化する前に、同じ表層形が複数の概念を担っていないか分類する」。判断の記録は `docs/adr/ADR-config-default-fallback-references.md`）。**`Default` 実装自身も既定関数を呼ぶ形に揃える**——serde は「セクション欠落 → `Section::default()`」と「キー欠落 → `#[serde(default = "default_X")]`」の 2 経路を持ち、両者が食い違うと**同じ既定が TOML の書き方によって変わる**（`config.rs` の `empty_section_deserializes_to_default_*` がこの一致を固定する）

## 状態を散在フラグで表さない（単一の導出源に集約する）

複数の boolean / nullable フラグの組み合わせで「モード」や状態を暗黙に表すと、排他律・優先順位・各状態での振る舞いがコード中の複数ガードに散らばる。各ガードが優先度を再導出するため、状態を1つ追加したときに全ガードの更新を忘れると、不変条件が気づかれないまま破れる。

この教訓は、検索モードの `folder` / `tool` / `instant` / `indexing` を散在する真偽フラグ群から**二軸導出**へ集約した経験から得た。二軸は UI スタックを入れ替えた今も生きており、`src-tauri/src/egui_shell/search_state.rs` の `ViewKind`（軸1: ビュースタック頂点）と `QueryIntent`（軸2: 入力の意味・`interpret()` が導出）がその実体である。

- **散在ガードを見たら問う:** これは単一の概念か（→ 1つの判別子・導出メモ / 関数に集約する）、それとも直交する複数軸か（→ 各軸を名前付きで分離する）。フラグの組み合わせは、本来 discriminated kind か直交軸であることが多い
- **優先度・排他律は導出源の一箇所だけに書く。** 各ガードはその導出を消費するだけにする。更新箇所を一点に集約すれば、網羅 `match` で「状態追加時の分岐漏れ」をコンパイラに検出させられる（Rust では言語機能だけで足りるので、TypeScript 期に要った網羅性チェック用の補助関数に相当するものは要らない）
- **オーバーレイ状態を軸に混ぜない。** 相互排他なモードは discriminated kind にし、どのモードにも重なりうる状態は独立フラグのまま分けておく
- **仕様との一対一対応を保つ。** 仕様側に優先順位・状態遷移が記されているなら、実装の導出源がそれと対応するようにする（例: SPEC §8.6 状態図・§18.5 優先度 ↔ `view_kind()` の射影順。優先順位の正本コメントは型ではなくこの導出関数の側に在る）。整合検証は `/state-check` で行う
- **SSOT を担う状態を削除するときは、その役割の移管先を明示する。** ある状態（特に複数箇所から読まれる派生の源）は、値だけでなく「ある判定の唯一の評価点」という SSOT 役割を暗黙に担っていることがある。これを消すと、判定述語が消費側に再び散在しうる。削除前に「この状態が単一情報源だった判定は何か、削除後は誰が担うか」を問い、必要なら述語を共有ヘルパへ抽出して SSOT を移管する（例: instant 検出ラッチを廃止したとき、検出述語を `is_instant_prefix()` へ抽出して instant 判定の SSOT にした。今日その唯一の消費者は `interpret()` である）

## 構造的設計原則と強制の階梯

2026-07-05 の構成調査で挙がった課題群（#426〜#442）を抽象化すると、5つの構造的原因に還元された。既存の原則（DRY・設定由来の派生状態・散在フラグ）を補完する横断原則としてここに明文化する。

前提として、不変条件・規則を守らせる手段には強さの序列（強制の階梯）がある:

> 構造で不可能にする（型・導出・単一通過点） ＞ コンパイルで検出（compile-fail・`#[must_use]`） ＞ テスト・CI で検出 ＞ チェックリスト・レビューで検出 ＞ 書き手の記憶

設計・レビューでは「この規則はいまどの段で守られており、1段上げるコストは見合うか」を問う。

- **1. Derive, don't duplicate — 同じ知識の第2表現を手書きで並行維持しない。** タブ対応表・デフォルト値・派生 Vec 群・翻訳テーブル・バージョン表記のように、1つの知識が複数の表現を持つ場合は、1つを正として他を導出（builder 集約・テーブル駆動・宣言的マップ）する。手書きの並行維持は追加時の更新漏れを必然にする。DRY 原則の「ロジックの重複」から「表現の並行維持」への拡張（#436, #437, #438, #439, #441）
- **2. 不変条件は単一の通過点（choke point）に閉じ込める。** 「世代カウンタは必ず更新する」「通知→世代→クリアの順で行う」のような規則が複数コードパスに散在すると、正しさが書き手の記憶に依存する。規則を1つの関数・型（世代更新ヘルパ・ライフサイクル高階関数・正規化済み型）に閉じ、違反をそもそも書けなくする。「散在フラグ」原則の状態版に対する、操作・手続き版（#428, #431, #435, #439）
- **3. 純ロジックと副作用の分離をフラクタルに適用する。** crate 境界（snotra-core / src-tauri）で成立している functional core / imperative shell を、ファイル・関数のレベルにも同じ形で適用する（`working_set.rs` の純関数抽出が成功例）。判断（純粋・テスト可能）と実行（副作用）が1関数に混在して肥大したら分割の合図（#431, #433, #435, #436）
- **4. テスト可能性は機能ではなく横断アーキテクチャ要件である。** 検証の死角は「テストが書かれていない」箇所ではなく「テストが書けない/回らない構造」の箇所に生まれる。永続化経路は dir 注入可能に、全 crate のテストは CI で実行、全 UI 層に最低1つの検証ハーネス——を構造の受け入れ条件とする（#426, #427, #429, #432, #440）
- **5. 境界を跨ぐ契約は1箇所で規約として定義する。** IPC 返り値・翻訳カタログ形式・プロセス間ファイルプロトコルのような境界契約が「各実装の集積」として暗黙に存在すると、表現の系統が分裂する。契約を規約として1箇所に書き、実装はそれに従う（#434, #438, #442）
- **6. 検出は構造化された信号で行い、テキストは証拠に留める。** 「成功したか」を判定するのに出力テキストを使うと、切り詰め・書式変更・ロケールで検出が壊れる。判定には exit code・型・戻り値のような構造化された信号を使い、テキストは人間/エージェントが読む証拠として添える。**どこで切っても取りこぼすものを検出手段にしてはならない。** **パイプは exit code をパイプ末尾のコマンドのものへ置き換える**——`cmd | tail && next` の形で検証と次の操作を繋ぐと、`cmd` が赤でも `tail` の 0 で先へ進む（#812 のサイクルで `governance:check` の赤を見落としたままコミットした）。**禁止ではなく安全形を使う**（#858 で同じ形を再発させたのは、危険だけを述べて代わりの手段を書いていなかったためである——規範は復帰手順とセットで書く）: **出力を絞りたいなら `set -o pipefail` を先に置く**（実測: `(exit 3) | tail -1` は 0 を返すが、`set -o pipefail` の下では 3 を返し `&&` の鎖も止まる。成功時は素通りするので既存の形を壊さない。`${PIPESTATUS[0]}` でも取れる）。**そもそも出力が数行のコマンドを絞らない**——`governance:check` は成功時 1 行であり、そこへ `| tail -1` を付けても節約はゼロで exit code だけを失う。**この危険は Bash 固有である**: PowerShell の `$LASTEXITCODE` は `Select-Object` / `Out-String` を挟んでも保たれる（cmdlet はプロセスではないため・実測）。 PostToolUse hook は `cargo test 2>&1 | tail -5` の出力有無で合否を伝えようとしていたが、成功時にも 5 行出るうえパイプ終端の `tail` が exit code を握り潰していた。検出を exit code へ移し、テキストは切り捨て可能な証拠に降格した結果、切り捨て通知も件数カウントも不要になった（#471）。**さらに、判定単位は「文字列が現れたか」ではなく「どの構文的位置に現れたか」で定義する。** 「言及」と「実行」を区別しない検出器は必ず誤爆する——PreToolUse hook は payload 全体を grep していたため `description` や `grep "gh pr create" f` の引数文字列で発火し、バグを説明する行為そのものを妨げた。判定を「コマンド位置に現れる呼び出し」へ移して根治した（#482）。同型の誤爆は `config-warn` がファイル内容中の `config.toml` に反応した件（#471）にもあり、この hook を守るために書いたカナリアテスト自身も、コメント中の `process.exit()` に反応して赤くなった
- **7. 失敗方向は、個別のハンドリングではなく既定値に埋め込む。** 「異常時にどちらへ倒れるか」を経路ごとの `if` で書くと、経路を 1 本足したときに倒れる向きが変わる。**安全側を既定値そのものに置き、安全と積極的に確認できた経路だけがそれを覆す**構造にすれば、未知の経路・将来の経路・例外経路がすべて自動的に安全側へ倒れる。PreToolUse hook は `exit 2` だけがツールをブロックし、`exit 0` は許可、それ以外の非ゼロ（Node が未捕捉例外で返す **1** を含む）はコマンドをそのまま実行する。ゆえに `pre-bash.mjs` は既定の `process.exitCode` を 2 に置き、許可が確定した経路だけが 0 を書く（#482）。これは階梯でいえば「構造で不可能にする」段であり、「全経路で fail-closed を忘れない」というチェックリスト段より 2 段上にある。**冗長に見える既定値は、冗長でなくなる日のために存在する**ため、その除去・反転を検知するテストを併せて置く
- **8. 全称条件だけの検査は、集合が縮んだときに空振りする。守りたい要素は名指しする。** 「全エントリが deny」「全 member が opt-in」のような ∀ 条件は、**要素が消えた形**に対して真のまま通る——空集合は ∀ を自明に満たし、必須要素が 1 つ消えても残りが条件を満たせば緑になる。ゆえに ∀ 条件には「非空」だけでなく**「守りたい要素が在る」という ∃ 条件を組にする**。#713 の `G-workspace-lints` は当初「`[workspace.lints.rustdoc]` が非空かつ全エントリ deny」で設計したが、`broken_intra_doc_links` の行だけが消え `invalid_html_tags = "deny"` が残る形（表を編集して 1 行消すだけで起きる）を緑で通した（実装前に述語を実データへ当てて発見）。必須 lint 名を名指しする形へ直した。**カナリアが「消えたら困る識別子」そのものを持つのは写しではなく設計である**——先例は `.claude/hooks/post-edit.test.mjs` の member 名ハードコードで、意識的な更新を強制するためにそう書かれている（`.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」が入力側を、この項が述語側を覆う）
- **拒否する機構の誤爆は一様でない——「拒否メッセージの復帰手順が適用できない誤爆」を別枠で探す。** 検出器を足すときは真陽性と誤爆の件数だけでなく、**誤爆した相手が示された手順で回復できるか**を問う。#768 の `\` パス判定は「語末 1 文字 + `:` + 正規表現エスケープ」を絶対パスと区別できず `rg "version:\s+" src` を止めたが、拒否メッセージは「`/` で統一せよ」であり**この相手に適用できる手順ではなかった**。件数で見れば誤爆の 1 つだが、「fail-closed 方向だから受容する」で片付けられる誤爆とは質が違う——回復手段のない拒否は、規範を機構へ移した設計そのものへの信頼を落とす。**同型の非対称は自分の機構同士にも生じる**（同 issue: PostToolUse が会話へ出す再現コマンドが PreToolUse の判定に当たり、片方が指示する形をもう片方が拒んだ）
- **「検知手段が無い」と書きかけたら、検知可能になる設計へ変えられないか先に問う。** 受容残余として記録するのは、動かせないと確かめてからでよい。動かし方は 2 種ある。**(a) 責務を検査可能な層へ移す**——#654 は失敗文言の区切りを呼び出し側（imperative shell のインライン処理・テスト不能）から文言テーブルの関数内へ移し、「理由が空のときコロンだけ残る」をユニットテストが固定する不変条件に変えた。**(b) 観測点そのものを作る**——同じ #654 で、実 install 失敗は再現手段が無く失敗トーストの描画は**一度も観測できなかった**ため、env ハッチ（`SNOTRA_EGUI_FAKE_UPDATE_FAILED`）を新設して視覚スモークの対象にした。どちらも階梯を 1 段上げる操作であり、**残余の記録は最後の手段である**
- **規範に条項を足す前に、その節が律する対象範囲（スコープ）が宣言されているか確かめる。** 検算の母集団は、自分が見ていた範囲ではなく**規範が名乗る範囲**である（`AGENTS.md`「検証の作法（全タスク共通）」の「既存の全事例に当てて検算」の、母集団の取り方に関する具体則）。**スコープの無い規範では、既存条項が既に偽でありうる**——#654 は `SPEC.md` §11「見た目の規範」へ「色の指定を省いてライブラリ既定に委ねない」を足そうとしたが、§11 に宣言が無いため射程は `snotra-settings`（色リテラルのデザイントークンを持ち `ui.label` 等を 60 件以上色未指定で描く）にも及び、既存条項「描画コードに色リテラルを書かない」の時点で**既に偽**だった。検算を検索 UI にしか当てていなければ、偽を 1 つ増やして終わっていた。**スコープ宣言を先に置くと、新条項が真になると同時に既存の偽も消える**
- **新設する検査の期待値は、SPEC・契約と照合してから書く。** 実装より強い期待を書いた検査は、**設計どおりの挙動を FAIL と判定する**——検査が赤いのに直すものが無い状態は、赤の信用を落とす。#749 のカテゴリ D 目視で「results がタスクバーの下へ潜らない」と書いたが、当時の `SPEC.md` は「作業領域の残りが 1 行に満たない場合でも 1 行分（+ padding）は表示し、そのぶんのはみ出しは受容する」と定めており（#675）、メイン窓を下端へ置けば設計どおり落ちる項目になっていた。**同じ誤りが #757 の目視シナリオにも先に書かれていた**——期待の書き写しは、検算されないまま複製される。受容残余を持つ挙動の検査では、**残余の境界そのものを判定条件にする**（当時なら「潜らない」ではなく「1 行 + padding を超えて沈むなら FAIL」）。**照合先は必ず現在の SPEC である**——この事例で引いた条文は #835 のクランプ撤去で消え、境界は `SPEC.md`「4.5 最大列挙数」へ移った（はみ出しを全面的に受容し、判定は「高さが動かないこと」になった）
- **チェックリストは「構造が規則を吸収できていない」ことの診断信号である。** AGENTS.md・各 CLAUDE.md に専用チェックリストや注意書きが必要な箇所は、階梯の下段で守られている箇所の正確な地図になっている。構造が規則を吸収したら（例: 派生 Vec 生成の builder 集約後）、対応するチェックリストを削除する——ドキュメントが軽くなることを設計改善の検収条件とする
- **故障注入は、本来の回帰より強い変異にしてはならない。注入が赤くなったことは、検査が当の回帰を捕まえる証拠にならない。** `.claude/rules/safety-nets.md`「効いていることは、フォールトインジェクションで一度は実測する」は**注入したこと**を求めるが、**注入の強さ**までは律しない。変異が本来の故障より強い／状態が本来と違うと、検査が縛れていなくても赤くなり、**縛れていない検査を「縛れている」と記録してしまう**。#872 のサイクルで同じ型を **3 回**踏んだ: (1) 移動した呼び出しが no-op になる状態で測っていた、(2) 「5 フレームとも偽」にする変異で赤くしたが**本来の回帰は「1 フレーム目だけ偽」**で、待ちが一致の最後を返すため検査は PASS していた、(3) 判定フレームより前にハーネスが既にフレームを走らせており、縛りたい分岐がそもそも走らない状態で測っていた。**変異は「実際に起きた回帰の姿」に合わせる**——姿の正本は、その回帰を直したときの実測コメント（#872 なら `view.rs` の focus 順序の記述）である。あわせて、**新設した検出器自身の入力集合が空になる経路**を疑う（同じサイクルで `AfterAll` の絞り込みキーが空なら母集団ゼロで自明に緑になる形を新設していた。入力側の検算は `.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」、述語側は本節の「全称条件だけの検査は…」が覆う）。**入力は空でなくとも退化しうる**——反復 12 で新設した 3 本は非空のキャッシュを渡しながら**空の木**を渡しており、そこでは「木に無いキー」と「全キー」が一致するので、**木を引く実装と引かない実装が同じ答えを返す**。母集団ゼロではないので入力側の検算では見えない。ゆえに**変異は 2 方向へ入れる**——「検査が狙う対象」を壊す向き（本来の回帰の姿）と、**「検査が対象を見ているか」を壊す向き**（依存を素通しへ差し替える）。後者を入れたところ、既存 222 本が緑のまま新設 1 本だけが落ちた
- **検知器を足す前に、その検知器が単独で捕まえる経路を数える。** 既存の検査が捕まえる経路を除いて残るものが無ければ、それは検知力ではなく**保守の対象**である。反復 12 は「検知器が自分の前提を自分で満たさなくなる」形を 3 巡続けて指摘され、毎回**その検知器を直す**ことで対処して新しい未検証の装置を投入していた。発火経路を数えたら守っていたのは 1 経路だけで、**2 行の断言で刺せた**（残りは既存の挙動テストが既に落としていた——同じサイクルの変異注入で実測済み）。「検知器が足りない」と読むのは誤診でありうる
- **テストのために可視性を広げる弁明を doc に書いたら、切り口が対象と合っていない兆候である。** 「なぜ `pub(crate)` にしたか」を散文で説明しなければならない時点で、公開したものと検査したいものがずれている。#977 は A/B 検知器のために `index.bin` を書く関数を `pub(crate)` へ広げたが、検知器が要るのは**導出**だけで、書き込みは「書いて、読まずに消す」ためだけに走っていた。代償は 3 つ——テストがファイルシステムを巻き込む（治具 30 行）、**型に無いロック契約**（`INDEX_WRITE_LOCK` は呼び出し側が保持する）の観客が crate 全体へ広がり**新しい呼び出し自身がその規範の反例になる**、doc が弁明を抱える。**純粋な導出（I/O 無し）を切り出してそちらを公開する**と 3 つとも同時に消え、症状（テスト用 temp ディレクトリの衝突）を個別に直すより源が断てる
- **やりすぎの境界（YAGNI）:** 原則の教条的適用（trait 化・proc-macro 生成・既存契約の一斉移行）より、choke point 関数1つ・テーブル1枚・新規分からの規約化で 80% を取る。「無理な抽象化よりも多少の重複を許容する」は本節にも適用される

## 検証の層と、層と層の隙間

上の階梯が「規則を**どの強さ**で守るか」を問うのに対し、ここは「その手段が**何を見ていないか**」を並べる。変更に対して層を選ぶための地図であり、**コマンド・実行条件・どの変更でどれを回すかは `docs/build-commands.md`「変更後の検証チェックリスト（必須・スキップ不可）」が正本**である（ここに写しを置かない）。

並べるのは**実行される検証**であり、型・`#[must_use]`・hook のような「走らせるまでもなく効くもの」は上の階梯が扱う。

| 層 | 手段 | 保証するもの | **見ないもの** |
|---|---|---|---|
| 純粋核のロジック | `cargo test`（`snotra-core` / `layout.rs` / `ime.rs` 等） | 入力 → 出力の変換 | **その出力が消費されているか** |
| egui の論理座標 | `cargo test`（`view.rs` の kittest・`run_pass`） | widget の構成・順序・論理位置 | **実ピクセルへの丸め・実フォント・DPI** |
| node の純関数 | `npm test`（vitest） | `scripts/` と hook の判定ロジック | それが実際に配線されているか |
| PowerShell の純関数 | `test:powershell` | 判定ロジック（色・幾何・trace 不変条件） | 実際の窓 |
| 起動と配線 | `smoke:startup` / `smoke:egui` | 起動・hotkey 登録・show/hide・trace 不変条件 | 見た目 |
| 実ピクセルの色 | `check:colors`（判定あり） | 宣言色が届いているか | 位置に紐付かない（クロス配線） |
| 実ピクセルの幾何 | `check:input-metrics`（**判定を持たない**） | 入力欄の縦位置の実測値 | 合否——読むのは人間 |
| 人間の目視 | `smoke:manual` | 総合的な違和感 | 実施の記録（残さないと未実施と区別できない） |
| 文書の整合 | `governance:check` | 参照・索引・命名の着地 | 意味の側（責務の妥当性等・受容する残余） |

**穴は層の内側ではなく境界に空く。** 各層は自分の担当を保証するので、抜けるのは「層 A の出力が層 B へ届いているか」である。2026-08-11 に 2 つ実測した。

- **純粋核 → 描画**: `snotra-egui-runtime` の `ime::active_range_chars` は変換の正しさをテストで固定しながら、egui が `legacy_visuals` の下でその値を参照せず、**検査 2 本が緑のまま機能が丸ごと死んでいた**。値の定義側から見た同じ構造は「config の値は到達性の検出器を持たない」が扱う——**あちらが「消費者ゼロ」を欠陥として述べ、ここは同じ穴を検証の地図の上に置く**
- **論理座標 → 実ピクセル**: 入力欄の文字を縦中央へ寄せた変更は、論理座標では 8 フォントすべて対称と測れたのに、**実機では 4 種で 1px ずれていた**（`raster.rs` がカバレッジ AA を持たないため・`snotra-egui-runtime/CLAUDE.md`「不変条件」）。**人間の目が唯一の検出器だった。** `check:input-metrics` はこの隙間を埋めるために置いた道具である

**ゆえに層を選ぶときは 2 つ問う。** (1) この変更は何を変えるか（値の計算・widget の構成・窓のライフサイクル・色・縦位置） (2) **その出力を消費する層まで届いているか**。(2) を飛ばすと、上の 2 例のように「全部緑なのに動いていない」へ落ちる。

**判定を持たない道具を層に数えてよい。** `check:input-metrics` は表を出すだけで合否を言わないが、**その層が無ければ差分は誰にも見えない**。フォント依存の 1px のように残余が構造的なとき、閾値を置けば「常に緑」か「常に赤」へ倒れる——**永久に赤いゲートはゲートが無いのと機能的に同じである**（`check:colors` が同じ理由で旧述語を捨てた経緯は `docs/adr/ADR-declared-colors-over-modal-color.md`）。合否を人間へ残す判断は、層を持たないことと同じではない。

## 列挙の完全性

全文監査・全箇所改名・コンパイラを持たない機構の廃止のように、**網羅性そのものが要件**のタスクでは、単一の分解枠組みは自身の盲点を構造的に継承する（#404）。第一の手段は独立再導出（枠組みを変えてもう一度導出し、差分を取る。手順は `/plan-review`「Step 2b — 独立導出による網羅性レビュー」）であり、それに加えて次の 3 クラスが特に取りこぼしやすい。**この 3 つは `/plan-review` の実行中に限らず効く**——手作業のスイープ・改名監査・規範文書の移動でも同じ形で踏む（#826 で `/plan-review` 本文から移設）。

- **その一覧の母集団を誰が知っているかを先に答える**: 正本は 4 通りしかない——**コンパイラ**（enum variant・trait impl）／**ソーステキスト**（`const` の集合・モジュール内の関数）／**ファイルシステム**（対象文書・glob）／**外部設定**（CI job・npm script）。「網羅を守ると主張しているか」は意味の問いで判定がぶれるが、「母集団を誰が知っているか」は構造の問いで一意に決まり、**分類が決まれば足し忘れを捕まえる変異の形も倒し先（射程を doc へ明記するか機構へ載せるか）も決まる**（#1011）。**文言の読みは篩、変異の実測は確定**——doc もコードももっともらしく見え、variant を実際に足して測って初めて「1 本も落ちない」と判明した例がある（#1000）。
- **列挙の SSOT はツール自身に問う（glob の意味論はツールごとに違う）**: `git` pathspec の `**/` は 1 段以上を要求し、`git ls-files` はブレース `{ts,tsx}` を展開しない。#471 はこれで深さ 0 の実在ファイルを列挙から落とした（当時は TypeScript の `exclude` の `**/` が 0 段にもマッチするという差が絡んでいた。フロントは #532 SU7 で撤去済みで、残るのは**意味論がツールごとに食い違う**という一般則である）。追跡ファイルなら `git ls-files <dir>` の全件フィルタ、ガバナンス文書なら `npm run governance:check` の照合件数のように、**当のツール自身に列挙させ、件数を証跡に残す**。**そのうえで出力を切るオプション（`head` / `Select-Object -First` / harness の Grep ツールの head_limit）を列挙に使わない**——ツールに列挙させても、切った時点で母集団は自分の推測に戻る（#666 で `grep ... | head -40` がアルファベット順で後ろの `PERFORMANCE.md` を落とし、スカウトが拾った）。
- **順序に依存する参照は、削除・挿入で気づかれないまま不整合になる**: 章番号・ルール番号のような**序数**で他所から参照されているものを削除・挿入するときは、参照側を全部数え上げる——概念ラベルで参照している箇所には当の語の grep では到達しない（#482 では番号参照する OPEN issue 5 件を独立再導出だけが検出した）。**直すときは番号ではなく名前で参照し直す**（命名の規約は `.claude/rules/governance-docs.md`）。
- **検索パターンは「概念」ではなく「自分が想定した書き方」を列挙する**: 同じ概念が複数の綴りで書かれていると、具体的なパターンは他の綴りを**静かに落とす**——出るのは 0 件ではなく**少なすぎる件数**なので、「1 箇所にしかない」という誤った結論がそのまま設計判断になる。#843 で 2 回踏んだ: `trace\] `（BRE では `\]` が `]` になり、ファイル側の `\[trace\]` に当たらず 2 本中 1 本を落とした）と `Get-Process -Name 'snotra'`（他 5 本は `Get-Process snotra` と書く）。どちらも「重複ではなく穴だ」という逆の診断を一度出した。**概念を数えるときは緩いパターンで全件を出してから目で分類する**か、**別の綴りを想定した第 2 のパターンで件数を突き合わせる**。件数が動いたら、動かなくなるまで緩める。**日本語の散文では書式そのものが綴りを割る**——`**`（強調）は語中に挿入されうるので、複合語を丸ごとパターンにすると静かに取りこぼす（`可視性を**変える**` は `可視性を変える` に当たらない）。**語幹の最短形で引く**（`可視性` だけで引き、絞り込みは目で行う）
- **列挙から列挙への転記は機械で差集合を取る**: 独立導出やスキャン結果を計画・実装へ手で写すと、件数が数十を超えたあたりで 1 件落ちる——落ちた 1 件は転記先だけを見る後工程からは見えない（#884: 導出 69 件を計画の表へ目視反映して 1 件落とし、転記元を知らない**再計測**が拾った）。転記の完了は「写し終えた」ではなく、転記元と転記先を機械で突き合わせた差分ゼロで宣言する。
- **コンパイラを持たない機構（CI トリガー・GitHub ラベル・スキル/ドキュメントの規約）を廃止・変更するとき**は、定義だけでなく依存側（別 workflow・スキル手順・ラベル運用）を機構名で grep + 独立再導出して数え上げる——検出器が無く、漏れた消費者は **false green で気づかれないまま残る**。**「コンパイルが通る＝消費者の漏れ無し」はコンパイラのある領域でしか成り立たない**（#145）。

## デバッグ・バグ修正

- バグ修正時は、コードを書く前に根本原因を一文で明示する
- 根本原因の説明には「壊れた不変条件（何が常に成り立つべきだったか）」を必ず1つ含める
- 最初の修正案が失敗した場合、同じ深さで別の推測を試みるのではなく、より深い調査に切り替える
- バグ修正時は、修正対象のパターンをコードベース全体で検索し、同一パターンが他にも存在しないことを確認してから完了とする（計画時の影響列挙版は `AGENTS.md`「バグ発見時は同一パターン全コードパス検索を行う」）
- **「値を渡していない」と「渡したが受け手に無視される」は別の欠陥様態であり、呼び出し側の grep では後者に到達しない。** 前者を探す検索（引数の欠落・未指定）は、**引数が書かれている箇所を全部「対処済み」に見せる**。ライブラリのウィジェット・API に値を渡す欠陥を 1 件見つけたら、**同種の値を渡している他の箇所について「受け手が実際にその値を使うか」をライブラリのソースで確かめる**。#654: 検索入力欄は 2 つの文字列を持ち、入力テキストは色を**渡しておらず**、hint は色を**渡していたが egui 0.35 の TextEdit が `weak_text_color` で無条件上書き**していた（egui 自身が "users won't be able to override it" と注記）。前者だけを直す修正で「テーマ消費の完全化」を主張しかけ、後者は `/plan-review`「Step 2b」の独立再導出が拾った。**受け手のソースを読むまでは、渡した値が届いたことにならない**
- **サブエージェントの報告が届かないとき、エージェントが死んだと決めない——`name:` を渡したかを見る。** `Agent` tool に `name:` を渡すと `taskKind: "in_process_teammate"` になり、**最終テキストが呼び出し元へ配送されない**（届けるにはエージェント自身が `SendMessage` を呼ぶ必要がある）。名前なしなら async task となり完了時に自動配送される。実測: 名前なしは 1 行が 2.7 秒・約 4,700 字が欠落なく到達。名前ありは turn 終了ごとに idle_notification（harness のメッセージ種別）（意味は「完了」ではなく**「待機中」**）だけが届く。ツールの返答文にも差が出る——名前なし=「完了時に自動で通知される」／名前あり=「mailbox 経由で指示を受け取る」。**成果は消えていない**: `~/.claude/projects/<project>/<session>/subagents/agent-a<name>-<hash>.jsonl` に全文が残り、`type=="assistant"` の text ブロックを繋げば回収できる（同階層の `.output` は**エージェントが走らせた Bash の stdout** であって transcript ではない）。2 セッション独立で 9 回中 8 回踏み、**そのたびに督促（`SendMessage`）で回復できたため 8 回とも機序を測らなかった**——安い回復手段は、根本原因を探す動機を奪う。規範側の対処は `CLAUDE.md`「サブエージェント委譲と worktree」
- `tauri.conf.json` や platform 固有ファイルに設定を追加する際は、その設定が Windows でサポートされているか事前に確認する（例: `tauri.conf.json` の backgroundThrottlingPolicy は Windows 非対応でビルドエラーになる。**現行の等価物が在ってはならない語**なので、識別子として書くと「現行語彙に無い」検査に当たる——バッククォートを外して素のテキストで書き、検索性だけ残す）
- 修正案が API 境界をまたぐとき、「呼び出し側パッチ」と「API 側で責務を完結させる修正」の両案を比較し、後者を優先する
- issue や plan.md の前提——特に **能力**（何を受け付けるか）・**セキュリティ防御**・**根本原因診断**——は、実装前に「対応する実行コード」と「兄弟機能の既存挙動」で裏取りする。issue 作者がユーザー本人でも前提は誤りうる。例:「instant の exe を `.exe` 限定にすれば防御になる」は実際には `Command::new` が `.bat`/`.cmd`/`cmd.exe` を受理して誤り（#395）。「footer 赤枠は id 重複」という診断も真因は id 不安定性で egui の push_id は効かず（#456）。`/plan-review` のサブエージェントは作者の枠組みに anchor しやすいため、盲点の是正には実証が要る。外部 issue・上流仕様を根拠にするときの時系列・最終 maintainer 回答の確認は `start-issue`（#565）が担う
- 乖離（実装とドキュメント・二つのコードパス等の食い違い）を解消するときは、issue が提示する「片方に揃える」二択を鵜呑みにせず、まずコードで前提を裏取りする——一方が呼び出し元の無い死蔵コードなら、**削除**が乖離の根本を断つ最小解になりうる（#409。選択肢空間は前提の裏取りで広がる）。削除の安全性は静的 grep + 独立再導出 + **compile/typecheck を「死蔵検出器」として使う**（live import が残れば module-not-found で落ちる）の独立経路で裏付ける
- 競合しやすい一時状態（通知・ローディング・遅延処理）を導入する場合は、タイマーや購読のライフサイクルを単一管理し、再実行時に必ず前回のハンドルを破棄する
- ガード（ロック・フラグ・CAS）を追加するときは「どの関数を守るか」ではなく「どのリソースを守るか」で設計する。同じリソース（ファイル・共有状態）を触る経路が複数あれば、全経路が同じガードを通るようにする。関数単位のガードは別経路の追加時に素通りされる
- **他者の指摘を自分で測り直すとき、「測って出なかった」を不在の証拠にしない——再現には入力の形が要り、その形は指摘者が持っている。** `AGENTS.md`「検証の作法（全タスク共通）」が求める「判定の中核は自分で測る」を実行しても、入力を取り違えれば**成立する指摘を棄却する**。#768: レビューが報告した正規表現の指数爆発（`FLAG` の `--x` が「`-`+`-x`」「`--`+`x`」の 2 通りに分割できる）を `git log --f0=v0 …` で測って 0.0ms を得て「問題なし」と判断しかけたが、`log` が非フラグなので量指定子が 0 回で即失敗し、**バックトラックがそもそも起きない入力**だった。フラグを `git` の直後に並べて初めて 747ms（n を 1 増やすごとに倍増）が出た。**再現しないときは自分の入力が指摘の条件を満たしているかを先に疑う**（報告に入力が書かれていなければ、それを聞くのが最短である）
- テストや挙動の red を自分の変更による回帰と断定する前に、変更前のベースライン（`main` 等）で同じ条件を実行して A/B 比較する。両者が一致すれば、その差分は原因ではない（既存バグまたは環境要因）。検索・索引など自分が触った領域の失敗ほど、思い込みを排してベースラインと突き合わせる。性能評価も同様で、同一マシンでの A/B でのみ退行を判定する（異なる環境の記録値との比較で判断しない）
- 層をまたぐ不具合は、上位層（UI）の症状から推測せず、最下層を直接観測して切り分ける（backend IPC を直接呼ぶ、アプリにロード済み状態をダンプさせる等）。観測点は `SNOTRA_TRACE`（`crate::trace_main`）のように、release ビルドでも残り最下層から直接読めるものを用意する
- 性能の訴え（もたつき・入力遅延）を調査するときは、まず **debug ビルドを疑う**。未最適化の CPU 密ループ（自作ラスタライザ・画像処理等）は release の 10-50× 遅く、`cargo run`（debug）の体感を実問題と誤認しやすい。release で再測してから原因を絞る（#532 SU1:「秒単位の IME 遅延」の正体は debug の `fill_mesh` 全画面塗り、release で 8× 改善し許容水準）。あわせて**症状の出所を先に切り分ける**——全 UI に及ぶなら renderer 性能、特定入力だけなら経路固有（「英語でも遅い・ウィンドウ移動も鈍い」の一言で renderer 性能と確定した）
- **その差分が触っていないコードでも「検証済み」ではない。** 移行で無改変のまま持ち越した経路が、新アーキで一度も実行されていなければ未検証である——受け入れで能動的に動かして確かめる（#532 SU1: runtime の IMM32 IME 経路は SU1 無改変だが人間が初検証で二重表示が露見。#582 は削除済み winit spike を検証していた）
- **周期の理論値から負荷を見積もらない——増幅段は理論値に現れない。** 機構を正しく同定していても、その周期がそのまま負荷になるとは限らない。#628: 源をキャレット点滅（on 0.5s / off 0.5s）と特定し「アイドルは 2fps・CPU 1% 未満」と見積もったが、実測は **11.5fps・5.1%** だった——`predicted_dt` の既定値が短い repaint 予約を「即時再描画」へ飽和させ、遷移ごとに 26ms スピンする**増幅段**が間にあった。**見積りを選択肢の比較表に載せてユーザーの判断材料にするなら、それが実測か理論値かを明示する**（この 5.8 倍の差は、実測前に提示した「受容しても 1% 未満」という判断根拠を無効にした）
- **修正は、それ自体が新しい欠陥の生成過程である——指摘への対処を検査するときは「指摘は解消されたか」と「この修正が何を持ち込んだか」を別々に問う。** 片側だけを見て直すと反対側へ倒れる: 狭すぎる全称を広げれば広げすぎになり、2 軸を 1 事実へ畳めば前提が落ち、落ちた前提を段落で補えば同じ事実が 2 か所になる（#725 で同型の失敗を 4 度踏んだ。3 件目を捕まえたのは、後者の設問を明示的に置いたレビューだけである）。**足す前に「その事実はすでにどこかに書かれていないか」を問う**——追加は常に重複の候補であり、書く側からは補強に見える。重複だと分かるのは片方だけが更新された後、つまり事故が起きた後である
- **その問いに答えられるのが実測だけのことがある——対処が「人間が裁定した仕様」や「実測で確かめた挙動」に触るなら、採用の前に測り直す。** レビュー指摘の動機が一次資料に照らして正しくても、その対処が正しいとは限らない。#738: `any_down()` がプロセス寿命のあいだ `true` に固着しうる（egui は `Event::PointerButton{pressed:false}` 以外で押下フラグを落とさない・実装で確認）という指摘は正しく、対処案（reset-on-show のフレームだけガードを外す backstop）も筋が通っていた。**実測するとドラッグ中も毎フレームクランプが走り、人間裁定「ドラッグを終えたら戻る」を壊していた**——窓が指から逃げる形の退行である。ユニットテストも smoke も緑のままで、**対照実験（対処の有無で同じ操作の窓矩形を比べる）だけが差を示した**。動機の正しさは対処の正しさを含意しない
- **検査が緑になったことと、その検査が正しい対象を見たことは別である。** 照合件数が増えても、指す先が意図した相手とは限らない——件数は「参照が生き残った」ことしか示さない。**「何件通った」を根拠に「正しい」と言わず、正しさは別の観測で裏付ける**（指した先を直接読む・fixture で両方向を押さえる）。#725: 見出し参照 3 件を正準形へ直したことは件数の増分（74→77）で確認できたが、意図した見出しを指しているかは grep で個別に確かめた
- **原因は推測せず、名乗らせる手段を先に探す。** 「毎フレーム積まれる常在項」は cause 欄に必ず現れるため、**原因の同定は cause 名だけでは足りず、時間構造（バーストの長さ・間隔の分布）が要る**（#628: 全フレームの cause が点滅だったが、引き金は 480ms の待ちと 26ms のバーストという構造が示した）。ライブラリが原因を報告する API を持つなら計器化を優先する（egui の `Context::repaint_causes()` は `file:line` を返す）
- **人手の観測時間には、観測条件を変える確認作業を混ぜない。** #628 の再測で、カーソル挙動の目視確認のためマウスホバーを同じ run に含めた結果、`ScrollArea` のフェードアニメーションが混入してアイドル計測が無効になった（測り直し）。目視確認は計測を止めてから行う。あわせて**ログのフラッシュ経路を手順に含める**——PowerShell の `Tee-Object` はパイプが閉じるまで書き出さないため、プロセスを終了させるまでログは 0 バイトに見える
- **観測条件が揃わない可能性に備え、プロトコル非依存の判別指標を用意する。** 総フレーム数や平均 fps はセッション長・操作量に汚染されるが、**局所構造**（#628 では「点滅待ちの直後に何フレーム続くか」）はそれらに依存せず、汚染された run からでも結論を出せる（修正前 0% / 修正後 100% がスピン消失を単独で証明した）
- **「このテストは X を検出する」と doc に書いたら、X を実際に起こして落ちることを確かめる。** 検出力の主張は実装より強くなりうる——#745 で「対照テスト 2 本が reset の呼び出しを消す変更を落とす」と書いたが、実測では**呼び出しを削除しても全数が通った**（あの 2 本は reset を呼ばない場合の挙動を assert するので、消えたときにこそ通る）。危険なのは向きである: 同じ差分の 4 か所が正しく「検知手段は無い」と書いているなか、**テストの doc だけが「呼び出し点は守られている」と誤信させた**。`.claude/rules/safety-nets.md`「効いていることは、フォールトインジェクションで一度は実測する」を**ユニットテストの doc にも当てる**——対象がセーフティネットでなくても、検出力を名乗った時点で同じ規律が要る
- **時限的な挙動の実機シナリオに、人間の反応時間より短い操作を要求しない。** 単純反応時間は〜200ms で、それより短い時限（#745 の blur 猶予は 100ms）の内側に手作業を差し込むシナリオは**原理的に実行できない**。#745 では計画レビュー 5 体を通してなお 3 シナリオがこの形で書かれ、実機で初めて不能と分かった。注入での代替も当てにしない——`SetForegroundWindow` はバックグラウンドからの呼び出しを OS が制限し、PowerShell からの呼び出し自体に 165ms かかる（実測）。**時限より短い窓が要るなら、その不変条件は純粋核テストへ降ろす**（実機は回帰確認だけを担う、と射程を明記して分担する）
- **レビュー通過・実行できた ≠ 実行時リソース挙動が検証済み。** 価値の中核が実行時プロパティ（メモリ常駐量・アイドル CPU/再描画・レイテンシ）である変更は、コードレビューがそれを見ない——受け入れで**計測**して初めて確かめられる。#532 SU6.5: egui hide 経路は SU2〜SU6 でレビューを重ね「Ready to merge」だったが、hidden で working set trim が効かず可視時同値 43MiB のままだった gap は SU6.5 の計測ゲート（メモリ実測）だけが暴いた（`hide_egui_main` が WebView2 の EmptyWorkingSet trim を呼んでいなかった）。「設計を決める前に測る」（#634/SU4 プローブ）と対を成す「マージする前に測る」——計測ゲートはレビューと冗長でなく、別クラス（実行時挙動）を捕える
