# 開発原則

このリポジトリで共有する設計と実装の原則である。人にもエージェントにも当てる。

本書の中心は、原則と、局面ごとに立てる問いである。具体の規則は、それを使う瞬間に届く文書（`AGENTS.md`・各 crate の `CLAUDE.md`・`.claude/rules/`・`docs/comment-guidelines.md`）に置く。本書にも、原則の理解に要る具体則が一部残っている。経緯と実測は issue と ADR に置く。条項を短くしても、前提と境界条件は条項の側に残す。

## 局面ごとに立てる問い

局面に来たら、まず問いを立てる。答えは右の節にある。

| この局面に来たら | 立てる問い | 節 |
|---|---|---|
| 新しいコードを書く・抽象化する | 今の要件で、いちばん単純な形はどれか | `docs/development-principles.md`「単純に保つ（KISS・DRY・YAGNI）」 |
| 何かを消す・移す | 消す差分の中で、**新しく書いた一文**はどれか | `.claude/rules/governance-docs.md`「条項を足す・消す・移すとき」 |
| 散文に精密な事実を書く | この一文は、振る舞いを保つリファクタを生き延びるか | `docs/development-principles.md`「文書に書くこと、コードに任せること」 |
| config から状態を導いて持つ | 既定の live-read で足りないか。キャッシュにするなら、無効化の所有者は誰か | `docs/development-principles.md`「config から導く状態はキャッシュとして扱う」 |
| config を足す・既定値を書く | この値の消費者は誰か。導出は 1 経路か | `docs/development-principles.md`「config の値は、読まれなくても誰も気づかない」 |
| フラグ・モードを足す | 単一の概念か、直交する複数の軸か | `docs/development-principles.md`「モードは 1 か所で導く」 |
| 規範に条項を足す・書き換える | この面の役割は、読者に行動を求めるか。リードを読んだだけで次の動作が決まるか | `docs/development-principles.md`「規範の書式は文書の役割から選ぶ」 |
| 規則を守らせたい | いまどの段で守られているか。1 段上げる費用は見合うか | `docs/development-principles.md`「規則を守らせる強さ」 |
| 「検知手段が無い」と書きかけた | 検知できる設計へ変えられないか | `docs/development-principles.md`「検出器を置くとき」 |
| 検査・検証手段を新設する | その手段は何を見ていないか。出力は、消費する層まで届いているか | `docs/development-principles.md`「検証の手段と、見ていないもの」 |
| 網羅性が要件 | その一覧の母集団を誰が知っているか | `docs/development-principles.md`「漏れなく数える」 |
| バグを直す | 壊れた不変条件は何か。この修正は何を持ち込んだか | `docs/development-principles.md`「バグを直す」 |
| 実機で計測する・足場を置く | 観測条件を変える作業が混ざっていないか。撤去の合図は何か | `docs/development-principles.md`「観測するとき」 |
| 案の採否・欠陥の有無を実測で決める | 対照列は在るか | `docs/development-principles.md`「確かめるときの落とし穴」 |

「主張は代理ではなく対象そのもので測ったか」は全タスクに効くので、`AGENTS.md`「検証の作法（全タスク共通）」が持つ。

## 単純に保つ（KISS・DRY・YAGNI）

今の要件で、いちばん単純で読みやすい形を選ぶ。

- 責務をまたぐ実装をしない。責務の境界は、各 crate の `CLAUDE.md` にある
- 新しいコードは、既存のファイル構成・命名・パターンに合わせる。独自のパターンを入れる前に、既存のパターンを使えないかを検討する
- 同じロジックの繰り返しは 2 回まで許す。3 回目で抽出を検討する。無理な抽象化より、多少の重複を選ぶ
- 同じ事実を複数の文書に書かない。正本を 1 か所に決め、ほかからは参照する
- 使う予定しかない抽象化（trait・generics・層）と、要求を超える機能を入れない。拡張性より、今の要件での単純さを選ぶ

## 消すとき

被依存の無い対象には、コンパイラの目が届かない。拾えるのは、手の列挙と最後の grep だけである。

- **旧 API を消すときは、名前で参照している文書を grep で数える。** compile-fail が名指すのはコード参照だけである（#752）。現在形で古くなる記述は直し、歴史を述べて真のままの記述は残す。ADR と設計書は、当時の名前のままでよい
- 文書を消す・移すときの作法は `.claude/rules/governance-docs.md`「条項を足す・消す・移すとき」に、Rust の公開面を狭めるときの作法は `.claude/rules/rust.md` にある

## config から導く状態はキャッシュとして扱う

config から導く状態は、キャッシュとして扱う（#347・#348）。

- **既定は live-read にする。** 毎回 config から計算し直し、計測して高くつくと分かったものだけをキャッシュにする。安いものを焼き込むと、設定の変更が反映されなくなるだけである
- **キャッシュにするなら、無効化の所有者を決める。** 所有者が居ないと、設定の変更の取りこぼしやデータ損失を招く
- setter で追従させるより、そもそも焼き込まない形を選ぶ
- 詳細設計は `docs/design/2026-05-31-coherence-staleset.md` にある

## config の値は、読まれなくても誰も気づかない

関数は呼ばれなければ `dead_code` になり、型は変えれば下流が compile-fail する。config のフィールドには、こうした検出器が無い。定義して誰も読まなくても、コンパイルは通る（関数の検出器にも穴はある。lib crate の `pub` 項目は、呼ばれなくても警告されない）。

- **欠如は 3 つの形で現れる。** 消費者ゼロ・導出が 2 経路・既定値の偶然の一致である。どれも、値が参照ではなく写しとして流れた結果である
- **自動で回る検証は、既定値の下でしか走らない。** 乖離は、利用者が既定と違う値を設定するまで表に出ない（#802）
- **規範では止まらない。** 写しは、変更者が通らない場所に散る。規範ではなく機構で守る（#794 は、config 側と platform 側が同じ型を消費する形で解いた）
- 具体則は `snotra-core/CLAUDE.md`「Config のフィールドと既定値」にある

## モードは 1 か所で導く

フラグの組み合わせでモードを表すと、排他と優先順位が複数のガードに散る。状態を 1 つ足したとき、ガードの更新を忘れても誰も気づかない。

- **散在したガードを見たら、単一の概念か、直交する複数の軸かを問う。** 単一の概念なら、1 つの判別子と導出関数にまとめる。直交する軸なら、軸ごとに名前を付けて分ける
- **優先度と排他は、導出源の 1 か所だけに書く。** ガードはその導出を使うだけにする。そうすれば、状態を足したときの分岐漏れを、網羅 `match` に検出させられる
- **単一の情報源だった状態を消すときは、その判定を誰が引き継ぐかを先に決める。** 状態は、ある判定の唯一の評価点という役割を暗黙に担っていることがある。決めないと、判定が使う側へ再び散る。必要なら、述語を共有のヘルパへ抽出する
- このリポジトリでの実体は `src-tauri/CLAUDE.md`「状態の二軸導出（`search_state.rs`）」にある

## 規則を守らせる強さ

規則を守らせる手段には、強さの序列がある。

> 構造で不可能にする（型・導出・単一通過点） ＞ コンパイルで検出（compile-fail・`#[must_use]`） ＞ テスト・CI で検出 ＞ チェックリスト・レビューで検出 ＞ 書き手の記憶

設計とレビューでは、「この規則はいまどの段で守られているか。1 段上げる費用は見合うか」を問う。次の 8 つは、#426〜#442 の課題群から抽出した構造の原則である。

1. **同じ知識の第 2 表現を手書きで維持しない（Derive, don't duplicate）。** 1 つを正本にして、残りは導出する（builder・テーブル駆動・宣言的な対応表）
2. **不変条件は単一の通過点（choke point）に閉じ込める。** 規則を 1 つの関数か型に閉じ、違反を書けない形にする
3. **純粋なロジックと副作用を分ける。** crate の境界で成り立っている分離を、ファイルと関数の単位でも保つ。判断と実行が 1 つの関数に混ざって肥大したら、分ける合図である
4. **テストできる構造を、横断の要件として扱う。** 死角は、テストが書けない・回らない構造に生まれる。次の 3 つを、構造の受け入れ条件にする。永続化の経路にディレクトリを注入できること。全 crate のテストを CI で回すこと。UI の各層に検証ハーネスを 1 つ以上置くこと
5. **境界をまたぐ契約は、1 か所で規約として定義する。** 実装はその規約に従う
6. **検出は構造化された信号で行い、テキストは証拠に留める。** 判定には exit code・型・戻り値を使う。どこで切っても取りこぼすものを、検出の手段にしない（#471）。とくに次の 2 つを守る
   - パイプの exit code は、末尾のコマンドのものになる。出力を絞るなら、`set -o pipefail` を先に置く（#812・#858）。出力が数行のコマンドは、そもそも絞らない。Bash に固有の危険で、PowerShell の `$LASTEXITCODE` は保たれる
   - 判定は、文字列が現れたかではなく、どの構文の位置に現れたかで決める（#482）
7. **失敗の向きは、経路ごとの処理ではなく既定値に埋め込む。** 安全側を既定値にし、安全を確かめた経路だけがそれを覆す。未知の経路は、自動で安全側に倒れる（#482）。既定値の除去と反転を検知するテストも置く
8. **全称条件だけの検査は、集合が縮むと空振りする。守りたい要素は名指しする。** ∀ 条件には、非空だけでなく、守りたい要素が在るという ∃ 条件を組にする（#713）。カナリアが、消えたら困る識別子そのものを持つのは、写しではなく設計である

この序列を運用するときの目安を 2 つ置く。

- **チェックリストが要る箇所は、構造が規則を吸収できていない箇所である。** 構造が吸収したら、チェックリストを消す。文書が軽くなることを、設計改善の検収条件にする
- **やりすぎない。** trait 化・コード生成・既存契約の一斉移行より、通過点の関数 1 つ・テーブル 1 枚・新規分からの規約化で 8 割を取る

## 文書に書くこと、コードに任せること

散文の陳腐化は、コードの精密な事実（式・バイト形式・列挙・機構名）を写した箇所から生じる（#404・#410）。

- **振る舞いを保つリファクタを生き延びるものを、文書に書く。** なぜ・何を・全体の構造は文書に書く。機構名・バイト形式・式はコードを正本にして、そこを参照する。書き方の規約は `docs/comment-guidelines.md` にある
- **参照するには、参照先に正本コメントが要る。** 参照先にインラインのコードしか無いなら、そこへ intent と式を書いた正本コメントを置き、SSOT として指名する
- **生成（doc-gen）より参照を既定にする。** 精密事実が十数件の規模では、ツールの固定費が便益を上回る
- **写すしかない精密事実は、一致を確かめるテストで守る**
- **規律の宛先（錠・層）を移したら、規律が挙げる理由も測り直す。** 宛先が変わると、文が真のままでも害の種類が変わる（#1123 では、遅延がデッドロックに変わった）。契約を 1 か所へ集める改稿は、書き直す機会に見えて、写す作業になりやすい

## 規範の書式は文書の役割から選ぶ

行動形は、読者が次に取る動作で終わる形である（`config の読みは read_config を通す`）。事実形は、断定で終わる形である（`Layer 1 は best-effort である`）。読んで次の一手が出るのは、行動形だけである。

- **書式は候補であって、規則ではない。** 役割から書式は一意に決まらないので、条項ごとに決める
- **決めるときは、条項を `A のときは B する。C が起きたため（#NNN 実測）` の形へ書き換えてみる。** 書き換えられるかどうかでは決まらないので、あわせて 2 つを問う。その面の役割が、読者に行動を求めるか。書き換えると失われる保証があるか（適用範囲の宣言は、逸脱の明記と対で初めて真になる。片方だけ書き換えると、全称が実装より強くなる）

| 役割 | 書式の候補 |
|---|---|
| 運用ガイド・開発プロセス（常時ロード） | トリガー → 行動／参照先 |
| 編集の瞬間の手助け（`.claude/rules/`） | `A のときは B する。C が起きたため（#NNN 実測）` |
| 開発原則・判断の型（本書） | 局面 → 立てる問い |
| モジュール固有の不変条件 | 行動形 + 適用範囲の明示 |
| プロダクト知識（地図） | 構造を記述する。**行動形にしない**（#326） |
| コマンドリファレンス | 索引 + 行動形 |
| 様式規約 | 様式を規定する |

役割の出所は `AGENTS.md`「ドキュメント参照」である。条項を足す・書き換えるときの作法は `.claude/rules/governance-docs.md`「条項を足す・消す・移すとき」にある。行動形と事実形のずれを見るゲートは作れない。語形では割れないためで、経緯は `docs/superpowers/specs/2026-08-22-norm-format-by-role-design.md` にある。

## 検証の手段と、見ていないもの

「規則を守らせる強さ」は、規則をどの強さで守るかを問う。この節は、検証の手段が何を見ていないかを並べる。コマンドと実行条件の正本は `docs/build-commands.md`「変更後の検証チェックリスト（必須・スキップ不可）」である。並べるのは実行する検証で、型や hook のように走らせなくても効くものは、「規則を守らせる強さ」が扱う。

| 層 | 手段 | 保証するもの | **見ないもの** |
|---|---|---|---|
| 純粋核のロジック | `cargo test`（`snotra-core` / `layout.rs` / `ime.rs` 等） | 入力 → 出力の変換 | **その出力が消費されているか** |
| egui の論理座標 | `cargo test`（`view.rs` の kittest・`run_pass`） | widget の構成・順序・論理位置 | **実ピクセルへの丸め・実フォント・DPI** |
| node の純関数 | `npm test`（vitest） | `scripts/` と hook の判定ロジック | それが実際に配線されているか |
| PowerShell の純関数 | `test:powershell` | 判定ロジック（色・幾何・trace 不変条件） | 実際のウィンドウ |
| 起動と配線 | `smoke:startup` / `smoke:egui` | 起動・hotkey 登録・show/hide・trace 不変条件 | 見た目 |
| 実ピクセルの色 | `check:colors`（判定あり） | 宣言色が届いているか | 位置に紐付かない（クロス配線） |
| 実ピクセルの幾何 | `check:input-metrics`（**判定を持たない**） | 入力欄の縦位置の実測値 | 合否——読むのは人間 |
| 人間の目視 | `smoke:manual` | 総合的な違和感 | 実施の記録（残さないと未実施と区別できない） |
| 文書の整合 | `governance:check` | 参照・索引・命名の実在 | 意味の側（責務の妥当性等・受容する残余） |

- **穴は、層の内側ではなく境界に空く。** 各層は自分の担当を保証するので、抜けるのは「層 A の出力が層 B へ届いているか」である。`ime::active_range_chars` はテストが緑のまま、描画がその値を使っていなかった。入力欄の縦中央寄せは、論理座標では対称なのに実機で 1px ずれた（どちらも 2026-08-11 実測）
- **層を選ぶときは、変更が何を変えるかと、その出力を消費する層まで届くかを問う。** 後者を飛ばすと、全部緑なのに動いていない状態になる
- **判定を持たないツールも、層に数えてよい。** 構造的な残余に閾値を置くと、常に緑か常に赤になる。永久に赤いゲートは、ゲートが無いのと同じである（`ADR-declared-colors-over-modal-color`）
- 計画文書の内部整合を見る層は、常設しない。要る計画では、臨時にレンズを回す（`ADR-plan-document-lens-not-permanent`）

**母集団を持つ検査では、母集団そのものが壊れる。** ソーステキスト検査（production のソースを読み、目的の呼び出しが在ることを assert する形）が典型である。経緯と却下した案は `ADR-source-text-probe-predicate-polarity` にある。

- **沈黙する向きは、述語の極性で決まる。** 存在形（`P.contains(x)`）は母集団が広がると、否定形（`!P.contains(x)`）は狭まると沈黙する。述語の形はこれで尽きないので、新しい形を足すときは、その述語がどちら向きに誤るかを問う
- **守りたい本体が母集団のどこかのファイルに在るなら、否定形から切り出しを外せる。** 外すなら、代わりに帰属の濾過層を置く。外しただけだと、禁止語の正当な出現で永久に赤くなる（#1112）。本体が母集団の外へ移りうる検査では、この前提が外れる
- **切り出しを持つ形は、行を `str::lines` で走査する。** helper は、LF と CRLF の両方の fixture で測る（#1077）
- **切り出しの helper は、母集団の形を共有する検査群ごとに 1 つに閉じる。** 禁じているのは写しであって、数ではない（`ADR-source-text-probe-helper-locality`）

### 検出器を置くとき

- **「検知手段が無い」と書きかけたら、検知できる設計へ変えられないかを先に問う。** 責務を検査できる層へ移すか、観測点を作る（#654）。残余の記録は最後の手段である
- 検出器を置く・動かすときの具体則は `.claude/rules/safety-nets.md`「検出器を置く・動かすとき」にある

## 漏れなく数える

網羅性そのものが要件のとき、単一の分解の枠組みは、自分の盲点を引き継ぐ（#404）。第一の手段は、独立した再導出である（`/plan-review`「Step 2b — 独立導出による網羅性レビュー」）。手作業のスイープ・改名の監査・規範文書の移動でも、同じ形で踏む。

- **その一覧の母集団を誰が知っているかを、先に答える。** 正本は 4 通りしかない。コンパイラ（enum variant・trait impl）、ソーステキスト（`const` の集合・モジュール内の関数）、ファイルシステム（文書・glob）、外部設定（CI job・npm script）である。正本が決まれば、足し忘れを検出する形も決まる（#1011）。文言の読みは粗い絞り込みで、確定は変異の実測で行う（#1000）
- **作業中の変更を含む母集団には、`git grep --untracked` を使う。** `git grep` は追跡ファイルしか見ない。新規ファイルを飛ばした結果は、成功した検索と見分けられない（#1210）。`grep -r` は `.claude/worktrees/` を混ぜる
- **列挙の意味は、ツール自身に問う。** glob の意味はツールごとに違う（#471）。列挙の出力を `head` などで切らない（#666）
- **検索パターンは、自分が想定した書き方しか拾わない。** 緩いパターンで全件を出して目で分けるか、別の綴りの第 2 パターンで件数を突き合わせる（#843）。日本語の散文は、語幹の最短形で引く（`**` が語中に入りうる）
- **除外句は、当たったもの全部を落とす。** 除外あり・なしの両方を走らせて差を見る。除外の根拠も、観測で確かめる（#1094）。母集団を散文で示すときは、母集団に入らないものを 1 つ名指す。名指せないなら、測っていない
- **1 つの理由を複数の対象へまとめて当てるときは、対象ごとに当たるかを確かめる**（#1201）
- **列挙から列挙への転記は、機械で差集合を取ってから完了を宣言する**（#884）
- **コンパイラを持たない機構（CI トリガー・ラベル・スキルや文書の規約）を廃止・変更するときは、依存側を機構名で grep し、独立に再導出して数える。** 漏れた消費者は、緑のまま残る（#145）

## バグを直す

### 原因を突き止める

- **コードを書く前に、根本原因を 1 文で書く。** 壊れた不変条件（常に成り立つべきだったこと）を必ず 1 つ含める
- 最初の修正案が失敗したら、同じ深さで別の推測を試さず、より深く調べる
- 修正したパターンをコードベース全体で検索し、同じパターンが他に無いことを確かめてから完了とする
- **値を渡していない欠陥と、渡したが受け手が無視する欠陥は別物である。** 後者は呼び出し側の grep に出ないので、受け手のソースで値が使われるかを確かめる（#654）
- **issue や計画の前提（能力・防御・原因の診断）は、実装前に実行コードと兄弟機能の挙動で確かめる。** 作者が利用者本人でも、前提は誤りうる（#395・#456）。外部の issue や上流の仕様を根拠にするときの確認は、`/start-issue` が担う（#565）。検討 issue では、比較している機構が今も在るかを先に確かめる（#761・#1234）
- **「片方に揃える」二択を鵜呑みにしない。** 片方が呼び出し元の無いコードなら、削除が最小の解になりうる（#409）。削除の安全性は、grep・独立した再導出・compile（死蔵の検出器として使う）の 3 つの経路で裏付ける
- **層をまたぐ不具合は、UI の症状から推測せず、最下層を直接観測する。** 観測点は、`SNOTRA_TRACE` のように release でも残るものにする
- **性能の訴えは、まず debug ビルドを疑う。** あわせて、症状が全 UI に及ぶか、特定の入力だけかで出所を分ける（#532）
- **周期の理論値から負荷を見積もらない。** 間に増幅段があると、理論値に現れない（#628）。比較表に載せる見積りには、実測か理論値かを書く
- **原因は推測せず、示させる手段を先に探す**（egui の `Context::repaint_causes()` など）。原因の名前だけでなく、時間構造（バーストの長さと間隔）も見る（#628）

### 観測するとき

- **人手の観測時間に、観測条件を変える確認作業を混ぜない。** 目視の確認は、計測を止めてから行う。ログが書き出される経路も手順に含める（`Tee-Object` は、パイプが閉じるまで書き出さない）（#628）
- **観測条件が揃わない場合に備え、セッションの長さや操作量に左右されない局所の指標を用意する**（#628）
- **一時的な足場は、撤去までを新設の時点で決める。** 対象は、調査・測定のための script・workflow・env フック・製品コード内の計装である
  - 新設時: 撤去条件と撤去対象を、その成果物自身の doc に書く。条件は「issue が閉じたら」ではなく、撤去より前に起きる事象で書く（#1370）
  - 撤去時: 引用されうる測定値を、`PERFORMANCE.md`「この文書へ記録するときの規約」に従って記録してから消す
  - 生ログ: 実 config・実索引で測った生ログは、リポジトリの外に置く。trace は利用者の実パスを載せ、このリポジトリは公開されている。コミットしてよいのは、経路を数えた派生の表だけである

### 直し方

- API 境界をまたぐ修正では、呼び出し側のパッチより、API 側で責務を完結させる修正を選ぶ
- 競合しやすい一時状態（通知・ローディング・遅延処理）は、タイマーや購読のハンドルを 1 か所で管理し、再実行のたびに前回のものを破棄する
- **ガードは、どの関数を守るかではなく、どのリソースを守るかで設計する。** 同じリソースを触る経路は、すべて同じガードを通す。偽の値も、露見した消費者で弾かず、値を導く点で無効にする（#1289）
- **修正そのものが、新しい欠陥を生む。** 「指摘は解消したか」と「この修正が何を持ち込んだか」を別々に問う（#725）。足す前に、その事実がすでにどこかに書かれていないかを問う
- **対処が、人間の裁定した仕様や実測で確かめた挙動に触るなら、採用の前に測り直す**（#738）

### 確かめるときの落とし穴

- **「この案は効かない」は全称の主張である。** 効かない例をいくら測っても、支持例にしかならない。却下するときは、この案が効く入力の形を 1 つ挙げ、それが母集団に無いことまで示す。示せないなら、「測った例では効かなかった」と弱める（#1214）
- **red を自分の変更の回帰と断定する前に、変更前のベースラインで同じ条件を走らせて比べる。** 性能の退行も、同じマシンでの A/B でだけ判定する
- **案の採否を実測で決めるときは、勝敗の比を分解する対照列も同じセッションで測る。** 判定が正しくても、添えた機序は誤りうる（#1059）。対照列は、片方の条件だけを外した列である
- **欠陥の再現を測るときも、対照列を並べる。** 症状が計測そのものを黙らせる形では、単独の測定から「起きなかった」と「観測できない」を区別できない（#1106）。修正後も、同じ 2 列を測る
- **差分が触っていないコードも、新しい構成で一度も動いていなければ未検証である。** 受け入れで実際に動かす（#532）
- **検査が緑になったことと、正しい対象を見たことは別である。** 正しさは、指した先を直接読むなどの別の観測で確かめる（#725）
- **他者の指摘を測り直して出なかったとき、それを不在の証拠にしない。** 再現には入力の形が要り、その形は指摘者が持っている（#768）。再現しないときは、自分の入力が指摘の条件を満たすかを先に疑う。報告に入力が無ければ、聞く
- **価値の中核が実行時の性質（メモリ・アイドル CPU・レイテンシ）である変更は、マージの前に計測する。** コードレビューはそれを見ない（#532・#634）
- 実機シナリオの書き方は `docs/build-commands.md`「エージェントが目視項目を自分で実施するとき」にある
