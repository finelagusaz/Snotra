# governance ドメイン Phase 3 — 台帳

> **For agentic workers:** 進みながら埋める台帳。1 タスク 1 コミット。

**Spec:** `docs/superpowers/specs/2026-08-19-governance-population-anchors-design.md`
**前段:** `docs/superpowers/plans/2026-08-19-governance-domains-phase2.md`（Ruling 節と「Phase 3 への申し送り」が前提）

**Goal:** **錨の無い母集団を無くす**（A）ことと、**錨が空虚でないことを機構で測る**（B）。
この 2 つは別の承認単位である——A は既知の沈黙経路を直接塞ぎ、B は錨の層自身を検める。

## この Phase は設計から再定義されている

設計 §3 の Phase 3 は「固定パスの 3 本へ錨を付ける」だった。**Phase 2 の Ruling がこれを廃した**
——残る 5 本は母集団が名指しされたファイルの中身から出るため、錨は検査自身の判定の言い直しになる。
設計は歴史資料ゆえ書き換えない。生きた記録はこの台帳が持つ。

## 着手の根拠になった実測（2026-08-20）

全 15 ドメインの錨 31 本について「貪欲に消しても真のまま残る最小の支え」を求めた。

- **`some` 形の錨は支えが 1 件**である。腕が丸ごと消えれば赤くなるが、**腕が 1 件を残して縮んでも沈黙する**
  （`scripts/governance/checks/` 直下が 42 件 → 1 件でも真）。31 本中 22 本がこの形だった。
- **強い錨はいずれも「別の SSOT から導いた `every`」である**（`CLAUDE.md` を持つ crate 全件・
  `.claude/skills/` の全ディレクトリ・workspace member 全件）。支えが母集団の構造そのものになる。

支えは貪欲な除去順に依存するため一意ではない。分類には足りるが、**正準値として機構へ埋め込まないこと。**

## A. 錨の無い母集団を無くす

Phase 2 と Phase 1 が「ドメインに属さない走査由来の母集団」として名指したまま残っている腕を閉じる。
**いずれも沈黙の向き**（腕が消えても検査は静かに対象を減らすだけ）である。

### A1 — `adrCitationDocs` の 2 腕

- **skills md の腕（13 件）は `skillDocs` と畳まない。** あちらは `SKILL.md` だけ、こちらは
  `.claude/skills/**.md` であり、実際に差がある（`.claude/skills/health-check/references/mechanized-checks.md`）。
  **この根拠を先に doc へ書く**——書かないとレビューが必ず畳めと言ってくる。
- 非 docs ソースの腕（138 件・最上位 6 ディレクトリ）。錨を最上位ごとに置けるか測る。
- 手順は Phase 2 と同じ（移送前後で集合同一・錨を併設）。凍結リストの刈り込みは不要。

- [ ] 2 腕をドメインへ出し、移送前後で集合同一を突き合わせる
- [ ] 錨を置き、B1 の写像へ載せる

### A2 — `headingRefDocs` の `.claude/` 腕とルート直下の腕

Phase 1 が「未着手のまま残した沈黙」として送ったもの。**この母集団は単一の filter（除外句の列）から
出ており腕の切り分けが自明でない**——錨を足すと正当な変更まで赤にする側へ倒れうる、というのが
当時の保留理由である。

- [ ] 2 腕の現在のメンバーを測り、腕を切り分ける述語を決める
- [ ] 除外句が増える将来の見積もりと併せて、錨を置くか「受容する残余」と宣言するかを決める
      （**置かない判断も成果である**。そのときは理由を本節へ書いて閉じる）

## B. 錨の空虚さを機構で測る

申し送りが要求した「完了判定を『腕ごとの絞り込みで発火を測る』形へ書き換える」の実体。

### B1 — 全錨に反証レシピを持たせ、腕ごとの発火を総称テストで測る

**腕の同定は自動導出できない**——実測 1 回目は腕を「1 ディレクトリ」で近似し、`docs/**`（複数
ディレクトリ）と ps 族（拡張子）の腕を誤分類した。ゆえに錨ごとに**宣言する**。

- 置き場は `domains.test.mjs` 側の写像（`"<ドメイン名>#<label>" → (members) => members'`）とする。
  本番コードにテスト専用のレシピを持たせない。
- **完全性 assert を 1 本置く**——全ドメインの全錨がこの写像に載っていること。載せずに錨を足すと赤。
- ⚠ **これは `npm test` の層に閉じる。** 本番の錨オブジェクトへ持たせれば `G-domain-anchors` が
  実行時にも見られるが、この案では見られない。**「本番配置と構造保証が同等」とは書かない**
  （同等なのは「レシピ無しの錨を足せない」ことだけで、評価される層は違う）。
- 総称テストの 3 点: `holds(full) === true` / `narrowed ⊊ full`（何も引いていない絞り込みを弾く）/
  `holds(narrowed) === false`。既存 4 ドメイン分の腕テストはここへ畳む（被覆 4/15 → 15/15）。

**支えの総称ゲートは作らない**——「支えが非空」は既存の `holds([], s) === false` と厳密に等価であり、
新しい情報は支えの**サイズ**だけである。サイズ 1 は `some` 形の性質であって欠陥ではない。

- [ ] 写像と総称テストを置き、既存の腕テストを畳む
- [ ] 錨を 1 本足して写像に載せ忘れる変異で、完全性 assert が赤くなることを測る

## 却下・保留したもの

- **`some` 錨を `every` へ強化する（第 2 の SSOT の導入）— 保留。** 唯一の確定候補だった
  `scripts/governance/checks/` 腕（`CHECK_MODULES` を第 2 SSOT にする案）は**配線できない**
  ——`registry.mjs` が `domains.mjs` を import しているため逆向きは循環し、registry は top-level
  `await` を持つので未初期化の値を掴む（実測）。`ctx` 経由・`buildDomains` の引数・`domains.mjs` 内の
  独立 `readdir` のいずれも、設計 §4「ドメインの導出は snapshot（と他ドメイン）だけを入力に取る」に
  反する。**§4 を改定する提案を別に立てない限り着手しない。**
- **「錨を強くする手は第 2 の SSOT に尽きる」とは書かない。** 別解がある——腕ごとの members を
  manifest の列へ載せれば部分的な縮小も base/head 差分で出る。**採らない理由は費用**で、
  members はファイルの増減で日常的に動くため毎 PR で宣言が要り、設計が退けた「ゴム印化」へ落ちる。
