# 規範の書式を文書の役割から決める Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 規範文書の条項を、読んだときに次の行動が分かる形へ寄せる。

**Architecture:** 文書の役割ごとに書式の候補を定め（正本は `docs/development-principles.md`「規範の書式は文書の役割から選ぶ」・役割の出所は `AGENTS.md`「ドキュメント参照」）、条項ごとに「書き換えテスト」で裁定する。ゲートは新設しない。条項の太字リードは `G-heading-refs` のアンカーなので、書き換えは参照の随伴修正とセットで行う。

**Tech Stack:** Markdown / `npm run governance:check`（Node・全 23 検査）/ `git` / `cargo check`（`.rs` の doc コメントに書かれた参照の検証）

**Spec:** `docs/superpowers/specs/2026-08-22-norm-format-by-role-design.md`

## Global Constraints

これらは全タスクの要件に含まれる。値は spec から逐語で写した。

- **すべてのタスクがセーフティネットの母集団に触る**（`AGENTS.md`「条件別チェック（トリガー → 参照先）」のセーフティネット行が「rules・skills・規範」を含む）。ルート `CLAUDE.md`「最重要ルール（常に適用）」により Claude が単独で判断しない。**着手前に、spec の「合意の記録」の射程に収まっているかを PR 本文で確認する。** 収まらない判断が要るなら、そこで止めて利用者に諮る。
- **各タスクは候補台帳を PR 本文へ載せる**（形式は共通の道具 (H)）。裁定は意味判断で機械では判定できないので、台帳が面の単位を覆っていることが受入条件である。
- **見出しへ昇格する前に、その面を `sectionOf` で切っている検査を確かめる。** `G-module-index` が見るのは `<crate>/CLAUDE.md` の 4 枚だけであり、他の面には当たらない。昇格先を `###` 以下にする理由は面ごとに違う。
- **`docs/comment-guidelines.md` はどのタスクも触らない**（spec が「行動形化を当てない面」として体言止めの分類ラベルが役割に合っていると裁定した）。

- **数値は UTF-8 バイトである。測るときは `wc -c` を使う。** `wc -m` と `awk length` の返す単位はロケールと実装に依存し、同じコマンドが環境によって文字数を返す（2026-08-22 に 2 つの環境で 216,329 と 422,374 に割れた）。日本語主体ではバイト ≒ 文字 × 2 なので「800 バイト超」は体感で約 400 字。
- **条項の太字リードは `G-heading-refs` のアンカーそのものである。** 照合は正規化後の**前方一致**なので、頭を変える書き換え（事実形 → 行動形）は着地していた参照を落とす。頭を残して末尾を足す書き換えは前方一致が生きるので安全。
- **見出しへ昇格するときは `###` 以下にする。** `##` は `sectionOf` の節を切り、`G-module-index` の順方向照合の母集団が finding を出さずに縮む。
- **定型スロット（規範／機序／機構の射程／受容する残余／前史）は任意である。** 持たない条項に節を作らない。
- **面は作業の単位であって裁定の単位ではない。** 条項ごとに書き換えテストを当てる。
- **`main` へ直接コミット・プッシュしない。** ブランチは `chore/734-norm-format-by-role`。
- **各タスクの検証が green になってからコミットする。**
- **行動形／事実形のずれを見るゲート（合否を持つ検査）を新設しない。** spec が測って却下した——語形では割れず、独立に書いた 4 本の述語がいずれも一点に収束しなかった。**計器（合否を持たない観測）の要否は spec が未決としている**ので、この計画では置かない。作業中に「これを機械で守れる」と思ったら、まず spec の当該節を読むこと。**既存の機構を再実装する道具も書かない**（共通の道具 (C) を参照）。

## 共通の道具

以降のタスクが繰り返し使うコマンド。**タスクごとに再掲せず、ここを参照する。**

**(A) 条項の列挙**（対象ファイルの条項と、そのバイト長）
```bash
grep -nE '^\s*- \*\*' <file> | awk '{ln=$0; sub(/^[0-9]+:/,""); printf "%s\t%d\t%s\n", substr(ln,1,index(ln,":")-1), length($0), substr($0,1,60)}'
```
**行番号を剥がしてから測ること。** `grep -n` の付ける `NNN:` を含んだまま `length($0)` を測ると、境界の条項が閾値を跨いで見える（2026-08-22 実測: `snotra-core/CLAUDE.md` で本文 799 バイトの条項が行番号込み 802 バイトになり、800 バイト超の本数が 7 → 8 に化けた）。**同じ型の混入が `grep -Hn` のファイル名でも起きている**（初版の設計が最長条項を 5,035 と書いた誤り。実際は 5,012）。

**(B) あるファイルの条項を指す正準形参照の列挙**（書き換え前に必ず取る）
```bash
git grep -n -oP '`<file>`\s*の?\s*「[^」]+」' -- . | sort -u
```
**`-oP`（PCRE）を使うこと。`-oE`（ERE）では `\s` が効かず、静かに数件しか拾わない**（2026-08-22 実測: 同じパターンで ERE 6 件 / PCRE 650 件）。

**(C) 参照の着地は機構に委ねる。自前で判定器を書かない**

**この工程で機構を再実装してはならない。** `.claude/rules/governance-docs.md`「ガバナンス文書の参照と命名のルール」が「対象として認める綴りの正本は `scripts/governance/lib.mjs` の `isRefTargetSpelling` である——**ここへ写さない**」と定めている。2026-08-22 に Phase 1 の実行中、この禁止を破って着地判定器を自前で書いたところ、`governance:check` が passed の状態で **MISS 52 件の偽陽性**を出した（検査自身の fixture の架空見出し・歴史記述の旧リード・`<file>:<行番号>` 形などを拾う）。**判定器を書き直すのではなく、書かないことが正しい。**

- **生きた面の参照**: `npm run governance:check` の `G-heading-refs` が照合する（共通の道具 (D)）
- **書き換えたリードへの参照**: (B) の記録を入力に (F) が判定する（母集団が「その面を指す参照」に限られるので偽陽性が出にくい）
- **`docs/superpowers/` 内の参照**: `governanceDocs` と `headingRefDocs` の双方から除外されているので機構は見ない。**書いた時点で参照先の実在を目視で確かめる**（`grep -n '^## <見出し>' <対象>`）

**(D) ガバナンス検査**
```bash
npm run governance:check
```
期待: `全検査 passed`。失敗時のみ finding が出る。

**(E) 書き換えテスト**（条項ごとの裁定手順・spec の「書き換えテスト——分類ではなく操作で裁定する」が正本）

**まずその面が自分の書式を宣言していないか確かめる**（`grep -n '形式\|書き方\|各ルールは\|本節は' <file> | head -5`）。宣言があれば、それが問い 3 の具体形になる——外から与えた書式の候補より、面の自己宣言のほうが強い根拠である（2026-08-22 の Task 4 で `snotra-settings/CLAUDE.md` が「太字 = 守る指示」と宣言しており、ラベル型のリードがその宣言に既に違反していた）。**宣言が無いことも情報である**——無いと分かったら、代わりに「節が自分の内容の性質を述べている箇所」を探す（4 面のうち `snotra-egui-runtime/CLAUDE.md` だけが冒頭の宣言を持たず、節ごとの性質の宣言が代わりになった）。

**行動形化の最頻の当たりは「行動が本文に埋もれている」型である**——頭は事実形で、2〜3 文あとに禁止や指示が在る。**書き換えは「新しい行動を発明する」のではなく「在る行動を頭へ出す」ことで足りる。発明が要ると感じたら、それは残す条項である公算が高い。**

**行動形化するのは「リードを読んだだけでは次の動作が決まらない」条項に限る。** リードが既に一意の動作を含意するもの——**禁止形**（「〜しない」「〜してはならない」）・**義務を課す否定**（「〜できない」「省略できない」＝やれ）・**許可形**（「〜しなくてよい」「〜してよい」）——は、語形が事実形に見えても残す。

**ただし否定には 2 種類ある。** 上の「義務を課す否定」と、**行き止まりを述べる否定**（「〜する手段が無い」「〜には届かない」）は別である。後者は読者に「何もするな」と読ませるが、**本文に回避手順が埋もれていることがある**——その場合は行動形化してよい（2026-08-22 の `.claude/rules/safety-nets.md` で、「main へ入る前に実測する手段が無い」の本文に「実験用の枝接頭辞へ `push:` を一時的に張って測り、役目を終えたら workflow ごと外す」という手順が在った）。**回避手順が無いなら残す。**

**1 つの条項が 2 つの内容を持つことがある**——射程の否定と、純粋な行動。**行動がリードから一切読み取れず、しかも取り返しのつかない操作にかかるなら、そちらを頭へ出す**（同日の `governance-docs.md` で、「ADR 本文内の参照は照合されない」の本文に「消すときは生きた層の引用を散文化してから」が埋もれていた）。この線を引かないと、**読者の動作が既に一意な条項まで語形だけ入れ替える churn** になり、目的（「次に何をすればよいかが分かる」）に何も足さない（2026-08-22 の `docs/build-commands.md` の実行で確立した規則）。

**射程の否定を持つ条項でも、頭を行動へ替えられることがある**——射程の否定と誤解の訂正を**本文へ逐語で残せる**なら、埋もれていた行動を頭へ出してよい。判断基準の否定側（下記 4）が禁じるのは「保証の境界が消えること」であって、頭が行動になること自体ではない。

1. 条項を `A のときは B する。C が起きたため（#NNN 実測）` の形へ**実際に書いてみる**
2. 嘘にならないか
3. その面の役割（と自己宣言）が読者に行動を求めるものか
4. 書き換えると失われる保証があるか——**射程の否定**（「〜では捕まらない」「best-effort である」「〜は状態の検査ではない」）を行動形へ寄せると「**何を保証しないか**」が消える。射程宣言と逸脱の明記の対も、片方だけ書き換えない
   → 2〜4 がすべて肯定なら書き換える。1 つでも否定なら現状のまま残し、**裁定の理由を候補台帳 (H) へ記録する**

**着地している条項は「頭を残して末尾へ足す」**——(B) の記録に載っているリードは、頭を逐語で保てば前方一致が生きて随伴修正が要らない。2026-08-22 の Task 2 は着地していた 7 種すべてをこの形にして、**修正した参照元ファイルを 0 件に抑えた**。

**(F) 随伴修正の判定**（書き換えた面について、(B) で記録した参照が今も着地するかを見る）
```bash
# 使い方: TARGET=<書き換えた .md> BEFORE=<(B) の出力ファイル> で置き換えて実行
PYTHONIOENCODING=utf-8 TARGET=src-tauri/CLAUDE.md BEFORE=/tmp/refs-src-tauri-before.txt python -c "
import re,io,os
tgt=os.environ['TARGET']; before=os.environ['BEFORE']
leads=[]
for l in io.open(tgt,encoding='utf-8'):
    m=re.match(r'^\s*(?:- \*\*(.+?)\*\*|#{1,6}\s+(.+))',l)
    if m: leads.append(re.sub(r'[\`\*]','',m.group(1) or m.group(2)).strip())
for l in io.open(before,encoding='utf-8'):
    m=re.search(r'「([^」]+)」',l)
    if not m: continue
    h=re.sub(r'[\`\*]','',m.group(1))
    if not any(x.startswith(h) for x in leads): print('MISS: '+l.strip())
"
```
期待: 出力が空。MISS が出た行は、その参照元を新しいリードへ直す。

**(G) 独立再導出**（(F) だけでは随伴修正が完結しないため必ず併せて行う）

`.claude/rules/governance-docs.md`「ガバナンス文書の参照と命名のルール」が「**移動・圧縮・分割の完全性は依然として機構の外**にある」として要求している工程。`G-heading-refs` は**正準形しか見ない**ので、散文形の参照（「ルート `CLAUDE.md` のフック節」のような形）と意味依存は機構から漏れる。

1. 書き換えた条項の**旧文言**を正本として、その主張を指している箇所を散文形でも探す:
   ```bash
   # 旧リードの特徴語（固有名詞・識別子）で全ツリーを引く
   git grep -n "<旧リードの特徴語>" -- . ':!.claude/worktrees'
   ```
2. ヒットした箇所を「正準形（(F) が拾う）／散文形（(F) は拾わない）／無関係」へ振り分ける
3. 散文形のうち、書き換えで意味が変わるものを直す
4. **振り分けの結果を候補台帳へ記録する**——「散文形 N 件を確認し、うち M 件を直した」ではなく、**確認した箇所の一覧**を残す（件数は腐る）

**(H) 候補台帳**（各タスクが PR 本文へ載せる）

```markdown

判定した単位: 太字の条項 / 太字でない箇条書き / 番号付き / 表行 のうち、実際に見たものを書く
判定しなかった単位: 見なかったものを宣言する（「無い」ではなく「見なかった」と書く）

| 条項（行番号と冒頭） | 裁定 | 理由 |

| :NN <冒頭> | 行動形化した | — |
| :NN <冒頭> | 別の形式へ移した | <移した先> |

参照の随伴修正: (F) の MISS を直した箇所 / (G) で確認した散文形の箇所（一覧）
```

`## ドキュメントとコードの分担（陳腐化の予防）` の隣（同じ階層の新しい `##` 節）として足す。**ここが書式と語の正本である。**

````markdown
## 規範の書式は文書の役割から選ぶ

**行動形**は読者が次に取る動作で終わる形（`config の読みは read_config を通す`）、**事実形**は断定の繋辞で終わる形（`Layer 1 は best-effort である`）。

**書式は候補であって規則ではない**——役割から書式は一意に決まらない。反例が実在する: 「実装契約」の `docs/hooks.md` に完全な行動形の条項があり、「運用ガイド」の `AGENTS.md` は表だけでなく順序付きのワークフローを持つ。ゆえに**条項ごとに裁定する**。

**裁定の手順（書き換えテスト）**: 条項を `A のときは B する。C が起きたため（#NNN 実測）` の形へ実際に書き換えてみる。**これが判定するのは「書き換えられるか」であって「書き換えるべきか」ではない**——ほとんどの事実形は変換できてしまう。併せて 2 つを問う: (1) その面の役割が読者に行動を求めるものか、(2) 書き換えると失われる保証があるか（射程宣言のように「逸脱の明記と対で初めて真になる」形は、片方だけ書き換えると全称が実装より強くなる）。

| 役割 | 書式の候補 |
|---|---|
| 運用ガイド・開発プロセス（常時ロード） | トリガー → 行動／参照先 |
| 編集の瞬間の手助け（`.claude/rules/`） | `A のときは B する。C が起きたため（#NNN 実測）` |
| 開発原則・判断の型（本書） | 局面 → 立てる問い |
| モジュール固有の不変条件 | 行動形 + 射程の明示 |
| プロダクト知識（地図） | 構造を記述する。**行動形にしない**（#326 が二重管理をドリフトの根治として撤去した面である） |
| 改修者向けの実装契約（`docs/hooks.md`） | 射程の宣言と、その逸脱の明記の**対**。片方だけ書き換えない（当該行は #768 を名乗り、入れたコミットは #774） |
| コマンドリファレンス | 索引 + 行動形 |
| 様式規約 | 様式を規定する |

**役割の出所は 1 か所ではない。** `AGENTS.md`「ドキュメント参照」が大半を持つが、常時ロード面自身と `docs/hooks.md` の役割は同節に行が無い（後者はルート `CLAUDE.md`「フック」が持つ）。
````

- [ ] **Step 5: 位置参照と数え上げを解く（昇格は手段のひとつ）**

**目的は位置参照（「上の」「末尾の」「次の N つ」）と数え上げ（「残余は N 件」）を消すことであり、昇格ではない。** 2026-08-22 の Task 2 の実行で、この順序が逆に読める字面だったことが分かった。次の順で選ぶ:

1. **名前への置き換えで解けるならそうする**——「上の閉包」→「可視性を変える 5 関数の閉包」。条項の構造を一切壊さない
2. **解けないものだけ昇格する**——1 行に圧縮されているために位置と数以外に指す語彙が無い条項がこれにあたる
3. **昇格するときは「構造として成立する最小の単位」で行う**——連続した塊の中の 3 本だけを `###` にすると、間に挟まる条項が見出しに分断された箇条書きとして残る。入れ子リストの途中を昇格するとリストが断ち切られて対比が読めなくなる
4. **昇格先は `###` 以下**（`##` は `sectionOf` の節を切る）。**スロットは任意**——持たない条項に節を作らない

候補を機械的に見つける。**条項へ絞る前にファイル全体へ当てること**——数え上げは条項の中より**節の導入段落**に居ることが多く、`^\s*- \*\*` で先に絞ると原理的に落ちる（2026-08-22 の Task 5 が導入段落の「保証は次の 2 つ」の直下に箇条書き 3 本という食い違いを見つけた）:
```bash
grep -nE '上の|末尾の|次の [0-9]|この [0-9]+ つ|は [0-9]+ 件|は [0-9]+ つ' <file>   # ファイル全体
grep -nE '^\s*- \*\*' <file> | grep -E '上の|末尾の|次の [0-9]|は [0-9]+ 件|は [0-9]+ つ'   # 条項に絞る
```

**昇格の既定は 0 本である。** Phase 2 の 4 面で昇格したのは 1 面の 7 本だけで、57 本の面も 8 本の面も 0 本が正しい裁定だった。**「位置参照・数え上げが名前では解けない」ことを積極的に示せたときだけ上げる。**

**昇格したら、その面の書式の自己宣言を確かめる。** 面によっては冒頭で自分の書式を宣言している（例: `src-tauri/CLAUDE.md` の「各ルールは『太字 = 守る指示』の形式」）。条項を `###` へ上げると、その宣言が実装より狭くなって偽になる。**同じ変更の中で直す**（Task 2 は「リード（`###` 見出しか太字）= 守る指示」へ改めた）。

## 受容する残余（spec から引き継ぐ）

- **行動形／事実形のずれを検知する機構は無い。** この plan の作業が正しく行われたことを機械が保証する手段は無く、受け皿は `.claude/rules/governance-docs.md`「書く約束」・レビュー・`/health-check` の意味判断である
- **裁定は意味判断であり、ぶれる。** 同じ条項でも実行者が変われば違う裁定になりうる
- **見出しへ昇格した条項は `- **` でなくなり、条項の母集団から消える。** 作業の前後で条項数を比べても改善の証拠にならない
- **この plan の計測は太字で始まる箇条書きしか見ていない。** 太字でない箇条書き・番号付き・表行は射程外である（Task 8 だけが番号付きを明示的に扱う）
- **rustdoc の指示を条項へ写すか、正本として指すかの扱いが Phase 2 で割れた。** Task 3 は「契約の正本は同関数の doc」と指す形へ寄せ、Task 5 は 1 句を写した。**どちらも正しい**——条項全体が既に rustdoc を大きく写している場合、1 句だけ正本を指すと読み手が 2 か所を往復する。`ADR-canonical-source-without-pointer-indirection`「同じ事実が 2 箇所で正しく述べられることは、この規範の違反ではない」が支える。**判断の分かれ目は「その条項が他に行動を持っているか」**であり、持たない条項へ 1 句足すのは写しの増加より読める方を採ったことになる
- **同じリストの中で太字と非太字の条項が混在している面がある。** `snotra-egui-runtime/CLAUDE.md`「一般」節は新しく足された 5 本だけが太字という履歴的な分裂を持つ。非太字 7 本はすべて既に行動形なので書式の問題は無いが、太字化すると条項の母集団が動く（8 → 15 本）ため、判定単位の宣言を跨ぐと考えて**この plan では触らない**
- **節を足したら、その節への入口を同じ変更で作る。** Phase 1 が `docs/development-principles.md` へ「規範の書式は文書の役割から選ぶ」を足したとき、同ファイルの「局面 → 立てる問い」表へ行を足し忘れた（Phase 4 で補完した）。**新しい節は、索引されるまで到達できない**——本設計が直そうとしている当の欠落を、作業中に作っていたことになる。
- **節を挿入する変更は、その面を指す序数参照を動かす。** Phase 1 が `docs/development-principles.md` へ 1 節を挿入したとき、ルート `CLAUDE.md` の「§6・§7」が節番号と読むなら指す先が変わっていた（Phase 3 で発見し、正準形へ置換した）。`.claude/rules/governance-docs.md`「ガバナンス文書の参照と命名のルール」の「番号は構造を凍らせ、**ずれても誰も気づかない**」がそのまま起きた形で、`governance:check` は緑のままだった。**節を足す／消す／並べ替える変更では、その面を指す序数参照を `git grep -n '§[0-9]'` で数え上げること。** 2026-08-22 に数え上げた結果、生きた層に残る `§<数字>` の宛先は 28 件が `SPEC.md`（同ファイルは `## 0.` `## 1.` と番号付き見出しを持つので正当）、1 件が `docs/hooks.md` の「§「構造的設計原則と強制の階梯」の**項目 6・7**」（節の指し方は見出し名で正しく、末尾の項目番号だけが序数）である。後者は `docs/hooks.md` に Phase の割り当てが無いため**この plan では直さない**。
