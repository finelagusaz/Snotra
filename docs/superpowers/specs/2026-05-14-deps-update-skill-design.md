# 設計: 依存関係更新スキル `/deps-update`

- 日付: 2026-05-14
- ステータス: 設計承認済み（実装計画待ち）
- 種別: 仕様変更（新規スキルの追加）

## 背景・目的

Cargo / npm の依存関係更新は、これまで複数回にわたって同一の手順で繰り返されてきた（`#312`〜`#322` 等）。手順は「依存更新 → ローカル検証 → `chore(deps)` ブランチ・PR 作成 → CI 確認 → スカッシュマージ」でほぼ固定されている。この繰り返しを単一の `/deps-update` スキルに畳み込み、毎回手順を再説明する必要をなくす。

## スコープ

### 含む

- cargo / npm の依存関係を一括更新する
- 更新後のローカル検証と、検証失敗時の修復ループ
- `chore/deps-*` ブランチの作成、`chore(deps)` コミット、PR 作成
- CI のポーリングと緑/赤の報告

### 含まない（意図的な YAGNI）

- **PR のマージ** — `main` へのマージは取り消しにくい外向きの操作のため、人間の判断に残す
- **メジャー bump の別ブランチ分離** — 全更新を一本の PR に束ねる（`#322` の運用パターンを踏襲）
- **無関係な CI 失敗の自動 issue 起票** — スキルは緑/赤を報告するに留め、issue 起票は人間が判断する
- **E2E・スモークテストのローカル実行** — 重いので CI に委ねる

## 設計判断（ブレインストーミングでの合意事項）

| 論点 | 決定 | 理由 |
|---|---|---|
| 自律の境界 | CI グリーン確認まで。マージは手動 | `main` へのマージは取り消しにくい外向きの操作。人間が握る |
| 更新の束ね方 | 全更新を一本の `chore/deps-*` ブランチ・1 PR。major bump は PR 本文に明記 | `#322` の既存運用パターン。CI ポーリングも一回で済み構造が単純 |
| 検証失敗時の振る舞い | `/implement` 型の修復ループ（最大5サイクル）。超えたら診断サマリーを書いて停止し PR は作らない | レポートの「自分が起こした壊れは直す」方針と、既存スキルの型に沿う |

## スキルの輪郭

| 項目 | 内容 |
|---|---|
| 名前 | `deps-update` |
| パス | `.claude/skills/deps-update/SKILL.md` |

## ステップ構成

### Step 1 — 前提確認

- 作業ツリーが clean か確認する。未コミットの変更があれば停止し、ユーザーに整理を促す
- `git fetch` して `main` を最新化する
- `chore/deps-YYYYMMDD` ブランチを `main` から作成する（`CLAUDE.md` の「`main` 直コミット禁止」を遵守）

### Step 2 — 更新

- `$ARGUMENTS` の対象（`cargo` / `npm` / 空=両方）に応じて依存を更新する
- 更新されたクレート・パッケージを列挙し、**minor/patch と major を分類**して記録する

### Step 3 — ローカル検証（最大5サイクル）

- `docs/build-commands.md` を SSOT として参照する。実行対象は「カテゴリ A の必須＋追加検証」「カテゴリ B の必須」「カテゴリ C のうちフロントユニットテスト（Vitest）」
- E2E・スモークはローカルで走らせず CI に委ねる
- 失敗した場合、原因を読み・修正し・失敗したステップから再検証する
- **5サイクル超でエラーが残る場合、診断サマリー（試みた内容・残存エラー・推定根本原因）を書いて停止する。PR は作らない。調査用にブランチは残す**
- 修復ループの節度: clippy 警告・型エラー・軽い API 追従はスキルが直す。**実ロジックの大幅な書き換えを要する破壊的変更**に当たった場合は、無理に直さず診断サマリーで停止しユーザーに委ねる

### Step 4 — コミット & PR

- このスキルで生じた変更（`Cargo.lock`, `package-lock.json`, 修復した実コード等）をステージする
- `chore(deps): ...` の conventional commit を作成する
- push して `gh pr create` で PR を作成する
- PR 本文に更新一覧を載せ、**major bump は ⚠ で明示**する

### Step 5 — CI ポーリング

- `gh pr checks` で CI の完了まで待機する

### Step 6 — 報告

- 緑なら「マージ可能」、赤なら失敗したチェックとログを報告する
- **いずれの場合もマージはせず停止する**

## 出力

以下を報告する:

1. 更新されたクレート・パッケージ一覧（minor/patch と major を区別）
2. ローカル検証の結果（修復サイクルがあればその内容）
3. PR の URL
4. CI の結果（緑/赤、赤の場合は失敗チェックとログ）

検証が5サイクルで通らなかった場合は、PR の代わりに診断サマリーを出力する。

## 不変条件・制約

- **SSOT 厳守**: `docs/build-commands.md` のコマンド本体を `SKILL.md` に直書きしない。カテゴリ参照に留める（`/health-check` Check 5 が直書きを検知する）
- **`main` 直コミット禁止**: 必ず `chore/deps-*` ブランチを作成してから作業する
- **マージ禁止**: スキルは PR 作成と CI 確認までで停止する
