# ドキュメント・ガバナンス再編 設計書

日付: 2026-07-19
状態: 設計合意済み・issue 起票前

## 背景と問題

ドキュメントの量が増え、同じ事実を複数の恒久文書へ写していることが管理負担とドリフトを生んでいる。設計時に以下の不一致を実地検証で確認した。いずれも「変更が正本を動かしたのに、写しが追従しなかった」という同一構造であり、個別の誤りではなく「写しの存在を列挙する仕組みがない」というシステム欠陥の症状である。

- **モジュール責務の SSOT 分裂**: `docs/architecture.md:52` は「各 `CLAUDE.md` を SSOT とする」と述べるが、`snotra-core/CLAUDE.md:10` は #562 以降「`//!` を正本とし、CLAUDE.md はファイル一覧と横断不変条件のみ」と定める。architecture.md 側が #562 に追従し損ねた
- **マージ方針の矛盾**: `CONTRIBUTING.md:16` の「スカッシュマージまたは通常マージ」は squash-only の現設定（`allow_merge_commit=false`、#488）と矛盾
- **safety-nets.md の配送範囲**: 本文は「スキル/ドキュメントの規約」も守備範囲と語るが、frontmatter の `paths` は hooks / githooks / settings.json / workflows のみで、規範文書の編集では配送されない
- **アイコンバッチ形式の 3 重記述**: `SPEC.md` / `docs/architecture.md` / `src-tauri/src/icon.rs` に同形式が併記され、`None` のとき長さを持たない条件が SPEC.md 側で曖昧
- **Markdown は編集時検査の対象外**（#497 で受容した残余）: PR CI が緑でもガバナンス文書は未検査になり得る

## 設計の核

**予防（責務分担表で写しを作らない）と検知（CI で追従漏れを捕まえる）の二層。** 表だけでは #562→architecture.md 型の追従漏れが再発し、検査だけでは検査項目にない写しが増殖する。main 保護が `.githooks/`（手前の親切）+ GitHub ruleset（最終防衛）の二層であるのと同じ骨格。

## §1 責務分担表

「正本」= その事実を修正する唯一の場所。

| 情報の種類 | 正本 | 他文書の役割 |
|---|---|---|
| ユーザー観測可能な契約 | `SPEC.md` | 実装名・式を書かず、コード/テストを参照 |
| 安定した層境界・依存方向・設計理由 | `docs/architecture.md` | 関数名・バイト形式・現在の状態式を持たない |
| 精密な実装契約 | `//!` / `///` / TSDoc / 型 / テスト | 散文側で再記述しない（#562 の路線を全 crate に徹底） |
| ファイル横断の未強制不変条件 | 各モジュールの `CLAUDE.md` | ファイル別責務散文を持たない（索引 + 横断条件のみ） |
| 変更時の配送・起動条件 | `AGENTS.md` 条件別チェック表 + `.claude/rules/` | rules は「引き金・正本参照・必須検査」のルーターに限定 |
| コマンド・検査写像 | 機械可読な共通定義（形式は issue 4 で決定） | `docs/build-commands.md` の表は照合対象 |
| 事故履歴・実測ログ | **圧縮して同居**（下記） | issue は深掘り時の入口。恒久文書の理由文が判断根拠 |

### 事故履歴の扱い（決定: 圧縮して同居）

- 「太字 = 指示、後続 = 理由」形式は維持し、理由部分を **1〜2 文 + issue 番号**に圧縮する
- 退去するのは**手順ログ級の詳細のみ**（再現コマンド列・exit code 表・検証の時系列）
- 根拠（実挙動の観察）: ルート `CLAUDE.md` / `AGENTS.md` は毎セッション全文がコンテキストに載り、インラインの理由散文は常に判断に効く。一方 issue 番号を `gh issue view` で辿ることは通常作業では起きない。issue 番号の実機能はリンクではなく**出所表示**（実測の印・重複防止の錨・深掘り時の入口）である。理由を完全退去するとエージェントの実効的な知識から消え、規範を守る動機づけが痩せる

## §2 governance:check の器（決定: CI + 手動 npm script、hook は現状維持）

- 決定的検査を `scripts/` 配下に置き、**PR CI の独立 job + `npm run governance:check`** で実行する
- PostToolUse hook は触らない（#497 の受容を維持）。ただし「Markdown の沈黙は未検査」という残余の過半を CI が引き取るため、ルート `CLAUDE.md` フック節の当該記述は弱められる
- 検査対象（機械化可能なもの）: 内部リンク実在・参照ファイル実在・rules の `paths` glob と本文の整合・スキル表とディレクトリの対応・モジュール索引と実ファイルの対応・`docs/build-commands.md` 表と定義の照合
- `/health-check` は機械化された Check を検査から外し、意味的判断（責務の妥当性・SPEC 整合の解釈）だけを残して痩せる

## §3 issue 分割（4 件）

1. **既知の不一致解消** — architecture.md:52 の SSOT 指名を `//!` へ更新、CONTRIBUTING.md:16 を squash-only に修正、safety-nets.md の `paths` 拡張（`.claude/rules/**`・`.claude/skills/**`）または本文の守備範囲宣言の縮小（どちらに寄せるかは issue 内で判定）、アイコンバッチ形式の 3 重記述を §1 の表に従い一本化
2. **governance:check 導入** — §2 の器 + 検査一覧。CI workflow 追加を含むため safety-nets.md の合意手順に従う
3. **rules ルーター化の試行** — 1 モジュール（候補: `search.rs` の rule）で「引き金・正本参照・必須検査」のみへ薄化し、情報損失がないか実運用で測ってから横展開を判断する
4. **検証写像の共通定義 + 事故散文の圧縮 + `docs/superpowers/` 非規範化** — 検証写像は JSON/TS 等の共通定義から hook と CI が同一スクリプトを呼ぶ形式を検討。`docs/superpowers/` はディレクトリ README で「歴史資料・現在の仕様ではない」と宣言し鮮度維持対象から除外する（削除しない）

依存関係: 1 は独立・即着手可。2 が入ると 1 の型の再発を検知できるため 1 → 2 の順。3・4 は 2 の後が安全だが、4 のうち非規範化宣言だけは独立に軽く済む。

## §4 更新タイミング

新たな表は作らない。「いつ何を更新するか」の正本は現行どおり **AGENTS.md 条件別チェック表**（引き金駆動）とし、同表へ「文書の写しを増やす変更 → §1 の表で正本を確認」の 1 行を足すだけに留める。追従漏れの検知は governance:check（事後・CI）が担う。
