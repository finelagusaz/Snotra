# 文書をなるべく必要としない開発システム 設計書

日付: 2026-07-19
状態: 設計合意済み・issue 起票前
関連: #593（本 issue）・#588 / #589（配下の実施例）・`2026-07-19-doc-governance-design.md`（前段の予防+検知二層）

## 背景

#586〜#591 の最適化目標は「文書同士の整合」だった。だが最上段の目標は**開発効率＝正しい行動に至るまでに読む量の最小化**であり、そこから見れば「文書同士を整合させる」より一段上位の勝ち筋は**守るべき恒久規範の面積そのものを減らす**ことにある。governance:check（#587）は「縮んだ残余を守る安価な網」として価値が残るが、本設計は**その面積を今後拡張しない上限（cap）を機構で宣言する**。

本設計は新しい作業列ではなく、**#588（rules ルーター化）/ #589（事故散文の圧縮）を配下に束ねる上位フレーム**である。両者に「なぜやるか」を与え、成功指標を「文書同士の整合」から「規範の面積の burn-down」へ再定義する。

## §1 文書の 2 つの費用モデル

戦略の基礎理論。文書は費用構造で 2 種に分かれる。

- **恒久規範（現在形）**: ルート `CLAUDE.md`・`AGENTS.md`・`.claude/rules/`。常時または引き金時にロードされ、**エージェントのコンテキスト予算への課税**であり、かつ**最新である義務＝ドリフトという持続負債**を負う。減らすほど効率に直結する
- **履歴（追記のみ）**: issue・spec・設計書・ADR。書いた瞬間に完成して腐らず、鮮度維持コストがゼロ。いくら書いても負債にならない

戦略の言い換え: **恒久規範を (a) 機構（型・テスト・compile-fail・hook）へ吸収するか、(b) 履歴へ退去させて縮め続け、残るのは「機構化も履歴化もできない少数の判断材料」だけにする。** これは `docs/development-principles.md` の「型・単一通過点・テストが規則を吸収した時点でチェックリストを削除する」と同一原理であり、本設計はそれを個別規則からシステム目標へ昇格させる。

## §2 北極星指標と二重 ratchet（機構で担保する cap）

`governance:check` に行数ゲート（新チェック）を追加し、恒久規範の面積を機械で単調非増加に保つ。二面を**独立に** ratchet する。

| 面 | 現在値（2026-07-19 実測） | 基準の扱い |
|---|---|---|
| 常時ロード（`CLAUDE.md` + `AGENTS.md`） | 233 行 | 単調非増加。基準はコミット済み定数で保持し、**引き上げは明示コミット + 理由コメント必須** |
| rules 合計（`.claude/rules/*.md`） | 173 行 | 同上（常時ロードとは独立の上限） |

- **面替えでの回避を塞ぐ設計**: 常時ロード→rules への移動は常時側を下げるが rules 側の上限に当たる。ゆえに単なる面替えでは両面が下がらず、**真の削減（機構吸収または履歴退去）だけが両面を下げられる**
- **行数は粗い代理指標である**（全称表現は前提とセットで書く）。密度で誤魔化す余地（1 行を長くする）は残る。ratchet は精密なメーターではなく**方向を守るラチェット**であり、この粗さを承知で受容する
- 行数は `\r?\n` 分割で数える（CRLF checkout で `.` が `\r` を落とす事故を #587 / #589 で二度踏んだ）
- **ADR・spec・issue は履歴側ゆえ、この ratchet の対象外**（append-only の履歴に上限を課すのは費用モデルに反する）

## §3 意思決定の記録 — ADR（決定記録）

「意思決定は記録する」を抽象原則から実際の仕組みへ具体化する。**否定の知識（なぜ B を捨てたか）に、課税されない append-only の正準の家を与える。**

### 問題

否定の知識は現在こう散らばっている: (1) issue/PR コメント（GitHub には残るが**実行時に読まれない**）、(2) ルート `CLAUDE.md` の事故散文（実行時に読まれるが**課税面に決定理由が漏れている**）、(3) `specs/` 設計書（HOW 中心で「B をなぜ捨てたか」の明示欄が無い）。退去先が無かったため、理由の散文が課税面（`CLAUDE.md`）に留まり続けていた。

### 決定

| 項目 | 決定 |
|---|---|
| 置き場 | `docs/adr/NNNN-<kebab-title>.md`（連番ゼロ埋め）。履歴側 = §2 の ratchet 対象外 |
| 引き金 | **否定の知識が生じたときだけ** — 「代替案 B を検討して却下した」決定に限定。自明な実装・一本道の選択は書かない |
| 形式 | 4 節 `## 文脈` / `## 決定` / `## 検討した代替案と却下理由` / `## 帰結`。末尾に status（Accepted / Superseded）+ 関連 `#issue`・`ADR-NNNN`・spec リンク |
| spec との棲み分け | **ADR = なぜ（判断・却下理由）、spec = どう作るか（実装設計）**。直交させ二重化しない |
| `CLAUDE.md` との接続 | 否定を伴う決定は ADR へ。`CLAUDE.md` には「太字＝守る指示 + `ADR-NNNN` ポインタ」だけ残し、理由の散文は課税面から ADR へ退去する（#番号ポインタ規約に ADR 変種を追加）。これが §2 の burn-down を実際に前進させる経路 |
| 既存事故散文の遡及移行 | **しない**（YAGNI・検収条件＝軽く保つ）。ADR は本設計以降の新規決定に適用。既存の 31 箇所の #番号事故散文は現状維持 |
| 索引 | 専用 index は作らない（`ls docs/adr/` で足りる）。`AGENTS.md`「ドキュメント参照」に 1 行ポインタのみ追加 |

本設計自身が最初の ADR（`ADR-0001`）になる。cap を機構化 vs 規範宣言、二面 ratchet vs 合計 ratchet を却下理由付きで検討しており、否定の知識が実在する。

## §4 4 箇条 → 設計原則への写像

issue #593 の 4 箇条を正典化する。

| 箇条 | 本設計での原則 |
|---|---|
| 実装をソースとする | 精密な実装契約 = `//!` / 型 / テスト。#588 の rules ルーター化がその実施例 |
| 実装で得た知見はストックする | 最良のストックは散文でなく**実行可能物**（回帰テスト・アサーション・カナリア）。散文で置くのは機構が表現できないものに限る |
| 意思決定は記録する | 履歴側ゆえ無制限に書いてよい。否定の知識は §3 の ADR へ。#589 の事故散文圧縮は恒久→履歴の引っ越し |
| 意図や背景は自分たちで書く | 機構化不能な散文の不可約な核 = `SPEC.md` と設計書 |

## §5 残余（「なるべく」の中身）

ゴールは「文書ゼロ」ではなく「**実装から導出できるものを二重化しない**」。実装から永遠に導出できない事実が 3 種あり、これらは縮められない:

- **外界の事実** — GitHub のマージ挙動（#488）など、コードの外にある真実
- **否定の知識** — なぜ B 案を採らなかったか（§3 の ADR が受け皿）
- **ファイル横断の未強制不変条件** — コンパイラ・型が跨いで守れない制約

## §6 配下への切り出し（本設計は方針確定・実作業は別 issue）

本設計はマージ後、以下を issue として切り出す:

1. **行数ゲート（§2）の実装** — `scripts/governance-check.mjs` に二面独立の行数チェック + 基準定数を追加。CRLF 対策必須
2. **初回削減パス** — 232 / 173 を実際に下げる。恒久規範から機構吸収または履歴退去できる規範を 1〜数本剥がす
3. **#588 / #589 を本設計の配下として issue 上で結び直す** — 成功指標の再定義を反映

ADR 規約の導入（`docs/adr/` の新設・`ADR-0001`・`AGENTS.md` の 1 行ポインタ・`/implement` Step 6 の回収ステップ）は本設計と対で同 PR に含める（規約の初例と発火配線を残すため）。

回収の配線（`/implement` Step 6）: `/implement` は完了時に `workspace/`（`plan.md` を含む）を削除するため、そこに生まれた否定の知識が git 履歴の底へ沈み grep できる決定記録として残らない。この取りこぼしの発生点（削除の直前）で「否定の知識があれば ADR へ回収」する。否定の知識が最も濃く生まれる場所と ADR の引き金を機構で繋ぐ。
