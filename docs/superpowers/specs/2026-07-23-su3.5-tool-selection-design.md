# SU3.5 — tool-selection（カスタムオープナーのツール選択メニュー・§18）+ #638

- 種別: 設計 spec（#532 Phase 2・ロードマップ `2026-07-21-phase2-softbuffer-migration-roadmap.md` の SU3.5）
- 日付: 2026-07-23
- 親: #532（メインウィンドウの egui/softbuffer 移行）・相乗り #638
- 履歴: 本設計は brainstorm（2026-07-23）で 2 分岐を確定して得た。(1) 状態表現は **2 スロット + 優先度射影**（SolidJS 実装 parity・`Vec<ViewFrame>` を却下）、(2) #638 正規化は**先勝ち**（挙動変化なし）。前提の実測: #634 G-SYNC は通過済み（同期直 `Engine` + debounce 50ms で確定・PR #640）

## 背景と位置づけ

SU3（M1–M3）で egui 経路の検索体験（plain/folder/instant/slash）は parity に達した。残るモーダルビューが §18 のツール選択メニューである。SU3 spec（`2026-07-22-su3-search-experience-design.md`）の決定 5 は tool を defer し「tool が実際に folder の上へ積まれる SU3.5 で stack へ一般化する」と書き残した。本 spec はその SU3.5 を設計する。

参照実装（parity の正）:

- SolidJS `ui/src/stores/tool-selection.ts`（`ToolSelectionFrame`）・`ui/src/stores/search.ts`（`stackTop`/`saveView`/`restoreView`/`popView`・#538）
- SPEC §18.3（起動フロー）・§18.4（ツール選択メニュー）・§18.5（状態モデル）・§19.6（instant の Shift+Enter）

## 決定事項

### 決定 1: 状態表現は 2 スロット + 優先度射影（`Vec<ViewFrame>` を却下）

`SearchState` に `tool: Option<ToolFrame>` を `folder: Option<FolderFrame>` の隣へ追加し、`view_kind()` を `tool > folder > results` の射影にする。

- **SolidJS の実際の格納構造と同型**: 参照実装は `toolSelectionState` / `folderState` の 2 シグナル + 固定優先度射影（`stackTop = tool ?? folder`）であり、Vec スタックを持たない。parity の写しがそのまま設計になる
- **tool-on-tool を型レベルで表現不能にする**（[[prefer-structural-over-documented-contract]] の設計選好）。深さは高々 2 で固定
- `FolderFrame`・M2 コードは無変更
- **否定の知識（supersede）**: SU3 spec 決定 5 の「`Option<FolderFrame>` を `tool` を積める stack へ一般化」の文言は、`Vec<ViewFrame>` 化を意味しない。第二の事例（tool）は現れたが、参照実装自身が Vec を必要としていない以上、SolidJS に無い一般性（深さ 3+・同種重複）を新造することは「live 到達不能な状態を建てない」規律（SU2 由来・M2 brainstorm で `Vec<ViewFrame>` を一度却下済み）に反する。第三のモーダルビューが実際に現れた時点で再検討する

### 決定 2: #638 は config ロード時の先勝ち正規化（挙動変化なし）

`instant_commands` の重複名を Config ロード時に検出し、**先頭の定義を残して後方を落とす** + stderr 警告。

- 現行の実行時解決（`iter().find` = first-match）と同じ行が残るため、**実行される action は従来と同一**（純粋な不整合除去。候補リストの表示だけが実行と一致するようになる）
- **config.toml へは書き戻さない**（load-time の in-memory 正規化のみ。ユーザーの手編集行をファイルから消さない）
- core レベルの単一修正で IPC / egui 両経路が同時に直る（構造的排除）
- 否定の知識: 後勝ち（TOML の「後が勝つ」直感）は実行 action が変わる挙動変更を伴うため却下。実行時解決の index ベース化（#638 案 B)は stale リスクとの整合設計が要るため採らない

## スコープ

## 状態核設計（`src-tauri/src/egui_shell/search_state.rs`・純粋）

```rust
pub struct ToolFrame {
    restore_query: String,        // 復元用の query（両ビュー共通。folder 中も query は展開前語のまま
                                  // なので実質不変だが SolidJS SavedViewState.query の写しとして退避）
    restore_results: Vec<SearchResult>,
    restore_selected: usize,
    target_path: String,          // TextEdit 表示用 + 起動対象
    target_is_folder: bool,
    tools: Vec<OpenerTool>,       // snotra_core::opener::OpenerTool（採用ルール 1 件分・§18.3 排他）
    launch_query: String,         // 起動 API へ渡す元クエリ。復元には使わない（SolidJS #538 の
                                  // launchQuery / restoreQuery 型分離を名前で踏襲）
    saved_folder_filter: String,  // folder 上に積んだときの 2 段復帰用（SolidJS savedFolderFilter）
}
```

- `view_kind()`: `if tool.is_some() { Tool } else if folder.is_some() { Folder } else { Results }`（§18.5 優先度と一対一）
- `interpret` は既存の `view_kind != Results → Plain` ゲートで Tool を自動カバー（変更不要見込み。テストで固定）
- **入場 API** `enter_tool(...)`: 現在の query / results / selected / folder_filter を frame へ退避してから tool を立て、tool 行を `set_results` する（SolidJS の `SavedViewState` + `savedFolderFilter` と同配置。Results からの入場では `saved_folder_filter` は空で未使用）
- **Escape ラダー拡張**（`on_escape`）: ① tool があれば解除し退避を復元（folder が残っていれば Folder ビュー + `saved_folder_filter` 復元、なければ Results 復元）→ ② 既存の folder 段 → ③ Hide。`EscapeOutcome` に tool 復帰を表す値を追加（既存 2 段の意味は不変）
- `reset()`（reset-on-show）が tool スロットもクリアする（§18.5「ホットキー再表示でツール選択はリセット」）

## driver 設計（`src-tauri/src/egui_shell/view.rs`）

- **入場（Shift+Enter）**: Results の通常行 / Folder の行で発火。instant 行は §19.6 どおり通常 Enter のまま（M3 実装済みの挙動を変えない）。選択行の path / is_folder でオープナー解決:
  - tools ≥ 2 → `enter_tool`（結果リストをツール一覧で置換・§18.4）
  - tools ≤ 1 → 通常 Enter と同一動作（§18.3。hide も同様）
- **解決・起動は IPC/トレイと同一 fn を共有**（M1 finding 5 の drift 防止規律）: 解決 = `commands/launch.rs` の `resolve_all_openers`、起動 = `launch_with_tool_core(&target_path, &exe, &args)` の同期直呼び。**履歴記録の責務配置は IPC 経路（`launch_with_tool` 系）を transcribe する**（plan で正確な記録タイミング・引数（`launch_query`）を写し、egui 側の read-without-write 非対称を作らない——M2 の folder 展開回数と同型の横断バグ予防）
- **ツール選択中のガード**（§18.5）: TextEdit は `target_path` を表示し無効化（入力無効）。←/→ 無効。↑↓ / Enter / クリックは有効。`run_search_with` は `ViewKind::Tool` で no-op（結果はツール一覧が占有し、検索で上書きされない）
- **行表示**: `name` + `exe` 淡色（SolidJS `ResultRow` の tool 行の写し）。クリックは既存どおり**行 index** で照合（§18.4——同一 exe 複数ツールの区別。パス文字列照合は禁止・`ui/CLAUDE.md` マウスイベント規約と同根）
- **Enter / クリックで起動後**: クエリクリア + hide（通常起動と同じ完了列）

## #638 設計（`snotra-core/src/config.rs`）

- Config ロード経路（`apply_migrations` 系列の一段として）で `instant_commands` を name で走査し、既出 name のエントリを除去（先勝ち）+ `eprintln!` 警告（除去した name と定義位置数）
- 設定 UI の保存時バリデーション（`Config::validate` の重複拒否）は既存のまま——正規化は手編集 config だけが通る救済路
- 書き戻しはしない（上記決定 2）
