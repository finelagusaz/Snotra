# plan.md チェックリスト化と PR 前ゲート・スキル起動経路の穴塞ぎ — 設計

日付: 2026-07-27 / 対象サイクル: ハーネス改善（#749 セッション実測に基づく）

## 背景（一次証拠）

#749 サイクルのセッション transcript（`05f67924`）の走査で、次の 2 つの構造的な穴が実測された。

1. **散文の指示ではスキル本文が配送されない。** ユーザーが「implement で実装して」と散文で指示 → モデルが `Skill(implement)` を呼ぶ → `disable-model-invocation: true` によりハーネスが拒否 → モデルは SKILL.md 本文を読まないまま「plan.md に従って直接実装します」と即興再現した。その結果、`/implement` Step 4a（実装後の check スキル再実行）と Step 5（workspace 削除前の ADR 回収）が脱落した。
2. **plan.md の本文に書いた作業が、完了条件に写っていなければ実行されない。** Phase 3 に「doc コメント中の `mod.rs::` 参照 3 件を訂正する」と書きながら実装で落とし、code-review の git 履歴観点が拾って初めて気づいた（RETROSPECTIVE.md「計画に書いたのに、実行を落とした」）。宣言と実行を照合する機構が存在しなかった。

どちらも「注意の減衰」ではなく機構の不在が機序である。よって対策も規範の増補ではなく機構で行う。

## 変更 1 — `disable-model-invocation` を外す（`/implement`・`/start-issue`）

両スキルの frontmatter から `disable-model-invocation: true` を削除する。

- **効果**: 散文の依頼（「implement で実装して」「issue N から始めて」）でモデルが Skill ツール経由で起動でき、SKILL.md 本文がコンテキストへ配送される。即興再現の経路が消える。
- **自発起動の抑え**: このフラグが担っていた「モデルの気まぐれな実装開始」の防止は、現在は `/implement` Step 1 の入口判定（同一性・レビュー到達の fail-closed 判定）と description の誘導（「計画が要る変更は `/start-issue` へ」）が担っている。防壁の二重化が解消され、外側の防壁が持っていた誤爆（ユーザーの散文指示まで弾く）だけが消える。
- フラグは #125 のスキル整理時からのもので、根拠が文書化された柵ではないことを git 履歴で確認済み。

## 変更 2 — plan.md のチェックリスト化（規範）

`/start-issue` Step 4 の計画様式に次の規則を加える。

> **実行を要する作業項目は、すべて Phase 配下の `- [ ]` 行として列挙する。散文は説明であり、散文にだけ書かれた作業は存在しない扱いになる。**

- Phase ごとの「完了条件」を本文と別に書く二重管理をやめ、チェックボックス列そのものを唯一の作業列挙 = 完了条件とする（RETROSPECTIVE の教訓「本文に書いた作業が完了条件に写っていなければ、書いたことは実行の保証にならない」の構造化）。
- **チェックリストを起こすのは `/start-issue`、育てて消し込むのは `/implement` である。** 後から起こす行為は散文からの転写であり、転写漏れこそが #749 の機序だった。計画誕生と同時にチェックリストが一体で生まれることで、(a) `/plan-review` が列挙の完全性を検証でき、(b) Step 6 のコミットで中断を越えて生き残り、(c) 転写工程そのものが存在しなくなる。
- `/implement` Step 2 に追記: **完了した項目はその都度 `- [x]` へ更新し、Phase のコミットに含める**。チェック状態が git に残ることで、中断・再開時にも「どこまでやったか」が接地する。**実装中に判明した計画外の作業は、その場で `- [ ]` として plan.md へ追記する**——途中発見のタスクも同じ hook のゲートに乗せる。
- `/implement` Step 5 に追記: PR 前に全項目が `[x]` であることを確認する（残っていれば変更 3 の hook が捕捉する）。

## 変更 3 — PR 作成前の hook ゲート（機構）

`.claude/hooks/pre-bash.mjs` の `decide` を拡張する。

- **発火点は既存の `gh pr create` 検出点のみ**（コマンド位置の検出・`TARGET_TOOLS` は現状のまま）。新しい発火点は作らない。
- **追加判定**: リポジトリルート（cwd から最近接 `.git` へ遡って導出）の `workspace/plan.md` が存在し、未チェックのチェックボックス行（`- [ ]`）が 1 件でも残っていれば `exit 2` で block する。理由メッセージに残項目数と対処を含める:「項目を完了させて `[x]` にするか、やらないと決めたなら項目を計画から外し、理由を記録してから再実行」。
- **`git commit` はゲートしない。** #749 実測でフェーズごとのコミット（plan.md に未チェック項目が残った状態のコミット）が正常な作業フローであるため、commit ゲートは誤爆源になる。
- **fail-closed の倒し方**:
  - plan.md が存在するのに読めない → block（判定不能は通さない）
  - plan.md が存在しない → この検査は管轄外（allow 方向。計画なしタスク・他リポジトリでの PR 作成を塞がない。push 検査は従来どおり働く）
  - `.git` が見つからない → cwd を root とみなす（従来挙動。リポジトリ外での誤爆を作らない）
- **判定の注入可能性**: `decide(payload, readGitState, readPlanState)` の形で plan 読み取りも注入し、分岐表全体を git・ファイルシステム無しでテストできる構造を保つ。
- **検出正規表現**: 行頭（インデント許容）の `- [ ]` / `* [ ]`。plan.md 内のコードブロック中に現れる `- [ ]` の誤検出は受容する（fail-closed 方向の過剰検出。対処はその項目をコードブロックごと整理すること）。

### テスト（safety-nets.md のフォールトインジェクション要件）

- `decide` の分岐表: 未チェックあり → block / 全チェック済み → allow / ファイル無し → allow（push 判定へ委譲）/ 読み取り失敗 → block。
- 実ファイル読み取り（`readPlanState`）は temp ディレクトリの実ファイルで実測する。
- `.claude/hooks/**` の編集で hook-selftest（`vitest run .claude/hooks`）が自動発火する（既存機構）。

## 文書同期

- ルート `CLAUDE.md`「フック」表の「PR 作成前 push チェック」行: 発火条件・正しい対応へ plan.md 残項目の判定を追記。
- `docs/hooks.md`「PreToolUse（pre-bash.mjs）の実装契約」: 追加判定と fail-closed の倒し方を追記。
- `.claude/skills/start-issue/SKILL.md` / `.claude/skills/implement/SKILL.md`: 変更 1・2 のとおり。

## 受容する残余

- `gh pr create` がコマンド位置に現れない迂回形（`sh -c` / `eval` / ラッパ経由）は従来どおり検出しない（人間専用・既存の受容リスクと同一）。
- 「実行を要する作業を散文にだけ書き、チェックボックスにしない」計画は機構では捕捉できない。これは規範（変更 2）と `/plan-review` の計画レビューに委ねる残余である。
- チェック済み `[x]` が実際には未実行である虚偽は捕捉できない。宣言と実装の照合は code-review（git 履歴観点が #749 で実際に拾った）に委ねる。
- `/implement` Step 5 は PR 作成より前に `workspace/` を削除するため、**未チェック項目を残したまま削除すれば hook の視界から計画が消える**。削除の前提条件（全項目 `[x]` の確認）を Step 5 の規範に置いて塞ぐが、規範を破る削除は機構では捕捉できない——虚偽の `[x]` と同じクラスの残余として code-review に委ねる。
