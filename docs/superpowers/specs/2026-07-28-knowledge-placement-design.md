# ナレッジ配置基準と規範散文の退避 — 設計書（2026-07-28）

## 背景と問題

失敗から得た知識の置き場が判断者の裁量に委ねられており、迷った教訓が最も安全に見える場所＝常時ロードされる `CLAUDE.md` / `AGENTS.md` へ流れ込む。結果として常時ロード面が手順散文で肥大し（最大例: squash マージの 4 手順・約 1,900 字）、#593 の面積 ratchet と衝突している。解決するのは次の 2 点:

1. **置き場の判断基準が明文化されていない**（新しい教訓 → どの器か、の判定フローが無い）
2. **規範文書の肥大**（手順書クラスの散文が常時ロード面に居座っている)

失敗の一次記録が issue に外部化される現行構造（RETROSPECTIVE.md は揮発・規範は圧縮結論のみ）は**維持する**。新しい文書種は作らない。

## 設計 1 — 器の分類基準（判定フロー）

新しい知識は二軸で器を一意に決める。

**第一軸「いつ効くか」**（読み込まれるタイミング）:

| 効くタイミング | 器 |
|---|---|
| 毎回・全タスク | `AGENTS.md`「検証の作法」（数点厳守・増やすなら減らす候補を挙げる） |
| 特定の局面・変更種別 | スキル本体＋`AGENTS.md`「条件別チェック」表のトリガー 1 行 |
| 特定ファイルを触ったとき | `.claude/rules/`（読取で自動配送） |
| 参照されたときだけ | `docs/`（development-principles.md 等） |

**第二軸「何であるか」**（内容の種別）:

- **手順**（ステップ列として実行できる）→ スキル。規範文書に手順本文を書かない
- **否定の知識**（なぜ B を却下したか）→ `docs/adr/ADR-<slug>.md`
- **失敗の一次証跡**（何が起きたか）→ GitHub issue / `RETROSPECTIVE.md`（揮発でよい）
- **意図（仕様）** → `SPEC.md`

**不変条件**: 常時ロード面（ルート `CLAUDE.md` / `AGENTS.md`）に置いてよいのは「トリガー＋参照＋根拠 issue 番号」まで。手順の本文を置いてはならない。

## 設計 2 — 基準の置き場

- SSOT は `/retrospective` の SKILL.md 振り分け節（教訓の置き場を決める瞬間に配送されるため）
- `/norm-review` からは参照 1 行で繋ぐ（規範新設時のもう一つの入口。本文は二重化しない）

## 設計 3 — 検算を兼ねた代表例の退避

`CLAUDE.md`「Git/GitHub 運用」の squash マージ 4 手順（#488）を退避する:

- 手順本文 → 新スキル `/merge-pr`（user 起動専用・`disable-model-invocation: true`）
- `CLAUDE.md` は「squash マージは `/merge-pr` に従う」＋機構の要点 2〜3 行へ圧縮（「なぜ」は既存の `docs/adr/ADR-squash-merge-issue-autoclose.md` が SSOT のまま）
- `CLAUDE.md`「利用できるスキル」表へ `/merge-pr` の 1 行を追加

## 実装時の関門

- エージェント設定の変更につき合意済み（本設計の承認・2026-07-28）
- セーフティネット変更: `.claude/rules/safety-nets.md` の適用、`/norm-review` の実施
- `npm run governance:check` の通過（G-skill-table・G-heading-refs。手順の移動は参照元の見出し参照を壊しうる）
- 手順移動の完全性は独立再導出で裏取りする（`/plan-review`「Step 2b」。旧本文を SSOT に、全命題の着地を確認）

## 射程外

- `CLAUDE.md` / `AGENTS.md` の全項目の一括再配置（後続サイクル。基準が定着してから）
- RETROSPECTIVE.md の運用変更・恒久的な失敗記録層の新設（不採用と決定）
