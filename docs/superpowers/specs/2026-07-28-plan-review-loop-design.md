# 計画に「未確定」欄を持たせ、それが空になるまでレビューを回す — 設計（2026-07-28）

日付: 2026-07-28 / 対象: #821（`/start-issue` → `/plan-review` → `/implement` の引き渡し）

## §0 要旨

`plan.md` に **「未確定（実装前に潰す）」節**を新設し、`/plan-review` を**その欄が空になるまで**回すループにする。

目的は「レビューが計画全体を覆ったこと」ではない。**実装時に判断が要らない `plan.md`** を作ることである。レビューの網羅は代理指標にすぎず、両者はずれる——**誰も疑問を出さなければ、レビューが全体を覆っても迷いは残る**。

引き渡し契約は「レビュー済みの計画」から「**未確定がゼロの計画**」へ変わる。判定は自己申告（セルフレビュー節の有無）から**機械判定**（`- [ ]` の件数）へ移る。

## §1 文脈

### 1-1. #821 の一次証拠（#713 サイクル）

`2026-07-26-skill-workflow-boundary-design.md` は「検証水準が**入口**で変わる」（F3）を、`/implement` を止めることで解いた。#821 はその残余で、**同じ入口の中で時間的に変わる**。

1. `/plan-review` を回し、台帳 4 エントリ（3 スカウト + 独立導出）が**全件成立**して着地した
2. 独立導出の発見をユーザーへ諮り、裁定を受けて計画へ **findings クラスを 1 つ丸ごと追加**した
3. 追加分は**どのレビューも受けていない**まま `plan.md` に同居した
4. 実際にその追加分に欠陥があった（`[workspace.lints.rustdoc]` が「非空かつ全エントリ deny」という述語が、必須 lint の行が 1 つ消えた形を緑で通す）。実装前に述語を実データへ当てて発見した

**既存の条項では拾えない。** `/start-issue`「5b. セルフレビュー（plan-review 固有の補完）」の免除除外は「plan-review が『独立レビュー不成立』と報告したエントリ」を対象とするが、今回は不成立ゼロゆえ発火しない。

**git のコミット順による検知は fail-open である。** #713 では `plan-review/` の最終更新（`6885b33`）と `plan.md` の最終更新（`724e6fa`）に差が出たが、これは Step 6 のコミット後に追記したという偶然による。通常フローは 5a → 5b → Step 6 の順で **1 コミットに畳まれる**ため、5b 中に育った計画は差を生まない。

### 1-2. 「実装時に迷いがない」の分解

#713 で実装時に判断を強いられた箇所は、次の 5 つが埋まっていないときだった。

| # | 埋まっているべきもの | #713 での実例 |
|---|---|---|
| 1 | 判定ロジック・値が**実データで確定**している | 述語 2 案を 9 ケースで測って初めて R2 の欠陥が出た |
| 2 | **選択が決着**している（代替案が却下理由付きで消えている） | 粒度・glob・lint 名の名指し |
| 3 | **事実の裏取り**が済んでいる | cargo の exit code 6 形、issue の引用先の腐り |
| 4 | **境界と異常系**が列挙されている | 母集団の欠落 6 形 |
| 5 | **完了の判定**が書いてある | テストと検証コマンド |

5 つはすべて「**まだ確定していない**」という 1 つの状態に還元できる。ゆえに置くべきは「レビュー回数の規則」ではなく、**未確定を明示する欄**である。

## §2 決定

### 2-1. `plan.md` の「未確定（実装前に潰す）」節

`/start-issue`「Step 4 — 実装計画（workspace/plan.md）」が定める `plan.md` の構成へ、この節を足す。

- **`- [ ]` のチェックリストで列挙する。** 各項目は 2 つを持つ: (a) **何が決まっていないか**、(b) **どう確定させるか**（測る / 決める / 裏取りする）
- フェーズ配下の作業項目（**何を実装するか**）とは**別のリスト**である。混ぜない（§3 で却下理由）
- 確定したら `- [x]` にし、**確定させた結果**（測定値・裁定・却下した代替案）を同じ行か直下に残す。「受容する残余」として畳んだ場合もそう書いて `- [x]` にする

例:

```markdown
## 未確定（実装前に潰す）

- [ ] ルート側の述語が「非空かつ全エントリ deny」で足りるか — **測る**: 必須 lint の行が
      1 つ消えた入力を作り、実ルート `Cargo.toml` を含む代表ケースで両案を実行する
- [ ] `members` の glob 要素を展開するか — **決める**: 現在 0 件。展開器は YAGNI か
```

### 2-2. ループ — 欄が空になるまで回す

```
ラウンド N（上限 3）:
  1. /plan-review を回す（Step 2 / Step 2b / Step 3）
  2. 指摘を必ずどちらかへ落とす:
       (a) 計画の修正        — 答えが決まっているもの
       (b) 未確定欄への追加  — 測る・決める・裏取りするまで答えが出ないもの
  3. 未確定欄を潰す（実測・裁定・裏取り）。潰せた項目を - [x] にし、結果を残す
  4. 未確定欄に - [ ] が残っているか
       残っていない → 収束。ループを抜ける
       残っている   → ラウンド N+1 へ（潰した結果が計画を動かしているため、再レビューが要る）
収束後: セルフレビュー節へラウンド数と最終ラウンドの結果を記す → Step 6
```

**レビューは欄を増やす役、実測と裁定は欄を減らす役**である。この非対称が収束を保証する——レビューが新しい疑問を出さなくなり、かつ出た疑問がすべて潰れたときだけ欄が空になる。

**「plan.md が動かなかった」は収束判定に使わない。** それはプロセスの不動点であって計画の性質ではなく、「レビューが何も言わなかった」でも成立する（§3）。

**順序の罠**: セルフレビュー節への記録（ラウンド数・不成立の有無・未収束で打ち切った事実）は**収束または打ち切りの後に 1 度だけ**書く。ラウンド内で行うのは計画の修正と未確定欄の更新だけである。

### 2-3. ラウンド 2 以降の範囲

- **Step 2b（独立導出）は毎ラウンド全体を再導出する。** issue が SSOT なので、計画がどう育っても引きずられない。全体の盲点検出はここが担保する
- **Step 2 のスカウトは、前ラウンドから変わった範囲に触れるレイヤーだけ**起動する。**「触れる」の判定は台帳の分割根拠に対して行う**——台帳は「レイヤー名 → 出力パス → 分割根拠（plan.md の変更ファイル）」で構成されるので、差分が動かした記述が指す**変更ファイル**を分割根拠に含むレイヤーが対象である。差分の行位置ではなく変更ファイルで判定する（節の移動や書式の変更だけで全レイヤーが起動するのを避ける）

台帳の値が 2 値から **3 値**になる。**「起動しなかった」を「問題なし」に化けさせない**ためである。

| 値 | 意味 |
|---|---|
| 実在 | 当ラウンドで起動し、成果物が着地した |
| 不着 | 起動したが届かなかった（1 度だけ再起動 → それでも不着なら独立レビュー不成立） |
| 当ラウンド対象外 | 前ラウンドで検証済みで、当ラウンドの差分がその範囲に触れていない |

`/plan-review`「Step 2」が起動時に `workspace/plan-review/` を `rm -rf` する仕様は**そのまま利点になる**。最終ラウンドの成果物が「最終形の `plan.md` を全レイヤーでレビューしたもの」であり、前ラウンド分は既に `plan.md` へ畳み込まれた、役目を終えた写しだからである。

### 2-4. 失敗時

- **3 ラウンドで収束しない**（未確定が残り続ける） → 停止してユーザーへ返す。**残っている未確定項目と、それを潰せなかった理由**を添える。無言で 4 ラウンド目に入らない
- **不着が残るラウンドは収束と判定しない**（そのレイヤーは検証されていないため）
- **ピンポン専用の検知は置かない**。上限 3 が事実上のガードになる（YAGNI）

### 2-5. 引き渡し契約と、既存機構へのただ乗り

`/start-issue`「出力」の引き渡し契約を「レビュー済みの計画」から「**未確定がゼロの計画**」へ言い換える。`/implement`「1a. workspace/plan.md の由来を確かめる」の表は **2 値のまま**で、「レビュー到達」の**判定基準だけ**が置き換わる（自己申告 → `- [ ]` の件数）。表に第 3 の状態を作らないのは、`2026-07-26-skill-workflow-boundary-design.md` が減らした判定を再び増やさないためである。

未確定を `- [ ]` で書くことで、**新しい検出器を書かずに 2 つの既存機構が効く**:

- `#749` の PreToolUse ゲート — 未チェックの `- [ ]` が `plan.md` に残ると `gh pr create` を拒否する
- `/implement`「Step 5 — コミット」 — 全項目が `- [x]` でなければ `workspace/` を削除しない

### 2-6. 効果の測定

この設計が効いているかを測る値を 1 つ持つ。`/implement`「Step 2 — 実装」は既に「実装中に判明した計画外の作業は `- [ ]` として `plan.md` へ追記する」と定めている。**その追記件数が「計画が残した迷いの量」の実測値**である。`/retrospective` でこれを見る（#713 サイクルでは Phase 5 の 7 件がそれに当たる）。

### 2-7. 費用

#713 のラウンド 1 は 4 体で約 52 万トークン（96k / 92k / 154k / 180k）。2-3 の分割により、典型的なラウンド 2 は独立導出（約 18 万）+ 差分スカウト 1〜2 体で**約半額**。典型 2 ラウンドの総額は約 80 万トークン。

## §3 検討した代替案と却下理由

- **条項だけを足す**（5b の免除除外に「レビュー後に追加した部分にも及ばない」を追加）: 却下。**書き手が「育った」と自覚しないと発火しない**。#713 では計画を育てた当人が、育てた自覚のないまま Step 6 まで進み `plan.md` に「レビュー済み」と書いた。自覚に依存する規範は、同じ地点で同じ判断を再生産する。
- **収束条件を「そのラウンドで `plan.md` が動かなかった」にする**: 却下。**プロセスの不動点であって計画の性質ではない**——「レビューが何も言わなかった」でも成立し、疑問が出なかっただけの計画を収束と判定する。目的は「実装時に判断が要らない計画」であり、判定はその性質そのもの（未確定がゼロ）に対して行う。なお未確定を潰せば計画は動くので、実務上この 2 つは連動する。**連動する 2 つのうち、目的に近い方を判定に使う。**
- **収束条件を「要対処 0 件」にする**: 却下。要対処 0 件でも「軽微な懸念」を取り込んで計画を直せば、その修正分がまた未レビューになる——同じ穴が小さく残る。
- **収束条件を「2 ラウンド連続で新規指摘なし」（loop-until-dry K=2）にする**: 却下。保証は最も強いが、収束していても必ずもう 1 ラウンド回るため費用が常に約 52 万トークン上乗せされる。計画レビューは探索（未知個数のバグ探し）ではなく**特定の成果物に対する照合**であり、K=2 が守る「まだ見ぬ発見」の余地は小さい。
- **未確定をフェーズ配下の作業項目に混ぜる**: 却下。新しい節を作らずに済むが、**「未確定が残っているか」を一目で数えられなくなる**。作業項目（何を実装するか）と未確定（何が決まっていないか）は種類が違い、後者だけが実装着手の可否を決める。
- **欄を作らず、セルフレビュー節で「未確定はない」と宣言する**: 却下。最も軽いが、**宣言は自覚に依存する**——#713 で失敗したのがまさにその形である。
- **差分の導線だけを足す**（レビュー時点の複製と `plan.md` を突き合わせて育った部分を明記する）: 却下。差分は見えるが、見えた後に何をするかが「自分で確認する」に留まり、`/plan-review` が担う多レンズ・独立導出は復元されない。
- **`/implement` 側で検知して止める**: 却下。1a の表に「一部だけレビュー到達」という第 3 の状態が生まれ、引き渡しが 1 往復増える。**責任は渡す前に閉じる側に置く**（利用者裁定・2026-07-28）。
- **毎ラウンド台帳をフルで回す / ラウンド上限を置かない**: 却下。前者は収束までに 100 万トークンを超えうる（独立導出を毎ラウンド全体で回す限り、盲点検出は落ちない）。後者はピンポンで止まらなくなる危険を利用者が引き取ることになる。

## §5 検証

規範の変更ゆえ機構のテストは書けない。代わりに 3 点で測る。

1. **実サイクルでのフォールトインジェクション**: 次に `/start-issue` を回すとき、レビュー後に意図的に疑問を 1 件足し、(a) それが未確定欄へ落ちること、(b) 欄が空でないうちはラウンド 2 が起動すること、を確かめる。稼働中のガードを弱める操作を含まないので実サイクルで行える（`.claude/rules/safety-nets.md`）
2. **既存ゲートへのただ乗りの実測**: 未確定欄に `- [ ]` を残したまま `gh pr create` を打ち、PreToolUse ゲートが拒否することを 1 度確かめる（`#749` の機構が新しい節にも効くことの確認）
3. **`/norm-review` は起動しない**: 判定を足す変更ゆえ条項上は対象だが、指摘の採用率が低いという 2026-07-27 の裁定に従う。この判断自体を本節に記録して、省略が黙って起きないようにする

## §6 受容する残余

- **欄が守るのは「書かれた疑問が潰れたこと」であって、「疑問が出尽くしたこと」ではない。** 誰も気づかなかった論点は欄に載らない。そこを担うのは `/plan-review`「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」であり、**欄はその出力の受け皿**である
- **未確定を潰す品質は測れない。** 「測って確定した」と書けても、測り方が悪ければ間違った確定になる。ここは `AGENTS.md`「検証の作法（全タスク共通）」の「判定の中核は自分で測る」に委ねる
- **上限 3 で打ち切った場合、未確定を残したまま人へ渡る。** そのとき `/implement` へ進むかは人の判断であり、進むなら残った未確定を `plan.md` に `- [ ]` のまま残す——PreToolUse ゲートが PR 作成を拒むので、**黙って PR まで抜けることはない**
- **`/plan-review` を単独起動した場合、ループは存在しない**（制御は `/start-issue` にある）。その経路で得られるのは従来どおり「その時点の計画に対する 1 ラウンド」である
