# 計画レビューをループにし、「最終形がレビューされた計画」だけを引き渡す — 設計（2026-07-28）

日付: 2026-07-28 / 対象: #821（`/start-issue` → `/plan-review` → `/implement` の引き渡し）

## §0 要旨

`/plan-review` を**一発勝負からループへ**変える。ループの制御は計画の所有者である `/start-issue`「5a. check スキルによる計画検証」が持ち、**そのラウンドのレビューが `workspace/plan.md` を 1 文字も動かさなかったとき**に収束と判定する。

これにより「レビューを受けていない部分を含む計画が、完成状態として `/implement` へ渡る」という状態そのものが**到達不能**になる。規範の増補（「追加分は自分で確認せよ」）ではなく、`docs/development-principles.md`「構造的設計原則と強制の階梯」でいう「その状態を作れなくする」段で解く。

## §1 文脈 — #713 サイクルの一次証拠

`2026-07-26-skill-workflow-boundary-design.md` は「検証水準が**入口**で変わる」（F3）を、`/implement` を止めることで解いた。#821 はその残余で、**同じ入口の中で時間的に変わる**。

#713 の実測:

1. `/plan-review` を回し、台帳 4 エントリ（3 スカウト + 独立導出）が**全件成立**して着地した
2. 独立導出の発見をユーザーへ諮り、裁定を受けて計画へ **findings クラスを 1 つ丸ごと追加**した
3. 追加分は**どのレビューも受けていない**まま `plan.md` に同居した
4. 実際にその追加分に欠陥があった（`[workspace.lints.rustdoc]` が「非空かつ全エントリ deny」という述語が、必須 lint の行が 1 つ消えた形を緑で通す）。実装前に述語を実データへ当てて発見した

**既存の条項では拾えない。** `/start-issue`「5b. セルフレビュー（plan-review 固有の補完）」の免除除外は「plan-review が『独立レビュー不成立』と報告したエントリ」を対象とするが、今回は不成立ゼロゆえ発火しない。

**git のコミット順による検知は fail-open である。** #713 では `plan-review/` の最終更新（`6885b33`）と `plan.md` の最終更新（`724e6fa`）に差が出たが、これは Step 6 のコミット後に追記したという偶然による。通常フローは 5a → 5b → Step 6 の順で **1 コミットに畳まれる**ため、5b 中に育った計画は差を生まない。

## §2 決定

### 2-1. ループの制御は `/start-issue` が持つ

`/plan-review` は **1 ラウンドを実行する単位**のまま変えない。理由は 2 つある。

- 収束判定は「`plan.md` が動いたか」であり、**計画を所有する側にしか測れない**。`/plan-review` は計画を所有せず、`allowed-tools` から `Write` を意図的に外してある（判定者が成果物を自分で書けると、実在確認も中身の検査も自作自演で通る）
- `/plan-review` の単独起動という経路を壊さない

### 2-2. ラウンドの形

```
ラウンド N（上限 3）:
  1. workspace/plan.md を workspace/reviewed-plan.md へ複製する（このラウンドの入力を固定）
     ※ 複製の置き場所は workspace/plan-review/ の**外側**である。同ディレクトリは
       /plan-review「Step 2」が起動時に rm -rf するため、内側に置くと毎ラウンド消える
  2. /plan-review を回す（Step 2 / Step 2b / Step 3）
  3. 要対処と 5b の 3 観点を反映して plan.md を**修正**する（記録は書かない・下記の順序の罠）
  4. git diff --no-index workspace/reviewed-plan.md workspace/plan.md
       空   → 収束。ループを抜ける
       非空 → ラウンド N+1 へ
収束後: セルフレビュー節へラウンド数と最終ラウンドの結果を記す → Step 6
```

収束したとき、最後のラウンドの `workspace/plan-review/` は「**最終形の `plan.md` を全レイヤーでレビューした成果物**」である。前ラウンド分が `/plan-review`「Step 2」の `rm -rf` で消えるのは正しい——既に `plan.md` へ畳み込まれた、役目を終えた写しだからである。

**順序の罠**: セルフレビュー節への記録を収束判定より**前**に書くと、その記述自体が diff を非空にして**永久に収束しない**。**ラウンド内で行うのは計画の修正だけ**であり、記録（ラウンド数・最終ラウンドの結果・不成立の有無・未収束で打ち切った事実）は収束または打ち切りの後に 1 度だけ書く。

### 2-3. ラウンド 2 以降の範囲

- **Step 2b（独立導出）は毎ラウンド全体を再導出する。** issue が SSOT なので、計画がどう育っても引きずられない。全体の盲点検出はここが担保する
- **Step 2 のスカウトは、前ラウンドから変わった範囲に触れるレイヤーだけ**起動する。**「触れる」の判定は台帳の分割根拠に対して行う**——台帳は「レイヤー名 → 出力パス → 分割根拠（plan.md の変更ファイル）」で構成されるので、diff が動かした `plan.md` の記述が指す**変更ファイル**を分割根拠に含むレイヤーが対象である。判定は diff の行位置ではなく変更ファイルで行う（節の移動や書式の変更だけで全レイヤーが起動するのを避ける）

台帳の値が 2 値から **3 値**になる。**「起動しなかった」を「問題なし」に化けさせない**ためである。

| 値 | 意味 |
|---|---|
| 実在 | 当ラウンドで起動し、成果物が着地した |
| 不着 | 起動したが届かなかった（1 度だけ再起動 → それでも不着なら独立レビュー不成立） |
| 当ラウンド対象外 | 前ラウンドで検証済みで、当ラウンドの差分がその範囲に触れていない |

### 2-4. 失敗時

- **3 ラウンドで収束しない** → 停止してユーザーへ返す。各ラウンドの diff の要約（何が毎ラウンド計画を動かしているか）を添える。無言で 4 ラウンド目に入らない
- **不着が残るラウンドは収束と判定しない**（そのレイヤーは検証されていないため）
- **ピンポン**（指摘を取り込む → 別の指摘が出るの往復）専用の検知は置かない。上限 3 が事実上のガードになる（YAGNI）

### 2-5. 費用

#713 のラウンド 1 は 4 体で約 52 万トークン（96k / 92k / 154k / 180k）。2-3 の分割により、典型的なラウンド 2 は独立導出（約 18 万）+ 差分スカウト 1〜2 体で**約半額**。典型 2 ラウンドの総額は約 80 万トークン。

## §3 検討した代替案と却下理由

- **条項だけを足す**（5b の免除除外に「レビュー後に追加した部分にも及ばない」を追加）: 却下。**書き手が「育った」と自覚しないと発火しない**。#713 では計画を育てた当人が、育てた自覚のないまま Step 6 まで進み `plan.md` に「レビュー済み」と書いた。自覚に依存する規範は、同じ地点で同じ判断を再生産する。
- **差分の導線だけを足す**（レビュー時点の複製と `plan.md` を 5b で突き合わせ、育った部分をセルフレビュー節へ明記する）: 却下。差分は見えるが、**見えた後に何をするかが「自分で確認する」に留まる**——独立性の無い確認であり、`/plan-review` が担うはずの多レンズ・独立導出は復元されない。ただしこの案の**複製を取る操作**はループの入力固定として採用した（2-2 の手順 1）。
- **`/implement` 側で検知して止める**: 却下。`/implement`「1a. workspace/plan.md の由来を確かめる」の表に「一部だけレビュー到達」という第 3 の状態が生まれ、`2026-07-26-skill-workflow-boundary-design.md` が減らした判定を再び増やす。加えて引き渡しが 1 往復増える。**責任は渡す前に閉じる側に置く**（利用者裁定・2026-07-28）。
- **終了条件を「要対処 0 件」にする**: 却下。要対処 0 件でも「軽微な懸念」を取り込んで計画を直せば、その修正分がまた未レビューになる——**同じ穴が小さく残る**。「`plan.md` が動かなかった」は #821 の不変条件そのものと同値であり、diff で機械判定できる。
- **終了条件を「2 ラウンド連続で新規指摘なし」（loop-until-dry K=2）にする**: 却下。保証は最も強いが、収束していても必ずもう 1 ラウンド回るため費用が常に約 52 万トークン上乗せされる。計画レビューは探索（未知個数のバグ探し）ではなく**特定の成果物に対する照合**であり、K=2 が守る「まだ見ぬ発見」の余地は小さい。
- **毎ラウンド台帳をフルで回す**: 却下。規則は 1 つで単純だが、収束までに 100 万トークンを超えうる。独立導出を毎ラウンド全体で回す限り、全体の盲点検出は落ちない。
- **ラウンド上限を置かない**: 却下。ピンポンで止まらなくなる危険を利用者が引き取ることになる。上限 3 + 停止して返す方が、判断の材料を人へ渡せる。

## §5 検証

規範の変更ゆえ機構のテストは書けない。代わりに 2 点で測る。

1. **実サイクルでのフォールトインジェクション**: 次に `/start-issue` を回すとき、レビュー後に意図的に計画を 1 節育て、(a) ラウンド 2 が起動すること、(b) セルフレビュー節を先に書くと収束しない罠を踏まないこと、を 1 度確かめる。稼働中のガードを弱める操作を含まないので実サイクルで行える（`.claude/rules/safety-nets.md`）
2. **`/norm-review` は起動しない**: 判定を足す変更ゆえ条項上は対象だが、指摘の採用率が低いという 2026-07-27 の裁定に従う。この判断自体を本節に記録して、省略が黙って起きないようにする

## §6 受容する残余

- **ループが守るのは `plan.md` の全体がレビューを受けたことであって、レビューの質ではない。** 収束は「レビューが計画を動かさなかった」ことしか意味しない——見落としたまま動かさなかった場合も収束する。質は `/plan-review`「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」が担う
- **上限 3 で打ち切った場合、その計画は未収束のまま人へ渡る。** そのとき `/implement` へ進むかは人の判断であり、進むなら「未収束である」ことを `plan.md` のセルフレビュー節へ書く
- **`/plan-review` を単独起動した場合、ループは存在しない**（制御は `/start-issue` にあるため）。その経路で得られるのは従来どおり「その時点の計画に対する 1 ラウンド」である
