# 計画に「未確定」欄を持たせ、それが空になるまでレビューを回す — 設計（2026-07-28）

> **Superseded:** 常時fan-outと最大3ラウンドの自動レビューは `docs/adr/ADR-risk-tiered-plan-review.md` で廃止した。未確定欄の契約だけが現行スキルに残る。

日付: 2026-07-28 / 対象: #821（`/start-issue` → `/plan-review` → `/implement` の引き渡し）

## §0 要旨

`plan.md` に **「未確定（実装前に潰す）」節**を新設し、`/plan-review` を**その欄が空になるまで**回すループにする。

目的は「レビューが計画全体を覆ったこと」ではない。**実装時に判断が要らない `plan.md`** を作ることである。レビューの網羅は代理指標にすぎず、両者はずれる——**誰も疑問を出さなければ、レビューが全体を覆っても迷いは残る**。

引き渡し契約は「レビュー済みの計画」から「**未確定がゼロの計画**」へ変わる。判定は自己申告（セルフレビュー節の有無）から**機械判定**（未確定欄の見出しが在り、かつ `- [ ]` がゼロ）へ移る。

**収束は 2 条件の AND である**——「未確定が空」（実装へ渡れるか）と「そのラウンドで計画が動かなかった」（再レビューが要るか）。**この 2 つは別の問いであり、1 つの判定器に畳んではならない**（§3・レビューで実測された欠陥）。

## §1 文脈

### 1-1. #821 の一次証拠（#713 サイクル）

`2026-07-26-skill-workflow-boundary-design.md` は「検証水準が**入口**で変わる」（F3）を、`/implement` を止めることで解いた。#821 はその残余で、**同じ入口の中で時間的に変わる**。

1. `/plan-review` を回し、台帳 4 エントリ（3 スカウト + 独立導出）が**全件成立**して着地した
2. 独立導出の発見をユーザーへ諮り、裁定を受けて計画へ **findings クラスを 1 つ丸ごと追加**した
3. 追加分は**どのレビューも受けていない**まま `plan.md` に同居した
4. 実際にその追加分に欠陥があった（`[workspace.lints.rustdoc]` が「非空かつ全エントリ deny」という述語が、必須 lint の行が 1 つ消えた形を緑で通す）。実装前に述語を実データへ当てて発見した

**既存の条項では拾えない。** `/start-issue`「5b. セルフレビュー（plan-review 固有の補完）」の免除除外は「plan-review が『独立レビュー不成立』と報告したエントリ」を対象とするが、今回は不成立ゼロゆえ発火しない。

**git のコミット順による検知は fail-open である。** #713 では `plan-review/` の最終更新（`6885b33`）と `plan.md` の最終更新（`724e6fa`）に差が出たが、これは Step 6 のコミット後に追記したという偶然による。通常フローは 5a → 5b → Step 6 の順で **1 コミットに畳まれる**ため、5b 中に育った計画は差を生まない。

### 1-2. 「実装時に迷いがない」の分解

#713 で実装時に判断を強いられた箇所は、次の 5 つが埋まっていないときだった。

| # | 埋まっているべきもの | #713 での実例 |
|---|---|---|
| 1 | 判定ロジック・値が**実データで確定**している | 述語 2 案を 9 ケースで測って初めて R2 の欠陥が出た |
| 2 | **選択が決着**している（代替案が却下理由付きで消えている） | 粒度・glob・lint 名の名指し |
| 3 | **事実の裏取り**が済んでいる | cargo の exit code 6 形、issue の引用先の腐り |
| 4 | **境界と異常系**が列挙されている | 母集団の欠落 6 形 |
| 5 | **完了の判定**が書いてある | テストと検証コマンド |

5 つはすべて「**まだ確定していない**」という 1 つの状態に還元できる。ゆえに置くべきは「レビュー回数の規則」ではなく、**未確定を明示する欄**である。

## §2 決定

### 2-0. 状態の置き場所の原則

**収束判定に要る状態はすべて `plan.md` に置き、かつ `plan.md` の差分として見える形で書く。**

このループで持続する面は `plan.md` だけである——`workspace/plan-review/` は `/plan-review`「Step 2」の `rm -rf` で毎ラウンド消え、セルフレビュー節への記録は収束後の 1 度だけで、会話コンテキストはセッション中断で巻き戻る（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）。

**判定に要る状態を持続面の外に置くと、中断のたびに判定が壊れる。** ラウンド番号（2-1）・「前ラウンドで検証済み」の根拠（2-3）・未確定を潰した結果（2-2 の手順 3）は、いずれもこの原則の系である。

### 2-1. `plan.md` の「未確定（実装前に潰す）」節

`/start-issue`「Step 4 — 実装計画（workspace/plan.md）」が定める `plan.md` の構成へ、この節を足す。

- **見出しは固定接頭辞への前方一致で照合する**（`## 未確定（実装前に潰す）` で始まる行）。**「固定文字列」ではない**——下記のとおり見出し行にラウンド番号が付くためで、完全一致で照合する実装は初回から見出しを見失う。`/implement`「1a」の判定と収束条件 (i) は**同じ照合形を共有する**（`#749` の PreToolUse ゲートは見出しを見ず `plan.md` 全体の `- [ ]` を数えるので、欄の項目もフェーズの作業項目も等しく効く。それでよい）
- `- [ ]` のチェックリストで列挙する。各項目は 2 つを持つ: (a) **何が決まっていないか**、(b) **どう確定させるか**（測る / 決める / 裏取りする）
- フェーズ配下の作業項目（**何を実装するか**）とは**別のリスト**である。混ぜない（§3 で却下理由）
- 確定したら `- [x]` にし、**確定させた結果**（測定値・裁定・却下した代替案）を同じ行か直下に残す。「受容する残余」として畳んだ場合もそう書いて `- [x]` にする
- **裁定によって受容した項目には、裁定の出所（利用者の発言の引用と日付）を必ず書く。** `- [x]` へ倒す正規手順（§2-4）は**脱出レシピの文書化でもある**——締切圧の下で裁定なしに自己受容されても、`1a`・`#749` ゲート・`/implement`「Step 5 — コミット」のどれも鳴らない。機構では止めず、**事後監査を可能にする**ことで受容する（ルート `CLAUDE.md` の外にある個人規範「指示の出所を確認する」と同型）
- **見出し行にラウンド番号を持たせる**（`## 未確定（実装前に潰す）— ラウンド N`）。台帳は `/plan-review`「Step 2」の `rm -rf` で毎ラウンド消え、セルフレビュー節への記録は収束後の 1 度だけなので、**ラウンド数を持つ永続面がほかに無い**。会話コンテキストにしか無いとセッション中断で巻き戻り、上限 3 が事実上外れて費用を二重払いする（ルート `CLAUDE.md`「サブエージェント委譲と worktree」の「中断を前提に設計する」）
- **欄を最初に埋めるのは、レビューではなく計画を書いた当人である。** `/start-issue`「Step 4 — 実装計画（workspace/plan.md）」の時点で §1-2 の 5 分類を自己チェックリストとして使い、**レビュー前に潰せるものは潰しておく**。これが最も安い埋め手であり、「レビュー → 潰す → 再レビュー」の 1 往復を「潰す → レビュー」へ縮める

例:

```markdown
## 未確定（実装前に潰す）

- [ ] ルート側の述語が「非空かつ全エントリ deny」で足りるか — **測る**: 必須 lint の行が
      1 つ消えた入力を作り、実ルート `Cargo.toml` を含む代表ケースで両案を実行する
- [ ] `members` の glob 要素を展開するか — **決める**: 現在 0 件。展開器は YAGNI か
```

### 2-2. ループ — 欄が空になるまで回す

```
ラウンド N（上限 3）:
  0. **先に**未確定欄の見出しのラウンド番号を N へ繰り上げ、**その後で** plan.md の
     スナップショットを取る（このラウンドで計画が動いたかの基準）。
     保存先は workspace/plan-review/ の**外側**（Step 2 の rm -rf の射程外）。
     ※ 順序を逆にすると、繰り上げそのものが差分になって条件 (ii) が恒偽になり、
       全サイクルが上限 3 の打ち切りへ落ちる
  1. /plan-review を回す（Step 2 / Step 2b / Step 3）
  2. 指摘を必ずどちらかへ落とす:
       (a) 計画の修正        — 答えが決まっているもの
       (b) 未確定欄への追加  — 測る・決める・裏取りするまで答えが出ないもの
  3. 未確定欄を潰す（実測・裁定・裏取り）。潰せた項目を - [x] にし、結果を残す。
     **潰す作業が新しい疑問を生んだら、それも欄へ足す**（疑問の出所はレビューに限らない）。
     **確定した結果は欄の中に留めず、計画本文（変更ファイル一覧・実装順序・不変条件・
     テスト方針）へ畳み込む**——欄の中だけで完結した差分は「変更ファイル」を動かさず、
     次ラウンドのスカウト起動判定（§2-3）に乗らないため、強制されたラウンドの中身が
     独立導出だけになる
  4. 収束判定（2 条件の AND）:
       (i)  未確定欄に - [ ] が残っていない
       (ii) このラウンドで plan.md が動かなかった（手順 0 のスナップショットとの差分が空）
       両方成立 → 収束。ループを抜ける
       いずれか不成立 → ラウンド N+1 へ
収束後: セルフレビュー節へラウンド数と最終ラウンドの結果を記す → Step 6
```

**条件 (ii) を落としてはならない。** (i) だけにすると、**最終ラウンドで未確定を潰した結果が、誰のレビューも受けずに収束する**——ラウンド 1 で未確定が 4 件出て 4 件とも実測で潰せた場合、計画は当然動いているのに欄は空になり、動いた部分が未レビューのまま実装へ渡る。これは #713 の「裁定を受けて追加した findings クラスが未レビューのまま同居した」の再演である。**(i) は「実装へ渡れるか」を、(ii) は「再レビューが要るか」を判定しており、別の問いである。**

条件 (ii) だけを収束条件にする案は §3 で却下しているが、それは「**不動点だけ**を条件にする」案に対する却下であって、第 2 条件としての併用には当たらない。

**収束を保証するのは上限 3 であって、「レビューが増やし実測が減らす」という非対称ではない。** その非対称は成り立たない——#713 で欠陥を見つけたのは**実測**（述語を実データへ当てた）であり、実測こそ新しい疑問を生んだ張本人である。**欄を増やせるのはレビューに限らない。**

**費用の見積もり**: 条件 (ii) の追加で必ず 1 ラウンド増えるわけではない。ラウンド N のレビューが何も言わず、未確定も残らず、計画に手を触れなければ、そのラウンドで両条件が同時に成立する。増えるのは「最終ラウンドで計画を動かした」場合だけで、そのときの追加分は差分スカウトだけの**縮小ラウンド**で済む。

**順序の罠**: セルフレビュー節への記録（ラウンド数・不成立の有無・未収束で打ち切った事実）は**収束または打ち切りの後に 1 度だけ**書く。ラウンド内で行うのは計画の修正と未確定欄の更新だけである。

### 2-3. ラウンド 2 以降の範囲

- **Step 2b（独立導出）は毎ラウンド全体を再導出する。** issue が SSOT なので、計画がどう育っても引きずられない。全体の盲点検出はここが担保する。**再導出は凍結した導出物の再利用より高いが、ラウンドごとに別の見落としへ気づく探索的価値を残す**ための費用である（利用者裁定・2026-07-28。凍結案の却下理由は §3）
- **Step 2 のスカウトは、前ラウンドから変わった範囲に触れるレイヤーだけ**起動する。**「触れる」の判定は台帳の分割根拠に対して行う**——台帳は「レイヤー名 → 出力パス → 分割根拠（plan.md の変更ファイル）」で構成されるので、差分が動かした記述が指す**変更ファイル**を分割根拠に含むレイヤーが対象である。差分の行位置ではなく変更ファイルで判定する（節の移動や書式の変更だけで全レイヤーが起動するのを避ける）
- **台帳のレイヤー集合は毎ラウンド `plan.md` の変更ファイル一覧から取り直す。** 未確定を潰した結果、計画に**新しい変更ファイル**が加わることがある（#713 の findings クラス追加がまさにこの形）。前ラウンドの台帳を使い回すと、その新ファイルは**どのレイヤーの分割根拠にも含まれず、どのスカウトも起動しないまま「当ラウンド対象外」へ化ける**——3 値を導入した当の目的（起動しなかったを問題なしに化けさせない）を自ら破る。**どのレイヤーにも属さない変更ファイルを見つけたら、新レイヤーとして台帳に足して起動する**

台帳の値が 2 値から **3 値**になる。**「起動しなかった」を「問題なし」に化けさせない**ためである。

| 値 | 意味 |
|---|---|
| 実在 | 当ラウンドで起動し、成果物が着地した |
| 不着 | 起動したが届かなかった（処理は `/plan-review`「Step 3 — 結果の統合と報告」の既存規則に従う） |
| 当ラウンド対象外 | **前ラウンドで検証済み**であり、かつ当ラウンドの差分がその範囲に触れていない。**新規に現れたレイヤーはこの値を取れない**（前段の前提が成り立たないため） |

**「前ラウンドで検証済み」を証せないときは、対象外にせず起動する。** 前ラウンドの台帳も成果物も `rm -rf` で消えており、レイヤー境界は毎ラウンド取り直しで動きうるので、**新旧レイヤーの対応と「検証済み」という事実は会話コンテキストにしか無い**——セッションを中断して再開した直後がその状態である。安全側（起動する）へ倒せば費用で済むが、規範に書かなければ実行者は記憶を根拠に「対象外」と書く。

`/plan-review`「Step 2」が起動時に `workspace/plan-review/` を `rm -rf` する仕様は**そのまま利点になる**。最終ラウンドの成果物が「最終形の `plan.md` を全レイヤーでレビューしたもの」であり、前ラウンド分は既に `plan.md` へ畳み込まれた、役目を終えた写しだからである。

### 2-4. 失敗時

- **3 ラウンドで収束しない**（未確定が残り続ける） → 停止してユーザーへ返す。**残っている未確定項目と、それを潰せなかった理由**を添える。無言で 4 ラウンド目に入らない
- **人が「未確定を受容して進む」と裁定した場合の正規手順は、`- [x]` へ倒して「受容する残余」と理由を書くことである**（§2-1 の形式）。`- [ ]` のまま残す運用にしてはならない。理由は 2 つ:
  - `#749` の PreToolUse ゲートが `gh pr create` を拒むため、**受容して進む経路に PR を出す手段が無くなる**。実際には結局 `- [x]` へ倒すことになり、ゲートは何も守らないまま「チェックを消化する圧力」だけを生む
  - `/implement`「Step 5 — コミット」は未チェックが残る `workspace/` を削除しないため、**残留した `plan.md` が次サイクルの無関係な PR 作成まで拒む**（ゲートの判定はリポジトリルートの `workspace/plan.md` 単位であり、ブランチや issue に紐づかない。`.claude/hooks/pre-bash.mjs` で実測）
- **不着が残るラウンドは収束と判定しない**（そのレイヤーは検証されていないため）
- **ピンポン専用の検知は置かない**。上限 3 が事実上のガードになる（YAGNI）

### 2-5. 引き渡し契約と、既存機構へのただ乗り

`/start-issue`「出力」の引き渡し契約を「レビュー済みの計画」から「**未確定がゼロの計画**」へ言い換える。`/implement`「1a. workspace/plan.md の由来を確かめる」の表は **2 値のまま**で、「レビュー到達」の**判定基準だけ**が置き換わる（自己申告 → 機械判定）。

**判定基準は「未確定欄の見出しが存在し、かつ `- [ ]` がゼロ」である。件数だけを見てはならない**——欄を**書かなかった**計画（＝まさに自覚なき書き手の産物）が件数ゼロで素通りする。旧判定（セルフレビュー節の有無）なら節の書き忘れで止まったものが、件数だけの判定では通ってしまい、**fail-open の向きに退化する**。§6 が認める `/plan-review` 単独起動の経路は欄の無い `plan.md` を今後も生むため、これは理論上の穴ではない。表に第 3 の状態を作らないのは、`2026-07-26-skill-workflow-boundary-design.md` が減らした判定を再び増やさないためである。

未確定を `- [ ]` で書くことで、**新しい検出器を書かずに 2 つの既存機構が効く**:

- `#749` の PreToolUse ゲート — 未チェックの `- [ ]` が `plan.md` に残ると `gh pr create` を拒否する
- `/implement`「Step 5 — コミット」 — 全項目が `- [x]` でなければ `workspace/` を削除しない

### 2-6. 効果の測定

この設計が効いているかを測る値を 1 つ持つ。`/implement`「Step 2 — 実装」は既に「実装中に判明した計画外の作業は `- [ ]` として `plan.md` へ追記する」と定めている。**その追記件数が「計画が残した迷いの量」の実測値**である。`/retrospective` でこれを見る（#713 サイクルでは Phase 5 の 7 件がそれに当たる）。

### 2-7. 費用

#713 のラウンド 1 は 4 体で約 52 万トークン（96k / 92k / 154k / 180k）。2-3 の分割により、典型的なラウンド 2 は独立導出（約 18 万）+ 差分スカウト 1〜2 体で**約半額**。典型 2 ラウンドの総額は約 80 万トークン。

## §3 検討した代替案と却下理由

- **条項だけを足す**（5b の免除除外に「レビュー後に追加した部分にも及ばない」を追加）: 却下。**書き手が「育った」と自覚しないと発火しない**。#713 では計画を育てた当人が、育てた自覚のないまま Step 6 まで進み `plan.md` に「レビュー済み」と書いた。自覚に依存する規範は、同じ地点で同じ判断を再生産する。
- **ラウンド 2 以降、独立導出を凍結した導出物との照合に置き換える**: 却下（利用者裁定・2026-07-28）。**却下の根拠は「導出は決定的ではない」ことである**——「issue が不変なら導出結果も不変ゆえ再導出は再計算にすぎない」という論は、前提が誤っている。同じ入力から同じ列挙が出るとは限らず、**再導出はその非決定性を引き直す操作**である。#713 では独立導出 1 体が、issue 本文が定義していなかったルート側の沈黙経路を見つけた。凍結すればその引き直しが二度と起きない。買っているのは「再計算」ではなく**再抽選**であり、費用（1 ラウンドあたり約 18 万トークン）はその対価である。
- **収束条件を「そのラウンドで `plan.md` が動かなかった」だけにする**: 却下。**プロセスの不動点であって計画の性質ではない**——「レビューが何も言わなかった」でも成立し、疑問が出なかっただけの計画を収束と判定する。目的は「実装時に判断が要らない計画」であり、判定はその性質そのもの（未確定がゼロ）に対して行う。なお未確定を潰せば計画は動くので、実務上この 2 つは連動する。**連動する 2 つのうち、目的に近い方を判定に使う。**
- **収束条件を「要対処 0 件」にする**: 却下。要対処 0 件でも「軽微な懸念」を取り込んで計画を直せば、その修正分がまた未レビューになる——同じ穴が小さく残る。
- **収束条件を「2 ラウンド連続で新規指摘なし」（loop-until-dry K=2）にする**: 却下。保証は最も強いが、収束していても必ずもう 1 ラウンド回るため費用が常に約 52 万トークン上乗せされる。計画レビューは探索（未知個数のバグ探し）ではなく**特定の成果物に対する照合**であり、K=2 が守る「まだ見ぬ発見」の余地は小さい。
- **未確定をフェーズ配下の作業項目に混ぜる**: 却下。新しい節を作らずに済むが、**「未確定が残っているか」を一目で数えられなくなる**。作業項目（何を実装するか）と未確定（何が決まっていないか）は種類が違い、後者だけが実装着手の可否を決める。
- **欄を作らず、セルフレビュー節で「未確定はない」と宣言する**: 却下。最も軽いが、**宣言は自覚に依存する**——#713 で失敗したのがまさにその形である。
- **差分の導線だけを足す**（レビュー時点の複製と `plan.md` を突き合わせて育った部分を明記する）: 却下。差分は見えるが、見えた後に何をするかが「自分で確認する」に留まり、`/plan-review` が担う多レンズ・独立導出は復元されない。
- **`/implement` 側で検知して止める**: 却下。1a の表に「一部だけレビュー到達」という第 3 の状態が生まれ、引き渡しが 1 往復増える。**責任は渡す前に閉じる側に置く**（利用者裁定・2026-07-28）。
- **毎ラウンド台帳をフルで回す / ラウンド上限を置かない**: 却下。前者は収束までに 100 万トークンを超えうる（独立導出を毎ラウンド全体で回す限り、盲点検出は落ちない）。後者はピンポンで止まらなくなる危険を利用者が引き取ることになる。

## §5 検証

規範の変更ゆえ機構のテストは書けない。代わりに 4 点で測る。

1. **実サイクルでのフォールトインジェクション**: 次に `/start-issue` を回すとき、レビュー後に意図的に疑問を 1 件足し、(a) それが未確定欄へ落ちること、(b) 欄が空でないうちはラウンド 2 が起動すること、を確かめる。稼働中のガードを弱める操作を含まないので実サイクルで行える（`.claude/rules/safety-nets.md`）
2. **既存ゲートへのただ乗りの実測**: 未確定欄に `- [ ]` を残したまま `gh pr create` を打ち、PreToolUse ゲートが拒否することを 1 度確かめる（`#749` の機構が新しい節にも効くことの確認）
3. **fail-open 側の実測**: 未確定欄の**見出しごと無い** `plan.md` を作り、`/implement`「1a」の判定が**止まる**ことを確かめる。件数だけを見る実装に退化していれば、ここが素通りする（§2-5 の欠陥がこの 1 件で必ず鳴る）
4. **`/norm-review` は起動しない**: 判定を足す変更ゆえ条項上は対象だが、指摘の採用率が低いという 2026-07-27 の裁定に従う。この判断自体を本節に記録して、省略が黙って起きないようにする

## §6 受容する残余

- **欄が守るのは「書かれた疑問が潰れたこと」であって、「疑問が出尽くしたこと」ではない。** 誰も気づかなかった論点は欄に載らない。そこを担うのは `/plan-review`「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」であり、**欄はその出力の受け皿**である
- **未確定を潰す品質は測れない。** 「測って確定した」と書けても、測り方が悪ければ間違った確定になる。ここは `AGENTS.md`「検証の作法（全タスク共通）」の「判定の中核は自分で測る」に委ねる
- **上限 3 で打ち切った場合、未確定を残したまま人へ渡る。** そのとき `/implement` へ進むかは人の判断であり、進むなら §2-4 の正規手順（`- [x]` へ倒して「受容する残余」と理由を書く）に従う。**この受容は記録に残るが、機構は止めない**——止めるべきかどうかを判断できるのは人だけである
- **`/plan-review` を単独起動した場合、ループは存在しない**（制御は `/start-issue` にある）。その経路で得られるのは従来どおり「その時点の計画に対する 1 ラウンド」である
