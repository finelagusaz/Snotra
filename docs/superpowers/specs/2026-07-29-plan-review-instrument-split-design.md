# /plan-review の計器分割 — 未確定の行き先と、有界な問いの道具化 設計（2026-07-29）

## §0 要旨

`/start-issue`「レビューのループ（上限 3 ラウンド）」は既に収束を保証している。**打ち切りに達する理由として 3 つを挙げる。うち 1 つは意図された設計である**（網羅は保証しない・§9）。本設計が扱うのは残る 2 つ。

1. **未確定欄が「実装前に潰す」だけを行き先に持つ。** 実装しなければ精度が出ない問いは定義上そこで潰せず、ラウンドを消費して上限に当たる（§2 機序 A）
2. **有界な問い（母集団がコードで決まるもの）を、道具ではなく読解者が数えている。** `plan:ledger` が機械化したのは配送であって、検証内容の母集団ではない（§2 機序 B）
3. **（設計どおり）非決定的な再導出を毎ラウンド回している。** 新しい発見は毎ラウンド出うる——盲点検出のための仕様であって、直す対象ではない（§2 機序 C）

**ゆえに本設計の目標は「打ち切りをゼロにする」ことではない。** 打ち切りの原因から 1 と 2 を取り除くことである。**この区別を落とすと撤回条件が書けない**——機序 C が独立に打ち切りを起こすため、「打ち切りが起きたか」で判定すると本設計が完璧に効いていても失敗と読める（§8）。

足す設計ではない。**問いを母集団で分け、それぞれ既にある計器へ配り直す。**

**投入は 2 段に分ける。** §4（申し送り節）は文書だけの変更で機構の追加がゼロ、§5（道具化）は**仮説の spike から始めて、支持されなければ着手しない**（§5）。どちらにも**撤回の条件を事前に書いてある**（§8）——検収条件が代理指標しか持たないため、失敗と認める線を先に引かないと後から解釈で守れてしまう。

## §1 文脈 — 既に入っているもの（本設計の前提であって、対象ではない）

| 機構 | 所在 |
|---|---|
| ラウンド上限 3 + 収束判定（未確定ゼロ AND 計画が動かなかった）+ 打ち切りで人へ返す | `/start-issue`「レビューのループ（上限 3 ラウンド）」 |
| 台帳の母集団固定・双方向照合・exit 3 値 | `npm run plan:ledger`（`scripts/plan-review-ledger.mjs`） |
| 計画が持ち込んだ述語を実測する規律 | `AGENTS.md`「検証の作法（全タスク共通）」+ 未確定欄の「測る」 |
| 判断の問いを人へ返す経路 | 同ループの 3 ラウンド打ち切り |

**これらを再設計しない。** 本設計は、この上に残った穴だけを扱う。

## §2 観測と、それを説明する機序

**観測**（利用者・2026-07-29）: `/plan-review` が 3 ラウンドまで回っても調べ切れず、`/implement` が残りを巻き取っている。

**一次情報は利用者の観察のみである。** 過去のラウンド数はリポジトリから復元できない（`workspace/` は `/implement`「Step 5 — コミット」が毎サイクル削除し、`RETROSPECTIVE.md` は上書き）。以下は、その観察を説明しうる機序であって、測定ではない。

### 機序 A — 潰せない問いが欄に残り続ける

未確定欄の定義は「実装前に潰す」であり、`/start-issue`「Step 4 — 実装計画（workspace/plan.md）」は「**計画の完成とは、この欄が空になることである**」と定める。`/implement`「1c. 止まったときの引き渡し」1c-B は、未確定が残る計画での実装着手を禁じる。

ところが、**実装しなければ精度が出ない問いが存在する**。利用者の観察はこうである——「実装中だとテストしながら進めるからコードリーディングより精度は高い」。これは計器の性能差であって、努力で埋まるものではない。

この類の問いは、欄の定義上どのラウンドでも `- [x]` にできない。ゆえに収束条件 (i) が成立せず、**上限 3 まで回って打ち切りになる**。

同じ矛盾が、別の面にも現れている。`/implement`「4a. check スキルの実行」は「**計画に無い変更は実装中に必ず生じる**」と書く。これは「計画の完成 = 未確定ゼロ」と正面から衝突する。加えてこの文は前提条件も引用も持たない全称であり、`AGENTS.md`「検証の作法（全タスク共通）」の「全称表現は前提条件とセットで書く。書けないなら書かない」に自ら当たっている。**どちらかが誤りなのではなく、両方が同じ取り違えの表と裏である**——実装前に決まる問いと、実装しないと決まらない問いを、一つの尺度で測っている。

### 機序 B — 有界な問いを、有界性を使わずに解いている

当時の /plan-review「Step 2 — 並列サブエージェントで検証」の検証観点は、呼び出し元 grep・対称ペア・リソースの生成/破棄・受け皿 issue の実在など、**母集団がコードから一意に決まるもの**を多く含む。にもかかわらず、各スカウトが自分で母集団を作って報告する形になっている。

`/plan-review` 自身が参照する `docs/development-principles.md`「列挙の完全性」は「列挙の SSOT はツール自身に問う」と定める。**有限の問いを、有限性を使わない方法で解いているから、ラウンドを重ねても残余が減らない。**

### 機序 C — 非決定的な再導出を毎ラウンド回している（**これは仕様であり、直さない**）

当時の /plan-review「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」は明記する——「**Step 2b（独立導出）も毎ラウンド全体を再導出する。** 導出は決定的ではなく、**再導出はその非決定性を引き直す操作**である」。`/start-issue`「レビューのループ（上限 3 ラウンド）」も同じことを反対側から言う——「**収束を保証するのは上限 3 である。**〔…〕**実測こそ新しい疑問を生む**」。

**新しい発見が毎ラウンド出うる以上、収束条件 (ii)（このラウンドで計画が動かなかった）は原理的に安定しない。** これは欠陥ではなく、盲点検出のために選ばれた性質である（#495 の実測——列挙型トリガの的中率 0%、独立再導出だけが毎回漏れを拾った）。

**帰結として、打ち切りは異常ではない。** 打ち切りが起きたという事実だけでは、機序 A・B が残っているのか、機序 C が働いただけなのかを区別できない。**両者を弁別しないまま「打ち切りが減ったか」を成否の指標にしてはならない**（§8）。

## §3 決定 — 問いを計器で五つに分け、名前で呼ぶ

序数では呼ばない（`.claude/rules/governance-docs.md`）。

**軸は 1 つ、「何をすれば答えが出るか」＝計器である。** 母集団の有限性を軸に採ってはならない——計画が持ち込んだ述語も、YAGNI の判定対象も、`plan.md` という有限の文書に列挙し切れる。**有限性はこの五つを分けない。**

| 計器（何をすれば答えが出るか） | クラス | 使える時点 |
|---|---|---|
| **数える** — 列挙し切る | 有界な問い | 実装前 |
| **実行する** — 計画が持ち込んだ述語を | 計画述語の問い | 実装前 |
| **実行する** — システムを | 実行時の問い | **実装後** |
| **読む** — 一次資料を | 裏取りの問い | 実装前 |
| **人が決める** | 判断の問い | いつでも |

「実行する」だけが**何を実行するか**で 2 つに割れ、それが使える時点を決める。時点は軸ではなく結果である。

| クラス | 母集団 | 担い手 | 終了条件 |
|---|---|---|---|
| **有界な問い** | コードから一意に決まる集合 | 道具（grep 全件・`cargo build` の compile-fail・`governance:check`・専用スクリプト） | 全件が出力に載っている |
| **計画述語の問い** | 計画が持ち込んだ判定ロジック・fixture | plan-review の主エージェント（**委譲不可**） | 代表入力で実行した結果が `plan.md` にある |
| **実行時の問い** | ソースの外（API の実挙動・タイミング・状態到達） | `/implement` のテスト | plan-review は判定しない。**申し送り節へ移して渡す**（§4） |
| **裏取りの問い** | 計画が前提にした外部の事実（upstream の issue・外部仕様・別 issue の本文） | plan-review の主エージェント | **出所と確認日つき**で `plan.md` にある。upstream は**最終 maintainer 回答まで辿る**（#565） |
| **判断の問い** | 決着していない選択 | 人（Opus が候補を出す） | 決めた、または受容すると書いた |

### 分類が既存の列挙と噛み合うことの検算

**新しい分類は、同じリポジトリの既存の列挙に当てて検算する。** 未確定欄が持つ確定動詞は 3 つ——`/start-issue`「Step 4 — 実装計画（workspace/plan.md）」の「どう確定させるか（**測る・決める・裏取りする**）」。

| 未確定欄の動詞 | 対応するクラス |
|---|---|
| 測る | 計画述語の問い ／ 実行時の問い |
| 決める | 判断の問い |
| 裏取りする | 裏取りの問い |
| （対応なし） | **有界な問い** |

**有界な問いに対応する動詞が無いのは正しい。** 有界な問いは道具が答えるので、そもそも未確定欄へ載らない——載っているなら、それは道具を回していないという別の欠陥である（機序 B）。

**裏取りの問いは、この検算で初めて見つかった。** 分類を計器から導いただけでは出ず、既存の列挙と突き合わせて欠落が見えた。

**不変条件**: **有界な問いに残った残余は欠陥であって、受容する残余ではない。** 母集団が有限なら数え切れるはずであり、残ったのは数え損ねである。ADR の末尾が「受容する残余」で終わるのは正しい作法だが、そこに有界な問いの取りこぼしが紛れ込む余地を塞ぐ。

**上限が要るのは判断の問いだけである。** 有界な問いは数え切れば終わり、計画述語の問いと裏取りの問いは実行・参照すれば出る。実行時の問いは plan-review が判定しないので、そもそも回らない。

## §4 実行時の問いは「実装時に確かめる（申し送り）」節へ移す

**未確定欄には入れない。** `- [x]` は「解決した」を意味する記号であり、解決していないものに付けると同じ表層形が 2 つの概念を担う（`AGENTS.md`「検証の作法（全タスク共通）」の「消す/共通化する前に、同じ表層形が複数の概念を担っていないか分類する」）。

`plan.md` に**別の節**「実装時に確かめる（申し送り）」を置き、実行時の問いをそこへ移す。項目は `- [ ]` で書く。

### 既存の 2 つの判定器が、ちょうど望ましく食い違う

| 判定器 | 何を見るか | 申し送り項目に対して |
|---|---|---|
| 収束判定 (i)（`/start-issue`「レビューのループ（上限 3 ラウンド）」） | **未確定欄**の `- [ ]` | **見ない** → ループが回らない |
| PR 前ゲート（PreToolUse hook） | `workspace/plan.md` **全体**の行頭 `- [ ]`（`countUnchecked`・`.claude/hooks/pre-bash.mjs`・実測） | **見る** → PR までに必ず消し込まれる |

**新しい機構を 1 つも足さずに、「ループは止めないが、PR までには必ず確かめられる」が成立する。** 申し送り項目を `- [ ]` で書くだけでよい。

### 記号の多重定義を、なぜ片方だけ禁じるのか

この解は `- [ ]` に**未確定欄では「収束を止める」・申し送り節では「収束を止めないが PR を止める」**という 2 つの意味を与える。**冒頭で `- [x]` について却下したのと同じ多重定義を、記号から節へ移している。** 論証を省くと、却下の理由が採用した形に跳ね返る。

**許されるのは、節が構文の一部だからである。** `- [x]` の多重定義には曖昧性を解消する手がかりが無い（同じ行を見て 2 通りに読める）。節による区別には手がかりがあり、しかも**読み手が実際に節で分かれている**——収束判定は節を特定して読み、PR 前ゲートはファイル全体を読む。曖昧なのではなく、2 人の読者が別の範囲を見ているだけである。

**ただし代償がある。** `countUnchecked`（`.claude/hooks/pre-bash.mjs`）は節を一切知らない。**この設計が成立するのは hook が両者を区別できないからであり、裏を返せば hook に節を区別させる改良は、入れた瞬間にこの設計を壊す。** 精密化が後退になる形を、意図して選んでいる。

### この設計が依存している前提 — 2 つの射程の非対称

上の食い違いは、誰かが意図して作ったものではない。**偶然そこに在る非対称に乗っている。** 次のどちらかが変わると、本設計は黙って壊れる。

- **収束判定 (i) の射程が `plan.md` 全体へ広がったら** — 申し送り項目がループを止め始め、機序 A が戻る。しかも「未確定欄は空なのに収束しない」という、原因の読み解きにくい形で出る
- **PR 前ゲートの射程が特定の節へ狭まったら** — 申し送り項目が誰にも確かめられないまま PR を通る。**沈黙する側の壊れ方**である

**本設計書はこの前提を守れない。** 射程を変える人が読むのは `/start-issue`「レビューのループ（上限 3 ラウンド）」と `.claude/hooks/pre-bash.mjs` であって、`docs/superpowers/specs/` ではない（`docs/development-principles.md`「構造的設計原則と強制の階梯」——規範は行為者の視界に入る面へ置く）。

**2 つの射程は、守り方の強さが違う。等しく注記で守ってはならない。**

| 射程 | 守り方 | 根拠 |
|---|---|---|
| PR 前ゲート（`countUnchecked`） | **テストで固定する** | `export` されており、`.claude/hooks/pre-bash.test.mjs` に専用の describe が既にある。「申し送り節の未チェック項目が数に入ること」を 1 ケース足せば、節を区別させる改変は赤で止まる |
| 収束判定 (i)（`/start-issue`） | **注記のみ**（残余） | `SKILL.md` の規範であり、実行可能な述語を持たないためテストできない |

**固定できる側を固定せずに残余へ数えない**（`docs/development-principles.md`「構造的設計原則と強制の階梯」の (a) 責務を検査可能な層へ移す）。注記で守るのは、テストが書けない側だけである（§8・§9）。

### 残る設計判断

- **落とせる条件**: 申し送りへ移せるのは、**確かめる手段（テスト名・スモーク項目・確認手順）が `plan.md` に書けたときだけ**である。書けないなら実行時の問いではなく、まだ分解されていない判断の問いである。この一文が無いと、潰せない項目の逃げ道になる
- **どちらの欄にも入らない項目の行き先**: 実装前に潰せず、実装でも確かめられない項目——決着していない判断の問い——は**未確定欄に残す**。ループが上限に達し、人へ返る。**これは漏れではなく設計である**（`/start-issue`「レビューのループ（上限 3 ラウンド）」の打ち切りが受け皿）。2 つの欄が覆っていないケースは無い
- **消し込みの作法**: `/implement` の出力で各項目に **実施／該当なし** を根拠つきで割り当てる（`/implement`「Step 3 — 検証（最大5サイクル）」と「4a. check スキルの実行」の報告が既に持つ三値の作法に揃える。「該当なし」にも根拠を書く）

**`/implement`「4a. check スキルの実行」の「計画に無い変更は実装中に必ず生じる」は、この分類へ書き換える。** 根拠を持たない全称を、母集団を持つ記述に置き換える。

## §5 Step 2 の観点を、問いへ分解して計器へ配る

**母集団は当時の /plan-review「Step 2 — 並列サブエージェントで検証」の検証観点だけである。** 同「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」と「Step 3 — 結果の統合と報告」の再照合は対象外——本節は plan-review 全体を覆っていない。

**観点は分類の単位ではない。問いへ分解してから分類する。** 1 つの観点が 2 つのクラスに跨るのは、観点が複数の問いを畳んでいるからであって、分類が曖昧なのではない。跨ったまま表に置くと、実装時に「この観点はどっち」で迷う——§3 が「列挙型は当てはめで迷う」として避けた症状そのものになる。

11 観点を問いへ分解すると 15 件になる。

| # | 問い | クラス | 担い手 |
|---|---|---|---|
| 1 | 変更する関数・型・イベント定数の呼び出し元は全部で何件か | 有界 | `git grep -n` 全件（出力を切らない・`docs/development-principles.md`「列挙の完全性」）+ `cargo build -p <下流>` の compile-fail |
| 2 | それらが `plan.md` の変更ファイル一覧を外れていないか | 有界 | 差集合（#761 に依存） |
| 3 | 対称ペア（`show`/`hide` 等）の候補はどれか | 有界 | 命名規則の grep |
| 4 | その対称ペアに同様の変更が要るか | 判断 | Opus |
| 5 | `plan.md` 記載の不変条件がコードで成立するか | **実行時** | 名指しして `/implement` のテストへ渡す（§4） |
| 6 | 新規リソースに「失敗・異常終了時にどうなるか」が記述されているか | 有界 | `plan.md` の文書検査（新規導入物の列挙 × 記述の有無） |
| 7 | `false` に戻さない `AtomicBool` / `join()` 無き `spawn` / `kill(` 無き子プロセスが生まれないか | 有界 | `scripts/race-boundaries.mjs` と同型の正規表現母集団 |
| 8 | issue の要求に対して過不足がないか（YAGNI・要求未達） | 判断 | Opus |
| 9 | 既存の類似パターンで済むものを新規実装していないか | 判断 | Opus（`/dry-check` の領域） |
| 10 | 送り先を名指ししていない deferred が無いか | 有界 | 正規表現 |
| 11 | 名指しされた受け皿 issue の**本文に当該項目が実在するか** | **裏取り** | `gh issue view`。本文の読解を要し、機械化できるのは番号の実在まで |
| 12 | SPEC.md 更新要否の判断が妥当か | 判断 | Opus |
| 13 | 挙げた SPEC の §番号が実在するか | 有界 | `governance:check` の G-spec-sections が**既に持つ**（新規作業なし） |
| 14 | smoke の前提（trace イベント名・hotkey）が壊れないか | 有界 | grep 有界 |
| 15 | 設定キーの 4 点セットが計画に揃っているか | 有界 | G-config-reachability が双方向照合を持つ（対象はコード。計画段階の 4 点揃いは追加が要る） |

内訳: **有界 9（うち 1 件は既に機械化済み）・判断 4・実行時 1・裏取り 1。**

**計画述語の問いはこの表に現れない。** Step 2 の観点は「計画が正しいか」を外から見るもので、計画が持ち込んだ述語を実行する仕事は未確定欄が持つ（`AGENTS.md`「検証の作法（全タスク共通）」の「判定の中核は自分で測る」）。**空になるクラスがあること自体は欠陥ではない**——母集団が Step 2 に限られているためである。

### 一般解の前に、1 観点で spike する

**上の割り当ては仮説である。**「読解者が数えているから残余が減らない」は測定されていない。この仮説のまま 8 件分（有界 9 のうち機械化済みの 1 件を除く）の道具と #761 への依存を積むのは、検証していない前提の上に大きな設計を載せる形になる。

**先に「変更する関数・型・イベント定数の呼び出し元 grep」だけを道具化し、1 サイクル回す。** この 1 観点を選ぶ理由は 3 つある——`plan.md` の parse を要さない（変更ファイル一覧ではなく、計画に挙がったシンボルを引数で受ければよい）ので #761 に依存しない、`cargo build` の compile-fail という**独立した答え合わせの手段がある**、そして発火頻度が高い。**3 つ目だけは見立てである**——頻度は測っていない。

**spike の射程は問い #1 だけであって、#2（`plan.md` の変更ファイル一覧との差集合）を含まない。** #2 は parse を要するため #761 に依存する。同じ観点から分解された 2 件が別の依存を持つのは、分解が効いている証拠でもある。

**評価**: そのサイクルで、道具が出した候補のうちスカウトが独自に挙げていなかったものが 1 件でもあるか。**この評価に `plan.md` の parse は要らない**——比較相手はスカウトの報告であり、計画そのものではないため。無ければ仮説は支持されず、§5 の残りは着手しない。

### spike の結果で決まること

spike が仮説を支持した場合にのみ、#761 と残り 7 件の道具化へ進む。支持しなかった場合、機序 B は「読解者が数えていること」ではなく別の原因を持つことになり、**本節の一般化は破棄して原因の再特定からやり直す**。§4 はこの判断に依存しない。

### 道具の出力仕様 — 先例から継ぐものと、継がないもの

`docs/adr/ADR-race-check-population-tooling.md`「帰結」が記録した先例に倣う。

- **継ぐ**: 0 件の種別も常に印字する。証拠が義務ではなく出力そのものになり、費用が結論に依存しなくなる（`docs/check-skill-skeleton-design.md`「必須 2 — 費用対称性」）。**同時に、対応する「打ったコマンドを添える」型の条項を削除する**
- **継ぐ**: 基準リビジョンを必須引数にし、省略は非ゼロ終了で拒む。規範ではなく引数の必須性で閉じる
- **継ぐ形を延ばす**: 同 ADR「受容する残余」は「候補から境界への写し方——落とした候補は報告に現れない」を残余とした。本設計はこれを**一覧ではなく理由別の件数**で塞ぐ。`候補 65 → 採用 2 / 落とし: 宣言のみ 41・import 15・シグネチャ行 7` のように、**内訳の件数だけを常に印字する。一覧は出さない**。0 件の種別も印字するのと同じ形の延長であり、出力は数行で済み、費用は結論に依存しない。これで `.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」が挙げる形（正常時に一覧へ出ない対象は、その一覧だけを見る検査からは永遠に見えない）だけが塞がる

  **一覧の出力を義務化する案は却下した。** 「規模が違うから先例の残余を継がない」は見立てであって測定ではなく、`docs/adr/ADR-race-check-simplification.md` 却下 1 と `docs/adr/ADR-race-check-population-tooling.md` 却下 3 が二度とも否定した「測定に支えられない義務追加」に当たる。件数の内訳は義務の追加ではなく、既にある出力の形をもう一段細かくしただけである

## §6 席の変化

- **層別スカウト**: 列挙から**絞り込み**へ。道具が母集団を一つ出し、スカウトはその全件に対して採否と理由を返す。**母集団が共通になって初めて歩留まりが測れる**
- **独立導出**（当時の /plan-review「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」）: 道具に落ちない。「同概念・別名（accessor 経由・派生 signal・概念ラベル等の間接参照）を概念で分類せよ」は正規表現の外にある。**エージェントを列挙器として使う正しい用途であり、本設計は触らない**
- **主エージェント**: 変化なし（計画述語の測定と要対処の再照合は既に持つ）

## §7 依存と順序

1. **§4（申し送り節）** — 文書だけの変更。道具にも新しい機構にも依存しない。**最初に入れる**（機序 A は打ち切りの直接原因であり、費用が最も小さい）
2. **§5 の spike（呼び出し元 grep の 1 観点だけ）** — #761 に依存しない。1 サイクル回して仮説を評価する
3. **#761（`plan.md` の機械可読性）** — spike が仮説を支持した場合のみ。残りの観点の差集合と文書検査は、変更ファイル一覧を parse できることが前提
4. **§5 の一般化** — 3 に依存

**1 と 2 の間に依存は無い。** 並行して進めてよいが、同じ `SKILL.md` を触るためマージ順は決める（ルート `CLAUDE.md`「サブエージェント委譲と worktree」）。

### 分類の正本をどこに置くか

四分類の名前は、実装後に `/start-issue`（申し送り節の説明）と `/plan-review`（観点の割り当て）の両方が使う。本設計書は `docs/superpowers/` にあり**履歴資料であって正本に向かない**（`scripts/governance-check.mjs` の照合母集団からも除外されている）。

**正本は `/plan-review` に置き、`/start-issue` は参照する。** 分類は検証観点の割り当てに使われるものであり、その割り当てを持つのが `/plan-review` だからである。設計書は「なぜその分類か」の記録として残り、**分類名の定義は持たない**（`AGENTS.md`「条件別チェック（トリガー → 参照先）」の「正本を 1 か所に定め他は参照へ」）。

## §8 検収条件

- **`SKILL.md` の行数・文字数が減ること。** 道具が吸収した条項を削除する（`docs/development-principles.md`「構造的設計原則と強制の階梯」の「構造が規則を吸収したらチェックリストを削除し、ドキュメントが軽くなることを設計改善の検収条件とする」）。前後の実測を ADR へ残す
- **`/norm-review` を回す。** 条項の削除を含むため `.claude/rules/safety-nets.md` が要求する。**対照は変更前の版そのものであって、対象条項だけを抜いた版ではない**（2026-07 サイクルで対照設計を誤り、効いている条項を削除候補にしかけた実測がある）
- **PR 前ゲート側の射程を、テストで固定したか。** `.claude/hooks/pre-bash.test.mjs` の `countUnchecked` の describe へ「申し送り節の未チェック項目が数に入る」ケースを足す。**注記ではなく赤で止める**（§4）
- **収束判定側の射程に、注記を置いたか。** `/start-issue`「レビューのループ（上限 3 ラウンド）」へ 1 行。こちらはテストできないため注記が上限であり、その事実を §9 に残す
- **ラウンド数の前後比較。** ラウンド番号は `plan.md` の未確定欄見出しと `/plan-review`「Step 3 — 結果の統合と報告」の報告に載るため、PR に残る。§4 投入前後の数サイクルを ADR へ記録する（`workspace/` は削除されるので、削除されない面へ）

### 撤回の条件（事前に決める）

**上の 3 つは代理指標である。**「`SKILL.md` が短くなる」は文章を別ファイルへ移しても満たせるし、必要な条項を落としても満たせる。「`/norm-review` を回す」はプロセスの実施であって結果ではない。ラウンド数は直接指標だが、**タスクの難度で動くため交絡している**（対照は取れない——同じ計画を 2 通りの規範で回すことはできない）。

代理指標しか無い変更は、後から解釈で守れてしまう。**失敗と認める条件を先に書く。**

**打ち切りの回数を指標にしてはならない**（§2 機序 C）。機序 C は本設計と独立に打ち切りを起こすため、回数で判定すると §4 が完璧に効いていても失敗と読める。**判定は、打ち切った回の中身に対して行う。**

- **§4**: 投入後 5 サイクルのうち 3 ラウンド打ち切りが起きた回について、**打ち切り時点で未確定欄に残っていた `- [ ]` を 1 件ずつ §3 の分類へ当てる**。
  - 残っていたのが**判断の問い**（人の裁定待ち）だけなら **§4 は効いている**。機序 C の正常動作である
  - **実行時の問いが 1 件でも未確定欄に残っていたら §4 は効いていない**——申し送りへ移せていない。規範（落とせる条件）を強める前に、**§4 を戻して原因を取り直す**
  - 5 サイクルで打ち切りが 1 度も起きなければ、**§4 の効果は判定できない**（機序 C が働かなかっただけかもしれない）。判定を保留してサイクル数を延ばす
- **§5 spike**: 道具が出した候補のうち、スカウトが独自に挙げていなかったものが 0 件なら仮説は支持されない。**§5 の残りへ進まない**
- **「もう 1 サイクル様子を見る」で延命しない。** 判定を先送りできる条件は、判定していないのと同じである。**上の保留はこの禁の例外ではない**——「指標が発火しなかったので判定材料が無い」場合に限り、「発火したが解釈で守る」場合には使えない。両者を取り違えないよう、保留するときは**何が発火しなかったか**を書く

## §9 受容する残余

- **観測の一次情報は利用者の観察のみである。** §2 の機序は説明であって測定ではない。§8 のラウンド数記録が、事後にこれを接地させる唯一の観測点になる
- **絞り込みの精度は測っていない。** §6 で母集団が共通になれば測れるが、本設計は測定そのものを含まない
- **申し送り節への誤分類。** §4 の落とせる条件（確かめる手段が書けること）は規範であって機構ではない。潰せない項目が未確定欄から申し送りへ逃げる経路は残る。**逃げても PR 前ゲートが `- [ ]` を数えるため PR までには表面化する**が、ラウンドの打ち切りは回避できてしまう
- **申し送り項目の消し込みが「実施」だけで通ること。** §4 の三値（実施／該当なし）は `/implement` の報告規律に乗るが、根拠の妥当性を測る検出器は無い
- **収束判定 (i) の射程は、テストで固定できない。** `SKILL.md` の規範であり実行可能な述語を持たない。注記が上限である（§4・§8）。PR 前ゲート側だけがテストで固定される**片側だけの防御**であることを、残余として明示しておく
- **分類の CE を検算した既存の列挙は 1 つだけである。** §3 は未確定欄の 3 動詞に当てて裏取りの問いを見つけたが、当てた列挙はそれ 1 つ。**別の列挙（`.claude/rules/` の事前調査項目・`code-reviewer` の 3 フェーズなど）に当てれば、さらに欠落が出る可能性がある**
- **機序の列挙が CE である保証は無い。** §2 は 3 つを挙げたが、打ち切りの原因が他にもないことは示していない（配送不着・タスク自体の難度）。§8 の撤回条件は機序 A と C を弁別するが、**未知の機序 D は機序 A に見える**
- **精密化が後退になる形を意図して選んでいる。** `countUnchecked` に節を区別させる改良は、正しい方向の改良に見えて本設計を壊す（§4）。テストは赤で止めるが、**なぜ止まるのかはテスト名でしか伝わらない**——テスト名に理由を書く

## §10 やらないこと

- **`/implement` の巻き取りを止めない。** 発見は起きるものとして許容する（利用者判断・2026-07-29）
- **`/implement`「4a. check スキルの実行」の二度実行は畳まない。** 対象が計画と実装で別という理由は `docs/adr/ADR-plan-ownership-boundary.md` が持つ
- **ラウンド上限・台帳・収束判定を再設計しない**（§1）
- **本設計の段階でスキル本体を編集しない。** ルート `CLAUDE.md`「最重要ルール（常に適用）」がエージェント設定の変更に合意を求める
