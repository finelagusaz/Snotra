# /plan-review の計器分割 — 未確定の行き先と、有界な問いの道具化 設計（2026-07-29）

## §0 要旨

`/start-issue`「レビューのループ（上限 3 ラウンド）」は既に収束を保証している。本設計が扱うのは、そのループが**打ち切りへ落ちる二つの構造的な理由**である。

1. **未確定欄が「実装前に潰す」だけを行き先に持つ。** 実装しなければ精度が出ない問いは定義上そこで潰せず、ラウンドを消費して上限に当たる
2. **有界な問い（母集団がコードで決まるもの）を、道具ではなく読解者が数えている。** `plan:ledger` が機械化したのは配送であって、検証内容の母集団ではない

足す設計ではない。**問いを母集団で分け、それぞれ既にある計器へ配り直す。** 検収条件は `SKILL.md` が短くなることである（`docs/development-principles.md`「構造的設計原則と強制の階梯」）。

## §1 文脈 — 既に入っているもの（本設計の前提であって、対象ではない）

| 機構 | 所在 |
|---|---|
| ラウンド上限 3 + 収束判定（未確定ゼロ AND 計画が動かなかった）+ 打ち切りで人へ返す | `/start-issue`「レビューのループ（上限 3 ラウンド）」 |
| 台帳の母集団固定・双方向照合・exit 3 値 | `npm run plan:ledger`（`scripts/plan-review-ledger.mjs`） |
| 計画が持ち込んだ述語を実測する規律 | `AGENTS.md`「検証の作法（全タスク共通）」+ 未確定欄の「測る」 |
| 判断の問いを人へ返す経路 | 同ループの 3 ラウンド打ち切り |

**これらを再設計しない。** 本設計は、この上に残った穴だけを扱う。

## §2 観測と、それを説明する機序

**観測**（利用者・2026-07-29）: `/plan-review` が 3 ラウンドまで回っても調べ切れず、`/implement` が残りを巻き取っている。

**一次情報は利用者の観察のみである。** 過去のラウンド数はリポジトリから復元できない（`workspace/` は `/implement`「Step 5 — コミット」が毎サイクル削除し、`RETROSPECTIVE.md` は上書き）。以下は、その観察を説明しうる機序であって、測定ではない。

### 機序 A — 潰せない問いが欄に残り続ける

未確定欄の定義は「実装前に潰す」であり、`/start-issue`「Step 4 — 実装計画（workspace/plan.md）」は「**計画の完成とは、この欄が空になることである**」と定める。`/implement`「1c. 止まったときの引き渡し」1c-B は、未確定が残る計画での実装着手を禁じる。

ところが、**実装しなければ精度が出ない問いが存在する**。利用者の観察はこうである——「実装中だとテストしながら進めるからコードリーディングより精度は高い」。これは計器の性能差であって、努力で埋まるものではない。

この類の問いは、欄の定義上どのラウンドでも `- [x]` にできない。ゆえに収束条件 (i) が成立せず、**上限 3 まで回って打ち切りになる**。

同じ矛盾が、別の面にも現れている。`/implement`「4a. check スキルの実行」は「**計画に無い変更は実装中に必ず生じる**」と書く。これは「計画の完成 = 未確定ゼロ」と正面から衝突する。加えてこの文は前提条件も引用も持たない全称であり、`AGENTS.md`「検証の作法（全タスク共通）」の「全称表現は前提条件とセットで書く。書けないなら書かない」に自ら当たっている。**どちらかが誤りなのではなく、両方が同じ取り違えの表と裏である**——実装前に決まる問いと、実装しないと決まらない問いを、一つの尺度で測っている。

### 機序 B — 有界な問いを、有界性を使わずに解いている

`/plan-review`「Step 2 — 並列サブエージェントで検証」の検証観点は、呼び出し元 grep・対称ペア・リソースの生成/破棄・受け皿 issue の実在など、**母集団がコードから一意に決まるもの**を多く含む。にもかかわらず、各スカウトが自分で母集団を作って報告する形になっている。

`/plan-review` 自身が参照する `docs/development-principles.md`「列挙の完全性」は「列挙の SSOT はツール自身に問う」と定める。**有限の問いを、有限性を使わない方法で解いているから、ラウンドを重ねても残余が減らない。**

## §3 決定 — 問いを母集団で四つに分け、名前で呼ぶ

序数では呼ばない（`.claude/rules/governance-docs.md`）。

| 名前 | 母集団は何が決めるか | 計器 | 終了条件 |
|---|---|---|---|
| **有界な問い** | コード。ツールが全件を数え上げられる | 道具（grep 全件・`cargo build` の compile-fail・`governance:check`・専用スクリプト） | 全件が出力に載っている |
| **計画述語の問い** | 計画が持ち込んだ判定ロジック・fixture | plan-review の主エージェント（**委譲不可**） | 代表入力で実行した結果が `plan.md` にある |
| **実行時の問い** | ソースの外（API の実挙動・タイミング・状態到達） | `/implement` のテスト | plan-review は**測る対象を名指しして渡す**。判定しない |
| **判断の問い** | 人 | 人（Opus が候補を出す） | 決めた、または受容すると書いた |

**不変条件**: **有界な問いに残った残余は欠陥であって、受容する残余ではない。** 母集団が有限なら数え切れるはずであり、残ったのは数え損ねである。ADR の末尾が「受容する残余」で終わるのは正しい作法だが、そこに有界な問いの取りこぼしが紛れ込む余地を塞ぐ。

**上限が要るのは判断の問いだけである。** 有界な問いは有限だから終わり、計画述語の問いは測れば出る。実行時の問いは plan-review が判定しないので、そもそも回らない。

## §4 未確定欄に「実装で測る」を足す

未確定欄の項目に、現在の (a) 何が決まっていないか / (b) どう確定させるか に加えて、**行き先**を持たせる。

- **実装前に潰す**（現行のまま）— 測る・決める・裏取りする。`- [x]` にして結果を計画本文へ畳み込む
- **実装で測る** — 実行時の問いに限る。**plan.md に「何を・どう測れば決着するか」を書いて `- [x]` にし、`/implement` のテスト方針へ畳み込む**。潰したのではなく、精度の高い計器へ引き渡したという記録である

**収束条件 (i) はこの行き先を含めて成立する。** 実行時の問いが残っていることは、着手を止める理由にならない——止めても精度は上がらないからである。

**この行き先へ落とせる条件を絞る。** 「実装で測る」と書けるのは、**測る手段（テスト名・スモーク項目・確認手順）が plan.md に書けたときだけ**である。書けないなら実行時の問いではなく、まだ分解されていない判断の問いである。この一文が無いと、潰せない項目の逃げ道になる。

**`/implement`「4a. check スキルの実行」の「計画に無い変更は実装中に必ず生じる」は、この分類へ書き換える。** 根拠を持たない全称を、母集団を持つ記述に置き換える。

## §5 有界な問いを道具へ

`/plan-review`「Step 2 — 並列サブエージェントで検証」の検証観点を割り当てる。

| 観点 | 分類 | 置き換え先 |
|---|---|---|
| 変更する関数・型・イベント定数の呼び出し元 grep、plan.md に漏れた影響先 | 有界 | `git grep -n` 全件（出力を切らない・`docs/development-principles.md`「列挙の完全性」）+ `cargo build -p <下流>` の compile-fail。plan.md の変更ファイル一覧との差集合まで機械的 |
| 対称ペア（`show`/`hide` 等）の存在 | 有界 → 判断 | 候補列挙は命名規則の grep。「同様の変更が要るか」は判断として残る |
| plan.md 記載の不変条件がコードで成立するか | **実行時** | 名指しして `/implement` のテストへ渡す |
| 新規リソースに「失敗・異常終了時にどうなるか」が記述されているか | 有界 | plan.md の文書検査（新規導入物の列挙 × 記述の有無） |
| `false` に戻さない `AtomicBool` / `join()` 無き `spawn` / `kill(` 無き子プロセス | 有界 | `scripts/race-boundaries.mjs` と同型の正規表現母集団 |
| issue の要求に対する過不足（YAGNI・要求未達） | 判断 | Opus |
| 既存の類似パターンで済むものを新規実装していないか | 判断 | Opus（`/dry-check` の領域） |
| 「別 issue が拾う」の受け皿が実在するか | 有界 | 番号なしの送り先検出は正規表現で完全に機械的。番号ありは `gh issue view` |
| SPEC.md 更新要否の判断の妥当性 | 判断 | 妥当性は判断。§番号の実在は `governance:check` の G-spec-sections が既に持つ |
| smoke の前提（trace イベント名・hotkey）が壊れないか | 有界 | grep 有界 |
| 設定キーの 4 点セット | 有界 | `governance:check` の G-config-reachability が双方向照合を持つ（対象はコード。計画段階の 4 点揃いは追加が要る） |

**十一観点のうち六つが道具へ落ちる。** 一つは実行時へ、三つは判断として残り、一つは半分に割れる。

### 道具の出力仕様 — 先例から継ぐものと、継がないもの

`docs/adr/ADR-race-check-population-tooling.md`「帰結」が記録した先例に倣う。

- **継ぐ**: 0 件の種別も常に印字する。証拠が義務ではなく出力そのものになり、費用が結論に依存しなくなる（`docs/check-skill-skeleton-design.md`「必須 2 — 費用対称性」）。**同時に、対応する「打ったコマンドを添える」型の条項を削除する**
- **継ぐ**: 基準リビジョンを必須引数にし、省略は非ゼロ終了で拒む。規範ではなく引数の必須性で閉じる
- **継がない**: 同 ADR「受容する残余」の「候補から境界への写し方——落とした候補は報告に現れない」を、本設計では受容しない。母集団 4 件の規模では残余だったものが、十一観点 × 全レイヤーでは `.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」が挙げる形（正常時に一覧へ出ない対象は永遠に見えない）そのものになる。**落とした候補と理由を出力に含める**

## §6 席の変化

- **層別スカウト**: 列挙から**絞り込み**へ。道具が母集団を一つ出し、スカウトはその全件に対して採否と理由を返す。**母集団が共通になって初めて歩留まりが測れる**
- **独立導出**（`/plan-review`「Step 2b — 独立導出 + 差分（常に実施・盲点クラスの漏れ検出）」）: 道具に落ちない。「同概念・別名（accessor 経由・派生 signal・概念ラベル等の間接参照）を概念で分類せよ」は正規表現の外にある。**エージェントを列挙器として使う正しい用途であり、本設計は触らない**
- **主エージェント**: 変化なし（計画述語の測定と要対処の再照合は既に持つ）

## §7 依存と順序

1. **`plan.md` の機械可読性**（#761「検討: `/plan-review` に「文書としての plan.md」を検査するレンズを常設するか」）。呼び出し元の差集合も文書検査も、変更ファイル一覧を parse できることが前提
2. §4（未確定欄の行き先）— 文書だけの変更。道具に依存しない。**単独で先に入れられる**
3. §5（道具化）— 1 に依存

**§4 を先に入れる。** 機序 A は打ち切りの直接原因であり、費用が最も小さい。

## §8 検収条件

- **`SKILL.md` の行数・文字数が減ること。** 道具が吸収した条項を削除する（`docs/development-principles.md`「構造的設計原則と強制の階梯」の「構造が規則を吸収したらチェックリストを削除し、ドキュメントが軽くなることを設計改善の検収条件とする」）。前後の実測を ADR へ残す
- **`/norm-review` を回す。** 条項の削除を含むため `.claude/rules/safety-nets.md` が要求する。**対照は変更前の版そのものであって、対象条項だけを抜いた版ではない**（2026-07 サイクルで対照設計を誤り、効いている条項を削除候補にしかけた実測がある）
- **ラウンド数の前後比較。** ラウンド番号は `plan.md` の未確定欄見出しと `/plan-review`「Step 3 — 結果の統合と報告」の報告に載るため、PR に残る。§4 投入前後の数サイクルを ADR へ記録する（`workspace/` は削除されるので、削除されない面へ）

## §9 受容する残余

- **観測の一次情報は利用者の観察のみである。** §2 の機序は説明であって測定ではない。§8 のラウンド数記録が、事後にこれを接地させる唯一の観測点になる
- **絞り込みの精度は測っていない。** §6 で母集団が共通になれば測れるが、本設計は測定そのものを含まない
- **「実装で測る」への誤分類。** §4 の絞り込み条件（測る手段が書けること）は規範であって機構ではない。潰せない項目がここへ逃げる経路は残る

## §10 やらないこと

- **`/implement` の巻き取りを止めない。** 発見は起きるものとして許容する（利用者判断・2026-07-29）
- **`/implement`「4a. check スキルの実行」の二度実行は畳まない。** 対象が計画と実装で別という理由は `docs/adr/ADR-plan-ownership-boundary.md` が持つ
- **ラウンド上限・台帳・収束判定を再設計しない**（§1）
- **本設計の段階でスキル本体を編集しない。** ルート `CLAUDE.md`「最重要ルール（常に適用）」がエージェント設定の変更に合意を求める
