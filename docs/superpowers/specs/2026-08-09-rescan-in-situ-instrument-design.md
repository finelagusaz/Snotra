# 背景再スキャンの in-situ 計器（#1001 受け入れ 1）

> **2026-08-10 追記: この計器は撤去された。** 測る対象（毎起動の全走査）そのものを消したためである（`docs/adr/ADR-rescan-explicit-only.md`）。**§8.2 が却下した「記録ファイルを間引きの入力に兼ねさせる」案の理由は今も有効である**——計器を振る舞いを決める部品に変えてはならない。

**この反復は挙動を変えない。** 再スキャンの頻度・条件・結果は一切触らず、**何が起きたかを後から読める形で残す**ことだけを行う。間引き（#1001 の着地点）は別の反復である。

## 1. 何が観測できないのか（前提の裏取り）

2026-08-09 に実機を外部から観測して確かめた事実（#1001 の 2 つのコメントが一次記録）:

- 背景再スキャンは**キャッシュヒットの起動ごとに走り、1 コアを約 22 秒使い切って終わる**（CPU の伸びとスレッド消滅が同時刻を指す）
- `Changed` なら `index.bin` を書く（launch + 22 秒に実測）。`Unchanged` なら**何も残さない**
- **セッションが走査より短いと成果はまるごと消える**（12 秒 kill → 書かれない / 45 秒 → 書かれる。同一の変更で A/B した）

そして**製品はこのどれも記録しない**。`RescanOutcome` は呼び出し側がアイコン無効化に使うだけで捨てられ、trace の終端も無く、#1000 の起動計器はホットキー登録で止まる。ゆえに 2026-08-08→09 に `index.bin` が更新されなかった理由は、**記録が無い以上いまも確定できない**（短命セッションで再現はできたが、それは「そうなりうる」の証明であって「そうだった」の証明ではない）。

**この計器が埋めるのはその穴である。**

## 2. 設計

### 2.1 物体 — `%APPDATA%/Snotra/rescan-log.jsonl`

- 保存先は `Config::config_dir()` から派生させる（**保存先を導く経路はここ 1 つだけ**という既存の不変条件に乗る。`SNOTRA_CONFIG_DIR` も自動的に効く）
- 記録の中身を知っているのは `try_background_rescan_in`（走査・整列・digest・保存の全区間がそこに閉じている）ゆえ、**正本は `snotra-core`** に置く。`indexer.rs` は既に大きいので新モジュール **`snotra-core/src/rescan_log.rs`** に分ける

### 2.2 形式 — JSONL であって `binfmt` ではない

`index.bin` / `history.bin` / `window.bin` / `icons.bin` は「magic + u32 version ヘッダ」の共通保存仕様を持つが、**この物体はその仲間ではない**:

| | 既存の 4 ファイル | `rescan-log.jsonl` |
|---|---|---|
| 書き方 | 全書き換え（tmp → rename） | **追記** |
| 版 | ヘッダ + フォールバック鎖 | **要らない**（未知キーの読み飛ばしは JSON の性質） |
| 壊れたら | `.bak` 退避・データ損失の問題 | **1 行捨てれば済む** |
| 消えたら | 機能が失われる／再構築が要る | **何も起きない** |

**この物体は消しても壊れても書けなくてもアプリの振る舞いが 1 ミリも変わらない。** ゆえに `/persistence-check` の版バンプ・後方互換テストの重みは要らない。読み手は人間と harness である。

### 2.3 2 行 1 組 — 「完走しなかった」を観測可能にする中核

```jsonl
{"ev":"start","ts":"2026-08-09T13:32:01.412Z","sid":"19212-1786...","roots":4,"cached":312625,"cached_version":7}
{"ev":"end","ts":"2026-08-09T13:32:23.832Z","sid":"19212-1786...","outcome":"changed",
 "scan_ms":22013,"sort_ms":180,"digest_ms":14,"save_ms":210,"unattributed_ms":3,
 "total_ms":22420,"scanned":311697,"format_upgrade":false}
```

**`start` は走査の前に書く。** 終端だけを書く設計では、短命セッションが「そもそも起動しなかった」と区別できない——**start だけ在って end が無い行が「完走しなかった起動」である**。これが本設計の全部である。

- **ペアリングは `sid`（pid + 起動時刻ミリ秒）。** pid だけでは再利用で衝突する。2 プロセスの同時稼働は実在する（2026-08-09 に観測）
- **`end` は `Skipped` でも必ず書く。** しかも理由を **`lock`（本式ビルドと競合）と `generation`（世代が変わった）に分ける**——別の話である
- **`format_upgrade`** を持つ。`outcome=unchanged` なのに save が走る唯一の経路（旧版の書き戻し）であり、**現状どこからも見えない**

### 2.4 純粋核 — 時計を持たない

`RescanRecord`（区間を `Duration` で保持する値型）→ `to_json_line()` を純粋関数にし、時計と I/O は呼び出し側が持つ。**時計を持たないのは測るためである**——丸め境界のような fixture は注入でしか作れない（`startup.rs` の `Timeline` と同じ理由）。

## 3. `startup.rs`（#1000）から継承する流儀

この計器は #1000 が確立した規約をそのまま当てる。**同じ罠を二度踏まないため**である。

1. **区間は網羅列挙し、通らなかった区間は `null`**（`0` にしない）。`save_ms` は書かなかったとき `null` である——「0 ミリ秒で書いた」と「書かなかった」は別である
2. **`total_ms` は終端で 1 回読み、部分和から作らない。** 代わりに `unattributed_ms` を置き、**恒等式 `total = scan + sort + digest + save + unattributed` を全経路で成立させる**。残余を項目にせず「和が一致すること」だけを不変条件にすると、`Skipped` 経路で検算が必ず破れ、読み手は理由が読めなくなる（反復 6 が `digest_ms` を足してフェーズ間の隙間を塞いだのと同じ形）
3. **丸めは表示境界だけ。** 内部は `Duration`、JSON へ出すときにだけ ms へ切り捨てる
4. **best-effort。** 書き込み失敗は握り潰す。**計器のために製品を落とさない**（release は `panic = "abort"`）
5. **剪定は `start` を書くときに 1 回だけ。** 上限（200 行・約 40 KB）超過時に**末尾**を残して書き直す

## 4. 受容する残余

- **`Config::config_dir()` が取れない起動は 1 行も残らない**（書き先が導出できない）。この経路は `try_background_rescan` の早期 return であり、`_in` に入る前に消える
- **2 プロセスが同時に剪定すると行が失われうる。** 追記自体は Windows の `FILE_APPEND_DATA` で小さい書き込みなら競合しないが、剪定は読み→書き直しゆえ競合する。**使い捨ての物体ゆえ許容する**——失われて困るなら、それは §2.2 の「消えても何も起きない」が偽になったということであり、そのときは設計を見直す合図である
- **記録は「何が起きたか」であって「なぜ」ではない。** `Skipped` の 2 理由は分けるが、`Changed` の中身（何件増えて何件減ったか）は持たない

## 5. 検証

**変異で落ちることまで確かめる検知器**を置く:

| 検知器 | 落とす変異 |
|---|---|
| 未完走の起動が `start` だけを残す | `start` を書かず終端だけ書く実装 |
| 剪定が**最新を捨てない** | 末尾ではなく先頭 N 行を残す実装 |
| `save_ms` が `null` と `0` を区別する | 書かなかったときに 0 を入れる実装 |
| `skipped` の 2 理由が分かれる | 両方を単一の `"skipped"` へ潰す実装 |
| 恒等式が `Skipped` 経路でも閉じる | `total` を部分和から作る実装 |
| 壊れた行があっても剪定・追記が続く | 行の parse 失敗で早期 return する実装 |

**完了ゲート（実機）**: 新設した検証経路は、報告の前に**その経路自体を走らせる**。2026-08-09 と同じ手順で (a) 通常起動 → `end` 行が出る、(b) 12 秒で kill → **`start` だけが残る**、を実演する。

## 6. 計器の分担 — 器は 2 つで 1 組

受け入れ 1 は「壁時計・確保回数・peak」を求めるが、確保回数と peak は計数アロケータを要し、それは `tests/memory_footprint.rs` にしか無い。**製品へグローバルな計数アロケータを常設する案は採らない**——検索ホットパスを含む全確保に atomic の加算が乗る。#1000 が「注入点を製品コードへ足す案」を却下したのと同型である。

| 器 | 測るもの | いつ |
|---|---|---|
| `rescan-log.jsonl`（本反復で新設） | 背景再スキャン経路の `scan` / `sort` / `digest` / `save` 区間の壁時計・件数・結末・完走の有無 | **実運用のキャッシュヒットの起動ごと** |
| `tests/memory_footprint.rs` の `report_scan_all_cost` | `scan_all` 区間の確保回数・peak・重複検算 | 手元（`#[ignore]`） |
| `LoadOrScanStats`（既存） | ロード経路（`load_or_scan_with_stats`）の区間 | cache-hit / cache-miss 両枝（起動時） |

**`report_scan_all_cost` は広げなかった。** 当初案は `sort_entries_canonical` + `entries_digest` まで測る区間を広げる予定だったが、実装せずに終わった——広げるには `sort_entries_canonical`（`indexer.rs` の `pub(crate)`）・`entries_digest`（private）のどちらかの可視性を緩めるか、計測専用の入口を製品コードへ足す必要があり、これは #1000 が却下した「注入点を製品コードへ足す」案と同型になる。ゆえに `report_scan_all_cost` は `scan_all` だけを測る計器のまま残し、**`sort` / `digest` / `save` は `rescan-log.jsonl` に任せる**分担になった。

**`LoadOrScanStats` はロード経路の計器であり、背景再スキャン経路の代理にならない。** 枝ごとに片方しか埋まらない——cache-hit 枝は `sort_ms` / `scan_ms` / `cache_save_ms` が 0 で `digest_ms` だけが実数、cache-miss 枝はその逆で `digest_ms` が 0 になる（`indexer.rs` の該当分岐）。背景再スキャンの `sort` / `digest` / `save` を読みたいときは `rescan-log.jsonl` を見る。

## 8. 却下した案

### 8.1 `SNOTRA_TRACE` の trace イベントだけにする

`startup.rs` と同じ流儀で stderr へ JSON 行を出す案。実装も検査も既存の型に完全に乗り、製品へ常設の物体を一切足さない。

**却下の理由**: GUI アプリの stderr は普段の起動では誰も見ない。**「実運用の起動で何が起きたか」は今後も分からないままで、2026-08-08→09 と同型の穴がそのまま残る**——それこそがこの反復の存在理由である。

### 8.2 記録ファイルを間引きの入力に兼ねさせる

「前回いつ完走したか」を同じファイルから読み、後の反復の間引きがそれを使う案。物体が 1 つで済む。

**却下の理由**: 計器が**振る舞いを決める部品**に変わる。欠損・破損・剥がれの扱いを全部決めねばならず、誤ると**「永遠に間引かれて再スキャンが一度も走らない」が沈黙で起きる**。resource と policy を分ける既存の選好に反する。間引きの状態は別の反復で別の物体として設計する（`index.bin` の `built_at` を使う選択肢もある）。
