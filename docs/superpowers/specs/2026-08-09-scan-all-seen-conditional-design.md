# `scan_all` の `seen` を根の重なりに条件づける（#1002）

作成日: 2026-08-09 / ブランチ: `perf/scan-all-seen-conditional` / 前提: `PERFORMANCE.md`「採用: PATH スキャンの問いを反転（反復 9）」（同型の先例）

`indexer::scan_all` は重複排除のため `seen: HashSet<String>` を持ち、走査した全ヒットの
正規化キー（`normalize_entry_key` = 1 件ごとに `String` を確保）を積む。実運用点では
311,695 件（実測）。**この `seen` が代金に見合うのは走査の根どうしが重なりうるときだけ**である。

> **訂正（2026-08-09・実測）。** 初稿は「実運用点は根が `C:\` 一本」を前提に書かれていた
> （#1002 本文も同じ）。**これは偽である。** 実 `config.toml` を読むと `paths.scan` は 4 根で、
> `C:\` は他 3 根（Start Menu / Desktop / Dropbox）の祖先である。ゆえに素朴な
> 「重なるなら建てる」判定では `seen` が建ち、**削減は 0 になる**（実測: allocs
> 5,991,749 → 5,991,979・peak 121.73 MiB で変化なし）。§2.2 はこの実測を受けて書き直した。
>
> **反証されたのは前提の測り方である。** #1002 のコメントは `dedup_scan_paths` を grep して
> 「入れ子の根は表現可能」＝ `seen` が**必要になりうる**ことを確かめたが、**実運用点で実際に
> 必要かは誰も測っていなかった**。config の**仕組み**を確かめたことが、config の**中身**を
> 確かめた気にさせている（`docs/development-principles.md`「config の値は到達性の検出器を
> 持たない」と同じ型）。

## 1. `seen` が捕まえるものは何か（前提の裏取り）

**木の走査は同じディレクトリを二度読まない。** ゆえに 1 回の `scan_all` の中で同じ正規化キー
が二度現れる経路は、**根が入れ子になっているとき以外に無い**（#1002 のコメントが `config.rs`
の grep で裁定済み）。

- `dedup_scan_paths` は**完全一致キーの重複排除であって接頭辞の畳み込みではない**。
  大文字小文字・区切り・末尾 `\` は同一視するが（`dedup_scan_paths_merges_case_variants` /
  `dedup_scan_paths_trailing_backslash_merge`）、`C:\` と `C:\Tools` は両方とも残る。
  **入れ子の根は表現可能であり、`seen` を素で消す案は成立しない**
- junction / reparse point で別名になった経路は**文字列が異なるので `seen` は元から捕まえない**。
  この変更で失われるものは無い

ゆえに本設計の形は「消す」ではなく「**根の集合に対して重なりを事前判定し、重ならないときは
建てない**」である。判定は根の数（一桁）に対する走査なので、額に影響しない。

## 2. 設計

### 2.1 述語 — `normalize_scan_path_key` を借り、dedup には依存しない

```rust
/// 2 つの正規化済み根について、a が b の祖先か同一か。
fn is_ancestor_or_same(a: &str, b: &str) -> bool

/// 走査の根どうしが重なるか。重なるときだけ `scan_all` は `seen` を建てる。
fn roots_overlap(scan_paths: &[ScanPath]) -> bool   // 全ペア O(n²)・根は一桁ゆえ無料
```

**境界の 2 枝を 1 本にまとめてはならない。** `normalize_scan_path_key` はドライブ根だけ末尾
`\` を残す非対称を持つ（`c:\` / `c:\tools`・`normalize_scan_path_key_preserves_drive_root`）。

- `a` が末尾 `\` で終わる（＝ドライブ根）なら `b.starts_with(a)` だけで正しい
- そうでなければ `b` の `a.len()` バイト目が `\` であることまで見る

前者に境界チェックを課すと `c:\\tools` を探して偽になり、後者から外すと `c:\tools` が
`c:\toolsextra` を入れ子だと誤判定する。

**完全一致も重なりとして拾う。** 通常の起動経路は `apply_migrations` → `normalize_scan_paths`
を通るので同一キーの根は残らないが、`scan_all` は dedup を通さない配列も受け取る
（`src-tauri/src/icon.rs` の `icon_pipeline_cost_probe` が `Config::default_scan_paths()` を
直接渡す）。**述語を config 側の dedup の性質に依存させない**ことで、呼び出し点ごとの前提
確認が要らなくなる。

### 2.2 判定の粒度 — 根ごとに「照合するか」と「積むか」を分ける

**`scan_all` 単位で建てる／建てないを決める形（初稿の案）では、実運用点の削減が 0 になる**
（§1 の訂正）。4 根すべてが `C:\` と入れ子なので判定が真になり、`seen` が建つ。
**「入れ子に関与する根だけ積む」案も同じ理由で 0 である**——4 根すべてが関与する。

額が出る形は 1 つで、**重複が起きる向きに着目する**。根 `i` の走査で入ったエントリが再び
現れるのは、**後続の**根 `j > i` が根 `i` と重なるときだけである。ゆえに根ごとに 2 つの
述語を持つ:

| 述語 | 定義 | 意味 |
|---|---|---|
| `check[i]` | `∃ h < i : overlap(h, i)` | 先行の根と重なる → **既出かを照合する** |
| `record[i]` | `∃ j > i : overlap(i, j)` | 後続の根と重なる → **自分のキーを積む** |

実運用点（`[StartMenu, Desktop, Dropbox, C:\]` の順）ではこうなる:

| 根 | `check` | `record` | 動作 | 件数 |
|---|:-:|:-:|---|---:|
| Start Menu | ✗ | ✓ | `insert` | 小 |
| Desktop | ✗ | ✓ | `insert` | 小 |
| Dropbox | ✗ | ✓ | `insert` | 小 |
| `C:\` | ✓ | ✗ | **照合のみ・積まない** | **311,695** |

**最大の根が最後に来るとき、その根のキー確保がまるごと消える。** これは反復 9 の
「候補側に小さい索引を作り、既存側は篩で素通しする」とまったく同じ形である。

**照合側も確保を持たない。** `normalize_entry_key_into` でスレッド内の 1 本のバッファへ
詰め直し、`HashSet<String>` を `&str` で引く（`Borrow<str>`）。**記録側と照合側が同じ関数を
通ることがバイト一致の根拠である**——別実装を書き起こしてはならない（`snotra-core/CLAUDE.md`
「`normalize_entry_key` の冪等性契約」）。

**額は根の順序に依存する。** `C:\` が先頭なら `record` が真になり積む側へ回る。**これは
判定の欠陥ではない**——順序に対して述語は正しく、額だけが構成に依存する。**順序を並べ替えて
額を取りに行ってはならない**: 返り値の順序が変わり、`entries_digest` がずれて毎起動
`index.bin` を書き直す（`sorted_comparison_ignores_enumeration_order` が守る不変条件）。

**拡張子集合の交差・`include_folders` の両立までは見ない**（過剰近似）。額は増えないのに
判定の面積だけが広がり、判定自体がバグりうる。

### 2.3 表現 — 状態を 1 つの型へ束ね、根ごとの役割を差し替える

`scan_directory_with_extensions` の引数は `&mut Dedup` の 1 つに保つ。集合・バッファ・
根の役割を別々の引数で並べると、再帰の呼び出し点で組を崩せてしまう。

```rust
struct Dedup {
    /// 重なる根が 1 つも無ければ `None`（この走査は重複排除を必要としない）。
    set: Option<std::collections::HashSet<String>>,
    /// 照合だけの根で使い回す正規化キーのバッファ。確保を走査あたり 1 回に抑える。
    buf: String,
    /// いま走査している根の役割。`scan_all` のループが根ごとに差し替える。
    role: RootRole,
}

#[derive(Clone, Copy)]
struct RootRole { check: bool, record: bool }
```

採否は 1 つのメソッドに閉じる:

```rust
impl Dedup {
    fn accept(&mut self, path: &str) -> bool {
        let Some(set) = self.set.as_mut() else { return true };
        match (self.role.check, self.role.record) {
            // 積む根は insert が照合を兼ねる（既出なら false が返る）。
            (_, true) => set.insert(normalize_entry_key(path)),
            // 照合だけの根。**ここが確保を持たないことが本設計の全部である。**
            (true, false) => {
                normalize_entry_key_into(&mut self.buf, path);
                !set.contains(self.buf.as_str())
            }
            // どちらでもない根は集合に触れない。
            (false, false) => true,
        }
    }
}
```

**`Option<&mut HashSet<String>>` を採らない。** 再帰へ渡すときに move されるため
`as_deref_mut()` が要るが、`HashSet` は `Deref` を実装していないので通らない。
`&mut Dedup` なら `&mut *dedup` を渡すだけで済む。

**呼び出しは `!name.is_empty() &&` の後ろに置く**（現行の短絡評価を保つ。名前が空の
エントリのキーを集合へ入れない）。

**ホットループの短絡を保つ。** 現行は `if !name.is_empty() && seen.insert(key)` の同一式で
判定と採用を繋いでいる（`scan_path_dirs_rejects_only_the_matching_candidate_among_several`
のコメントが「ずれることが原理的に起きない」形として記録している）。この構造を壊さず、
`seen` が `None` なら `normalize_entry_key` を**一度も呼ばずに** `true` を返す形にする。

## 3. 額の性質 — 反復 9 と同型だが現れ方が違う

**反復 9 の見出し（壁時計 -71%）と同じ形にはならない。**

| | 反復 9（PATH スキャン） | 本件（`scan_all`） |
|---|---:|---:|
| 区間全体の壁時計 | 186 ms | **数万 ms**（実走査そのもの。キャッシュの温度で倍近くぶれる——実測 65,416 / 23,833 ms） |
| 区間の確保回数 | 314,395 | **5,991,749**（実測。うち `seen` の `String` は 311,695 ＝ **約 5%**） |
| 区間 peak | 48.10 → 0.03 MiB | 121.73 MiB（実測）から `HashSet<String>` のぶんが落ちる |

**確保回数の比率では反復 9 のようにならない。** 走査そのものが `DirEntry` / `PathBuf` /
`Metadata` を大量に確保しており、`seen` はその 5% である（**`index.bin` のロードは同規模の
エントリに対し 411,613 確保**——ディスクから読む方が、ファイルシステムを歩くより 14.6 倍
安い）。**額として効くのは peak の側**であり、`PERFORMANCE.md` の見出しはどちらで書くかを
実測を見て決める。

`scan_all` は背景再スキャンで低優先度スレッドから走るため**壁時計は元から問題ではない**。
削るべきは瞬間の常駐であり、**受け入れ判定を確保回数に置く #1002 の規約はそのまま正しい**。
`PERFORMANCE.md` へ書くときも**見出しに壁時計を載せない**（反復 9 の規約）。

## 4. 検証

| 対象 | 形 |
|---|---|
| 述語の境界 | `c:\` ⊃ `c:\tools` 真 / `c:\tools` vs `c:\toolsextra` **偽** / 逆順 / 完全一致 真 / 別ドライブ 偽 |
| 入れ子の根で重複が出ない | 実ディレクトリ 2 根（`X` と `X\sub`）を走査し、正規化キーが一意であること |
| **変異注入** | `roots_overlap` を常に `false` へ潰し、上のテストが**落ちることを実測する**（反復 8 で 3 本中 1 本が落ちなかった教訓） |
| 非重なりで `seen` を建てない | `roots_overlap` の直接テスト。**これが無いと削減そのものの退行が静かに通る** |
| 実データの不変 | 新実装（実 config・`seen` = `None`）の返り値について、**正規化キーの重複が 0 件**であること |

**「A/B で `entries_digest` が一致すること」を受け入れゲートにしてはならない。** 対象は
生きた `C:\` 全体であり、A（実装前）と B（実装後）は別プロセス・別時刻の走査になる。その間に
temp ファイル・ログ・キャッシュの churn が必ず挟まる（`PERFORMANCE.md` が `scan_ms` 35,573 対
22,187 ms のぶれを記録しているとおり、この対象は凍結できない）。**digest 不一致はほぼ確実に
出るが、原因はコード変更ではなく churn である**——それを受け入れ条件に据えると、偽の理由で
§6 の分岐に入る。

**代わりに走査 1 回の中で閉じる検算を使う。** 新実装の返り値に対し正規化キーの重複件数を
数え、0 であることを確かめる。旧実装は同じ列挙に対し「既出キーを落とす」だけなので、
**重複が 0 なら旧実装は何も落としておらず、件数も順序も一致することが論理的に閉じる**。
churn は無関係になる（1 回の実走査についての反実仮想だから）。

順序まで見るのは、ずれると背景再スキャンが「変わった」と誤判定して毎起動 `index.bin` を
書き直す静かな劣化になるためである（`sorted_comparison_ignores_enumeration_order` が守って
いる不変条件と同じ軸）。上の検算はその順序も同時に閉じる。

**確保回数の A/B も件数の変動を伴う。** 同じ churn がエントリ数を動かすので、削減額は
エントリ件数と併記し、**削減が件数変動のオーダーを大きく超えること**で判定する
（30 万オーダーの削減に対し件数のぶれは数十〜数百件の桁）。

## 5. 計器 — `tests/memory_footprint.rs` Phase A

**A 側標本は実装前にしか取れない。** 現在この区間を測る計器は無い（Phase A はキャッシュ
ヒット経路ゆえ `scan_ms` が 0 で、`rescan_task` は `drop` される）。

PATH スキャンと同じ「**常駐外・返り値は捨てる**」形で `scan_all` 区間を足し、
`live / peak / blocks / allocs` と**エントリ件数・正規化キーの重複件数**を出す。

**`entries_digest` は出さない。** 受け入れゲートに使えない（§4——A/B の digest は churn で
必ずぶれる）うえ、`indexer.rs` の private 関数ゆえ統合テストのクレートからは呼べない。
ゲートに使うのは重複件数 0 の方である。

- **置き場は Phase A の末尾**（既存区間の後ろ）。rayon のグローバルスレッドプールの初回
  起動コストを新区間が被らないようにする（`memory_footprint.rs` の `//!` が記す罠）
- `//!` に「この区間は実走査そのものゆえ Phase A の実行時間が大きく伸びる」を明記する。
  **秒数を書かない**——ファイルシステムのキャッシュの温度で倍近くぶれ（実測 65,416 /
  23,833 ms）、書けば測り直すたびに腐る。初稿はここに「+20〜35 秒」と書き、実測がそれを
  反証した（同じ記述が計器の doc と計画にもあり、**写しが 2 つできていた**）
- **返り値は entries へ混ぜない**（PATH スキャンと同じ理由——実行ごとにぶれ、常駐がバイト
  単位で再現しなくなる）

## 6. 受容する残余 — case-sensitive ディレクトリ

**「重なりが無ければ `seen` は何も捕まえない」には反例が 1 つある。** NTFS の
case-sensitive ディレクトリ（`fsutil` / WSL 由来）では `Foo.exe` と `foo.exe` が同居でき、
`normalize_entry_key` は小文字化するので**単一根の 1 回の走査内でも同一キーが二度現れうる**。
現行はこれを 1 件に潰すが、変更後は 2 件返る。

**§2.2 の改訂でこの残余は広がった。** 初稿の案は「重なる構成では現行と 1 バイトも変わらない」
——差が出るのは `seen` を建てない構成だけだった。改訂後は `record` が偽の根（実運用点では
`C:\`）が**自分のキーを積まない**ため、**その根の中の case 重複も弾かなくなる**。つまり
差の出る場所が「集合を建てない走査」から「積まない根」へ広がっている。

**帰結は変わらない**（どちらも case-sensitive 同居があるときだけ 2 件返る）が、**論証は
弱くなった**——「重なる構成では不変」という構造的な保証を失い、実測に依存する。実運用点の
実測は **0 件**であり、§4 の検算をこの形の実装に対して取り直すことがゲートである。

**扱い: 重複件数が非 0 だったら、どのパスが重複したかを提示して止まる。** 事前に受容とも
取り下げとも決めない——起こらない分岐の判断を先回りしない。

**この形なら、非 0 の原因は本当に case-sensitive 同居だけに絞れる**（走査 1 回の中で閉じる
検算なので churn が混ざらない）。実測が 0 なら受け入れ条件「エントリ列が不変」は実データで
満たされ、この節は「測って 0 だった」の記録になる。非 0 なら仕様変更として扱い直す
（`SPEC.md` 同期の要否がそこで再判定になる）。

## 8. 却下した案

| 案 | 却下の根拠 |
|---|---|
| `seen` を素で消す | `dedup_scan_paths` が完全一致マージのみゆえ、入れ子の根は表現可能。**構造的に到達不能ではない** |
| **`scan_all` 単位で建てる／建てない**（初稿の採用案） | **実測で却下。** 実 config は 4 根で `C:\` が他 3 根の祖先ゆえ判定が真になり、削減が 0（allocs 5,991,749 → 5,991,979・peak 変化なし）。**判定は正しく、前提が偽だった** |
| **入れ子に関与する根だけ `seen` へ積む** | 同じ理由で却下。4 根すべてが `C:\` と入れ子なので全部が関与し、やはり 0 |
| 拡張子交差・`include_folders` まで見る | 額が増えないのに判定の面積が広がる（§2.2） |
| 根を並べ替えて最大の根を最後へ回す | 返り値の順序が変わり `entries_digest` がずれる。毎起動 `index.bin` を書き直す静かな劣化（§2.2） |
| 測定用に config を単一根へ書き換えて A/B を取る | 実運用点の実態を測らずシナリオを再現するだけになる。**測るべきは実運用点である** |
| 一時的な足場で A/B を取り撤去 | 「エントリ数に比例する仕事がこの区間へ戻る退行」を捕まえる計器が残らない。PATH スキャンの計器を反復 9 の後も残した判断と同じ（§5） |
