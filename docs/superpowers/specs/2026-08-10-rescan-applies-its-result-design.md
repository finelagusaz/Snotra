# 背景再スキャンの結果を、走っているセッションへ適用する

**代金を払うセッションと、恩恵を受けるセッションが別だった。** 背景再スキャンは `index.bin` を更新するが、走っているプロセスのメモリ上の索引は最後まで差し替わらない。この反復はそこを繋ぐ。**走査の回数は増やさない。**

## 1. 何が起きていないのか（前提の裏取り）

2026-08-09〜10 にコードで確かめた事実:

- `RescanOutcome` を見ている箇所は `src-tauri` 全体で 1 か所だけで、`Changed` のときに**アイコンキャッシュを無効化するだけ**である（`main.rs` の `setup_background_rescan`）
- 索引を差し替える機構（`Engine::apply_prebuilt_index` / `complete_index_drain`）は在るが、それを呼ぶのは `indexing.rs` の drain ループだけで、その起動点は 5 つ——手動再構築・first-run・config 変更・finish 後の再 kick・監視スレッドの first-run 補完。**背景再スキャンからは 1 本も繋がっていない**
- 帰結: **索引は常に 1 起動ぶん遅れる。** セッション N は N−1 の再スキャンが書いた `index.bin` で検索し、N の再スキャンは N+1 のために書く。新しく入れたアプリは、再起動するまで見つからない

そして `indexer.rs` の `try_background_rescan_in` には**事実でない記述**がある——「建てるのは呼び出し側（`Changed` を見た `src-tauri` が再構築を kick する）」。kick は存在しない。**意図が書かれ、実装が追いついていない。**

なお `SPEC.md` §3.3 は「差分があればキャッシュを更新」としか言っておらず、ライブの索引の差し替えを約束していない。**SPEC とコードは一致しており、乖離しているのはこのコメント 1 つである。** 本反復は挙動を変えるので §3.3 を同期する。

## 2. 設計

### 2.1 走査は 1 回のまま — 捨てている材料を運ぶ

**`start_index_build` を呼んではならない。** その drain ループは `indexer::rebuild_and_save` を呼び、それは `scan_all` を**もう一度**走らせる。素直に繋ぐと全走査が 2 回・`index.bin` の書き込みが 2 回になり、#1001 が問題にしている代金が倍になる。

材料は既に手元にある。`try_background_rescan_in` は保存の戻り値を捨てている:

```rust
drop(save_cache_sorted_in(dir, scanned, config_hash));
```

`save_cache_sorted`（権威的経路が使う版）は同じ `save_cache_sorted_in` の戻り値を `IndexMaterial::derived(tree, masks)` へ包んで返している。**再スキャンも同じ形にするだけでよい**——新しい走査も新しい確保も要らない。

### 2.2 運ぶ形

`BackgroundRescanTask::run()` の返りを、結末と材料の組にする。

- 材料を載せるのは **`Changed` のときだけ**である。形式の昇格だけ（`format_upgrade`）のときは中身が同一なので、差し替えても得るものが無い
- `RescanOutcome` 自身に材料を持たせない（`Copy` と `PartialEq` を失い、既存の検知器が一斉に書き換えになる）。**組を運ぶ新しい型を足す**

### 2.3 適用側は `src-tauri`、ただし **drain と同じ 1 つの関数を通す**

材料から `PrebuiltIndex` を建てる手順は、**PATH エントリのマージを含む**:

```rust
if inputs.include_path_env {
    let path_entries = indexer::scan_path_env(material.tree(), inputs.show_hidden_system);
    material.extend_with_path_entries(path_entries);
}
PrebuiltIndex::from_material(material, inputs.migemo_enabled)
```

**この手順を再スキャン側へ書き写してはならない。** 写せば「片方だけ PATH マージを忘れる」が沈黙で起きる——PATH のコマンドが検索から消え、検索結果は出るので気づく手段が無い。`indexing.rs` の drain ループと再スキャンの適用が**同じ 1 つの関数を通ることが、両者が一致することの根拠**である（`normalize_entry_key_into` と同じ理屈）。

### 2.4 差し替えの安全性 — 台帳を claim せず、stale なら譲る

- 差し替えは **`apply_prebuilt_index`** を使う。これは `search_engine` を差し替えるだけで `index_stale` 台帳に触らない。**`complete_index_drain` を使ってはならない**——あれは「このビルドが現在の `IndexInputs` を満たした」と台帳へ宣言する操作であり、再スキャンはその資格を持たない（走査したのは起動時の config である）
- 差し替えの直前に `is_index_stale()` を読み、**真なら差し替えない**。config が変わって本式ビルドが動いている（あるいはこれから動く）ということなので、そちらに譲る
- 重い構築（`PrebuiltIndex::from_material`）は**ロックの外**で行う。ロック内に入れてよいのは `apply_prebuilt_index` の一瞬だけである

### 2.5 通知は出さない

`indexing-started` / `indexing-complete` を出さない。ユーザーは待っておらず、既存の索引で普通に検索できている。出すと**変更のあった起動のたびに** UI が「インデックス構築中」になり、トレイの設定・終了がグレーアウトする。

## 3. 受容する残余

- **索引 1 本ぶんの一時常駐が背景スレッドに乗る。** 差し替えまでの間だけである。`indexer.rs` のコメントが警告していた当のものだが、**「その場で新しい索引を得る」ことの代金として受容する**——捨てれば代金は消えるが、得るものも消える
- **config 変更の窓は閉じた。** 2 回目のロックで `IndexInputs::from_config(engine.config())` の同一性まで snapshot と照合し、比較と `apply_prebuilt_index` は同じロック内で行う——検査後に config が割り込む余地は無い。**照合するのは入力の同一性であって索引の新しさではない。** ゆえに「同一 inputs のまま、本式ビルド（手動再構築。config 経由の kick は inputs 不一致で弾かれる）が 1 回目の検査より前に完走していた」場合は 1 回目・2 回目とも通過し、**より新しい索引を、同じ入力で建てた古い索引が上書きする**並びが残る。**受容する**——到達には「起動窓の中で手動再構築が再スキャンより先に走り終える」ことが要り、そのとき両者の走査は同じ起動窓の中で並走しているので、失うのは高々 1 走査ぶんの新しさである。config も台帳も正しいまま保たれる（台帳が主張するのは「現在の `IndexInputs` を反映」であって「ファイルシステムの最新」ではない）。世代番号の機構はこの残余に対して重すぎるため建てない。**lock で囲まない**のは重い構築（`build_index_from_material`）だけである（原則として重い構築をロックで囲まない）
- **稼働中に起きた変更は依然として見えない。** 再スキャンは起動時に 1 回きりであり、watch はこの反復の対象外である

## 4. 検証

**変異で落ちることまで確かめる検知器**を置く:

| 検知器 | 落とす変異 |
|---|---|
| `Changed` のとき材料が返る | 材料を捨てる実装（現状への回帰） |
| `Unchanged` / 形式の昇格だけのときは材料を返さない | 常に材料を返す実装（無駄な差し替え） |
| `Skipped` のときは材料を返さない | 同上 |
| 材料から建てた索引が PATH エントリを含む | 適用側が PATH マージを飛ばす実装 |
| 走査が 1 回だけであること | `start_index_build` を呼ぶ実装（全走査 2 回への回帰） |

最後の 1 つは**時間ではなく回数で測る**——「速いこと」は環境で揺れるが、「`scan_all` が何回呼ばれたか」は揺れない。

**完了ゲート（実機）**: 起動 → 索引に無いファイルを作る → 再スキャンの完走を待つ → **再起動せずに**検索して出ることを確かめる。新設した検証経路は報告の前にその経路自体を走らせる。

## 5. 文書更新

- **`SPEC.md` §3.3 を同期する**（これは仕様変更である）: 差分があればキャッシュを更新するだけでなく、**実行中のセッションの索引も差し替える**ことを書く
- **`indexer.rs` の事実でないコメントを直す。** 「`src-tauri` が再構築を kick する」ではなく、実際に起きること（材料を返し、呼び出し側が索引を建てて差し替える）を書く
- `snotra-core/CLAUDE.md`「indexer.rs の背景再スキャン」と `src-tauri/CLAUDE.md` の該当箇所を、返り値の形の変更に合わせる

## 6. 却下した案

### 6.1 `Changed` から `start_index_build` を呼ぶ

最初に検討した形。実装量は最小（1 行）だが、drain ループが `rebuild_and_save` を呼ぶため**全走査が 2 回**になる。#1001 の当の代金を倍にする案であり、却下する。

### 6.2 適用の手順を再スキャン側へ書き写す

`indexing.rs` の drain と同じ 3 行（PATH マージ + `from_material`）を再スキャン側にも書く案。短いので写したくなるが、**片方だけ PATH マージを忘れる欠陥が沈黙で起きる**（検索結果は出るので気づけない）。共有の 1 関数を通す。

### 6.3 `complete_index_drain` で差し替える

台帳の re-diff まで含めて「正規のビルド」として扱う案。再スキャンが走査したのは**起動時の** config であり、現在の `IndexInputs` を満たしたと宣言する資格が無い。宣言すれば、config 変更で立った stale を**誤って落とす**——本来走るべき再構築が走らなくなる。

### 6.4 `indexing-started` / `complete` を出す

UI に進捗を見せる案。ユーザーは待っておらず、出すと変更のあった起動のたびにトレイが操作不能になる。**この差し替えは「気づかれないこと」が正しい振る舞い**である。
