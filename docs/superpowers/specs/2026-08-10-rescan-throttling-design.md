# 背景再スキャンの間引き設計（#1001 受け入れ 3・4）

キャッシュヒットの起動が毎回 `C:\` を全走査している状態を、「**前回の完走から一定期間が空いた起動だけ走る**」へ変える。#1001 が「順序としては間引きが先、watch が後」と書いた前半にあたり、watch 枝の設計には依存しない。

この反復で変えるのは**頻度と、その頻度を決める状態の置き場所**だけである。走査そのもの（`scan_all`）・比較（`entries_digest`）・結果の適用（PR #1017）には触れない。

## 1. 何を根拠にこう決めたか

### 1.1 実測（`rescan-log.jsonl`・2026-08-10・実起動 2 標本）

| sid | scan_ms | total_ms | outcome | cached → scanned |
|---|---|---|---|---|
| 5936 | 29,547 | 30,127 | changed | 311,939 → 312,017（+78） |
| 17432 | 22,717 | 23,625 | changed | 312,017 → 312,018（**+1**） |

読めること:

- **`Changed` が 2/2**。しかも 2 本目の差分は 31 万件中 **1 件**である。その 1 件のために 22.7 秒走り、`Changed` ゆえ**アイコンキャッシュを毎起動捨てている**。間引きの支持証拠としてはこれが最も強い
- **`Skipped` は 0 件**（`skip_reason` は 2 行とも `null`）
- **「走査より短いセッションの割合」はこの標本では答えられない**。2 標本しかなく、両方とも `start`/`end` が揃っている。#1013 の Gotcha が記録するとおり、dir 注入へ直す前の行はすべてテスト由来だったため、実起動由来の記録は 2026-08-10 ぶんしかない。**「完走しない起動が実在する」の根拠は #1001 の一次観測（12 秒セッション < 22 秒走査）側にあり、このログではない**

### 1.2 参照実装（Everything・voidtools 公式ドキュメント）

Everything は索引を二本立てで持つ。

- **NTFS index**: MFT を直読みして初期索引を建て、以後は USN change journal で監視する。全走査という概念が無い。**管理者権限を要する**（公式 FAQ: "Everything requires administrative privileges for low level read access to NTFS volumes for NTFS indexing"）
- **Folder Index**（ネットワークドライブ・FAT/FAT32 等）: 監視は "the same approach as the Windows search"、そのうえで**予定された再スキャン**を持つ。設定できるのは「毎日 hh:mm」「週の特定曜日の hh:mm」「N 時間ごと・N 分ごと」「Never」、加えて **Rescan on full buffer**

Snotra が居るのは **Folder Index の側**である。#1001 の実測どおり USN ジャーナルの読みは非昇格で通るが `ENUM_USN_DATA` は拒否される——Everything が管理者権限で買っているのはまさにその半分であり、それが無いとカーソルを失ったときに数秒で建て直せない（保持窓は実測 6.1 時間で、日常的に失う）。

**結論として言えるのは 2 つだけである。**

1. 権限を買えない経路には、参照実装ですら「watch ＋ 予定された全走査」を置いている。#1001 の着地点は参照実装と同じ形である
2. 選べる粒度の語彙は日次・週次・時間・分・Never である

**公式ドキュメントに Folder Index の既定間隔は書かれていない。** ゆえに「Everything の既定が N だから」という論法は使えない。使えるのは粒度の語彙と構造だけである。

### 1.3 決定

- **間引きの軸**: 起動起点（「前回の完走から N 経過していれば走る」）。壁時計スケジュールは採らない（タイマーとスレッドが増え、かつ「その時刻に PC が落ちていたら」を別途決める必要があり、結局「前回完走からの経過」の状態が要る）
- **N = 7 日・ハードコード定数**。config キーにはしない（新規記録・既存移行・外部参照 API・設定 UI が同時に要り、スコープが 1 反復ぶん増える。求められたときに別反復で足せる）
- **状態の置き場所**: `index.bin` の `built_at`（→ §3）

## 2. 判定

述語を副作用から切り離し、`now` を注入する純関数にする。

```rust
/// 前回の完走から `interval` 以上経ったか。
///
/// **`built_at` が未来（時計の巻き戻し・別マシンからの設定フォルダ持ち込み）なら
/// 「期限切れ」側へ倒す。** 巻き戻した時計で永久に間引かれるより、1 回余分に走る方が安い。
/// `checked_sub` ゆえ u64 の wrap も起きない。
fn full_scan_interval_elapsed(built_at: u64, now: u64, interval: u64) -> bool {
    now.checked_sub(built_at).is_none_or(|age| age >= interval)
}
```

判定点は `try_background_rescan_in` の中、**書き込みロック取得の前**に置く。

```rust
let due = cached_version != INDEX_CACHE_VERSION
    || full_scan_interval_elapsed(built_at, now, FULL_SCAN_INTERVAL_SECS);
```

**旧版のバイパスが `||` の左に居ることが要点である。** これを欠くと、2026-08-07 に実運用点で実測した「v4 が残り、毎起動 `normalized_keys` 35.98 MiB を読んでは捨てていた」が「7 日間だけ」再発する。形式の昇格はこの経路にしか置けない（`sort_entries_canonical` を通した走査結果を既に持っている唯一の場所であり、ロード側へ移すと反復 6 で消した 62.5 MiB の複製が復活する）。

判定を `load_or_scan_with_stats` 側へ上げて `rescan_task: None` で消す形は**採らない**。記録の「行が無い」の意味が「起動しなかった」「cache-miss だった」「間引かれた」の 3 つに増え、受け入れ 3 の証拠がログから読めなくなる（→ §4）。

### 2.1 `built_at` の運び方

`LoadCacheResult` は現在 `material` / `read_ms` / `version` の 3 つしか運んでいない。`built_at` を 1 本足し、`version` と同じ経路で `BackgroundRescanTask` まで運ぶ。旧版の構造体（`IndexCacheV2`〜`V6`）は `built_at` を持ったまま `#[allow(dead_code)]` が付いているので、これを外して各フォールバック枝でも読む。

単位は **UNIX 秒**である（`save_cache_sorted_in` が `SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default().as_secs()` を書いている）。判定側の `now` も同じ導出を使う。`unwrap_or_default()` ゆえ、システム時計が UNIX epoch より前を指す異常系では `0` が書かれる——`0` は「十分に古い」＝期限切れ側なので、走る方へ倒れる。

## 3. 完走の記録 —「走ったら必ず書く」

現在 `if changed || stale_format` で条件づけられている保存を、**無条件**にする。間引きを通過して走査した以上、結末によらず `save_cache_sorted_in` を通す。

得られる不変条件:

> **走ったら書く。書かなかったなら走っていない。**

これにより `built_at` は「最後に完走した走査の時刻」と厳密に一致する。`Skipped`（ロック競合・generation 不一致）は走査していないので自動的に据え置かれ、権威的ビルド（`rebuild_and_save`）と cache-miss 枝も走査して書くので同じ不変条件の中に居る。

**この設計を選んだ理由は 3 つある。**

1. **権威的ビルド・手動再構築・形式昇格が、完走の記録をタダで進める。** どれも既に `index.bin` を書くので、追加の書き込み点がゼロである
2. **「開始を完走として記録する」バグが構造的に表現不能である。** `built_at` を進める唯一の手段は `save_cache_sorted_in` であり、それは完走したスキャン結果を引数に要求する。文書契約を 1 行も増やさずに済む
3. オンディスク形式が変わらない

**返す結末は `Unchanged` のままとする。** `Changed` にすると呼び出し側がアイコンキャッシュを無用に捨てる（既存の形式昇格と同じ構図）。材料（`IndexMaterial`）も `scanned_config_hash` も運ばない——中身が同一なので差し替えても得るものが無く、索引 1 本ぶんの常駐を無駄に積むだけである。

### 3.1 この変更が偽にする既存の記述

**同じコミットで直す。** 写しを取りこぼすのは写しを直す当のコミットである（#977）。

| 場所 | 現在の記述 | 直す方向 |
|---|---|---|
| `snotra-core/src/rescan_log.rs` の `RescanRecord::format_upgrade` の doc | 「`outcome=unchanged` なのに `save_ms` が非 null になる**唯一の理由**である」 | 偽になる（完走した `Unchanged` は常に `save_ms` を持つ）。`format_upgrade` は「その保存が版の書き戻しだったか」を示す観測量へ言い直す |
| `snotra-core/src/indexer.rs` の「`scanned` を捨てる操作の帰属は分岐で変わる」コメント | `Unchanged` 側は暗黙 drop され `unattributed_ms` に入る | 走査した経路は常に `save_cache_sorted_in` へ move するので、`unattributed_ms` の指すものが結末で分岐しなくなる |
| `snotra-core/CLAUDE.md`「indexer.rs の背景再スキャン」 | 「**書く契機は「中身が変わったとき」だけではない**」以下の 2 契機の説明と、検知器 2 本の名前 | 契機を「走査が完走したとき」1 つへ言い直し、検知器名を §6 の対へ差し替える |
| `docs/superpowers/specs/2026-08-09-rescan-in-situ-instrument-design.md` §8.2 | 「間引きの状態は別の反復で別の物体として設計する（`index.bin` の `built_at` を使う選択肢もある）」 | 本設計書への参照を 1 行足す（決着したことを示す。§8.2 の却下理由自体は今も有効なので書き換えない） |

## 4. 記録 — 間引かれた起動も 2 行書く

`rescan_log::LoggedOutcome` に `SkippedThrottled` を足す。`outcome()` は `"skipped"`、`skip_reason()` は `"throttled"` を返す。`scan_ms` 以下は `null` のまま（「通らなかった区間は `None` である」という既存の規約どおり）。

`start` 行は判定より前に書かれるので位置を変えない。これにより SPEC §13.4 の「キャッシュヒットの起動ごとに 2 行」が字義どおり真のまま残り、**受け入れ 3「全走査の頻度が毎起動でなくなった」がログから実測できる**。

## 5. 失敗時の振る舞い

前提: `INDEX_WRITE_LOCK` はプロセスローカルの `Mutex<()>` である（ファイルロックではない）。`BinFile::save_bytes` は `.tmp` へ書く → 旧ファイルを削除 → rename の 3 段である（Windows の `rename` は宛先が在ると失敗するため削除が要る）。

| 落ち方 | 起きること |
|---|---|
| 走査中にプロセス／電源が落ちる | 保存に到達しないので `built_at` は据え置かれ、次の起動でも期限切れのまま走る。部分的な走査結果が `index.bin` へ入る経路は無い（`save_cache_sorted_in` は `scan_all` が返り切った後にしか呼ばれない） |
| 保存中に電源が落ちる | 削除と rename の間に落ちると `index.bin` が消える。次回起動は cache-miss ＝ 本式の再構築になる。**破損した索引を読むのではなく作り直す方へ倒れる**。既存の性質であり、本設計が作るものではない |
| ロックを握ったまま落ちる | プロセスローカルの `Mutex` ゆえロックもプロセスと共に消える。「前回のクラッシュ以降、全再スキャンが永久に `SkippedLock`」は起きない |
| 記録の側 | `start` だけ在って `end` が無い行がクラッシュの信号として残る。間引かれた起動は `end` を `skip_reason="throttled"` で書くので**両者は区別できる** |

**書き込み頻度への影響はマシンによって向きが逆になる**ため、一言では書けない。

- 実運用点（`Changed` が 2/2 ＝ ほぼ毎起動書いている）では**減る**（7 日に 1 回へ）
- **一切変化しないマシン**では、今日の「一度も書かない」が「7 日に 1 回書く」へ**増える**

## 6. 検知器

既存の `background_rescan_does_not_rewrite_when_format_is_current` は**更新ではなく反転**する。旧い意図（毎起動書き直す退行の検知）は間引きの間隔そのものが肩代わりする。

| 検知器 | 固定する事実 |
|---|---|
| `full_scan_interval_elapsed` の単体テスト | 間隔内・間隔ちょうど・間隔超過・**未来**（`built_at > now`）の 4 点。`now` を注入するので固定入力で決定論的 |
| `background_rescan_is_throttled_within_the_interval` | 間隔内は走らず書かず、記録に `skip_reason="throttled"` が出る |
| `background_rescan_runs_when_the_interval_has_elapsed` | 間隔超過なら走る |
| `background_rescan_bypasses_the_interval_when_the_format_is_stale` | 旧版は間隔によらず走る（v4 教訓の「7 日間だけ」再発防止） |
| `background_rescan_stamps_built_at_when_entries_are_unchanged` | 完走した `Unchanged` で `built_at` が進む（旧検知器の反転先） |
| `background_rescan_does_not_stamp_built_at_when_skipped` | ロック競合では据え置かれる。**これが無いと「一度も完走しないまま永久に間引かれる」が沈黙で起きる** |

**変異で落ちるところまで確かめる。** 当てる変異は 3 つ:

1. 判定を反転する（`>=` → `<`）
2. **stamp を走査の前へ移す**（＝「開始を完走として記録する」バグそのもの）
3. 旧版バイパスを外す

**変異 2 は結果が 2 通りに分かれ、どちらでも設計の主張になる。** ロックの内側で走査より前に stamp することは**表現できない**はずである——タスクが持つのは digest だけでエントリを持たないので（反復 6）、走査前に `save_cache_sorted_in` へ渡す材料が存在しない。これが実証できれば §3 の主張 2（構造的に表現不能）そのものである。ロックの外で stamp する形の変異は表現できるが、それは `background_rescan_does_not_stamp_built_at_when_skipped` が落とす。**落ちる変異をでっち上げないこと**——実装時にどちらだったかを記録する。

**時刻の制御は 2 層に分ける。** 純関数のテストは `now` を引数で与えるので完全に決定論的である。統合側は `now` を注入せず、`built_at` を実 `now` からの相対値（例: `now - 8 日`）で与えることで分岐を選ぶ——`built_at` は §2.1 で `try_background_rescan_in` の引数になるので、`now` を注入可能にする改造は要らない（**現行の引数にはまだ無い。足すのは §2.1 である**）。

いずれもテストは `try_background_rescan_in` の **dir 注入**経路で書く。`.run()` 経由（`Config::config_dir()` 解決）で書くと実 `%APPDATA%\Snotra\rescan-log.jsonl` を汚し、上限つきの記録ゆえ実運用の観測を食いつぶす（#1013 の Gotcha）。`SNOTRA_CONFIG_DIR` での迂回もしない（プロセス大域の env であり並列実行中の他テストの保存先まで動かす）。

**検算**: フルテスト実行の前後で実 `rescan-log.jsonl` の行数が変わらないことを実測する。緑であることは根拠にならない。

## 7. SPEC 同期（受け入れ 4）

§3.3 の「バックグラウンドで**差分スキャン**を実施」が実装に届いていない乖離を、**実装側の言葉へ寄せて**解消する。書く内容:

- 通常起動の背景処理は全走査 ＋ digest 比較であること（「差分スキャン」ではない）
- **前回の完走から一定期間が空いた起動でのみ**走ること
- 形式が旧版なら期間によらず走ること
- 手動再構築・設定変更は間引きを経ず本式の再構築を kick すること（既存の挙動・脱出口）
- 間引かれた起動では材料が返らないので、走っているセッションの索引の差し替え（PR #1017）も起きないこと

**日数を SPEC へ書かない。** 正本はコードの定数（`FULL_SCAN_INTERVAL_SECS`）に置き、SPEC は「一定期間」と書いてその正本を名指す。

§13.4 には `skip_reason` に `throttled` が加わることを 1 行足す。

## 8. 受容する残余

**セッションが常に走査より短いマシンでは、間引きが一度も engage しない。** 走査が完走しない → `built_at` が進まない → 毎起動フルスキャンのまま、という帰結である。今日と同じ挙動なので悪化はしないが、改善もしない。**そしてそれは #1001 が名指した当の相手である**（12 秒セッション < 22 秒走査）。

これは完走を要求する設計から必然的に出るもので、構造では消せない。消すには「完走しないまま試行した回数」を状態に入れることになり、それは §9.1 で却下する。

**この残余が watch 枝（#1001 の後半）の動機である。** 監視は起動直後から変更を受け取れるので、走査の完走を待たずに鮮度を保てる。

## 9. 却下した案

### 9.1 K 回連続で完走しなかったら諦めて間引く

§8 の残余を消す案。**却下**: 間引きの状態が「完走した事実」から「試行した回数」へ汚染される。これは「開始を完走として記録する」の変装であり、誤ると「永遠に間引かれて再スキャンが一度も走らない」が沈黙で起きる。`2026-08-09-rescan-in-situ-instrument-design.md` §8.2 が計器の兼用を却下したのと同じ理由である。

### 9.2 専用の状態ファイル（`rescan-state.*`）を新設する

policy を resource から分ける既存の選好には合う。**却下**: 「権威的ビルドの直後に、間引きを知らないまま無駄な全走査が走る」を避けるには `rebuild_and_save` と cache-miss 枝の**全書き込み点**へ状態更新を足す必要があり、「`index.bin` を書いたら状態も更新せよ」という文書契約を新設することになる。加えて新しい永続形式なので版・欠損・破損の扱いを全部決めることになる。§3 の案はそのどちらも要求しない。

### 9.3 `index.bin` のファイル mtime を触る

17 MiB の書き戻しを避けられる。**却下**: 読まれない事実（mtime）と読まれる事実（`built_at`）の二重化になる。同じ事実を 2 か所へ書こうとしている時点でそれは写しである（`AGENTS.md` 条件別チェック）。避けようとしているコストは実測 `save_ms` = 458 / 683 ms であり、7 日に 1 回の 0.5 秒を惜しんで二重化を買う取引になる。

### 9.4 壁時計スケジュール（Everything の Folder Index と同じ形）

**却下**: Everything は常駐プロセス前提でタイマーを持てる。Snotra もトレイ常駐だが、タイマーとスレッドが増えるうえ「予定時刻に PC が落ちていたらどうするか」を別途決める必要があり、結局「前回完走からの経過」の状態が要る。起動起点の判定はその状態だけで完結する。

### 9.5 config キーで間隔を可変にする

**却下（今は）**: 永続形式の変更であり、新規記録・既存移行・外部参照 API・設定 UI を同時に揃える必要がある（`/plan-review` の 4 点セット）。求められたときに別反復で足せる。脱出口としては手動再構築が既に在る。

## 10. 触らないもの

- `scan_all` の中身（#1002 が別途扱う）
- `entries_digest` / `sort_entries_canonical`
- `src-tauri` 側の spawn とアイコン無効化（間引きは既存の `RescanOutcome::Skipped` として届くので、呼び出し側の分岐は変わらない）
- watch 枝（`notify` / USN）——#1001 の後半として別反復
