# governance:check の母集団を宣言・強制する設計

**前提**: 本設計は #1143（PR #1145）が着地した木を出発点とする。そこで新設した
`G-rules-script-coverage` と、その `//!` が宣言する死角を引き継ぐ。

## 1. 文脈 — 何が壊れているか

#1143 は「`.claude/rules/` の `paths` が `scripts/governance/` 配下を覆わず、判定コードを編集しても
ルールが配送されない」という欠陥だった。修正そのものは小さいが、**その修正を検める検出器が
3 巡にわたって同型の欠陥を出した**（母集団の下界を縛っていない → 走査側の狭窄に反応しない →
前方一致で中間層の消滅が沈黙）。この反復が本設計の出発点である。

5 つの独立した導出（歴史の監査・結合の地図・費用対効果・Codex への反証依頼・主エージェント）が
同じ結論へ着地した。以下は 2026-08-19 の実測値である。

| 観測 | 値 |
|---|---|
| 機構に触れたコミット（2026-07-19 導入〜2026-08-19） | 69 件 / 31 日。うち製品ソースに 1 行も触れないもの 52 件 |
| 検査の実装行数 | 474 → 3475 行 |
| 保守費の転換点 | `4f5f4d3f`（1 検査 1 ファイルへの分割）。fix 率 0.11 → 1.75 件/日 |
| CI で赤くなった実績 | 785 run 中 3 回、うち 2 回が誤検出（※ローカルでの捕捉は痕跡を残さないため過小評価） |
| 走査器（`WALK_EXCLUDE_PATHS`）に依存する検査 | 14 / 20。向きは沈黙 |
| 手で維持する列挙 | 22 件。大半が沈黙側 |
| 母集団の弱い下界（`|P| > 0`）を持つ検査 | 16 / 20 |
| **守りたい対象が母集団に居ることを固定した検査（強い下界）** | **4 / 20** |

**負債の所在は検査の本数ではなく、母集団と配線という「検査を検査する層」である。** 挙がった実例の
ほぼ全件が判定ロジックではなく母集団・配線の欠陥だった。

### 1.1 なぜ既存の防具では足りないか

`|P| > 0` は #1143 に対して**原理的に無力**である。あのとき母集団は空ではなかった——facade
（`scripts/governance-check.mjs`）が `scripts/*.mjs` に 1 件マッチし続けたので、
「マッチ 0 件」を見る `G-rules-globs` は緑のままだった。**必要なのは「空でないこと」ではなく
「守りたい対象が実際に入っていること」である。**

これは `.claude/rules/safety-nets.md`「検査の入力集合を、具体対象で検算する」として**規範には既に
書かれている**。守られているのが 4/20 だというのが、いま測れた事実である。規範は在り、機構が無い。

### 1.2 中心は既に在る（2026-08-19 実測）

`buildChecks`（`scripts/governance-check.mjs`）は**名前つきの母集団を 8 個、中央で組んでいる**
（`docs` / `refDocs` / `refSourceDocs` / `refCommentDocs` / `allRefDocs` / `staleDocs` /
`staleGuides` / `staleTargets`）。検査の内訳は次のとおり。

- **6 本** — `ctx` 経由でその共有母集団を消費する（＝**既にドメインを使っている**）
- **11 本** — 自前で `snapshot.files` を filter する
- **3 本** — 固定パスだけを読む（母集団を作らない）

**ドメインは新概念ではなく、胚の形で既に存在する。** 本設計はそれに名前と錨を与え、残りを寄せる。

## 2. 設計の核

### 2.1 部品 1 — 母集団の錨（anchors）

各母集団が「ここには**これが必ず居る**」を構造的事実として宣言する。

**錨は構造を名指す。単一ファイルを名指さない。** #1143 の canary は
`.githooks/githooks.test.mjs` という単一ファイルを錨にしたため、そのテストを移設するだけで
検査が赤くなり、しかもメッセージが `WALK_EXCLUDE_PATHS` を指して原因から目を逸らさせた（実測）。
**件数も錨にしない**——文書は毎日増減するので、件数を縛れば正当な変更のたびに赤くなり、
無視されるゲートに化ける（`ADR-retire-area-budget` が面積 ratchet について通った道と同じ）。

錨の形の例: 「`scripts/governance/checks/` 直下が 1 件以上」「`CLAUDE.md` を持つ workspace member が
すべて」。前者はディレクトリの実在、後者は他の SSOT（`Cargo.toml`）からの導出であり、
どちらも設計が変わったときだけ動く。

### 2.2 部品 2 — 登録時の強制とラチェット

`scripts/governance/registry.mjs` は既に `id` / `run` の不在をファイル名つきで throw する
（#1093 が「忘れうる登録行」を構造的に消した仕組み）。ここへ**「ドメイン参照」か「未移行マーカー」の
どちらかの宣言**を要求する。どちらも無い検査は登録できず、`governance:check` が起動時点で落ちる。

**未移行マーカーはラチェットである。** 数はメタ検査が報告し続け、新しい検査はマーカーを使えない
（＝ドメイン必須）。0 になった時点でマーカーを API から消し、逃げ道が構造的に無くなる。
規約ではなく機構が持つ保証であり、`docs/development-principles.md`「構造的設計原則と強制の階梯」の
向きに沿う。

### 2.3 部品 3 — メタ検査 1 本

ドメインごとに「錨 ⊆ 実際のメンバー」と `|P| > 0` を照合し、未移行マーカーの残数を報告する。
今バラバラに在る弱い下界と、場当たりに書かれた実ツリー検算が、これ 1 本へ集約される。

### 2.4 `ctx.record` の経路を使える根拠（ADR の再測定）

`ADR-facade-evidence-static-imports`（#1094）は「evidence を `ctx.record` へ寄せる」案を
「`record` の呼び忘れは誰にも捕まらない（実測: `undefined 件` と印字して exit 0・`npm test` も全緑）」
を理由に却下している。**この却下理由は #1098/#1118 の evidence view によって既に無効化されている。**

2026-08-19 に使い捨ての複製で同じ変異（`G-heading-refs` から `ctx.record` の呼び出しだけを外し、
findings は正しく返す）を当てた結果:

```
governance:check — 1 件の不整合:
  evidence が読む `headingRefs` が未記録である（供給側が消えた疑い）
exit=1
```

ADR は凍結された歴史ゆえ書き換えないが、**却下理由が実測なら、引用する前に取り直す**。
本設計は「申告の消失は今日すでに赤くなる」という測定の上に立つ。

## 3. 段階

**各検査に実質 1 度しか触らない。** 母集団の抽出を一旦 `population()` という中間 API へ出してから
ドメインへ寄せる二段構えは採らない（§6 に却下理由）。

| Phase | 内容 | 完了の判定 |
|---|---|---|
| 1 | `buildChecks` の 8 母集団をドメインへ格上げし、錨を宣言。メタ検査を置き、registry が宣言を要求する（既存検査は未移行マーカー 1 行） | 宣言を落とした複製で `governance:check` が起動時に落ちる。**この時点で 6 本が錨を得る** |
| 2 | 自前 filter の 11 本を、1 クラスタ 1 コミットで直接ドメインへ | 移送前後で母集団が**集合として同一**（旧式の抽出を当該コミットの足場として使い、突き合わせる） |
| 3 | 固定パスの 3 本へ錨を付ける（移送するものは無い） | 錨を 1 つ外す変異で赤 |
| 4 | 未移行マーカーが 0 になった時点で API から削除。`WALK_EXCLUDE_PATHS` をドメイン単位へ移す | 除外を 1 つ足す変異が、影響を受けるドメインの錨で赤くなる |

**事前のクラスタリングは行わない。** 2 本目が同じ母集団を要求したときにドメインを作る
（extract-on-second-use）。どの母集団が同じかを机上で決める必要はなく、2 本目が来た時点で
集合の比較として決まる。

**Phase 1 の時点で沈黙の面が減り始める。** 全体を終えるまで何も守られない、という形にはしない。

## 4. 不変条件と異常系

- `governance-check.mjs` の契約（依存ゼロ・決定的）を守る。ドメインの導出は snapshot（と他ドメイン）
  だけを入力に取る。
- メンバーは文字列の配列とする。ファイル一覧に限らない（`G-clippy-disallowed` の禁止メソッド、
  `G-hook-fires` の表の行など、ファイルでない母集団を持つ検査がある）。錨はその配列に現れるべき文字列。
- 錨がメンバーに無い → finding。メンバーが空 → finding。宣言が無い → **registry が throw**（起動時に落ちる）。
- メタ検査自身の母集団は「登録済みの検査とドメイン」であり、その縮小は `governance-manifest` の
  `checks` 列の差分が捕まえる。**ただしこれは PR でしか走らず、本文への宣言で通る**——射程の限界として宣言する。

## 5. テスト方針

各 Phase の完了判定（§3 の表）は、すべて**変異を複製へ当てて測る**形で書く
（`.claude/rules/safety-nets.md`「フォールトインジェクションでは、稼働中のガードを弱めない」）。
変異の強さは「実際に起きた回帰の姿」と同じかを確かめてから証拠に使う——#1143 では、
本来の回帰より強い変異が 157 件を出し、逐語の frontmatter で測り直して 106 件を得ている。

## 6. 却下した案

- **母集団を `population()` として全検査へ生やしてからドメインへ寄せる（二段構え）** — 却下。
  `ctx` を使う 6 本にとって中間 API は**何も足さない**。移送の正しさを測る継ぎ目は、**移送する
  コミットの中の足場で足り**、恒久 API を 20 本へ生やす必要はない。全検査を二度触ることになる。
- **母集団の件数を `governance-manifest` の 5 列目にする** — 却下。サイズは毎日動くので PR 本文での
  宣言がゴム印化する。錨は構造なので動かない。
- **錨を各検査のテストに置く（登録時強制をしない）** — 却下。今日 4/20 がやっている形そのもので、
  **宣言し忘れが沈黙する**。全検査に届かせるには登録時の強制が要る。
- **同一メンバーのドメインを gate で禁じる** — 却下。このリポジトリの「重複に見える 4 対」は
  **すべて意図的で、畳むと片方向が沈黙する**実測記録を持つ（heading-refs↔near / module-index↔module-linkage /
  adr-citations↔adr-file-names / rules-globs↔rules-script-coverage）。**合否を持たない計器として報告し、
  判断は人に残す。**
- **検査を減らして機構を縮小する** — 本設計では採らない。測定された痛みは「多すぎる」ではなく
  「黙る」であり、退役は沈黙の面を減らさない。退役の候補と根拠は別途 issue へ送る。
- **静的 import 閉包で配送範囲を導く** — 却下済み（`ADR-rules-paths-subtree-coverage`）。
  hook からの spawn と registry の動的 import が中心経路なので、静的解析では届かない。

## 7. 受容する残余

- **メタ検査は「錨がメンバーに居る」までしか言わない。** 母集団が正しい・十分であることは言わない。
- **事前のクラスタリングを捨てたので、似て非なるドメインが 2 つできる余地が残る。** 上記の計器が
  報告するが、止めはしない。
- **`globToRegex` は harness の配送判定の近似である**（#1143 の残余をそのまま引き継ぐ）。
- **機構への変更が更に積み上がる。** §1 の測定（69 コミット / 31 日）に照らして意図的に引き受ける費用である。
