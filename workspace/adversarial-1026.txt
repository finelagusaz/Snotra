## 争点4: 「導出を finish の外（Timeline 等の純粋側）へ置けば単体テストで8通り踏める」

**壊せなかった。ただし現状カバレッジには穴がある（⚠️ 追記）。**

- `finish`（524-548行）は `FINISHED`（`AtomicBool` CAS）と `TIMELINE`（`OnceLock<Mutex<...>>`）
  という process-global static に依存しており、`#[cfg(test)]` から素朴に複数回呼べない
  （2回目以降は CAS で早期 return する）。この制約は research.md の技術的制約節（53行目）が
  正しく明記している。
- 一方 `Timeline::to_json(&self, post_main_elapsed, outcome)` は既に純粋関数として単体テスト
  from複数箇所で直接呼ばれている（`outcome_is_carried_in_the_payload` 等）。event 名の導出
  （`if outcome.is_ok() { "startup:ready" } else { "startup:failed" }`）を `StartupFailure`
  または `Result<(), StartupFailure>` に対する自由関数として切り出し、`to_json` 同様に
  `#[cfg(test)]` から直接呼べば、8通り全部を実際に単体テストで踏むことは構造的に可能に見える
  （ブロッカーは見当たらない）。
- ⚠️ **確信が持てない所見**: 現状のテスト `outcome_is_carried_in_the_payload`（916-926行）は
  `Ok(())` と `Err(HotkeyRegistration)` の2通りしか検証していない。`failure_reasons_are_stable_
  and_unique`（888-914行）も手書きで7 variant の `reason()` の一意性だけを見ており、
  「event 名との対応」は見ていない。つまり **research.md が issue の要求として書いている
  「全8通りの event/ok 対応を固定する単体テスト」は、現時点のコードにはまだ存在しない**。
  research.md 自身はこれを「issue のやること（未達成）」として書いており矛盾はしていないが、
  読み手が「もう検証済み」と誤読しないよう明記しておく。

**この所見を偽にする手順**: `cargo test -p snotra -- startup::` を実行し、
`outcome_is_carried_in_the_payload` が8 variant を網羅しているかを実際のテスト本文で数える
（現状2件のみのはず）。

## 争点5: 「ハーネスの整合検査は、導出点が1つになると match 自体の誤りしか捕まえず単体テストと重なる」
## ＋ ハーネスにしか捕まえられない故障の型

**壊せた。** 少なくとも3種の独立した理由で、統一後も `Test-SnotraStartupPayload` は
Rust 単体テストが原理的に触れない層を検査している。

1. **trace() のシリアライズ／プロセス境界。** `trace.rs`（44-67行）には `#[cfg(test)]` が
   1つも無い（`grep -n "cfg(test)" src-tauri/src/trace.rs` は0件）。Rust 単体テストは
   `to_json()` が返す `serde_json::Value` を直接 assert するだけで、実際に
   `eprintln!("[trace] {line}")` で吐かれた文字列を誰も読み直していない。ハーネス
   （`Wait-SnotraTraceCondition` → `Read-SnotraTraceEvents` → `Test-SnotraStartupPayload`）は
   **実プロセスの実 stderr を `ConvertFrom-Json` で読み直した結果**を検査する。ここには
   「キー過不足」チェック（psm1:82-93）が含まれており、たとえば `trace()` 側でフィールドが
   欠落する・シリアライズが壊れるという回帰は、Rust 単体テストの視界には一切入らないが
   ハーネスは捕まえる。これは今回の課題文が例示する「trace の直列化経路」そのものである。
2. **複数スレッドが本当に競合するタイミング。** `main.rs:495-504` のコメントが明記する通り、
   platform スレッド（`platform/mod.rs:352` が撃つ `finish`）と main スレッド
   （`main.rs:284/394/523` が撃つ `finish`）は実際に並行に走り、どちらが `FINISHED` の CAS を
   先に取るかで `setup_rest` 区間の意味が変わる。Rust 単体テストはシングルスレッドで
   `Timeline::mark` に手で `Duration` を渡すだけなので、この実タイミング競合は原理的に
   再現できない。ハーネスは実バイナリを実際に起動して初めてこの経路を踏む。
3. **一度きり性（FINISHED CAS）自体は module doc（69-72行）が「検知手段は無い」と明記して
   おり、これは実は**「壊せなかった」側の所見**——ハーネスも単体テストもここを検知できない
   受容残余であることを研究メモは正しく書いていないが、issue 本文にも研究メモにも出てこない
   ので独立に発見した死角として記録する。

**この所見を偽にする手順**: `trace.rs` に `#[cfg(test)]` モジュールを追加し、`trace()` の
出力を実際にキャプチャして assert するテストを書けるかどうかを試す。書けて、かつ将来
そのテストが「`event` と `ok` の食い違い」を実際に検出できるなら、この所見（=ハーネス固有の
価値がある）は弱まる。また `main.rs` と `platform/mod.rs` の2並行 `finish` 呼び出しを
単一プロセス内の Rust テストで確定的に競合させる仕組み（determinism injection）が既存する
かを再確認する（現状は無いはず）。

## 争点5-補足（測定環境そのものへの疑い）: ハーネス整合検査は実際どこから呼ばれ、何を守っているか

**壊せた（research.md が触れていない重大な非対称を発見）。**

`Test-SnotraStartupPayload` の呼び出し元は grep で2つだけ実測された:

1. `scripts/bench-startup.ps1:166`（実バイナリを起動して実ペイロードを検査する、本来の
   integration 用途）
2. `scripts/lib/SnotraStartupContract.Tests.ps1:50`（Pester。合成データ `New-StartupPayload`
   を検査関数自身に当てる、**検査ロジックの自己単体テスト**であり実バイナリの出力は一切
   関与しない）

このうち **(1) の実行経路は `smoke.yml` の "Measure startup timeline" ステップであり、
`continue-on-error: true` が明示的に付いている**（smoke.yml:135-137。理由コメント自身が
「回帰の検査ではなく観測」「今は基準そのものが無い」と明言）。つまり `startup.rs` を変更する
PR で実バイナリの `event`/`ok` が実際に食い違っても、**この CI ステップは赤にならず PR は
ブロックされない**（コメントに残るだけ）。`SnotraStartupContract.psm1` 自身の module doc
（14-16行）も「`smoke.yml` の `continue-on-error: true` なステップからしか走らず、壊れても
誰も気づかない位置に居た」と自己申告しており、この点は矛盾しないが、**research.md 本文にも
issue 本文にも、この非対称（自己単体テストは blocking／実データ検査は non-blocking）は一言も
出てこない**。

一方 (2) の Pester 自己単体テスト（合成データのみ）は `.github/workflows/ci.yml:238-239`
`"Run PowerShell tests (Pester)"` → `npm run test:powershell` 経由で実行され、この ci.yml の
windows job には `continue-on-error` が付いておらず、かつ `on: pull_request` に paths 制限が
無い（ci.yml:3-9）ため**全 PR で blocking として走る**。

**帰結**: 現状「ハーネス側の検査」のうち実際に PR をブロックしうる部分は「検査ロジックが
合成フィクスチャに対して正しく動くこと」だけであり、「実バイナリの `event`/`ok` が実際に
一致していること」は non-blocking な観測に留まる。research.md の未解決の疑問（末尾60-65行）
は「ハーネス側の検査を残すか外すか」を Rust 単体テストとの重なりの観点だけで論じているが、
**実態としてこのハーネス検査は現在ほぼ「一致していないことを人間が気づけば直す」程度の弱い
保護であり、9割方の実効的な保護は既に Rust 側の（将来の）単体テストに移っている**と読める。
これは issue の判断（残すか外すか）に直接効く事実であり、研究メモに欠落している。

**この所見を偽にする手順**: `.github/workflows/smoke.yml:135-137` を再度読み、
`continue-on-error: true` が "Measure startup timeline" ステップに付いているかを確認する
（付いていなければ本所見は偽）。また `ci.yml` の `pull_request:` トリガーに `paths:` フィルタが
無いこと（238-239行のステップが全PRで走ること）を `.github/workflows/ci.yml` 冒頭3-9行で
再確認する。

## 争点6: 「ADR-startup-instrument-contract-shape §1 に抵触しない」

**壊せなかった。**

- ADR §1（10-19行）が却下したのは「終端を1つのイベントにして `ok` フラグで分ける」案であり、
  却下理由は「ハーネスが `ok` の検査を1つ忘れた瞬間に沈黙で通る」——つまり**イベント名が
  2種類あること自体**（`startup:ready` / `startup:failed`）が守りたい性質であって、
  「その2つの文字列をコード上のどこから導出するか」は ADR の争点に含まれていない。
- issue #1026 本文・research.md とも「event 名を2つ保つ」ことを明言しており、実際に
  `finish` の書き換え案（導出点を1つにする）でも `event` 変数自体は `"startup:ready"` /
  `"startup:failed"` の2値を返す設計のままである（研究メモの「再利用できる既存パターン」節の
  例示、および issue 本文「ADR との関係」節と整合）。

**この所見を偽にする手順**: ADR 本文（10-19行）を再読し、却下理由が「イベント名の導出箇所」
ではなく「イベント数を1つに畳むこと」自体に向いているかを確認する（向いていれば偽）。
