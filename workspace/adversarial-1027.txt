--- A1. 命題3（PERFORMANCE.md 不変の根拠＝digest_ms 先例）: 先例の同一性が崩れる ---

research.md §4 は「PERFORMANCE.md を直さない根拠は先例の実測」とし、digest_ms を引く。
だが `git log --all --oneline -S"digest_ms" -- snotra-core/src/indexer.rs` で調べると:

  9acd129f perf(core): 背景再スキャンの比較を digest へ（#970・導入）
  ae3335df perf(core)!: 背景再スキャンを撤去し、索引の更新を明示操作だけにする（#1023・削除）

`git show ae3335df -- snotra-core/src/indexer.rs` を読むと、`digest_ms` フィールド宣言・
生成・doc が丸ごと削除されている（`pub digest_ms: u128,` が消え、`digest_started.elapsed()`
の行も消えた）。これは「改名」ではなく「機能ごと撤去」である——背景再スキャン機構自体が
#1023 で廃止され、digest という概念そのものが製品コードから消えた。

一方 #1027 の変更は「total_ms という概念は生き続けたまま、Rust 上の表現だけが
u128→Duration に変わる」型変更である。「概念が消滅した撤去」と「概念は生きたまま識別子の
形だけ変わる改名」は構造が違う——PERFORMANCE.md の 1883 行目
（`ロード（壁時計・total_ms）| 216 ms | 80 ms`）が記録する「ロード時間」という量は
#1027 後も実在し続けるが、digest_ms が測っていた「背景再スキャンの digest 比較」という量は
#1023 後は存在しない。前者は「今も居るが名前が違う値」、後者は「もう居ない値」であり、
「先例と同じ扱いを踏襲する」という論法は、比較対象の性質が違う分だけ効力が落ちる。

さらに、研究が併せて引く PERFORMANCE.md 自身の規約（30-40行）
「適用は、これ以降に新しく書く記録に限る。既存の記述へ遡及して補完しない」は、
文脈上**機体名のような「今は分からない情報を後から埋める」ことを禁じる規約**であり
（「過去の測定がどちらの機体で取られたかを知る手段は無く、埋めれば測定記録の顔をした
推測が残る」と明記）、「今分かっている改名を反映して識別子を訂正する」こととは性質が違う。
この規約を「識別子の改名を反映しない」の根拠として引くのは、規約の射程を広げすぎている
可能性がある。

**この所見を偽にする手順**: PERFORMANCE.md の規約節に「識別子の改名時は追随させない」を
明文で追加するか、#1023 以外に「改名」型（概念は生存・識別子だけ変わる）の先例が
実在することを `git log -S` で示せば、この所見は崩れる。

**ただし裁定への影響は限定的である**——「PERFORMANCE.md を直さない」という結論自体は、
同規約の「この文書を『今も支えている値』と『歴史』に分けない」（今も設計を支える値は
コードの doc を正本にする）という**別の**文言でなお正当化できる可能性があり、
research.md の§4 も既に「⚠ 先例1件からの帰納」「人間レビューで覆りうる」と自己申告
している。私の指摘は「その帰納がさらに弱い（比較対象の性質が違う）」ことを補強するもので
あって、結論を覆すには至らない。

--- A2. 命題5（compile-fail は「findReferences より強い全数検出器」）: cfg(debug_assertions) が穴になりうる ---

`src-tauri/src/main.rs:178-187` の消費箇所（研究の§2表で「消費 | main.rs:185」と挙げた eprintln）は
`#[cfg(debug_assertions)]` の下にある:

    #[cfg(debug_assertions)]
    {
        let s = &result.stats;
        eprintln!(..., s.total_ms, ...);
    }

Cargo のデフォルトでは `[profile.release]` に `debug-assertions` の明示上書きが無く
（`Cargo.toml` を実測）、release プロファイルは `debug-assertions = false` が既定値である。
ゆえに **`cargo build --release -p snotra` / `cargo test --release -p snotra` を単独で走らせると、
この cfg ブロックは一切コンパイルされない**——`s.total_ms` を `s.total.as_millis()` へ
移行し忘れても、release ビルドはそれを検出しない。

research.md §2 は「型変更は `cargo build -p snotra-core` / `cargo build -p snotra` /
`cargo test -p snotra-core --no-run` の compile-fail が findReferences より強い全数検出器に
なる（フィールドの型が変われば、読む側は必ず落ちる）」と書くが、これは**プロファイルを
明示していない**——「必ず落ちる」は dev プロファイル（`debug-assertions = true` が既定）
でのみ正しい。

**実害の有無**: `docs/build-commands.md` のカテゴリ A 必須コマンド（`cargo check --workspace`・
`cargo test -p snotra`）はどちらもデフォルトで dev プロファイルを使うため、**このリポジトリの
必須検証フローでは実際には穴が開かない**（`cargo check`/`cargo test` を release 抜きで打てば
debug_assertions ブロックも型検査される）。ただし `npm run bench:startup`（release 本体を測る・
`cargo build --release -p snotra` を要求）や `npm run tauri build` のように**release だけを
ビルドする経路がこのリポジトリに実在する**ため、「compile-fail は全数検出器」という言い切りは
過大主張であり、正しくは「dev プロファイルで走らせる限り全数検出器」である。

**この所見を偽にする手順**: `[profile.release] debug-assertions = true` を明示するか、
main.rs:185 の cfg(debug_assertions) ブロックを消せば、この穴は閉じる（が、現状では未対応）。

--- B2. 命題2（to_ms(d) == d.as_millis() は常に成り立つ） ---
