テストが実在すれば、内包はその文言と直接矛盾し主張は壊れる。grep で該当箇所は見つからなかった

5. 「RowsSnapshot::input_idle と is_unsettled は別概念であり、修正を当ててはならない」
   ＋逆向き: 「is_unsettled の式を変えると input_idle の doc の導出 1 行が沈黙で腐るか」
============================================================
判定（前半・分離の意図）: 壊せなかった。
判定（後半・式が変わって腐るか）: 壊せなかった、ただし ⚠️ 別経路の腐り方が実在する。

一次証拠（前半）: results_view.rs:36 の doc を読了。「これは perf ヒューリスティックであって
正しさの述語ではない」「食い違うのは armed == false ∧ pending != 0 のときである」と明記。
数式で検算した: `input_idle = !armed`、`is_unsettled(armed, pending) = armed || pending != 0`。
`!is_unsettled = !armed && pending == 0`。両者が食い違うのは `armed == false` かつ
`!(pending == 0)` すなわち `armed == false ∧ pending != 0` のとき——doc の記述と数学的に一致した
（自分で式を立てて検算した一次証拠であり、doc の転記の裏取りではない）。8ca9950（#1074 のコミット）
のコミット件名は「settled の二義性を消す」で、この分離が直近の意図的な設計判断であることと符合する。

一次証拠（後半・式は変わるか）: research.md の決定 2 が明記する新しい式は
`armed || self.dispatch.pending_seq() != 0`——旧来の自由関数 `is_unsettled(armed, pending_seq)`
の本体（search_dispatch.rs:79-81）と**論理的に同一の式**である。housing（型の所在）が変わるだけで、
入出力関係は変わらない。ゆえに doc の導出行「食い違うのは armed==false ∧ pending!=0 のとき」は
式の意味では腐らない。

⚠️ 別経路の腐り方: research.md の決定 2 は「自由関数を残すか削除するか」を明記していない。
results_view.rs:36 の intra-doc link は `[crate::egui_shell::search_dispatch::is_unsettled]`
という**特定のパス**を指す。もし実装時に自由関数を削除し `SearchState::is_unsettled` という
メソッドだけへ一本化すると、この intra-doc link は解決先を失い `cargo doc` が壊れた link として
検出する（`.claude/rules/comments.md` の手動検査対象・PostToolUse hook は沈黙する）——これは
「式が沈黙で腐る」のではなく「リンクが騒がしく壊れる」経路であり、#1039 コメント 2 が
警告した「cargo doc は式の形を検査しない」という前提そのものは正しいが、**リンク切れ自体は
cargo doc が捕まえる**ため完全な沈黙ではない。真に沈黙するのは、自由関数を残しつつ実装だけ
こっそり式を変える（例: `&&` に取り違える）場合で、その場合はリンクが生きたまま式だけ乖離し、
研究が懸念した「沈黙で腐る」が文字通り起きる。**research.md の決定 2 は自由関数を残すか削除するか
を確定させていない**ため、この危険（intra-doc link 破壊 or 式の意味的乖離のどちらが起きるか）は
plan.md 側で明示的に選択する必要がある——現状は §7 未解決の疑問にも入っていない**空白**である。

偽にする手順: plan.md（または実装）が「自由関数 `search_dispatch::is_unsettled` を残す/消す」を
明記していれば、この ⚠️ は該当箇所を読むだけで解消する。現時点の research.md にその記述は無い
（決定 2 のコードスニペットはメソッド定義のみを示し、自由関数の去就に触れない）。
