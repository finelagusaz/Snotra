- 実 config.toml の [[paths.scan]] は **5 本**: C:\Toolbox(.exe, folders) / C:\KISS(.exe) / Start Menu(.lnk) / C:\workspace(extensions=[], include_folders=true) / C:\(extensions=[], include_folders=false)。C:\ は最後。→ 依頼文の「根 4 つ」と食い違う（research.md 自体は根の数を書いていない。食い違うのは依頼側の前提）。

  - 理由の裏付け（scan.rs scan_directory_with_extensions）: 走査は常に全再帰し、ファイルは `matches_extension(extensions, ext)` のときだけ登録する。build_extension_list は空配列をそのまま空にし、binary_search は空で必ず false → **extensions=[] かつ include_folders=false の `C:\` は、全ディスクを再帰しても 1 件も登録しない**。C:\workspace は include_folders=true なのでフォルダだけは入る。
  - 帰結（本件で最も重い）: 走査の所要の大半（C:\ の再帰）で「登録件数」は動かない。issue の例示「128,000 / 約 312,000 件」型の進捗は、この config では「件数がほとんど進まないまま数十秒」になる。research.md の疑問 7 は「件数を AtomicUsize で出す」前提だが、**登録件数は仕事量の代理にならない**（訪問ディレクトリ数・read_dir 回数のほうが仕事量に近い）。壊せた（後述 R-9 / R-1）。
  - ⚠️ 確信度: index.bin の件数は strings 概算であって、デコードして数えていない。issue（2026-08-11）時点の config と今の config（mtime 2026-11-07）が同じとは限らない。偽にする手順: `snotra-core` の `load_cached_entries` 相当を #[ignore] テスト等で読み `entry_count` を出す（読むだけ）。または config.toml を issue 当時の版（bak は 3 月）と見比べる。
- 偽にする手順（根の数）: `grep -c "^\[\[paths.scan\]\]" "$APPDATA/Snotra/config.toml"` → 5。

### B5 争点 5: rebuild_and_save を scan_and_sort_timed に通せるか
[壊せなかった（通せる）。ただし 1 点の注意]
- rebuild_and_save（cache.rs L656）: `with_index_write_lock(|| { scan_all → sort_entries_canonical → compute_config_hash → save_cache_sorted })`。scan_and_sort_timed は scan_all＋sort だけで INDEX_WRITE_LOCK を取らない（doc に明記・「ロックの範囲は呼び出し側が決める」）。cache-miss 分岐も同じく with_index_write_lock の内側から呼んでいる（L469 付近）。よって同じ形でクロージャ内に置け、config_hash はその後に計算する順序も保てる。戻り値 Scanned は同モジュール private で、rebuild_and_save も同モジュール → 可視性の問題なし。
- 注意（壊せた小）: メモは「`rebuild_and_save` はこれを通っていない」と書き、再利用の利点を言うが、rebuild_and_save の返り値は IndexMaterial のみ。区間を呼び出し側（indexing.rs）へ運ぶには返り値を広げる必要がある（メモ疑問 5 が既に認識済み）。さらに scan_and_sort_timed の `scan` はシャドーイング罠（#1178）あり。
- save（save_cache_sorted）区間は scan_and_sort_timed の外にある。load_or_scan_with_stats_in は cache_save を別計測しているので、同形に揃えるなら save も測る必要がある。
- 手順: cache.rs の scan_and_sort_timed と rebuild_and_save を並べて読む（済）。実際に差し替えてビルドする検証は未実施 ⚠️。

### B6 争点 6: 測定環境
[壊せた（重要）]
- issue の 29.3 / 82.8 秒は **/s（rebuild_and_save 経路）**。根拠: issue 本文「egui_slash {RebuildIndex} の trace 時刻と index.bin の mtime で外から挟んで採った」。起動時 cache-miss（load_or_scan_with_stats）で測ったのは「参考」の v0.18.3 25.6 秒のほう。メモの扱いは概ね正しい。

### B7 争点 7: 分母 entry_count
[壊せなかった。補足あり]
- Engine::entry_count → SearchEngine::entry_count = `self.entries.len()`（search.rs L500）。現在メモリにある索引の件数で、drain 完了の complete_index_drain で swap された後の値。PATH マージは build_index_from_material（material.extend_with_path_entries）で swap 前に入るので、**分母（前回）は PATH エントリを含む**。一方 scan_all の出力は PATH 前で、dedup（Dedup::accept）は scan_all の内側で済んでいる。メモの記述どおり。
- 補足（壊せた小）: 起動時のロード経路は PATH を `PrebuiltIndex` ではなく Engine へ直接マージする（indexing.rs の doc が別手順と明記）。それでも entry_count は両経路で PATH 込み。ただし**設定で include_path_env を切り替えた直後の分母は、新設定の件数と PATH 分だけずれる**（メモの「根が変わると分母は意味を失う」は PATH 設定にも当てはまる）。
- 手順: search.rs entry_count と indexing.rs build_index_from_material を読む（済）。
