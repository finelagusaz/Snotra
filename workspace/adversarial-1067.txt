## 壊せた項目

### [争点A / §2.2(a)] 「実 config は `include_path_env = true` ゆえ実運用は必ず旗が下りている」

**過大な全称表現である。「必ず」は成立しない。** `IndexTree::extend_with_roots`
（`snotra-core/src/index_tree.rs:732`）の先頭:

```rust
pub(crate) fn extend_with_roots(&mut self, entries: Vec<AppEntry>) {
    if entries.is_empty() {
        return;
    }
    ...
    *sorted_by_path = false;
}
```

**`entries` が空なら早期 return し、旗は下ろされない。** `entries` の出所は
`indexer::scan_path_env`（`snotra-core/src/indexer.rs:1772`）で、これは
「`HKCU\Environment\Path`（ユーザー PATH。システム PATH を含まない）が未設定/空なら
`Vec::new()`」「新規実行ファイルが 0 件（すべて `reject_existing` で既存と重複）でも空」
を返す。**この経路は製品コード自身が明示的に「無害な no-op」として認識している**——
`src-tauri/src/main.rs:206` のコメント: 「**空の場合のガードは持たない**——追記も木への
追加も、空なら何もしない」。

つまり `include_path_env = true` は「旗が下りる**必要条件**」であって**十分条件ではない**。
実際に下りるかどうかは「ユーザー PATH が非空」かつ「その中に索引未登録の実行ファイルが
1 件以上ある」という**追加の前提**に依存する。

**この所見を偽にする手順**: `HKCU\Environment\Path` を空にした config（または
`scan_path_env` が返す `entries` が空になるよう、PATH の全ディレクトリを事前に
`paths.scan` の根へ含めた config）で `measure_path_query_frame_cost` 系の計器を走らせ、
`sorted_by_path` が真のままであることを確認すれば、この crack が実害を持つことが示せる
（未実施——ビルド不要の書面調査の範囲では、コードパスの存在までしか示せない）。

**注記（実環境では偶然 false 側）**: 本セッションで実際に `HKCU:\Environment\Path` を
読んだところ（後述「測定環境について」）、64,101 バイトの非空値で、`cargo\bin` /
`scoop\shims` / `npm` など C:\ 配下の複数ディレクトリを含み、そのどれも既存スキャン根
（`.lnk`/`.txt` 限定 + 4 根）には含まれない実行ファイルを持つ可能性が高い。**したがって
「この開発機の“今の”実行では」旗は下りる公算が高い**が、これは環境の偶然であって
「実運用は必ず」という全称の根拠にはならない。CI・別マシン・PATH が空のユーザーでは
容易に崩れる。`AGENTS.md`「検証の作法」の「全称表現は前提条件とセットで書く」に
そのまま抵触する一文である。

### [争点D / §2.5] 「TopK::push は満杯後ヒープの worst 1 件としか比べない」→ tie-break 総当たりは過大、という結論の**根拠付けが不完全**

**部分的に壊れる。** `TopK::push` の候補 vs worst の比較が 1 回であることは正しい
（`scoring.rs:253` 実装を確認済み）。しかし研究がここから導く「だから cmp_paths への
到達は稀」という含意は、**`BinaryHeap::PeekMut` の `Drop` 実装を見落としている**。

Rust 標準ライブラリの実装（
`C:\Users\Eoh\.rustup\toolchains\stable-x86_64-pc-windows-msvc\lib\rustlib\src\rust\library\alloc\src\collections\binary_heap\mod.rs:308-321`）:

```rust
impl<T: Ord, A: Allocator> Drop for PeekMut<'_, T, A> {
    fn drop(&mut self) {
        if let Some(original_len) = self.original_len {
            ...
            unsafe { self.heap.sift_down(0) };
        }
    }
}
```

`original_len` は `DerefMut::deref_mut` が呼ばれたときだけ `Some` になる（同ファイル
335-345 行）。`TopK::push` の `scored.cmp(&worst)` は `&worst` の**不変** `Deref` しか
使わないので sift_down を誘発しないが、**`*worst = scored`（置換が起きた場合）は
`DerefMut` を要求し、`worst`（`PeekMut` ガード）が drop される時点で必ず
`sift_down(0)` が走る。** これは `O(log limit)` 段の**内部比較**であり、各段は
`ScoredEntry::cmp`（= score→last_launched→lower_name→**cmp_paths**）を再度呼ぶ。
つまり「置換が起きた回数」×「置換 1 回あたり `log2(limit)` 回程度の追加比較」が
研究の勘定から漏れている。

**この漏れが `c:\` で無視できない規模になる根拠**:
- 全 312,108 件が `score = 3000`（`PATH_BASE - 0`）で一致し、履歴が乏しい実環境
  （後述、`history.bin` 4,040 B）では `last_launched = 0` もほぼ全件一致するため、
  tie-break は**キー 3（`lower_name`）とキー 4（`cmp_paths`）にほぼ全負荷が乗る**
- 実 config は `C:\` を `extensions=[".txt"], include_folders=true` で走査しており、
  `scan_directory_with_extensions`（`indexer.rs:256`, 279 行の
  `if include_folders { push }`）は**拡張子を問わず全フォルダを無条件で積む**。
  `snotra-core/CLAUDE.md`「history.rs のキー正規化」節が引く実データの folder 比率
  81.9% と符合し、`node_modules` / `.git` / `target` / `src` / `bin` のような
  **開発機で桁違いに反復するフォルダ名**が大量に混入する構成である
- ゆえに「候補 vs worst の `lower_name` がバイト一致」（cmp_paths へ落ちる条件）は、
  研究が想定するより高頻度で起きうる。**「稀」と断定する根拠は無い**——研究自身も
  「実運用点で効くかが本 issue の分岐点」と留保しているが（§2.5 末尾）、そこへ至る
  「1 件としか比べない」という記述そのものが sift_down の追加比較を見落としており、
  過大評価の否定が過小評価にすり替わっている

**この所見を偽にする手順**: `sift_down` のログ計装（テストコードでの候補比較回数カウンタ、
または `cmp_paths` 呼び出し回数のグローバルカウンタを一時的に注入）を入れて実 index で
`c:\` を 1 回実行し、`cmp_paths` の実呼び出し回数を数える。回数が heap の初期充填分
（`limit` 件程度）にとどまるなら本所見は誤り、`limit` を大きく超えるなら本所見が正しい。
**未実測**（ビルドを要するため本調査の範囲外）。

### [争点C / §2.1] 11.4 ms は引き算で作った推定であり、888 と 3,204 を `c:\` の行へ移す操作の妥当性

- **部分的に構造的な裏付けが取れた**（研究が「誰も測っていない」と留保した点への追加情報）。
  `score_one_entry`（`scoring.rs:461-463`）のガードは

  `\zzz-no-such-path\` も `c:\` も**どちらもパス区切りを含み `plan.path_query` が

  （キー組み立て・研究の 3,204 µs 成分）へ到達する**。この成分に関しては
  「両行で同じ額」という前提を裏付ける構造的根拠がある
- 一方、「888 µs のループ素オーバーヘッド」は #1059/#1067 のアブレーション実測から
  来ており、コード読解だけでは独立に検算できない（bitmask pre-filter・
  `entry_view` 構築など、両クエリで同一パスを通ることは確認できるが、正確な額は
  実測ハーネスの結果に依存する）
- `find(pq)` については、`c:\` は index 0 の 3 バイト一致で即終了、`zzz` は

  （研究もこれを前提にしており、矛盾しない）
- **壊せなかった理由**: 「加法性が代数的恒等式に過ぎない」という #1059/#1067 自身の
  留保は妥当で、これを覆す独立検算はビルド・実測なしには行えない。ただし
  「888 と 3,204 が両行で同額」という**仮定の一部（3,204＝キー組み立て）**は、
  上記のとおりコード構造上支持される。888（純粋なループ・pre-filter オーバーヘッド）
  については支持材料はあるが確証はない

## ⚠️ 確信が持てない所見

- **§2.4「16 コアで概算 1 ms 未満」の桁**: オーダーの計算は矛盾しないが、
  FxHash の実スループットは CPU・ビルド設定（LTO・codegen-units）に依存し、
  実測なしでは「1 ms 未満」と「3〜5 ms」を判別できない。ablation 実測が必要
  （偽にする手順: `snotra-core/src/search/tests/performance.rs` に履歴照合 3 種のみを
  ON/OFF するアブレーションを足し、`#[ignore]` ベンチとして実行）

- **争点D の実害の大きさ**: sift_down の見落とし自体は構造的に確実だが、
  「これが 11.4 ms の中でどれだけの比率を占めるか」は測定なしには言えない。
  `cmp_paths` 呼び出し回数が実際に heap 初期充填分を大きく超えるかどうかは
  folder 名の実際の重複密度（`node_modules` 等がこの開発機に何件あるか）に依存し、
  本調査では `index.bin` の中身を個別デコードして数えていない（偽にする手順:
  `snotra-core/tests/path_query_cost.rs` に近い形で実 index を読み、
  `lower_name` の重複度数分布を集計する一時スクリプトを書けば直接測れる）

- **争点A の「実害」**: 本セッションで確認した限り、この開発機の「今」の PATH は
  非空で新規実行ファイルを含む可能性が高く、実際には旗が下りている公算が高い
  （＝命題の**帰結**は生きている）。壊れているのは「必ず」という**全称の言い回し**で
  あって、この特定の測定セッションの結論そのものではない——読み手が「一般に成立する
  不変条件」と誤読するリスクを指摘するに留める

- **§2.2(b) の name/file スコアリング短絡の記述**: 「`skip_name` は Fuzzy のみ要求する
  ので substring では発火しない」は `scoring.rs:376-378` のコードで確認済みで正しい。
  ただし「#1057 の -4.3 ms はそもそも substring では効いていない」という結論は
  #1057 の実測データを直接見ておらず（本調査のスコープ外）、コード上の整合性のみ
  確認した

## 見落とし（母集団の外に在ったが本 issue に効くもの）

- **`TopK::new(max_results)` の実引数は 200（`effective_result_limit()`）であり、
  `search.rs:311/328` の `max_results` は `TopK::new(limit)` の `limit` そのもの**。
  研究 §6「疑問 1」の傍注が触れる `TopK::new(201)` という数字は、`TopK::new` 内部の
  `BinaryHeap::with_capacity(limit + 1)`（`scoring.rs:247`）という**予約容量**と
  混同していると思われる小さな不正確さ（実 config の `limit` 自体は 200）。
  結論には影響しないが、ablation 設計時に `limit` と `capacity` を取り違えると
  検知器の閾値がずれる

- **`rayon` のタスク分割数は固定 16 ではない**: 研究 §6「疑問 1」「疑問 3」・
  `PERFORMANCE.md` の議論は暗黙に論理コア数（16）をタスク数と同一視しているが、
  `into_par_iter().fold(...)`（`search.rs:308-311`）の実際の分割数は rayon の
  work-stealing が動的に決めるものであり、`TopK::new` の呼び出し回数（＝fold の
  accumulator 生成回数）はコアより多い可能性がある。ablation で「タスクごとの
  ヒープ充填コスト」を見積もるときはこの点を測ってから固定値を使うべき

- **`index.bin` に保存されている `sorted_by_path` の実値は本調査では確認できていない**
  ——バイナリを直接デコードするには postcard 形式のパースが要り、ビルドなしの

  本文が主張）は、`sort_entries_canonical` を通した後の走査結果が実際に
  バイト順単調増加であることに依存しており、これも独立には検算していない
  （`IndexTree::build` の `sorted_by_path = entries...`(654 行) の判定ロジックは
  読んだが、実データでの結果は未測定）
