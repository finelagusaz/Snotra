命題 1: 「パスクエリで集めた local_matches は原理的に再利用されない」
====================================================================

【裁定】壊せなかった。ただし当初は壊せる可能性がある経路を見つけたので、その経路を
実際に潰した過程を記録する。

can_reuse は「前回クエリ Q1 が has_path_sep」ではなく「今回クエリ Q2 の has_path_sep」
だけを見る（search.rs 204-217行）。ゆえに Q1（区切りあり）が集めた prev_candidates を
Q2（区切りなし）が読む、という一段ずれた再利用が理屈の上ではあり得る。これが成立する
条件は「Q2.norm_query が Q1.norm_query（区切り文字を含む）を前方一致で含みながら、
Q2 自身の生クエリには区切り文字が 1 つも無い」。normalize_query（query.rs 152-199行）は
小文字化・nucleo の accent-fold・空白圧縮しかせず、`\` `/` `¥` を他の文字から生成しない
ので、素朴には Q2 の norm_query が区切り文字を持つには Q2 の生クエリ自身が区切り文字を
持つ必要があり、その時点で Q2.has_path_sep が真になって can_reuse の `!plan.has_path_sep`
条件に阻まれる——一見、命題は自明に成り立つ。

唯一の抜け道として検討したのが `¥`(U+00A5) の畳み込みである。query_plan.rs のフィールド
doc（29-38行）が「¥ が畳まれる版では生クエリに区切りが在っても needle には無く」と
条件付きで書いており、これが事実なら Q1 の生クエリを¥だけで組めば norm_query から
区切り文字が消え、Q2（区切り無しの生クエリで norm_query が偶然 Q1 の norm_query を
前方一致で含む）が prev_candidates を読める可能性が生まれる。

実際に nucleo-matcher 0.3.1（`C:\Users\Eoh\.cargo\registry\src\index.crates.io-...\
nucleo-matcher-0.3.1\src\chars\normalize.rs`）の table を読んだ:
`pub fn normalize(c: char) -> char` は `i < DATA1_START` なら `c` をそのまま返す。
DATA1 配列の最初のエントリは `'\u{00C0}'`（0xC0）であり、¥(0xA5) は 0xC0 未満なので
即座に恒等写像で返る。DATA1〜DATA3 のどのテーブルにも 0x00A5 のエントリは無い
（`grep -n "00A5|00a5"` が 0 件）。つまり **今の依存バージョンでは ¥ は畳まれない**。
query_plan.rs のコメント自体も「¥ が畳まれる版では」という条件文であり、現在の挙動を
断定してはいない。この経路は現在のコードでは通らない。

結論: 現在の nucleo-matcher 0.3.1 の下では、命題 1 を破る具体的な打鍵列を作れなかった。
ただし論証は「外部クレートの正規化テーブルに ¥ のエントリが無いこと」という**外部依存の
バージョン挙動**に立脚しており、契約として保証されたものではない。

⚠️ 命題 1 の真偽は C1 changes の**性能上の動機**（「無駄な収集をやめる」）にのみ関わり、
**安全性**には関わらない。命題 2 の議論（下記）は命題 1 の真偽と無関係に成立するため、
命題 1 が万一将来のクレート更新で偽になっても C1 の安全性は揺らがない。

この所見を偽にする手順: nucleo-matcher を、¥(U+00A5) を何らかの ASCII 文字へ畳む
バージョンへ更新したうえで、Q1="c¥documents"（またはそれに相当する¥区切りのパス
クエリ）→ Q2=（Q1 の norm_query の折り畳み結果を prefix に持つ、区切り文字を含まない
生クエリ）の順で打鍵し、2 打鍵目で can_reuse が true を返すこと、かつ
prev_candidates が Q1 の local_matches そのものであることをデバッガ/ログで確認する。

命題 2: 「収集をやめても検索結果は集合・順序とも不変である」
====================================================================

【裁定】壊せなかった。この命題は命題 1 の真偽に依存しない、より強い論証で支えられている。

同一クエリ内での影響: fold クロージャ内（search.rs 312-325行）で
`top_k.push(scored)` は `local_matches.push(i)` と独立に、スコアが Some の全候補へ
無条件で実行される。local_matches の収集を止めても top_k の中身は 1 ビットも変わらない
——同一呼び出しの結果は自明に不変。

次回呼び出しへの影響: C1 は `all_match_indices`（= 次回の prev_candidates）を空にする
だけで、`prev_query` / `prev_mode` / `prev_kana_query` の 3 フィールドは
`plan.norm_query.into_owned()` 等そのままの値で書き続ける（search.rs 341-348行）。
can_reuse の `!self.prev_candidates.is_empty()`（211行）が false を返すため、次回は
必ず `candidate_indices = (0..self.entries.len()).collect()`（288-292行）へ落ちる。
全件走査は「候補集合の上位集合」ではなく**候補集合そのもの**（母集団全体）であり、
score_one_entry は past の incremental 状態を一切参照しない純粋なエントリ単位の述語
（引数は i / plan / mode / kana_available / history / options のみ）なので、
全件走査から得られる top-k は常に「正しい」top-k と一致する。C1 は
can_reuse を false→true へ倒す方向には一切作用しない（prev_candidates を空にする
方向にしか効かない）ので、「reuse が起きたはずなのに起きない」ケースはあっても
「reuse してはいけないのに reuse してしまう」ケースは構造的に生まれない。

ゆえに命題 2 は「C1 が命題 1 を成立させているかどうか」とは独立に、**full scan が
常に正しいという既存の不変条件 1 点だけ**で証明できる。命題 1 が偽であっても
（＝ C1 が「本当は再利用できたはずの候補」を捨てる場合があっても）、その捨てた先は
必ず full scan であり、結果は変わらない。

この所見を偽にする手順: score_one_entry が `self.incremental_cache` や他の
呼び出し間状態を読んでいないことを otherwise 崩す変更（例えば candidate_indices の
順序に依存する非決定的な副作用）を注入し、full scan と reuse 経路で異なる top-k が
出る入力を実 index で 1 件構成できれば、この論証は崩れる。

命題 3: 「C2（top-k 挿入）には結果を保つ実装形が無い」
====================================================================

【裁定】部分的に壊せた。「無い」という全称否定は、研究文書が検討した 3 手法
（score 枝刈り・k 縮小・tie-break 変更）に対してのみ成立しており、探索空間の全体を
覆っていない。

ScoredEntry::Ord（scoring.rs 137-147行）は score → last_launched → lower_name →
cmp_paths の順で `then_with` を辿る。TopK::push（253-261行）は heap が満杯なら
`peek_mut()` した worst と `scored.cmp(&worst)` を**都度**呼ぶ。`c:\` では 312,208 件
のほぼ全てが score=3000・last_launched=0 で並ぶため、ほぼ全 push が lower_name の
文字列比較まで落ちる（cmp_paths まで落ちるのは lower_name も一致する重複ファイル名
の対だけ——実運用のファイルシステムでは readme.txt 等の同名ファイルが複数フォルダに
存在しうるので、この経路もゼロではない）。

研究文書が検討したのは (a) score 下限での早期棄却（発火しない）、(b) k を下げる
（機能変更として却下済み）、(c) tie-break 規則を変える（結果が変わる）の 3 つのみ。
これらとは別に、**「1 件ずつ heap へ push して都度フル比較する」というアルゴリズム
自体を変える**選択肢が探索されていない。具体的には:

- **バッチ選択（quickselect 系）**: 各 rayon タスクの結果を `BinaryHeap` へ都度
  挿入する代わりに `Vec` へ集め、タスク単位で `select_nth_unstable_by`（同じ
  `ScoredEntry::Ord` を使う）で上位 limit 件だけを一括選出する。これは
  「N 件全部を最低 1 回は見る」という不可避なコストは変えないが、heap の
  sift-up/sift-down（O(log k) 回の比較のうち大半が k=200 の深さぶん発生する）を
  避けられるので、比較回数の**定数倍**を削れる可能性がある。結果は
  `ScoredEntry::Ord` が同じである限り heap 版とビット等価になる（top-k の定義は
  全順序で決まり、実装アルゴリズムに依存しない）
- **比較キーの事前計算**（この調査タスク自身の指示文が示唆している観点）:
  `(score, last_launched)` を 1 つの i128/u128 へパックし、`lower_name` の先頭
  数バイトも同じキーへ詰め込んで、真の同点（先頭バイトまで一致）のときだけ
  文字列比較へ落とす、という多段フィルタは結果を変えない

これらは**測っていない**——「max ゲートに届くか」は不明であり、命題 5 の X2
（C1+C2 双方の効果の天井）自体が 1/3 の実行で 16,700 を超えている（下記）ことを
踏まえると、たとえアルゴリズムを変えても定数倍の削減で天井を超えられる保証は無い。
ゆえに壊せたのは「無い」という**存在命題の強さ**であって、「ゲートに届く」という
実用上の結論ではない。

⚠️ 上記 2 案はいずれも未測定・未実装であり、「試したが効かなかった」のではなく
「研究文書の 3 択に含まれていなかった」という指摘に留まる。

この所見を偽にする手順: quickselect 版 TopK を実装し、実 index で
`sorted_prefix_fast_path_changes_nothing_over_real_index` 相当の全件突き合わせ
テストを通したうえで、実運用点の max を計測する。結果が変わらずかつ max が
有意に下がらなければ、この所見は実用上は無価値だったと確定する。

命題 4: 「c:\ が重いのはクエリの字面ではなくマッチ件数が索引全件に及ぶからである」
====================================================================

【裁定】壊せなかった。

score_one_entry（scoring.rs 320-507行）にドライブレターや `c:\` という字面へ
特別に反応する分岐は無い（grep で `search.rs` / `scoring.rs` / `query_plan.rs` /
`query.rs` を確認）。パスマッチは `key.find(pq)` という汎用の部分文字列探索であり、
`pq` の中身に依存する分岐は存在しない。

数値でも支持される: baseline（実測 §1）で
`c:\users`（96,482 件）は floor（`\zzz-no-such-path\` の p50 10,353〜10,500）に対し
+1,142〜1,506（0.0118〜0.0156 µs/件）、
`c:\`（312,208 件）は floor に対し +4,984〜5,269（0.0160〜0.0169 µs/件）。
比例係数は完全な線形ではないが同じ桁（0.012〜0.017 µs/件）に収まっており、
「マッチ件数に比例する」という主張と矛盾しない。

`c:\users` と `c:\users\`（末尾セパレータの有無で字面は違うがマッチ件数はほぼ同じ）
の p50 はほぼ同じ（11,495〜11,859 対 11,661〜11,826）——字面差はコストに現れず、
マッチ件数の近さがコストの近さを説明する、という命題の予測と整合する。

⚠️ 完全な線形性は確認できていない（0.012 と 0.017 の間に約 40% の開きがある）。
これは「字面依存」ではなく、むしろ命題自身が認めている非線形要因（top-k が
200 件で頭打ちになった後の追加候補の扱い・tie-break の深さが件数に応じて変わる
こと等）で説明が付く範囲であり、字面固有の経路を示す証拠ではない。

この所見を偽にする手順: 索引を汚さずに、`c:\workspace` のような**別の根**を
`[[paths.scan]]` へ足して独立にビルドした索引で、根のクエリ（例 `c:\workspace\`）と
`c:\`（全件マッチ）のマッチ件数が同程度になる 2 つのクエリを作り、コストが
マッチ件数ではなく特定の字面（ドライブレター・特定の禁則文字等）に応じて
桁違いに変わることを実測する。

命題 5: 「max のゲート（16,700 µs）は結果を保つ変更では到達できない」
====================================================================

【裁定】壊せなかった。むしろ ablation の生ログを読むと、命題の射程より**さらに
強い**（悲観的な）事実が見つかった——結果を「捨てる」変更（X2）ですら常には
ゲートに届かない。

X2（`ablation-1070.txt` 76-112行, 380-416行, 428-463行の 3 実行）は
`top_k.push` そのものを殺し、results 列が全行 0 になる（検索結果が空になる、
製品には出せない変異）。この「もう削るものが無い」状態でも:

- 1 回目（オリジナル実行, 76行）: max = **17,335**（16,700 を超える）
- 2 回目（X2 再測 1, 380行）: max = 13,080
- 3 回目（X2 再測 2, 428行）: max = 14,412

3 回中 1 回、**結果を空にする変異ですら 16,700 を超えている**。これは
research.md 自身の点 3 が「X2 は max が 13,080〜17,335 で、1 回は 16,700 を
超えている」と書いており、この事実自体は research.md も認識している
（見落としてはいない）が、**命題 5 の言明「結果を保つ変更では到達できない」は
射程が狭すぎる**——実際には「**どんな変更でも**毎回確実に到達できるとは限らない」
という、より強い（そしてより悲観的な）主張のほうが実測と整合する。ゲートを
「3 回中 3 回」ではなく「複数回のセッションで安定して」満たすことを要求するなら、
結果を破壊してもなお失敗しうる測定を根拠に「結果を保つ変更が原理的に届かない」と
断定するのは、削るべき原因（アルゴリズムの重さ）と測定自体の性質（分散）を
混同するリスクがある。

未探索の候補（⚠️ 未測定）:
- **rayon の分割戦略をより細かくする方向**: 研究文書の C3 は粒度を「粗くする」
  方向（24 分割ではなく、より少ない分割数）だけを試して退行を確認した（下記
  命題 6 の追加所見も参照）。**より細かい方向**（`MIN_PAR_CANDIDATES` を下げる、
  または静的な chunk 分割で worker 間の作業量を均す）は試されていない。
  tail latency（max/p90）に効く可能性のある独立した軸であり、research.md の
  「候補と、それぞれを名指す測定」に挙がっていない
- 上記は「結果を保つ」設計変更の候補としては挙げられるが、X2 の実測（結果を
  空にしてさえ 1/3 の実行でゲートを割る）を踏まえると、**この軸だけで
  安定的にゲートへ届く見込みは薄い**と見るのが妥当

この所見を偽にする手順: 上記の細粒度パーティショニングを実装し、命題 3 の
検知器（実 index 全件の結果一致テスト）を通したうえで、同一機・同一セッションで
5 回以上の実運用点計測を行い、max が 5 回とも 16,700 未満になることを確認する。

壊せた点（対照row の検証範囲の抜け）:

⚠️ この所見は「C1 が zzz/\program files\ 行を退行させる」と断定するものではない

という言明は zzz の p50 1 点（10,475）だけを引用しており、**p90/max まで含めた

が、実際には**対照行が本来超えてはならないゲート自体を超えている**——却下の

既存の却下判断をむしろ補強する（research.md の却下は正しいが、根拠として
引用した数字が実際の深刻さを過小に伝えている）。

この所見を偽にする手順: \program files\ の X1 3 回・baseline 3 回を、
同一セッション内で交互に（A→X1→A→X1→A→X1 のように）測り直し、

（research.md が暗黙に前提している）主張を壊す。
