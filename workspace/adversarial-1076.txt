敵対的レビュー（issue #1076 research.md 監査）
====================================================

## A. 壊せた項目（一次証拠つき）

### A1. 命題1は文面どおりでは偽——「Plain の打鍵エッジで engine lock は instant_prefix の1個だけ」は成立しない

research.md 自身の §4 が確立した事実（auto_hide_enabled が可視中の毎フレーム engine.lock() を取る）が、
§6(a) の命題「Plain の打鍵エッジで、UI スレッドがそのフレームで取る engine lock は instant_prefix の
1 個だけである」と直接矛盾する。

一次証拠:
- `src-tauri/src/egui_shell/view.rs` 全体を grep すると `return` が 0 件（`update()` に早期 return は
  一切無い）。ゆえに `view.rs:666` の `self.controller.on_focus_changed(pre.focused, &ctx);` は
  update() が走る全フレームで無条件に実行される。
- `view.rs:666` は `search_input_ui` の changed 処理（`view.rs:830-875`）より**前**に位置する。
- `launcher_controller.rs:1233-1247` の `on_focus_changed` は 1236 行目で無条件に
  `let auto_hide = self.auto_hide_enabled();` を呼ぶ（config 値の真偽に関わらず読みそのものは必ず走る）。
- `launcher_controller.rs:730-742` の `auto_hide_enabled` は
  `s.engine.lock().unwrap().config().general.auto_hide_on_focus_lost` で engine lock を取る。

帰結: Plain の打鍵エッジが起きたフレームでは、UI スレッドは**少なくとも 2 回**（auto_hide_enabled 経由
で 1 回、その後 instant_prefix 経由でもう 1 回）engine.lock() を取る。§6(a) の文の字面（「1 個だけ」）
は偽であり、これは research.md 自身の §4 の発見と自己矛盾している。

### A2. 表 §6 の行「#6 instant_commands...(B)成立（`start_launch`→履歴記録）」は事実誤認

`execute_instant_selected`（launcher_controller.rs:489-527）の config 読み（503 行）の後に続く
`start_launch` は、Instant では**履歴を記録しない**。

一次証拠:
- `launcher_controller.rs:487`（doc コメント）「instant は履歴を記録しない（§19.6）」
- `launcher_controller.rs:317`（コード）「(o, None) // instant は履歴を記録しない（IPC 経路 parity）」
- `launcher_controller.rs:322-327`: `record_and_save` の呼び出しは
  `if matches!(outcome.status, LaunchStatus::Ok) && let Some((path, query)) = record ...` でガードされ、
  Instant では `record` が常に `None` なのでこのブロックは実行されない。

帰結: #6（launcher_controller.rs:503）の config 読みの後、そのオペレーション（Instant 起動）は
**どこでも engine.lock() を再取得しない**——`instant_prefix` と構造的に同型であり、research.md が
「(B) 成立」とした根拠（履歴記録）は存在しない。

### A3. `commands/icon.rs:17` は (B) を満たさない

`ensure_icon_cache_loaded_if_enabled`（icon.rs:7-28）内の唯一の engine 参照が config 読み（15-19 行）
であることを grep で確認済み（同ファイル中 `state.engine`/`engine.` の出現は 1 箇所のみ）。
icon キャッシュの読み書きは別の `Mutex`（`icons.lock()`）であり、engine.lock() は config を読むためだけ
に取られている。「別目的で同じ錠を既に取るものがある」という (B) の根拠は成立しない。

このコードパスは `results_view.rs:201-214` の `spawn_icon_load` が生成する worker スレッド上で走る
（UI フレームを直接ブロックしない）ため実害の性質は instant_prefix と異なるが、research.md §10 の
「`commands/` の 4 件はすべて (B) が成立し」という**未検証の断定**に対する反例である。

### A4. `commands/instant.rs:12`（`get_instant_commands`）も (B) を満たさない——しかも UI スレッド・毎打鍵

`get_instant_commands`（instant.rs:6-17）の唯一の engine 参照も config 読み（11-12 行、grep で確認）。
この関数は `run_search_with` の `QueryIntent::Instant` 分岐（launcher_controller.rs:904）から呼ばれ、
Instant プレフィックスでの検索中は**毎打鍵**同期的に UI スレッドで走る（30ms debounce 撤廃済み・
コメント「§19.5: 前方一致フィルタ。毎打鍵同期」906 行付近）。この「検索」オペレーション自体は
他の engine.lock() を一切取らない（起動は別の・後の・任意発生のイベント）。

これは research.md が全く分析していない `commands/` 内の項目であり、instant_prefix よりも高頻度
（毎打鍵）で UI スレッドをブロックしうる、より深刻な未検証の未移行候補である。

### A5. §3 の母集団「全 12 か所」は Engine 経由の間接 config 読みを取りこぼしている

タスクが警告したとおり「リテラル `config()` を狙った grep は組み立てられた読みを落とす」を実際に確認した。

- `snotra-core/src/engine.rs:163-170` `Engine::capture_folder_list_context` は
  `self.config.read().unwrap()` で `folder_mode` / `show_hidden_system` / `effective_result_limit()`
  を読む。呼び出し元 `launcher_controller.rs:818`
  （`state.engine.lock().unwrap().capture_folder_list_context()`）には**リテラル "config()" が
  一度も現れない**——grep `\.config\(\)` では検出不能。
- `snotra-core/src/engine.rs:158-161` `Engine::recent_history` も
  `self.config.read().unwrap().search.effective_recent_limit()` で config を読む。呼び出し元
  `launcher_controller.rs:939-940`（`engine.recent_history()`）も同様にリテラル一致しない。

両者とも「engine.lock() 経由でしか呼べないメソッドの内部で config を読む」という、タスクが名指しした
「間接的な読み」の実例である。§3 の 12 件（11 件の literal `.config()` + コメント1行）という数え上げは
この 2 件を含んでおらず、「母集団は grep で尽くせる」という前提が崩れている。
（ただし両呼び出し元とも UI スレッドのフレーム内 live-read ではない——818 は worker スレッド、
939-940 は Command 分岐でのみ・毎フレームではない。#1032 規範の射程内かどうかは C3 へ）

## C. ⚠️ 確信の持てない所見
