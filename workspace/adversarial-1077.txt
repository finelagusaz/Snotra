### 見つけた欠落: poll_async 経由の 3 分岐

view.rs:653 は毎フレーム無条件に呼ばれる:

`poll_async`（launcher_controller.rs:1065）は無条件に `drain_launch` を呼ぶ:

    pub(super) fn poll_async(&mut self, ctx: &egui::Context) {

        ...

`drain_launch`（:379）は `self.launching`（Enter/クリックで起動した in-flight launch）が
Some のときだけ意味を持つが、以下の 3 分岐すべてで `self.run_search()` を呼ぶ:

  - `Ok(outcome)` → `finish_launch(tag, outcome)`（:387）→ `LaunchStatus::Failed` 分岐
    （:358-373）→ `self.run_search()`（:372）
  - `Empty` かつ `elapsed >= LAUNCH_TIMEOUT`（:391-401）→ `self.run_search()`（:401）
  - `Disconnected`（:409-419）→ `self.run_search()`（:418）

`run_search()` → `run_search_with()`（:754）の `ViewKind::Results` ∧ `QueryIntent::Plain`

「同一用途（クリアするか）」の読みと**全く同じ形**である。

### 再現可能性（架空のシナリオではない）

これは config.toml をいじる必要がある P3/P4 よりもありふれた経路である:
1. Results ビューで plain クエリを検索（settled）
2. Enter で起動（`activate_or_execute` → `start_launch`）
3. 起動が失敗する（例: 壊れたショートカット・削除済みファイル）
4. 次フレーム以降、`poll_async` → `drain_launch` → `finish_launch` の `Failed` 分岐が
   `self.run_search()` を呼ぶ。**この瞬間 `indexing` が true なら**（`start_launch` から
   結果が返るまでの間に config 変更や再 kick で index build が走っていた場合）、
   `run_search_with` は `self.indexing()` を読んで結果を同期クリアする

### この読み点は research.md のどの行にも現れない

事実1 の表（研究文書 15-25 行目）は 6 行しかなく、`poll_async` も `drain_launch` も
