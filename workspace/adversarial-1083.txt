一方で、**research.md 自身が「未測定」「未解決」と書いた箇所に、今回の検証で実測値が得られた**。
その実測値は research.md の楽観的な仮定（案 A の効果は後で測ればよい）を裏切る方向に倒れている。
これは既存の主張を「壊す」というより、research.md が意図的に開けたままにした問いを埋めて、
GO 判断の前提を変える発見である。最重要点を先に書く:

  【新発見】このセッション自身が起動した rust-analyzer（後述のプロセス系譜で確認）が、
  つい先ほど（本検証実行時刻の直前）cargo check（flycheck）を実行し、その出力が
  `target/debug/` に書かれていた。`rust-analyzer.toml` には既に `[cargo] targetDir = true`
  が設定済み（2026-08-13 19:25 のコミットで導入。#1083 の提案より前、既に main にマージ済み）

  → 「target/rust-analyzer/ の有無で効果を判定する」という rust-analyzer.toml のコメント自身の
    検算手段が、**実際に測ってみると「効いていない」ことを示す**。research.md の Evidence E は
    これを「未測定」と留保していたが、実測すると留保では済まない。P5 の項目で詳述。

[新規実測・強い証拠] このセッションが起動した rust-analyzer が今まさに動いている
  検証: `Get-Process rust-analyzer` で 2 プロセスを検出:
    PID 19952: `C:\Users\Eoh\.cargo\bin\rust-analyzer.exe`（`where rust-analyzer` と同一パス）
    PID  8844: `C:\Users\Eoh\.rustup\toolchains\stable-x86_64-pc-windows-msvc\bin\rust-analyzer.exe`
  `Get-CimInstance Win32_Process` で親子関係を確認:
    PID 19952 の ParentProcessId = **1520**（= このセッションの `$CLAUDE_PID`）
    PID  8844 の ParentProcessId = 19952
  → `.cargo/bin/rust-analyzer.exe` は実バイナリと bytewise で異なり（`cmp` で確認）、
    rustup 系の薄いプロキシシムであり、実体（.rustup 配下）を子プロセスとして再exec する。
    したがって「二重起動」ではなく単一の論理インスタンス。
  → 結論: **公式 plugin の `command: "rust-analyzer"`（PATH 解決）で Claude Code が
    起動した RA が、このセッション自身の直下で今も稼働中**であり、両プロセスの起動時刻は
    本日 9:50 台——`[cargo] targetDir = true` のコミット（8/13 19:25）より確実に後。
    つまり上記の flycheck0 は「設定が反映されていない古いセッションの残骸」ではあり得ず、
    **設定コミット後に新規起動されたこのセッションの RA 自身が targetDir を無視して
    target/debug に書いた**、と解釈するのが最も自然である。
  ⚠️ Get-Process Code（VS Code）は 0 件——現時点で VS Code の RA は存在しない。
    したがって「VS Code 側の古い RA が書いた」という代替説明は今回は排除できる
    （マシン全体で rust-analyzer.exe は上記 2 プロセス＝1 系譜のみ）。
  偽にする手順: `Get-CimInstance Win32_Process -Filter "Name='rust-analyzer.exe'"` を
  再実行し ParentProcessId が変わっていないか確認。`Get-Process Code` で VS Code 不在を
  再確認。

  偽にする手順: 実際に `.lsp.json` へ `diagnostics: false` を設定した plugin を有効化し、

[新規実測・部分的に解決] 「未解決の疑問 1」— `extraKnownMarketplaces` の `directory` source の
  `path` はどう解決されるか
  検証: `Xdg` 関数を発見:
  `function Xdg(e,t){if((e.source==="directory"||e.source==="file")&&!cQi.isAbsolute(e.path)){
  let r=t??Tn(),n=Hu(r);return{...e,path:cQi.resolve(n??r,e.path)}}return e}`
  `Tn()` は `KM()?.originalCwd??gr.project.originalCwd`（起動時のカレントディレクトリ）。
  `Hu(r)` は `r` の git root を正準化して返す（`Kc(e)` でルート探索し
  `canonicalRootByRoot` マップで正準化）。
  呼び出し箇所（実際にインストール判断で使われる経路）は `Xdg(t[d].source)` で
  第 2 引数省略——常にデフォルトの `Tn()`（originalCwd）が使われる。
  → **相対パスは絶対パス必須ではなく、起動時のカレントディレクトリ（の git root）を
    基準に解決される**。research.md が「絶対パス必須なら worktree で再現しない」と
    留保していた懸念について、少なくとも「絶対パス必須」ではないことは実測で判明した。
  ⚠️ ただし「起動時のカレントディレクトリ」は `${CLAUDE_PROJECT_DIR}` と常に一致するとは
  限らない（agent worktree でセッションをどのディレクトリから起動したかに依存する）。
  したがって「worktree で再現するか」という研究の本来の懸念自体は、絶対パス問題ではなく
  **cwd 依存問題として形を変えて残る**——完全解決ではなく論点のすり替わりに近い。
  research.md の未解決欄はこの新事実で更新されるべきだが、「再現性の懸念そのもの」は消えない。
  偽にする手順: `.claude/worktrees/` 配下であえて別ディレクトリから claude を起動し、
  相対 path 指定の directory source marketplace が解決されるか実地で確認する（未実施）。
