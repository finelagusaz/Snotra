- [命題3 / research.md 28-30行「start_index_build の本体に、列 0 の } は終端の 1 つしか現れない」]
  現在は真だが、**将来偽になる形を実際に構成し、rustc でコンパイル・実行して確認した**。
  一次証拠: scratchpad の `terminator_probe.rs`（`multiline_string_probe.rs` で raw string 単体の
  コンパイル可否も別途確認済み・警告のみで成功）。

  ```rust
  pub fn start_index_build(flag: bool) -> bool {
      let s = r#"foo
  }
  bar"#;
      try_begin_index_build();
      if flag { invalidate_icon_cache(); }
      true
  }
  ```
  この関数は実際にコンパイルが通る（`rustc` 実測）。提案されている「`lines()` で
  `line == "}"` を終端にする」ロジックに通すと:
  ```
  terminated = true   ← 見つかる。だが raw string の中の "}" 行であり、本物の終端ではない
  body2.contains("try_begin_index_build") = false
  body2.contains("invalidate_icon_cache")  = false
  ```
  **「終端が見つかったこと」は「正しい終端が見つかったこと」を意味しない。** raw string /
  複数行文字列は、`lines()` ベースの単純な `line == "}"` 判定を出し抜いて**列 0 の "}" を偽装**できる。

  ただし severity には限定が要る: このケースでは truncate された結果、
  `try_begin_index_build(` と `invalidate_icon_cache(` の**両方**が母集団から欠落し、
  実際の `assert!(body.contains(...))` は 2 本とも**大声で失敗する**（indexing.rs の現行実装が
  2 つの `contains` を canary 兼必須項目として使っているため）。つまりこの具体的な壊れ方は
  **沈黙して緑にはならず、無関係な変更（文字列リテラルの追加)でテストが壊れるノイズ方向**に出る。
  #1108 が問題にしている「沈黙して緑」という一次被害ではなく、「lines() 終端判定は
  raw string / 複数行文字列の内容に脆弱である」という**設計上の脆さ**として報告する。

  この所見を偽にする手順: `terminator_probe.rs` を書き換え、raw string の代わりに
  通常の複数行文字列（`"foo\n}\nbar"` をソース中で改行を含めて記述する形）でも同じ結果になるかを
  確認する。あるいは提案実装が `blankRustNonCode`（`G-module-linkage.mjs` のような文字列/コメント
  除去の前処理）を経由するよう変更されていれば、この構成は無効化される——**実装案が
  前処理を入れるなら、この所見は解消する**。
