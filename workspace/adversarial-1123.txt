P2: icon の 2 値は単一 guard で原子的に読め、icon_cache_cap() は錠も I/O も取らない
================================================================================
判定: ✅ 壊せなかった

根拠:
- `snotra-core/src/config.rs:667-676` `icon_cache_cap()`:
  ```
  pub fn icon_cache_cap(&self) -> usize {
      let working_set = self.appearance.effective_visible_rows()
          .max(self.search.effective_result_limit())
          .max(self.search.effective_recent_limit());
      working_set.max(1).saturating_mul(ICON_CACHE_RETENTION_FACTOR)
  }
  ```
  呼ぶ 3 つの `effective_*` アクセサ（config.rs:309-316, 364-366）はいずれも

- `icon.rs:15-23` は `(show_icons, cap)` を同一 `engine.config()` guard の中で読んで
  タプルにまとめてから guard を解放しており、単一 guard 内の原子性は現状も維持されている。
  移設後も同じ形（`AppState::read_config` のクロージャが `(cfg.appearance.show_icons,
  cfg.icon_cache_cap())` を返す）を取れば原子性は変わらない。

この所見を偽にする手順:
`icon_cache_cap` および `effective_visible_rows` / `effective_result_limit` /
`effective_recent_limit` の実装を再読し、`.lock()` / `.read()` / ファイル I/O が

P3: 錠を Mutex<Engine> → RwLock<Config> の read guard へ替えても新しい deadlock も
    優先度逆転も生じない。ただし is_dir() を guard 内に入れると危険
================================================================================
判定: ✅ 壊せなかった（コア主張）／⚠️ 確信が持てない（一般化 1 点）

根拠:
- `AppState.config` と `Engine.config` は**同じ `Arc<RwLock<Config>>`**
  （`snotra-core/src/engine.rs:109,239-241,260-262`、`src-tauri/src/state.rs:24`）。
  したがって「engine 錠を外す」変更は錠の**種類を変える**のではなく、既に
  `egui_shell::read_config` が取っている**同一の** `RwLock<Config>.read()` の外側の
  `Mutex<Engine>` ラッパーを取り除くだけである。新しい lock オブジェクトは増えない。
- `AppState.config` への read/write の全地点を自分で列挙した
  （`grep -n "\.config\.(read|write)\(\)" src-tauri/src` 相当）:
  - read: `egui_shell/mod.rs:429`（`read_config`、製品コードで唯一）、
    `state.rs:106,128`（`#[cfg(test)]` 内 2 行）
  - write: `snotra-core/src/engine.rs:247`（`update_config` 内の 1 行）のみ。
    `update_config` の呼び出し元も製品コードでは `config_watcher.rs:146` の 1 か所のみ
    （`engine.rs:484,592` と `state.rs:125` はテスト、`path_query_cost.rs` は別 crate の
    `#[ignore]` ベンチ）。
  research.md §2.3 の「1 + 2 行のみ」という主張と完全に一致する。
- 錠の入れ子（§3.3）: `icon.rs:15-23` は config guard をブロックで閉じてから
  `icons.lock()` を取る（現状もこの順）。`config_watcher.rs:145-159` も
  `update_config`（engine 錠）をブロックで閉じてから `drop_icon_cache`（icon 錠）を
  別に撃つ。両方向とも入れ子は無い——実測どおり。
- `is_dir()` は `resolve_opener`/`resolve_all_openers` で**常に engine.lock() の前**
  に置かれている（`launch.rs:104,159`）。この規律を read guard 内へ持ち込まない限り、
  §3.1 が警告する 21 秒ブロックのシナリオ（writer 待ち→後続 reader も詰まる）は
  移設後も発生しない。

⚠️ 確信が持てない点: 「`std::sync::RwLock` は待ち writer が後続 reader を塞ぎうる」
という一般化は、Windows の `SRWLOCK` ベース実装の典型的挙動（writer starvation を
避けるための writer-preference）とは整合するが、Rust std の公式ドキュメントが
プラットフォームごとの公平性ポリシーを明示的に保証していないため、この 1 文だけを
独立に実測で裏取りすることはこのレビューの範囲では行っていない。既存の #1032 の
問題意識（このリスクを理由に `Mutex<Engine>` から `Arc<RwLock<Config>>` へ切り替えた）
と整合するので、大きく外れているとは考えにくいが、確信は持てない。

この所見を偽にする手順:
`grep -rn "\.config\.write\(\)\|RwLock<Config>" --include=*.rs .` を実行し、
`engine.rs:247` 以外の write サイト、または `state.rs`/`engine.rs` 以外の
`Arc<RwLock<Config>>` 定義が出れば偽になる。実測では出なかった。

- P4 の欠落自体は、issue #1123 の実装可否や P1〜P3・P6 の技術的結論を
  揺るがすものではない。あくまで「§4 の条項書き換え計画のドキュメント上の
  完全性」に対する指摘であり、計画段階で見つけておくべき粒度の欠落である。
  節 1（条項冒頭の全称文）は、実装時にほぼ確実に「生き残る・かつ強化される」
  側に分類されるはずだが、それを研究時点で明示的に列挙し損ねている。
  ADR 参照文（末尾）は、削除するか改稿するか、あるいは意図的に残すかの判断が
  computed されておらず、計画フェーズで扱いを決めるべき残タスクである。
