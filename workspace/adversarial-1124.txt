### [3] `AppState` 不在の経路は実運用で到達しない（根拠: `.manage` は `.setup` より前に走る）

- 試した反証:
  - `try_state::<AppState>()` の全呼び出し点を grep（`main.rs:440`・`window.rs:167`・`launcher_controller.rs` 複数・`search_worker.rs:51` 等）→ すべて `.setup()` クロージャの**中**、または `.setup()` クロージャ内で spawn されたスレッド（platform thread・settings monitor thread・config watcher）の中にある。`.setup()` より外側（`.plugin()` 登録コールバック自体の即時実行部分等）で `try_state` を呼ぶ箇所は無かった
  - **`tauri` クレートのソースを直接読んで機序を検算した**（`C:/Users/Eoh/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tauri-2.11.4/src/app.rs`。ただし実際に `Cargo.lock` が指すのは **2.11.5**——研究/コードコメントが引く「2.11.4」とはパッチバージョンが 1 つずれている。挙動は同一と推定されるが未検証）:
    - `Builder::manage()`（1943 行）は `self.state.set(state)` を呼ぶだけで、これは `TypeMap` への蓄積であり「実行」ではない
    - `Builder::build()`（2243 行）が `AppManager::with_handlers(..., self.state, ...)`（2251-2271 行）で **`self.state` を manager へ焼き込む**。これはランタイム生成（2338 行）・プラグイン初期化（`app.manager.initialize_plugins(handle)`、2440 行）・`setup` 呼び出し（`App::run` 内、`build()` の外）**より前**に完了する
    - `setup: Some(self.setup)` は `App` 構造体のフィールドとして保持されるだけで（2371 行）、呼ばれるのは別の場所（`run()` の内部、イベントループの `Ready` 処理中）
  - 結論: 「`.manage` は `.setup` より前に走る」という言い回しは**逐語的には不正確**——両者は main.rs の記述順で「実行される」文ではなく、`.manage()` は Builder への設定の蓄積、`.setup()` はコールバックの登録に過ぎない。**正確な機序は「`build()` が `self.state` を `AppManager` へ確定させるのが、`setup` 呼び出しよりも構造的に先である」**（`setup` は `build()` が返した `App` を使って後で `run()` が呼ぶ）。**AppHandle を手にできるのは `build()` 完了後の世界に限られる**（`.plugin()` の初期化コールバック・第二インスタンス起動時の callback・全 `try_state` 呼び出し元）ので、いずれの経路でも state は既に載っている
  - 結果: **結論（到達しない）は壊れなかった**が、コードコメント（`egui_shell/mod.rs:434`）と `ADR-config-default-fallback-references` が採用している「`.manage` は `.setup` より前に走る」という表現は、Builder メソッドを逐次実行文と誤解させる粗さがある。実質的な保証はより強い（`build()` 時点で state 確定、setup はおろかプラグイン初期化より前）
- この所見を偽にする手順: tauri 2.11.5 のソース（2.11.4 ではなく実際に `Cargo.lock` が指すバージョン）で `build()` の該当箇所を読み、`self.state` の焼き込みタイミングが変わっていないか確認する。変わっていれば結論ごと崩れる

### [4] `SPEC.md` §19.5 の表示規則は DTO を廃して純関数へ寄せても同一に保てる

- 試した反証:
  - `SPEC.md` §19.2（904 行）・§19.5（1027-1037 行）を読み、`launch.rs:234-251`（`From` impl）・`launcher_controller.rs:914-931`（Instant 枝）と突き合わせた
  - 境界条件を洗い出した:
    - `description` が空文字 → `display` を表示（`is_empty()` で判定・`Option` ではなく `String` に `#[serde(default)]`）
    - `description` が空白のみ（例 `" "`）→ `is_empty()` は `false` なので「設定されている」扱いになり `description` を表示する。これは仕様上の記述（「description が設定されている場合」）とも矛盾しない挙動で、純関数へ移しても `is_empty()` の呼び出し先を変えなければ保たれる
    - `Exec` の `args` が空白のみ → `is_empty()` は `false` なので `format!("{exe} {args}")` が使われ、末尾に意味のない空白が付く。バグではなく既存の忠実な移植対象
    - 0 件マッチ（filter が空 vec を返す）→ `unwrap_or_default()` を経て空 `Vec` → `SPEC.md` の「結果を空にする」と一致。移植後も `Vec::new()` を返せば同じ
    - `InstantAction::Legacy` 枝: **`snotra-core/src/config.rs` の `migrate_instant_legacy_commands`（911-916 行）が `Config::load()`（975 行）と `Config::default()` に相当する `default_normalized()`（945 行、`let _ = config.apply_migrations();`）の両方から必ず呼ばれる**ため、`InstantCommand.action` が `Legacy` のまま `matching_dtos` まで到達することは**構造的にあり得ない**。**これは `commands/instant.rs:78` のコメント「load 後は移行済みで到達しないが、防御的に Url 扱い」が実装コード自身によって明言している一次資料**であり、research.md の §9「Exec 種別と Legacy 種別が実運用点に 1 件も無い」という観測（実 config.toml の 2 件だけを見た結果）よりも**強い**主張が成り立つ: Legacy は「今のユーザーの config にたまたま無い」のではなく「いかなるユーザーの config でも load 後には存在しない」。ただし enum が 3 variant を持つ限り、純関数の `match` は Legacy 腕を書かないとコンパイルが通らない（未使用にはならない——unreachable であって unrepresentable ではない）
  - 結果: 壊れなかった。抜け落ちる条件は見つからなかった。**Exec 種別も実 config.toml には無い**（url 種別 2 件のみ）ため、Exec 分岐も実運用点では未踏——research.md の §7 の観察（description 有/無の 2 パターンのみ実在）と完全に一致し、私が実ファイルを読んだ結果とも一致した
- この所見を偽にする手順: `C:/Users/Eoh/AppData/Roaming/Snotra/config.toml` に Exec/Legacy 種別のエントリが増える、または SPEC.md §19.5 に上記で洗った境界条件外の規則が追記されれば、この所見は再検証が要る

## ⚠️ 確信の持てない所見

1. **tauri バージョンの不一致**: `Cargo.lock` が指す実際の tauri バージョンは **2.11.5** だが、`egui_shell/mod.rs` のコメント・`ADR-config-default-fallback-references` は「tauri 2.11.4」を根拠として引いている。私は 2.11.4 のソース（cargo registry にキャッシュされていたもの）で機序を検算した。2.11.5 で `Builder::build()` の `self.state` 焼き込みタイミングが変わっていないかは確認していない（両バージョンとも registry にキャッシュされていたので、2.11.5 側の該当箇所も読めば数分で埋まる差分だが、今回は時間の都合で 2.11.4 側だけを読んだ）。
2. **命題 3 の根拠の言い回しについて**: 「`.manage` は `.setup` より前に走る」という表現自体は、コードコメント（`egui_shell/mod.rs:434`）や 2 つの ADR に**複数箇所**で使われている定型句である。結論は正しいと確認できたが、この言い回しを字面通り読むと「main.rs の記述順で逐次実行される」と誤解しうる。より正確には「`Builder::build()` が `self.state` を `AppManager` へ焼き込むのが `setup` 呼び出しより構造的に先である」。これが issue #1124 の実装や plan に影響するかは分からない（直接は関係ないが、fallback を書く際にこの規範を再度引用するなら、より正確な言い回しへ更新する余地がある）。
3. **行番号の軽微なずれ**: research.md が引用する行番号のうち、`launcher_controller.rs:917-930`（DTO→SearchResult 組み直し）は実測では 914（呼び出し開始）〜931（`.collect()`）に相当し、923-927 が実際の description/display 分岐である。ずれは数行程度で実害は無いが、「917-930」という区間指定は分岐そのものというより `.unwrap_or_default().into_iter()` を含む前後の行まで含んでいる。テスト行「315-352」も実測は「314-352」相当（1 行のずれ）。どちらも本質的な誤りではないが、以後 plan で引用する際は再確認を勧める。
