# 敵対的調査 — #1129 research.md

## 壊せた項目

無し。全 7 争点および research.md の全主張について反証を試みたが、いずれも一次証拠と一致し、破壊できなかった。

## 壊せなかった項目

### 争点 1: `AppState { .. }` 構築点は 3 件で全部か／取りこぼしはコンパイラが露見させるか

- `grep -n "AppState {" .`（フィルタ無し、`--exclude-dir=target,.git` のみ）を実行。ヒットは
  `main.rs:240`、`commands/system.rs:44`、`state.rs:110` の 3 件のみ（他は `.superpowers/sdd/*.diff`・
  `docs/superpowers/plans/*.md` という**過去の計画/レビュー diff**であり、現行コードではない）。
- `[lib]` ターゲットが無く（`Cargo.toml` に `[lib]` 節なし、`src-tauri/src/lib.rs` 不在）、`[[bin]]` も
  明示宣言が無い（Cargo のデフォルト `src/main.rs` バイナリのみ）ので、外部 crate から `AppState` を
  構築する経路も存在しない。
- 取りこぼしがあってもコンパイラが検出するという主張は、`config` を private にする変更が
  「他モジュールでの構造体リテラルはコンパイル不能」という Rust の可視性規則（争点 4 参照）に
  直接由来しており、経験的にも `pub(crate) fn new` 必須化＋呼び出し元置換という AGENTS.md の
  既定パターンと一致する。**壊せなかった**。

### 争点 2: `Engine::config_handle()` の呼び出し点はその 3 件の構築だけか

- `grep -rn "config_handle" --include=*.rs .` と `grep -rn "config_handle" .`（フィルタ無し、
  node_modules/target/.git 除外）の両方を実行し、結果が一致することを確認。
- 定義（`snotra-core/src/engine.rs:267`）を除く呼びは `main.rs:242`／`commands/system.rs:45`／
  `state.rs:111` の 3 件のみ。残りは doc コメント内の言及（`state.rs:20`・`main.rs:241` コメント・
  `snotra-core/CLAUDE.md:192`・`RETROSPECTIVE.md:15`・`docs/adr/ADR-config-read-without-exception.md:46`）。
  **壊せなかった**。

### 争点 3: `src-tauri` は bin crate で `AppState` は外部 crate から不可視か

- workspace 直下 `Cargo.toml` を読み、`members` は `snotra-core` / `snotra-egui-runtime` / `src-tauri` /
  `snotra-settings` の 4 crate のみ。`src-tauri/Cargo.toml` に `[lib]`・`[[bin]]`・`[[test]]`・
  `[[bench]]`・`[[example]]` のいずれも無いことを `grep` で確認（デフォルトの `src/main.rs` バイナリ
  ターゲットのみ）。他 3 crate のソース全文検索で `AppState` の出現は 0 件（`grep -rl "AppState" .`
  の結果に `snotra-core`・`snotra-egui-runtime`・`snotra-settings` 配下は 1 件も無い）。**壊せなかった**。

### 争点 4: `config` フィールドだけを private にすれば外から綴れなくなるか（抜け道の有無）

- `AppState` に `#[derive(...)]` は無い（`grep -n "derive\|Default" state.rs` は 0 件）。serde 実装も
  手書き `impl Serialize/Deserialize` も無い。
- `tauri::State` / `Manager::state()` / `try_state()` の呼び出し点（27 件、`main.rs`・`indexing.rs`・
  `platform/tray.rs`・`egui_shell/*`・`commands/*`）はすべて型パラメータ `AppState` を通した不透明な
  取得であり、`.config` へのドット参照を伴う箇所は無い（`state\.config\|AppState::` の全文検索で
  ヒットするのは `commands/system.rs` / `main.rs` / `state.rs` 自身の構築リテラルと doc コメント内の
  `AppState::read_config` 言及のみ）。
- `src-tauri/tests/` ディレクトリ・ベンチ・examples は存在しない（`[[test]]` 等が Cargo.toml に無く、
  ディレクトリ自体も無い）。build script（`build.rs`）は `AppState` に触れない（tauri codegen の
  sidecar プレースホルダ生成のみ）。
- `macro_rules!` で `AppState` を組む箇所は無い（同名の grep で該当なし）。
- ドキュメントコードフェンス（doctest 化しうる ```` ``` ```` ブロック）は `src-tauri/src/icon.rs` の
  1 件のみで `AppState` と無関係。加えて lib ターゲットが無いので doctest 自体が走らない。
- **壊せなかった。** ただし `#[cfg(test)] mod tests`（`state.rs` 自身の子モジュール）は Rust の可視性
  規則上、私有フィールドでも定義モジュールの子孫として引き続き綴れる——これは research.md 自身が
  「変更後に残る残余」の 2 番目として明記しており、隠された抜け道ではなく申告済みの事実である。

### 争点 5: 変更後も `engine.lock().unwrap().config_handle().read()` は通るか

- `snotra-core/src/engine.rs:267` の `pub fn config_handle(&self) -> Arc<RwLock<Config>>` は
  `#[cfg(test)]` で閉じられておらず、可視性は `pub`。`AppState.config` の可視性変更は
  `Engine::config_handle` に一切触れないため、この経路は構造的に不変。**壊せなかった**。

### 争点 6: 検知器を置かない判断は issue 自身の順序から導かれるか

- `gh issue view 1129` で本文を実際に取得し照合した。「判断の順序（提案）」節の文言は research.md の
  引用と一致する：「1. まず `AppState.config` を private にできるかを測る（構築点の列挙。通るなら
  検査は不要になる） 2. 通らない場合にだけ、検査の是非を評価する。そのときも発火しうるかを先に
  測る」。issue 本文はさらに「反対材料」として private 化を「構造で塞げるなら検査は要らない」と
  明示しており、research.md の測定 1 が「できる」に決着した時点で測定 2 へ進まない判断は issue の
  文面から直接導出できる。**壊せなかった**（⚠️ 「追加の測定を要さない」という結論自体は issue の
  手続き解釈であり経験的反証の対象ではない——このメタ性質は後述）。
- 誤検出リスクの実測値: issue 本文は「`Engine` 自身が `self.config.read()` を **7 か所**で正当に
  書いており」と述べるが、research.md は「実測 9 行——`engine.rs:150,161,166,221,226,247,297,315`
  の read と 254 の write」としている。`grep -n "self\.config\.(read|write)\(" snotra-core/src/engine.rs`
  で実測すると、まさにこの 8 read + 1 write = 9 行がヒットする。**数字は矛盾していない**——
  issue の「7 か所」は production の read のみ（247 行目は `#[cfg(test)]` の `config()` アクセサ内、
  254 行目は write）を数えており、research.md はそれとは別に「read 8 + write 1 = 9」という
  粒度の異なる（より生の）数え方を明示しているため、同じ grep 結果に対する異なる集計であって
  食い違いではない。

### 争点 7: 文書の写しの母集団は生きた層 2 件＋凍結 ADR 2 件で全部か

- フィルタ無しの `grep -rn "AppState\.config\|state\.config\.read\|AppState::read_config" .`
  （node_modules/target/.git/.superpowers 除外）を実施。ヒットしたファイルは research.md が
  列挙したもの（`state.rs:47,150`／`CLAUDE.md:57`／`ADR-config-read-exception-discriminator.md:25,32`／
  `ADR-config-read-without-exception.md:20,45`／`commands/instant.rs:10`／
  `launcher_controller.rs:731`／`egui_shell/mod.rs:419,422`／`snotra-core/src/engine.rs:240`）と
  完全に一致し、他の未申告ファイルは 0 件だった。
  - `state.rs:150` は「`AppState.config` と `Engine` は同じ Arc を共有する」という identity の主張で
    あり、可視性とは独立の事実なので private 化で偽にならない——research.md の「参照のみで更新
    不要」分類と整合する。
  - `ADR-config-read-without-exception.md:20` の「案 2」節は却下した過去案の記述で、現状主張ではない
    ため偽にならない（research.md は明示的に触れていないが、性質上「要更新」に含める必要はない）。
- `docs/adr/ADR-adr-frozen-history.md` を全文読み、「ADR は凍結された歴史として編集しない」という
  運用規約と、それを ADR 自身に適用した先例（同 ADR が自ら「同 ADR は凍結ゆえ編集しない」と書き、
  #1123 も同じ扱いをした）を確認した。ADR を凍結扱いにする判断は本 issue 固有ではなく既存の
  リポジトリ規約であり、research.md の適用は妥当。**壊せなかった**。

### 測定環境そのものを疑う指示への対応（フィルタ差・cfg 分岐・lint 設定）

- **grep フィルタの有無**: `config_handle` と `AppState.config`/`state.config`/`AppState::read_config`
  のいずれについても、`--include=*.rs` あり/なし・`--exclude-dir` の範囲を変えた複数回の実行で
  結果が一致することを確認した（差分なし）。research.md の「フィルタ無しでも同じ」という主張は
  実測どおりだった。
- **cfg 条件**: `windows` ターゲット限定 (`[target.'cfg(windows)'.dependencies]`) は Win32 API 依存の
  話であり `AppState` 構造体定義・フィールド可視性には無関係（`state.rs` に `cfg(windows)` は無い）。
  `#[cfg(test)]` の分岐は `state.rs` 自身の `mod tests` と `commands/system.rs` の `mod tests` の
  双方で確認済みで、research.md の記述と一致する。
- **clippy.toml / disallowed-methods**: `src-tauri/clippy.toml` を全文読んだが、禁止リストは
  `egui::Context::set_visuals` 系 7 メソッドと `Engine::sorted_by_path` の計測用アクセサのみで、
  `config` フィールドや `AppState` には一切触れていない。本変更が `clippy.toml` を更新する必要は
  無い（research.md も触れていないが、これは沈黙ではなく該当が無いことを確認した上での不要判定）。
- **`cargo check -p snotra`** をベースラインとして実行し、`Finished` で正常終了することを確認した
  （現在の HEAD が clean にビルドできることの直接確認。読み取りのみ、ソース改変なし）。

## 私が新たに見つけた争点

- ⚠️ **issue 本文の「7 か所」と research.md の「9 行」は数字が違って見えるが、対象範囲が異なる
  だけで矛盾ではない**（上記争点 6 参照）。ただし research.md 自身はこの数字の差を issue 本文と
  突き合わせて明示的に断っていない。実装 PR の本文で `engine.rs` の誤検出リスクに触れる際、
  「9 行」とだけ書くと issue の「7 か所」と照合した読者が食い違いを疑う可能性がある——一次証拠は
  一致しているので実害は無いが、粒度の違いを一言添えるとよい（**低リスクの体裁上の指摘**）。
- ⚠️ **`npm run governance:check` を実際には走らせていない**（ファイル非改変の制約下では意味のある
  差分が無く、実行しても現状は無変更で green になるだけなので省略した）。実装後の検証チェック
  リストとしては `AGENTS.md`「ガバナンス文書を変更、または `.rs` のコメントの見出し参照を変更」
  トリガーに該当するため、`state.rs` の doc・`src-tauri/CLAUDE.md:57` を実際に書き換えた後は
  `governance:check` を通す必要がある（research.md の想定どおりだが、私はこれを検証していない
  という限界を明記する）。
- ⚠️ **フォールトインジェクションによる実測（`未解決の疑問」に research.md 自身が記載済み）は
  私も実施していない**——`config` フィールドを実際に private にしてエラーコード・エラー箇所数を
  見る実験はファイル改変を要するため、今回の敵対的レビューの権限（読み取り専用）の範囲外である。
  この空白は research.md が自覚的に「未解決」と明記しているので隠れた欠落ではない。
