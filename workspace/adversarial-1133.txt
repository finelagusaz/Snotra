--- 命題5: 「expand_envの意味論はアイコンキーとして使える文字列を返す」（F3）---
判定: 偽にできなかった（実測で補強）

一次証拠:
`src-tauri/src/commands/launch.rs:226-251` を読んだ。`ExpandEnvironmentStringsW`
（Win32 API）を2回呼び出し（サイズ取得→書き込み）、失敗時（`needed == 0` /
`written == 0`）は入力をそのまま返す（パニックしない・空文字列を返さない）。

**実測**（`[Environment]::ExpandEnvironmentVariables` は同じ Win32 API を
P/Invoke するため直接の代理測定として有効）:
```
[Environment]::ExpandEnvironmentVariables('%THIS_VAR_DOES_NOT_EXIST_XYZ%/foo.exe')
  → "%THIS_VAR_DOES_NOT_EXIST_XYZ%/foo.exe"   （未定義変数は展開されず素通り）
[Environment]::ExpandEnvironmentVariables('%LOCALAPPDATA%/foo.exe')
  → "C:\Users\Eoh\AppData\Local/foo.exe"      （定義済みは正しく展開）
[Environment]::ExpandEnvironmentVariables('100% done')
  → "100% done"                                （孤立した % はそのまま）
```
いずれのケースでも panic・空文字列・例外は起きず、**常に「文字列」として
アイコンキーに使える値を返す**（未定義変数を含む場合は単に SHGetFileInfoW が
その文字列で失敗するだけで、アイコン抽出パイプライン自体は #692 の
transient/permanent 分岐で安全に扱う）。F3 の結論「exe は同じ展開を通すべき」
の技術的前提（=展開結果が常に使える文字列である）は成立している。

偽にする手順: 上記コマンドを実行し出力を確認する（実施済み・上記出力）。

--- 既定 config（Config::default()）---
`snotra-core/src/config.rs:621-636` を読んだ。既定の `instant_commands` も
2件（"g" / "gh"）で、**両方とも `InstantAction::Url`**。**exec 型は既定にも0件。**

*** これは research.md の設計候補の優先順位づけに影響する重要な事実である ***
研究文書の決定は「exec 種別は exe のアイコンを出す（改善）／URL 種別・Legacy
種別は抽出しない（無駄削減）」という2枚看板だが、**実測した実 config・既定
config のどちらにも exec 型 instant コマンドが1件も存在しない**。つまり
「Explicit(exe) による本物のアイコン抽出」という改善は、**この利用者にも
既定ユーザーにも現状は何も届かない**（Exec 型を手で設定した利用者にしか
効果が無い）。一方「Skip による無駄仕事削減」は実 config・既定 config の
**両方**に直接効く（"g" は description 非空で日本語文字列がキーになり、
"gh" は description 空で `https://github.com/search?q={query}` という
`{query}` 未展開のURL文字列がキーになる——どちらも SHGetFileInfoW への
入力として無意味な文字列であり、現状ずっと再試行され続けている）。
research.md はこの非対称（Skip は実運用点に届くが Explicit は届かない）を
一言も述べていない。案 C の設計判断自体を覆すものではないが、
**優先度・検証労力の配分（Exec 側は実機で誰も踏まない経路になりうる）**
に関わる情報として issue/plan へ持ち越す価値がある。

--- icons.bin の実物 ---
`%APPDATA%\Snotra\icons.bin` は**存在しない**（読み取りのみ試行・書き換えなし）。
これは上記の config 実測と整合する——"g"/"gh" のどちらの path も実在ファイルを
指さない文字列であり、`SHGetFileInfoW` は常に失敗する。`commands/icon.rs` の
`load_icon_pngs`（Step 3・行103-110）は **`Ok(png) => c.insert(...)` のときだけ
キャッシュへ挿入し、`Err` は `failures` マップに理由を残すだけでキャッシュには
入らない**——つまり**現状のコードでも、失敗し続ける URL/description 文字列が
`icons.bin` へキーとして永続化されることは無い**（挿入は成功時のみ）。
これは issue #1133 の「⚠ 未確認3」（instant 行の表示文字列がキーとして
永続化される懸念）に対する部分的な反証材料になる——**description/URL文字列が
キーとして書き込まれる条件は「抽出が成功すること」であり、通常のURL文字列
では原理的に起こらない**。ただし exec 型（args込みの `"exe args"` 文字列等）
が実在しない exe を指す場合は同様に失敗するが、実在する exe を指す場合は
研究文書の issue が指摘した通り成功し、`"exe args"` のような文字列がキーとして
永続化されうる（これは案Aでも案Cでも起こり得た経路で、案Cの Explicit(exe) は
むしろこれを args 抜きの exe 単体キーへ正規化するので改善方向である）。

- `cargo check -p snotra-core` は実施しなかった（必須ではないため。命題2の
  E0063 個数一致は未検算のまま「テキスト上の確認」に留まる）。
- F4・F6・F8（未確認1「別文字を打つたびに0から積み直す」等）は指定5命題の

その他の⚠所見（5命題外・低〜中確信度）
===============================================================================

⚠ IconSource 設計候補（`enum IconSource { FromPath, Skip, Explicit(String) }`）は
derive 注釈を持たないスケッチだが、実装時には少なくとも以下が要る:
1. `RowsSnapshot::matches`（`results_view.rs:59`）が `cur_rows.as_slice() == rows`
   で `SearchResult` の `PartialEq` に依存しており、`SearchResult` は `Eq` も
   derive している（`ui_types.rs:14`）。`icon: IconSource` を足すなら `IconSource`
   も `PartialEq, Eq` を持たないと `SearchResult` の derive が壊れる（compile error）。
2. `SearchResult` は `Serialize, Deserialize` も derive している（消費者はいない
   が derive 自体は生きている・F7 参照）。`IconSource` がこれらを持たなければ
   同様に compile error になる。
これは「設計候補」節の未完成さの指摘であり、F1〜F9 のどの事実も偽にしない
（plan 化の際に埋まるべき詳細）。確信度: 中（コンパイラで検算していない）。
