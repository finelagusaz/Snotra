[壊-2] 設計上の分岐 (B)（`.rs` の Edit まで発火対象を広げる）の「判定つきの subprocess は
  頻度が下がる」という主張は片面しか見ていない。
  `checkModuleIndex` は crate 単位の**全ファイル**の順方向・逆方向照合であり、「今編集した 1 ファイル」
  だけを見る述語ではない。ゆえに、あるクレートに未解消の索引債務（findings > 0）が 1 件でも残っている間、
  Edit まで発火対象を広げると**そのクレート内の無関係な別ファイルへの Edit のたびに同じ reminder が
  繰り返し出る**——「実際に欠けているときだけ鳴るので頻度が下がる」という書き方は、Write 単発の
  通知と比べてむしろ「同じ未解決債務について何度も鳴る」形の頻度増加をカバーしていない。
  今日の母集団は 0 findings（下記で実測）なので今この瞬間には出ないが、issue 自身のデータ
  （45 日で 9 回赤）が示すとおり債務が生じる窓は現実に起きており、その窓の**間**は Edit 広げにより
  通知が「1 回」から「その crate へのすべての Edit 回数」へ増える。これは設計判断であり
  additional context として計画に書く価値がある（reminder だから実害は「無視されるかどうか」の
  水準ではあるが、慣れ（`partial-automation-habituates`）を早める方向へ働く）。
  偽にする手順（この機体で 0 findings であることの確認・債務が今は無いことの検算）:
    cd C:/workspace/Snotra && node -e "import('./scripts/governance/lib.mjs').then(async l=>{const {checkModuleIndex}=await import('./scripts/governance/checks/G-module-index.mjs');console.log(checkModuleIndex(l.makeSnapshot(process.cwd())).length)})"

  ソースを読むと checkReferences は「対象文書に書かれた参照の実在」を判定するのであって、

  編集対象ファイルを指す壊れた参照」は、今回の編集それ自体では発生しえない——発生させるとしたら
  リネーム／削除で、それは元から Edit|Write の外である。壊せなかった。
