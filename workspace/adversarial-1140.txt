争点1: 「逆引き索引の構築は約190msである」
--------------------------------------------
【壊せた】
proto-dependents.mjs の `makeSnapshot(ROOT, files)` はバグである。lib.mjs の実際の
`makeSnapshot(root)` は引数を1つしか取らない（`scripts/governance/lib.mjs:43`）。
第2引数 `files`（`git ls-files` の結果）は JS が黙って無視し、makeSnapshot は自前で
`fs.readdirSync` を再帰する。つまり計測区間の中で `git ls-files` サブプロセスを起動している
のに、その結果は一切使われていない——**測っているつもりのものを測っていない**、まさに
sed のバックスラッシュと同型の事故である。

実測（probe-timing.mjs、フェーズ分解）:
  git ls-files 単体: 29.8 ms（無駄）
  makeSnapshot(fs walk) 単体: 13.6 ms
  走査+索引構築 単体: 142.4 ms
  合計（git込み・researchmd の計測方法）: 187.2 ms ≒ 「約190ms」に一致
  合計（git抜き・実際に使われる処理だけ）: 156.1 ms
→ 190ms のうち約 30ms（16%）は不要な計測混入である。

さらに重大なのは「hook が実際に走る条件（node の起動費用を含む）」への回答:
proto-dependents.mjs をプロセスとして5回実行し、壁時計で測った（date +%s%N 挟み込み）。
  wall: 384 / 380 / 409 / 391 / 395 ms（内部計測は 195/194/221/207/200 ms）
  bare `node -e "1"` の起動費用単体: 120 / 127 / 122 ms（3回）
  `node -e` で lib.mjs を import するだけ: 113 / 119 / 140 ms
→ 壁時計はほぼ内部計測の2倍。差分（約190ms）は node プロセス起動費用にほぼ一致する。
researchmd の「190ms」は t0 を `process.hrtime.bigint()` で node 起動**後**に取っている
ため、node 起動費用を最初から除外した数字であり、issue 側の疑問5「node の起動費用を含む」
という条件には答えていない。

この事実は未解決の疑問2（判定をどこに置くか）と直結する重大な論点である:
- 案(i) hook が lib.mjs を import する場合: post-edit.mjs は既にそのプロセス内で走っている
  ので、真の追加費用は「git抜きの156ms」に近い（今より約16%軽くできる余地がある、との
  示唆にもなる）
- 案(ii) `node scripts/<新スクリプト>` を subprocess で呼ぶ場合: 既存の hook プロセスの
  外にもう1回 node を起動することになり、追加費用は 190ms 前後 + 新規 node 起動 120ms強
  ≒ 310ms超になる——researchmd が書く「190ms」の実に1.6倍
research.md はこの分岐を「未解決の疑問2」で扱ってはいるが、「技術的制約（実測）」節の
190ms という数字自体が「案によって2倍近く変わりうる」ことを注記せずに単一の値として
提示しているため、読者が「190msが上限」と誤読するリスクがある。

【壊せなかった】
- cold/warm の区別（Windows ファイル I/O の効き）は、リブートなしでは再現できなかった。
  5回連続実行のばらつきは 194〜221ms（標準偏差約10ms・5%程度）で、明確な cold/warm 差は
  観測できなかった。**この点は未検証のまま残す**（⚠️、後述）。
- 「約190ms」という数字自体（内部計測・git込みの定義で）は3回とも一貫して再現でき、
  研究文書の実測記録としては正確である。壊れているのは数字ではなく「この数字が何を
  代表しているか」の説明である。

偽にする手順: `node C:/workspace/Snotra/scripts/governance/lib.mjs` の `export function
makeSnapshot(root)` のシグネチャが変わり第2引数 `files` を実際に使うようになれば、
この指摘（git ls-files の呼び出しが無駄）は成り立たなくなる。壁時計と内部計測の比較は
`date +%s%N` を挟んで proto-dependents.mjs を再実行すれば誰でも再現できる。


争点2: 「依存を持つ節は116個・中央1件・最大19件」
--------------------------------------------
【壊せた（小さいが実在する）】
前方一致による過大カウントは実在する。probe-ambiguity.mjs で、索引の鍵121個のうち
「同一対象文書内で複数節に前方一致する」鍵を数えたところ 3個 見つかった:
  - CLAUDE.md 鍵="フック" → 2節（「フック（.claude/settings.json）」と
    「フックの改修者向けの実装契約…」）にマッチ
  - .claude/skills/start-issue/SKILL.md 鍵="出力" → 2節にマッチ
  - .claude/skills/implement/SKILL.md 鍵="出力" → 2節にマッチ
これらは、実際には1箇所の節だけを指しているはずの参照が、短いラベルゆえに同一文書内の
別の節（たまたま同じ接頭辞を持つ）にも当たってしまい、その節を触ってもいないのに
「依存が動いた」と誤って報告されうる形である。ただし規模は小さい（121鍵中3鍵=2.5%）。
これを除いても「116節・中央1・最大19」という headline の分布はほぼ動かない
（最大の19件は AGENTS.md「条件別チェック」で、これは曖昧マッチではなく19本の別々の
参照が同じ1節を正しく指している——正当な多重依存であり過大カウントではない）。

【壊せなかった】
- 前方一致という設計そのものは実装のバグではない——`scripts/governance/checks/
  G-heading-refs.mjs:61` の実チェック本体も全く同じ方向（`anchors.some(a =>
  a.startsWith(normAnchor(label)))`）で前方一致しており、プロトタイプは実物の挙動を
  正しく模倣している。researchmd の注記「参照は見出しの接頭辞を書きうる」もこの実装
  コメントと一致する。
- 267件の参照・251文書・121鍵という母集団の数え方は、実際の `governance-check.mjs` の
  出力（`allRefDocs = [...refDocs, ...refSourceDocs, ...refCommentDocs]`）と完全一致
  しており、ここに漏れ・過大は見つからなかった。
- normAnchor による正規化の取りこぼし（issue側の懸念）は、現行の実チェックが「全検査
  passed」で通っている（267件全てが着地している）ことから、少なくとも**今日時点では**
  未着地の参照は0件であり、正規化起因の false negative を裏付ける具体例は見つからな
  かった。

⚠️（確信が持てない所見）: proto の節切り出し（独自 ANCHOR_LINE）は open question 6 が
自認するとおり `sectionOf` の**フェンスマスクを通していない**。実測では `collectAnchors`

争点3: 「発火は全hunkで46%、純追記を外すと25%」
--------------------------------------------
【壊せた】
これは今回の調査で最も明確に壊せた主張である。researchmd 自身が「近似: 節の境界と索引は
現在の木のもの」と断っているが、この近似は**未来にしか存在しない参照を過去の発火として
数える**方向にしか働かない片側バイアスであり、実測すると無視できない量だった。

手順: 直近80本のうち「触られた節が現在の索引で依存を持つ」とされたコミットについて、
各ヒット参照（doc:line）が**そのコミット時点で実際にそのファイルに存在していたか**を
`git show <sha>:<doc>` で当時のファイル内容を取得し、該当行の文字列が含まれるかで検算した
（probe-firing-corrected.mjs）。

結果:
  生の発火（現在木の索引をそのまま適用・researchmd と同じ手法）: 37/80 = 46%（再現一致）
  補正後の発火（当時ファイルに実在した参照だけを数える）: 33/80 = 41%
  報告件数合計: 生309件 → 補正後211件（32%減）
  「生では発火扱いだが、補正すると依存ヒットが0件になる」＝完全に未来汚染由来だった
  コミットが4件（d11dcc30・8182cb5f・925ef3ad・a14ff768。いずれも2026-08-09〜08-12、
  すなわち80本の窓のうち「古い方」に偏っている）。

さらに、古い方10本だけを抜き出すと汚染はもっと激しい（probe-forward-leak.mjs）:
  f1827b08（2026-08-09。PERFORMANCE.md「設定の読みをengine lockの外へ出す」節を触った
  コミット）は、そのヒット2件（docs/architecture.md:231・src-tauri/CLAUDE.md:57）が
  両方とも、当時それらのファイルにまだ存在しなかった記述（#1123・#1129 等、明らかに
  後日追記された内容）だった——このコミット単体の「発火」判定は100%捏造である。
  a1bcaf2a・6ccacd01 も同じ節への19ヒット中10件が未来汚染だったが、残り9件は当時から
  実在したので発火判定そのものは（件数は誇張されつつも）真だった。

私が使った「当時実在したか」の判定は**寛容側**（同一文言がファイルのどこかに含まれて
いれば「実在」とみなす。正確な行番号・正準形での一致までは要求していない）ため、
この32%/5ptという数字は控えめな見積もりである可能性が高い——真の汚染はこれより大きい
可能性がある。

【壊せなかった】
- 「46%」という headline 自体（全hunk・現在木近似という定義のまま）は正確に再現できた。
  補正後も41%であり、劇的な逆転（例えば「実は10%だった」）は無かった——汚染は実在し
  無視できないが、「発火が起きること自体は稀ではない」という定性的な結論までは覆せ
  なかった。
- 「AGENTS.md『条件別チェック』1節が結果を支配しているか」という疑いは、支配的では
  なかった。この1節を除外して再計算すると:
    全hunk: 46%(37/80) → 43%(34/80)。純追記除外: 25%(20/80) → 20%(16/80)
  発火率への影響は数ポイントに留まる。ただし**件数**（「1回あたりの件数」列の分布）
  への影響は大きい: 全hunk合計309→176件（43%減）、純追記除外合計233→119件（49%減）。
  つまり「発火するかどうか」はこの1節に支配されていないが、「発火したときの件数の
  多さ」はこの1節でほぼ半減する——researchmd の表の「中央3/最大41」「中央10/最大31」
  という**件数分布**はこの1節に強く依存しており、この依存を研究文書は明記していない。

⚠️（確信が持てない所見）: 「純粋な追記を外す」変種（25%側）についても forward-looking
汚染を補正する計算は今回実施していない。全hunk側で41%（-5pt, 相対-11%）だったことから
類推すると、25%側も同程度かやや大きい相対的下振れ（20%前後）になると予想するが、実測
していない。

偽にする手順: probe-firing-corrected.mjs に `DELETIONS_ONLY` 分岐を足して同じ補正を
純追記除外版にも適用すれば、この⚠️は解消できる。


争点4: 「.claude/hooks/ は scripts/ を1つも import していない」
--------------------------------------------
【壊せなかった】
`.claude/hooks/` 配下の全6ファイル（post-edit.mjs / pre-bash.mjs / lsp-config.mjs と
その3本のテストファイル）の import 文を全数grepしたが、`scripts/` を参照する import は
1件も無かった（`node:` 標準モジュールと `vitest` と相互 import のみ）。

import 以外の依存経路も検めた:
- subprocess: `post-edit.mjs` の `spawnSync` は `buildCommand()` が組む
  `cargo fmt/clippy/test/check` と `node .../vitest.mjs run <target>`（hook-selftest /
  githooks-selftest）だけで、`scripts/` 配下のファイルを起動する分岐は存在しない
  （switch文の case を全数確認）。`pre-bash.mjs` の spawnSync は `git` コマンドのみ。
- 設定・JSON経由: `lsp-config.mjs` が読む JSON は `.lsp.json` / `plugin.json` /
  `marketplace.json` のみで、`scripts/` が生成する成果物（governance-manifest 等）への
  依存は無い。
- 文字列としての `scripts/` 参照は `lsp-config.mjs` のコメント2箇所と `post-edit.test.
  mjs` のテストケース内文字列のみで、いずれも「散文でscripts/governance-check.mjsに
  言及している」だけであり、実行時の依存関係を作っていない。

この主張は全称否定（「1つも無い」）であり、AGENTS.md「検証の作法」が要求する「不在の
観測1つで確定させない」を意識して import・subprocess・設定読み込み・文字列参照の4経路
を独立に検めたが、いずれからも反証は出なかった。

偽にする手順: `.claude/hooks/*.mjs` に `from "../../scripts/..."` または
`scripts/governance-check.mjs` を起動する `spawnSync` が新たに追加されれば、この主張は
その時点で偽になる（つまり本件の新機能実装が案(i)を選んだ瞬間に、この記述は書き換えが
要る）。


争点5: 「発火するのは.mdの編集だけである」
--------------------------------------------
【壊せなかった】
`resolveRefTarget`（`scripts/governance/lib.mjs:379`）の実装を読んだ:
```
if (/^\/[a-z0-9-]+$/.test(target)) {
  const p = `.claude/skills/${target.slice(1)}/SKILL.md`;   // → 常に .md
  return snapshot.files.includes(p) ? p : null;
}
if (!target.endsWith(".md")) return null;                    // → .md 以外は即 null
```
正準形 `` `<対象>`「<見出し>」`` の対象は必ず `.md` に着地するようハードコードされて
おり、`.rs`・`.mjs`・`.ps1` 等がヒートリファレンスの**対象（target）**になることは
構造的にありえない（`headingRefSourceDocs`/`headingRefCommentDocs` が返すのは「参照
**元**になりうる文書」であって「参照先になりうる文書」ではない——この非対称性は
lib.mjs のコメントでも明示されている）。同じ `resolveRefTarget` は
`G-near-heading-refs.mjs` からも共有されており、抜け道となる別実装は見当たらなかった。

したがって「節の中身が変わった」を検出する新機能は、変更対象ドキュメントが `.md`
（または `.claude/skills/*/SKILL.md`、これも拡張子は `.md`）でない限り、そもそも
その変更が依存索引のキー（対象パス）に一致しえない——推論に穴は見つからなかった。

⚠️（確信が持てない所見・別角度からの弱い指摘）: この争点は「参照の**対象**が変わる
条件」を扱っているが、「参照**そのもの**（正準形の記述）が変わる条件」は別問題として
残る。たとえば `.rs` のコメント中の正準形参照が編集で書き換えられた場合（対象は変えず
ラベルだけ変える等）、それは対象文書の中身の変化ではないので本件の「節の中身が変わった
報告」の対象外だが、これは researchmd の主張自体は壊さない——単に「.md以外の編集が
本件と無関係である」ことの確認が、争点5が書いている理由（対象は必ず.mdに着地する）
だけでなく、もう一段（参照元の変更は"対象の中身"ではない）でも成立する、という
補強的な観察に留まる。壊す材料にはならなかった。

偽にする手順: `resolveRefTarget` に `.rs`/`.mjs` 等を対象として受理する分岐が新設
されれば、この主張はその時点で偽になる。


総括
----
- 最も強く壊せたのは争点3（forward-looking 近似による発火率・件数の過大評価。全hunk
  46%→41%、件数-32%、うち1コミットは100%捏造）と争点1（190msがnode起動費用を除外して
  おり、subprocess統合案では実質2倍になりうる。加えて計測自体に無駄な30msの
  git subprocess混入がある——makeSnapshotのシグネチャ不一致による「効いていない計器」）。
- 争点2は小さいが実在する過大カウント（3/121鍵）を確認できたが、headline の数字
  （116/中央1/最大19）自体は大きくは動かなかった。
- 争点4・5は反証できなかった——全称主張だが、複数の独立経路（import・subprocess・
  設定・文字列参照 / resolveRefTarget の全分岐）から検めて破れなかった。
- 「効いていない計器」パターン（sed のバックスラッシュ事故と同型）は、プロトタイプ
  自身（makeSnapshotへの無駄な第2引数）と、私が最初に書いた検算スクリプト
  （touchedSecsへhits.length>0の条件を付け忘れ、生の発火率が100%になるバグ）の
  両方で実際に発生し、自分の分の事故は本ファイル執筆前に発見・修正した
  （probe-firing-corrected.mjs 参照）。この種の事故は書いた本人には気づきにくいという
  ことの追加の実例になった。
