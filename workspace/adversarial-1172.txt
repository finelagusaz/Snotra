敵対的レビュー — workspace/research.md（issue #1172）

## 壊せた項目

1. 【重大】「`linesOfComments` は `trim()` 済みの行を返す」は偽。実装（scripts/governance/lib.mjs 287-317行）は
   `text.split("\n").forEach((raw, i) => { const line = raw.trim(); ... if (isComment) out.push([i + 1, raw]); })`
   —— 判定にだけ `trim()` した `line` を使い、**push するのは未加工の `raw`**。つまり返る行はインデント込み。

   偽にする手順:
   ```
   node -e "
   const { linesOfComments } = await import('./scripts/governance/lib.mjs');
   const sample = 'mod foo {\n    /// indented doc comment\n    pub struct X;\n}\n';
   console.log(JSON.stringify(linesOfComments(sample, 'x.rs', 'js')));
   "
   ```
   出力: `[[2,"    /// indented doc comment"]]` — 先頭に 4 スペース。

   実害: research.md 自身が計画として書いている絞り込み `line.startsWith("///") || line.startsWith("//!")` を
   `linesOfComments` の戻り値へそのまま適用すると、**インデントされた `///` 行はすべて素通りする**
   （`"    /// x".startsWith("///")` は `false`）。そして現行ツリーの実際の doc コメントはほぼ全てインデント済み
   （`src-tauri/src/egui_shell/window_coordinator.rs:115,629,650` 等、モジュール直下 `//!` を除く `///` は
   ネストした impl/struct/fn の中にあり列頭に来ない）。トップレベル `//!` だけが列 0 で無傷に判定される。
   これは受け入れ条件 (a)「production の doc へ注入して赤」の実測を、注入先の選び方次第で
   **偽陽性の green**（注入したのに検知しない）にしうる致命的な計画バグである。
   research.md の「再利用できる既存パターン」節にある一文がそのまま誤りであり、実装フェーズで
   `line.trimStart()` を呼び出し側に追加しないと検査全体が事実上死ぬ。

2. 「`#[cfg(test)]` を絞らない設計でも、`#[cfg(test)]` 内へ注入すると赤になる」は上と同型の理由で疑わしい。
   `mod tests { ... }` 内の `///` も同じくインデントされるため、絞り込みの実装がインデント対応で
   なければ `#[cfg(test)]` 内外を問わず全滅する。「絞らない設計だから test 内も赤」という主張は
   trim バグを踏まえると「絞らない設計だが test 内も production 内も同じ理由で見逃す」に化ける可能性が高い。
   ⚠️ これは (1) の帰結であり、実装がどう `line.trimStart()` を当てるか次第で解消するので、
   「計画の記述として現状誤り」という限定で壊せた項目に置く。

3. 【中確度】claim「evidence は記録したが読まないキーには何も起きない」は evidence.mjs の実装で裏付けられる
   （`evidenceView` の Proxy get トラップは `target[key]` が読まれたときだけ未記録判定を行う。書いただけで
   読まれないキーは Proxy を経由しないので判定自体が発火しない）——ここは research.md の主張どおりで**壊せなかった**
   が、逆方向（新キーを載せたら test が壊れないか）を検算すると危うい:
   `scripts/governance-check.test.mjs` に `codeSpans` 等の値を直接 assert する行がないか確認したところ
   0 件（grep 一致なし）。よって新キー追加で test 破壊は起きない、という意味では research.md は正しい。
   これは「壊せなかった」側へ計上。

## 壊せなかった項目

- 述語 `/\[[^\[\]［］\n]*］|［[^\[\]［］\n]*\]/g` の判定。issue 実例・逆向き・reference 形混在
  （`[Type][BadRef］`）・全角対・バッククォート内・素のリンク形など計 11 パターンを node で実測したが、
  research.md が主張する当たり方／外れ方と全て一致した。行を跨ぐ構造（`\n` 除外）も含め破綻を見つけられなかった。
  ```
  node -e "const re=/\[[^\[\]［］\n]*］|［[^\[\]［］\n]*\]/g; console.log('[a][b］'.match(re))"
  ```
  → `['[b］']`（意図通り拾う）。

- 「現行ツリーで `［` / `］` は 0 件」。`git grep` ではなく node で `.rs/.mjs/.ps1/.psm1/.ts/.md` の
  全追跡ファイルを bytewise に読み `includes('［')`/`includes('］')` で独立再測したが、結果は同じく 0 件。
  ただし ⚠️ 節にある通り、この独立測定も「追跡ファイル」母集団は `git ls-files` で `git grep` と同じ土俵。
  未追跡ファイルまで含めた別経路（下記 ⚠️ 参照）は今回のツリーでは差が出なかった（未追跡 `.rs` が 0 件のため）。

- 「`checks/` にファイルを置けば検査になり、他に登録行は無い」。`docs/hooks.md`（研究文書が既に認めている
  `checkFoldedCodeSpans` 行）以外に、`docs/build-commands.md`・`scripts/governance-manifest.mjs`・
  `scripts/governance-check.test.mjs`・`.github/workflows/*.yml` を grep したが検査 ID の逐語登録は
  見つからなかった。`governance-manifest.mjs` の `undeclared` は ID を「PR 本文で宣言する」運用要求であり
  リポジトリ内の静的な登録簿ではない——research.md の「manifest」節の記述と整合する。

- `assembleEvidence` / `evidenceView` の設計（未記録キー読み取りで finding、read されない記録キーは無風）は
  実装を読んだ限り研究文書の記述通り。

- `governance-manifest.mjs` の `undeclared` が「差分は PR 本文に `G-<name>` を逐語で要求する」という記述も
  実装（62-85行）と整合。

- `#[cfg(test)]` を絞らない設計判断そのもの（境界判定の非自明さ・沈黙側へ倒れるリスク）の**理由付け**は
  壊せなかった。これは実装方針の当否の話であり、trim バグとは独立に妥当。

## ⚠️ 確信の持てない所見

- ⚠️ `git grep` の母集団は既定で**追跡ファイルのみ**（未追跡ファイルは対象外）。今回のツリーには未追跡 `.rs`/`.mjs`
  等が存在しない（`git status --porcelain` で確認）ため実害は出ていないが、research.md の「0 件」実測は
  この限定を明記していない。`makeSnapshot`（scripts/governance/lib.mjs 39行 `WALK_EXCLUDE_PATHS`）は
  ファイルシステムを歩いて `.gitignore` を読む方式で、追跡/未追跡を区別しない。**将来、gitignore されていない
  未追跡の `.rs` が作業ツリーに置かれた場合、`git grep` は見ず `governance:check`（`makeSnapshot` 経由）は見る**
  という非対称が理論上ありうる。今は再現できないため確信度は低いが、research.md の「実測」節に
  「追跡ファイルのみ」という限定を明記すべきという指摘は妥当だと考える。

- ⚠️ NFKC 互換の他の全角括弧（`〔〕`・`【】`・`﹇﹈`等）を intra-doc link の誤りに含めるべきかは、
  research.md は明示的に検討していない（「述語は 1 物理行」節で `［］` のみを扱う）。rustdoc が
  intra-doc link を認識するのは ASCII `[`/`]` のみなので、`〔〕`等の全角括弧単体では最初から
  リンクとして解釈されず「壊れたリンクが沈黙する」構造そのものが生じない。したがって対象外という
  research.md の暗黙の判断は妥当だと考えるが、**明示的に「なぜ除外するか」を検査の doc に書いていない**
  （母集団の境界説明が薄い）。壊せる主張ではないため確信度を下げて ⚠️ に置く。

- ⚠️ `linesOfComments` の trim バグは、呼び出し側で `line.trimStart()`（または `raw.trim()`）を追加すれば
  解消する軽微な実装漏れとも言える。「research.md の記述が誤り」という事実は確定だが、「計画全体が破綻する」
  とまでは言い切れない——設計判断としては軽微な追記で救えるため、severity の評価に確信は持てない。
  ただし research.md の受け入れ条件 (a) のフォールトインジェクション手順（「既存 doc 行へ注入」）は
  対象行がインデント済みかどうかで結果が変わるため、**実装時にこの前提が見落とされたまま進むと
  検査が silently 効かない状態で merge されうる**——ここは高確度で問題だと考える。
