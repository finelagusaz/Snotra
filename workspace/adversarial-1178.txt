争点4:「upgrade_save_ms: Option<u128> → Option<Duration> は Some(0) の意味論を壊さない」
判定: 壊せなかった（Some(0) 意味論は保たれる）が、判定強度が変わる箇所を 1 件発見
======================================================================

一次証拠（Some(0) 意味論について）:
- `Some` を作る行は `upgrade_legacy_cache_in`（indexer.rs:1218）の 1 行だけ
  （`let upgrade_save_ms = Some(save_started.elapsed().as_millis());`）。
  型を Duration に変えても `Some(save_started.elapsed())` になるだけで、
  variant を作る条件（このクロージャを通ったか）は 1 バイトも変わらない。
- `None` を作る 2 箇所（indexer.rs:1271, 1329）も条件不変。
- `load_cache_reports_upgrade_save_ms_only_when_it_upgrades_a_legacy_format`
  （indexer.rs:3628-3694）は `is_some()` / `== None` のみを見ており、型変更で
  判定強度は不変。

⚠️ 判定強度が変わる箇所（強くなる方向）:
`load_or_scan_with_stats_reports_upgrade_save_ms_in_cache_save_ms`
（indexer.rs:3711-3803）の assert（3771 行目）:
  `assert!(result.stats.cache_save_ms > 0, ...)`
現在は `LoadOrScanStats::cache_save_ms: u128`（`.as_millis()` で生成時に丸め済み）
への比較であり、テスト自身のコメント（3726-3729 行目）が「1 件の治具では 8 回中 3 回
落ちた（近傍のテストが先に同じ経路を通って温めた実行だけが 0 になる）」と明記して
いる——**ms 量子化に起因する既知の flaky 挙動**であり、20,000 件の fixture は
「仕事量を跨がせて実測時間を確実に 1ms 以上にする」ためだけに存在する。
改名表どおり `cache_save_ms` → `cache_save: Duration` にすると、この assert は
`result.stats.cache_save > Duration::ZERO` になり、**ms 未満の任意の正の経過時間でも
成立する**——ms 境界を跨ぐ必要が構造的に消える。これは検知器の対象（配線が
`result.upgrade_save_ms` を捨てて 0 を焼き込む退行）に対する感度を落とさない
（むしろ量子化ノイズを排除するぶん強くなる）。

research.md の Q2 はこの変化に触れているが（「`> Duration::ZERO` は ms の量子化に
載らない」）、**「治具は残す（測定の安定性のため）」と結論づけている一方で、
この治具が 20,000 件である理由（ms 境界を跨ぐため）自体が型変更で構造的に消滅する
ことは指摘していない**——「言い回しの書き直しが要る」という文書上の問題としてしか
扱っておらず、「fixture のサイズを維持する根拠が変わる（残す/縮めるは実装判断が
要る）」という設計上の問題としては扱っていない。これは研究の欠落というより
Q2 の扱いが浅い、という程度の所見。

この所見を偽にする手順: 実際に `cache_save_ms` を `Duration` へ改名し、1 件の
fixture で `load_or_scan_with_stats_reports_upgrade_save_ms_in_cache_save_ms`
相当のテストを 8 回以上流し、flaky が本当に消えるかを実測する（今回は改名前
なので未実施——research.md 側もこの検証を計画に含めていない）。

争点5:「memory_footprint.rs の残余算式は案 B が正しい」
判定: 壊せなかった（数学的には正しい）が、案 B 実装時の具体的な罠を 1 件発見
======================================================================

一次証拠:
- `snotra-core/tests/memory_footprint.rs:304-342` の現行実装（案 A）を確認。
  `s.total.as_millis().saturating_sub(s.hash_ms + s.cache_load_ms + s.scan_ms +
  s.sort_ms + [cache_save_ms if !cache_save_is_internal])`。
  各項は生成時に `.as_millis()` で個別に floor 丸め済み。
- 数学的検算: floor は劣加法的でない性質を利用すると
  `floor(a) + floor(b) <= floor(a+b)`（両辺とも a+b 以下の整数で、右辺が最大値）が
  常に成り立つ。ゆえに `Σfloor(phase_i) <= floor(Σphase_i) <= floor(total)`
  （後者は phase の生 Duration の和が total の生 Duration を超えないという、
  ネストした逐次区間である限りにおいて常に成り立つ前提に依存）。**この前提が
  破れるのは「二重計上」等のロジック上の欠陥があるときだけであり、丸めそのもの
  からは残余が負に振れることは無い**——research.md の「saturating_sub が黙って
  潰す」という記述はロジックバグ（例: cache_save_is_internal の判定漏れ）に
  対する保険であって、丸め由来の負振れを想定したものではない、という理解で
  research.md の記述と整合する。
- **争点で見つけた具体的な罠**: 案 B（生 Duration で引いてから 1 回丸める）を
  素朴に `s.total - (s.hash + s.cache_load + s.scan + s.sort + cache_save_term)`
  （`std::ops::Sub` の `-` 演算子）で書くと、Rust の `Duration::sub` は内部で
  `checked_sub().expect("overflow when subtracting durations")` を呼ぶため、
  **もし将来 cache_save_is_internal の判定にロジックバグが再導入され二重計上が
  起きた場合、案 A では `saturating_sub` により無音で 0ms 表示に潰れる
  （research.md 自身が「気づけない」と書く形）のに対し、案 B では `panic` に
  変わる**。research.md の Q1 はこの型変更を「代償は各フェーズ ms の和が
  印字した total と厳密には一致しなくなること（ずれ < ~5ms）」とだけ書いており、
  **「潰れ方が『無音の 0』から『panic』へ変わる」という失敗モードの変化には
  言及していない**。
  - 実害の程度: `memory_footprint.rs` は `#[ignore]` の手動計測専用ハーネスであり
    CI では走らない。`cargo test` はプロファイルに関わらずテストを常に unwind
    でビルドする（ルート `Cargo.toml:37-41` の `[profile.release] panic = "abort"`
    はテストプロファイルには適用されない——Cargo の既知の挙動）ため、panic は
    プロセスクラッシュではなく該当テストの失敗として観測される。**このリポジトリ
    の哲学（無音の欠陥より panic を好む・snotra-core/CLAUDE.md「読み込み失敗は
    種類で扱いを分ける」等に通底する fail-loud 志向）とは整合的であり、むしろ
    改善**と評価できるが、research.md はこれを設計判断として明示的に選んでおらず、
    実装時に `saturating_sub`（Duration にも存在する）を使うか生 `-` を使うかで
    挙動が変わることに触れていない。

⚠️ 実測できなかった点: `%APPDATA%\Snotra\index.bin` の実データ（後述）は現行版
（v7）でヒットする構成のため、実際に `cache_save_is_internal` の判定漏れが
案 B 下で panic するシナリオを手元では**再現していない**（理論的検算のみ）。
