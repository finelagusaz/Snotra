--- 争点 2（部分的に崩れる）: 「cargo metadata --manifest-path <worktree>/Cargo.toml は worktree
自身の target を返す」 ---

CARGO_TARGET_DIR **未設定**の場合は 4 本の別 worktree（a5b0f5810c7344357 / a802f374e32d2b999 /
a9ccfdc217264f542 / ac5ec9f15ef4cb614）すべてで確認でき、research.md の実測と一致する。
ここまでは崩れない。

しかし **CARGO_TARGET_DIR が相対パスで設定されている場合、target_directory はマニフェストの
場所ではなく「cargo metadata を実行したプロセスの cwd」を起点に解決される**。これは
Resolve-SnotraCargoExecutable の設計が暗黙に仮定している「$RepositoryRoot だけで解決先が
決まる」を破る。

実測（cwd=C:/workspace/Snotra のまま、--manifest-path で worktree を指す）:
  $ CARGO_TARGET_DIR=custom-target cargo metadata --no-deps --format-version 1 \
      --manifest-path ".claude/worktrees/agent-a5b0f5810c7344357/Cargo.toml"
  → target_directory = C:\workspace\Snotra\custom-target
  （worktree 配下の custom-target ではなく、cwd 側のメイン作業コピー配下になる）

対照（cwd を worktree 自身へ移した場合）:
  $ cd .claude/worktrees/agent-a5b0f5810c7344357
  $ CARGO_TARGET_DIR=custom-target cargo metadata ... --manifest-path "Cargo.toml"
  → target_directory = C:\workspace\Snotra\.claude\worktrees\agent-a5b0f5810c7344357\custom-target
  （このときは正しく worktree 配下になる）

**意味**: Resolve-SnotraCargoExecutable 自身は `-RepositoryRoot` だけを受け取り、内部で
`& cargo metadata --manifest-path $manifestPath` を呼ぶ（cwd を明示的に worktree へ変えない・
SnotraSmoke.psm1:399）。呼び出し元 `.ps1` の `$repoRoot` は `$PSScriptRoot` から正しく worktree
を指すが、**cargo 子プロセスの cwd は呼び出し元 PowerShell セッションの `$PWD` のままである**。
ゆえに「worktree のスクリプトを worktree の絶対パスで直接叩くが、シェルの cwd はメイン作業
コピーのまま」という、まさに issue が問題にしている使われ方の変種で、かつ環境に相対
CARGO_TARGET_DIR が設定されているケースに限り、**この修正は同じ欠陥（別作業コピーを黙って
測る）を CARGO_TARGET_DIR 経由で再導入しうる**。

偽にする手順: 上記コマンドをそのまま再実行する（cwd をメイン作業コピーに置いたまま、
`-manifest-path` だけ worktree を指し、`CARGO_TARGET_DIR` に相対パスを設定する）。

**評価の重み**: 本セッションの env や CI（3 経路とも -ExePath 明示）はこの経路を踏まない
（research.md の実測はそちらについては正しい）。危険なのは「worktree エージェントが
-ExePath を明示しない標準ユースケース」かつ「そのエージェントの shell に相対
CARGO_TARGET_DIR が設定されている」の交差だけである。CARGO_TARGET_DIR は sccache 等の
ビルドキャッシュ運用で相対値のまま設定されることが珍しくない値なので、可能性はゼロではない。
research.md 8 節「測定環境（前提の裏取り）」は「本セッションの env に CARGO_TARGET_DIR は
設定されていない」としか書いておらず、**相対パスで設定された場合の cwd 依存性そのものは
検討されていない**——これは research.md の実測の誤りではなく、実測していない前提の穴である。
plan.md では、この経路をリスクとして明示するか（例: throw する resolveされたパスが repoRoot
配下でないときの検知）、少なくとも既知の残余として書くことを推奨する。

--- 争点 1（部分的に崩れる・方法論の穴）: 「同一パターンの生きた出現は bench-startup.ps1:28 と
smoke-startup.ps1:9 の 2 件だけ」 ---

`.superpowers/sdd/` 配下（`.gitignore:25` で除外・`git ls-files .superpowers/` は 0 件）に、
$repo = "C:/workspace/Snotra" 形の絶対パスを持つ実際の .ps1 ファイルが複数在る（例:
`.superpowers/sdd/2026-08-04-main-show-height-derivation/measure-fixA-position.ps1:19`,
`verify-fixA-invariant.ps1:12`）。生の `grep -r`（.gitignore を見ない）ではヒットするが、
Grep ツール（ripgrep 系・.gitignore を尊重）では出ない——実測で確認した:
  - `grep -rniI` (bash, .gitignore 無視): .superpowers/sdd 配下 20+ 件ヒット
  - Grep ツール（ripgrep 相当）: workspace/research.md, scripts/bench-startup.ps1,

    5 件のみ（research.md 2 節の記述と完全一致）

つまり **research.md 自身の走査もおそらく .gitignore を尊重するツールで行われており、
`.superpowers/` を「見た上で除外した」のではなく「そもそも視界に入らなかった」**。
research.md は `.claude/worktrees/` は明示的に「追跡外の写しが混じる」と除外理由を書いて
いるが、`.superpowers/` については一言も触れていない——除外を意図した記述ではなく、
走査ツールの既定挙動による欠落である。

**評価の重み**: `.superpowers/sdd/*.ps1` は git 追跡外の一時スクリプト（過去の調査の副産物）
であり、`scripts/` 配下の「今回直す」対象と同じ層ではない。範囲決定（bench-startup.ps1 +
smoke-startup.ps1 の 2 件）を変える理由にはならないと判断する——`.claude/worktrees/` を
除外するのと同じ理由（追跡外・生きたスクリプト層ではない）が事後的には当てはまる。
ただし研究 2 節の「リポジトリ全体で...走査した」という文言は、実際には
「git 追跡下（および .gitignore 非対象）を走査した」の意味でしか成立しておらず、**全称の
強さで書かれた完全性の主張として読むと偽になる**。plan.md では「範囲は git 追跡ファイルに
限る」と明示するか、この一文を弱めることを推奨する。

⚠️ 確信の持てない所見
====================================================================

1. ⚠️ 「$Profile パラメータ名が自動変数 $PROFILE と衝突するのでは」という論点は、実測では
   衝突しなかった。関数スコープの `param()` の `$Profile` はローカル変数として束縛され、
   呼び出し前後で `$global:PROFILE`（起動時プロファイルスクリプトのパス）は不変だった
   （Set-StrictMode -Version Latest 下でも同じ）。この論点は破棄してよいと考えるが、
   `Resolve-SnotraCargoExecutable` は既に本番コードに存在し Pester で検査されている関数
   なので、今回の変更そのものの新規リスクではない。

2. ⚠️ 争点 2 で見つけた CARGO_TARGET_DIR の相対パス依存は、issue #1179 が名指す「worktree
   から既定のまま回すと本体が別コピーになる」という被害像そのものの**別ルート**である。
   `Resolve-SnotraCargoExecutable` を直す設計そのものは正しいが、**このヘルパー関数を
   直さない限り、今回の PR は同種の欠陥を CARGO_TARGET_DIR 経由で残す**。ただし
   `Resolve-SnotraCargoExecutable` は今回のスコープ外（既存の共通ヘルパーで、
   run-pester.ps1 等が既に依存している）なので、直すなら別 issue が妥当かもしれない。
   plan.md でこの残余をどう扱うか（無視/別issue/このPRで一緒に直す）を明示すべき。

3. ⚠️ .superpowers/sdd/ の実測は「今日時点で実行可能な .ps1 が置かれている」ことまでしか
   確認していない。これらのスクリプトが実際に定期的に実行される運用物か、単なる過去調査の
   死骸かは git 履歴・利用実態からは判定していない（時間の都合で未実施）。
