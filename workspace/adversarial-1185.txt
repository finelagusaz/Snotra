## 壊せなかった項目

### P2: G-stale-identifiers の走査元に `.rs` は入らない

- `scripts/governance/lib.mjs` を直接読んだ。`staleIdentifierDocs`（667行）は
  `/^\.claude\/(skills\/.*|rules\/[^/]+|agents\/[^/]+)\.md$/` で `.claude/**/*.md` のみ、
  `staleIdentifierGuideDocs`（678行）は `docs/**.md`（`docs/superpowers/`・`docs/adr/` 除外）のみ、
  `STALE_EXTRA_DOCS`（661行）は `["SPEC.md", "CLAUDE.md", "AGENTS.md",
  "snotra-settings/SETTINGS-DESIGN.md"]` の固定4パスのみ。`staleIdentifierTargets`（687行）は
  この3つの和で、`.rs` はどの経路にも現れない。
- 注意点（research.md が明示していないニュアンス）: `.rs` は「検査対象（docs）」には入らないが、
  「**現行語彙の供給源（vocab）**」には入る（`VOCAB_SOURCE_EXT` に `rs` を含む・
  `G-stale-identifiers.mjs:109`）。つまり `.rs` のコメント自体は検査されないが、`.rs` の
  **非コメント本文**（関数名などの識別子）が「腐っていない証拠」として使われる。この非対称は
  research.md の主張（「`.rs`は入らない」）を否定しないが、精度を上げる情報として付記する。
- **試した反証**: `.rs` を対象に含む可能性のある他の関数（`headingRefSourceDocs` 等）と混同していないか
  確認したが、`G-stale-identifiers.mjs` のコメント自身が「**`.rs` の doc コメントは母集団外**」
  「#975 で `.rs` を足す案を測って却下した」と明記しており、P2 は正確である。

### P3: `snotra-core/CLAUDE.md:10` は全モジュール一括で `//!` を責務の正本に指名している

  （責務は`//!`）」、`index_tree.rs`「`target_path`をフォルダ木の接頭辞共有で表す…（責務は`//!`）」

- **試した反証**: 「全モジュール一括」という強い言い方が言い過ぎでないか、例外規定の射程を

### P4: `IndexTree::file_key_into` が「頻度は数を添えられないなら根拠に使わない」の唯一の模範例で
あり、削除で規約の根拠が消えうる

  `snotra-core/src/index_tree.rs:805`（`pub(crate) fn file_key_into`）に実在する（整理対象ファイル）。
- **⚠️ 追加のニュアンス（machinery の限界）**: `G-stale-identifiers.mjs` を読むと、この検査が
  守るのは「**識別子が現行語彙（productionソースの非コメント本文）に存在するか**」だけである
  （54行目「現行語彙の正本はproductionのソースの非コメント本文ただ1つ」）。つまり `file_key_into`
  という**関数名自体**が消えなければ green のままで、その doc コメントの**内容**
  （「実データで根は約200件（0.06%）」という頻度の実測）が圧縮で失われても検査は何も言わない。
  過去2回の事故（`Engine::new_from_cache` 消失・test fixture 消失）はどちらも「名指しの対象が
  消えた」形だったが、この model example は「対象は残るが中身が変わる」形の事故に対して**もっと
  無防備**である——research.md の制約2は「シンボルごとに外から名指されていないかを先に測る手順」

### P6: `index_tree.rs` の `//!`（35行）は既存基準「数行で」への違反である

- `grep -c '^//!' snotra-core/src/index_tree.rs` → **35**（1〜35行が連続する1ブロック、

  模範例群は4〜10行に収まっており、`index_tree.rs` の35行はその3.5〜9倍で明確な外れ値。
  P6 は正確——research.md の主張より踏み込んだ実測でも支持される。

### P5（弱く壊れた・⚠️）: 「機械検査を新設しない判断はADRの却下3・却下4とissueの非目標だけで
十分に根拠づけられる」

- 却下3（行またぎコードスパン検知器）・却下4（散文の数え上げ検知器）は**特定の2つの具体案**への
  却下理由であり、「//! の長さを数える検知器」のような**別形の新規検知器**を機械的に排除する論拠
  ではない。ただしissueの非目標「文字数・行数のhard limitを導入すること」は、行数ベースの検知器を
  直接禁じているので、その限りではP5の結論は保たれる。
- しかし P1 の発見により、「新しい検査を作る必要が無い」というP5の**結論**はさらに別の理由でも
  支持される: PERFORMANCE.md/ADR への参照を正準形見出し参照で書けば、**既存のG-heading-refsが
  そのまま保護する**（新設不要）。research.md はこの経路自体に気づいていないため、P5の論証は
  「たまたま結論が保たれている」状態であり、根拠として却下3・4を引用するのは正確でない
  （却下3・4は無関係な提案の却下理由であり、今回の完了条件1「短く保つための明示的な基準を追加する」
  にどう当たるかを独立に検討していない）。
- **この所見を偽にする手順**: 却下3・4の却下理由（語彙依存regexの偽陽性率・行またぎ検知の低い
  事故率）が「//! 行数カウント」のような別形の検知器にも一般化できると示せれば、この所見は
  無効化される。今回はその一般化を検証せず「非目標条項で十分」と読み替えた。

## ⚠️ 確信の持てない所見

- **数値の食い違い（2件）**——research.md がまったく触れていない実データの矛盾を発見した。
  1. `snotra-core/src/search/build.rs:29`（`DerivedStrings` の doc）: 「分ける実益は2つある:

     「分離の実益は残る: **312,690回の比較を丸ごと省ける**ことと…**構築89 → 58 ms**のうち、
     比較ぶんがここに当たる」——**開始値が68msと89msで食い違う**（終了値58msは一致）。
  2. `snotra-core/src/search/build.rs:181-185`（`assemble` の doc）: 「serdeの`size_hint`は
     DoS防止のため事前確保を**1 MiB相当**で頭打ちにし…」
     vs. `PERFORMANCE.md:302-304`（「Vec本体の確保が実使用の約2倍あった」節）:
     「serdeの`size_hint`はDoS防止のため**4,096要素**で頭打ちにし…」——単位も値も異なる記述。
  - これは「圧縮でコード側の数値をPERFORMANCE.mdへ集約する」というハイブリッド方針の実行時に、
    **既に正本候補同士が食い違っている**ことを意味する。research.md の未解決の疑問1・2
    （判定粒度・出所喪失値の扱い）は「PERFORMANCE.mdに無い値をどう扱うか」を問うているが、
    「PERFORMANCE.mdとコード双方に**異なる値**がある」場合の扱いは論点として存在しない。
  - 確信度を⚠️にする理由: どちらが正しい値か（あるいは両方とも別の実験条件を指しているのか）を
    独立に検証できていない。数値自体の正誤ではなく「**2つの正本候補が食い違っている**」という
    事実だけを報告する。
  - **偽にする手順**: `git log -S"構築 68"` や `-S"構築 89"` でコミット履歴を辿り、どちらが後から
    書かれた値か（＝どちらがより新しい実測か）を確認すれば、少なくとも「新しい方を正とする」の
    判断はできる。今回はその履歴調査を行っていない。

  再走査したところ、`CachedMasks` は `docs/superpowers/plans/`・`docs/superpowers/specs/` に
