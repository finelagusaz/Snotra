# 敵対的レビュー: research.md（issue #1201）

調査日: 2026-08-27。走査範囲: src-tauri/, docs/adr/, .claude/rules/ のみ。worktrees/ と target/ は見ていない。

## 壊せた項目

### 1. 命題 (ii) はワーディングどおりに読むと偽である

主張: 「launcher_controller/ 配下の activation.rs 以外のどのファイルも、fn on_enter( / fn
activate_or_execute( / fn shift_activate( のいずれの綴りも含まない」

反証: `activation/tests.rs` は launcher_controller/ の**配下**（activation/ サブディレクトリの中）に
在り、この 3 つの綴りをすべて**文字列リテラルとして**含む。

再現手順:
```
grep -n "fn on_enter(\|fn activate_or_execute(\|fn shift_activate(" \
  src-tauri/src/egui_shell/launcher_controller/activation/tests.rs
```
→ 418:"fn on_enter(", 419:"fn activate_or_execute(", 420:"fn shift_activate(",
   498:("fn activate_or_execute(", ...), 499:("fn shift_activate(", ...), 566:"fn on_enter("

**ただし実害は無い**——(iii) が示すとおり、`read_dir` は非再帰なので tests.rs は
そもそも列挙されず、"is_file() && ends_with(".rs")" フィルタを経るまでもなく構造的に
population へ入らない。「配下のどのファイルも」を **read_dir が直接返す 6 エントリに限る**
と読めば真になる（research.md 自身は §2 の表で tests.rs を 6 ファイルと別枠に置いており、
おそらくその意味で書いている）。**壊れているのは、この命題単体を「配下」の自然な広い
語義（子孫を含む）で読んだときの字面であって、設計の正しさではない。** 読み手が「配下」を
再帰的に取ると誤って「アンカーの一意性は今日不成立」と結論しうるので、母集団の範囲
（直接の子だけ）を明示すべき箇所である。

## 壊せなかった項目（検算方法つき）

- **(i)** 6 ファイルの needle 出現はすべて同一ファイル内の字下げ4ヘッダより後——
  `grep -n` で self.indexing() / read_config( の全出現を洗い出し、各ファイルの直前ヘッダを
  目視突合。self.indexing() は search_flow.rs:87（run_search_with 内、header 63 行）、
  read_config( は activation.rs:357,572・hide_request.rs:49・search_flow.rs:46,128 の
  5 箇所すべてで直前に同ファイルの 4 空白ヘッダが在ることを確認。read_visible_rows( は
  0 件（grep で確認）。
- **(iii)** is_file() && ends_with(".rs") で tests.rs が母集団から落ちる——
  scratchpad/simulate.mjs を実行し `files-only *.rs:` の出力に tests.rs が現れないことを
  実測。加えて `read_dir` が非再帰である以上、is_file() フィルタを経るまでもなく
  activation/tests.rs はそもそも列挙されないことを Rust の `std::fs::read_dir` の仕様
  （子ディレクトリの中身は列挙しない）から確認。
- **31 本のヘッダ数** — simulate.mjs の出力 `total indent-4 headers: 31` を、
  独立した `grep -nP "^    (pub(\([^)]*\))?\s+)?(async\s+)?fn "` の集計（activation.rs=11,
  folder_nav.rs=4, frame_stages.rs=3, hide_request.rs=4, search_flow.rs=7,
  updater_toast.rs=2, 合計31）で二重に検算し一致。
- **行数・ファイルサイズ** — `wc -l` / `wc -c` で 635/218/138/106/311/93/207 行、
  launcher_controller.rs=13479 バイト（≈13KB）をすべて実測し研究文書の表と一致。
- **§3.7 の include_str! サイト一覧** — `grep -rn "include_str!" src-tauri/src/` の
  実コード呼び出し（doc コメント中の言及を除く）が icon_textures.rs:427,433 /
  view.rs:1421 / indexing.rs:317 / activation/tests.rs:416,495,565 の 4 サイトと完全一致。
- **read_dir 順序の「実測1台ぶん」宣言** — research.md 自身が
  「この順序は実測1台ぶんであり、OS/FS依存の主張はしない」と明記しており、暗黙の一般化は
  していない。過大な全称化なし。
- **§3.5 の「この作業ツリーは全ファイルLF」宣言も同様に機体スコープを明示**——
  `git config --get core.autocrlf` = `input`（ユーザーの global 設定）を確認、
  `.gitattributes` は `.githooks/**` にだけ `eol=lf` を強制し src-tauri/ には掛からない
  ことを確認。したがって現在の LF は「このマシンの global autocrlf=input」に由来する
  作業ツリー固有の事実であり、.gitattributes 冒頭コメントが記す
  「global設定を持たない新規cloneはCRLFに変換する」との非対称も文書の記述どおり。
  過大な一般化なし。
- **ADR 引用** — `ADR-source-text-probe-helper-locality.md` の却下理由1・2、
  反転条件（「3つ目のソーステキスト検査を新設するなら」）の文言を原文と突合し完全一致。

  直前ヘッダ `pub(super) fn lang(`（193行）へ帰属、`mod tests` 無し、を実読で確認。
  親ファイルは launcher_controller/ ディレクトリの**外**（兄弟ファイル）であることも
  ディレクトリリストで確認済みなので、「アンカーが1枚にも見つからず赤になる」という

- **helperの本体不変（命題(v)）** — Design B は method_body/method_header/owners_of の

## ⚠️ 確信の持てない所見（返り値の列挙に含める）

1. **⚠️ simulate.mjs の owners_of は Rust の owners_of と厳密には逐語ではない。**
   Rust（tests.rs:246-248）: `owners.extend(current.map(str::to_string))` — `current` が
   `None` のとき（最初のヘッダより前で needle が出現）は**何も push しない**。
   JS（simulate.mjs:46）: `out.push(cur)` — `cur` が `null` でも**必ず push する**。
   偽にする手順: 各ファイル内で最初のヘッダより前に needle を置いた入力を両者に与えると、
   Rust 版の owners 配列の長さは変わらないが JS 版は 1 要素増える。
   **ただし現在の実データには影響しない**——今回の6ファイルはどれも needle 出現が
   自ファイルの最初のヘッダより後に在る（上の「壊せなかった (i)」で確認済み）ため、
   `<NONE>` に該当するケースが実際には1件も無く、報告されている数値（headers=31,
   owners=1/5, attributed=0/0）はこの分岐差の影響を受けていない。
   **したがって「method_header / owners_of を逐語で移植した」（§3 冒頭）という記述は
   厳密には不正確**（owners_of の None 分岐が逐語ではない）が、実測値そのものは
   汚染されていない。

2. **⚠️ activation.rs の `//!` の引用行範囲がわずかに広すぎる。**
   research.md §2「規範の写し」1: 「activation.rs の `//!` 3〜15行 — 『起動の入口を
   このファイルの外へ出してはならない』＋『守られ方は方向で違う』」とあるが、実際に
   読むと該当する2つの論点は3〜13行に収まり、14〜15行目は既に次の話題
   （slash コマンドの即実行を activation.rs に置く理由）に移っている。2行分の
   ズレで実害は無いが、`.claude/rules/src-tauri.md` が「位置は行番号で断定せず見出し・
   シンボル名でgrepする」よう求めている理由がまさにこの手の陳腐化である。

3. **⚠️ research.md が明示的に触れていない沈黙経路: 将来 6 ファイルのいずれかに
   inline `#[cfg(test)] mod tests { ... }` を足した場合、Design B の `fs::read_to_string`
   はソースを生バイト列として読むため `#[cfg(test)]` 属性の有無を区別しない。**
   もし将来だれかが（現状は無いが）例えば `search_flow.rs` の末尾に
   `#[cfg(test)] mod tests { fn on_enter() { self.indexing(); } }` のような
   テスト専用コードを直接埋めた場合、その中の字下げ4見出しや needle 文字列は
   「production の呼び出し」として母集団へ混入し得る——これは現行 `include_str!` 設計
   （activation.rs 自身に inline `#[cfg(test)]` を足した場合も同型の潜在的リスク）が
   既に持つ性質で issue #1201 が新規に持ち込むものではないが、母集団をディレクトリへ
   広げることで曝露面が1ファイルから6ファイルへ拡大する点は research.md のどこにも
   言及が無い。現状 grep で確認した限り、6ファイルのいずれにも inline `#[cfg(test)]`
   は存在しない（`activation.rs:634-635` の `#[cfg(test)] mod tests;` は外部ファイルへの
   宣言のみ）ので **今日の欠陥ではない**。
   偽にする手順（この所見自体を再現したいなら）:
   `grep -n "#\[cfg(test)\]" src-tauri/src/egui_shell/launcher_controller/*.rs` で
   activation.rs 以外に inline test が無いことを確認できる（今回それを確認した）。

4. **⚠️ §5.2 の「ディレクトリが空・読めないときの沈黙」の扱いは read_dir の失敗しか
   明示的に検討していない。** `fs::read_to_string` が個々のファイルで失敗する経路
   （非 UTF-8 バイト列を含むファイルが将来紛れ込む等）については、research.md も
   issue 本文も名指しで扱っていない。おそらく同じ `unwrap`/`expect` で panic＝赤に
   落ちる設計になるはずだが、§8「未解決の疑問」にもこの分岐は挙がっていない。
   実害は低い（現行6ファイルはすべて有効なUTF-8のRustソースであることをこのレビューで
   確認済み——`file` コマンドで全ファイルが "UTF-8 text" と判定された）が、
   実装時に明示すべき分岐として指摘する。

5. **⚠️（低確信）変異 (d)〜(g) は Design B 実装前の予測であり、今日のツリーに対して
   実行して確かめることができない。** 論理的な追跡（owners_of の per-file 呼び出しに
   よる帰属の非跨境界性、sole_file_with の一意性 assert）は一貫しているように見えるが、
   これは「実装がその通りに書かれれば」という条件付きの検証であり、変異注入の実測
   ではない。research.md 自身も §6 冒頭で「設計を確定する前に書き下ろす」と位置づけて
   おり、実装後に再実測する前提を明記しているため、これは research.md の欠陥という
   よりはこの調査段階の必然的な限界として記録する。
