=== 争点1: 「windows crate の Win32_System_Registry feature が既に有効なので依存追加が 0」 ===

重大度: ❌（部分的に偽。列挙した3 API のうち1つは追加 feature が要る）

一次証拠:
  snotra-core/Cargo.toml:23-29 で `windows 0.62.2` が
  `["Win32_Storage_FileSystem", "Win32_System_Environment", "Win32_System_Registry",
    "Win32_System_Threading"]` を持つことを確認（Win32_Security は無い）。

  snotra-core/src/_probe_registry_write.rs（一時ファイル。検証後に削除・lib.rs の mod 宣言も
  revert 済み・`git status --short snotra-core/` で汚れが無いことを確認済み）で
  RegCreateKeyExW / RegSetValueExW / RegDeleteValueW / RegCloseKey を呼ぶコードを書き、
  `cargo check -p snotra-core` を実行した。

  1回目（RegCreateKeyExW 使用）:
    error[E0425]: cannot find function, tuple struct or tuple variant `RegCreateKeyExW` in this scope
       --> snotra-core\src\_probe_registry_write.rs:14:17
    help: a function with a similar name exists: RegCreateKeyW

  windows-0.62.2 のソース（$CARGO_HOME/registry/.../windows-0.62.2/src/Windows/Win32/System/Registry/mod.rs）
  を確認すると、RegCreateKeyExW の直上に `#[cfg(feature = "Win32_Security")]` が付いている
  （SECURITY_ATTRIBUTES 引数を持つため）。この cfg が付くのは RegCreateKeyExA/W・
  RegCreateKeyTransactedA/W・RegGetKeySecurity・RegSaveKey*・RegSetKeySecurity の10箇所のみで、
  RegOpenKeyExW / RegSetValueExW / RegDeleteValueW / RegCreateKeyW（Ex 無し版）は
  ゲート無しでコンパイルできる。

  2回目（RegOpenKeyExW(KEY_WRITE) + RegSetValueExW + RegDeleteValueW + RegCloseKey に差し替え）:
    Checking snotra-core v0.1.0 (C:\workspace\Snotra\snotra-core)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 1.83s
  → 成功。

結論: research.md 本文 (行48) は「書き込み系 API（RegSetValueExW / RegDeleteValueW /
RegCreateKeyExW）」の3つを名指しして「既存 feature だけで閉じる」と述べているが、
このうち RegCreateKeyExW は Win32_Security feature の追加なしにはコンパイルできない
（Win32_System_Registry feature だけでは不足）。ただし——実装上は RegCreateKeyExW は不要である
可能性が高い。`HKCU\...\CurrentVersion\Run` キー自体は既存の well-known key（`CurrentVersion`
の子）なので、新規作成の必要が無く RegOpenKeyExW(KEY_WRITE) で開けば足りる
（path_env.rs の read_user_path が使うのと同じ RegOpenKeyExW。今回 KEY_WRITE でも成功を確認）。
その経路なら claim は実質的に正しい結論（feature 追加 0）へ着地するが、**根拠として明示的に
名指しした3つの API のうち1つは、そのままでは成立しない**——「既存 feature で閉じる」という
主張の論証には瑕疵があり、計画には「RegCreateKeyExW ではなく RegOpenKeyExW を使う」という
1行の訂正が要る。

これを偽にする手順: 別の windows crate バージョンで Win32_Security 抜きでも RegCreateKeyExW が
コンパイルできることを示す（現行 lockfile のピン止めバージョン 0.62.2 では上記の通り不可能）。

=== 争点5-3: StartupApproved\Run のレコード ABSENT 実測が測定タイミングに依存していないか ===

重大度: ⚠️（否定も肯定もできない。意図的にテストを避けた——理由を明記する）

検討: probe-run-key.ps1 は Run 値を書いた**直後**、同一 PowerShell セッション内で
StartupApproved\Run の GetValueNames() を読んでいる。一般に知られている Windows の挙動として、
StartupApproved のレコードは Explorer（`explorer.exe`）が起動時（ログオン時）に Run/RunOnce の
現在値を走査して未記録の値へ「有効（02...）」のレコードを補完する、という説がある（公式文書での
断定は見つからなかった）。これが事実なら、「新規 Run 値に対するレコードが自動生成されない」という
research.md の実測は「まだ Explorer が次のログオン走査を行っていない」窓の中でだけ真であり、
次回ログオン（または `explorer.exe` の再起動）後には記録が現れる可能性がある。

**この可能性を実機で検証するには explorer.exe の再起動、または実際のログオフ/ログオンが要る。**
今回はどちらも実施しなかった——explorer.exe の再起動はタスクバー・デスクトップアイコン・
開いているエクスプローラーウィンドウを巻き込む破壊的操作であり、ユーザーの実セッションに
影響するため、明示的な許可なく実行すべきでないと判断した（「やらないこと」に列挙された
「実レジストリの Run キーへ恒久的な値を書かない」の精神に照らし、同程度に破壊的な操作は
慎重側に倒した）。

結論: research.md の記述「新規に作った Run 値に対する StartupApproved\Run のレコード:
ABSENT（自動生成されない）」は、**「値作成直後の同一セッション内では」という条件付きでのみ
確認されている**。research.md 自身もこの限定を暗黙に認識しているように見える
（§2 「逆に、レコードが無いこと（**新規作成直後**）は『有効』を意味する」と書いており、
「新規作成直後」という時間限定の語を使っている）。ただし §7「未解決の疑問」には
「タスクマネージャーの『無効化』が Run 値を消すか、StartupApproved にマークを置くだけか」
という関連する疑問は明記されているが、**「StartupApproved レコードが後から遅延生成されうるか」
