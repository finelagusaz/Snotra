命題1: DeleteRegValue の値名は RUN_VALUE_NAME と逐語一致するか
=====================================================================

結論: 崩せなかった。一致する。

- `${PRODUCTNAME}` は installer.nsi:35 `!define PRODUCTNAME "Snotra"` で展開される。
  `tauri.conf.json` の `productName: "Snotra"` から来ており、autostart.rs:41
  `RUN_VALUE_NAME = "Snotra"` とバイト単位で一致（大文字小文字含め完全一致、
  末尾空白等の混入もない）。
- 大文字小文字: Windows レジストリの値名比較は大文字小文字を区別しない
  （Win32 の一般知識。ローカルで反証する術は無いが、逐語一致な以上そもそも
  この論点は発火しない）。
- レジストリビュー（WOW64）: `SetContext` マクロ（utils.nsh:3-18）は
  `RunningX64` かつ `INSTALLMODE==currentUser` のとき `SetRegView 64` を呼ぶ。
  **しかし `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` は WOW64 の
  リダイレクト/リフレクション対象キーではない**（リダイレクトは
  `HKLM\Software\...` と `HKCU\Software\Classes\...` に限定され、
  `HKCU\...\Run` はプロセスのビット数によらず単一の実体）。ゆえに
  `SetRegView` の値は本命題に影響しない。アプリ側 `win_registry.rs::open_hkcu`
  も `KEY_WOW64_64KEY`/`32KEY` を指定せずデフォルトのまま `HKEY_CURRENT_USER`
  を開いており、インストーラ側と食い違うレジストリビューを見に行く経路も無い。

偽にする手順: `target/debug/nsis/x64/installer.nsi:35` と
`snotra-core/src/autostart.rs:41` を diff。値が違えば命題は崩れる
（現状は "Snotra" == "Snotra"）。

命題2: INSTALLMODE=currentUser ゆえ非昇格・HKCU=利用者ハイブ
=====================================================================

結論: 崩せなかった。

- installer.nsi:103-104 `!if "${INSTALLMODE}" == "currentUser" /
  RequestExecutionLevel user` を実測。マニフェストで管理者権限を要求しない。
- `SetContext`（utils.nsh:4-8）は `currentUser` のとき
  `SetShellVarContext current` を呼ぶ（`all` ではない）——`$APPDATA` 等の
  シェル変数を「現在のユーザー」に固定する側で、これも HKCU 前提と整合する。
- アンインストーラの `un.onInit`（installer.nsi:727-745）も同じ `SetContext`
  を呼んでおり、インストール時と実行時で文脈が食い違わない。

偽にする手順: `RequestExecutionLevel admin` が currentUser 分岐に紛れて
いないか、または un.onInit が別の SetContext 変種を呼んでいないかを grep。
現状は 1 系統のみ。

=====================================================================
命題4: updater 経由では消えない
=====================================================================

結論: 崩せなかった。経路は実在し、必ず通る。

- `tauri-plugin-updater-2.10.1/src/updater.rs:801-817` を実測。
  `WindowsUpdaterType::Nsis` 分岐は `install_mode.nsis_args()`
  （passive のとき `["/P","/R"]`）に**無条件で** `.chain(once("/UPDATE"))`
  する。config 分岐（`update.windows.installMode`）が何であっても
  `/UPDATE` は必ず付く——`/UPDATE` の有無は install_mode と独立。
- `extract()`（同ファイル:882-929）: `bundle.targets: ["nsis"]` のみ・
  `createUpdaterArtifacts: true`・release.yml の `latest.json` url は
  `.exe` 直リンク（zip ではない）なので `extract_exe` → `infer::app::is_exe`
  → 必ず `WindowsUpdaterType::Nsis` に解決する。Msi 分岐へ落ちる経路は
  このアプリの構成に存在しない。
- `un.onInit`（installer.nsi:727-745）が `/UPDATE` を `$UpdateMode` へ
  読み取り、`Section Uninstall` の削除ブロック（:816）がそれを見て
  スキップする。`$UpdateMode` を読む箇所は installer.nsi 全体で 2 箇所
  （:478 の `.onInit`／:741 の `un.onInit`）のみで、いずれも `${GetOptions}`
  経由の同じ読み取り。

偽にする手順: `tauri.conf.json` の `bundle.targets` に `"msi"` を足すと
updater が Msi 型を選びうる経路が開く（現状は未使用）。または
`updater.rs` の該当バージョンが変わり `.chain(once("/UPDATE"))` の
無条件性が失われていないかを都度確認する。

命題5: `.nsh` を足すと更新退行になる（却下理由が強すぎないか）
=====================================================================

結論: 「未対策のまま足せば退行する」は崩せない。ただし
**却下理由そのものはやや強すぎる**——ガード付きなら回避可能。

- `NSIS_HOOK_PREUNINSTALL` は `Section Uninstall` の最上部（:749-751、
  `CheckIfAppIsRunning` より前）で `!insertmacro` される。`$UpdateMode`
  を見る削除ブロック（:816）より確実に**前**に走る。
- **ただし `$UpdateMode` は `un.onInit`（Function、Section より必ず先に
  実行される NSIS の標準順序）で既に設定済み**。つまりフックのコード内で
  `${If} $UpdateMode <> 1` を自分で書けば、上流と同じガードを再現でき、
  更新退行を回避できる。research.md §5 は「ガードを持たない削除を重ねる」
  としか書いておらず、これは issue が提示した**素朴な実装**（無条件
  `DeleteRegValue`）を却下する理由としては正しいが、**「.nsh 案は必ず
  退行になる」という強い主張ではなく「素朴に書けば退行する」という
  限定つきの主張として読むべき**。この区別は research.md の文面からは
  やや読み取りにくい（結論の§2でも「足すと更新のたびに…退行になる」と
  断定的に書かれており、「ガード無しなら」の限定が明示されていない）。
  もっとも、§6・§9で「写しの結合」「issue の確認事項」を論じている以上、
  .nsh 案自体は「不要な写しを増やす」という**実装しなくてよい理由**が
  本筋であり、退行リスクは補助的な理由に留まる。結論（.nsh 不要）は
  揺るがない。

偽にする手順: `NSIS_HOOK_PREUNINSTALL` を実際に定義し、ガード無し版と
ガード付き版をそれぞれビルドして `/UPDATE` 付き起動で挙動を比較する
（未実施・下記「壊せなかった項目」に計上——ローカルで実インストーラを
2種ビルドして起動検証するのは本レビューの権限・時間の外）。

1. **debug ビルドと release ビルドの installer.nsi の差分** ⚠️
   実際に差分の存在を確認した: `installer.nsi:10` に `SetCompress off`
   （debug 固有と推測される。release は圧縮ありのはず）。この 1 点は
   実測で「debug と release の installer.nsi は同一ではない」ことを
   示している。**しかし release 版の installer.nsi 自体をローカルで
   生成して比較することはしていない**（`npx tauri build --bundles nsis`
   に `--debug` を付けない実行は時間がかかる上、`target/` を触るなと
   指示されているため未実施）。よって「Autostart 削除ブロック
   （:812-818）が debug 限定ではなく release にも存在する」という
   research.md の暗黙の前提は、**この installer.nsi 単体だけでは
   証明されていない**。ただし該当ブロックは `!if`/`!ifdef` 等の
   条件コンパイルで囲まれておらず、`SetCompress off` のような
   明示的な debug 分岐とは書かれ方が違う（tauri-bundler 側で
   `--debug` フラグが変えるのは主に圧縮設定・ログ出力であり、
   アンインストール手順のテンプレートを丸ごと変える形跡は
   このファイル内には無い）。**確信度: 中**——render soft evidence
   のみで、release テンプレートの直接確認はできていない。

2. **ローカル `node_modules/@tauri-apps/cli` と CI (`npm ci`) のバージョン一致**
   実測: 両方とも 2.11.4（node_modules/@tauri-apps/cli/package.json の
   version フィールドと package-lock.json の resolved version が一致）。
   `package.json` の `^2.0.0` は範囲指定だが、`npm ci` は
   package-lock.json を厳密に使うため決定的。崩せなかった。

3. **tauri.conf.json の実値** 実測: `productName: "Snotra"`・
   `bundle.targets: ["nsis"]`（他ターゲット無し）・
   `plugins.updater.windows.installMode: "passive"`。
   research.md の前提と完全一致。崩せなかった。
