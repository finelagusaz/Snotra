[命題6] 「TopK::merge の結果は葉の順序に依らない(reduce_with にしても結果列は変わらない)」 -> 壊せなかった。条件つき(⚠️)。
  根拠: scoring.rs:172-181 の Ord は score → last_launched → lower_name → cmp_paths(バイト順)。同一 index は Equal、異なる index でも
        target_path は dedup で一意なので全順序。top-k は全順序の下で到着順に依らない。reduce(identity, op) と reduce_with(op) は
        op の結合順が同じで、identity は op(空, x)=x を満たす(merge は空へ push、extend は空へ extend)。index の連結順も左→右のまま。
  穴: 「全順序」は target_path の一意性に依る。SearchEngine::new は任意入力を受けるので、同一 target_path 2 件を渡せば cmp_paths が Equal になり、
        top-k 境界をまたぐときだけ選択が併合順に依る。製品は scan_all/scan_path_env の dedup 後なので影響しない見込みだが、
        私は 22,660 件(PATH マージ後)の target_path 一意性を実測していない。
  偽にする手順: 索引の全 target_path で重複を数える(0 でなければ境界での Equal が起こりうる)。PathStore は private なので
        indexer 側(IndexTree の raw_path_into)で全件組み立てて HashSet に入れる。

## research.md の他の主張

[E1 壊せた] 判定5「葉の税が乗るのは、候補が 2×MIN_PAR_CANDIDATES を超える打鍵だけ。co・code は『候補の広い2打鍵目』」
  -> 機序が誤り。co も code も「候補が広い」のではなく、incremental 再利用が外れて全件走査になっている。
  根拠: query_plan.rs:77-90 kana_query = migemo_enabled && ASCII && 文字数 >= migemo_min_chars(2) && ローマ字がかなに完全変換できる。
        c -> None(1 文字)、co -> Some("こ")、cod -> None(「こd」は ASCII 残留で None)、code -> Some("こで")。
        search.rs:246-250 can_reuse の kana_monotonic: (Some, None) => false。ゆえに c->co と cod->code は再利用が外れる。
        一方 cod は (None, _) => true で再利用でき、候補が少ない。実測の葉数と一致(co:32, cod:2, code:32)。
        葉数 32 は候補 >= 16K を要する(min_len 512 で分割下限)。c の一致は約12K(local_matches のバイト数から推定)なので、
        co が c の一致のみを再利用したなら 32 葉は出ない。
  含意: migemo 有効(実 config)では、かな変換可能な語の 2・4... 打鍵目ごとに全件走査 + 葉の税が乗る。research の
        「cod は葉が2つで税が乗らない」は正しいが、「code は候補の広い2打鍵目」は事実と違う。
  偽にする手順: co/code の 2 回目検索で use_incremental(can_reuse)を eprintln して true なら偽(製品コードを触るので私はしていない)。
        代替: 候補数を直接読めるテスト内フックは無いので、migemo_enabled=false の config で co の葉数が減る(2〜24)ことを見る。
