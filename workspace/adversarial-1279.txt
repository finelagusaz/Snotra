[B2] research.md「技術的制約」: 発行 1 回あたりの matches は Arc 比較で O(1) になる、は条件付き(書き方を誤ると偽)

 実測(t/a.rs): `x == y`(Arc 同士・同一 Arc)= 比較関数呼び出し 0 回 / `*x == *y`(deref したスライス)= 200 回。別 Arc で中身が等しい `x == z` も 200 回。
 研究メモは「&Arc で比べる」とは書くが、`&Arc == &Arc` 以外(deref 版)で黙って O(n) に戻る罠を書いていない。matches に単体テストが無い(grep: `.matches(` は view.rs 1156 だけ)ので、書き間違えても緑のまま推移する。
 偽にする手順: matches を `**cur_rows == **rows` で実装し、同一 Arc を渡して比較回数を数える(カウント付き PartialEq の型で 200 回)。

[B4] 命題 5 の細部: 「trailing の結果着で同じ内容の行が届いた場合、別の Arc になるので中身比較が走る」— 走るが、その比較は無駄で、並びの修正で消せる(研究メモに無い)

   フレーム N: on_input_changed → reset_selection・debounce.on_input()(armed=true・leading=true なので run_search_with)。Plain なら search_tx.send のみ(set_results は呼ばない。空クエリ/indexing/送信失敗のときだけ set_results(Vec::new()))。発行 1: input_idle が true→false(行は同じ)。

   → 「発行 4 回・行の内容が変わるのは 1 回」は、単発打鍵では正しい。ただし put_rows は 2 回走る(世代は 2 つ進む)ので、Vec→Arc 変換(確保 1 回+要素の memcpy)も 2 回走る。変更後に打鍵あたり払うのは「Arc 変換 2 回+Arc::clone 4 回」で、0 ではない。

[W1] ⚠️ 無変化フレームの matches の額は小さい(約 1.1us/200 行・合成データ)
 issue は「main の毎フレームの matches は行の全件を中身で比べる(額は未実測)」。t/b.rs の合成行(名前27B・パス60B前後・200 行)で別 Arc 同一中身の比較が 1.15us、同一 Arc は 0.009us。実 config の行・実 CPU キャッシュ状態(発行ブロックは 1 フレームに 1 回・ほぼコールド)では上下しうる。1 フレーム 16.7ms に対し 0.007% で、今回の変更の価値は「発行時の深い複製(約 12us)を無くす」に集中する。額の主張に 1us を使うなら実データで測り直すこと。
 偽にする手順: results_view.rs の隣に matches 単体のプローブを置き、実 index.bin から作った 200 行で測る(未実施)。

[W2] ⚠️ Vec→Arc 変換のコスト(put_rows 側の memcpy)は未測定
 SearchResult は String×2+IconSource(String を持ちうる)+bool×2 で約 80B 前後。200 行で約 16KB の memcpy+確保 1 回。t/b.rs の「clone Vec + From<Vec>」12.0us は Vec の clone(String 複製)を含むので From<Vec> 単体の額ではない。分離して測っていない。受け入れ条件「確保が行数に比例しない」は put_rows 側の確保(1 回)・バイト(比例)を含めると文言が曖昧になる。発行側とは別の層に帰属する、と書き分けること。
 偽にする手順: put_rows 前後で heap_trace::snapshot() の allocs 差を取る(feature 付きビルド・計数専用)。

[W3] ⚠️ view.rs 側の `rows` の組み立て方(空のとき Arc::default() を毎フレーム作る)の費用
 非表示フレームは Arc::default()(確保なし・static の参照カウント加減算 1 往復)を毎フレーム作る形になる。確保は 0 だが、原子操作が毎フレーム乗る(無視できる額と見ているが未測定)。代替は Arc を作らず Option で空を表すこと。matches の rows 引数を &Arc にする案と衝突するため、設計時に選ぶ必要がある(研究メモは言及なし)。

[W4] ⚠️ ptr_eq を固定する検知器の席: 「rows() の前後で同じ Arc」案(b)は必要条件にすぎない
 SearchState 側で move_selection の前後に Arc が同じと固定しても、発行側(view.rs)が Arc::clone を使っていることは何も保証しない(B3 参照)。発行側まで縛るには、発行ブロックを関数へ出して「同じ state→同じ Arc を指す snapshot」を単体テストで固定する案(a)が必須。AGENTS.md「検証の層と、層と層の隙間」が言う境界の穴に当たる。
 偽にする手順: 発行側を Arc::from(slice) に変異させたコードで、案(b)のテストだけが緑のまま推移することを確かめる(変異テスト・未実施)。

[W5] ⚠️ 並行性: snapshot の Mutex を握ったまま行う作業が変わる
 現行は guard を握った状態で rows.into()(深い複製 12us)を実行する。変更後は Arc::clone だけで guard 保持時間が短くなる(results ウィンドウとの競合が減る方向)。逆方向のリスクは見当たらないが、race-check(AGENTS.md 条件別チェック: 共有状態を扱う変更)の対象かは未判断。
