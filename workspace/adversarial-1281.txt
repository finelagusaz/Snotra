B2. [research omits incremental reuse entirely; it is the main branch-selection gate for BOTH candidates]
  search.rs:246-258 `can_reuse`: reuse iff mode same, prev_candidates non-empty, norm_query.starts_with(prev_query),
  `(!plan.has_dot || prev_query.contains('.'))`, !has_path_sep, kana monotonic.
  Consequences at the real operating point (substring, interactive typing):
   - A full scan with the dot branch runs essentially ONCE per dot-query: on the keystroke that introduces '.'
     ("foo" -> "foo." cannot reuse). Later keystrokes ("foo.t", "foo.tx") reuse the (small) set matched by "foo.".
     Candidate 1's real-world frequency = one full scan per typed dot-query, not per keystroke.
   - Candidate 2 (find) likewise runs a full scan only on the first keystroke / non-monotonic edits / empty-prev cases;
     later keystrokes scan only prev_candidates. The first keystroke is typically 1 char, which matches a huge share of
     entries, so per-match work (with_normalized_key derivation + 3 history lookups, scoring.rs:482-515) can dominate
     over find cost -- research's microbench is find-only (research itself says so) but the proposed "alternating 3x" must
     choose queries that are selective AND defeat reuse.
  Any benchmark for candidate 1 must (a) type a non-dot query first then the dot query so the full scan happens, and
  (b) reset with a non-matching query (RESET_QUERY "zzzz" pattern in tests/search_allocations.rs:149) between repeats;
  otherwise it measures the reused small set (a different branch = the "instrument measures a different branch" trap).
  How to falsify: call search("foo.txt") twice in a row on one engine and time the 2nd (reuse => much faster); or read can_reuse.

=== ENVIRONMENT / BRANCH-COVERAGE FINDINGS (⚠️ = uncertain) ===

E1. Real operating point branches: Substring (find twice on ~82% flagged entries for dot queries), migemo off => kana_substring_score
  site NEVER fires (candidate 2's kana sub-site has zero effect here; research already notes), path site fires only for
  separator queries (path_query_cost.rs) and its cost is dominated by with_normalized_key derivation (ADR-path-query-forward-single-pass.md,
  PERFORMANCE.md ~1316-1324 show per-byte scan cost is NOT the dominant term; memchr/SIMD `contains` already used there).
  ⚠️ So Finder gain at the path site is bounded by the find share of a frame that is mostly derivation.

E2. Fuzzy default (other users) flips the priority: candidate 1 is worth MORE (a nucleo match, ~10x a substring find, runs twice for every
  flagged entry that passes the mask; fn_mask==name_mask for flagged so the mask does not cull the duplicate), candidate 2 is worth
  ~0 (Fuzzy arm never calls find; only the kana/path sites remain, and kana needs migemo). The existing Fuzzy ladder
  (bench_fuzzy_search_scaling) has no dot query and no flagged entry, so it cannot show it either. Fuzzy + dot + flagged requires a
  new fixture (name == file_name, e.g. is_folder=true entries whose name has no dot-stem mismatch). ⚠️ Magnitude unmeasured.
  Falsify: bench Fuzzy with flagged entries, query "foo.bar", with/without the 1-line change, interleaved x3.

E3. ⚠️ A Finder built unconditionally in QueryPlan would cost an allocation + prefilter setup in Fuzzy/Prefix searches where it is
  unused (every keystroke). Construct lazily/only for Substring (or only for the 3 sites) -- research's (a)/(b) comparison ignores this.

E4. ⚠️ Research benchmark plan risk: "ラダー(合成)" + "実 index.bin" both ignore PATH merge (include_path_env=true in the real config;
  search_allocations.rs doc says PATH merge is not passed). PATH entries are unflagged exes and are the ONLY entries where
  dot queries ("git.exe") produce hits via the fn branch that candidate 1 leaves intact. Result-equality validation must include them
  (the differential test over flagged-only entries would miss the unflagged fn branch).

E5. ⚠️ Cheaper unconsidered baseline for candidate 2: std `str::contains(&str)` has an x86_64 SIMD fast path (the repo already
  relies on it: ADR-path-query-forward-single-pass.md:38, PERFORMANCE.md:1240), `str::find(&str)` uses Two-Way. A miss-test via
  `contains` before `find` (or memmem) is a third arm worth including in the microbench; research compares only find vs memmem.
  Falsify: add contains+find arm to the scratchpad microbench.
