F5  incremental 条件 2 — 壊せなかった
================================================================
根拠:
- search.rs:255 は plan.norm_query.starts_with(self.prev_query) で判定（正規化済み同士のバイト prefix）。
- 反例を探した: (a) 合成が起きる打鍵（か → が）は norm が prefix にならず full scan。(b) e → e+U+0301 は NFC+fold で n2 == n1（同一）。
  starts_with は真だが同一クエリなので候補集合は同じ。(c) ł→ł+U+0301 は C 構成の固定点で l に収束、n2 == n1 の側。
  (d) Hangul L+V+T は prefix にならない（合成で先頭が変わる）。
- 論理: Substring・Prefix は n2 ⊇ n1 の prefix なら名前が n2 を含む⇒n1 を含む。Fuzzy は needle の prefix 拡張で単調（nucleo の needle は文字列の prefix）。
  名前列は同じ世代で固定。ゆえに NFC 化は prefix 判定の健全性を変えない。
- ただし弱い点（壊せなかったが ⚠️）: 構成が非冪等（F3）だと prev_query（1 回適用）と新クエリ（1 回適用）の関係は、前回が a(q1)、今回が a(q2) で比較される。
  q2 = q1 + 結合文字 のとき a(q2) が a(q1) の prefix にならない（full scan へ倒れる）か同一になるかのどちらかで、健全側。
  prefix と判定されて前回の候補に無い名前が一致する例は見つからなかった。探した範囲: 基底（fold で変わる 1,823）×結合（1,952）の対で、
  prefix 判定になる対を数え上げて照合するところまでは実行していない。⚠️ 論理による結論であって、全数の実測ではない。
- ⚠️ 副次: ASCII ゲート。kana_query は「クエリが ASCII のみ」で建つ。現行では e+U+0301 は非 ASCII のため kana_query=None。NFC+fold 後は "e"（ASCII）なので
  Some になりうる。条件 4 は(a)今回 None は無条件 OK、(b)今回 Some なら前回も Some を要求。None→Some の遷移は full scan（健全）。
この所見を偽にする手順: 前回 q1 の候補集合に無い名前が、q2（norm が q1 の prefix 拡張）で一致する (q1, q2, 名前) を見つける。名前が q1 を含まず q2 を含む
  ことは Substring では起こりえない。
