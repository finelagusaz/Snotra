## 命題 5: 宣言した集合 + mergedAt 以降に閉じた issue で現行 (1)(2)(3) を覆える → 壊せた(部分的)
覆えない/弱くなる点:
a. 事後突合せは検出のみで予防にならない。誤爆の復旧は reopen で close イベントは履歴に残る。予防は事前の「宣言 vs closingIssuesReferences」照合が担う。
b. commit message 経由の close は closingIssuesReferences に出ない(SKILL.md 手順 3)。覆うのは事後検索だけ。一方 (1)「全件が閉じたか」は番号で state を引く必要がある(検索だけだと索引遅延で偽陰性)。
c. 並行セッションの無関係 close は誤報(research Q4 の指摘どおり)。誤報方向なので安全側だが、頻発すると人が慣れる。issue の timeline `closed` イベントの帰属(今回のマージ由来か)で絞れるか未確認(⚠)。
d. クロスリポジトリ参照: `Closes owner/other#N` は他リポジトリの issue を閉じる。`--repo` 固定の検索は拾わない(⚠ closingIssuesReferences が他リポジトリ分を含むかは未実測)。
e. `gh pr merge` が非 0 を返すが実はマージ済み、の場合: `gh pr view --json state,mergedAt` で確定してから検証へ進む必要がある。
