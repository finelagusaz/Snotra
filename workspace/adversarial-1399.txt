P1. find_matching_tools is the only place a path condition is compared against a launched path.
  Verdict: NOT BROKEN (could not break). Grep over src-tauri/src, snotra-settings/src, snotra-egui-runtime/src, snotra-core/src for extract_path_condition / starts_with(cond): the only consumers of extract_path_condition are opener.rs (find_matching_tools, opener_specificity_order, extract_ext_part) and settings tabs/opener.rs:52 (form prefill, no matching). Tray menu goes resolve_tools closure -> commands::resolve_all_openers (tray.rs:441) -> launch.rs:158 -> find_matching_tools. Other equality-ish sites exist but compare *rule targets to rule targets*, not condition vs launched path: settings tabs/opener.rs:177,369,378 `r.target == target` and normalize_openers dedup (opener.rs:213 `existing == &target`). Those are a related NFC/NFD hole (an NFC and an NFD rule for the same dir are never folded/deduped, and edit-in-place misses) but out of the claimed scope; research.md does not mention them. is_preset_already_added compares exe file names only.
  Falsify: find a new caller that does prefix/eq on OpenerRule.target (e.g. grep '\.target' in src-tauri/snotra-egui-runtime) - none found.

P2. Callers pass the raw entry/history path.
  Verdict: NOT BROKEN. launch.rs:107/158 take `path` from the IPC/tray; activation.rs:110,517 pass `result.path.clone()` / `row.path.clone()` from SearchResult. Tray recent menu: Engine::recent_history -> search.rs:457-492 looks up by *normalized key* but returns scoring::result_at(entries, i), i.e. the entry's real path, not the lowercase key (so it is raw, not the normalized key). Folder-navigation rows come from folder.rs (read_dir, OS spelling, line 65 to_string_lossy). Caveat (⚠️ uncertain): I did not trace scoring::result_at to confirm it rebuilds exact OS spelling from the compressed path store; research's claim "NFD possible" depends on the index storing raw spelling (indexer scan uses OS names, so very likely).
  Falsify: unit-test engine.recent_history with an NFD entry and assert result.path bytes equal the NFD input.

P3. Composing only the path side would regress NFD-extension rules.
  Verdict: NOT BROKEN (confirmed, with nuance). kind_match (opener.rs:97-107) compares path_ext (slice of path_lower after last '.') with raw to_lowercase(rule ext) + '.'. normalize_extensions (paths.rs:61) does trim/lowercase only. So an NFD-spelled extension in a rule matches an NFD path today; composing only path_lower would break it. Nuance: trivially reachable only for non-ASCII extensions (very rare); the research's "regression" is real but near-theoretical. Also: NFC rule ext vs NFD path ext fails today (same hole as the issue) - research says "拡張子もパスから切り出している" and lists it as open question 3, fine.
  Falsify: test with rule "ext:.é" in NFD and path "C:\\a.é" in NFD after path-only composition.

P4. Boundary check and specificity must use composed lengths; opener_specificity_order would disagree.
  Verdict: boundary half: NOT BROKEN (confirmed: opener.rs:88 indexes path_lower.as_bytes() at cond_lower.len(); both must be the composed strings, else byte offset lands mid-char or wrong place). Specificity half: partly BROKEN as stated / understated:
   - research says raw-length specificity only makes ties break wrongly ("NFD の方が長く ... 同具体度なら定義順が効かなくなる"). It is worse: specificity is compared across *nested* rules that all match the same path. Rule A = NFD "C:\ゲ" (+3 bytes for U+3099) vs rule B = NFC "C:\ゲ\a": after path composition both match; raw len A = NFC_len+3, B = NFC_len+2 (for "\a") => A (shallower) wins over B (deeper). So wrong-winner, not just tie-break. Fix needs composed length in find_matching_tools (opener.rs:116).
   - "opener_specificity_order would disagree with find_matching_tools": ⚠️ overstated. find_matching_tools does NOT depend on rule order except for equal specificity (defined as earlier index wins, :118-123). The sort in normalize_openers (:224) only supplies (a) tie order and (b) settings-UI display order (settings tabs/opener.rs:100). So the sort disagreeing matters only for tie-break between canonically-equal-length rules and display. Also opener_specificity_order is called with the stored (lowercased, not composed) target; making it compose is optional, not required for correctness.
   - also unnoticed: split_ext_and_path/extract_ext_part use byte arithmetic (opener.rs:49 `after_ext.len() - path_cond.len() - 1`) where path_cond is `.trim()`med in split_ext_and_path (:147) - pre-existing latent mismatch if a target has trailing whitespace; unrelated to NFC but fragile if someone composes the target before splitting. Composing in find_matching_tools after extraction (not the target) avoids it.
  Falsify: unit test as above (nested NFD shallow vs NFC deep rule).

P5. lowercase-then-compose on both sides yields equal strings for canonically equivalent inputs.
  Verdict: NOT BROKEN for all single code points, ⚠️ uncertain for sequences/Rust-vs-Python. I enumerated all 0x110000 scalar values with Python 3 unicodedata: NFC(lower(c)) == NFC(lower(NFD(c))) holds for every c (0 mismatches), and NFC(lower(NFC(c))) == NFC(lower(c)) too (0 mismatches). Includes U+0130 (İ -> i + U+0307), Kelvin K, Angstrom, Greek (final-sigma context is the only context-dependent case: Rust str::to_lowercase maps Σ to ς at word-final using Unicode Final_Sigma; Python does too). Not tested: multi-codepoint sequences with combining marks whose canonical reordering interacts with lowercasing (none known), Rust's Unicode version vs Python's, and Final_Sigma in path with NFD marks between letters (a combining mark after Σ is Case_Ignorable, handled the same in both forms). Also lowercase-first matches #1394's order and the already-lowercased stored target. Note: stored target lower-cased by normalize_scan_path_key BEFORE compose is fine as shown.
  Falsify: run the same enumeration with Rust (str::to_lowercase + ComposingNormalizer) over all scalars and over pairs (base, combining) - the repo already has normalize_for_match_*_on_every_codepoint detectors in query.rs that could be extended.

P6. NFC in normalize_opener_target (persisted form) would be worse than composing at match time.
  Verdict: NOT BROKEN as direction, but the research's reasoning is incomplete and one of its premises is shaky. Pro-match-time (agree): normalize_opener_target runs only on save/migration, so rules written by older versions or hand-edited config.toml, and (more importantly) the PATH side, still need match-time composition; persisting NFC would not fix the path side at all. Counter-point (⚠️ not in research): persistence is a no-version-bump normalization (apply_migrations already rewrites lowercase), config.toml rewrite on load changes bytes, and AGENTS/ snotra-core CLAUDE says "データの意味を変えるときは版バンプ" - persisting NFC would invoke /persistence-check; match-time avoids it. Counter-counter: normalize_openers dedup (:213) and settings `r.target == target` equality are only fixed by composing the persisted/compared target - so a minimal fix could add compose to normalize_opener_target AND match-time on path side; research treats them as exclusive. Not clearly "worse"; "insufficient alone" is the defensible claim.
  Falsify: show a rule that match-time composition alone mishandles (e.g. two canonically-equal rules both kept, last-wins/dup display) - dedup case above is such a case.
