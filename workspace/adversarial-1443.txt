[F1 / 争点6 / 壊せた] worker は要求を合流（coalesce）するので `settled + dropped` は dispatch 数の下限にすぎない
  根拠: src-tauri/src/egui_shell/search_worker.rs `coalesce` / `spawn_search_worker` は recv 後に try_iter で溜まりを吸い、最後の 1 件だけを走らせて Done を返す。
        間引かれた seq は Done を返さないので settled にも dropped にも出ない（drain_search は Done 受信ごとにしか trace しない）。
        同期クリア（空クエリ・indexing・送信失敗）は dispatch ではないので trace に出ない（これは正しい）。
  影響: 「worker へ送った数 = settled + dropped」は成立しない。コーパスが 1 件でパス検索が sub-ms の smoke ではほぼ一致するが、
        実索引（数万〜30万件・検索 12〜150 ms）では打鍵が詰まると過小になる。正確な dispatch 数が要るなら、
        run_search_with の send 直前に一時 trace を足す（撤去を新設時に決める作法に従う）か、worker 側の `engine.search` 呼出し数を数える。
  偽にする手順: 検索が 100 ms かかる索引で leading と trailing を 100 ms 内に送り、Done が 1 件しか出ないことを trace で見る。

        smoke の L484 コメント「debounce(50ms) の trailing を跨がせる」は、変更後は「バーストを分ける」の意味に変わり、trailing を跨ぐ目的は消える。
  影響: smoke の数は 2n → n の確認にしかならず、受け入れ 2 の検証にならない。受け入れ 2 は Debouncer の純粋核テスト（leading→on_input→poll で発火）か、
        50 ms 未満の間隔で 2 打鍵する別注入が要る。

[F3 / 争点6 / 壊せた] smoke の基準線が決定的でない（Backspace → c の 50 ms 競合）

        PowerShell の Sleep 50 + 注入のオーバーヘッドは 50 ms の周りで揺れるので、main の期待値は 5〜6、変更後は 3 に定まる。
  影響: 「main で 6、本ブランチで 3」と書くと、main 側が 5 でも正常。比較は seq 窓（最初の changed〜3 文字観測）で切り、main は複数回走らせる。

[F7 / 争点1 / 壊せなかった] 同じクエリ・同じ解釈で同じ要求を送る
  根拠: leading は on_input_changed が取った prefix で interp し、run_search_with が同じ state.interp(prefix) を引く（同一フレーム・同一 prefix）。
        trailing は query（set_query は on_input_changed と clear_search だけ。grep 済み）が不変なら同一文字列を送る。
        Engine::search は &self.history と config を読むだけで状態を持たない（PathCursor・増分キャッシュは高速化で、同じクエリの結果は変わらない設計。#1442 の直近修正も別件）。

  補足 ⚠️: trailing が兼ねていた「再読み」は instant_command_prefix だけではない。engine.search は呼出し時に config（normal_mode・boost・result_limit）と history も読む。
        50 ms 以内にこれらが変わる経路（設定ウィンドウ適用・別スレッドの履歴記録）は手操作ではほぼ起きないが、issue の「注意」は prefix だけを挙げている。

[F8 / 争点2 / 壊せなかった] armed の意味を保てば #1038・input_idle・repaint はそのまま
  根拠: poll_search_debounce は poll の返り値で run_search を撃つだけで、armed の読みと request_repaint_after は is_armed() から導く。返り値だけを変えれば不変。
        view.rs の順序は drain_search(L1111) → poll(L1114) → publish(L1165, input_idle = !is_search_armed)。disarm したフレームの publish が input_idle=true を運び、
        results 側の wake も同フレームで発行される。trailing の結果着という次の wake に頼っていない（頼っていたら変更後はアイコン要求が止まるが、頼っていない）。
        on_enter の flush: armed または pending_seq != 0 または restored_rows_stale。leading が遅く（> 50 ms）poll の disarm 後も in-flight なら pending_seq が覆う。
        Debouncer が作り直される（show）ので、持たせる「入力があった」の印も同時に落ちる。cancel/new が印を落とすこと（research.md の制約）が前提。
  新たな効果（良い方向）: 検索が 50 ms を超えるとき、従来は trailing が leading の in-flight を追い越して leading の結果を捨てていた。変更後は leading が採り込まれる。
  偽にする手順: poll が false を返して disarm した直後のフレームで input_idle が false のままか、view.rs の順序を入れ替えて確かめる（現状は入れ替わっていない）。

[F9 / 争点3 / 壊せなかった] leading が送られなかったバーストでも trailing 省略は無害
  根拠: 各経路を確認した。
   - Plain の最初の on_input は必ず leading（armed が false のときだけ true を返す）。cancel 後（Instant・Command・ツール突入・clear_search・Enter flush）も次の Plain は leading。
     Command/Instant → Plain の遷移では armed は cancel 済みなので必ず leading が撃たれる（trailing に救われていない）。
   - 空クエリ・indexing 中・送信失敗は run_search_with が同期クリア。trailing も同じクリアをするだけ。
   - indexing 中の leading のあと索引が完成する場合: finish_index_build は indexing=false を先に、index_generation を後に更新する（state.rs）。
     consume_external_pending（段 5-6）が世代変化で run_search（段 22 の打鍵より前）。完了は indexing.rs の notify_indexing_complete で wake される。
     どの順序でも「leading が indexing=true を読んだのに、世代変化も観測されない」窓は無い（leading が indexing=true を読むなら、その後の finish は次フレームで世代として観測される）。
   - Folder へ入った後の trailing は Folder ブランチの再フィルタにすぎず、検索は出さない。Escape で戻ったあとの未反映は restored_rows_stale と Enter flush が覆う。
     trailing が Results に戻った後で救うのは「Escape が最後の打鍵から 50 ms 以内」という窓だけで、人の操作ではほぼ起きず、従来もほとんどの場合 folder 中の poll で落ちていた。⚠️（極小の窓として残る）
   - Tool ビューは run_search_with が no-op。
  偽にする手順: leading 経路の run_search_with が早期 return する分岐（Tool・Folder 以外）を探す。見つからなかった。
