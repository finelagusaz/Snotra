1. 子孫に入りうる／hide のたびに trim される : 壊せなかった（実機で補強）。ただし「起動したアプリが実際に失う額」と「Command 経路の比率」は別。
2. trim すべき子孫は自プロセス + 設定サイドカーだけ／サイドカーは子を作らない : 前半は壊せなかった。後半は壊せた（偽）。
3. 擬似ハンドル / Child の raw handle で EmptyWorkingSet できる : 壊せなかった。ただし「ロックを放してから raw handle を使う」実装は壊れる（下の F3）。
4. lock() で止まりうる／try_lock でよい／state.rs 規範の射程外 : 壊せなかった（前提の強度は弱める）。
5. collect_descendant_pids は消せる : 壊せなかった。ただし消すと連動する残骸が 4 件ある（F6）。
6. 受け入れの測り方 : 壊せた。measure:memory は本変更の分岐を一切通らない（F5）。

== 所見（各々に偽にする手順）==

F1. [確認] ShellExecuteW で起動した exe / lnk / 関連付け文書は、呼び手のプロセスの子になる（争点 1 を実機で補強）。
  実験: 一時 PowerShell プロセス（PID 38016）内から ShellExecuteW を直接呼び、winver.exe（exe）・charmap.exe を指す .lnk・.txt（関連付け、Win11 の packaged Notepad）を起動。
  3 件とも ParentProcessId = 38016（呼び手）。Notepad は子 Notepad(孫)まで付いた。結果: Toolhelp の BFS はこれらを子孫として拾う。
  なお 実験の一時ファイルと起動プロセスは削除・終了済み。常駐 snotra は実験時に存在しなかった（Get-Process に snotra 無し。争点 1 を「常駐の子」で直接見ることは不可）。
  偽にする手順: 開発ビルドを SNOTRA_CONFIG_DIR 付きで起こし、Snotra から実際にアプリを起動して Get-CimInstance Win32_Process -Filter "ParentProcessId=<snotra pid>" が空になる起動経路（exe/lnk/folder/URL）を 1 つでも見つければ「通常は子」は弱まる。今回の実験の限界: 呼び手は Snotra ではなく PowerShell（STA / 昇格状態は同じ非昇格）。

F2. [壊せた] research.md「設定サイドカーは子プロセスを作らない（Command::new / ShellExecute が 0 件）」は偽。
  snotra-settings/src/app.rs:493,496 と tabs/backup.rs:115 が open::that を呼ぶ（Web / Mail リンク・データフォルダを開く）。open::that は子を作りうる（ブラウザ・メーラ・explorer）。grep の語彙が Command::new / ShellExecute に限られ、open クレートを見落とした。
  帰結: 現行コードはこれらの子孫（ブラウザ等）も trim している。新設計では trim されなくなる。これは「望ましい」方向だが、「従来 trim されていた子は無い」は偽。PR 本文・コメントに「サイドカーは子を作らない」と書くと偽の全称になる。
  偽にする手順（=この所見を覆す手順）: git grep -n "open::\|Command::new\|ShellExecute" -- snotra-settings/src が 0 件になる（今は 3 件）。
  補足: 同様に src-tauri 側の spawn は launch.rs:65（opener ツール）・:268（exec instant command）・window.rs:82（サイドカー）、snotra-core/src/folder.rs:440 の attrib（索引構築中の短命子）。updater は tauri-plugin-updater の installer 起動 + std::process::exit(0)（updater_toast.rs の doc）で hide と無関係。従って「他に trim すべき子は無い」（争点 2 前半）は壊せなかった。

F3. [壊せた・実装上の罠] 争点 3/4 の「try_lock で取って Child の raw handle を使う」は、ロックを放してから raw handle を使うと use-after-close になる。
  Child は main.rs:575（exit ハンドラの child.kill() 後 drop）と window.rs の監視スレッド（*guard = None）が別スレッドで落とす。Child の drop で CloseHandle される。raw handle を取り出して guard を放し EmptyWorkingSet を呼ぶと、その間に閉じられたハンドル（再利用で別オブジェクトの可能性）を叩く。
  対処: EmptyWorkingSet の呼び出しが終わるまで guard を持つ（数 ms。監視スレッドの 250ms ポーリングと hotkey リスナーの lock().unwrap() を一瞬待たせるだけ）。または DuplicateHandle。research.md の「Child を持っている間は PID 再利用の問題が無い」は、持っている間だけ真。
  偽にする手順: guard をスコープ末尾まで持つ実装で、監視スレッドの終了とのレース（kill 直後の hide）を再現して、アクセス違反・誤ハンドル操作が出ないことを確認する。

F4. [壊せなかった] lock() の害は deadlock ではなく短時間の停止にとどまる。
  launch_settings_process は spawn 中だけ lock を保持し、drop(guard) の後で set_always_on_top する（window.rs: `*guard = Some(child); drop(guard);`）。監視スレッドの保持は try_wait の間だけ。ロックを持ったまま別スレッドの応答を待つ経路は見つからなかった。lock() でも停止は spawn 時間（AV 次第で数十〜数百 ms）。try_lock は「止まりうる」への十分な対処で、必須ではない。research.md の「止まりうる」は事実だが「デッドロック」ではない。
  state.rs read_config の規範の射程: doc は「read に渡すクロージャの中」の話（壊せなかった。hide_egui_main は read_metrics の後で guard を保持していない）。
  偽にする手順: hide_egui_main から trim までの間に read_config のクロージャ内で呼ばれる経路がある（呼び出し元を LSP で列挙して 1 件でも見つければ偽）。今回は見つからず。

F5. [壊せた・最重要] 計測コードが測る分岐と、変更が触る分岐が違う。
  - scripts/measure-memory.ps1 はルート snotra と子孫を合算するが、計測中にアプリを起動しない。measure-memory-stages.ps1 は段階 C でクエリ（既定 "code"）を入れるだけで Enter を打たない。段階 D は {ESC} の hide。従って「Snotra から起動したアプリ」という分岐を一度も通らず、変更前後で必ず同じ値になる。受け入れ 2（measure:memory で自身の PrivWS が変わらない）は、この変更が自プロセスに掛かる trim を変えないことしか測らない。「自プロセスへの trim が引き続き動く」の回帰検出としては有効（PERFORMANCE.md の 2.2 MiB という期待値）だが、効果も副作用も測らない。
  - 受け入れ 1 は WorkingSet64、measure は PrivWS（WorkingSetPrivate）。軸が違う。受け入れ 1 は別手段（Get-Process）で、起動 → hide → 再計測を手で行う必要がある。
  - 陰性対照が要る。変更前（main）のビルドで「hide 後に起動アプリの WorkingSet64 が落ちる」ことを先に再現しないと、変更後に落ちなかったことは何も示さない。対照アプリも要る（Snotra の子でない起動、例: explorer 経由）。アプリの WS は起動直後に自然に増減するので、複数標本で比べる。
  - 設定サイドカーが「今までどおり trim される」（受け入れ 3）も、どの計測も通らない。Snotra 実行中に open_settings → hide → サイドカーの WS を見る手順を別に決める必要がある。
  - measure-memory.ps1 の冒頭は「現構成でツリーに乗りうる子は設定サイドカー snotra-settings だけである」と書く。F1 で偽。起動アプリの有無で合算値が変わるのは、この変更で消えるのではなくスクリプトの前提の誤り。この変更で偽の記述を残すなら一緒に直す対象。
  偽にする手順: 計測中にアプリを起動する手順（Enter 注入）を足した版で、変更前後に hide 後の WorkingSet64 が差を示すこと。示さなければ、この変更は実機では効果が無い（あるいは測れていない）。

F7. [実運用の経路比率] 実 %APPDATA%/Snotra/config.toml の openers は 1 件のみ: target 'folder:c:\workspace' に Windows Terminal(wt.exe) と VS Code(Code.exe)。拡張子ルールの opener は無い。

F8. ⚠️ 設定サイドカーを trim すること自体が意図どおりか疑わしい（争点 2 の「意図した」）。
  サイドカーは可視の対話 UI。hide の合流点で trim が掛かるのは、典型的にはサイドカーの起動直後（main から開いて main が hide する場合）で、初期化・初回描画の最中に working set を落とす。ホットキーはサイドカー存命中は無視される（main.rs:430）ので、「サイドカー存命中に main が hide する」場面は起動直後か focus-lost 経路に限られる。その trim が得か損かを測った記録は見つからない（PERFORMANCE.md に設定サイドカーの hide 時 trim の計測は無い。grep: working_set / EmptyWorkingSet の出現は 87, 95, 150, 584, 2618 行で、いずれも本体）。
  issue の受け入れ 3 は維持を求めているので維持が既定。ただしチーム憲章（簡単にする方向の指摘を歓迎）の観点で、「サイドカーの trim をやめて自プロセスのみ」案を選択肢として併記する価値がある。ただし挙動変更なので、やるなら issue の合意が先。
  偽にする手順: 設定を開いた直後と hide 後の snotra-settings の WS/起動レイテンシを trim あり・なしで 1 回ずつ測る。差が無ければ F8 は無害として畳める。

F9. ⚠️ 起動アプリで本当に害が出るかは未測定のまま（issue 自身が認める）。
  EmptyWorkingSet は soft fault で戻るため、メモリに余裕があれば体感差は小さい。ただし機序（ShellExecuteW → 子 → 子孫 BFS → EmptyWorkingSet）は F1 と working_set.rs のコードで成立。確度「機序はコードで確定」は壊せなかった。額は未測定のまま。優先度の「測った額が小さければ #1445 と入れ替わる」という issue の条件は、F5 の測定が済むまで評価できない。
  偽にする手順: 変更前のビルドで起動アプリ（例: VS Code）の hide 前後の WorkingSet64 と、起動直後のウィンドウ操作の再 fault 量（PerfCounter Page Faults/sec）を測り、差が誤差内なら効果は実質ゼロ。

F10. [壊せなかった] 擬似ハンドルと Child の raw handle の権限（争点 3 の前半）。
  GetCurrentProcess の擬似ハンドルは PROCESS_ALL_ACCESS 相当、Rust の Command::spawn は CreateProcessW の返すハンドル（PROCESS_ALL_ACCESS）を Child が保持する。EmptyWorkingSet が要る PROCESS_QUERY_INFORMATION | PROCESS_SET_QUOTA は含まれる。実機でこの呼び出しを行う実験はしていない ⚠️（コードは変更禁止・スクラッチ実験は F1 に使った）。
  偽にする手順: 開発ビルドでサイドカー起動後に hide し、サイドカーの PrivWS が落ちること（または EmptyWorkingSet の戻り値が成功であること）を採る。
