## 命題 2: first-run の起動形を cache-miss に流用しても first-run と同じに働き、first-run 固有の分岐が誤発火しない
[壊せなかった] window.rs:166 の `is_indexing() && !is_index_build_started()` は、設定アプリ起動後の監視スレッドの中にしか
無い（`is_index_build_started` の読み手はここ 1 か所だけ）。cache-miss は設定アプリを起動しない。setup で
`start_index_build` を呼べば `try_begin_index_build` が started=true を立てるので、仮に発火しても条件が偽。
[壊せなかった] `is_indexing` の読み手は ensure_not_indexing（/s）・open_settings・window_coordinator::read_indexing
（status 行）のみ。どれも first-run と同じ値を見る。tray は platform スレッドのループ変数 `indexing_in_progress` を
SetIndexing で更新する。SetTrayVisible は setup の最後（setup_tray・main.rs 438）なので、SetIndexing(true) が先に届き、
メニューは構築中の状態で作られる。
[壊せた] 「first-run の起動形をそのまま使う」は、契約検査と起動計測の分岐を壊す形に読める。
  - first-run の起動形は `startup::mark(Phase::IndexLoad)` を通らない。SnotraStartupContract.psm1 の `$skippedByBranch` は
    「index_load が null であってよいのは first_run のときだけ」。cache-miss を first-run 形で書いて `first_run:false` のまま
    IndexLoad を刻まないと、bench-startup（CI の観測ステップ）で「説明されない null: index_load」になる。逆に
    `first_run:true` を立てると、cache-miss と first-run が計測上区別できなくなる。research.md は
    「set_index_load_stats_total / set_branch / mark(IndexLoad) を刻む」と書くが、「first-run の起動形を再利用」との
    両立（どの分岐でどちらを刻むか）は未記述。
  - `index_load_unattributed_ms` の非負性: 新しい入口が返す stats.total は外側の区間以下でなければならない。
  偽にする手順: main.rs の分岐を `if is_first_run || cache_miss {空材料}` に畳み、set_branch を first_run の else でだけ
  呼ぶ。bench-startup.ps1 -UseVerificationProfile の最初の run が契約違反になる（実行はしていない。コードの読みからの帰結）。
[壊せた]（小）main.rs のコメント「initial_indexing は first-run でしか立たないので、そこから導くと非 first-run の cache-miss が

だったので実害は見つからなかったが、コメントは書き換え対象。

## 命題 3: 昇格は cache-hit でしか起きず、INDEX_WRITE_LOCK の doc は偽にならない
[壊せなかった] load_cache_in の旧版分岐はハッシュ不一致で None を返し（走査へ落ちる）、昇格は一致したときだけ。
drain_index の読み直し（`load_cached_material`）は LegacyUpgrade::Skip 固定。背景構築の書き手は `rebuild_and_save`
（ロック内）だけ。昇格を main の起動段に残す限り、doc の「索引ビルドのスレッドはまだ居ない」は真のまま。
  偽にする手順: 背景スレッドから `LegacyUpgrade::Write` の読みを呼ぶ。または背景構築を起こした後に main 側で
  load_cache_in(Write) を呼ぶ。（research の方針はどちらでもない）
⚠️ 入口を分割するとき、ロックの外で `Write` の読み → miss と判明 → 空を返す、の順を保つ必要がある。miss の判定を `Skip` で
行うと、旧版かつハッシュ一致の昇格が起きなくなる。research.md は新入口の `LegacyUpgrade` 引数を明記していない
（「昇格は起動の読みに残す」とは書いてある）。

     なり、`cache_hit` 列と memory_MB（構築中のメモリを含む）が測る対象が変わる。
