[N1] 命題1: 行ごとの半直線（余白 2 px）の範囲の中だけで今の内外判定を行えば出力は変わらない
  試験: f32 で xs = ax + (bx-ax)*(py-ay)/k、向きは sign(area)*k の符号、k == 0 は範囲を狭めない、lo-2・hi+2 の候補を実装し、
        元の inside 述語と全画素で突き合わせた（t.rs）。
        (a) 一様ランダム三角形 20 万個（座標 0..1920×0..1080）: 内側 8.4 億 px、範囲外へ漏れた内側画素 0
        (b) 1 辺を |dy| = 1e-5〜1e-2 の近水平にした 20 万個: 内側 24 億 px、漏れ 0
        (c) 座標を 0..20000 まで広げ近水平も混ぜた 20 万個: 内側 4.2 億 px、漏れ 0
        (d) 敵対的: 近水平の辺の y を行の中心（n+0.5）に ±1e-6〜1e-4 だけずらし、|dy| = 1e-7〜1e-4（t2.rs）: 内側 26 億 px、漏れ 0
  理屈: 境界の x* の誤差は「相対 6e-8 × |x*-ax|」なので、2 px を超えるには |x*-ax| が 3e7 px 級でなければならず、画面外である。
        k が極小でも、py-ay は Sterbenz で正確、積の相対誤差は x* に比例してしか効かない。
  NaN / inf: 頂点が NaN → area が NaN で `abs() < EPSILON` は偽（スキップされない）、min_x は clip へ落ち、max_x の `NaN as usize` は 0 → 空範囲。
        現行も w が NaN で inside が常に偽。範囲の側が NaN になっても、範囲内で現行の判定を残す限り、描かれる画素は現行の部分集合かつ
        現行が描く画素を落とさない（NaN の min/max は Rust の f32::min/max が NaN を無視するので狭めない側へ倒れる）。
        頂点が inf: max_x は usize::MAX（clip で切れる）。w が NaN で何も描かれないのは現行と同じ。
  clip による切り詰め・min_x..max_x の境界: 範囲を min_x/max_x との交差にして負の浮動小数は `as usize` が 0 へ飽和するので問題は起きない
        （実装が `.max(min_x)` を忘れても、飽和が 0 を返すだけで min_x より下を描く＝現行より余計に描く方向の誤りになりうる点だけが残る。
        これは実装の注意で、命題の反例ではない）。
  限界: 試験は inside 述語の集合一致のみ（画素の色の計算は同一コードを通るので同じ）。f32 の演算順序を実装が変えた場合（FMA・逆数の乗算）は別問題で、
        issue もその版を採っていない。
  偽にする手順: 上の候補の margin を -1.5 へ壊すと漏れが出ることを t.rs の margin 引数で確かめられる（issue も同じことを言っている）。

[N2] 命題2: 3 頂点の UV がすべて (0,0) でテクセル pixels[0] が [255;4] なら modulate(color, sample) == color
  Nearest: (u*w) as isize で u は ±0 または NaN。NaN as isize = 0。clamp(0, w-1) → pixels[0]。
  Linear: fx = clamp(u*w - 0.5, 0, w-1)。u = ±0 → -0.5 → 0。x0 = 0、tx = 0。top = c00*1 + c10*0。c10 は u8 由来で有限なので c10*0 = 0。
        ty も同様。out = round(255*...) = 255。-0.0 の経路も t3.rs で fx = 0 を確認。width == 1 / height == 1 でも x1 = min(...) で同じ。
  modulate: (255*c + 127)/255 = c（c を 0..255 で整数除算するので 127/255 が切り捨てられる）。恒等。
  epaint のアトラス: epaint-0.37.0/src/texture_atlas.rs（TextureAtlas::new）が最初の allocate((1,1)) を (0,0) に置いて Color32::WHITE を書く
        （assert_eq!(pos, (0,0)) 付き）。lib.rs:99 の WHITE_UV = (0,0)。textures.rs:31 の doc も「(0,0) に白画素が必須」。
        Snotra 側の CpuTexture は ImageData::Color の c.to_array() をそのまま premultiplied で持つ（raster.rs の image_to_pixels）。WHITE = [255;4]。
  部分更新: apply_texture_delta の Some([x,y]) が (0,0) を上書きする経路は、epaint が (0,0) を再割当しないので無い。
  幅 0 のテクスチャ: sample は [255;4] を返す。
  実行時の判定は pixels[0] を見る方式にしておけば、白でないテクスチャ（ユーザーテクスチャで UV が (0,0)）は自動で除外される。
  NaN の u（巨大座標で b が NaN/inf のとき）: Linear では texel が 0 に化けるが、その場合は同時に color の全チャネルも NaN→0 になるので
        modulate(0, 0) = 0 = 省略版の color と一致する、と推論した（巨大座標の数値例は t3.rs で作れず、inside が偽になった。到達不能に近い）。
  偽にする手順: (0,0) を白でないテクスチャ（pixels[0] = [255,255,255,254] など）で fast path の条件文が通るかを単体テストで見る。
