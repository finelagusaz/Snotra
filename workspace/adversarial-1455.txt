■ 争点 1: fork-join + 根ごとに今の Dedup::accept を同じ順に当てれば出力は逐次と完全一致
  判定: 壊せなかった（条件付き）
  根拠: scan.rs scan_directory_with_extensions は「dir エントリ(include_folders 時) → その場で再帰 → 次の兄弟」の前順。
        スパイクの fork_join(main.rs) は items を readdir 順に積み、Dir の直後にその sub を連結する同じ前順。
        順序の指紋が逐次と fj4/fj8/fj16 で一致（run2.out: 84caed6171d7b0b0、件数 696,226）。
        accept の状態は「呼ばれた列」だけの関数なので、列が同じなら勝者も同じ。check 専用の根は set を読むだけで、set が変わるのは
        record の根だけ（scan.rs:114-122）。
  条件・弱点:
   - 構成で示せるのは「列が同じ」まで。実装時は accept の前段の絞り込み（`!name.is_empty()`・拡張子・include_folders）を
     収集側で逐次と同じ位置に置く必要がある（accept を呼ぶ/呼ばないで set の中身が変わる）。
   - スパイクの指紋は「フォルダ + .exe/.lnk のパス」だけで、AppEntry（name 導出・is_folder）や accept 後の集合は検証していない。
     製品実装後の `index.bin` バイト一致（issue の受け入れ）は未検証。
   - 指紋が一致したのは温めの 4 回。FS が動いた回は 1 件差で指紋が変わる（メモ自身が記載）。非決定は FS 側で、形の差ではない。
  偽にする手順: 実装後に fork-join 版と逐次版の scan_all を同一 FS で比べ、sort 前の Vec<AppEntry> が一致しない根を探す
   （同名で大文字小文字だけ違う兄弟を、大文字小文字を区別するディレクトリに作る fixture が最も鋭い）。

■ 争点 2: 同じ根の中の重複排除（record の根は先勝ち・record 偽の根は落とさない）は現行コードの読みとして正しい
  判定: 壊せなかった
  根拠: scan.rs:114-122。(_, true) は set.insert(正規化キー)＝既出なら false → 先に accept した方が勝つ（根をまたぐ先行も同じ関数で効く）。

        root_roles の doc（:48-69）とも矛盾しない。
  補足（メモの軽い欠け）: 「record の根で先に列挙した方が勝つ」は、先行の根のキーが既に入っている場合は「先行の根が勝つ」が先に効く。
        メモの制約 1 に両方書いてあるので誤りではない。
  偽にする手順: record=true の根へ、正規化キーが同じになる 2 兄弟（`A.exe` / `a.exe`）を置いて scan_all の結果に 1 件だけ残るか見る。
        既存テストは scan_keeps_same_name_different_paths など。同じ根の中の大小文字重複を直に固定するテストは scan/tests.rs には見当たらない

■ 争点 3: DirEntry::metadata は Windows でリンクを辿らず、ジャンクション/シンボリックリンクへは再帰しない
  判定: 壊せなかった（実測）
  根拠: スクラッチに junction と symlink を作り、製品と同じ `read_dir → entry.metadata() → is_dir()` を実行（rustc 1.99.1）:
        "jn" is_dir=false is_symlink=true / "sl" is_dir=false is_symlink=true / "real" is_dir=true。
        jn は祖先（root）へ向けた循環 junction だったが再帰対象にならない。後始末済み（junction は rmdir で外した）。
  限界: 名前サロゲートでない reparse point（OneDrive プレースホルダ・WSL・dedup 等）は is_dir が真のまま再帰される。
        これは現行の逐次でも同じで、並列化で変わらない。本機の maxdepth は 22・最長パス 257 文字（私の計測）。
  偽にする手順: 名前サロゲートでない reparse tag を持つディレクトリが自分の祖先を指す例を作る（通常のユーザー操作では作れないはず）。

■ 争点 4: スパイクは製品の走査と同じ操作を測っているか（実 config を読んで照合）
  判定: 概ね壊せなかった。ただし差が 5 点あり、うち 2 点はメモに書いていない。

      逆に逐次側もスパイクは余分に積んでいるので、逐次 27 s の中身は製品より少し重い可能性。差は I/O（read_dir + metadata）に比べ小さいが未測定。
   b) [書いていない] 拡張子照合: スパイクは eq_ignore_ascii_case("exe"/"lnk") を全根に適用。製品は根ごとの extensions

   c) スパイクの根は `C:/…`（スラッシュ）。製品の根は `C:\…`。子の path は "C:/" + name の混在。PathBuf::push の費用は同等で、

   e) 製品は run 中に UI / 検索 / 設定画面が同居する。スパイクは単独。

     スパイク（11-17〜18）は dirs = 680,8xx。+67,5xx（+11%）の差は 3 日間のファイル増（worktree・target 等）と読めるが、同じ FS の状態では比べていない。
   - 1 ディレクトリあたり: 製品 27.3〜28.1 s / 613,341 = 44.5〜45.9 µs。スパイク逐次 39.0〜41.8 µs（私の再実行: 11-18 に dirs = 680,817・28.4 s・41.8 µs）。

     逐次 27 s という見出しの一致は、dirs の増加と µs/dir の差が相殺した結果で、同じ状態の対応ではない。
   - 報告する価値のある欠落: 11-15 以降の製品側の scan-log が無い。受け入れ条件の A-B-A（scan_ms/dirs）は実装後に同じ日・同じ FS で取る必要がある。

■ 争点 6: 「並列度 8 が最良」はこの 1 台の測定から出ており、min(8) 以外の上限の決め方に根拠の差は無い
  判定: 壊せなかった（メモの自己申告のとおり）。さらに弱点を足す。
  根拠: run.out / run2.out は HAL9000（16 論理コア）1 台。測った点は 1/2/4/8/16 のみ（6・12 は無い）、各点 2 巡。
        2→4→8 は 15.3 → 8.8 → 6.2 s で、8 → 16 は 6.2 → 7.8〜8.0 s に悪化。8 が谷底という以上は言えない。
  ⚠️:
   - 16 論理 = 8 物理コア（SMT）の可能性が高く、「8」は FS の飽和ではなく物理コア数かもしれない。available_parallelism() は論理数を返す。
     `min(8)` は 8 論理（4 物理）の機で全論理を使い、同居する UI/検索を飢えさせうる。反対に 4 論理の機は 4。
   - 冷えた状態の並列は未測定（メモも認める）。冷えの逐次は 85〜117 s で I/O 待ちが混じるため、HDD や遅い SSD での並列は逆効果もありうる。
   - Defender の有無・別の AV・ネットワークドライブの根は測っていない。
   - ワーカーの優先度は下げていない。8 本が常時 CPU を使い切ると起動直後の UI（show_on_startup / 検索）に響きうる。体感の測定は無い。
  偽にする手順: 別の機（4 コア / 8 論理・HDD・企業 AV）で 2・4・8・16 を測り、最良点が 8 でない/16 で悪化しない例を 1 つ出す。
