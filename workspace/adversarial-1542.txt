争点3 ロックと行の割り込み
========================================================================
[壊せなかった（std 1.98/1.99 の stdio.rs を読んだ）]
  - eprintln! → _eprint → print_to → Stderr::write_fmt → (&Stderr)::write_fmt → self.lock().write_fmt(args)。ロックは fmt 全体の間保持。
  - Stderr::write_all も (&Stderr)::write_all → self.lock().write_all(buf)。write_all の部分書き込みのループもロックの内側。
  - ロックは ReentrantLock<RefCell<StderrRaw>>。StderrRaw は無バッファ（研究文書の前提どおり）。
  - 同一プロセス内ではどちらの形でも行は割り込まない。trace.rs の trace() も同じ Stderr を使うので同じロックで直列化される。
  偽にする手順: 2 スレッドが各々 10 万行を eprintln! / write_all で書き、ファイルへリダイレクトして行の連結が崩れないか数える
  （std の実装を読んだだけで、この数え上げは実行していない）。
[⚠️] 「割り込まない」の射程
  1. プロセス内・std の Stderr 経由に限る。stderr のハンドルを継承した子プロセス（WebView2 の msedgewebview2 等）や、
     Win32 の WriteFile を直接呼ぶ依存 crate の書き込みはロックの外にある。1 回書き込みにすると、むしろ
     「ファイル上で 1 行が連続するバイト列になる」確率は上がる（改善の向き）ので、受け入れ条件は壊れない。
  2. eprintln! は format 引数の Display/Debug を、ロックを持った状態で評価する（引数の式そのものはロックの前）。
     Display の中で stderr へ書く実装があると同スレッド内で交錯する（ReentrantLock なので deadlock はしない）。
     現行の 11 件の引数にそういう型は見当たらない（window_id の Debug・String・数値・egui 型の Debug）。
  3. libtest の出力捕捉: eprintln! は OUTPUT_CAPTURE に乗るが、stderr().write_all は乗らない（print_to_buffer_if_capture_used は
     print_to 経由だけ）。出口を stderr().write_all に替えると、単体テストの実行中にその行が捕捉されず端末へ出る。
     テストは W: Write を取る関数（trace.rs の write_line と同じ形）に対して書けば影響しないが、
     計装を呼ぶ既存テスト（input.rs / windows_ime.rs の tests）がもし input_trace を踏むと出力が増える。
     （INPUT_TRACE は env 未設定なら出ないので、実害は env を立てたテスト実行に限られる。）
  偽にする手順: input_trace を W: Write 版へ分けた上で、`cargo test -- --nocapture` なしの実行で端末に行が出るか確かめる。
