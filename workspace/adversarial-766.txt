命題5: 測定環境の疑い — agent側のeffortを覆いうる上書きが存在する
============================================================
判定: 一部について「真」を確認（上書き機構自体は存在する）が、今回の測定環境ではそれが効いていないことも確認した

実際に読みに行った設定ファイル・環境変数:
- C:/workspace/Snotra/.claude/settings.json — effortLevel/modelSettings/ultracode の記載なし
- C:/workspace/Snotra/.claude/settings.local.json — 同上（permissions と outputStyle のみ）
- ~/.claude/settings.json — **トップレベルに `"effortLevel": "high"` を実測**
  （`modelSettings` キーはこのファイルには存在しない）
- env — `CLAUDE_CODE_EFFORT_LEVEL` は未設定。`ultracode` 系も未設定。
  ただし `CLAUDE_EFFORT=high` が実際に設定されていた（`env | grep -i effort` で実測）。

⚠️ 重要な区別（早合点すると誤った警鐘になる所見）:
`CLAUDE_EFFORT` と `CLAUDE_CODE_EFFORT_LEVEL` は**別物**である。バイナリ中の文字列
(オフセット180294201近傍、hookペイロードのzodスキーマ内) を実測すると:
`effort:{level:...describe('Active effort level for the current turn ..., after any silent downgrade
for the selected model. Also exposed to hook commands and Bash as the CLAUDE_EFFORT env var.')}`
→ `CLAUDE_EFFORT` は「このターンで実際に解決された effort を hook/Bash に**出力として**渡す」ためのものであり、
  effortの解決に**読み込まれる入力**ではない。一方 `CLAUDE_CODE_EFFORT_LEVEL`（オフセット94722396近傍、
  `sC()` 関数が読む）は文言 `overrides effort this session` の通り、**入力側の上書き**である。
→ つまり私のBashツール呼び出し環境に `CLAUDE_EFFORT=high` が見えたのは、「今この瞬間の私自身のターンの
  effortがhighに解決されている」ことを示すログのようなものであり、これから起動するcode-reviewerサブエージェントの
  effortに介入する上書き設定ではない。前者を後者と取り違えると「上書きが効いているので測定は無効」という
  誤った結論になるところだった。

上で見つけた `"effortLevel": "high"`（ユーザー設定・トップレベル）の意味を追加で確認した:
- スキーマの説明文（オフセット179124788近傍）: `effortLevel:le(["low","medium","high","xhigh"])...
  describe("Persisted effort level for supported models.")` — これは**セッション全体のデフォルトeffort**であり、
  modelSettings[].effortLevel（モデル別）とは別のグローバル既定値。
- `Y()` 関数（180857895近傍）が `qe()`（設定オブジェクト）から `A({cli:{effort:void 0},env:process.env,
  settings:e})` の形でデフォルトのeffortテーブルを構築しており、これがagentの `{kind:"default"}` 解決先になる
  と読める。

結論として command 5 で確定できたのは:
1. 上書き機構は実在する（`CLAUDE_CODE_EFFORT_LEVEL` env、ユーザー設定の `effortLevel`、`modelSettings[].effortLevel`）。
2. **今回の測定環境ではenv経由の上書きは効いていない**（CLAUDE_CODE_EFFORT_LEVEL未設定）。
3. しかし ⚠️ **ユーザー設定のトップレベル `effortLevel: "high"` は効いている可能性が高い**。
   `.claude/agents/code-reviewer.md` は現在 `effort` キーを持たない（`model: inherit` のみ）ため、
   命題4の3状態モデルでいう `{kind:"default"}` に該当し、これはグローバルな既定効果レベル
   （ユーザー設定の "high"）へ解決されると推測される。つまり**「code-reviewer は今何も指定していないのに
   実は既に"high"相当で動いている」**可能性があり、これは research.md の「残る不明点」欄・issueの
   「effort未確認」という前提そのものを一部修正する。
- 偽にする手順: `qe()`（設定を読む関数）の戻り値と `Y()` の実際の解決結果を、実機でデバッグ出力するか
  `/config` の effort 表示で確認する。静的読みだけでは「トップレベルeffortLevelが本当にdefaultの解決先か」は
  100%確定していない——ここは⚠️付きの推測として扱うべき。

追加で答えた問い: agent frontmatterのeffortは実リクエストへ届くか
============================================================
判定: 届く経路をバイナリ内で末端近くまで追えた（検索文字列つきで報告する）

追跡した経路:
1. mar()（.md agentローダ、184704620近傍）が frontmatter の `effort` を検証済み値 `we` として
   `...we!==void 0&&{effort:we}` の形でagent定義オブジェクトへ載せる（研究のF1で確認済みの延長）。
2. Workflow の `agent()` 実行部（193174883近傍、検索文字列 `workflow_agent_`）で、この定義オブジェクトが
   `ve` という変数名で保持され、`nS({agentDefinition:ve, ...})` として渡される。
   同じ関数内で `on=[...,String(ve.effort??kc(W)??""),ve.agentType,...].join(...)` という形で
   `ve.effort` が直接参照されているのを実測（キャッシュキー/識別子構築のためだが、`.effort` フィールドが
   spawn時点まで生きて運ばれている直接証拠）。
3. **決定的な箇所**: `nS({agentDefinition:e,...})`（185194008近傍、検索文字列 `async function*nS(`）の関数本体で
   `Di=[{kind:"model",mainLoopModel:hn},...e.effort!==void 0?[{kind:"effort",effort:e.effort}]:[]]`
   を実測。agentDefinition（`e`）の `effort` が存在すれば、モデルのオーバーライドと**全く同じ形**
   （`{kind:"effort",effort:...}`）でオーバーライド配列 `Di` に積まれる。この `Di` は同じ関数のその後の
   処理（ツール権限コンテキスト構築など）に渡されていく変数として使われ続けている。
- これは「frontmatterのeffortがagent定義オブジェクトに載る」だけでなく「そのagent定義オブジェクトが
  実際にサブエージェントのターンを構築する関数（nS）の中で、モデルのオーバーライドと並ぶ形で
  effortのオーバーライドとして明示的に取り出されている」ことを示す、issueの残る不明点に対する
  かなり強い実証である。
- 追えなかった部分（正直に書く）: `Di`（kind:"model"/"effort"のオーバーライド配列）がその後、
  実際のAnthropic APIリクエストのペイロード（例えば `thinking.budget_tokens` 相当のパラメータ）へ
  どう変換されるかまでは追っていない。`Di` を消費する関数を特定していないため、「APIリクエストの
  JSONに effort という名のフィールドとして最終的に現れる」ところまでは未確認。ここは「追えなかった」
  と明記する。
