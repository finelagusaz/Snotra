## 1. 「1 手目の set_size を消しても視覚的影響は定義上ゼロ」の**根拠**が不完全（結論は生き残る）

research.md 2.2 の逐語引用:
> 「当時より安い理由: ... いまは 2 手の間にフレームが 1 枚も描かれない（窓は hidden のまま）ので、
> 1 手目を消しても視覚的な影響が定義上ゼロである。」

**この理由づけは、実在する消費者を見落としている。** `src-tauri/src/egui_shell/mod.rs:377-383` に
main 窓の `Moved` イベントを購読するクロージャが登録されている:

```rust
window.on_window_event(move |event| {
    if matches!(event, tauri::WindowEvent::Moved(_)) {
        window_coordinator::position_results_below_main(&handle);
    }
});
```

`show_egui_main` の 1 手目 `set_size(width, bar_height)` の直後に呼ぶ
`position_on_target_monitor` は `main.set_position(...)` を実行する（`window_coordinator.rs:257-259`）。
これは main 窓の位置を変えるので、tao が `WindowEvent::Moved` を配送しうる——配送されれば
上記クロージャが発火し、`position_results_below_main` が **その時点の `main.outer_size()`**
（＝まだ 1 手目のバー高のまま、2 手目の実高 `set_size` はまだ実行されていない）を読んで
results の位置を計算する。

**「フレームが 1 枚も描かれない」は、この消費者を止める理由になっていない**——`Moved` リスナーは
`view.rs` の `update()`（フレーム）の外で動く別経路であり、egui のフレームが 0 枚でも発火しうる。
research.md 自身が §7 未解決の疑問 3 で「2 手のあいだの中間サイズを観測する消費者は本当に居ないか
（… results driver …）」と名指ししていた対象そのものである。

**ただし調べた限り、結論（視覚的影響ゼロ）自体は別の理由で生き残る**: `results` 窓は
`show_egui_main` の実行中ずっと OS 側で `visible(false)` のままである（`ResultsWindow::show` を
呼ぶのは `drive_results_window`、その呼び出し元は `view.rs` の毎フレーム driver であり、
show 完了後の最初のフレームまで走らない）。ゆえに `position_results_below_main` が中間の
バー高で results 位置を書いても、**画面には出ない**——次の実フレームで正しい実高を使って
上書きされる。

**評価**: 主張（視覚的影響ゼロ）は生き残るが、**理由づけは誤り**である。「フレームが描かれない
から安全」ではなく「results がまだ hidden だから安全」が正しい理由であり、これは
`position_results_below_main` 自身が**フレームに閉じない**（`Moved` リスナーからも呼ばれる）
という研究文書自身の §2.3 の記述と整合させて書き直す必要がある。§7 未解決の疑問 3 は
「裏取り」待ちのまま残さず、「消費者は存在するが、results が hidden な間だけ効くため無害」と
確定させるべきである。

**これを偽にする手順**: `mod.rs:378-382` のクロージャ内に `trace_main` を仕込み、
`show_egui_main` 実行中に `Moved` イベントが実際に配送されるか（同期か次のイベントループ
イテレーションか）を smoke で観測する。配送されないなら本項目自体が成立しない
（=消費者は理論上存在するが実行時には発火しない）。

⚠️ 確信の持てない所見
================================================================

1. **`Moved` イベントの配送タイミング（同期か非同期か）は未実測。**
   `mod.rs` のクロージャが `main.set_position()` の呼び出し中に同期的に発火するのか、
   次のイベントループ反復まで遅延するのかを、tao のソースを読まずに確定できなかった。
   いずれであっても「壊せた項目 1」の結論（視覚的影響ゼロ）は変わらないと考えるが、
   `show_egui_main` 実行中に本当に発火するかどうかは実測が要る。
   **偽にする手順**: `position_results_below_main` の先頭に一時的な `trace_main` を仕込み、
   smoke 実行中の trace 順序で `egui_show:done` より前に発火するかを確認する。

2. **R1（`position_on_target_monitor` の `outer_size()` 読み）を引数渡しへ変える改修が
   実現可能かは、hidden な窓に対する `outer_size()`/`inner_size()`/`scale_factor()` の
   有効性に懸かっており、これは research.md 自身が §7 未解決の疑問 1 として認めている
   未検証事項である。** 私はコード読解だけでこれを裁定できない（実機測定が要る）。
   research.md の裁定則（「コード自身が直前に書いた寸法を読み戻してはならない」）は、
   もし hidden 窓で非クライアント差分が読めないなら「渡す手段を作る」こと自体が
   実装不能になり、R1 を「唯一の違反」として残す（＝現状追認）以外の選択肢が
   無くなる可能性がある。
   **偽にする手順**: `show_egui_main` の 1 手目 `set_size` 直後（`show()` を呼ぶ前）に
   `window.outer_size()` / `inner_size()` / `scale_factor()` を trace 出力し、値が
   `Ok(...)` で妥当か（0 や前回値の使い回しでないか）を実機で確認する。

3. **R4（`position_results_below_main`）を「例外条項で正当」と結論するのは早計かもしれない。**
   research.md は「`Moved` リスナー経路にフレーム文脈が無い」ことを理由に read-back を
   容認しているが、コードベースには既に「フレーム文脈に依らず、書いた値をそのまま
   共有 atomic へ残し、後から読む」パターンが実在する（`EguiShellState.show_applied_height_bits`
   ——show が導出した高さを atomic へ格納し、`view.rs` の reset-on-show フレームがそれを
   読んで突き合わせる）。同じ形で「main の直近の書き込み高さ（物理 outer px）」を
   共有 atomic として持ち、`show_egui_main` の 2 手目 `set_size` と `view.rs` の
   フレーム内 `set_size` の両方の書き込み点でこれを更新すれば、`position_results_below_main`
   は `main.outer_size()` を読み戻さずに済む可能性がある。**この代替を research.md は
   検討していない。** 一方で、この代替が実際に安全かは非クライアント差分（DPI 依存・
   `read_bar_anchor` が実測 10 物理 px と記録）のキャッシュが hidden 中の DPI 変更等で
   陳腐化しないかに懸かっており、私はこれを裁定できるだけの実測を持たない——
   ゆえに「壊せた」ではなく「⚠️」に置く。
   **偽にする手順**: 上記の共有 atomic 案を試作し、(a) 非クライアント差分がウィンドウ生成後に
   変化しうるか（DPI 変更・モニター移動）を trace で観測、(b) 変化した場合にキャッシュが
   古い値のまま `position_results_below_main` へ渡って results が誤配置されるかを再現する。
   陳腐化が実際に起きるなら、research.md の「R4 は例外として正当」という結論は補強される。

4. **キーボードによるネイティブ移動（Alt+Space → M → 矢印キー）が、マウスドラッグと
   同じ `any_down()` ベースの保護を受けるかは未検証。** もしこの操作系がモーダル
   メッセージループに入り、その間 egui のフレーム更新が一切走らない（`update()` が
   呼ばれない）なら、移動終了後の最初のフレームで `any_down()` は元から `false` のため
   クランプ自体は効くはずだが、**「離した直後に即座に引き戻される」ことでキーボード移動が
   実用上機能しなくなる**可能性がある。これは継ぎ目 4 の閉包（不変条件が破れないこと）を
   崩す発見ではなく、UX 上の別の問題である可能性が高いが、確証を持てなかった。
   **偽にする手順**: 実機で Alt+Space → M → 矢印キー → Enter のシーケンスを送り、
   移動後の位置が保持されるか（クランプで押し戻されないか）を確認する。
