### 壊せた-1: H1（held_since_focus_gain）は「両キー同時抑止」よりもっと弱い候補である
**主張**: research.md は H1 への反証を「Down と Escape が同時に held へ残るには窓が狭い」という
タイミングの問題としてのみ扱っている（L55-58）。だが `admit_key`（input.rs:98-113）を読むと、
それより手前で 2 つの構造的制約が H1 を強く弱める。

1. **release は無条件に許可・解除する**（`if !pressed { held.remove(&physical); return true; }`。
   `is_synthetic` を見ない）。つまり「1 回 held に入った特定のキー」も、その release イベントが
   `admit_key` へ届きさえすれば即座に解除される。ゆえに H1 が「以後そのキーの押下**だけ**」を
   永久に抑止できるのは、**release イベント自体が admit_key へ届かない**（＝入力配送が全体的に
   止まっている）場合だけであり、それは H1 固有の症状ではなく H2／(B) と同じ「配送停止」の帰結に
   すぎない。
2. **held_since_focus_gain は Focused(true) 受信の瞬間に「その時点で物理的に down なキー」しか
   拾わない**（tao の `get_async_kbd_state()` 由来）。issue の注入は `keybd_event` の
   down→(40ms/50ms)→up を**キーごとに直列**で行う（`Send-SnotraKey` の呼び出しパターン、
   `smoke-egui.ps1:359-401`）ため、Down と Escape が同時に物理的に down である瞬間はまず存在しない
   （時間的に重ならない）。**加えて**、H1 が発火するには「focus 喪失 → 再獲得」という
   WM_KILLFOCUS/WM_SETFOCUS の往復自体が、この注入シーケンスの最中に起きる必要がある。
   **research.md はこの往復イベントが #999 の再現手順のどこで起きるかを一度も名指ししていない**
   ——results 窓は `focusable(false)` で focus を取らない（研究文書自身の U-3、`mod.rs:372`,
   `runtime.rs:246-247` のコメントで確認済み）、設定窓も開いていない。往復の発生源が無ければ
   `held_since_focus_gain` は再現シーケンス全体を通じて空のままであり、H1 は原理的に**一度も
   発火しない**。

**結論**: H1 は「issue の症状（Down と Escape の両方が、以後**すべて**沈黙し続ける）」の説明として、
research.md 自身が書いた反証よりさらに弱い。持続的な全キー沈黙を H1 単独で説明するには、結局
「release も届かなくなる」＝入力配送そのものの停止を仮定する必要があり、それは H1 が独自に説明する
現象ではなくなる。**`drop_key` 行の出現だけで採否を決めてよい、という research.md の結論（L58）は
変わらないが、その根拠は「タイミングが狭い」ではなく「focus 往復イベントの発生源が無い」および
「release は無条件に admit される」という、より強い構造的理由に置き換えるべきである。**

⚠️ 確信度: 中〜高。`admit_key` のコード（input.rs:98-113）は一次資料として確定しているが、
「往復の発生源が無い」は "grep で見つからなかった" という不在の主張であり、全称否定の弱さを持つ
（`.claude/rules` の「全称否定はプローブの形が違う」を踏まえ、慎重に中確信とする）。

**偽にする手順**: `grep -rn "Focused" src-tauri/src/egui_shell/ snotra-egui-runtime/src/` を再実行し、
main 窓が結果表示〜打鍵注入の間に focus を失う経路（例: アイコン抽出スレッドが COM STA 経由で
何らかの一時的な shell dialog / hidden window を作る、Explorer アイコンオーバーレイハンドラが
フォーカスを奪う等）が無いかを確認する。見つかれば H1 は復権する。

### 壊せた-2: 判定表の「心拍あり/なし」二値は、フレームが回るが 1 枚が異常に重い中間状態を見落とす
**主張**: research.md の判定表（L33-38）は `take` の心拍を「途切れる（=H2 系の不回転）」か「あるか」の
二値で扱う。だが `take` の心拍は 100ms 間引きのため、**フレーム間隔が 100ms を大きく超えても
（例: 1 フレームに数秒かかっても）「途切れていない」という誤読を招く**——heartbeat は「前回の
`take` 呼び出しから 100ms 以上経過したら次の `take` で 1 行出す」というだけで、フレームの実周期を
測る計器ではない。

具体的な main スレッドの重さの候補: `results_view.rs:534` の `update()` は毎フレーム
`while let Ok(msg) = self.icon_rx.try_recv()` でアイコン worker からの完了メッセージを**イベントループ
スレッド上で**同期的にドレインし、`icon_ctx.load_texture(...)`（L579）を件数ぶん呼ぶ。抽出は別スレッド
だが、**適用（テクスチャ生成）は main/イベントループスレッドである**。WinSxS のような重いシェル
問い合わせ（issue が言及）で多数のアイコンがバースト的に完了すると、この drain ループ 1 回が
長時間化しうる——research.md の H3 反論（メインスレッドで抽出しない・viewport 範囲に絞る）は
**抽出コスト**だけを否定しており、**drain/load_texture という別の main スレッドコスト**には触れていない。

この状態では: `rx_key` は届く（tao の配送自体は生きている）、`take` の心拍もいずれ出る（フレームは
最終的に回るので heartbeat 条件は満たされる）が、**フレーム間隔が数秒〜数十秒に伸び、実質的に
「打鍵が効かない」ように見える**——これは H2（0 フレーム）でも (A)/(B) の単純な二分でもない、
第 4 の状態である。research.md の判定表はこれを「心拍あり」側に分類してしまい、H3 を実質的に
過小評価する。

**結論**: 判定表に「心拍はあるが著しく間隔が伸びている（`ts_ms` の差分を見る）」という中間区分を
足すべきである。二値のままだと、実際にはこの経路が起きていても「心拍正常→H3 は無関係」と誤って
結論しうる。

⚠️ 確信度: 中。drain ループが実際にどれだけの時間を食うかは未計測（release ビルド・実 config・
313,028 件索引 + WinSxS 級抽出でどれだけの icon が同時に完了するかに依存し、静的読解だけでは
定量化できない）。

**偽にする手順**: `SNOTRA_EGUI_INPUT_TRACE=1` に加えて `take` の `ts_ms` の差分をポスト処理で
ヒストグラム化し、100ms を大きく超える間隔が沈黙区間の直前〜最中に集中するかを見る。

### 壊せなかった-4: -ExtraVariables の子プロセスへの到達（争点4・前半）
`SnotraSmoke.psm1` の `Start-SnotraProcess`（L321-383）は `Invoke-SnotraEnvironment`
（L280-319 付近）でカレント PowerShell プロセスの `Env:` を一時的に書き換えてから
`Start-Process @startParameters` を呼ぶ。`$startParameters` を実読すると `-Credential` も
`-UseNewEnvironment` も指定していない（L354-378）。PowerShell の `Start-Process` はこれらを
指定しない限り既定で**呼び出し元プロセスの環境ブロックを継承**するため、`-ExtraVariables` で
渡した `SNOTRA_EGUI_INPUT_TRACE=1` は子プロセスへ届くと判断できる。research.md の主張と一致。
⚠️ 確信度: 中——これは PowerShell/Win32 の一般仕様への依拠であり、コードだけからの断定である
（brief の制約で実機起動はしていない）。
偽にする手順: 実機で `Start-SnotraProcess -ExtraVariables @{FOO='1'}` 相当を実行し、
子プロセス側で `echo %FOO%`（あるいは自プロセスの env をダンプする一時コード）が見えるか確認する。

### 壊せなかった、むしろ補強・具体化: SNOTRA_TRACE と SNOTRA_EGUI_INPUT_TRACE の二重要件（争点4後半）
`src-tauri/src/trace.rs` を実読した。`window_coordinator.rs:1084` の `crate::trace_main("egui_results:show", ...)`
は `trace.rs` の `trace()` を経由し、`trace_enabled()`（L35-38）＝ `env_flag("SNOTRA_TRACE")` の
**許可リスト判定**（`1|true|yes|on`、trim+小文字化）でゲートされる。これは `snotra-egui-runtime/src/env.rs`
の `trace_hatch_enabled("SNOTRA_EGUI_INPUT_TRACE")`（空文字以外なら真、という**別の意味論**）
とは完全に独立した判定である。**確認できた**: research.md が示唆したとおり、`egui_results:show`
「その他 issue の trace に出ている `hotkey:registered` / `egui_show:done` / `egui_input:focus_state` /
`egui_search:dispatch` 等」（すべて `trace_main` 経由と推定される）を観測するには
`SNOTRA_TRACE` を、`rx_key`/`drop_key`/`take` を観測するには `SNOTRA_EGUI_INPUT_TRACE` を
**両方**立てる必要がある。`Start-SnotraProcess -Trace` スイッチは `SNOTRA_TRACE='1'` を予約名として
自動設定するが（L351）、`SNOTRA_EGUI_INPUT_TRACE` は `-ExtraVariables` で別途明示しないと立たない。
**この2つを両方立て忘れると**（例: `-ExtraVariables` だけ渡して `-Trace` を付け忘れる）、
`rx_key` 等は出るが「`egui_results:show` の直後で止まった」という issue の観測基準点そのものが
記録されず、判定表を適用できなくなる。research.md の懸念は正しく、**再測定の実務上の落とし穴として
最重要**だと判断する。
偽にする手順: `trace.rs:35-38`（`trace_enabled`）と `env.rs:29-32`（`trace_hatch_enabled`）を
読み比べ、両者が別の `OnceLock`/別の env 名を参照することを確認する。
