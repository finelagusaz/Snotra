## Correctness verdict

No input found where results/scores differ from main.

- Change 1 (flag skip): when `file_name_is_lower_name` is set, `entry_view` returns `lower_file_name = Some(lower_name)` (scoring.rs entry_view), so the skipped call would be `match_score_single_cached(mode, lower_name, plan)` again — identical to `name_score` (pure; Fuzzy uses a thread-local nucleo Matcher, deterministic). `(Some(s),Some(s)) -> s`, `(None,None) -> None` — identical. `skip_name` already short-circuited both. The flag is only set from a measured byte equality (query.rs:136 `lower_file_name == Some(lower_name)`, build.rs:266/301 `mark_file_name_is_lower_name` is the only setter). Folders with path separators in the name: the flag is a byte-equality fact, independent of `any_name_has_path_sep`; no interaction.
- Change 2 (Finder): needle and haystack are both `&str` (valid UTF-8), so leftmost byte match == `str::find`. Empty needles: norm_query empty -> plan is None; path_query nonempty by construction (contains a separator); kana_query: Finder("") and str::find("") both return Some(0) anyway. Prefix mode only changed `query` -> `plan.norm_query` (same value).
- `expect` in the Substring arm: unreachable in production. The only production caller (search.rs:326/396) builds the plan and calls `score_one_entry` with the same `mode`. Reachable only if a future caller passes a plan built for a different mode (the tests' `score_at` also passes the same mode). See finding L1.

## Findings

### L1 (Low) scoring.rs `match_score_single_cached` / query_plan.rs `QueryPlan` — mode is passed separately from the plan that encodes it
- Evidence: `QueryPlan` does not store `mode`; `substring_finder.is_some()` <=> mode==Substring is an invariant held only by `prepare_query_plan` + the single caller passing the same `mode`. The `expect` documents rather than enforces it. Test `query_plan_builds_finders_exactly_for_the_needles_in_use` pins the producer side only.
- Not a bug today. A structural alternative (store `mode` in the plan, or match on `plan.substring_finder` instead of `mode`) would make the panic unrepresentable; the repo's stated preference (prefer-structural-over-documented-contract) suggests at least noting it.
- How to falsify: show a second caller of `score_one_entry`/`match_score_single_cached` that can receive a plan prepared under a different mode — `grep -n "prepare_query_plan\|score_one_entry(" snotra-core` returns only search.rs:326/396 and tests.

### L2 (Low) PERFORMANCE.md 「等価性の根拠と検知器」 — `has_dot_on_shared_file_name_scores_like_the_name` is listed as a detector for change 1 but cannot fire on any mutation of the flag condition
- Evidence: mutation m1 (invert the flag) made 12 tests red but NOT this one; m1b (drop the optimization, `&& true`) is green everywhere. This is inherent: change 1 is semantically invisible, so on a flagged entry every variant of the condition yields the same score. What the test actually detects is the Substring position (m2: red at basic.rs:381) and the substring-finder source (m4). The real detector for the flag condition is `has_dot_fuzzy_matches_distinct_file_name` (+11 pre-existing has_dot/extension tests).
- Suggested wording: call it a non-regression / equivalence check (it pins that flagged entries still match via the name), not a detector of the flag condition.
- How to falsify: find a mutation of line `&& !v.entry.file_name_is_lower_name` that makes this test red. Logs: .delegate/mut-m1.log, .delegate/mut-m1b.log.

### L3 (Low) snotra-core/tests/match_cost.rs `//!` — 「実 `index.bin` を書き換えない」 is false on cache-miss
- Evidence: the very next clause and the assert message (match_cost.rs:130 「全走査が走り index.bin を書き換えた」) say the overwrite has already happened when the assert fires; the guard stops the measurement, not the write. Sibling instruments word this correctly (`path_query_cost.rs:22` 「書き換えうる」, `memory_footprint.rs:16`).
- How to falsify: show that `load_or_scan_with_stats` on cache-miss does not write index.bin before returning (cache.rs:506 `load_or_scan_with_stats_in`).

### L4 ⚠️ (Low, uncertain) path_store.rs `CompactEntry::file_name_is_lower_name` doc — 「偽であるべきエントリに立つと file name 側の一致が消える」 attributes the consequence to the new reader
- Evidence: a wrongly-set flag already loses the real file name in `entry_view` (it returns `lower_name` and the `lower_file_names` slot is None), before #1281. The new skip adds no further loss. The sentence is not false as a statement about the whole system, but placed under 「読み手はもう 1 つある——score_one_entry が…」 it reads as a consequence specific to score_one_entry.
- How to falsify: construct an engine with the flag set on an entry whose true file name differs and show main (feaa2de8) matches the file name while 1429dd54 does not.

### L5 (Low, informational) Substring↔path swap in Substring mode is not detected by the NEW test alone
- Evidence (m4r: path site uses `substring_finder`): `substring_kana_and_path_positions_agree_with_std_find_on_non_ascii` failed only on the Fuzzy iteration (「assertion failed: Fuzzy left: None right: Some(2987)」) — its Substring iteration passed because `norm_query` and `path_query` are the same bytes for `tool\alpha`. The swap IS detected in Substring mode by pre-existing tests where norm_query != path_query: `path_match_slash_normalized`, `path_match_yen_sign_normalized`, `path_match_consecutive_spaces_preserved`, `path_match_incremental_disabled_avoids_accent_false_negative` (all `SearchMode::Substring`). Main agent's suspicion confirmed for the new test, refuted for the suite.

### L6 (Low, informational) `.max(1)` in the path score is dead code; `.max(1)` in kana is effectively untested
- PATH_BASE 3000 - min(pos, PATH_POS_CAP 500) >= 2500, so m6p is an equivalent mutant. Kana floor needs a kana name >= 4500 bytes; m6k green. Both pre-existing, unchanged by this diff; no action required for #1281.

No Critical/High/Medium findings. SPEC sync: no SPEC-described behavior changes (results identical); none needed.
