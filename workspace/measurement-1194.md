## Q3 — モーダルループ中のフレームは 0 枚（5/5）

移動区間（`M` 打鍵後の最初のサンプル 〜 `Enter` 直前）を注入側の epoch ms で切り、
本体の `egui_frame` / `egui_main:clamp` の `ts_ms` を数えた。

| 反復 | 移動区間 | `egui_frame` | `egui_main:clamp` |
|---|---|---|---|
| 1 | 3 秒 | **0** | **0** |
| 2 | 3 秒 | **0** | **0** |
| 3 | 3 秒 | **0** | **0** |
| 4 | 3 秒 | **0** | **0** |
| 5 | 3 秒 | **0** | **0** |

実行全体でもフレームは 118 枚しかなく、`interval_us` の最大は **4.27 秒**。

**ゆえに、この条件では「ループ側の `SetWindowPos` とクランプが競り合っている」は成立しない**
——競り合う相手が 1 フレームも走っていない。**「競り合いは決して起きない」とは言えない**:
フレームが 1 枚でも走る条件が在れば、そこでは競り合いが機序になりうる（#1173 が観測した
「出入りを 2 度繰り返す」はその形に見える）。**この文を偽にするのは「モーダルループ中に
フレームが走る条件」を 1 つ挙げることである。**`egui_main:clamp` の発火は全実行で **5 回、反復あたりちょうど 1 回**であり、
すべて `Enter` の後である。

**これは `src-tauri/CLAUDE.md`「イベント駆動 wake の不変条件」の予言どおりである**——
「通常フレームは勝手に回らない」。`mod.rs` の `Moved` リスナーが results を**直接**動かしているのも、
まさにこの状況のためである（コメントが「ネイティブ移動ループ中は egui フレームが回る保証が無い」と
書いている）。

**tao の `WM_PAINT` → `RedrawRequested` 直結経路（research U2）は、この条件では発火していない。**
経路の存在は真だが、窓を動かしても `WM_PAINT` は来ていない（移動は再描画を要求しない）。

## Q2 — 確定後の移動はクランプでも製品コードでもない

反復 1（物理 px、`GetWindowRect`）:

| 位相 | top | bottom | 高さ |
|---|---|---|---|
| `before`（表示直後） | 478 | 542 | 64 |
| `moving` 最終 | 1066 | 1130 | 64 |
| `before_enter` | 1066 | 1130 | 64 |
| **`after_enter` 最初** | **1042** | **1106** | **64** |
| `settled` | 956 | 1020 | 64 |

**`egui_main:clamp` が観測した `pre` は 1042 であって 1066 ではない。** 全 5 回の発火がすべて
`pre_y = 1042 → post_y = 956` で、**1066 を見たサンプルは 1 つも無い**。ゆえに:

- **クランプは 24 px を動かしていない**——動いた後の値しか見ていない
- **製品コードのどのフレームでもない**——その区間にフレームが 0 枚である
- **高さは 64 px のまま不変**（1130−1066 = 1106−1042 = 64）＝ **純平行移動**

**残るのは OS である**（`Enter`＝ `WM_EXITSIZEMOVE` の確定処理）。#1173 の 27〜28 px に対して
本測定は 24 px で、どちらも「カーソル限界から少し戻る」形。**値が config と scale に依存しうるため、
`24 px` を定数として文書へ書かない。**

## `GUI_INMOVESIZE` は一度も真として観測されていない（0/10 サンプル）

**述語の欠陥ではなく、観測者が居ないためである**——フラグを読むのはクランプのフレームだけで、
そのフレームがモーダルループ中に 1 枚も走らない。**この条件では、真の側を観測する手段が無い。**

ゆえに `/symmetric-check` が要求する「両向きに立つ」は、**この経路では満たせない**。

## 判別実験（測る前に予測を書く）

**仮説**: 上の 8/8 でフレームが 0 枚だったのは、打鍵が `↓` の単調移動だったからである。窓が
画面下端から出ていく向きの移動は**隠れていた領域を再露出させない**ので `WM_PAINT` が来ず、
research U2 で確かめた tao の `WM_PAINT` → `RedrawRequested` 直結経路が発火しない。
**`↑` で戻す向きの移動なら、クリップされていた領域が再露出して `WM_PAINT` が来る。**

`↓`×200 のあと `↑`×80 を撃つ変種で、次の 3 つを**測る前に**分岐として固定する。

| 分岐 | 観測 | 裁定 |
|---|---|---|
| **A. 和解** | `↑` 区間に `egui_frame` ≥ 1、かつ `in_move_size: true` が出る | 挙動は**双安定**である。#1173 と本測定は**どちらも真**で、条件が違っただけ。`GUI_INMOVESIZE` のガードは**その条件でこそ効く**——計画どおり Phase 2 へ進む |
| **B. 述語が壊れている** | フレームは走るが `in_move_size` は偽のまま | スレッド同一性か `hwndMoveSize` の前提が誤り。**設計の土台が崩れるので止める** |
| **C. 依然フレーム 0** | `↑` 区間にもフレームが来ない | 仮説が外れ。モーダルループ中にフレームを走らせる条件が別に在るはずで、#1173 との食い違いは未解決のまま残る |

**`SNOTRA_EGUI_WAKE_TRACE` を併せて立てる**——各フレームを起こした `RedrawRequested` の受信が
見えるので、U3（確定後のフレームを誰が起こすか）も同じ 1 回で測れる。

### 結果: 分岐 C（依然フレーム 0）。**ただし実験は狙った枝へ入っていない**

`↓`×200 → `↑`×80、5 反復、`SNOTRA_EGUI_WAKE_TRACE` 有効。

| 観測 | 値 |
|---|---|
| 移動＋戻し区間のフレーム（5 反復すべて） | **0** |
| 実行全体のフレーム | 120（`SNOTRA_EGUI_WAKE_RECV` も 120＝**全フレームが `RedrawRequested` 由来**） |
| `in_move_size: true` | **0**（累計 16 サンプル中） |
| フレーム間隔の最大 | **5.9 秒** |

**この実験は仮説を反証していない。** `returning` 区間の最後のサンプルが `moving` の最大値と
同値であり（1130/1132 で不変）、**`↑`×80 が窓を 1 px も動かしていない**。動いていない以上
「クリップ領域の再露出」は起きておらず、**仮説が試されていない**（`AGENTS.md`「観測形が対象を
含むか」——対象を含まない検証は自明に「差が無い」を返す）。

`↑` が効かなかった理由は**未測定**である。候補: 注入した矢印が `bScan = 0` ゆえ
`ADR-injected-arrow-key-physical-identity` の言う Numpad 相当として届き、OS のモーダルループ側が
`↓` とは別に扱う／カーソルが画面下端でクランプされた分のオフセットを使い切るまで戻らない／
その時点でループを抜けている。**どれも測っていないので、ここに機序を書かない。**

**ゆえに #1173 との食い違いは未解決のままである。**

## 副産物: `request_repaint_after` の鎖はモーダルループを越えない

toast 条件（`SNOTRA_EGUI_FAKE_UPDATE`）でも移動中のフレームは 0 枚だった。一時通知は
armed 期限を持ち毎フレーム残余を再要求する（`src-tauri/CLAUDE.md`「armed 期限」）にもかかわらず、
**モーダルループ中は 1 枚も届いていない**。

**これは計画の U3 の対処候補 (a)「ループ中の各フレームで `ctx.request_repaint()` を撃って
フラグが偽へ落ちる最初のフレームまで鎖を繋ぐ」を、他の論点と独立に潰す**——鎖を繋ぐ相手の
フレームがループ中に 1 枚も来ない。

## 帰結（計画への影響）

1. **Q2・U1 は答えが出た**（Q2 の受け入れ条件を満たす）
2. **Q3 は「この条件では競り合いではない」まで**。フレーム 0 枚という、2 仮説のどちらよりも
   強い事実が出たが、**#1173 が観測した「出入りを 2 度繰り返す」条件を再現できていない**ので、
   あちらの逸脱の機序を棄却したことにはならない
3. **Q1 は前提が再現しない（13 反復・3 条件）**——拘束が起きない以上、ガードを差し替える動機が
   消える。差し替えても、クランプがモーダルループ中に走らない限り**挙動は 1 ビットも変わらない**
   （毎フレーム `GetGUIThreadInfo` を 1 回増やす費用だけが残る）
4. **`GUI_INMOVESIZE` の真の側は、この経路では原理的に観測できない**——読み手はクランプの
   フレームだけで、そのフレームがループ中に走らないため。`/symmetric-check` の「両向きに立つ」は
   **満たせない**
5. **`SPEC.md:478` と `clamp_main_into_work_area` の rustdoc は、実測と食い違う記述を抱えている**
   ——#1173 の表が「クランプ有効: 移動中に落ち着く値 1020・留まれない」と書いているのに対し、
   本測定は 13/13 で「留まれる」である。**どちらが何を測ったかの裁定が要る**

## この測定を偽にするなら

- **モーダルループ中に `egui_frame` が 1 枚でも出る条件を 1 つ挙げる**（それが在れば Q1 の前提は
  その条件下で復活し、ガードの差し替えに意味が戻る）
- #1173 の測定手順のうち、本測定と違う要素を 1 つ挙げる（arrow の cadence・クエリの有無・
  index build の進行中か・hide/show を挟んだか）。**PR #1193 の本文と rustdoc には
  これらが記録されていない**
