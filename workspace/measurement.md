## 何を判定するのか

issue #710 の受け入れ条件:

1. **同一条件**（同じクエリ・同じホバー操作・release）で A/B を取り、操作中の fps が #628 前後で変わったかを判定する
2. 300 fps 級の区間が存在するなら、**「アニメーションの収束までの正常な連続描画」なのか「収束しないループ」なのか**を `since_prev_ms` の時間構造で切り分ける
3. **直すべき欠陥があった場合のみ修正する**（無ければ「正常」として記録して閉じる）

issue 自身が既存の数字について「**修正前後の数字は比較できない**——別セッション・別操作（後者はカーソル挙動の目視確認のためホバーを多く含む）であり、`predicted_dt` の変更が増やしたのか操作量の差なのかは判別していない」と述べている。**だから測り直す。**

## 観測設計（#628 の教訓を織り込む）

`docs/development-principles.md`「デバッグ・バグ修正」から、この測定に効く 3 点:

- **人手の観測時間に、観測条件を変える確認作業を混ぜない。** #628 の再測はカーソル挙動の目視確認のためホバーを同じ run に含め、`ScrollArea` のフェードが混入してアイドル計測が無効になった（測り直し）。**今回はホバーが測定対象そのもの**なので、逆に「ホバー以外の余計な操作を混ぜない」ことが要件になる
- **総フレーム数・平均 fps はセッション長・操作量に汚染される。プロトコル非依存の判別指標を用意する。** 本測定の主指標は**局所構造**（下記 M3・M4）であり、総数は補助である
- **ログのフラッシュ経路を手順に含める。** PowerShell の `Tee-Object` はパイプが閉じるまで書き出さないため、**プロセスを終了させるまでログは 0 バイトに見える**。本手順は `2>` のリダイレクトを使い、終了まで開かない

### トレース形式（`snotra-egui-runtime/src/runtime.rs`）

```
SNOTRA_EGUI_REPAINT window=<main|results> focused=<bool> since_prev_ms=<f64> causes=<file:line,...>
```

同ファイルが明記する読み方の注意（**解析でこれを踏まない**）:

- `repaint_causes()` が返すのは **1 パス前**に積まれた原因である（egui 0.35 の pass 冒頭 swap）
- **遅延ゼロの `request_repaint()` は 2 フレーム生む**（`outstanding` の記帳）。「1 要求 = 1 フレーム」で件数を照合してはならない
- `focused` は必須項目。egui はフォーカスがあるときだけキャレット点滅の repaint を出すため、非フォーカス行を混ぜると「眠っている」に見える
- 初回フレームの `since_prev_ms` は **NaN**（0 と紛れない）。hide をまたぐと巨大値になる

## 手順（人間が操作する。**目視確認を混ぜない**）

### 0. 準備

```powershell
cargo build --release -p snotra
```

実行中の snotra があれば終了しておく（多重起動はトレースを混ぜる）。

### 1. 計器付きで起動し、stderr をファイルへ

```powershell
$env:SNOTRA_EGUI_REPAINT_TRACE = "1"
$env:SNOTRA_TRACE = "1"
target/release/snotra.exe 2> "$env:TEMP\710-hover.log"
```

`2>` のリダイレクトを使う（`Tee-Object` はプロセス終了までフラッシュしないため、途中経過が見えないうえ中断時に失われる）。

### 2. 操作列（**この 4 段以外を行わない**）

| 段 | 操作 | 目的 |
|---|---|---|
| **A. 静止（20 秒）** | ホットキーで表示し、**何もしない**。マウスをウィンドウの**外**へ置く | アイドル基線。#628 の 11.5fps / 2.0fps と突き合わせる |
| **B. 検索（固定クエリ）** | `e` と入力して結果が出るのを待つ（**8 行前後出るクエリ**。件数が違うと results の描画コストが変わる） | results 窓を可視にする |
| **C. ホバー往復（20 秒）** | **results 窓の結果行の上を、上端↔下端でゆっくり 10 往復**。クリックしない・スクロールしない | 行ホバー + スクロールバーのフェードを踏む |
| **D. スクロール往復（20 秒）** | results 窓の上でホイールを**上下 10 往復**。マウスは動かさない（ホバー位置固定） | スクロール由来の連続描画を C と分離する |

**段の境界を判別できるように、各段のあいだに 3 秒の完全静止を置く**——`since_prev_ms` に大きな値が現れ、解析で段を切り分けられる。

### 3. 終了

ウィンドウを Escape で隠し、**さらに 10 秒待ってから**プロセスを終了する（hidden 中にフレームが 0 であることの再確認。SU6.5 G3(a) と同型）。

タスクトレイから終了するか、`Stop-Process -Name snotra`。

### 4. 報告

`$env:TEMP\710-hover.log` のパスを伝えてください。解析は私が行います。

## 原因の同定（一次資料）

`context.rs:525`（results の 73.8%）は egui 0.35 の `Context::begin_pass` 内:

```rust
let repaint_after = viewport.input.wants_repaint_after();
if let Some(delay) = repaint_after {
    self.request_repaint_after(delay, viewport_id, RepaintCause::new());
}
```

`InputState::wants_repaint_after()`（`input_state/mod.rs:652`）:

```rust
if self.pointer.wants_repaint()
    || self.wheel.unprocessed_wheel_delta.abs().max_elem() > 0.2
    || !self.events.is_empty()
    || !self.raw.hovered_files.is_empty()
    || !self.raw.dropped_files.is_empty()
{
    return Some(Duration::ZERO);   // Immediate repaint
}
```

`PointerState::wants_repaint()`（同 `:1250`）:

```rust
fn wants_repaint(&self) -> bool {
    !self.pointer_events.is_empty() || self.delta != Vec2::ZERO
}
```

**ポインタが動いている間、egui は毎パス「遅延ゼロ」の再描画を要求する。** 止まれば `delta == ZERO` かつイベント空となり `None` を返して収束する。これは egui の入力応答性の設計そのものであり、Snotra 側の欠陥ではない。

同じ機構は main にも当たる——段 A の 145fr/844fps バーストは、マウスを窓外へ動かす動作が main のポインタ入力として拾われたものである（cause が `visuals.rs:313` なのは、runtime が明記するとおり `repaint_causes()` が **1 パス前**の原因を返すため）。

**`predicted_dt = 0`（#628）はこの経路に関与しない。** `wants_repaint_after` は `Some(Duration::ZERO)` を直接返しており、`predicted_dt` を経由しない。#710 が「未検証」としていた点はこれで解消する。

## 判定

### 受け入れ条件 2 — 収束するか

**収束する。** 入力駆動の連続描画であり、ポインタが止まればバーストが終わる。482 バーストすべてが終端し、最長 1.97 秒（ホバー 1 掃き分）。「収束しないループ」ではない。

### 受け入れ条件 1 — #628 前後で変わったか

**直接の A/B は取れない**（#628 以前のバイナリでの同一条件データが無く、issue 本文自身が既存の数字を「比較できない」と宣言している）。

ただし**機構の同定によって間接的に答えられる**: 操作中の高 fps は egui 自身の `wants_repaint_after` に由来し、#628 が変更した `predicted_dt` を経由しない。**#628 は操作中フレームレートに関与していない。**

### 受け入れ条件 3 — 直すべき欠陥はあるか

**ポインタ移動中の 460fps は欠陥ではない**（egui の設計・収束する・占有時間は 16.6%）。

**残るのは「results の非移動時 25.3fps」という常在コスト**である。main のアイドル 2.7fps に対して約 9 倍で、`wake_results` の level-triggered 呼び出し（`view.rs:850`）が main のキャレット点滅フレームを results へ伝播していることに由来する。

**ただしこれを単純に消してはならない**——`research.md`「最重要の発見」のとおり、この 1 行が **config hot-reload（font / 色 / 行高）が results 窓へ届く唯一の経路**である（`wake_results` の呼び出し点は 2 箇所のみ、`register_config_wake_listeners` は `wake_main` しか呼ばない）。消すなら代替経路を同じ変更で用意する必要がある。

## 判定の更新 — 何が欠陥かが変わった

**非移動時の常在コストは問題ではなかった。** 1 回目の推定「25.3fps」は分母の取り方が粗く、実測は **14.0fps / 1 コアの 2.7%**。level-triggered `wake_results` の実額はこの程度であり、**config hot-reload の唯一経路を壊してまで削る価値は無い**（YAGNI）。

**残るのは「ポインタ移動中の 448fps で 1 コアの 84.7%」である。**

機構は egui の設計どおり（`wants_repaint_after` → `Some(Duration::ZERO)`）で収束もする。しかし **448fps はどの表示装置のリフレッシュレートも大きく超えており、描いたフレームの大半は一度も表示されない**。egui は「即座に再描画してよい」と要求しているだけで、**何 fps に抑えるかを決めるのは runtime 側の責務**である——`snotra-egui-runtime` はこの要求を無条件に消化しており、フレームレートの上限を持たない。

したがって #710 の受け入れ条件 3 に対する答えは:

- **egui の即時再描画要求そのものは欠陥ではない**（設計・収束する）
- **その要求を上限なしに消化している runtime 側**に、表示され得ないフレームへ 1 コアの 85% を払う無駄がある

**ただしこれは #710 の枠（`wake_results` の level-triggered 化）とは別の対象**であり、`snotra-egui-runtime` の変更になる。スコープの判断が要る。

### M6（hidden 中のフレーム停止）— **合格**

`egui_hide:done` の 319ms 後に main のフレームが 1 件、その後**プロセス終了までフレーム 0**。

**判定の根拠は操作者の申告である**（「hide してから 10 秒待って終了した」）。ログ単独では「10 秒待って 0 フレーム」と「待たずに終了」を区別できない——待っても書込が無ければ最終書込時刻は動かないためである。**接地した観測点はログではなく人間の証言**であり、機構で置き換えるなら hide 後に一定間隔で書く計器が要る（本 issue の範囲では作らない）。

SU5 要石（hidden 中は `update()` が走らない）の回帰は無い。

### 表示装置のリフレッシュレート — 実測 144Hz

`Win32_VideoController`: NVIDIA GeForce RTX 4060 Ti / **CurrentRefreshRate 144**（Max 300）/ 1920×1080。フレームレート制限は設定していない（操作者申告）。

したがって移動中の **448fps はリフレッシュレートの 3.1 倍**であり、**描いたフレームの約 68% は一度も表示されない**。「大半が表示されない」は一般論ではなくこの環境の実測に基づく。

**ゲーミング PC での値である点に注意する。** paint コスト（results `total_ms` p50 1.64ms）はこの機体のものであり、非力な機体では 1 フレームが重くなって fps は下がるが、**CPU 占有は下がらない**（上限が無いので描けるだけ描く）。

### 測っていないもの（受容する残余）

**CPU 占有は測っていない。** 本測定は `SNOTRA_EGUI_REPAINT_TRACE` のみで、#628 が併用した `SNOTRA_EGUI_PAINT_TRACE`（`total_ms` / `raster_ms`）を有効にしなかった。「460fps が何 % のコアを食うか」は本ログからは出せない。

`docs/development-principles.md`「デバッグ・バグ修正」が言う「**見積りを選択肢の比較表に載せてユーザーの判断材料にするなら、それが実測か理論値かを明示する**」に従い、**#628 の paint コスト実測（`total_ms` 平均 1.41ms）を流用した推定は行わない**——行高・件数・窓が異なる。
