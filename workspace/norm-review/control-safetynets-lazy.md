# 手を抜く読者 — safety-nets

1. 機構と規範のどちらの分岐に自分の変更を置くかを、自分で選べる（費用が非対称）
   - 根拠となる文言の引用: 「効いていることは、フォールトインジェクションで一度は実測する」／「セーフティネットが「規範」（ドキュメント・スキル・チェックリスト）の場合、フォールトインジェクションとは「回避しようとする読者」である」「規範は機構ではないので実行して測れない」
   - どう手を抜けるか: 文書は 2 本の検証経路を用意し、費用が大きく違う（機構 → 故意に壊して実測／規範 → 文言を読んで抜け道を探す）。両方の性質を持つ変更（例: 拒否メッセージに復帰手順を書き込んだ hook、判定表とスクリプトが対になったチェック）はどちらにも分類できるのに、分類の決め方がどこにも書かれていない。安い方の分岐を選び、選んだ理由を書かずに完了できる。この選択は以下の全項目の上位にあり、1 回の分類で下流の義務がまとめて消える。

2. 冒頭のスコープ宣言を使って、文書全体を「該当なし」にできる
   - 根拠となる文言の引用: 「ここに置くのは、そのセーフティネットが**本当に効いているか**を確かめる運用手順である」
   - どう手を抜けるか: 自分の変更を「効き方は変えていない（メッセージ文言の改善・リファクタ・コメント追加・条件の整理）」と自己申告する。文書自身が「効いているかを確かめる手順」と名乗っているので、効き目に触れない変更にはどの節も適用されない、と一行で結論できる。「効き方を変える変更とは何か」の定義が無いため反証もされない。

3. 「配送されなかった＝対象外」の循環で、ファイルでないセーフティネットを丸ごと落とせる
   - 根拠となる文言の引用: 「このファイルは、セーフティネットそのもの（対象は上の `paths` が SSOT）を触ると自動配送される」
   - どう手を抜けるか: 対象集合の SSOT が `paths`（＝配送機構そのもの）だと書いてあるので、「この rules が配送されてこなかった変更はセーフティネットではない」と読む。GitHub ruleset のようなリポジトリ外の設定、PR テンプレート、CI の設定値、リリース設定は配送されないので、触っても義務が発生しない、と処理できる。

4. `paths` 自体の変更が、本文のどのトリガーにも掛からない（自分の適用範囲を自分で狭められる）
   - 根拠となる文言の引用: 「対象は上の `paths` が SSOT」「**rules 自身を含むため、本ファイルの編集でも配送される**（この手順は自分自身にも適用される）」
   - どう手を抜けるか: 「自分自身にも適用される」と言うが、適用される中身（実測・`/norm-review`・入力集合の検算・経路列挙）はどれも `paths` の glob を狭める編集を捕まえない。glob を 1 行狭めれば、以後のセーフティネット変更はそもそも配送されず、項目 3 の循環と組み合わせて「対象外」が量産できる。検査の入力集合を定義する行が、その検査の対象になっていない。

5. 規範の列挙に含まれない prose 資産は、両方の分岐から同時に落ちる
   - 根拠となる文言の引用: 「パスに属する規範（`.claude/rules/` `.claude/skills/` **および規範文書**）を新設・変更したら起動する」
   - どう手を抜けるか: この列挙は `.claude/agents/`（サブエージェント定義）・PR テンプレート・workflow 文書に埋め込まれたチェックリストを名指ししていない。これらを変更したとき、prose なのでフォールトインジェクションはできない（機構でない）、列挙に無いので `/norm-review` も起動しない（規範でない）——両分岐で該当なしになる。

6. 「省く前に」という条件節で、フォールトインジェクションの中核義務そのものが外れる（N1・中核）
   - 根拠となる文言の引用: 「それに依拠して**手順を省く前に**、故意に壊して検知されることを 1 度確かめる」／同じ文書内の「「判定が〜なら」のような**条件節を免除と読んではならない**（#504…）」
   - どう手を抜けるか: 義務の発火条件が「期待に依拠して**手順を省く**こと」になっている。「自分は何の手順も省いていない（むしろ手で検証も回した）」と言えば、故意に壊す作業は不要になる。しかもこの文書は条件節を免除と読むことを明示的に禁じているのに、その禁止は第 2 節のモダリティ（「判定が〜なら」）にしか届いておらず、**文書全体の中核義務がぶら下がっている条件節を自ら塞いでいない**。禁止の存在が、この条件節は禁止対象ではないという読みをかえって補強する。

7. 「一度は」の数え上げ単位が無指定なので、過去の実測を流用できる（N1）
   - 根拠となる文言の引用: 「効いていることは、フォールトインジェクションで**一度は**実測する」「故意に壊して検知されることを **1 度**確かめる」
   - どう手を抜けるか: 「一度」が「セーフティネットごと」か「機構のクラスごと」か「リポジトリで一度」かが書かれていない。引用された #471 で hook 経路は既に実測済みなので、「この機構クラスの実測はもう一度行われている」と読み、新設したチェックそのものは一度も壊さずに済ませられる。

8. 「効くと書かなければ、測る対象が生まれない」（N1）
   - 根拠となる文言の引用: 「「hook が自動実行する」「CI が担保する」は**書かれた時点の期待**であって、測定結果ではない」
   - どう手を抜けるか: 義務は「期待の記述」に紐付いている。ドキュメントに「自動実行される」「担保する」と書かず、「〜を実行する設定を追加した」と事実記述だけにすると、測定すべき期待が存在しないことになり、対象が消える。

9. 実測の時期が指定されていないので、後回しにできる（N1）
   - 根拠となる文言の引用: 「一度は実測する」
   - どう手を抜けるか: コミット前・PR 前・マージ前のどれとも書かれていない。「後で一度やる」と宣言して変更を先に入れ、実測はフォローアップ issue へ送る。期限を言う語が無いので文面に反していない。

10. 実測をサブエージェントへ委譲して報告で済ませられる（N1）
    - 根拠となる文言の引用: 「一覧・索引・**サブエージェントの報告**を根拠に「全部」「一致した」と言うときは…」（＝サブエージェント不信は第 4 節の網羅主張にだけ掛かる）
    - どう手を抜けるか: 文書はサブエージェントの報告を疑えと言うが、その不信は「全部／一致した」と言う場面に限定されている。第 1 節の実測には及ばないので、「サブエージェントに壊させ、検知されたと報告を受けた」で実測を履行したと書ける。自分では一度も壊さない。

11. 「稼働中の」という限定で、編集中・未有効のガードは本体を直接弱められる
    - 根拠となる文言の引用: 「フォールトインジェクションでは、**稼働中の**ガードを弱めない——複製に変異を当てる」
    - どう手を抜けるか: いま編集しているガードを「変更途中で稼働状態が確定していない」「新設なのでまだ稼働していない」と分類し、複製を作らず本体を書き換えて試す。#504 は「稼働中のものを触った事故」として自分の状況から切り離せる。

12. 「行使は対象外」を、第 1 節の実測の履行として計上できる（N1）
    - 根拠となる文言の引用: 「意図的に規則違反となる操作を行い、拒否されることを確認する類はガードの**行使**であり、弱めていないので**対象外**」
    - どう手を抜けるか: 違反操作を 1 回打って弾かれるのを見て「フォールトインジェクション済み」と記録する。複製の用意も不要（この文が明示的に対象外と言っている）。結果として、検知器が沈黙・起動失敗・タイムアウトしたときに素通りしないか（fail-closed 側）は一度も測らないまま「実測した」と言える。

13. 複製の作り方が 2 モダリティしか示されないので、それ以外は「該当なし」にできる
    - 根拠となる文言の引用: 「判定が**ソース述語でも実 git 操作でも**規則は同じで、変わるのは複製の作り方だけである。述語はメモリ上へコピーして変異させ、git 操作は hook を一時ディレクトリへコピーして…」
    - どう手を抜けるか: 触ったのが CI ワークフロー・スキル・rules・設定 JSON など 2 例のどちらでもない種類なら、「複製の作り方が定義されていない＝この節が想定していない対象」と読み、複製も変異も作らずに終える。

14. 「パスに属する規範」の定義が冒頭と矛盾し、規範文書側で `/norm-review` を回避できる（N2・中核）
    - 根拠となる文言の引用: 冒頭「規範文書（ルート `CLAUDE.md` / `AGENTS.md` 等）もセーフティネットだが **`paths` 外**＝自動配送されない」／第 3 節「**パスに属する規範**（`.claude/rules/` `.claude/skills/` および規範文書）を新設・変更したら起動する」
    - どう手を抜けるか: 冒頭が「規範文書は paths 外」と明言しているので、起動条件「パスに属する規範」に規範文書は入らないと読む（括弧内の列挙より、括弧の外の限定語を優先するのが素直）。ルート `CLAUDE.md` / `AGENTS.md` の改訂で `/norm-review` を起動しない経路が正当化される。しかもこれらの編集では本ファイルが配送されないので、そもそもこの条項を誰も読んでいない。

15. 起動条件が「新設・変更」だけで、削除・移動・分割が抜けている（N2）
    - 根拠となる文言の引用: 「パスに属する規範…を**新設・変更**したら起動する」
    - どう手を抜けるか: 条項を削る／別ファイルへ切り出す／2 ファイルに分ける作業を「新設でも変更でもない（内容は同一・場所が変わっただけ）」と分類して飛ばす。抜け道は削除と移動で最も生まれやすいのに、その 2 つが列挙に無い。

16. 「起動する」までが義務で、所見への対応義務が書かれていない（N2）
    - 根拠となる文言の引用: 「**手順は `/norm-review` が持つ**（停止条件の決め方・2 クラスの読者・塞ぎの分量予算）。…新設・変更したら**起動する**」
    - どう手を抜けるか: 起動して所見を受け取り、「分量予算の都合で今回は塞がない」と判断して終える。塞ぐ義務・塞がなかった項目の記録義務・再検証の義務がこちら側に無く、判断基準は委譲先の中にあるため、履行としては「起動した」で完結する。

17. 「読ませる」相手が指定されておらず、2 クラスの読者はこの文面に無い（N2）
    - 根拠となる文言の引用: 「想定読者の観点で**文言だけを読ませ**、抜け道を探させる」
    - どう手を抜けるか: 誰に読ませるか（別のエージェントか・独立した視点か・何クラスか）が本文に無いので、自分で想定読者になったつもりで読み返し「抜け道は見当たらなかった」と書いて完了にする。「2 クラスの読者」は委譲先スキルの括弧内に列挙されているだけで、履行の必須要素として書かれていない。

18. 4 スロット義務が「名前の接尾辞」で発火するので、命名で外せる
    - 根拠となる文言の引用: 「**check 系スキル（`*-check`）は** 4 スロット（母集団・証拠・停止・接続）と費用対称性を満たす」
    - どう手を抜けるか: 実質は検査スキルでも `verify-foo` / `foo-review` / `foo-audit` と命名すれば `*-check` に当たらず、4 スロットの設計義務も費用対称性の検討も不要になる。自己分類が可能な唯一の判定キーが名前である。

19. 「条項を足す前に…見る」は、書き換えに掛からず、出力物も要求しない
    - 根拠となる文言の引用: 「**条項を足す前に**その節のスコープ宣言を**見る**（検算の母集団は規範が名乗る範囲）」
    - どう手を抜けるか: (a) 既存条項の書き換え・強化・全称表現の追加は「足す」ではないと分類して素通りする。(b) 足す場合も動詞は「見る」なので、開いて眺めれば履行済み。矛盾していないかを書き出す義務も、矛盾時の扱いも書かれていない。

20. 検算義務が「言葉づかい」に発火するので、その語を使わなければ発火しない（N3・中核）
    - 根拠となる文言の引用: 「一覧・索引・サブエージェントの報告を根拠に「**全部**」「**一致した**」と**言うときは**、(1)…(2)…」
    - どう手を抜けるか: 報告文から「全部」「一致した」を外し、「一覧を確認した」「主要な対象を確認済み」「差分は見当たらない」と書く。実質は一覧を根拠にした網羅主張だが、引き金となる 2 語を避けたので (1)(2) の検算は要求されていない、と読める。

21. 検算のサンプルが 1 件で足り、示す先も形式も無い（N3）
    - 根拠となる文言の引用: 「(1) 守りたい対象を **1 件**名指しし、それが実際に読む入力に現れることを示し、(2) 判定対象外が同じ入力に混じらないことを示す」
    - どう手を抜けるか: 明らかに引っ掛かる代表例を 1 件だけ選ぶ（＝「正常時に一覧へ出ない対象」＝本当に危ない対象は選ばない）。「示す」の宛先・証跡形式・保存先が無いので、PR 本文に一文書けば履行になる。(2) も反例 1 件で足りる。

22. 「起きた事実から取る」の例が issue ドメイン固有なので、他分野では該当なしにできる（N3）
    - 根拠となる文言の引用: 「母集団は**派生した参照集合ではなく、起きた事実**から取り（`closingIssuesReferences` ではなく `gh issue list --search "closed:>=<mergedAt>"`）」
    - どう手を抜けるか: 自分の対象（hook の発火・CI の対象ファイル・スキルの適用範囲）には「起きた事実」に相当する独立した観測点が無いと判断し、設定ファイルや一覧の記述をそのまま母集団に使う。「観測点が無い場合どうするか」が書かれていないため、既定は一覧に戻る。

23. 「これまで無意味だった状態」が自己分類なので、意味づけの追加を否認できる（N4・中核）
    - 根拠となる文言の引用: 「**これまで無意味だった状態に意味を与える変更は**、その状態に到達する全経路を列挙する」
    - どう手を抜けるか: 「その状態は元から意味を持っていた（既存挙動を明文化しただけ）」「意味を与えたのではなく読みやすくしただけ」と分類する。この判定は変更者自身が行い、判定を記録する義務も無い。

24. 意味づけの例示が 2 形しかないので、別形だと主張できる（N4）
    - 根拠となる文言の引用: 「「**無出力 = 合格**」「**空 = 未設定**」のような意味づけは…」
    - どう手を抜けるか: 「exit 0 = 合格」「マッチしない = 対象外」「未報告 = 問題なし」「タイムアウトしなかった = 正常」を、例示の 2 形とは違う種類だと分類して列挙義務から外す。「〜のような」は例示であって定義ではないため、境界は読者が引ける。

25. 「全経路を列挙する」に完全性の手続きが無い（N4）
    - 根拠となる文言の引用: 「その状態に**到達する全経路を列挙する**」
    - どう手を抜けるか: 思いついた経路を 3 つ書いて「列挙した」と宣言する。独立再導出・SSOT への照会・網羅の検算といった手続きがこの節に無いので、十分性は自己判断で閉じられる（#471 の内訳＝タイムアウト・起動失敗・出力溢れを写せば体裁も整う）。

26. 「塞ぐ」対象の判定者が自分であり、「隣接分類」が未定義（N4）
    - 根拠となる文言の引用: 「**意味が成り立たない経路をすべて塞ぐ**」「**分類を 1 つ足したときは、隣接分類への到達経路も再列挙する**」
    - どう手を抜けるか: 列挙した各経路に「この経路でも意味は成り立つ（実際上起きない・起きたら別の仕組みが拾う）」と注釈し、塞ぐ作業を 0 件にする。「隣接」の定義が無いので「隣接分類は存在しない」と宣言すれば再列挙も不要。

27. どの義務も完了ゲート・証跡・検査に接続されておらず、未実施が観測されない
    - 根拠となる文言の引用: 「一度は実測する」「起動する」「示す」「列挙する」「塞ぐ」（いずれも記録先・提出先・確認者の指定なし）
    - どう手を抜けるか: 本ファイルは配送されるだけで、PR チェックリスト・CI ジョブ・コミット前ゲートのどれとも結び付いていない。全義務が自己申告で完結するので、最小コストの遵法は「PR 本文に『フォールトインジェクション実施済み・入力集合の検算済み』と 1 行書く」ことになる。この記述の真偽を第三者が確かめる経路が文書内に存在しない。
