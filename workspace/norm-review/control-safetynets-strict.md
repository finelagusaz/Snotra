## 規則を全部守る読者 — safety-nets

1. フォールトインジェクションの義務が条件節に括られており、「手順を省かないなら不要」と忠実に読める（N1）
   - 根拠となる文言の引用: 「**「hook が自動実行する」「CI が担保する」は書かれた時点の期待であって、測定結果ではない**。それに依拠して手順を省く前に、故意に壊して検知されることを 1 度確かめる」
   - 忠実に従うと何が起きるか: 義務の発火条件は「それに依拠して手順を省く」ことである。新設したセーフティネットが既存の手動手順を代替せず純増なら（例: 新しい CI job を足すが手動確認も残す、新しい hook 検査を足すが既存の検証チェックリストは維持する）、条件が成立しないので一度も壊さずに済む。節見出しは「一度は実測する」と無条件だが、規則を全部守る読者は見出しではなく本文の条件節を採る。「新設したら必ず 1 度」と書けば塞がる。

2. 「条件節を免除と読むな」という条項と、この文書自身の条項の形が矛盾している
   - 根拠となる文言の引用: 「「判定が〜なら」のような条件節を免除と読んではならない」／同一文書内の「それに依拠して手順を省く**前に**」「「全部」「一致した」**と言うときは**」
   - 忠実に従うと何が起きるか: 条件節を免除と読んではならないなら、本文の「〜する前に」「〜と言うときは」も免除ではなく常時義務になり、あらゆる変更に全条項が課される。逆に条件節を額面どおり読めば 1・9 の抜け道が開く。どちらの読みが正しいかを文言が決めていないため、厳しい読者は過剰に止まり、緩い読者は素通りする。同じ文書が両方を正当化する。

3. 「1 度確かめる」に主体・粒度・時点・記録先の指定がなく、既存ネットへの追加は「以前 1 度測った」で済ませられる（N1）
   - 根拠となる文言の引用: 「故意に壊して検知されることを 1 度確かめる」
   - 忠実に従うと何が起きるか: 粒度が「セーフティネット単位」と読めるため、既に一度フォールトインジェクション済みの hook へ新しい検査を足すときは「この hook は測定済み」と言って免除できる。時点の指定が無いのでマージ後に回してもよく、完了ゲートにならない。記録先の指定も無いので実施の証跡は会話にしか残らず、後から実施の有無を区別できない——「書かれた時点の期待であって測定結果ではない」ことを問題にする文書でありながら、この文書の遵守自体は書かれた主張でしか確認できない。

4. 「一度は」が回帰検査を要求しないため、実測後の劣化を捕まえる仕組みが残らない
   - 根拠となる文言の引用: 「効いていることは、フォールトインジェクションで一度は実測する」／「手本は `.githooks/githooks.test.mjs`」
   - 忠実に従うと何が起きるか: 手作業で 1 回壊して直せば要求は満たされ、テストとして残す義務はない。手本として挙がっているのは自動テストファイルなのに、要求されているのは一過性の 1 回である。次の変更でネットが黙って壊れても、#471 と同じ「届いていないのに届くと書いてある」状態へ戻る。

5. 複製の作り方が「ソース述語」と「実 git 操作」の 2 種にしか与えられておらず、CI・GitHub ruleset では 2 条項が両立せず実行不能になる（N1 と衝突）
   - 根拠となる文言の引用: 「判定がソース述語でも実 git 操作でも規則は同じで、**変わるのは複製の作り方だけ**である。述語はメモリ上へコピーして変異させ、git 操作は hook を一時ディレクトリへコピーして使い捨て repo の `core.hooksPath` をそこへ向ける」／「稼働中のガードを弱めない」
   - 忠実に従うと何が起きるか: この文書のタイトルは CI を対象に含むが、CI job / GitHub ruleset / `settings.json` の matcher を「複製して変異させる」手段が一切示されていない。ruleset を試すには live の ruleset を触るしかなく、それは明示的に禁じられている。忠実な読者は「1 度は壊して測れ」と「稼働中を弱めるな」の板挟みで変更を出せない。緩い読者は黙って ruleset を一時無効化する——#504 の再演をこの文言が誘発する。

6. 規定された「述語をメモリ上へコピーして変異させる」方法は、配送・登録経路を一切検査しない
   - 根拠となる文言の引用: 「述語はメモリ上へコピーして変異させ」／根拠として引かれる「#471: hook の出力が一度も届いていないのに「届く」という記述の上に PR が積まれていた」
   - 忠実に従うと何が起きるか: コピーした述語の変異体が落ちることを確認しても、実物が発火するか（matcher に載っているか・出力が会話へ届くか）は測れていない。それでも本条項を満たしたので「効いていることを実測した」と言える。引用されている #471 の失敗はまさにこの未検査部分で起きた失敗であり、規定の方法ではその失敗を再現できない。実測が届く経路（登録・発火・出力の到達）まで含むと書かないと、条項が守れば守るほど誤った安心を生む。

7. 「ガードの行使」を live で行うことを許しており、ガードが効いていなければ違反が実現する（後始末の指示も無い）
   - 根拠となる文言の引用: 「意図的に規則違反となる操作を行い、拒否されることを確認する類はガードの**行使**であり、弱めていないので対象外（#482）」
   - 忠実に従うと何が起きるか: 効いているか未知だから測るのであって、拒否されない場合が当然ありうる。live repo で `pre-commit` を行使すれば、拒否されなかった時点で main が実際に進む。「弱めていない」は真だが「壊していない」ことは保証しない。使い捨て repo で行使せよとも、失敗時に何を巻き戻すかとも書かれていない。加えて「対象外」の指示対象が曖昧で、(a) 複製義務の対象外（＝ live で行使してよい）とも (b) 実測に数えない、とも読める。(a) を採ると、拒否されたことだけを確認して検知経路（通知・出力・記録）の検査を一切せずに完了できる。

8. 入力集合の検算が「〜と言うときは」に括られており、言い回しを変えるだけで回避できる（N3）
   - 根拠となる文言の引用: 「一覧・索引・サブエージェントの報告を根拠に「全部」「一致した」と言うときは、(1)…(2)…」
   - 忠実に従うと何が起きるか: 報告に「全部」「一致した」と書かず「確認した」「問題は見当たらない」「一覧を見たかぎり漏れなし」と書けば条件が成立せず、(1)(2) の義務が発生しない。検算の要否が対象の危険性ではなく自分の文章表現で決まる。「一覧・索引・報告を入力に使う検査を新設・変更したら」と対象側で発火させないと塞がらない。

9. (1) の「守りたい対象を 1 件名指し」は、一覧に現れる対象を選べば無条件に満たせる——直後の根拠説明と逆を向いている（N3 の核）
   - 根拠となる文言の引用: 「(1) 守りたい対象を 1 件名指しし、**それが実際に読む入力に現れることを示し**」／「**正常時に一覧へ出ない対象は、その一覧だけを見る検査からは永遠に見えず**」
   - 忠実に従うと何が起きるか: 危険なのは「一覧に現れない対象」だと直後に書いてあるのに、手順が要求するのは「入力に現れることを示せる対象を 1 件」である。忠実な読者ほど、現れることを示しやすい対象を選んで合格判定を得る——守りたい当の対象は一度も見られない。「現れないはずの対象を 1 件立て、それが検査の視界に入らないことを確認したうえで、入らないなら別の観測点を足す」と書かないと、手順が根拠を裏切ったままになる。

10. (2)「判定対象外が混じらないことを示す」は手段が指定されておらず、この節が禁じたはずの「一覧を見た」に還る
    - 根拠となる文言の引用: 「(2) 判定対象外が同じ入力に混じらないことを示す（両方向）」
    - 忠実に従うと何が起きるか: 有界でない入力に対する全称否定を「示す」方法が書かれていないため、実際にできるのは一覧を目で眺めることだけになる。N3 が禁じたい「一覧を見たで済ませる」が、N3 を満たす手順として通ってしまう。

11. 「母集団は起きた事実から取れ」は、事実の台帳が存在しない検査では実行不能
    - 根拠となる文言の引用: 「母集団は**派生した参照集合ではなく、起きた事実**から取り（`closingIssuesReferences` ではなく `gh issue list --search "closed:>=<mergedAt>"`）」
    - 忠実に従うと何が起きるか: 例示は GitHub の close 履歴という台帳のある領域だが、この文書が対象とする多くのネット（文書索引・rules の glob・スキル表・hook の写像）には対応する「起きた事実」のログが無い。忠実な読者は母集団を作れず検算に着手できない。例外の扱い（台帳が無い場合は何を母集団に立てるか）が書かれていないため、実務では黙って派生集合に戻ることになる。

12. 全経路列挙の発火条件が「これまで無意味だった状態」に限定され、最初から意味を持つ新状態が条項の外に落ちる（N4）
    - 根拠となる文言の引用: 「**これまで無意味だった状態に意味を与える変更は**、その状態に到達する全経路を列挙する」
    - 忠実に従うと何が起きるか: 新しい exit code や新しい出力規約を最初から「合格の印」として定義する変更は、既存状態の意味を変えていないので対象外になる。生成される false green は「無出力 = 合格」と同型なのに条項が発火しない。さらに「意味を与えたのではなく既存挙動を明文化しただけ」と自己申告すれば、既存状態の場合でも回避できる。発火条件を「ある状態・値を合格/正常の根拠として読む規約を新設・変更したら」と書けば両方塞がる。

13. 「全経路を列挙」「すべて塞ぐ」に停止条件・分量予算・残余の扱いが無く、忠実に守ると変更を出せない
    - 根拠となる文言の引用: 「その状態に到達する**全経路**を列挙する」／「意味が成り立たない経路を**すべて塞ぐ**」
    - 忠実に従うと何が起きるか: 塞げない経路（プロセス強制終了・OS レベルの失敗・上流ツールのクラッシュ）が 1 つでも残れば、条項を満たせないので変更を出せない。同じ文書が規範レビューについては「停止条件の決め方・塞ぎの分量予算」を `/norm-review` に持たせていると明言しているのに、この節には停止条件も予算も無い。結果として、受容する残余をどう記録するかの経路が無く、黙って無視する運用へ倒れる。

14. 「規範文書はセーフティネットだが paths 外」と「パスに属する規範（…および規範文書）」が矛盾し、ルート規範の改訂が 2 クラス読者検証から抜ける（N2）
    - 根拠となる文言の引用: 「規範文書（ルート `CLAUDE.md` / `AGENTS.md` 等）もセーフティネットだが `paths` 外＝自動配送されない」／「パスに属する規範（`.claude/rules/` `.claude/skills/` **および規範文書**）を新設・変更したら起動する」
    - 忠実に従うと何が起きるか: 同じ文書の中で、規範文書は「paths 外」であり同時に「パスに属する規範」だとされている。前者を採る読者は `/norm-review` の起動義務が無いと判断する。しかも規範文書を触ってもこのファイルは配送されないので、そもそも矛盾を読む機会が無い——ルート `CLAUDE.md` / `AGENTS.md` の改訂は 2 クラス読者検証を素通りする。逃げ道は「必要時に手動参照する」だけで、必要かどうかを判断する材料が本人の側に無い。

15. 適用範囲の SSOT と配送条件の SSOT が同じ `paths` に重ねられており、「対象か」の判定を誤らせる
    - 根拠となる文言の引用: 「このファイルは、セーフティネットそのもの（**対象は上の `paths` が SSOT**）を触ると自動配送される」
    - 忠実に従うと何が起きるか: 「対象は paths が SSOT」を額面どおり適用すると、paths 外の規範文書は本手順の対象外という結論になる（直後の一文がそれを否定しているが、括弧書きの断言のほうが SSOT 宣言として強く読める）。配送条件（何を触ると配られるか）と適用範囲（何にこの手順が課されるか）は別物なので、後者を paths に紐づけない書き方が要る。加えて、貼られた本文には `paths` の実体が含まれない（「上の」frontmatter）ため、配送された文面だけでは対象集合を確定できない。

16. `*-check` スキルの 4 スロット条項が「義務」ではなく「事実の記述」の形で書かれ、かつ命名で回避できる
    - 根拠となる文言の引用: 「**check 系スキル（`*-check`）は 4 スロット（母集団・証拠・停止・接続）と費用対称性を満たす**」
    - 忠実に従うと何が起きるか: 述語が「満たす」（現状の記述）であり「満たさなければならない」ではないため、新設時の義務と読む根拠が文中に無い。さらに対象は名前が `*-check` のスキルに限られるので、`/foo-audit` `/verify-foo` `/foo-review` と名付ければ条項の外に出る。名前ではなく役割（検査を行うスキル）で発火させないと、命名だけで回避できる。

17. 「その節のスコープ宣言を見る」は、スコープ宣言が無い節に対して行動が定義されていない
    - 根拠となる文言の引用: 「条項を足す前にその節のスコープ宣言を見る（検算の母集団は規範が名乗る範囲）」
    - 忠実に従うと何が起きるか: 対象の節にスコープ宣言が無い場合に何をするか（足さない／宣言を先に書く／別節へ移す）が書かれていない。また「見た」結果として何を判断するかも無いため、見るだけで条項を満たせる。
