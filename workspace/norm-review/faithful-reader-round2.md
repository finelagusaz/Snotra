# norm-review 2 巡目 — 規則を全部守る読者

## 書き換えが作った新しい誤誘導

- **(A) 「一時ファイル（`$env:TEMP/<名前>`。区切りは `/` を使う——`\` はこの hook の別判定に当たります）」**
  逐語引用: `一時ファイル（$env:TEMP/<名前>。**区切りは / を使う**——\ はこの hook の別判定に当たります）へ書いて git commit -F <tmpfile> や --body-file で渡す`
  忠実な読者は Write ツールに渡す `file_path` を絶対パスで書く必要がある（Write ツールは相対参照や未展開の環境変数を解釈しない）。`$env:TEMP` はそれ自体では絶対パス文字列ではなく PowerShell の変数参照であり、Write ツールに渡すには読者自身がまず値を解決しなければならない。その解決結果は Windows では `C:\Users\<user>\AppData\Local\Temp` のように**先頭が `C:\`** になる——まさに 3 形のうちの 1 つである。読者が指示どおり「区切りは `/`」を末尾のファイル名部分にだけ適用し、解決済みディレクトリ部分の `\` はそのままにすると、後続の `git commit -F <tmpfile>` コマンド文字列には結局 `C:\...\Temp/<名前>` が literal に現れ、まさに回避しようとした `\` 判定（`C:\` 形）を踏む。指示文は「`$env:TEMP/<名前>`」という表記だけを与え、どちらを意味するか（(a) 未展開のまま渡せという意味なら Write ツールに渡す時点でそもそも無効なパスになる／(b) 解決済み絶対パスの**全区切りを** `/` に置き換えろという意味）を明示していない。読者は一意に安全なコマンド列を導けない
  （合格条件 1: 代替の一時ファイルパスが Write ツールの絶対パス要件と食い違い、かつ後続コマンドで自分自身が警告した `\` 判定に再突入しうる／箇所 A）

- **(B) 「履歴が発散して FF できないなら `git fetch` してから `git rebase` / `git merge` を明示的に打ってください」**
  逐語引用: `git pull --ff-only を使ってください（この判定はブランチを見ないのでどのブランチでも同じです。履歴が発散して FF できないなら git fetch してから git rebase / git merge を明示的に打ってください）`
  この拒否メッセージが発火する典型状況は「main の同期」（`--ff-only` でない `git pull`）であり、機構の事実により main は `.githooks/` の 4 hook（直接 commit・非 FF merge・rebase・push の拒否）で保護されている。main 上で発散していて FF できない場合、この指示に忠実に従って `git rebase` を打てば pre-rebase hook に、`git merge`（非 FF ゆえマージコミットを作る）を打てば `pre-merge-commit` hook に、いずれも拒否されて詰む。指示文はどちらの代替も無条件に「明示的に打ってください」と勧めており、main 上ではその代替自身が別の hook に引っかかって行き止まりになることに触れていない。読者は「拒否メッセージの言うとおりにしたのに、また拒否された」という状態に落ちる
  （合格条件 1: 提示された代替コマンドが別の hook 判定に引っかかる／箇所 B）

- **(D) 「接頭辞を持たない相対パスの `\` は見ない」に規範の再確認が無い（(C) との非対称）**
  逐語引用（D）: `接頭辞を持たない相対パスの \ は見ない（cat docs\hooks.md）。\ 判定は上表の 3 形しか見ないので、これは形を絞ったことの代償である。`
  直前の逐語引用（C）: `検出しないだけで、規範としては / を使う。`
  同じ「受容する未対応リスク」節で、直前の (C) 項目は「検出されないが規範は変わらず `/` を使う」と明示的に念押ししている。その直後に追加された (D) 項目は同じ構造（検出漏れの説明）でありながら、この念押し文だけが欠けている。読者が (C) と (D) を並べて読めば、(C) にだけ念押しが付いている非対称そのものを「(D) の形は念押しされていない＝規範上も特に問わない」という**意図的な省略**と解釈しうる。節の見出し自体が「受容する未対応リスク」であり、これは検出機構としての受容であって規範としての許可ではないが、(D) の文はその区別を自力で補わない限り伝わらない
  （合格条件 3: 一覧が「検出されないなら使ってよい」と読める／箇所 D、(C) との対比が新たに生んだ非対称）

## 新しい問題が無いと判断した箇所

- (B) の「main では」を外し「この判定はブランチを見ない」と一般化した部分自体は、渡された機構の事実（pull 判定はブランチを見ない・platform 非依存）と整合しており、単独では誤誘導を生まない。問題は後続の代替コマンド提示（上記で指摘）にある
- (C) 自身の文面（`.\` / `..\` を検出対象外とし、かつ規範は `/` のままと明示する）は、1 巡目で問題視されたであろう「検出されない＝許可」の誤読を先回りして塞いでおり、今回の書き換えとしては健全
- (A) の「`git commit -F <tmpfile>`」を main 上で直接使うと `.githooks/pre-commit` に拒否される点は、この巡で新たに書き換えられた箇所ではなく（1 巡目から存在する前提であり）当該指摘は対象外とした
