# norm-review 1 巡目 — 規則を全部守る読者

## 忠実に従うと誤る箇所

- **拒否メッセージ[1]の代替が拒否メッセージ[2]の判定に落ちる** — [1] は「複数行テキストは Write ツールで一時ファイル（`$env:TEMP` 配下）へ書いて `git commit -F <tmpfile>` や `--body-file` で渡すか」と指示する。だが `docs/hooks.md` の表は `usesBackslashPath` を「`C:\` / `$env:X\` / `%X%\` の 3 形」で発火すると定義している。`$env:TEMP` は文字どおり `$env:X` の形そのものであり、忠実な読者がこの指示に従って自然に書く経路名 `$env:TEMP\msg.txt`（あるいは `$env:TEMP\out.txt`）は `$env:X\` パターンに一致し、`git commit -F $env:TEMP\msg.txt` や `gh pr create --body-file $env:TEMP\body.txt` は今度は [2] の判定で再度拒否される。[1] のメッセージ内には「その経路名は `/` に変換せよ」という一言も、[2] への参照もない。[1] だけを読んだ読者はここで手詰まりになる（次に打つべき一意なコマンドを決められない）。
  （合格条件: 1。かつ「特に注意して確かめてほしいこと」に直接該当——代替手段そのものが別の判定に引っかかる）

- **拒否メッセージ[5]は危険を「main」に限定して語るが、実装は全ブランチを止める** — [5] は「非 FF の `git pull` は main にマージコミットを作り、`.githooks/pre-merge-commit` が拒否します」と言い、暗に「main でなければ問題ない」と読める。しかし `docs/hooks.md` は明記する:「**`pull` はブランチを見ない**ので `git pull --rebase` も feature ブランチでの pull も止まる（過剰検出）」。さらに [5] が示す唯一の代替 `git pull --ff-only` は、履歴が発散した feature ブランチ（リモートと ローカルコミットが分岐し、本来 `git pull --rebase` で追従すべき状況）では fast-forward 不能で失敗する。この状況を解決する経路（例: `git fetch` と `git rebase` を分けて打つ等）は [5] にも `docs/hooks.md` の当該追記にも書かれていない。忠実な読者は「main の話だから自分のブランチは大丈夫」と誤解した上、実際に拒否されても提示された唯一の代替コマンドでは目的を達成できない。
  （合格条件: 1。「main にマージコミットを作り」という限定句が実際の発火条件（ブランチ非依存）より狭く、暗黒に 2 も誘発しうる）

## 全称表現が実装より強い箇所

- **「受容する未対応リスク」の列挙が網羅を装うが、実際にはもう一つ穴がある** — `docs/hooks.md` は `usesBackslashPath` の発火形を「`C:\` / `$env:X\` / `%X%\` の 3 形」に限定すると明記した上で、受容する未対応リスクを 4 件（引用内分割・非 ASCII 非表示・`.\`/`..\` 除外・`pull` の過剰検出）だけ列挙している。しかし `C:\`・`$env:X\`・`%X%\` のいずれのプレフィクスも持たない素のバックスラッシュ相対パス（例: `mkdir foo\bar`、`type docs\hooks.md`）は「3 形」のどれにも一致せず検出されない——これは拒否メッセージ[2]が主張する一般則「パス区切りの `\` は…壊れやすく」の対象そのものだが、受容リスクの列挙には現れない。「受容する未対応リスク」という見出しは、既知の穴を尽くしたという含意を持つが、実装の穴の集合はこれより広い。
  （反例: `docs\hooks.md`, `foo\bar\baz.txt` のような env/drive 接頭辞の無い相対パス）

## 矛盾する 2 条項

- **拒否メッセージ[2]の「`/` で統一してください」（無条件）と `docs/hooks.md` の `.\`/`..\` 除外の理由付け** — [2] は「`/` で統一してください — PowerShell でも Git / Node / Cargo は `/` を受け付けます」と、バックスラッシュ経路全般を対象に無条件の変換を求める。一方 `docs/hooks.md` は判定の除外理由として「**`.\` / `..\` を `\` 判定に含めない。** `.\scripts\x.ps1` は PowerShell で正しく動く形であり、止める理由が弱い」と述べ、この形は「正しく動く」ため変換不要であることを示唆する。[2] を忠実に読む読者は `.\scripts\x.ps1` も `/` へ変換しようとするが、`docs/hooks.md` を読む側（フック改修者）は同じ形を「問題ない」と判断する——同じコマンド形について「常に変換すべき」と「変換しなくてよい」という 2 つの規範が並立する。
  （両立しない理由: [2] は例外を設けない全称の変換指示、`docs/hooks.md` は同一の入力形に対し変換不要の判断を明文化している）

## 問題が無いと判断した箇所

- 拒否メッセージ[3]（Python 非 ASCII）は cp932 という Windows 固有のコンソール符号化を根拠にしており、`needsPyEncoding` が `win32 のみ` である設計と整合する。「Windows だけの話だから macOS では好きにしてよい」という誤読（合格条件2）を招く余地は薄い——根拠自体が Windows 特有の事象だからである。
- 拒否メッセージ[4]（`--no-verify` 禁止）と `docs/hooks.md` の `_lib.sh` に関する記述（人間向けの迂回案内は「人間専用」と明示されているため矛盾ではない）は、文書内で明示的に矛盾ではないと解決されている。
- `docs/hooks.md` の「受容する未対応リスク」冒頭括弧書き「**『検出されないなら使ってよい』ではない**」は、合格条件3（検出されないリスクは使ってよいと読める）を先回りして明示的に否定しており、この一文単体では誤誘導にならない。
