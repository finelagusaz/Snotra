# norm-review 2 巡目 — 手を抜く読者

## 書き換えが作った新しい抜け道

- **(A)+(D) 組み合わせ: 「別判定」に当たらない `\` を選んで温存する**
  (A) は「`$env:TEMP/<名前>`。**区切りは `/` を使う**——`\` はこの hook の別判定に当たります」と言う。この一文は「`\` を使うと別判定に引っかかる」としか言っていない。(D) はその別判定の形を明示している——「`\` 判定は上表の 3 形しか見ない」「接頭辞を持たない相対パスの `\` は見ない（`cat docs\hooks.md`）」。
  この二つを重ねれば、私は一時ファイルのパスを `$env:TEMP\out.txt` のような接頭辞つき形にはせず、代わりに **相対パス**（例: `out\commit-msg.txt`、あるいは `git commit -F out\commit-msg.txt`）で `\` を使えばよいと分かる。(A) が名指しした「別判定」は (D) によれば "上表の3形" しか見ないので、接頭辞なし相対パスの `\` はどの判定にも当たらない。つまり (A) の警告文をそのまま守った（「別判定に当たる書き方は避けた」）ことにしつつ、`/` を使うという本来の指示は無視できる。
  合格条件 1（代わりに打つコマンドを一意に決められない）と 3（「検出されないなら使ってよい」と読める）の両方に当たる。箇所は A と D。

- **(B): 「main では拒否します」と「この判定はブランチを見ない」の内部矛盾を使い分ける**
  引用: 「非 FF の `git pull` はマージコミットを作り、**main では** `.githooks/pre-merge-commit` が拒否します。`git pull --ff-only` を使ってください（**この判定はブランチを見ないのでどのブランチでも同じです**。…）」。
  1文目は拒否の主体を「main では」と明示的に限定している。括弧内の「この判定はブランチを見ない」は、これと矛盾する（同じ段落内で「main 限定」と「ブランチ非依存」の両方を主張している）。手を抜く読者としては、フィーチャーブランチで非 FF `git pull` をしたいとき、都合の良い1文目（「main では」＝main以外は対象外）だけを根拠に採用し、括弧内の「ブランチを見ない」は「単なる注意書きの一般化であって実際の拒否機構の話ではない」と解釈して無視する。文面上どちらの読みも排除されていないので、この選択的採用を止める材料がない。
  合格条件 1・2 の派生形（「main だけの話だから他ブランチでは好きにしてよい」という、OS限定と同型の誤読）に当たる。箇所は B。

- **(B): 「明示的に `git rebase` / `git merge` を打つ」を対称な選択肢として提示している**
  引用: 「履歴が発散して FF できないなら `git fetch` してから `git rebase` / `git merge` を明示的に打ってください」。
  この文は `git rebase` と `git merge` を `/` で並置し、どちらも同格の解決策として提示している。しかし直前の文で拒否の理由として挙げているのは「マージコミットを作ること」そのものであり、`git merge` を明示的に打っても（`git pull` が内部でやることと同じ）マージコミットは作られる。手を抜く読者としては、「拒否されるのは `git pull` という**コマンド名**であって、`git merge` という別のコマンド名を使えば、たとえ結果が同じマージコミットでも、この一文が推奨する正規の手順を踏んだことになる」と読む。文面は `git merge` の使用を無条件に推奨しており、「main 上で非 FF なら merge も同様に拒否されうる」という限定を一切書いていないので、この読み替えを妨げる記述がない。
  合格条件 1（一意に決まらない——rebase と merge が非対称なのに対称に見える）に当たる。箇所は B。

- **(D) は新規追加なのに (C) が得た「規範としては」の念押しを持たない**
  (C) は書き換えで「**検出しないだけで、規範としては `/` を使う**」という念押しを追加された。同じリストに今回**新規追加**された (D) は「`\` 判定は上表の 3 形しか見ないので、これは形を絞ったことの代償である」で終わり、(C) と同じ「規範としては `/` を使う」という一文を持たない。リスト全体の前置き（「検出されないなら使ってよいではない」）は変更されていないので建前上は効いているはずだが、手を抜く読者は個々の項目だけを読んで行動を決める——(C) には自分に向けた念押しがあるのに (D) にはない、という非対称は「(D) は前置きの念押しの対象外」という誤読の余地を作る。前置きを都合よく読み飛ばし、(D) の記述だけを「相対パスの `\` は仕様上ノーマークだ」という許可として使う。
  合格条件 3 に当たる。箇所は D（C との比較）。

## 新しい抜け道が無いと判断した箇所

- (C) 単独の書き換え（「正当化が弱い」を外し「検出しないだけで、規範としては `/` を使う」を明記）は、1巡目の「検出されないなら使ってよいと誤読される」懸念に対して項目自身に規範文を持たせており、この項目単体では新しい抜け道を作っていない（(D) との非対称という形で上に別途指摘した）。
- (A) の `$env:TEMP/<名前>` という具体的な代替パスの提示自体（`/` 区切り・`$env:` 接頭辞つき）は、上表の3形の一つに正しく合致しており、この部分だけを見れば別判定にも元の `\` 判定にも矛盾なく捕捉される——抜け道は (D) と組み合わせたときにのみ生じる。
