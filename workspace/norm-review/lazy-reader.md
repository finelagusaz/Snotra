# norm-review 1 巡目 — 手を抜く読者

## 見つけた抜け道

- **`.\`/`..\` の除外理由が「正しく動く」への一般的な太鼓判に読める** — hooks.md: 「**`.\` / `..\` を `\` 判定に含めない。** `.\scripts\x.ps1` は PowerShell で正しく動く形であり、止める理由が弱い。」直前の「受容する未対応リスク」の見出しは「**「検出されないなら使ってよい」ではない** — 検出されない形も**規範に反するなら**人間専用の意図的迂回」と条件付きで否定している。裏を返せば「規範に反しない」形は対象外——`.\` の項はまさに「正しく動く」＝規範に反しないと明言している。自分は「`.\scripts\build.ps1`」のような相対パスを常用し、さらに「これも実際に正しく動く」と自分で判定できるパス（例: 絶対 Windows パスでも自分のスクリプトでは問題なく動く）にも同じ論法を延伸して、メッセージ2の「`/` で統一してください」を無視する。
  （合格条件: 3。加えて自分で分類を選べる=「規範に反しない」を自己認定できる点で1にも波及）

- **`usesHeredoc`/`usesBackslashPath`/`needsPyEncoding` が `win32 のみ` なので、非 Windows では「規範の射程外」と明記されている** — hooks.md 表: 「| `usesHeredoc` | ... | win32 のみ |」「| `usesBackslashPath` | ... | win32 のみ |」「| `needsPyEncoding` | ... | win32 のみ |」、および本文「渡されないときは Windows 専用判定を発火させない — これは「判定不能」ではなく「**規範の射程外**」であり、block へ倒すと非 Windows で false block になる。」自分が非 Windows 環境（あるいは非 Windows と自称できる文脈）で作業しているなら、heredoc・`\` パス・Python エンコーディング前置のどれも「射程外」と明記されているので、代替コマンドへ切り替える義務そのものが無いと判断して終える。
  （合格条件: 2）

- **メッセージ2の「`/` で統一してください」という全称指示と、hooks.md の検出範囲「3 形」に不一致がある** — 拒否メッセージ[2]:「パス区切りの `\` はエスケープが要るため壊れやすく...`/` で統一してください」（無条件）。一方 hooks.md 表:「`usesBackslashPath` | `C:\` / `$env:X\` / `%X%\` の 3 形。正規表現エスケープ（`\d`）や `find -exec \;` は巻き込まない」。ドライブ文字や環境変数プレフィックスを持たない裸の相対パス（例: `src\main.rs`、`scripts\build.ps1`）はこの 3 形のいずれにも当たらないため、検出されない。拒否メッセージだけを読む読者は「/ に統一」という広い義務を負うが、実際に確認できる／確認された義務は「3 形を避ける」という狭い範囲だけになり、どちらを守れば十分かを一意に決められない。自分はこの不一致を使って「列挙された 3 形以外の `\` はそもそも問題にされていない」と判断し、裸の相対パスでは変換をやらない。
  （合格条件: 1）

- **メッセージ2の根拠が「Bash では黙って食われて」に限定されており、Bash ツール以外なら適用外と読める** — 拒否メッセージ[2]:「パス区切りの `\` はエスケープが要るため壊れやすく、**Bash では**黙って食われて**エラーではなく誤った結果**になります。」根拠として名指しされているのは Bash の挙動だけである。自分は「この事故は Bash ツールでの解釈の話であり、PowerShell ツールを使えば `\` は素直に解釈されるので事故は起きない」と判定し、以後 Windows パスを書くときは常に PowerShell ツールを選んで `\` をそのまま書き続け、`/` への変換を省く。hooks.md の判定表は `usesBackslashPath` がどのツールのコマンドに対しても発火するかを明示していない（platform 列があるだけでツール列がない）ため、この自己分類を退ける根拠を拒否メッセージ単体からは拾えない。
  （合格条件: 1）

- **引用内で `--no-verify` がセグメント分断される具体例が、既存の免責文とセットで「知られた手口」として読める** — hooks.md 受容リスク: 「**引用内の区切りでセグメントが切れる**（`git commit -m "a;b" --no-verify"）。引用認識の分割は shell パーサ相当になり、payload 全体 grep の誤爆を作り直す。」直前の総論（「検出されないなら使ってよいではない」）を読み飛ばし、具体例だけを拾えば「`;` を含む引用文字列に `--no-verify` を埋め込めば素通りする」という実行可能な手順がそのまま手に入る。総論は同じ段落内にあるが、箇条書き自体には個別の禁止の再掲がなく、末尾の一般論に頼っている。
  （合格条件: 3）

- **Python の非 ASCII 検出が「コマンド文字列に現れない」場合は不可視と明記され、ロジックをスクリプトへ退避すれば前置が要らないと読める** — hooks.md 受容リスク: 「**コマンド文字列に現れない非 ASCII は見えない**（`python foo.py` でスクリプト側が出す形）。コマンドの形からは判定材料が無い。」自分は非 ASCII を出す処理を常に外部 `.py` ファイル側に押し込み、コマンドラインは `python foo.py` のような素の呼び出しに留めることで、`PYTHONIOENCODING=utf-8` 等の前置を毎回省く判断をする。
  （合格条件: 3）

## 抜け道が見つからなかった箇所（塞がっていると判断した理由）

- **`--no-verify` の全面禁止**: 拒否メッセージ[4]は「主保護の迂回」という限定的根拠のあとに「**人間専用であり、エージェントは使用してはなりません**」という無条件文が続く。根拠（main 保護）に依存しない絶対禁止の言い切りなので、「自分は main に触っていないから対象外」という分類は通らない。またサブエージェントの `.githooks/_lib.sh` 由来の案内文についても、hooks.md が「明示的に『人間専用。エージェントは使用禁止』と書いてあるため矛盾ではない」と先回りして塞いでいる。
- **`git pull --ff-only` の代替**: 拒否メッセージ[5]は理由（非 FF マージコミット）と手段（`--ff-only`）が 1 対 1 で対応し、他の選択肢（`--rebase` 等）を匂わせる語がない。hooks.md 側の「`git pull --rebase` も feature ブランチでの pull も止まる」という過剰検出の記述も、「それでも止まる」という結論であって「だから使ってよい」という結論には繋がらない。
- **Python エンコーディングの前置形**: 3 形（`PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1` / `-X utf8`）が拒否メッセージ[3]に列記され、hooks.md の判定条件とも一致している。どれを選ぶかの曖昧さはあるが、いずれを選んでも義務は果たされるため「省略してよい」方向の抜け道にはならない。
- **heredoc の代替（git commit 文脈）**: 拒否メッセージ[1]は一時ファイル＋`-F`/`--body-file`、または here-string という 2 系統を提示し、いずれも「複数行テキストを安全に渡す」という同じ結果に落ちる。目的別の対応が明確なため、コミットメッセージや PR 本文の文脈では読者が選べる余地はあっても、義務を免除される余地はない。
