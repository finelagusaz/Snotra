# 忠実読者レビュー（round 1）— `.claude/skills/implement/SKILL.md`

- **問題**: 「実行不能」の対象が D に閉じていない。項目2は `カテゴリD等` と書いており、`等` が実行できる他カテゴリを実行不能側へ逃がす扉になる。Step 3 本文は D だけを「エージェントが実行できない」理由（対話入力）に限定しているのに、報告節はそれを踏襲せず一般化した。
  引用: `.claude/skills/implement/SKILL.md:127`「**該当するが実行不能**（カテゴリD等。人間へ引き渡す目視項目を列挙する——実行できるカテゴリをここへ入れてはならない）」／対比: `.claude/skills/implement/SKILL.md:88`「**カテゴリDはエージェントが実行できない**（対話入力を要する）」
  さらに具体例: `docs/build-commands.md:105-116`「Windows のみ実行可能（`windows` クレートや Win32 API・実行バイナリに依存）」がカテゴリ A の `cargo test -p snotra-core` 等を再掲し、非 Windows 環境では**実行それ自体が不可能**と明記する（この検証を行っている実行環境は Darwin）。この場合、理由は D の「対話入力」ではなく「プラットフォーム制約」であり、`人間へ引き渡す目視項目を列挙する` という実行不能の書式が意味をなさない（目視項目が存在しない）。忠実な読者は「カテゴリD等」を根拠に、macOS 上で cargo 系が動かせないカテゴリ A を「実行不能」へ丸め込むか、逆に書式に困って「該当なし」へ誤分類するかの二択を迫られる——どちらも実装より強い/弱い報告になる。
  **合格条件との対応**: 3

- **問題**: 項目3の母集団定義が、4a 自身の「二重管理を避けるためここに再掲しない」という宣言と矛盾する。4a は括弧書きの6スキルを**例示**として挙げつつ、直後で「トリガー→検査の写像のSSOTはその表[AGENTS.md]。二重管理を避けるためここに再掲しない」と明言している——つまり4aの括弧書きは写像のSSOTではないと自ら否定している。ところが項目3はその同じ括弧書きを報告母集団の確定根拠として使う。
  引用: `.claude/skills/implement/SKILL.md:104`「変更の種類に応じたcheckスキル（`/symmetric-check`・`/dry-check`・`/race-check`・`/cache-check`・`/persistence-check`・`/state-check`）を、**`AGENTS.md`「条件別チェック（トリガー → 参照先）」表に従って**実行する（トリガー→検査の写像のSSOTはその表。**二重管理を避けるためここに再掲しない**）」
  vs `.claude/skills/implement/SKILL.md:128`「母集団は「4a. check スキルの実行」が**名指しする** check スキルと、4bの`code-reviewer`であり、**その全員が1度ずつ現れる**」
  AGENTS.md の「条件別チェック」表に新しい check スキル行が増えても（例えば将来 `/foo-check` が追加されても）、4a の括弧書きを直さない限り項目3の母集団には現れない。全称表現「その全員が1度ずつ現れる」は、4aの括弧書きが表と同期している間しか成立しない前提を持つが、その前提はどこにも書かれていない（`AGENTS.md`「全称表現は前提条件とセットで書く」への違反）。
  **合格条件との対応**: 6（4aの宣言との直接矛盾という点で、想定より強い形の同一の穴）

- **問題**: Step 3 の5サイクル中止は「途中で止まった場合」の停止パスであると同時に、Step 2 は完了しているため「Step 2以降まで進んだ場合」の報告バンドルの適用条件も満たしてしまう——両方が同時に真になる場合にどちらが優先するか本文が決めていない。前者に従えば診断サマリーのみを置き、後者に従えば項目1〜4（うち項目2はカテゴリA〜Fの三値）を書く。項目2の三値（実行/該当なし/実行不能）には「5サイクル試みて失敗し断念した」を表す値が無いため、後者を選んだ読者は失敗したカテゴリを「実行不能」（人間へ目視項目を渡す体裁に合わない）か「該当なし」（虚偽）へ押し込まざるを得ない。
  引用: `.claude/skills/implement/SKILL.md:122-123`「途中で止まった場合、到達しなかったStepに対応する項目は書かない……代わりに**どこで止まったか**と、その停止が定める報告（Step1なら1cの渡し方に沿った引き渡し、**Step3の5サイクル中止なら診断サマリー**）を置く」／`.claude/skills/implement/SKILL.md:125`「Step 2以降まで進んだ場合、以下を報告」／`.claude/skills/implement/SKILL.md:95-98`「5サイクル後もエラーが残る場合、中止して診断サマリーを書く」
  **合格条件との対応**: 新規（5 に隣接するが、対象は項目3ではなく項目2であり、「どちらの書式で書くか」自体が未決という点で異なる穴）

- **問題**: 出力節の停止時マッピングが「Step1なら1cの渡し方」と書いており、文字どおりには**Step1で**発生した停止だけを指す。しかし Step 1 自身は「サインは実装の途中で立つこともある。その場合もその時点で止める」と明記しており、1c の引き渡し（issue草案の打診等）は Step 2〜4 の途中で発覚したときにも発動しうる。忠実な読者が出力節の「Step1なら」を文字どおり読むと、Step 3 や Step 4 の途中で「計画が要るサイン」が立って 1c-A 相当の停止をしたケースに対応する報告書式がどこにも定義されていないことになる。
  引用: `.claude/skills/implement/SKILL.md:66`「**サインは実装の途中で立つこともある。** その場合もその時点で止める」／`.claude/skills/implement/SKILL.md:123`「その停止が定める報告（**Step1なら**1cの渡し方に沿った引き渡し、Step3の5サイクル中止なら診断サマリー）を置く」
  **合格条件との対応**: 新規

- **問題**: 項目2・項目3の「該当なし」バケットにだけ、根拠・理由の提示義務が無い。項目3は「未実施」に対して「理由を付けて1件1行」を要求し、項目2は「実行不能」に対して「人間へ引き渡す目視項目を列挙する」という実質的な根拠提示を要求するが、「該当なし」にはどちらの項目にも理由や根拠を求める文言が無い。`health-check` の同型三値（Check 7）は逆に「**結論には根拠を添える。「発見事項なし」も同じである**」と明記しており、根拠なしの「該当なし」を許さない。この非対称により、忠実な読者は「本来は4aのトリガーに当たるが判定が面倒な check スキル」を無根拠に「該当なし」で丸めても、項目3の書式要件（「該当なしは1行にまとめて名前を列挙」）を満たしてしまう。
  引用: `.claude/skills/implement/SKILL.md:127`「**該当なし**」（実行不能の直前、理由提示の要求なし）／`.claude/skills/implement/SKILL.md:128`「**該当なし**は1行にまとめて名前を列挙、……**未実施**は理由を付けて1件1行」／対比: `.claude/skills/health-check/SKILL.md:51`「結論には根拠を添える。「発見事項なし」も同じである」
  **合格条件との対応**: 新規（1 に隣接するが、1 は「1件も名指ししない」経路であるのに対しこれは「名指しはするが無根拠に該当なしへ丸める」経路であり、現行の反対策（0件も0件と書く 等）ではブロックされない）
