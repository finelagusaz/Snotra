# race-check SKILL.md — 忠実な読者による round1 レビュー

- **F1. frontmatter の `allowed-tools` が Step 1 を実行不能にしている。** frontmatter は `allowed-tools:` に `Read` / `Grep` / `Glob` の 3 つだけを列挙するが、段 (1) は `git diff main...HEAD` と `git show $(git merge-base main HEAD):<path>` の実行を要求する。どちらも列挙された 3 ツールでは打てない。忠実な実行者は「実装レビュー」の母集団を原理的に取得できず Step 1 で詰まる（証拠形式 (iii) の「打ったコマンドとその出力」も同じ理由で `rg` として書けない）。

- **F2. 規定どおりのコマンド自体が、警告している空母集団を鏡像で生む（R1）。** 段 (1) は「**素の `git diff` を使わない**——コミット後は空を返し、母集団が空のまま全種が正直に 0 件になる（非該当が形式上完全に成立する）」と書くが、代わりに指定する `git diff main...HEAD` は**コミット済みの差分しか見ない**。未コミットの作業ツリーで走らせれば母集団は空になり、全種別が正直に 0 件、(iii) を全種別ぶん添えて「非該当」が成立する。本文には出力表 `[要修正]` 行の括弧「`/implement`「4a. check スキルの実行」は「発見事項があれば修正してから 4b に進む」と定める」があり、修正 → 4b という並びは**この検査がコミット前の作業ツリーで走りうる**ことを示している。にもかかわらず line 49 が挙げる逸脱は「`main` 上で実行する場合や積み重ねブランチの場合」の 2 つだけで、未コミットの場合が列挙から漏れており、この 2 件の列挙が完全なものとして読める。

- **F3. `<base>` が未定義のため、リビジョン明示が 0 件の不定性を閉じていない（R1）。** 「`main` 上で実行する場合や積み重ねブランチの場合は、基準を `git merge-base <base> HEAD` で求めて明示する」の `<base>` を選ぶ規則がどこにも無い。忠実な実行者が `<base>` に `HEAD` を明示すれば基準は HEAD になり差分は空、全種別が 0 件で非該当が成立する。「**捕まえるべきは 0 件ではなく、0 件を生んだ手順の不定性**であり、それは段 (1) のリビジョン明示が閉じている」は、実装より強い全称主張である——明示は要求しているが、何を明示してよいかを制約していない。

- **F4. 証拠義務が「候補」に紐づき「種別」に紐づかないため、1 件宣言で残り種別を見ずに抜けられる（R2）。** 「**候補集合の各要素について、次のいずれか 1 つを書く。**」と「境界を 1 件見つけても、残りの**候補**の裁定は免除されない」は、いずれも実行者が自分で作った候補集合の要素にしか義務を掛けない。全種別ぶんの (iii) を要求するのは「**全種別について (iii) を示し**」だけで、その節の見出しは「**「並行境界なし」と結論してよいとき**」である。ゆえに ① を 1 件だけ候補に立てて境界と宣言すれば、②〜⑧ は一度も grep せずに Step 2 へ進める——どの条項にも違反しない。

- **F5. 母集団に対して grep を打とうとすると、3 つの条項が両立しない（R4）。** 段 (1) が与える対象は `git diff` の**出力テキスト**、段 (3) は「**以降の母集団は候補集合である。** 差分でもファイルでもない」と宣言する。一方で証拠 (iii) は「`rg '\.await' <対象>` → 0 件」、段 (3) は「**呼び出し元の集合に対して種別の grep を 1 回打つ**」と、いずれも**パス引数**を要求する。候補集合はパスではなく、差分とファイルは母集団から明示的に除外されているため、規定どおりのコマンドを書ける対象が存在しない。さらに候補は grep の結果として定まる一方、その grep は母集団に対して打てと言われており、定義が循環している。

- **F6. 実行者は入口を選ばないとされるが、選ばないための手段が本文に無い（R5）。** 「**実行者は選ばない。** 選べる形にすると、重い側を避けて軽い側を自称できる」は、呼び出し元を観測する方法をどこにも与えていない全称主張である。表の第 3 行「実装が既にあるなら実装レビュー。`workspace/plan.md` しか無いなら計画レビュー」の判別語「実装が既にある」も未定義で（リポジトリには常にコードがある／「この変更の実装が」とは書かれていない）、それを差分で判定しようにも F1 により差分が取れない。結果として入口は実行者の自己申告になる。

- **F7. ⑥ は証拠形式 (iii) を原理的に満たせず、非該当の成立条件を塞ぐ（R3）。** 種別 ⑥ の手がかり欄は「**独立した grep は無い**——① のヒットを送信の有無で分類し」と明言するのに、(iii) が要求する書きものは「**打ったコマンドとその出力**」であり、「**全種別について (iii) を示し**」た時だけ「並行境界なし」と結論してよい。⑥ 固有のコマンドは定義上存在しないため、候補 0 件の変更でも非該当の成立条件を文言どおりには満たせない。

- **F8. 差分が触っていない候補は、「1 行の理由で足りる」と「[要修正] にせよ」の両方に掛かる（矛盾）。** Step 4 は「**全面適用は差分が新設・変更した境界に限る。** 既存のまま触っていない境界は 1 行の理由（「この差分は触れていない」）で足りる」と言うが、段 (3) は呼び出し元 1 ホップ・呼び出し先 1 段を母集団に入れ、Step 5 は「**Step 1 の候補数と Step 5 のマトリクスの行数は一致させる**」と要求する。1 行の理由で済ませた境界は 5 観点が未確認なので「**`[要確認]` が 1 つでも残る境界は `[安全]` にしてはならない**」により `[要確認]`、出力表により「安全側へ倒し `[要修正]` として扱う」。忠実に従うと、差分が触っていないコードに対して修正案を出す義務が生じる。

- **F9. 表を「例示」と認めた同じ文が、表外経路の不在証明を要求する（詰まる）。** Step 3 は「**この表は例示であって網羅ではない。** 対象コードに現れる入力ハンドラ・イベント名を grep し、**表に無い経路が無いことを示す**」と書く。網羅でないと認めた集合について不在を示す手段は規定されておらず、「共有状態を変えうる経路を grep で探す」の grep パターンも経路表の「トリガー」欄も（「ユーザー入力（毎フレーム受け付ける）」等）シンボルではないため、打つべきコマンドが書けない（F5 と同じ欠陥の再発）。

- **F10. 根拠の規律が計画レビュー経路を止める（矛盾）。** 出力節は「全判定に、**`file:シンボル` と、その判定を支える実際のコード片（該当行）の両方**を付ける」と全判定に義務を掛けるが、段 (1) の計画レビューは「計画が新設する記述はコードにまだ無く」と明言する。存在しないコード片は添えられず、計画レビューの例外も書かれていないため、計画レビューは出力段で終端できない。

- **F11. Step 5 の雛形が提示する `[要確認]` を、出力表が終端として禁じる（未規定）。** 雛形は「総合判定: [安全] / [要修正: …] / [要確認: <未確認の項目>]」と `[要確認]` を選択肢として並べ、Step 5 本文も「その境界の総合判定は `[要確認]` である」と要求する一方、出力表は `[要確認]` を「終端にできない。安全側へ倒し `[要修正]` として扱う」とする。Step 5 で記録し出力層で変換する運用は一貫しうるが、その変換規則は本文のどこにも書かれておらず、雛形どおりに `[要確認]` で提出してよいかが決まらない。

- **F12. Step 2 の判定軸が、送信を持たない境界に当たらない（誤る）。** 「**判定軸は「送信路が view 寿命の共有か、per-request か」である**」は全称の形だが、種別 ⑥（「channel を経由しない worker」＝① のうち**送信を持たない**もの）と ⑧（paint より後に走るもの）には送信路が無い。忠実な実行者は二択のどちらかを無理に選ぶか、Step 2 を空欄にして Step 5 で `[要確認]` → `[要修正]` へ落とすことになる。

- **F13. 「多数」の閾値が未定義で、個別裁定を回避できる（費用の抜け道）。** 「**呼び出し元が多数あるときは全件を個別に裁定せず、呼び出し元の集合に対して種別の grep を 1 回打つ**」の「多数」に基準が無いため、2 件でも「多数」と称して一括 grep 1 回で済ませられる。さらにその grep がヒットした場合に何をするかが書かれておらず、次の手順が決まらない。

- **F14. 「両方あるなら実装レビュー（計画は既に検証されている）」は偽でありうる前提に基づく（誤る）。** 括弧内の理由は、`workspace/plan.md` が存在すれば計画レビューを通過済みだと仮定しているが、人が直接起動する経路（表の第 3 行）は `/start-issue`「5a」を経ていない場合を含む。忠実に従うと、未検証の計画に対する計画レビューが恒久的に飛ばされる。

- **F15. 非該当の停止権が出力表に無い（未規定）。** 出力表の行は `[安全]` / `[要修正]` / `[要確認]` の 3 つで、末尾の「**Step 1 の候補が 0 件だった場合は「並行境界なし（非該当）」と明示する**」に対応する行が無い。「停止権」という語自体も定義されておらず（`[安全]` 行は「—」）、非該当のときに誰が次を決めるかが決まらない。

- **F16. 「並行境界なし」の成立条件が、存在しない候補を起点とする手順の実行を要求する（未規定）。** 「**全種別について (iii) を示し、かつ辿る範囲（上の 3 つ）を実行したとき**だけである」の「辿る範囲」は 3 つとも候補を起点に定義されている（「候補が読み書きする状態」「呼び出し元（上流）」「呼び出し先（下流）」）。候補 0 件のとき「実行した」と言える内容が無く、空虚に満たされたと読むか実行不能と読むかが本文からは決まらない。

- **F17. ⑧ の手がかり「クリック/ダブルクリックのハンドラ名」は grep パターンではない（詰まる）。** 種別表の他の行がリテラルの正規表現を与えるのに対し、⑧ だけは「`request_repaint_after`, `dispatch`, クリック/ダブルクリックのハンドラ名」と、プロジェクト固有の未定義の名前に義務を掛ける。名前を知るには母集団の外を読む必要があり、(iii) の「打ったコマンドとその出力」を書けない。

- **F18. 「値を運ばない wake」が未定義のまま免除条件になっている。** 4a の「hidden 窓への wake は実効 no-op でよい（次の show で live-read が拾う）が、**それを前提にしてよいのは値を運ばない wake だけ**である」は、wake が「値を運ぶ」とは何かを定義していない（wake handle は通常シグナルのみを運ぶ）。免除の可否が実行者の解釈に委ねられる。
