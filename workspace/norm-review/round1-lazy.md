# race-check SKILL.md — 手を抜く読者によるレビュー（round 1）

- **L1（R1 成立）**: 段 (1) は「**素の `git diff` を使わない**」だけを塞ぎ、「`main` 上で実行する場合や積み重ねブランチの場合は、基準を `git merge-base <base> HEAD` で求めて明示する」の `<base>` を束縛していない。`main` 上で `<base>` に `main` を選べば `git diff $(git merge-base main HEAD)...HEAD` は空を返し、**リビジョンを明示したまま**全種別が正直に 0 件になって「非該当」が成立する。文書自身の「捕まえるべきは 0 件ではなく、0 件を生んだ手順の不定性であり、それは段 (1) のリビジョン明示が閉じている」という閉塞の主張は、この経路で反証される（素の `git diff` との違いは、禁止された文字列を打っていない点だけで、結果は同一）。検査されなくなるもの: 変更全体。

- **L2（費用対称性の宣言が文言自身で破れている）**: 証拠形式は **(i) 境界** が「種別・シンボル・何が誰へ渡るか」のみでコマンドもコード片も要らないのに対し、**(iii) 候補なし** は「**打ったコマンドとその出力**」を要求する。ゆえに「境界あり」と宣言する方が常に安く、「**仕事量は候補の数で決まり、結論の向きでは変わらない**——「境界あり」と結論する方が安い形にしてはならない」は文言レベルで既に破れている。さらに L3 と鎖にすると、**段 (3) で引き込んだ候補**（差分に無いので Step 4 の免除条件に当たる）は (i) で境界宣言 → Step 4 で 1 行免除 → Step 5 の行数一致（「Step 1 の候補数と Step 5 のマトリクスの行数は一致させる」）も満たしたまま、コード片を一度も出さずに閉じられる。差分内の候補には鎖は効かないが、(i)/(iii) の費用非対称そのものは単独で成立する。

- **L3（Step 1 で広げた母集団が Step 4 で無料で捨てられる）**: 段 (3) は候補の**呼び出し元 1 ホップ・呼び出し先 1 段**まで母集団へ入れさせるが、Step 4 冒頭は「**全面適用は差分が新設・変更した境界に限る。** 既存のまま触っていない境界は 1 行の理由（「この差分は触れていない」）で足りる」と免除する。1 ホップで引き込んだ境界は定義上「差分が新設・変更した」ものではないので、**段 (3) で辿らせた対象はもれなくこの 1 行で落とせる**。段 (3) が守りたかった「純粋関数であっても staleness 判定・可視性/表示ゲート述語・世代の照合に使われているなら境界の要石である」は、検証されないまま報告に残る。加えて「差分が新設・変更した」かの分類は実行者の自称であり、既存関数への追記は「境界自体は既存」と言い張れる。さらに免除の射程が上へ開いている——文言は「**全面適用**は…に限る」であって「4a〜4e の適用は」ではないため、同じく境界ごとに走る Step 2（型同定）・Step 3（経路列挙）にも同じ 1 行免除が及ぶと読める（＝辿り込んだ候補について Step 2〜4 が丸ごと消える）。

- **L4（(ii) は理由 1 行の自己申告で、行数検算はその後に走る）**: 「**母集団の外にあるもの**: **同じファイルに居るだけの既存ヒット**」「外したヒットは、**どれをなぜ外したかを 1 行で書く**」— 外す理由に検証水準が無いため、`Mutex`・`.send(` のヒットを「既存ヒット」の一行で任意に間引ける。しかも Step 5 の検算「**Step 1 の候補数と Step 5 のマトリクスの行数は一致させる**」は**除外後の候補数**に対して走るので構造上必ず一致し、(ii) の濫用は検知できない。`git diff` の出力には文脈行（未変更行）が含まれるため、「差分に現れるシンボル」と「同じファイルに居るだけ」の境目も実行者が引ける。

- **L5（型の自称と 5 型目の宣言で 4b が空になる）**: Step 2 の 4 型は「**網羅ではない。5 型目以降を見つけたらそう報告する**」とされ、4b の点検項目は既知 4 型ごとに列挙されている（世代カウンタ＝「**書き側の全サイト**」、per-request＝「**enum の全アームを尽くしたか**」、重複 spawn ガード＝「全終端での remove」に対し、level-triggered は「後着の書き込みが先着の意味のある遷移を黙って上書きしないか」の一判断のみ）。よって **level-triggered を自称するか、「5 型目」と報告する**だけで、4b の重い列挙義務が消える。Step 2 には証拠形式の規定が無く、型の同定に `file:シンボル` もコード片も要求されない。判定軸「送信路が view 寿命の共有か、per-request か」は共有スロットへ直書きする level-triggered も共有側に含むため、この自称を排除しない。そもそも Step 5 の行テンプレートは 4a〜4e の 5 行だけで**型を書く欄が無い**ため、Step 2 の型同定は報告に一度も現れなくてよい。

- **L6（計画レビューは無検証で終わる最安経路 / 入口の自己判定 — R5 部分成立）**: 入口表の第 3 行「どちらでもない（人が直接起動した）」は「実装が既にあるなら実装レビュー。`workspace/plan.md` しか無いなら計画レビュー」と定めるが、「実装が既にある」の判定手段（差分が非空か・ファイルの有無か）が無く、**実行者が判定する**。そして計画レビューは「**grep を結論の根拠にしない**」「**候補は計画が新設すると述べる操作から取る**」、非該当条件も「**計画が新設すると述べる操作を列挙し、そのどれもが種別表に当たらないことを示す**」だけで、**コマンドも出力も要求されない**（実装レビューの (iii) と非対称）。すなわち母集団も結論も自分の散文だけで作れる。呼び出し元が `/implement` か `/start-issue` かを検証する機構は文書内に無く、「実行者は選ばない」という宣言は自己申告に依存する。

- **L7（(iii) のコマンドは対象も手がかりも実行者が選べる）**: 証拠テンプレートは `` 種別 ⑦: 候補なし — `rg '\.await' <対象>` → 0 件 `` と書くが、`<対象>` は最後まで束縛されない（段 (1) の「対象」は diff の**出力テキスト**でありパス集合ではない）。差分テキストへ `rg` を通す読みを採れば、段 (3) で辿った呼び出し元・呼び出し先のファイルは **(iii) の 0 件の射程外**のまま「全種別について (iii) を示し」た体裁が整う。加えて種別 ②④⑤⑧ の手がかりは複数トークンなのに、(iii) は 1 コマンドで足りるため、最も当たりにくい 1 トークン（例: ⑧ を `dispatch` のみ、⑤ を `events::` のみ）で 0 件を作れる。「**0 件は「この手がかりでは見つからなかった」であって「無い」ではない**」と自ら書いているのに、手がかりの網羅を要求していない。

- **L8（未束縛の語の束。しかも文書は外部参照を禁じている）**: 「**呼び出し元が多数あるときは全件を個別に裁定せず**」の「多数」に閾値が無く、2〜3 件でも「多数」と称して grep 1 回で畳める。Step 3 の「共有状態を変えうる経路を grep で探す。**主な**経路」「**対象コードに現れる**入力ハンドラ・イベント名を grep し」の「対象コード」も未定義（差分か・候補の関数本体か・ファイル全体か）で、候補の関数本体に限れば「表に無い経路は無い」が容易に成立する。冒頭が「どちらも本スキルを**改修するとき**に読む——**検査で従うのは本文である**」と定めるため、`<base>`・`<対象>`・「対象コード」を ADR や設計書で埋めることは**文書自身が禁じている**＝曖昧さは本文内で解消不能である。

- **L9（Step 3 の非該当宣言と 4c の拘束範囲の穴）**: Step 3 で到達不能と結論するには「**そのガードの条件式（`if` / `match` / 早期 return）を `file:シンボル` か grep 結果で示す**」という重い義務があるが、**到達可能と宣言する側には証拠が要らない**。そして受け皿の 4c が具体的義務を課すのは「**ユーザー操作**」と「**hide / show を跨ぐか**」の 2 種だけで、表に載る「config 適用」「index build 完了」「他 worker の到着」には対応する点検項目が無い。ゆえに**全経路を「到達可能」と宣言して 4c で `[OK]` と書く**のが最安で、config 監視スレッド・index build 世代 bump・他 worker の総入れ替えは実質的に検査されない。また「表に無い経路が無いことを示す」には証拠形式 ((i)(ii)(iii) 相当) の指定が無く、「grep した、無かった」で閉じられる。

- **L10（4a の hidden 自称）**: 「**hidden 窓への wake は実効 no-op でよい**（次の show で live-read が拾う）が、**それを前提にしてよいのは値を運ばない wake だけ**である」— 「値を運ばない」の判定は実行者の自称であり、対象の窓が hidden かどうかを示す証拠も要求されない。wake 漏れの主要経路（土台 2 が種別 ⑧ 経由で拾うとしたもの）を「hidden なので no-op でよい」の一行で通過させられる。

- **L11（[要確認] の封鎖は Step 4 の 1 行免除で迂回できる）**: 「**`[要確認]` が 1 つでも残る境界は `[安全]` にしてはならない**」「`[要確認]`｜終端にできない。安全側へ倒し `[要修正]` として扱う」は強いが、**未確認を `[要確認]` と書かず L3 の「この差分は触れていない」1 行で処理すれば発火しない**。出力の「根拠の規律」＝「**全判定に、`file:シンボル` と…実際のコード片（該当行）の両方**」も、この 1 行免除が「判定」かどうかを定めておらず、Step 4 が明示的に代替として認めている以上、免除側に読める。

- **L12（種別 ⑥ は沈黙で飛ばせる。文書自身が「最も見落とされる」と名指した種別である）**: ⑥ の手がかり欄は「**独立した grep は無い**——① のヒットを送信の有無で分類し、送信を持たないものがこれである」であり、一方 (iii) は「**打ったコマンドとその出力**」を要求する。**⑥ に書けるコマンドが無い＝(iii) が書けない**ので、手を抜く読者は ⑥ の行を報告に立てないまま「全種別について (iii) を示し」たと称せる。① が非 0 のときの ⑥ は grep で足場が取れない分類労働なのに、それを促す証拠形式も、⑥ を飛ばしたことを検知する検算も無い。落ちるのは「**⑤（listener）と ⑥（① のうち送信を持たない分類）が最も見落とされる**」と文書自身が名指した当の種別＝channel を経由せず managed state / 窓 API を直接叩く監視・再スキャン系スレッドである。

- **L13（空振りの `[OK]` に根拠を付けようが無く、それが引用義務全体を緩める）**: 出力の「根拠の規律」は「**全判定に、`file:シンボル` と、その判定を支える実際のコード片（該当行）の両方**」を課すが、設定値を読まない候補の 4e `[OK]`、状態を共有しない候補の 4d `[OK]` のように**引くべきコード片が存在しない判定**への例外規定が無い。実行者は「引用の無い `[OK]` は許される」と学習し、その扱いを 4a〜4c へも横滑りさせる（規律は 5 観点で同文なので、どれが空振りかを外から区別できない）。

**合格条件の判定**: R1 = **成立（L1）** / R2 = 成立せず（「**証拠は候補集合の各要素に 1 つずつである。境界を 1 件見つけても、残りの候補の裁定は免除されない**」が Step 1 で閉じている。ただし同等の効果は Step 4 で得られる → L2・L3） / R3 = 成立せず（「**候補が 0 件であること自体は正当な結論である**」「Step 1 の候補が 0 件だった場合は「並行境界なし（非該当）」と明示する」で報告経路がある） / R4 = 成立せず（境界的。母集団＝候補集合は定義されており `git diff main...HEAD | rg <手がかり>` へ束縛可能だが、`<対象>` が未束縛のため段 (3) で広げた範囲は grep の射程外に落とせる → L7・L8） / R5 = **部分成立（L6）**（`/implement` `/start-issue` 経由では閉じているが、直接起動時の「実装が既にあるなら」の判定は実行者に委ねられ、呼び出し元を検証する機構が無い）
