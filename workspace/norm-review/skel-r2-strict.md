## 規則を全部守る読者 — 骨格 2 巡目

対象範囲: `docs/check-skill-skeleton-design.md` の `## 骨格 — 4 スロット` 〜 `## 貫く性質 — 費用対称性`（前後の節は文脈としてのみ参照し、指摘の対象にしていない）。

1. 差分アンカーの移行手順 (1)(2)(3) は、背景表 2 行目（`/symmetric-check` の移行漏れ検出）の母集団を作れない——どちらの読みを採っても、要石の射程がその欠陥に届かない
   - 種別: 実行不能（下位に手順の穴）
   - 根拠となる文言の引用:
     - 「(1) 差分を決定的に取得（リビジョン明示）→ (2) その中の候補を列挙 → **(3) 以降の母集団は候補集合**」
     - 「この 1 文が、背景の表に挙げた 2 スキルの同型欠陥を同時に閉じる。」
     - 背景表 2 行目「旧 Set/Map に `.add`/`.set` していた全箇所を grep」「リビジョン未指定。廃止後の作業ツリーでは構造的に 0 件 → **移行漏れ無し**という逆の結論へ導かれる」
     - 「**それを得る決定的な手順**——差分アンカーならリビジョンを明示する（`git diff main...HEAD`）、構造物アンカーなら起点の構造物を明示する」
     - アンカー型表「**差分アンカー** | `/race-check`・`/symmetric-check`」
   - 忠実に従うと何が起きるか: `/symmetric-check` を骨格へ寄せる書き手は、型表の分類（差分アンカー）に従って (1)(2)(3) を当てる。ここで「候補」の読みが 2 つあり、**どちらを採っても手が止まる**。
     - 読み (i)「候補 ＝ 差分の中の `.add`/`.set` 該当箇所」: 母集団 ⊆ 差分 になる。しかし検出すべき移行漏れは定義上「変更されなかった箇所」＝差分に現れない箇所であり、規定どおりに作った母集団はその欠陥を**構造的に含みえない**。背景表が「閉じた」と宣言した当の誤結論（移行漏れ無し）を、リビジョンを明示したうえで再生産する。
     - 読み (ii)「候補 ＝ 差分に現れた廃止対象の構造物そのもの（要素 1 件）」: 母集団は健全だが、各要素の検査中に打つ「旧 API 全箇所の grep」の**リビジョンは要石の射程外**になる。要石が縛るのは母集団取得手順だけであり、元の欠陥（grep のリビジョン未指定）はそのまま残る。
     どちらの読みを採るべきかを本文は書いていない。逃げ道も塞がっている: 必要なのは「基準リビジョンに固定した構造物アンカー」（`git grep <base>` 相当）だが、項目 2 の「——」節は差分／構造物の 2 分岐しか持たず、その枠が無い。かつ廃止後の作業ツリーには起点の構造物が存在しないため構造物アンカー側へも倒せない。加えて「`/cache-check` が健全なのはこの形（述語を列挙 → 述語ごとに検証）だからである」で示される唯一の手本は、同じ本文の型表で**構造物アンカー**に分類されており、差分アンカーに対する実例になっていない——曖昧さを解く例が本文に存在しない。

2. 「貫く性質」の検算とスロット 4 の要求が同時に満たせない——判定値ごとに次の動作を書くと、結論を反転させた時点で仕事量が変わる
   - 種別: 論理衝突
   - 根拠となる文言の引用:
     - 「**費用は母集団の関数であって、結論の関数であってはならない。**」「検算方法: **母集団を固定して結論を反転させ、仕事量が変わるなら非対称**である。」
     - スロット 4「1. **各判定値に対して次の動作**を書く」「`/symmetric-check` は `[適用]`（＝非対称を発見した）と正しく判定しても、その先に修正・報告・停止を課す文言を持たない。」
     - 「ゆえに**義務を足さず、費用を母集団の関数にすることで解消する**。」
     - 非対称の実例表の見出しが「結論 | **課される義務**」であり、「境界あり」側に散文 3 項目という**判定後の報告義務**を費用として数えている。
   - 忠実に従うと何が起きるか: 書き手はスロット 4 を埋めるため `[適用]` に「修正・報告・停止」を、`[不要]` に「終了」を割り当てる。次に貫く性質の検算を当てる——母集団を固定して結論を `[不要]`→`[適用]` と反転させると仕事量は当然変わるので、**非対称と判定される**。ここから出口が無い: (α)「不要」側にも同量の作業を課す＝「義務を足さず」に反する、(β) スロット 4 を空にする＝「6/6 が空欄」として本文が名指しで否定した状態へ戻る、(γ)「費用」を判定に至るまでの作業に限定して判定後の動作を除外する＝本文にその限定は無く、むしろ実例表が判定後の散文 3 項目を「課される義務」に数えているため取れない。「費用」がどこまでを含むかが未定義のまま、その語で書かれた検算が全スキルに適用される。結果、判定値のいずれかに修正・停止のような判定後作業を割り当てた検査は——本文が `/symmetric-check` の `[適用]` に対して名指しで要求している形がまさにこれである——スロット 4 を埋めた時点で必ず検算に落ちる。

3. 「構造物アンカーの 3 スキルは停止スロットが自動的に埋まっている」が本文自身の 2 か所と矛盾し、書き手はスロット 3 を空のまま出すことになる
   - 種別: 論理衝突
   - 根拠となる文言の引用:
     - 「**母集団を正しく定義すれば停止は無料でついてくる**——構造物アンカーの 3 スキルは、母集団が有界であるために停止スロットが自動的に埋まっている。」
     - 型表「**構造物アンカー** | `/dry-check`（関数の主要操作）・`/cache-check`（再利用述語の全項）・`/persistence-check`（対象 struct）」
     - （文脈・証拠）採点表 `/dry-check` の停止欄「無し ❌」／却下 2「薄いのは停止・接続スロットが空だからであって、母集団は健全（関数の主要操作＝構造物アンカー）」
   - 忠実に従うと何が起きるか: 構造物アンカーの検査を書く人は、この一文を根拠にスロット 3 の 3 項目（費用の書き下し・深さと幅の打ち切り・射程外の残余）を書かずに済ませる。ところが同じ文書が、構造物アンカーである `/dry-check` の停止を「無し ❌」と採点し、却下 2 で「停止・接続スロットが空」と明記している——**「自動的に埋まっている」は 3 例中 1 例で反証されている**。書き手は「有界だから書かなくてよい」と「3 項目を埋めよ」のどちらに従うかを決められず、決めずに前者を採ると `/dry-check` と同じ ❌ を新規スキルで再生産する。

4. 列挙アンカーには母集団の手順規定が無く、唯一の参照先「列挙が 3 職を兼ねる」が文書内に存在しない
   - 種別: 手順の穴（参照先については実行不能）
   - 根拠となる文言の引用:
     - 型表「**列挙アンカー** | `/state-check`（「最低限確認する既存状態」の列挙） | 列挙の外にあるものが構造的に不可視になる（下の「列挙が 3 職を兼ねる」）」
     - 項目 2「差分アンカーならリビジョンを明示する（`git diff main...HEAD`）、構造物アンカーなら起点の構造物を明示する」
   - 忠実に従うと何が起きるか: アンカー型は 3 つ提示されているのに、項目 2 の具体的な手順規定は 2 型ぶんしか無い。列挙アンカーの検査（`/state-check` の書き直しを含む）を書く人は、「決定的な手順」を何に対して書けばよいかの指定を持たない。唯一示された補足先「下の「列挙が 3 職を兼ねる」」は**この文書内に存在しない**（本文 165 行を通読し、加えて grep 実測——該当する見出しは無く、当該語の出現は型表のこの参照 1 件のみ。参照先が外部ファイルで読めなかったのではなく、内部参照が空である）。しかも型表はその型の危険（列挙の外が構造的に不可視）だけを告げるので、書き手は危険を知らされたまま対処法へ辿り着けない。

### (a)〜(d) への回答

- **(a) 衝突は解消している。** 全面禁止だった旧項目 4 が消え、「空そのものを咎める規則では捕まらない（それは候補 0 件という正しい結論まで禁じる）」と本文が明示的に候補 0 件を保護しているため、移行手順 (1)(2)(3) と現在の要石（決定的な母集団取得手順）は**両立する**。指摘 1 が突いているのは要石の*十分性*（背景表 2 行目を本当に閉じるか）であって、旧衝突の再発ではない。
- **(b) 新しい穴は開いていない。** 母集団 ∅ は判定値「該当なし」として、スロット 2「「ヒットあり」と「ヒットなし」の**両方に合法な形**を与える」とスロット 4「各判定値に対して次の動作」が受け止める設計になっており、書き手の手は止まらない。唯一残るのは「判定ではなく手順自体が失敗した」場合（基準 ref が無い・ブランチが main 由来でない等）だが、これは受容する残余であって詰まりではない——書き手はスキルを書き切れるし、実行者が従うのはこの文書ではなく個々のスキルである。
- **(c) 書き切れない。** 指摘 1 のとおり、リビジョンを明示した `git diff main...HEAD` は書けるが、そこから作った母集団は `/symmetric-check` が最重視すると自称するケース（廃止・移行漏れ）を構造的に含みえない。かつ必要な「基準リビジョンに固定した構造物アンカー」の枠が項目 2 に無く、差分アンカーに対する健全な実例（`/cache-check` は型表では構造物アンカー）も本文に無い。
- **(d) 序数参照の齟齬は無い。** 「4 スロット」は母集団／証拠／停止／接続の 4 つで整合、「2 が要石である」も「3 の良い前例である」（スロット 3 項目 3 ＝ 射程外の残余）も現存する項目を指し、スロット 1 の項目数に依存する記述は本文に残っていない（165 行を通読し、`項目\s*4` `4 個` `4 つの項目` `4 項目` の grep もすべて 0 件）。唯一の残り香は「却下の経緯は `docs/adr/0011-check-skill-skeleton.md` 却下 5」で、配置表が同 ADR の内容を「上の却下 1〜4」と書いているのと食い違うが、外部 ADR は本レビューの読取範囲外で実在を確認できず、かつ誰の手も止めないため番号付きの指摘にはしていない。
