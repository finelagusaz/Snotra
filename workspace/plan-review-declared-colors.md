# plan-review: #953（計画準拠レビュー・観点 = ∃ 述語の実効性 / 失われる命題）

## 要対処

- **∃ 述語は「クロス配線（値の取り違え）」を検出できない** — `plan.md:34-40` の設計は「宣言された色が
  それぞれ窓のどこかに下限占有率以上あるか」だけを見る、位置に紐付かない存在検査である。main が
  `background=X` / `input_bg=Y`（X≠Y）を宣言しているとき、もし実装が両者を取り違えて描く
  （背景領域に Y、入力欄領域に X が出る——例えば `background_color` と `input_background_color` を
  引数の順で渡し違える類のバグ）と、X は入力欄領域に約 43% 、Y は背景領域に約 33%（研究メモの実測値・
  `research.md:18-23`）現れ、**両方とも下限 5%（`plan.md:45`）を軽々超えるため `Ok=true` で緑になる**。
  これは `plan.md:29-30` が「実際に捕まえたい失敗（色が届かない）は…不在（0 px）として現れる」と書く
  前提が成り立たない具体例で、色は「不在」ではなく「別の場所に存在」する。
  `plan.md:95-100`「受容する残余」はこの経路に触れておらず、`plan.md:162-168` Phase 4 の唯一の
  故障注入（`view.rs` の `frame.set_clear_color` を落として**全消失**させる）もこの経路を通らない
  （全消失は不在型の失敗であり、クロス配線は不在型ではない）。**推奨**: 少なくとも
  「受容する残余」へこの限界を明記する（位置に紐付く判定へ拡張すると (b)「窓ごとの宣言色をデータに
  載せる」設計は保てても述語が「その領域で」という条件を持つことになり、射程を広げる判断が要る）。
  費用対効果で見送るとしても、書かれていない残余は「気づかれていない」と「気づいて許容した」を
  区別できない。

- **`$KeepShot` と `-Color '#FFF'` の不変条件が Phase 4 の検証コマンドに現れない** —
  `plan.md:90`「`-Color '#FFF'` の 3 桁 hex 受理を壊さない（#680 の 1 の回帰検査を兼ねている）」と
  `plan.md:93`「`$KeepShot` / スクリーンショット保存の挙動を変えない」はどちらも明記された不変条件
  だが、`plan.md:104-127`「テスト方針と検証コマンド」にも `plan.md:162-168` Phase 4 の作業項目にも
  `-Color '#FFF'` を渡す実行も `-KeepShot` を渡す実行も無い（並ぶのは既定色での
  `npm run check:colors` のみ）。加えて `:171-175`（現行 `Measure-WindowBackground` 内の
  `if (-not $ok -or $KeepShot) { ... Save ... }`）は判定 `$ok` を計算した直後にスクリーンショットを
  保存しているが、計画では判定（`$ok`）がヒストグラム構築から切り離されて新モジュールへ移る
  （`plan.md:60-61`, `72`）。この保存処理を**どちらの側（`.ps1` 呼び出し元 or 新モジュール）に置くか**
  が「変更ファイル一覧」（`plan.md:66-77`）の `:239-240` / `:255-256` 行に明記されておらず、
  `$Capture.Bitmap` を握るのはスクリプト側だけ（純関数はヒストグラム dict しか受け取らない設計・
  `plan.md:60-61`）なので機械的には呼び出し元に残すしかないが、それが作業項目として書かれていない。
  **推奨**: Phase 2 の作業項目に「スクリーンショット保存判定を呼び出し元へ移す」を明記し、Phase 4 に
  `-Color '#FFF'` と `-KeepShot` それぞれの実行を検証コマンドとして追加する。

- **背景色と入力欄色が同一値になる経路を計画が排除していない** — `plan.md:152`（Phase 2 作業項目）は
  「seed する `[visual]` へ `input_background_color` を非既定色で足す」とだけ書き、背景色（`-Color`
  由来、現行 `visual-check-colors.ps1:107` の `background_color = "$Color"`）と**異なる値**にする、
  とは書いていない。現行コードは `$additionalSections` に `background_color = "$Color"` を 1 行書く
  形（`:105-108`）なので、素朴な差分追加は同じ `$Color` 変数を使って
  `input_background_color = "$Color"` と書いてしまう誘惑が強い（コピペ距離が 1 行）。両者が同値だと、
  「入力欄が実は自分の色を持たず背景色をそのまま透過している」という誤配線（#953 の遠因と同型の
  取り違え）が構造的に見えなくなる——背景領域・入力欄領域のどちらも同じ宣言色を示すため、ヒストグラム
  上は「両方届いている」としか読めない。`plan.md:172-174`「未確定」は #949 カテゴリ D の実測
  （背景 `#101010` / 入力欄 `#7A1F1F`、**異なる値**）を引いているが、これは「入力欄色を seed する経路が
  実在する」ことの根拠として引用されているだけで、「2 色は相異なる値を使う」という要件として
  `plan.md` 本文（`受け入れ条件`・`不変条件`・`作業項目`のどこにも）に昇格していない。**推奨**:
  `不変条件と異常系`（`plan.md:86-93`）に「背景色と入力欄色は相異なる非既定リテラルを使う」を明記する。

## 軽微

- 現行 `:153-154` のコメント「**1 点ではなく最頻色で判定する。**…背景は窓で最も広い色なので、最頻色と
  占有率を観測する。」のうち、後半「背景は窓で最も広い色なので」は #953 が反証した前提そのもの
  （main では偽）であり、計画どおり `Measure-WindowBackground` がヒストグラム構築だけに縮む
  （`plan.md:72`, `150`）と、この行はもう成立しない処理の上に取り残される。前半（1 点サンプルでなく
  ヒストグラムで測る技法自体）は生き続けるべき知見だが、「変更ファイル一覧」（`plan.md:66-77`）の
  `:145-185` 行は「ヒストグラム作成までに縮め、判定は新モジュールへ委ねる」としか書いておらず、
  このコメントの書き換え（後半の削除・前半の移設）を明示していない。実装時にコメントが放置されると
  「もう計算していない `mode` の話」が残る。
- 現行の戻り値 `Actual`（実測モード色、`:169`, `:181`）は「窓全体で最も多く見えた色」という診断情報
  だが、∃ 判定へ移ると「モード色」は判定に使わない値になる。それでも人間向けの診断（「何が一番広く
  出ているか」）としては有用な可能性があるが、計画は出力を「色ごとの実測占有率を常に出す」
  （`plan.md:75`）としか書いておらず、モード色の情報を残すか捨てるかを明示的に決めていない。
  実装判断に委ねてよい程度の粒度だが、書いておくと Phase 2 の手戻りが減る。

## 未検証

- Phase 2 の実装（`scripts/lib/SnotraWindowColors.psm1` と `visual-check-colors.ps1` の実差分）は
  まだ存在しないため、「背景色と入力欄色に実際に異なるリテラルが使われるか」（要対処 3 件目）は
  コードで確認できていない。plan.md の記述だけを根拠にした指摘であり、実装が先回りして正しく
  書かれる可能性はある。
- クロス配線（要対処 1 件目）が現行 `src-tauri` / `snotra-egui-runtime` の描画コードで実際に起こり
  得る具体的なバグ経路（`background_color` と `input_background_color` を渡す call site の実装）は
  この計画レビューの範囲外として監査していない。ここで指摘したのは「この検査の設計がその種の
  バグを検出できない」という述語の限界であり、「そのバグが今存在する」という主張ではない。
