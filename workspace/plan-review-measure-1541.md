# 計画レビュー: issue #1541（trace 1 行が約 8〜10 ms かかる回の機序を測る）

対象: `workspace/plan.md`。観点は (1) 測定の妥当性 (2) 文書の整合。裁定（この issue では直さず、測定・記録・読み方まで）は争点にしない。コード・文書は変更していない（読み取りと grep のみ）。

## 要対処

1. **M3 の「書かない処理」が、H2（起床・省電力）を試せない形である。**
   - 計画は M3 を「`Instant::now()` 2 回の差」とする（plan.md 12 行目）。連続する 2 回の `Instant::now()` は数十 ns で、8〜10 ms の待ちに当たる窓がほぼ無い。常に小さく出て、「同じスレッドの他の処理が同じ待ちを受けるか」（issue「確かめていないこと」）に答えが出ない。
   - スレッドの起床の遅れは、コールバックが走り始める前に起きる。計装の区間（`trace` の入口から出口）の外である。区間の内側で 8〜10 ms を食うのは、ロックか I/O の待ちか、区間の途中での descheduling に限られる。
   - 対処案: 書かない処理を、システムコールを伴うものにする（例: 起動時に開いた別の NUL ハンドルへ 1 バイトの `WriteFile`、`GetFileType` など）。これを stderr の `write_all` の直前に同じ点で置く。「別ハンドルの `WriteFile` は速く、stderr だけ遅い」なら、装置とファイルシステムの側に絞れる。「両方遅い」なら、スレッドの側に絞れる。
   - 起床の遅れそのものを知りたいなら、`WM_HOTKEY` の受信時刻（platform の `GetMessageW` 復帰直後）と listener の入口の差を別に取る。
2. **複製の単位が足りない。** 峰は巡（プロセスの起動）ごとに状態が変わっているように見える。
   - 根拠: `PERFORMANCE.md` 「採用: trace 1 行を 1 回の書き込みにする（#1539）」の表で、`hotkey:listener_enter` の後の p50 が 445 / 8,321 µs と、巡ごとに分かれた。同じ操作・同じ 570 ms の空白である。1 回の起動ごとに状態が持ち越される（スレッドの置き先・EcoQoS・ハンドルの状態など）なら、独立な標本は 25 回ではなく起動の数である。
   - 計画は「各測定は 2 巡以上、交互」（plan.md 36 行目）。M1 の 4 条件が各 2 起動では、条件の差と起動間の差を分けられない。
   - 対処案: 起動を複製単位として、各条件で 4 起動以上（交互）にする。結果表は起動ごとの率（4 ms 超の件数 / 標本数）を並べる。p50 だけで条件を比べない。
3. **基準条件の再現を停止条件にしていない。** 計装版を (a)（#1539 と同じ受け方）で回して、峰が再現しなければ、M1 の (b)〜(d) の比較は何も言えない。観察者効果は、計装・env・`Wait-SnotraTraceCondition` を使わない操作で変わりうる。
   - 対処案: 「(a) の峰の率が #1539 と同程度（`listener_enter` で 25 回中 3 件以上、`push_key` の down で約 3〜4 割）に出ない場合は、そこで止めて報告し、条件を探す」を計画へ書く。再現しなかった場合の記録の形も書く。
4. **終了時の書き出しの設計に穴がある。**
   - 「スレッド局所の変数」は、他のスレッドから読めない。プロセス終了時に走るスレッドが、platform スレッドと egui スレッドの局所の値を読めない。さらに、終了時に他のスレッドの thread-local の Drop は走らない。global のレジストリ（スレッドごとの `Arc<Mutex<Vec>>` を登録する形など）が要る。計画は「メモリに貯めて終了時に書く」としか書いていない（plan.md 31 行目）。
   - 退避策の「一定件数ごとに書き出す形」は、M1 を壊す。測定対象の装置（C: の NVMe）へ周期的な書き込みを足すと、H1 の「空白の後の装置の復帰」を試せなくなる。(c) の NUL の条件も、ファイル I/O が混じる。
   - 対処案: 退避策を、ファイル I/O を使わない出口にする。例: 名前付きの共有メモリ（ページファイル裏付けの `CreateFileMapping`）へ書いておき、計測スクリプトが測定の後に読む。または、測定の最後に 1 回だけ（操作がすべて終わってから）書き出す。どちらを採るかを新設の時点で決める。
   - 計時値を次の行へ載せる設計（plan.md 30 行目）は、メモリの記録があれば不要になる。行へ載せると行の長さが変わる。記録の 1 件に (tid, QPC の開始, 組み立て, ロック, WriteFile, サイクル) を持たせるほうが、帰属が自明である。
5. **M4 の「egui_frame を同じだけ空けた直後」を作る手段が書かれていない。** 非表示の間は egui のフレームが出ない。
   - 可視のアイドルの egui は約 2 fps（キャレット点滅）で `egui_frame` を書く（`PERFORMANCE.md` 「計測と受け入れ基準」の可視アイドルの基準値）。この 500 ms おきの行が、入力を伴わない別スレッドの「空白の後の最初の 1 行」になる。入力なしの可視アイドルを 10〜20 秒置く条件にすれば、手段になる。計画へ明記する。
   - 空白の振り幅は、`powercfg` の閾値をまたぐように決める。現在値は Primary NVMe idle 200 ms・Secondary 2000 ms・許容遷移遅延 15 ms（adversarial-1541.txt の B4 付近）。例: 50 / 150 / 300 / 570 / 1,500 / 2,500 / 5,000 ms。計画は「振る」としか書いていない（M4）。
6. **文書の整合: 名指しが漏れている。**
   - `PERFORMANCE.md` 4007 行目: 「…`hotkey:registered` の trace を書く間に費やされていた（その書き込みのどこで待つかは測っていない）」。18 ms 規模の trace の書き込みの待ちで、同じ機序の可能性がある。計画の「変更するファイル」に無い。結論が出たら、この行から新しい節を指すか、別事象と書く。
   - `PERFORMANCE.md` 3784 行目（「計測と受け入れ基準」の trace の所要の項）: 「cmd の `2>file` のほうが約 10 倍速かった（本体では測っていない。…）」。M1 の (a)/(b) は本体の測定そのものなので、この括弧は偽になる。計画は同項の 3785 行目の「（機序は未確認）」だけを名指ししている。
   - `PERFORMANCE.md` 829〜832 行目（#1543 の節）: 「release 本体（windows サブシステム）を子にしたときの mode は観測していない」。M1 で本体の stderr の `FileModeInformation` を 1 回読む（起動時 1 回、計装版のみ）と、(a) が write-through であることを前提から外せる。コストはほぼ 0 である。計画へ足し、結論で直す。
   - `PERFORMANCE.md` 890 行目: 「打鍵の間の待ち（30〜80 ms）」。adversarial-1541.txt の [3] は、リポジトリの既定（`Send-KeyTap` の HoldMs 50 ms ほか）に一致する値が無く、呼び出しスクリプトも残っていないと指摘している。新しい節がこの値を使うなら、同じ変更で直す（`governance-docs.md`「触った節の近くにある主張が、今も正しいか確かめる」）。
7. **計画の grep が、名指した記述の 1 件を拾わない。** 計画 24 行目は `git grep -n "機序は未確認\|機序は確かめていない\|測っていない" PERFORMANCE.md` で「漏れを数え直す」とする。
   - 実測: このパターンは 37 件に当たるが、ほとんど無関係（索引・メモリ・NAS の話）である。選択的でない。
   - 一方、`PERFORMANCE.md` 768 行目（#1526 の「回ごとに揺れる原因…は確かめていない」）は、このパターンに 0 件である（`sed -n 768p | grep -c` で確認）。名指しはしてあるが、検査としては機能しない。
   - 対処案: 母集団は、峰を指す語（`listener_enter`・`8〜10 ms`・`約 10 ms`・`二峰`・`峰`）で数える。計画には、数え直すコマンドと、各ヒットの処置（直す / 歴史として残す）を表にして置く。
8. **「計測と受け入れ基準」への書き足しが、数の写しを増やす恐れがある。** 受け入れ条件 4 は「どの行が、どの条件で、どの規模の所要を負うか」を書くとする。
   - 3784〜3785 行目と 3817 行目は、すでに p50 0.11 ms・p90 0.27 ms・8〜10 ms を写している。`governance-docs.md` の書く約束 (1) は、同じ主張を正本の 1 か所に寄せ、他からは参照する。
   - 対処案: 読み方の項には「どの行が負うか」と「差分で読む」までを書き、額は新しい節（と #1542 の節）を指す。既存の写しは、新しい節への参照へ置き換える（増やさず、むしろ減らす）。

## 軽微

1. **M1 の (b)(c) が `cmd /c` で起動するなら、本体の PID と終了の経路がずれる。** `Start-SnotraProcess` が追う PID は cmd のものになる。GUI サブシステムの本体は cmd を待たせない。ウィンドウの特定・終了要求・`Stop-Process` の対象が替わる。条件ごとの起動の形（誰が親か・ハンドルの継承）を計画へ書く。(a) と (b) の差は「write-through の有無」と「起動の経路」の 2 つ。#1543 の probe と同じ交絡である。
2. **M2 の `Stderr` のロックと `write_all` の分割は、実現できる。** `io::stderr().lock()` が `StderrLock` を返し、`write_all` は `Stderr` 経由でも内部で同じロックを取る（`src-tauri/src/trace.rs` の `write_line` は `&mut Stderr` に `write_all`）。ただし計装版は、出口を `lock()` + `write_all` へ替える。別の形の呼び出しになるので、「製品と同じ経路」の主張は「同じロックと同じ `WriteFile`」までにする。ロックが再入可能（`ReentrantLock`）で、無競合のときは数十 ns であることも、結果の読み方に書く。
3. **H3（ロック）の観測は、計装した行しか見えない。** `trace()` と `trace_line!` の外から stderr へ書く経路（`eprintln!` は `src-tauri/src`・`snotra-egui-runtime/src` に 11 件ある。panic・依存 crate・同じハンドルを継承した子プロセス）は、「スレッドを問わない直前の行との間隔」に出ない。stderr を継承する子（`src-tauri/src/commands/launch.rs:272` は `Stdio::null()`）以外の起動経路を、1 回確かめる。
4. **`QueryThreadCycleTime` の陽性対照が無い。** 既知の CPU ループと既知の `Sleep` の区間で、サイクルの増え方が期待どおりかを最初に 1 回見る。ブロック中は進まないこと、カーネル時間が入ることを確かめてから使う。サイクルが小さく壁時計が長いという所見は、H1・H2・H5 のどれにも共通する。M2 だけでは分けられず、M1（置き先・NUL）で分ける、と結論の書き方に入れる。
5. **「新しい節」の見出しの語が決まっていない。** `PERFORMANCE.md` の節の見出しは `### 採用: …` / `### 不採用: …` で書かれ、「採用せず記録」は既存の語彙に無い（`grep -n "採用せず" PERFORMANCE.md` は 0 件）。「不採用」か、記録だけなら語を決める。これは文体の問題で、governance:check は通る。
6. **`main.rs` のコメント（566〜568 行）は、結論で書き直す候補が他にもある。** 計画 25 行目は「結論で額や理由の書き方が変わるときだけ直す」とある。「1 回の書き込みにしても数 ms かかる回が残る」は、機序が分かった後は「何で数 ms かかるか」の記述に替えるのが自然である。`trace.rs` の `//!`（`PERFORMANCE.md` を指す）と `stderr_line.rs` の `//!` には、峰への言及は無かった（`git grep -n "8〜10 ms\|数 ms かかる\|listener_enter"` の `PERFORMANCE.md` 以外は `main.rs` の 2 箇所だけ）。
7. **足場の撤去: 設計はあるが、撤去条件が散文の「撤去する」だけである。** `docs/development-principles.md`「観測するとき」は、新設時に撤去条件と撤去対象を成果物の doc に書き、条件を「issue が閉じたら」ではなく事象で書くとする。計画の撤去対象（一時の worktree・`CARGO_TARGET_DIR`・scratchpad の計測スクリプト・プローブ）と、撤去より前に起きる事象（例: 新しい節が `PERFORMANCE.md` に着地した）を、足場の先頭のコメントへ書く。測定値は撤去の前に `PERFORMANCE.md` へ着地させる（同「撤去時」）。生の stderr（利用者の実パスを含みうる）はリポジトリの外に置く。計画はこれを含んでいるが、ファイルの置き場を「scratchpad と別の worktree」としか書いていない。
8. **測定条件の記録に足りない項目。** 電源プランは測定日の値を記録する（`powercfg` は現在値で、過去の測定には効かない）。さらに、Windows の電力スロットリング（EcoQoS）の状態・AC/DC・USB の SSD の省電力設定（D: の条件で効く）・ウイルス対策の除外の有無。H5 のミニフィルタを疑うなら、`fltmc filters` の一覧も 1 回取る。

## 未検証

1. **peak が write-through を外すと消えるかは、測るまで分からない。** #1543 の probe は 20 ms おきの書き込みで、峰が出ていない（p90 ≤ 0.5 ms）。空白が違う別条件であり、peak を再現する条件では未観測である。
2. **`listener_enter` と `push_key` down の峰が同じ機序かは不明。** 空白は 570 ms と数十 ms で、NVMe の idle 200 ms と整合するのは前者だけ（adversarial-1541.txt の [4]）。M1〜M4 の結果を 1 つの結論へまとめる前に、2 つの峰を別々に結論してよい形にしておく（受け入れ条件 2 は「1 つの結論」と書く）。
3. **tauri の `emit_filter` の `try_lock` 失敗で別スレッドへ回る回は、実際には起きないかもしれない。** 計画は ID で見分けて数える（不変条件の節）。起きなければ 0 件と書く。
4. **`QueryThreadCycleTime` の分解能と、他スレッドの CPU サイクルの帰属。** 現在のスレッドに対しては期待できるが、本機での挙動は未実測。
5. **NUL への書き込みの経路。** Windows の std は、ハンドルが null / invalid のときだけ書き込みを無視する。`cmd` の `2>NUL` は有効なハンドルを渡すので、`WriteFile` は実際に呼ばれるとみているが、本機では未確認。(c) の計装で `WriteFile` の呼び出し回数と戻りを確かめる。
6. **Wait/待ち方の差。** 計測スクリプトがウィンドウの可視でタイミングを取る間に、スクリプトのポーリングが stderr のハンドルへ触れないこと（`Wait-SnotraTraceCondition` を使わないこと）は計画に書いてある。実行して、操作中に stderr のファイルが開かれていないことを（Process Monitor 等で）確かめるまでは、観察者効果の排除は未検証である。
