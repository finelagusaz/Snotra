## 要対処

### A1. Phase 1 のフォールトインジェクションが「新ヘルパの分岐検査」であって「効いていることの実測」になっていない

`plan.md:69` の検証は「`WaitForExit` が false を返す状況を Mock で作り、警告が出て throw しないことを検査する」。これが測るのは**新ヘルパの期限切れ分岐の挙動**であり、`safety-nets.md`「効いていることは、フォールトインジェクションで一度は実測する」が要求する「そのセーフティネットが**本当に効いているか**」ではない。守りたい対象は「単一インスタンス衝突（実測 3/30）が起きなくなること」であって、警告の文言ではない。

なお `safety-nets.md`「稼働中のガードを弱めない——複製に変異を当てる」は Phase 1 / Phase 2 とも**満たしている**——Pester の `Mock` は `It` のスコープに閉じ、稼働中の `Resolve-SnotraExistingProcess -Policy Reject` を無害化する形は計画のどこにも無い（`plan.md:62` が明示的に禁じてもいる）。

**足すべきもの**: 変異は**複製側の待ちを外す**方向へ当てる。`Stop-SnotraProcessAndWait` の `WaitForExit` を no-op にした複製で `実機配管` の 2 つの `It` を連続実行し、`Tests.ps1:441` の `Reject` が throw する（＝直した機序を意図的に再現できる）ことを 1 度示す。これができないなら「衝突は待たないことが原因だった」は依然として仮説のままである（`research.md:35-45` の推論は構造からの導出であって、注入による確認ではない）。

### A2. Phase 2 のフォールトインジェクションに、読み手側の変更を一度も行使しない経路がある

`plan.md:121` の (a)(b)(c) 両方向は**形として正しい**——`safety-nets.md`「これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する」の測り方に適っている。ただし穴が 1 つある: **両側を同じ PR で直すため、修正後は空文字がそもそも生まれない**。(b)「2 反復目の `caret.err` に `SNOTRA_EGUI_INPUT` 行が無い」は、PowerShell 側の修正（`Remove-Item`）だけで通ってしまい、Rust 側の `env_flag` は一度も行使されない。`safety-nets.md`「**故障注入は回復機構ごと巻き戻して行う**」がまさにこの形を名指ししている。

**足すべきもの**: 空文字を**直接注入する**第 3 の条件。`$env:SNOTRA_EGUI_INPUT_TRACE = ''` を立てた状態で本体を起動し、`caret.err` に `SNOTRA_EGUI_INPUT` 行が現れないことを測る。空文字が Process スコープに残り子プロセスへ継承されることは本レビューで独立に実測済み（PowerShell 7.6.4: `SetEnvironmentVariable(name, $null, 'Process')` → `Test-Path Env:` が真・値は空文字・子 pwsh も真）。

### A3. 空文字 env の「到達する全経路」の母集団が `scripts/` に限られており、対象ゼロで自明に green になる

`plan.md:128` の作業項目は「**`scripts/` 内で**上記 6 種の env を設定している箇所を grep し、挙動が変わらないことを 1 件ずつ確認する」。実測すると、5 つの trace env のうち `scripts/` に設定箇所があるのは `SNOTRA_EGUI_INPUT_TRACE` だけである（`scripts/repro-pester-flake.ps1:129` のみ）。残る 4 つ（`PAINT` / `WAKE` / `REPAINT` / `IME`）の設定箇所は `scripts/` に 1 件も無く、実在するのは:

- `PERFORMANCE.md:251-253`（3 つの計器の使い方を正本として記述）
- `docs/superpowers/plans/2026-07-24-su6.5-flip-hardening.md:919`（`$env:SNOTRA_EGUI_PAINT_TRACE=1`）
- 人手（診断時に手で立てる。計器の性質上これが主要な設定経路である）

`AGENTS.md`「検証の作法」の「**検証コマンドは『観測形が対象を含むか』まで測る**……対象ゼロのまま自明に green を返す」に正面から当たる。

**足すべきもの**: 母集団を**設定側のディレクトリ**ではなく**読み手側の env 名 5 つ**から取り、`scripts/` / `docs/` / `*.md` / `.github/workflows/` / `.rs` を横断して 1 件ずつ当てる。加えて `PERFORMANCE.md` の 3 行は受理値が変わる旨を書き換える対象として計画へ入れる（`AGENTS.md`「文書に事実の写しを増やす変更」ではなく、既存の写しが陳腐化する方の問題）。

### A4. `plan.md:114` の「変わるのは空文字・`0`・`false` を渡していた経路だけである」は成り立たない

`src-tauri/src/trace.rs:20-28` の `env_flag` は `trim` + 小文字化した上で `1｜true｜yes｜on` の**許可リスト**である。ゆえに移行後は**許可リスト外のあらゆる値**が計器を消す——`2`・`verbose`・`y`・`enabled` などがすべて含まれる。「空文字・`0`・`false` だけ」は許可リストではなく拒否リストを想定した書き方であり、実装より弱い主張になっている（`AGENTS.md`「全称表現は前提条件とセットで書く」）。

`safety-nets.md`「**分類を 1 つ足したときは、隣接分類への到達経路も再列挙する**——逃げ道は塞いだ扉の隣に現れる」がこの箇所に当たる。

**足すべきもの**: 次のどちらか。
- (a) 主張を実装へ合わせる（「許可リスト外のすべての値が OFF になる」と書き、A3 の母集団でその値を渡している箇所が無いことを確かめる）
- (b) **より狭い既存の手本へ寄せる**。`snotra-core/src/config.rs:697` の `config_dir_from` は `var_os` + `!is_empty()` で「空文字は未設定」だけを足しており、その理由（`PathBuf::from("")` が CWD 相対になる）を rustdoc に持つ。今回の実バグは空文字ちょうどなので、これなら**新しい分類を 1 つも作らずに**塞げる。
どちらも設計として妥当だが、**(a) の実装をしながら (b) の射程を主張する**現状は不可。

### A5. `Tests.ps1:502` 側の `Write-Warning` は、下流に検出器を持たない新しい沈黙経路である

`plan.md:57` は throw しない理由をこう置く: 「次の It の `Resolve-SnotraExistingProcess -Policy Reject` が、生き残りを大きな音で落とす役を引き続き担う」。**この根拠は 2 つの呼び出し点のうち片方にしか当てはまらない。**

- `Tests.ps1:381`（seed の It）→ 次の It が `Tests.ps1:441` で `Reject` を呼ぶ。**根拠は成立する**
- `Tests.ps1:502`（キャレットの It）→ **計画自身が `plan.md:46` で「この It の後に本体を起動する経路は無い」と書いている**。本レビューでも裏取り済み（`scripts/lib/SnotraTraceInvariants.Tests.ps1` の `Start-Process` / `Start-SnotraProcess` は 0 件）。ゆえに期限切れは**Pester 実行全体から生きた `snotra.exe` を漏らしたまま、誰にも見られない**

`Write-Warning` は CI の log には出る（`research.md:102-105` が実際に grep で拾っている）。ただし:
- `scripts/run-pester.ps1:52` は `FailedCount` / `FailedContainersCount` だけを見るので **exit code には一切影響しない**（`.github/workflows/ci.yml:141` はその exit code だけを読む）。GitHub Actions の annotation にもならない（`::warning::` ではないため）
- そして `research.md:100-110` が実測で示すとおり、**この警告ストリームは既に読めない**——`SnotraSmoke.psm1:574` と同一文言の警告が `Tests.ps1:186` の単体検査から毎回 1 件出るため、本物と区別が付かない

ルート `CLAUDE.md`「フック」の「**検出は exit code、出力は証拠**」「沈黙しうる経路はすべて塞いである」に照らすと、これは「出力はあるが検出が無い」形＝規律の反対側である。**「見えない」ではなく「log には出るが読めない」**が正確な記述であり、悪さは同じである。

**足すべきもの**: `Describe '実機配管'` に `AfterAll` を置き、`Get-Process snotra` が空であることを assert する。`AfterAll` からの throw は `It` の例外を覆い隠さないので、**`finally` からの throw を避けたいという計画の理由をそのまま満たしたまま**、検出を exit code の層へ移せる（`docs/development-principles.md`「構造的設計原則と強制の階梯」の一段上げ）。

### A6. 待ちが隠す退行（本体の終了遅延）の読み手が決まっていない

`safety-nets.md`「回復機構（fail-safe・自己修復・リトライ）を足したら、**その機構が隠す退行を誰が見るかを同時に決める**」に該当する。終了待ちが隠すのは **本体のシャットダウン所要の退行**である。

- 現在: 終了が遅い ⇒ 次の It が single-instance 衝突で落ちる（実測 3/30・**うるさいが信号ではある**）
- 修正後: 最大 5,000ms までは吸収され、**検査は緑のまま通る**

これは #755/#801 と同型である——`safety-nets.md:41` が「回復機構が 1 フレームで補正するため、外から窓を測る検査は緑のまま通る」と記した構図そのもの。加えて、**衝突率そのものが #872 の判断材料である**（`research.md:22-33` の 3/30）。読み手を置かずに消すと、runner 上で終了が遅くなっていること自体を示す唯一の信号が消える。

**足すべきもの**: `Stop-SnotraProcessAndWait` が実際に待った時間（ms）を記録し、`SNOTRA_PESTER_TRACE_DIR` が立っている実行では反復ディレクトリへ残す。Phase 2 が既に `summary.md` へ「計器つきの反復: N / M（証拠）」を出す配管を作るので、**同じ配管に載せられる**（新設ではない）。閾値超過を ⚠️ として並べれば読み手が決まる。

### A7. 遅着警告のノイズ分離を範囲外にしたまま、同じストリームへ新しい警告を足している

`plan.md:156` は遅着警告のノイズ埋没を「第 5 の候補の前提条件だから同じ枝で直す」として範囲外へ送る。**一般の分離作業を先送りすることは妥当**である。しかし Phase 1 は、**読めないと実測で確定しているストリーム（A5）へ新しい警告を 1 本足す**。これは範囲外の判断ではなく、範囲内の変更が既知の欠陥を悪化させる形であり、`safety-nets.md`「回復機構を足したら読み手を同時に決める」に反する。

**足すべきもの**（どちらか一方で足りる。どちらも 1 行相当なので、費用を理由にした先送りは成立しない）:

### A8. `plan.md:14` の「この検査だけが起動直後の打鍵喪失を捕まえていた」は、前提条件なしでは成り立たない

この全称は候補 (c)（ゲートから外す）と (d)（再試行でくるむ）を**両方とも否定する根拠**として使われている。ところが #938 のコミット本文（`8a03252`）自身がこう書いている:

> 検出器: **単体テスト**（両方の並びを 1 フレームずつ走らせ、後ろに置くと落ちることまで固定）と実機の `egui_input:focus_state`

`src-tauri/src/egui_shell/view.rs` は同コミットで +114 行変更されており、順序を固定する単体検査が**現在は存在する**。ゆえに「だけ」が真なのは **#938 以前**に限られる。今日の判断の根拠として使うなら、「#938 以前は」という前提条件を付けた上で、**単体検査が入った今も同じ理由が成り立つか**を書き直す必要がある（`AGENTS.md`「全称表現は前提条件とセットで書く——**書けないなら書かない**」）。

判定を覆せとは言わない——Pester 検査は「実プロセス起動後の最初のフレーム」という単体検査が届かない層を見ており、ゲートに残す結論自体は支持できる。**理由の書き方だけが実装より強い。**

### A9. `research.md:43` の「同じ確率で起こる」は、同じ調査の発見 3 と矛盾する

`research.md:43`:

> **この経路は反復再現ハーネスに固有の要素を 1 つも含まない**……すなわち **`rust-check` の 1 回きりの実行でも同じ確率で起こる**。

### C1. `research.md:118` の「同一 runner」は artifact から確定できないのではないか

「両 run が同条件（同日・同 runner・同じく計器つき）だからである」——GitHub hosted runner は run ごとに新しい VM が割り当てられる（共有されるのは runner **イメージ**であって物理マシンではない）。「同日・同イメージ」までは言えても「同一 runner」は artifact から establish できないと考えるが、self-hosted runner を使っている可能性を確かめていない（`ci.yml:64` は `windows-latest` なので hosted のはずだが、`pester-flake-repro.yml` の `runs-on` は未確認）。**これが効くのは #938 の主張（25/30 → 8/30）の土台がこの一文だからである。**

### C2. `Stop-Process -Id` の PID 再利用

`Stop-SnotraProcessAndWait` は「`HasExited` なら何もせず返す」→ そうでなければ `Stop-Process -Id $Process.Id`。この 2 つの間にプロセスが自然終了し、Windows が PID を再利用していると、**無関係なプロセスを kill する**。理論上の窓であり、CI の実際の頻度は測っていない。`Stop-Process -InputObject $Process` にすればハンドル経由になり窓が閉じるはずだが、`Resolve-SnotraExistingProcess` 側の既存 Mock（`-ParameterFilter { $Id -eq 123 }`・`Tests.ps1:248`）との整合を要するので、費用対効果の判断は実装者に委ねる。

### C3. `src-tauri/src/icon.rs:423` の `SNOTRA_ICON_DIAG_PATHS` の空文字扱い

`std::env::var("SNOTRA_ICON_DIAG_PATHS")` で読んでおり、空文字が渡ったときに何が起きるかを確認していない（split の結果が空要素 1 個になるなら無害の可能性が高い）。今回の変更対象外だが、B1 の「意味論が複数ある」の母集団に入るべきかを判断できていない。

### C4. `Write-Warning` が Pester 6 の `-Output Detailed` でどのストリームに現れるか

`research.md` の grep 結果から「log に出る」ことは確定しているが、それは反復再現ハーネスが `*>&1 | Tee-Object` で全ストリームを畳んだ形での観測である。CI の `rust-check`（`npm run test:powershell` → `pwsh -NoProfile -File scripts/run-pester.ps1`）で `finally` 内の `Write-Warning` が同じように log へ出るかは、**実際に走らせて確かめていない**。出ない場合、A5 はさらに悪い（log にすら残らない）。**PR の CI で 1 度確かめる価値がある**——`safety-nets.md:40` に従い、これは計画の作業項目ではなく PR 本文のチェックリストへ。

### C5. Pester のテストファイル実行順序に対する `plan.md:46` の依存

「この It の後に本体を起動する経路は無い」は、`SnotraSmoke.Tests.ps1` → `SnotraTraceInvariants.Tests.ps1` の順で走ることに依存する。今日の実測（後者の `Start-Process` 0 件）で結論は変わらないが、**新しい `*.Tests.ps1` が追加された日に黙って破れる**種類の前提である。A5 の `AfterAll` を置けばこの前提自体が不要になるので、そちらで一緒に解消するのが筋だと考える。
