## 要対処

- **不変条件 7 の `poll_async` に対する注記「folder drain」が誤り。** `poll_async`（`launcher_controller.rs:903-938`）内の folder drain ループ（`:914-937`）は `self.folder_cache`/`self.folder_error`（controller 側フィールド）と `run_search()` しか触らず、`SearchState.folder`/`tool`/`view_kind()` は一切変えない（`accept_folder_result` も `&self`）。`poll_async` が実際に `view_kind()`/`folder`/`tool` を変えうる唯一の経路は、同メソッド冒頭の `self.drain_launch(ctx)`（`:905`）→ `finish_launch`（`:297-334`）→ `LaunchTag::Tool` かつ `LaunchStatus::Ok` のときだけ呼ばれる `self.state.reset()`（`:309`）である（tool を起動して成功した瞬間、`folder`/`tool` を丸ごとクリアする）。現在の記載は「folder drain」という無関係な理由を挙げており、`poll_async` を含める本当の理由（Tool 起動成功時の暗黙 reset）を書いていない。この記述のまま実装コメントへ落とすと、「folder drain に関係ない変更なら `poll_async` の呼び出し順序をいじってよい」という誤った検算に導きかねない——ラウンド 2 が「3 本→4 本」を訂正した目的（正しい検算手続きの担保）を、別の誤った根拠で再び損なう形になっている。修正は `poll_async（316 行・drain_launch → finish_launch の Tool 起動成功時 state.reset()）` のように実際の経路を書くこと。
- **フェーズ 1 で `strings.rs` の `//!` へ足す「この表は描画面が 2 系統に分かれる（placeholder 系 / status 行系）」という一文が、コードベース自身の分類と矛盾する。** `SPEC.md:184-185` は「status 行と toast 行は独立に積む（同時成立時にどちらも隠さない）」と明記し、`notify.rs:1-5` の module doc も「一時レーン（検索バー overlay）」と「updater 持続レーン（toast 行の状態機械）」を別レーンとして扱う。`view.rs` の実装も、status 行（`:440-480`、`indexing_hint`/`launching`/`notice_message` が描く）と toast 行（`:482-563`、`update_available`/`update_installing`/`update_failed`/`update_install_now`/`update_dismiss` が描く）を別ブロックとして持ち、`has_status`/`has_toast` は独立な bool で両方同時に真になりうる（`main_window_height` へそれぞれ別に加算）。つまり `strings.rs` の関数は実際には placeholder / status 行 / toast 行の**3 系統**に分かれており、`update_*` 系を「status 行系」と一括りにする、または 2 系統としか書かない一文は `AGENTS.md`「全称表現は前提条件とセットで書く」に反する過大な断定になる。このまま書くと、将来 `update_*` を `overlay_kind` の排他ラダーへ配線しようとする誤読（toast は本来 `overlay_kind` と独立に共存できる）を新たに誘発しかねない——ちょうど本タスクが警戒している「grep から生じる誤配線」と同型の罠を、別の場所に作ってしまう。追記文は 3 系統（placeholder / status 行 / toast 行）として書くか、少なくとも `update_*` の扱いを明示的にスコープアウトする一文を添えること。
