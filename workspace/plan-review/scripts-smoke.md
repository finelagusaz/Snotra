## 問題なし

- **seed の 3 必須セクションは `Config` 構造体と一致する**（`snotra-core/src/config.rs:92-104` 実読）: トップレベルで `#[serde(default)]` を持たないのは `hotkey` / `appearance` / `paths` の 3 フィールドのみで、`general` / `visual` は `#[serde(default)]` を持つ。`HotkeyConfig`（`:108-112`）の `modifier`/`key`、`AppearanceConfig`（`:328-330` 相当・`window_width: u32`）も同様に必須。plan が指す縮小 seed（`[hotkey]`/`[appearance]`/空の`[paths]`のみで `[general]`/`[visual]`/`[[paths.scan]]` を含まない）はこの必須集合とちょうど一致し、parse は成立する。
- **`[general]` を省略しても smoke-startup の挙動は変わらない**: `default_show_on_startup()`（`config.rs:130-132`）= `false`（hidden 起動）・`default_auto_hide_on_focus_lost()`（`:134-136`）= `true`。smoke-startup.ps1 はウィンドウの show/hide を注入・検査しない（trace の `*:error` 不在と件数だけを見る）ため、どちらの既定値も観測対象に影響しない。round 2 の懸念（「`show_on_startup`/`auto_hide_on_focus_lost` が挙動に影響しないか」）は解消していると判断できる。
- **縮小 seed は再保存を誘発しない**: `Config::load_from_dir_reporting`（`config.rs:927-931`）は `apply_migrations()` が `true`（何か移行が起きた）を返したときだけ `save_to_dir` する。縮小 seed はレガシーキーを一切含まないため `apply_migrations()` は何もせず `false` を返し、5 起動共有プロファイルへの書き戻しは発生しない——1.8 秒 kill を 5 回繰り返しても書き戻し途中の破損リスクは無い。
- **PowerShell の `exit` は `try` 内にあれば `finally` を必ず通る**（実測）: `try { exit 1 } finally { ... }` で finally が実行され、exit code は 1 のまま保たれることを確認した。ネストしたケース（内側 `try/catch` が `throw` を再送出し、外側は `finally` のみで `catch` を持たない）でも外側 `finally` が実行され、最終 exit code は非 0 のまま保たれることも確認した（下記コマンド参照）。plan が要求する「新設 `try` の `finally` で env を戻す」設計は PowerShell の意味論上成立する。
- **`-ResultsQuery ''` は StrictMode 下でも意図どおり空文字として束縛される**（実測）: `[string]$ResultsQuery = "z"` の param に `-ResultsQuery ''` を渡すと `IsNullOrEmpty($ResultsQuery)` は `True` になる（`Set-StrictMode -Version Latest` は明示的な param には影響しない）。フォールトインジェクション点として技術的に機能する。
- **`cmd:launch_settings_process:` の 4 派生イベントはすべて `:error` サフィックスを持たない**（`src-tauri/src/commands/window.rs:53,74,87,123` 実読・grep で当該文字列の全出現を確認）: `:already_running` / `:not_found` / `:spawned` / `:exited` の 4 種のみで、smoke-startup の `-like "*:error"` フィルタから構造的に漏れるという plan/research の主張は正確。

## 要対処

- **smoke-startup の seed 記述「そのまま写す」が引用行範囲と矛盾しており、実装時に過剰コピーへ誘導しうる。** plan `:47` は「`visual-check-colors.ps1:108-130` の seed（値を持つ `[hotkey]`/`[appearance]` + 空の `[paths]`）をそのまま写す」と書くが、実際の `108-130` 行（`visual-check-colors.ps1` 実読）には `[general]`（`$showOnStartup` 変数を埋め込む）・`[visual]`（`$Color` 変数を埋め込む）・値入りの `[[paths.scan]]` も含まれる——括弧内の説明（3 セクションのみ）と行範囲の実内容（5 セクション）が一致しない。「索引 0 件」という要件（`:47` 冒頭）と `[[paths.scan]]` を含む全文コピーは両立しないため、「そのまま写す」を文字どおり実装すると (a) 索引 0 件の要件に反する、(b) `smoke-startup.ps1` には存在しない `$showOnStartup`/`$Color` を参照し `Set-StrictMode -Version Latest` 下で未定義変数エラーになる。実装前に「3 セクションのみを抜粋する」ことを明記し、行範囲の引用を「抜粋」である旨に修正すべき。
- **`smoke-egui.ps1` 側の新設 `try`/`finally` のスコープ終端が plan に明記されておらず、字面どおりに読むと不要に広い入れ子構造へ誘導しうる。** plan `:31-32` は「env を設定する行より前から始まる `try` を新設し」と**開始点**しか指定しない。終了点が未指定のまま「スクリプトが throw しても呼び出し元のシェルへ漏らさない」（不変条件 2）を満たそうとすると、実装者は安全側に振って新設 `try` をスクリプト末尾（`:462-482` の `exit 1` 分岐と成功時 `Write-Host` まで）まで広げがちである。しかし `$env:SNOTRA_CONFIG_DIR` は子プロセス（`Start-Process`）の起動時に一度スナップショットされるだけで、それ以降のスクリプト本体（`:297` 以降の `try`・`:462` 以降の判定）は env 変数を再読しない——**同じファイルの `$env:SNOTRA_TRACE` の扱い（`:211-219`）がまさにこのパターンで、`Start-Process` の直後に即座に復元しており、`try`/`finally` すら使っていない**。`SNOTRA_CONFIG_DIR` は不変条件 2 により `finally` での復元が要る点だけが `SNOTRA_TRACE` と異なるので、`Start-Process` 呼び出し 1 行だけを囲む小さな `try { $env:SNOTRA_CONFIG_DIR = ...; $proc = Start-Process ... } finally { Remove-Item Env:SNOTRA_CONFIG_DIR }` で十分であり、既存の `:297` の `try`/`catch`/`finally` や `:462` 以降の分岐と入れ子にする必要が無い（`Start-Process` 自体が例外を投げるケースだけを finally で保護すれば足り、それより後段の失敗は env 変数に触れない）。plan はこの終端を明示していないため、実装時に不要に大きい diff（既存 `try` との二重入れ子・`exit` 文の扱いの再検証）を生みかねない。
- **`smoke-egui.ps1` に smoke-startup と同型の「first-run を踏んでいないことの肯定的検査」が無い。** plan の不変条件 6・フェーズ 2 は smoke-startup に対してのみ `cmd:launch_settings_process:` の trace 不在を肯定的に検査するタスクを置いているが、smoke-egui.ps1 も「常に seed してから `Start-Process`」という同じ構造（seed 失敗時に `is_first_run()` が true になり `launch_settings_process(--first-run)` が飛ぶリスク）を持つ。plan が smoke-egui 側に追加する「seed 健全性検査」（本体 stderr の `[config] ` prefix 行の有無）は `Config::load_from_dir_reporting`（`config.rs:927-971`）の **parse 失敗 / 非UTF-8 / read エラー**の 3 分岐でしか eprintln されず、**「ファイルが存在しない」（`NotFound` 分岐・`config.rs:944-948`）は `[config] ` を出力しない**——これはまさに `is_first_run()`（`config_path.exists()` が false）が真になる分岐そのものである。つまり smoke-egui の seed 書き込みが何らかの理由で失敗・スキップされた場合、既存の seed 健全性検査はこれを検出できず、first-run 経路を静かに踏みうる。round 2 の設問が指摘するとおり、smoke-egui にも `cmd:launch_settings_process:` 不在の肯定的検査を足すか、足さない場合はその理由（例: smoke-egui は unconditional seed の直後に必ず `Test-Path $cfgPath` で書き込み成功を検査するので構造的に到達しない、等）を計画に明記すべき。
