## 軽微な懸念

- **`{ flag: "wx" }` の「観測点を1つ増やす」という主張は、`main()` の実制御フローでは過大**: `init` の非冪等 `mkdirSync(dir)`（`recursive` 無し）は、`rmSync` が silent fail していれば `EEXIST` で即座に落ちる。この失敗経路では `writeLedger` に到達する前に main が停止するため、`writeLedger` が呼ばれる時点で `dir` は必ず新規作成直後（内部に `ledger.json` が存在し得ない）である。したがって `main()` を経由する限り `wx` の `EEXIST` は到達不能で、実質的な追加観測点にはならない。値があるのはフェーズ2の「`writeLedger` を直接呼ぶユニットテスト」文脈のみ（そこでは意味がある）。プランの言い回し（「観測点を1つ増やす」）は控えめに直すか、「`main()` 経由では到達しないが、直接呼び出す文脈での契約として保持する」と明記した方が正確。
- **`parseArgs` テスト `:34-36`（サブコマンド無しでエラー）は意味的にドリフトしうる**: 新しい `parseArgs` が「`--slug` は `command === "init"` のときのみ許可」という形でゲートすると、`["--slug", "rust"]`（`command` が未確定のまま `--slug` に遭遇）は「サブコマンドが無い」ではなく「`--slug` は `init` 専用」という別理由でエラーになりうる。テストは `.error` の truthy しか見ていないため壊れはしないが、テスト名（「サブコマンドが無ければエラー」）と実際に発火する分岐が食い違う可能性がある。実装時にコメントかテスト名を実際の分岐に合わせておくと後続の誤読を防げる。
- **`main()` の制御フロー再構成が checklist に明示的な1行として無い**: 現行 `main()` は `validateSlugs(args.slugs)` を `init`/`verify` の分岐**前**に無条件で呼んでいる（`scripts/plan-review-ledger.mjs:171-175`）。新設計で `verify` が argv から `slugs` を受け取らなくなる（`parseArgs` が `verify` には `slugs: []` しか返さない）以上、この共有の事前呼び出しを command 別に分けない限り、`verify` は `readLedger` に到達する前に「スラグが0件」で即 exit 2 になってしまう——それはまさに I2 が求める「exit 2」ではあるが、理由が「台帳不在/parse不能」等の専用復帰手順ではなく紛らわしい「0件」になる。plan.md フェーズ1の 25・26 番目の項目からは意図（`init`: 事前検証→rm→mkdir→writeLedger、`verify`: readLedger→validateSlugs→classifyEntries）は読み取れるが、「共有の前置き `validateSlugs` 呼び出しを削除し各分岐内へ移す」という破壊的リファクタ自体は明示されていない。TDD（フェーズ2の赤テスト）で検出されるはずだが、見落としやすい箇所として実装時に注意を要する。
- **`readLedger` の例外捕捉が catch-all であるべき点が checklist の粒度では未確定**: I2 の5形（台帳不在／parse不能／shape不正／0件／形不正スラグ）を漏れなく exit 2 に落とすには、`readLedger` 内の `fs.readFileSync`/`JSON.parse` の例外捕捉が `error.code === "ENOENT"` のような狭い分岐ではなく、ブランケットな `try/catch` である必要がある（`EACCES` 等の他の I/O エラーを取りこぼすと、`main()` の制御外で uncaught exception としてプロセスがクラッシュし、「専用の復帰手順」を経ない別の exit 経路になる）。plan.md はこの実装粒度を明記していない。
- **SKILL.md フェンス行を `parseArgs` に食わせるテスト（YAGNI 判断）**: `scripts/governance-check.mjs:409-411` は「`npm run X` が `package.json` の `scripts` に存在するか」だけを検査し、引数列の妥当性は検査対象にしていない。したがってこの新テストは既存機構と重複せず、独自の価値（`SKILL.md` の呼び出し例が新しい `parseArgs` 契約に適合するかの回帰検出）を持つ。一方で正規表現で Markdown のフェンスをパースするテストは、フォーマット変化（行継続・引用符・コメント混入）に対して脆く、対象は現状 `SKILL.md` 内の2行（`init`/`verify`）のみという狭いスコープである。また `--slug` を `verify` へ戻す regression は `/plan-review` の実運用でも即座に exit 2 として現れる（fail-closed が既に効いている）ため、このテストは「実行時に気づく」を「CI 時に気づく」へ早めるだけの二重の安全網であり、必須ではない。導入自体に反対する根拠はないが、「なければ致命的」という位置づけではないと判断する。

## 要対処

- **「テスト方針」の CI 記述が事実誤認**: plan.md は「CI は ubuntu + windows の両方で走る（`.github/workflows/ci.yml`）。`mkdtemp` とパス区切りを両 OS で通す。」と書いているが、`.github/workflows/ci.yml` を確認したところ `npm test`（vitest、`plan-review-ledger.test.mjs` を含む）を実行するのは `node-check` ジョブのみで `runs-on: ubuntu-latest`。windows 側で走る `rust-check` ジョブ（`runs-on: windows-latest`）は `cargo check`/`cargo test -p ...`/`cargo clippy`/`cargo doc` のみで **`npm test` を一切実行しない**。したがって新設するプロセス級 e2e（cwd 一時ディレクトリ化）が Windows 上で CI として検証されることは無く、Windows 固有の不具合（`mkdtemp` の挙動・パス区切り・`rmSync`/`mkdirSync` の EPERM 等）は実装者がローカルで手動実行した場合にのみ捕捉される。plan.md がこの主張を検証根拠として書いている以上、修正が必要——「CI は ubuntu のみで、Windows 側の担保はローカル手動実行（本開発機は Windows）に依存する」と書き直すか、windows-latest ジョブにも `npm test` を載せるかを明示的に判断すべき。なお `scripts/clean-worktrees.test.mjs`（`mkdtempSync(path.join(tmpdir(), ...))`）という同型パターンの先例が既に存在し動作しているため、機構自体が Windows で壊れるリスクは低いと見られるが、それは「CI が両OSで担保する」こととは別の事実であり、plan.md の記述はそのまま残すべきではない。
