# plan: #953 `check:colors` の main 窓判定が構造的に赤である

## 目的

判定の前提を「**窓で最も広い色 = 背景**」（main で偽）から「**各窓が宣言した色がすべて在る**」へ
移し、main の判定を構造的な赤から救い出す。同時に、入力欄背景色の到達が自動で測られるようになる。

射程は**背景 + 入力欄の 2 色**（ユーザー裁定・2026-08-06）。選択色・hint 色の計器化は含めない。

## 受け入れ条件

1. main の判定が背景と入力欄の**両方の到達**を測り、正常な状態で **`exit 0` に到達する**
   ——**main が緑になった状態は一度も観測されていない**（未証明の状態であって既定ではない）。実測する
2. results の判定が従来どおり動く（背景 1 色の宣言として同じ述語を通る）
3. 判定述語が**純関数**として `scripts/lib/` に在り、Pester が論理を測る
4. **配線が届くことを end-to-end の故障注入で測る**——Pester 緑 + ゲート死は、#952 で閉じたばかりの
   沈黙する検出器そのものである。製品の色経路を壊して赤になることを確認し、戻す
5. seed する config が背景・入力欄とも**非既定色**である
6. `docs/build-commands.md` の記述が実態と合う

## 設計

### 判定述語は ∃ 形（各色を名指しし、それぞれが下限占有率以上）

**ランキング（上位 N 色）を採らない。** 当初案は「上位 2 色の集合 == {背景, 入力欄}」だったが却下する:

- ランキングは presence の **proxy** であり、判定を 2 つの独立した量の**相対**面積へ結びつける。
  `bar_padding` / `window_width` / status 行の有無 / `font_size` はランキングを覆しうるが、
  **そのとき両色は完全に届いている**——偽陽性がレイアウト変更のたびに出る
- 実際に捕まえたい失敗（色が届かない）は「3 位に落ちる」ではなく**不在**（0 px）として現れる
- `docs/development-principles.md`「構造的設計原則と強制の階梯」が「**守りたい要素は名指しする**」
  「∀ 条件には**『守りたい要素が在る』という ∃ 条件を組にする**」と定めている

**形**（窓が「見せねばならない色」を**宣言**する）:

```
main    → { background, input_bg }
results → { background }
述語: 宣言された色がすべて下限占有率以上か
```

**分岐を書かない**——main の特別扱いも `-Label` による条件分岐も要らない。results は宣言が 1 色なので
従来と同じ意味になる。非対称はロジックではなくデータに載る。

**下限は宣言ごとに持つ**（グローバル固定ではない）:

| 窓 | 宣言 | 実測 | 根拠 |
|---|---|---|---|
| main | `background: 15%` / `input_bg: 15%` | 33.3% / 43.1% | 2 色が窓を分け合う。実測に対し 2 倍以上の余裕 |
| results | `background: 50%` | 76.1% | 背景が支配的な設計（行の塗りは選択行だけで、行数に依らず比率は概ね一定）。実測に対し 1.5 倍の余裕 |

**グローバル固定の下限（当初案の 5%）を採らない理由**: 旧述語は `mode == expected`（最頻）であり、
**「最頻である」は「5% 以上」を含意するが、逆は成り立たない**。results で背景が 10% しか届かない
状態は**今日は赤、5% 固定では緑**になる——**現に動いている検出器を弱める**ことであり、#953 の欠陥の
ちょうど裏返しである。下限を宣言へ載せれば、宣言をデータに置く設計のまま results の強度を保てる。

**測定した占有率は常にログへ出す**（合否に依らず）。レイアウトのドリフトが**失敗になる前に
「margin の縮小」として見える**。

### 理由分類器を作らない

「色が届いていない」と「レイアウトが崩れた」の区別は、失敗メッセージが**実測占有率**を持てば
自然に読み分けられる（`0 px` = 不在 / `3%` = 在るが下限未満）。分類器は射程の膨張である。

### モジュール分割は「純粋な半分」だけ

| 段 | 性質 | 置き場所 |
|---|---|---|
| Bitmap → 色ヒストグラム | I/O・合成しにくい | `visual-check-colors.ps1` に残す |
| ヒストグラム → 判定 | **純関数**・欠陥が在る場所 | `scripts/lib/SnotraWindowColors.psm1`（新設） |

`SnotraTraceInvariants.psm1`（671 行）は**形**の先例であって**規模**の先例ではない。あちらが大きいのは
H1/H4/H5 × trace 区間が本質的に複雑だからで、本件の述語は数十行に収める。

## 不変条件と異常系

- **results の判定を弱めない**——宣言 `{background: 50%}` が旧述語（最頻）と同等以上の強度を持つ。
  **「1 色になるだけで意味は同じ」ではない**: 「最頻である」は「下限以上」を含意するが逆は成り立たず、
  下限をグローバル固定にすると検出器が緩む（設計節）。**Pester に単一宣言の窓で下限未満を落とす
  ケースを置いて、この強度を固定する**
- **`$succeeded` の合議を壊さない**（`seedHealthy` / `profileWritten` / 各窓の判定の連言）
- **`-Color '#FFF'` の 3 桁 hex 受理を壊さない**（#680 の 1 の回帰検査を兼ねている）
- 異常系: 宣言色が 0 件の窓は**赤**にする（「何も宣言しない = 何も測らない = 自明に緑」を作らない。
  `docs/development-principles.md` の「空集合は ∀ を自明に満たす」）
- **`$KeepShot` / スクリーンショット保存の挙動を変えない**。保存は `$Capture.Bitmap` を握る
  **呼び出し元に残す**（純関数はヒストグラムしか受け取らないので機械的にもそこにしか置けない）
- **背景色と入力欄色には相異なる非既定リテラルを使い、同値なら throw する。** 現行は
  `background_color = "$Color"` の 1 行なので、隣へ `input_background_color = "$Color"` と書く誘惑が
  強い（コピペ距離 1 行）。**同値にすると「入力欄が自分の色を持たず背景を透過している」誤配線が
  構造的に見えなくなる**——ヒストグラム上は「両方届いている」としか読めないためである。
  **さらにこの不変条件は実行時にユーザーが破れる**: `-Color` はパラメータで input_bg はリテラルゆえ、
  `npm run check:colors -- -Color '<input_bg と同じ値>'` が 2 色を静かに 1 色へ潰す。**規範ではなく
  機構で守る**——解決後の 2 値が等しければ throw する

### 受容する残余

- **∃ 述語は「クロス配線」（値の取り違え）を検出できない。** 位置に紐付かない存在検査であるため、
  背景領域に入力欄色・入力欄領域に背景色が出る取り違えでは、**両色とも下限を超えて緑になる**
  （実測比 43.1% / 33.3%）。この失敗は「不在」ではなく「**別の場所に存在**」として現れるため、
  述語の前提（不在＝ 0 px）の外にある。**Phase 4 の故障注入（`set_clear_color` の除去＝全消失）も
  この経路を通らない。** #949 が `InputVisuals` の構築点について記録した「同型ペアの取り違えは
  型でもテストでも捕まらない」と**同じ型の欠陥**である
  - **位置に紐付く判定へ拡張する案は却下する**: 入力欄の矩形を検査側で知るには `bar_padding` /
    `bar_inset` / `font_size` からの導出が要り、**製品のレイアウト計算の写しを検査側に作る**ことに
    なる（`docs/development-principles.md`「ドキュメントとコードの分担（陳腐化の予防）」の向きに反し、
    式が 2 箇所になる）。**書かれていない残余は「気づいていない」と「気づいて許容した」を区別できない**
    ため、ここに残す
- **このゲートは人間が起動したときだけ走る**（`ci.yml` にも `e2e.yml` にも無い・GUI 依存）。
  直したところで「誰も起動しなければ黙る」性質は残る。**それがこの修正の価値の上限である**
- 選択色・hint 色の計器化は射程外（ユーザー裁定）。hint は文字のアンチエイリアスで面積が小さく、
  判定に閾値と許容距離の 2 つのマジックナンバーを要する

## テスト方針と検証コマンド

### Pester（純関数の論理）

合成ヒストグラムで測る。**両方向**を置く:

| ケース | 期待 |
|---|---|
| 宣言色がすべて下限以上 | 緑 |
| 宣言色の 1 つが**不在**（0 px） | 赤・その色を名指し |
| 宣言色の 1 つが在るが**下限未満** | 赤・実測占有率を示す |
| 宣言色が最頻でないが下限以上（＝ #953 の当の状況） | **緑**（これが直ったことの証明） |
| **単一宣言の窓**で宣言色が 10%（下限 50% 未満） | **赤**（results の強度を弱めていないことの証明） |
| 宣言が空 | 赤 |
| 2 つの宣言色が**同一値** | 赤（throw・下の不変条件） |

### 実機（配線が届くことの証明）

- `npm run check:colors` が **exit 0** に到達する（未証明の状態ゆえ実測する）
- **end-to-end 故障注入は宣言色ごとに 1 本ずつ置く**（スクリプトごとに 1 本ではない）。
  `.claude/rules/safety-nets.md`「**検出器のカバー範囲は、欠落のパターンごとに検算する**」——
  「足ごとに壊して測り、捕まらない足は機構へ載せる」（#858 でカナリアは 3 本中 1 本しか捕まえなかった）:

  | 注入 | 落とす経路 | 測る宣言色 |
  |---|---|---|
  | ① `view.rs` の `frame.set_clear_color` を落とす | 背景（`run_ui` → paint） | `background` |
  | ② `search_input_ui` の `visuals.extreme_bg_color = input_visuals.input_bg` を落とす | 3 値（`ui.visuals_mut()`）——**背景とは完全に別経路** | `input_bg` |

  **②は本 issue が新たに計器化する当の色である。**①だけでは、`input_bg` の宣言が飾りでも緑になる。
  実現可能性は #949 の変異 ii-a で確認済み——落とすと `dead_code` が出るが**警告**であり、
  `cargo build -p snotra` はバイナリを生成する（赤くなるのは clippy の `-D warnings` だけ）。
  どちらの注入も測定後に**戻す**。Pester だけでは「述語は正しいがゲートが死んでいる」を捕まえられない
