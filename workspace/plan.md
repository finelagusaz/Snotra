# 計画: issue #1541 — trace 1 行が約 8〜10 ms かかる回の機序を測る

## 目的と受け入れ条件

目的: `hotkey:listener_enter`（と、同じ規模の `SNOTRA_EGUI_INPUT push_key` down）の 1 行の書き込みが約 8〜10 ms かかる回の所要が、どこにかかっているかを計装で区切って測り、`PERFORMANCE.md` に記録する。

受け入れ条件:

1. 次の測定の結果が `PERFORMANCE.md` の新しい節にある。分布は、起動ごとの「4 ms 超の件数 / 標本数」と、全体の p50・p90・最大で示す（**独立な標本はプロセスの起動である**。#1539 では同じ版の p50 が巡によって 445 / 8,321 µs に分かれた）。
   - M0 基準の再現: 計装版を (a) の条件で起動し、`listener_enter` と `push_key` down に 4 ms 超の行が出ることを確かめる（下の「不変条件と異常系」の停止条件）
   - M1 ハンドルの種類と置き先: 同じ操作で stderr を (a) `Start-SnotraProcess` のリダイレクト（write-through・C: の NVMe）(b) write-through なしのディスクファイル（C:）(c) `NUL` (d) (a) と同じで置き先を D:（USB の SSD）、で受ける。各条件 4 起動以上を交互に回す。各起動の最初に、本体が自分の stderr の `GetFileType` と `NtQueryInformationFile(FileModeInformation)` を 1 回読んで記録する（(a) が write-through であることを本体で確かめる）
   - M2 区間の分割: 1 行の所要を「行の組み立て」「`std::io::stderr().lock()` の取得」「ロックした `StderrLock` への `write_all`（`WriteFile`）」へ分け、それぞれの壁時計（QPC）と `QueryThreadCycleTime` のサイクルを記録する。製品と同じなのは「同じロックと同じ `WriteFile`」までである
   - M3 同じ点の別のシステムコール: stderr の `write_all` の直前に、別に開いた `NUL` のハンドルへの 1 バイトの `WriteFile` を置き、その所要を記録する（同じスレッドの他の処理が同じ待ちを受けるか・issue の「確かめていないこと」）。あわせて、`WM_HOTKEY` を受けた時刻（`GetMessageW` が戻った直後の QPC）から listener の入口までを記録する（スレッドの起床の遅れは計装の区間の前で起きるため）
   - M4 空白とスレッドと入力: 非表示のアイドルを 50 / 150 / 300 / 570 / 1500 / 2500 / 5000 ms に振ったときの `listener_enter` の峰の出方（`powercfg` の閾値 200 ms / 2000 ms をまたぐ）。各行について、スレッドを問わない直前の記録との間隔と、同じスレッドの直前の記録との間隔。`push_key` down の、1 回の中の位置（文字 1〜3・Escape）別の 4 ms 超の率と、down / up の直前の空白の長さ。入力なしの可視アイドル（10〜20 秒。egui はキャレット点滅で約 2 fps のフレームを書く）での `egui_frame` の行の所要（別のスレッドで、入力を伴わずに空けた直後の 1 行）
2. 峰の所要がどの区間にかかっているかの結論を `PERFORMANCE.md` に書く。`listener_enter` と `push_key` down は、別々に結論してよい。決めきれなければ、何を測って何が残ったかを書く。`QueryThreadCycleTime` で「サイクルが小さく壁時計が長い」と出ても、それだけでは H1・H2・H5 を分けない（分けるのは M1 の置き先と `NUL`）と書く。
3. 峰を述べる既存の記述（下の「変更するファイル」の表）を、新しい節を指す形に直す。
4. `PERFORMANCE.md`「計測と受け入れ基準」の trace の所要の項に、この峰をどう読むかを書く。**額は写さず**、新しい節を指す。既存の額の写し（同項の 8〜10 ms と、`SNOTRA_EGUI_INPUT_TRACE` の項の p50・p90・8〜10 ms）は、触る範囲で参照へ置き換える。
5. この issue では直さない（「未確定」の裁定）。直す価値のある原因が出たら、新しい節に理由と再開の条件を書き、別の issue にする。峰が write-through に由来すると分かったら、「不採用: `Start-SnotraProcess` の起動の形を替えて stderr の write-through を外す（#1543）」の末尾の「関係は測っていない」をその事実へ直す。
6. 製品のコード（`SNOTRA_TRACE` 無効時の挙動、trace の出口の「1 行 1 回の書き込み」）を変えない。一時の計装・計測スクリプト・生の stderr はコミットしない。

## 実装の順序

1. 一時の足場を用意する（コミットしない）
   - 計装版: `origin/main` から切った一時の worktree（リポジトリの外、`C:\workspace\snotra-probe-1541`）に、`src-tauri/src/trace.rs` の `trace`・`snotra-egui-runtime/src/stderr_line.rs` の `emit`・`src-tauri/src/platform/mod.rs` の `WM_HOTKEY` の arm へ計時を入れる。`CARGO_TARGET_DIR` は別にする。足場の先頭のコメントに撤去の条件（「`PERFORMANCE.md` の新しい節が着地したら worktree ごと消す」）を書く
   - 記録の出口: 計時値は、プロセス共有の固定長のリングバッファ（`static` の配列と `AtomicUsize` の添字）に `(tid, QPC, 種別, 区間ごとの QPC, サイクル)` を積む。**測定中はファイル I/O をしない**（周期的な書き出しは C: の NVMe を起こし、H1 の検定を壊す）。測定の最後に 1 回だけ、計測スクリプトが本体へ書き出しを頼み（計装版が受ける私用のウィンドウメッセージ、またはトレイの終了の経路の直前のフック）、`SNOTRA_PROBE_OUT` のパスへ書かせる。stderr の行そのものは製品と同じバイト列のまま
   - 計測スクリプト: scratchpad に置く。`scripts/lib/SnotraSmoke.psm1` を Import し、Alt+F12 で表示 → 3 文字打鍵（down・50 ms・up・50 ms を明示）→ Escape で非表示 → アイドル（M4 で振る）を 25 回で 1 起動とする。**操作中は stderr のファイルを読まない**（`Wait-SnotraTraceCondition` を使わず、表示の確認はウィンドウの可視で行う）。呼び出し側の env に `SNOTRA_EGUI_INPUT_TRACE` を立てない（`Send-SnotraKey` が `Write-Host` を挟むため）
   - 起動の形: (a) は `Start-SnotraProcess -StandardErrorPath`。(b)(c) は `ProcessStartInfo` で起動し、stderr の受け方だけを替える。.NET 11（ローカルの pwsh 7.7.0）の `StandardErrorHandle` に `File.OpenHandle(..., FileOptions.None)` / `NUL` のハンドルを渡す（#1543 の C の形）。これで (a) と (b)(c)(d) の差は、ハンドルの性質だけになる（PID も本体を指す）。(c) の `NUL` で `WriteFile` が呼ばれることは、M2 の区間の計時（0 でない）で確かめる
2. 測る前に、測定条件を記録する: stderr のファイルを置くドライブ・電源プランと AC/DC・`powercfg /q` の NVMe の idle timeout と許容遷移遅延・USB の選択的サスペンド・EcoQoS（効率モード）の状態・ウイルス対策の除外の有無・`fltmc filters` の一覧・計装版の基になった sha
3. `QueryThreadCycleTime` の陽性対照を 1 回取る: 既知の CPU ループ（約 1 ms）と `Sleep(10)` を計装版の同じ関数で測り、サイクルと壁時計が期待どおりに分かれることを確かめる
4. M0 → M1（M2・M3 は同じ記録から取れる）→ M4 の順に測る
5. 結果を `PERFORMANCE.md` へ書き、既存の記述を直す
6. 足場を撤去する（一時の worktree と `CARGO_TARGET_DIR` を消す）

## 不変条件と異常系

- 製品のコードに差分を残さない。`git diff origin/main...HEAD -- '*.rs'` が空であること（`main.rs` のコメントを直す場合はコメント行だけ）
- **停止条件（M0）**: 計装版を (a) で 2 起動回して、`listener_enter` にも `push_key` down にも 4 ms 超の行が 1 件も出なければ、M1 以降へ進まない。計装が峰を消した（観察者効果）か、条件が #1539 / #1542 と違うかを疑い、計装を外した版（`origin/main` の release）で `listener_enter` の行の `ts_ms` の間隔を見て再現を確かめる。それでも再現しなければ、「再現しなかった」ことと条件を新しい節に記録し、受け入れ条件 2 は「決めきれなかった」として書く
- 書き出しが走らなかった起動（`SNOTRA_PROBE_OUT` が無い・空）は、標本から外し、外した数を記録する
- `listener_enter` が tauri の `try_lock` の失敗で別のスレッドへ回った回は、tid で見分けて数える（0 件でもそう書く）
- H3（ロック）の観測は、計装した行どうしの取り合いしか見えない（計装していない `eprintln!`・panic・依存 crate の書き込みは見えない）。結論にこの限界を書く
- 計測中は、他の重い処理（ビルド・別のベンチ）を同じ機体で走らせない
