# plan — issue #765: `/implement`「出力」に Step 4 の受け口を作る

## 方針（ユーザー確認済み）

「出力」節に Step 4 の項目を 1 つ足し、**母集団を SSOT から導出する三値**で書かせる。併せて項目 2（最終検証結果）の母集団も同じ形へ揃える。issue 後半が名指しした「`check, clippy, test` の 3 種」は #764 で既に解消済みであり（`research.md`「前提の是正」）、直す対象は**そこに残った同型の残余**——母集団が「実行したカテゴリ」＝書き手の裁量になっている点である。

採る形の根拠は `/health-check`「Check 7 — MEMORY.md 参照の実在性」の三値と `/plan-review`「Step 3 — 結果の統合と報告」の配送欄。どちらも**母集団を先に閉じ、各要素に必ず 1 つの値を割り当てる**。#764 の総括パターン 2（書き手が分類を決める限り義務は書き手が消せる）・パターン 3（記録テンプレートの有無が実施の有無の唯一の観測点）への既存解である。

## 不変条件

1. **母集団は書き手が選べない集合として閉じている** — 項目 2 は `docs/build-commands.md` のカテゴリ A〜F（SSOT そのもの）、項目 3 は `/implement`「4a. check スキルの実行」が名指しするスキル集合。どちらも件数を本文に書かない（スキル・カテゴリの増減で写しが腐るため）。**この不変条件が破れた形**＝「実行したもの / 該当したものだけを書けばよい」と読める文言に戻ること

   **ただし項目 3 の母集団は SSOT ではなく写しである** — 4a 自身が「写像の SSOT は `AGENTS.md`「条件別チェック（トリガー → 参照先）」表。二重管理を避けるためここに再掲しない」と述べたうえで、6 スキルを括弧書きで列挙している。**本変更はこの括弧書きを「便宜的な列挙」から「報告義務の閉じた母集団」へ格上げする**（`.claude/rules/safety-nets.md`「これまで無意味だった状態に意味を与える変更は、その状態に到達する全経路を列挙する」に当たる操作である）。表へスキルを 1 件足して 4a の括弧書きを直し忘れると、そのスキルは報告母集団から**沈黙して落ちる**。**この乖離を検知する機構は存在しない**（`scripts/governance-check.mjs` を grep して確認済み——4a の列挙と表を結ぶ検査は無い）。表を直接指す形へ寄せると `AGENTS.md` 表の非スキル行（rules 参照・grep 指示）を読み違える経路が開くため寄せず、**写しであることを名指しした受容する残余として扱う**
2. **「該当なし」「未実施」「実行不能」が互いに区別可能である** — 3 つを同じ記号・同じ省略で書ける文言にしない。破れると「検証されていない」が「問題が無かった」に化ける（`/health-check`「Check 7 — MEMORY.md 参照の実在性」の三値と同じ理由）
3. **報告面と実況面の境界が明示されている** — `:19` の実況制限が「出力」節の義務を削れない。破れると issue が指摘する「正直に書いた側が罰される形」が残る
4. **到達しなかった Step の項目が要求されない** — 母集団は 1c 経路（1c-A / 1c-B / 1c-C）**だけではない**。Step 3 の中止経路（`:94`）も Step 4・5 に到達しない。破れると、到達していない実行で存在しないレビュー結果を書かせることになる（**書けないので捏造か沈黙のどちらかになる**）。ゆえに免除は経路の列挙ではなく「到達しなかった Step」という原理で書く
5. **外部からの参照が壊れない** — `## 出力` / `### 4a.` / `### 4b.` の見出し文字列を変えない。`CLAUDE.md:74`・`docs/adr/0004-canonical-heading-references.md` が正準形で指し、G11 が照合する。「出力」項目への**序数参照は外部に 0 件**（`research.md` で grep 済み・plan-review で 2 レイヤーが独立に再確認）のため、項目の繰り下げは外へ波及しない。**ただし番号付きリスト項目自体が G11 のアンカー面である**（`scripts/governance-check.mjs:722` の `collectAnchors` が `^\s*\d+[.)]\s+` を拾う）——新項目の行頭語はこの変更の瞬間から公開面になるため、後から気軽に変えられる文言のつもりで書かない
6. **常時ロード面を増やさない** — frontmatter の `description` を触らない（G10 の `alwaysLoaded` には skill description が算入される。skills 本文は対象外）

## テスト方針

このファイルには実行可能な検査が無いため、**検証は 2 系統**である。

- **機械**: `npm run governance:check`（カテゴリ F）— 参照実在（G11 の正準見出し照合）・スキル表・面積 ratchet（G10）。**これが覆うのは形式であって、三値の文言が実際に義務を課すかは覆わない**
- **規範**: `/norm-review` の 2 クラスの読者（Phase 2）— 上の合格条件 4 件が、機械検査の外側を受け持つ唯一の検証である

**このサイクルで新規のユニットテストは追加しない**（対象が `*.md` の規範文言であり、`post-edit.mjs` の `selectChecks` にも `vitest` の include にも母集団が無い）。

## SPEC.md 更新要否

**不要。** 変更対象はエージェントの運用規範であり、プロダクトの挙動・状態遷移ではない（`AGENTS.md`「3層分担（責務分離）」の第 1 層のうち `SPEC.md` が持つのは製品仕様であって、スキルの報告契約ではない）。

## セルフレビュー

### `/plan-review` の要対処（2 件・いずれも本計画へ反映済み）

- **免除のスコープ不足** → Phase 1 の該当項目と不変条件 4 を「列挙から原理へ」書き換え、`/norm-review` の合格条件 5 を追加した。**先行欠陥の是正を含む**（既存の「コミット」項目も Step 3 中止経路では充足不能だった）
- **カテゴリ D の吸収禁止** → Phase 1 の項目 2 に、D を無限定の「未実施」へ畳まず独立に名指しし目視項目の列挙を残す旨を明記した

配送は台帳 3 件中 3 件が実在し、**独立レビュー不成立のエントリは無い**。Step 2b の独立導出は変更ファイル・変更箇所・「issue 後半は既に古い」の判断で計画と一致し、加えて上記 2 件と G11 アンカー面の指摘を持ち込んだ（不変条件 5 へ反映）。

### 5b の 3 観点

1. **境界条件** — 報告の形が壊れうる端は 5 つあり、`/norm-review` の合格条件と Phase 1 の文言でそれぞれ 1 件ずつ当てる: (a) check スキルが 1 件も該当しない変更（全 6 名が「該当なし」の 1 行に並ぶ最小形） (b) 全 6 件が該当する変更（最大形） (c) `code-reviewer` が Critical/High とも 0 件（**実施したのに書くことが無い**——「実施 / Critical 0・High 0」と書けることを文言で保証する） (d) Step 3 中止経路（項目 3・4 が省かれる） (e) 1c 停止経路（項目 2・3・4 が省かれる）
2. **シンプル化の挑戦** — 新しい状態・プロセス・機構は導入しない（文言のみ）。却下した代替案は 2 つあり、**どちらも `/implement` Step 5 で ADR へ回収する候補である**: (i)「項目 2 と項目 3 を 1 つに畳む」——検証（カテゴリ A〜F）とレビュー（check スキル・エージェント）は別の失敗様態であり、同じ項目に混ぜると片方が沈黙する。(ii)「4b の結果をコミットメッセージ側へ寄せる」——git に残る利点はあるが、**issue が述べる失敗面は意思決定時に読む会話面であって永続性ではない**。報告面を git へ移しても、その場で「実施した回と素通りした回」を区別する手立ては増えない
3. **破壊不変条件 + 検知手段** — 壊れたら即アウトなのは不変条件 1・2（母集団が閉じなくなる＝実施の有無が再び区別できなくなる）。**検知手段は `/norm-review` の 2 クラスの読者だけであり、機械検出器は無い**。`docs/development-principles.md`「『検知手段が無い』と書きかけたら、検知可能になる設計へ変えられないか先に問う」に従って (a) 責務を検査可能な層へ移す・(b) 観測点を作る の 2 種を検討したが、**どちらも成立しない**——`governance:check` に検査器を足せば「規範文が書かれているか」は測れても、報告そのものは会話にしか存在せず git にもディスクにも残らない（これは issue #765 が述べる失敗様態そのものであり、本変更が規範で塞ぐと決めた対象である）。**受容する残余として記録する**

### 受容する残余

- **`/norm-review` 自身は項目 3 の母集団の外にある** — `AGENTS.md`「条件別チェック（トリガー → 参照先）」表 → `.claude/rules/safety-nets.md` の 2 段間接で到達し、4a が名指しする 6 スキルに含まれない。**本変更自身がその実例である**（規範を変える変更では `/norm-review` が走るのに、項目 3 はそれを報告させない）。母集団を広げると閉じた集合を失うため広げず、**名前を挙げて残余とする**
- **項目 3 の母集団は `AGENTS.md`「条件別チェック（トリガー → 参照先）」表の写しである**（不変条件 1 の後段）。表と 4a の括弧書きの乖離を検知する機構は無く、表へ足したスキルが報告母集団から沈黙して落ちうる。`/norm-review` の合格条件 6 で読者側からは当てるが、機構では塞がない
- **本変更の遵守を測る機械検出器は置かない**（上記 3 の結論）
- **`/norm-review` は上限 2 巡で打ち切る** — 2 巡目の塞ぎが作る新しい抜け道は検証されずに残る（`/norm-review`「Step 4 — 次巡、または停止」）
