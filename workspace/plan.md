# 実装計画 — issue #766: `.claude/agents/*.md` の `effort` を実測する

## 目的

`.claude/agents/*.md` の frontmatter で `effort` が honored されるかを、**推論ではなく起動して**確かめ、結果を残す。

調査（`workspace/research.md`）で、キー名が `effort` であること・ローダが読んで検証すること・agent 定義の `effort` が model の上書きと同じ配列へ積まれることまでは一次読み取りで確定した。**残るのは末端である**——その配列が実際にそのサブエージェントの解決 effort を動かすか。issue が求めた実測はここに当たる。

## 受け入れ条件

1. `.claude/agents/*.md` の `effort` キーが**ローダに読まれる**ことを、起動時のメッセージで観測した
2. `effort` を書いたときと書かないときで、そのサブエージェントの**解決 effort が変わるか**を観測し、結果（変わる / 変わらない / 観測できなかった）を根拠つきで記録した
3. 測定のために置いた足場が撤去され、`.claude/agents/` が測定前の状態に戻っている（内容ハッシュで照合）
4. 結果が issue #766 へ記録され、偽になったメモリが訂正されている

## 射程外（この計画では**やらない**）

- **`.claude/agents/code-reviewer.md` へ `effort` を書くこと。** `.claude/agents/` は `AGENTS.md`「条件別チェック（トリガー → 参照先）」のセーフティネット行に属し、ルート `CLAUDE.md` 最重要ルール 2 が「Claude が単独で判断しない」と定める。**この計画の成果物は測定結果と推奨水準であって、共有物への適用ではない**——適用は人間の判断として分ける。
- **issue が名指しした「`code-reviewer.md` に `effort` を書いて測る」方法を採らない。** 使い捨てのプローブ定義で同じことが測れ、そちらはセーフティネットに触れない。issue がその方法を挙げたのは当時 `.claude/agents/` に定義が 1 枚しか無かったためで、**測りたい事柄は「agent 定義一般で効くか」であって「code-reviewer で効くか」ではない**。

## 方法の変更（承認後に判明したので記録する）

計画は Phase 2 で「起動して解決 effort の変化を観測する」としていたが、**候補の観測量が 2 つとも失格した**（上の未確定 1・2）。issue が求めた「実 Agent を 1 体起動して実測する」は実行し、そこから得られたのは次の 2 つである。

- agent 定義はセッション中に読み直される
- 無効な effort（`bogus`）はロードを止めず、値が載らないだけである

**残る 1 本の鎖は一次読み取りで閉じた。** `permissionLayers` から `effort` を取り出す `kc()` と、同じ配列から `model` を取り出す `c()` が構造の同じ関数である（`workspace/measurements-766.txt`「鎖が閉じた」）。`model` の上書きが効くことは疑いがないので、`effort` は同じ経路に乗る。

⚠ **これは end-to-end のランタイム観測ではない。** 「同じ配列を同じ形で読む隣の要素だから効く」という形の主張であり、そう書いて残す。

## 測定結果

**答え: キー名は `effort` であり、`.claude/agents/*.md` で honored される。** 有効値は `low` / `medium` / `high` / `xhigh` / `max` または整数（版 2.1.250）。

根拠は 4 段の鎖で、すべて本体バイナリの一次読み取りである（検索文字列は `workspace/measurements-766.txt`）。ローダが `effort` を読んで検証し、通れば agent 定義へ載せ、spawn 経路が `{kind:"model"}` と並べて `{kind:"effort"}` を `permissionLayers` へ積み、`kc()` がそこから取り出す。**`model` を取り出す `c()` と構造が同一で、`model` の上書きが効くことは疑いがない。**

⚠ **end-to-end のランタイム観測ではない。** 用意した観測量が 2 つとも失格したためである（`CLAUDE_EFFORT` はセッション水準の変数だった／名前付きサブエージェントの通知にトークン使用量が載らない）。主張の形は「同じ配列を同じ形で読む隣の要素だから効く」であって、リクエストのペイロードを見たわけではない。

起動して得た実測は 2 つ。**agent 定義はセッション中に読み直される**（起動時ロスターに無い型で起動できた）。**無効な effort はロードを止めない**（`effort: bogus` の定義でもエージェントは起動し、値が載らないだけである）。

### `code-reviewer` への推奨水準（提示のみ・適用しない）

**推奨: 今は据え置く（`effort` を書かない）。**

- `code-reviewer` の 3 フェーズ（実装検証 / 計画判断・SPEC.md 同期 / パフォーマンス）は**単一の値を共有せざるをえない**。frontmatter にフェーズ別の手段は無い（`sZt` のキー集合に該当するものが無い）
- そのうち実装検証は、このリポジトリで**最も所見が出ている面**である（本サイクルだけでも High 1 件・Medium 4 件を worktree のレビューが出した）。下げる先が全フェーズ共通になる以上、費用の節約と引き換えに最も効いている面を削ることになる
- **効果を測る手段が無いことも据え置きの理由である。** 上のとおり解決 effort を外から観測できないので、下げた後に「品質が落ちていない」を実測で言えない。issue が引く "Prompting Claude Opus 5" の「品質を保ったまま」は、測れる人が測って初めて根拠になる
- 下げるなら**パフォーマンス面だけを別エージェントへ切り出してそちらに `effort: low` を置く**形が筋だが、これはセーフティネットの構成変更であり、費用対効果が `code-reviewer` 1 体分に留まる（issue 自身が「優先度は低い」と書く）ことを踏まえるとやりすぎだと考える

**適用はチームの判断に委ねる**（`.claude/agents/` は共有物・ルート `CLAUDE.md` 最重要ルール 2）。
