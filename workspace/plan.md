## docs/comment-guidelines.md のアウトライン

1. **目的と適用範囲** — Rust（rustdoc）/ TypeScript（TSDoc）/ テストコード。エージェント・人間共通
2. **第一原則: コメントは「なぜ」を書く** — コードから読み取れないこと（設計判断の理由・却下した代替案・不変条件・過去の事故）のみ。コードの逐語訳を書かない
3. **配置基準（3 層）** — development-principles.md の「リファクタを生き延びるか」基準を参照:
   - 散文 docs（intent・全体構造）／ doc コメント（契約・精密事実の SSOT = 正準コメント）／ インラインコメント（局所的な why）
4. **rustdoc の様式** — `///` は公開アイテムの契約（保証・パニック条件・呼び出し前提）。`//!` はモジュール冒頭の責務宣言（既存 6 ファイル——3 クレートに分散: snotra-core の opener.rs / src-tauri の monitor.rs, trace.rs, working_set.rs / snotra-settings の style.rs, tabs/common.rs——の慣習を追認。「同一クレート内の慣習」と書かない）。設計判断の長文は `# Why ...` 見出しで構造化（`SearchEngine` の doc（search.rs）を模範例として参照）
5. **TSDoc の様式** — `/** */` は `lib/` プリミティブと `stores/` の契約に必須級、`.tsx` コンポーネントは非自明な props 契約・ライフサイクル制約がある場合のみ。Markdown 太字で契約の要点を強調（`exclusive.ts` / `ownedTimer.ts` を模範例として参照）
6. **定型ラベル（既存慣習の追認・一覧化）** — 「保守注意:」「不変条件:」「実装メモ:」「検出マーカー:」「回帰テスト: <由来>」の意味と使い所
7. **歴史メモの様式** — issue 参照 `#NNN`・実測値には日付/条件・却下案は「試した→結果→採用理由」の順。**長さ自体は問題ではない**（search.rs のベンチ表は模範）。粒度基準: 「この情報が消えたら、将来の変更者が同じ失敗を繰り返すか？」
8. **言語（日英）** — 現状追認: 日本語を既定、Win32/プラットフォーム低レベル部や英語圏 API 文脈は英語可。同一ブロック内の混在は避ける（新規分から適用）
9. **書かないもの** — 未実装計画（YAGNI。`ui/CLAUDE.md` の具体則を参照）・コードの逐語訳・変更履歴の再現（git log が持つ）・レビュー向けの一時的説明（PR 説明に書く）
10. **同期コストへの答え** — コメントは実装と同じ場所・同じ PR で更新する。挙動を変える PR でコメントの why が変わるなら同時に直す（「fix でも文書化された挙動を変えたら仕様変更」の類推）

## 不変条件

- **ドキュメント間 DRY**: 既存規範（正準コメント・YAGNI コメント則・「リファクタを生き延びるか」）を**再記述せず参照する**。ガイドラインが第 2 の SSOT にならないこと
- **既存文化との無矛盾**: 模範例として参照する実在コード（`search.rs` の `SearchEngine` doc / `exclusive.ts` / `ownedTimer.ts` 等）の参照が正確であること（ずれるとガイドライン自体がドリフト源になる）。**注意: 当該構造体の実名は `SearchEngine` である**（plan-review が `SearchIndex` 誤称を検出・修正済み。search.rs:140 で実在確認済み）
- **エージェント設定不変**: `.claude/`（スキル・フック・rules）を触らない。CLAUDE.md の行動制約も変えない（参照リンク追加のみ）
- 失敗・異常系: 純ドキュメント変更のためランタイムリスクなし。最悪ケースは「参照先の行番号ドリフト」→ 行番号ではなく**アイテム名参照**（`search.rs` の `SearchEngine` doc、`exclusive.ts` の `createExclusive` 等）を基本にして緩和する。`ui/CLAUDE.md` の YAGNI 則は見出しアンカーが無いため、行番号でなく文言（「実装しない機能のコメントは書かない」）で参照する
