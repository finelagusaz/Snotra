# 計画: #1269 直前のキー押下に連結されない `WM_CHAR` が入らないことを、受容する残余として記録する

## 目的と受け入れ条件

調査（`workspace/research.md`「実測」）で次が分かった。

- Alt+テンキーの文字コード入力は、この環境（日本語配列・日本語 IME）では tao 0.35 の旧版でもメモ帳でも文字にならない。**回帰ではなく、この環境では測れない**
- 他のアプリが `PostMessage(WM_CHAR)` で直接送る文字は、tao 0.35 では入り、tao 0.37 では入らない。**回帰として実在する**

ユーザー判断（2026-10-09）: **直さずに、受容する残余として記録する。**

受け入れ条件:

1. `snotra-egui-runtime/CLAUDE.md`「不変条件」の「一般」に、この残余が 1 項として書かれている。項には次の 4 点が入る
   - 何が入らないか: 直前のキー押下に連結されない `WM_CHAR`（tao 0.37 は `event_info` の無い `WM_CHAR` を `KeyEvent` にしない）
   - 実測の範囲: `PostMessage(WM_CHAR)` は 0.35 で入り 0.37 で入らない（2026-10-09 実測）。Alt+テンキーは日本語配列・日本語 IME の環境では OS 側で文字にならず未測
   - 直さない理由: 拾うには subclass が tao の判定を写す必要があり、写しがずれると通常の打鍵が二重に入る
   - issue 番号（#1269）
2. 既存の「通常文字は `KeyEvent::text_with_all_modifiers()` から…それぞれ 1 経路だけ」の項と矛盾しない（その項の主張を弱めない・同じ事実を 2 か所へ書かない）
3. `npm run governance:check` が緑
