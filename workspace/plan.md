# 実装計画 — issue #766: `.claude/agents/*.md` の `effort` を実測する

## 目的

`.claude/agents/*.md` の frontmatter で `effort` が honored されるかを、**推論ではなく起動して**確かめ、結果を残す。

調査（`workspace/research.md`）で、キー名が `effort` であること・ローダが読んで検証すること・agent 定義の `effort` が model の上書きと同じ配列へ積まれることまでは一次読み取りで確定した。**残るのは末端である**——その配列が実際にそのサブエージェントの解決 effort を動かすか。issue が求めた実測はここに当たる。

## 受け入れ条件

1. `.claude/agents/*.md` の `effort` キーが**ローダに読まれる**ことを、起動時のメッセージで観測した
2. `effort` を書いたときと書かないときで、そのサブエージェントの**解決 effort が変わるか**を観測し、結果（変わる / 変わらない / 観測できなかった）を根拠つきで記録した
3. 測定のために置いた足場が撤去され、`.claude/agents/` が測定前の状態に戻っている（内容ハッシュで照合）
4. 結果が issue #766 へ記録され、偽になったメモリが訂正されている

## 射程外（この計画では**やらない**）

- **`.claude/agents/code-reviewer.md` へ `effort` を書くこと。** `.claude/agents/` は `AGENTS.md`「条件別チェック（トリガー → 参照先）」のセーフティネット行に属し、ルート `CLAUDE.md` 最重要ルール 2 が「Claude が単独で判断しない」と定める。**この計画の成果物は測定結果と推奨水準であって、共有物への適用ではない**——適用は人間の判断として分ける。
- **issue が名指しした「`code-reviewer.md` に `effort` を書いて測る」方法を採らない。** 使い捨てのプローブ定義で同じことが測れ、そちらはセーフティネットに触れない。issue がその方法を挙げたのは当時 `.claude/agents/` に定義が 1 枚しか無かったためで、**測りたい事柄は「agent 定義一般で効くか」であって「code-reviewer で効くか」ではない**。

## 方法の変更（承認後に判明したので記録する）

計画は Phase 2 で「起動して解決 effort の変化を観測する」としていたが、**候補の観測量が 2 つとも失格した**（上の未確定 1・2）。issue が求めた「実 Agent を 1 体起動して実測する」は実行し、そこから得られたのは次の 2 つである。

- agent 定義はセッション中に読み直される
- 無効な effort（`bogus`）はロードを止めず、値が載らないだけである

一度は「残る鎖を一次読み取りで閉じた」と書いた——`permissionLayers` から `effort` を取り出す `kc()` と `model` を取り出す `c()` が構造の同じ関数だから、と。**公開前の検算がこれを壊した。** 消費の段で 2 つは非対称である: `model` は層の値がそのまま勝つが、`effort` は `BT()` の優先順位で env と**モデルの pinned launch effort** が上位に立つ。**「隣の要素だから効く」は成り立たない。**

**この節は誤りの記録として残す。** 同じ形を 2 度踏んだ——(1) 観測が失格したと決めつけてその機序を書き（`N6t`）、(2) その決めつけを前提に構造で代替した。**どちらも「所見を狭める根拠の側」を測っていなかった。** 訂正後の結論は下の「測定結果」が正本である。

## 測定結果

**キー名は `effort` である**（版 2.1.250）。`.claude/agents/` を走るローダがそれを読み、`RA()` で検証し、通れば `model` と同じ形で agent 定義オブジェクトへ載せる。**値は `low` / `medium` / `high` / `xhigh` / `max`（別名 `med` も通り、大文字小文字は問わない）または整数**——正本は `RA()` と `lg` と別名表であって、エラーメッセージの文言ではない。

**その値がサブエージェントの解決 effort を実際に動かすかは、実測できていない。** 構造としては、spawn が `{kind:"effort"}` を `{kind:"model"}` と同じ `permissionLayers` へ積み、`kc()` がそこから取り出すところまでを一次読み取りで確認した。**ただし `model` と違い、`kc()` の値は候補にすぎない**——`BT()` の優先順位で env `CLAUDE_CODE_EFFORT_LEVEL` と**モデルの pinned launch effort**（`oO()`）がその上位に立つ。**ゆえに「効く」はモデル依存であり、無条件には言えない。**

起動して得た実測。新規に置いた agent 定義はその session で起動でき、無効な `effort` を書いてもロードは止まらなかった（値が載らないだけである）。`effort` を `bogus` / `low` / `medium` にした 3 起動は、**どれも `CLAUDE_EFFORT=high`**——親セッションと同じ値——を返した。

**この観測は決着に足りない。** `CLAUDE_EFFORT` は（当初そう考えたのと違って）セッション水準の変数ではなく、Bash ツールが呼び出しごとに `kc(t)` を通して解決する値である。つまり**観測は正しい枝を見ている**。それでも差が出なかった説明は複数立ち、どれも潰せていない——子プロセスが親の環境を継承する形と注入が同じ値へ落ちる／モデル側の pinning が上位で勝つ／実際に効いていない。`low` と `medium` の 2 水準で見る再測定は**実施済みで、どちらも `high` だった**ため、`high` が既定の落ち先であることを使った切り分けも成立しなかった。

**残るのは「構造は在るが、その値が届いているかを外から示せていない」という状態である。**

### `code-reviewer` への推奨水準（提示のみ・適用しない）

**推奨: 今は据え置く（`effort` を書かない）。** 上の訂正で、この結論はむしろ強くなる。

- **効果を測る手段が無い。** 解決 effort が動いたかを外から示せていないので、下げた後に「品質が落ちていない」も「安くなった」も実測で言えない。issue が引く "Prompting Claude Opus 5" の「品質を保ったまま」は、測れる人が測って初めて根拠になる
- **効果がモデル依存である。** `BT()` の優先順位でモデル側の pinning が上位に立つ以上、「今のモデルでは効く」が明日も真とは限らない
- **フェーズごとに分ける手段を私は見つけられなかった。** `sZt` に該当キーが無いことは根拠にならない（あれは shadow validator であって挙動のゲートではない）——**見つけられなかったという以上のことは言えない**
- 下げるなら 3 フェーズのうち軽い面だけを別エージェントへ切り出す形が筋だが、これはセーフティネットの構成変更であり、得られる効果が `code-reviewer` 1 体分に留まる（issue 自身が「優先度は低い」と書く）ことを踏まえるとやりすぎだと考える

**適用はチームの判断に委ねる**（`.claude/agents/` は共有物・ルート `CLAUDE.md` 最重要ルール 2）。
