## 2. 変更の中身

### 2.1 `health-check` Check 7 — 所在と委譲規約

現状は 3 行で、所在も委譲時の前提も書いていない。書き換え後に含めるもの:

1. **`MEMORY.md` はリポジトリに存在しない。** harness のユーザー領域（`~/.claude/projects/<project-slug>/memory/`）にある
2. **絶対パスはメインエージェントの system prompt に与えられる。** スキル本文にハードコードしない（マシン固有・harness 内部仕様のため）
3. **委譲するときは絶対パスをサブエージェントのプロンプトに明記する。** サブエージェントは system prompt を継承しない（実測: リポジトリ内を探して「不在」と誤報した）
4. `Read` / `Glob` / `Grep` は絶対パスでリポジトリ外へ届く（実測）
5. **リポジトリ内の `Glob` で見つからないことは発見事項ではない**
6. **パスが与えられていない場合は「検証不能」と報告する。「不在」と報告してはならない**

検証内容（現状どおり）: リンク先の実在性、各メモリの `description` と内容の一致。

### 2.2 `health-check` 出力節 — 第三の値 `Skipped`

現状の語彙は `Critical` / `Warning` / `Info` の三段しかなく、**「実施できなかった」を表現できない**。ゆえに Check 7 は「実施できなかった」を「不在」（Info）へ潰した。

追加する契約（`/plan-review` の 2 体が独立に同じ形へ収束した）:

> 実施できなかったチェックは **`[Skipped]`** として、理由とともに報告する。発見事項としては数えない。
> **`[Skipped]` が正当なのは、そのチェックが文書化した前提を満たせない場合に限る。** 現状その前提を持つのは **Check 7 のみ**（メモリ領域の絶対パスが与えられていない）。リポジトリ内のファイルだけを対象とする Check 1〜6・8〜10 は前提が常に満たされるため、**それらが `Skipped` になること自体が発見事項**（検査基盤の異常）である。
> **「All checks passed」は「全チェックを実施して異常が無かった」を意味する。** 発見事項ゼロ **かつ** `Skipped` ゼロのときだけそう書く。

サマリー雛形も更新する（散文の契約だけでは、機械可読なサマリーが「実施したか」を示さないまま残る）:

```markdown
## サマリー
- チェック項目数: N（実施: M / Skipped: K）
- 発見事項: N件（Critical: N / Warning: N / Info: N）
```

**`Skipped` の正当域を限定しないと、「面倒な検査は Skipped にしておけば楽」という fail-open の抜け道ができる**（`Skipped` は発見事項に数えないため）。理由の記述を要求するだけでは捏造で破れる。上記の限定により、`Skipped` は無料の免罪符ではなく**可視の劣化**になる。

これは #482 の hook が「管轄外 = allow」「判定不能 = block」を区別した構造と同型であり、#471 の「沈黙 = 合格と読めるのは、沈黙しうる経路をすべて塞いだから」と同じ規律である。**「異常なし」と「見ていない」を同じ記号で書かない。**

### 2.3 `retrospective` Step 6 / Step 7

- **Step 6**（メモリの鮮度チェック）: 「`MEMORY.md` はリポジトリ外にある。詳細は health-check の Check 7 を参照」の一行参照に留める。**同じ前提を 2 箇所に書かない**（DRY）
- **Step 7**（サイクル末 health-check）: 「本スキルが直接実施する」に加えて、**委譲する場合の契約**を書く。「Check 7 を委譲するならメモリ領域の絶対パスをプロンプトに渡す。渡さないなら Check 7 は `Skipped` である」。あわせて「`Skipped` があるまま『All checks passed』と報告しない」

#### なぜ Step 7 にも書くのか（`/plan-review` の指摘を実測で退けた）

レビュアーの 1 体は「`retrospective/SKILL.md` の `allowed-tools` に `Agent` が無い**から委譲できない**。ゆえに Step 7 の委譲契約は到達不能なデッドレターであり、書くべきは『インライン実行ゆえ安全』だ」と、frontmatter を根拠に主張した。

**これは推論であって実測ではない。実測すると偽である。**

- `retrospective/SKILL.md:6-13` に `Agent` が無いのは事実（確認済み）
- **にもかかわらず、本セッションの `/retrospective` 実行中に `Agent`（Explore）を起動して health-check を委譲できた**。誤報はまさにその経路で起きた
- すなわち `allowed-tools` は、メイン会話でインライン実行されるスキルに対して**ツールを拘束しない**

「インライン実行ゆえ安全」と書けば、**実際に起きた経路を安全と偽る**ことになる。Step 7 は委譲が起きた当の場所であり、契約はそこにも要る。Check 7 本体（定義に付随して旅する）と Step 7（実施トリガー）の**両方**に書くのが、どちらの経路でも効く安全側の判断である（独立再導出の 1 体も同じ結論に達した）。

### 2.4 `AGENTS.md` — 横断ルール

「環境制約」の並列エージェント委譲まわりに 1 項追加する。

> **委譲はコンテキストを継承しない。** メインエージェントの system prompt にしか無い事実（メモリ領域の絶対パス等）は、サブエージェントのプロンプトへ明示的に渡す。渡し忘れると、サブエージェントは「見えないもの」を「無いもの」として報告する（#489: health-check Check 7 が `MEMORY.md` を「存在しない」と誤報した。これは #482 の根と同型で、**判定に使う情報と検査対象がずれている**）。委譲先に「何を渡し、何をあえて渡さないか」を明文化する（`/plan-review` Step 2b の「`plan.md` を読ませない」が良い先例）。
