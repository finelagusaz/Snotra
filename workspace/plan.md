# 計画 — issue #1552

## 目的と受け入れ条件

`/implement`「1a」が「機械判定」と呼ぶ計画の入口判定（未確定ゼロ・承認の形）を、`scripts/plan-check.mjs` に移し、`npm run plan:check` から呼ぶ。判定の正本はスクリプトにする。

- `npm run plan:check -- [--plan <path>]`（既定 `workspace/plan.md`）は、次を判定する
  - 未確定ゼロ: レベル 2 の見出しで `## 未確定（実装前に潰す）` で始まるものがあり、その節（次のレベル 1・2 の見出しまで）に未チェック項目が無い
  - 承認: レベル 2 で `承認` と完全一致する見出しがあり、その節に人間承認の行か自己承認の行が 1 件ある
    - 人間承認: `- [x] 承認済み — <日付> / 問い: "<空でない>" / 回答: "<空でない>"`
    - 自己承認: `- [x] 自己承認 — <日付> / 仕様変更: なし — <根拠> / 戻せない変更: なし — <根拠> / 人の裁定: なし`
  - 自己承認の追加条件（すべて満たすときだけ成立）
    - 未確定欄に「（裁定）」の印の付いた項目が無い
    - `## 変更するファイル` で始まる見出しの節があり、その節に `SPEC.md` の項目が無い
    - `## セルフレビュー` で始まる見出しの節に「check スキル」の行があり、節の全体に `/persistence-check` が無い（子の箇条で check スキルを並べる形があるので、行だけでは見落とす）
- 終了コード: 0 = 成立 / 3 = 不成立（理由を全件、直し方つきで出す） / 2 = 判定できない（使用法の誤り・ファイルが無い・読めない）。0 と 3 以外はすべて「判定できない」と読む（node がロードの前に落ちると 1 になるので、不成立に 1 を使うと区別できない。`scripts/merge-pr.mjs` と同じ考え方）
- コードフェンスは非対称に扱う。成立の証拠（見出し・承認の行・check スキルの行）はフェンスの外だけで数え、不成立の証拠（未チェック項目・（裁定）・`SPEC.md` の項目・`/persistence-check`）はフェンスの中でも数える（雛形を引用した計画を通さない）
- `/implement` Step 1 は、`plan.md` があり同一性が立ったときにこのスクリプトを呼ぶ。exit 0 なら Step 2、exit 3 なら 1c-B、それ以外なら 1c-C で止まる（1c-C の文言を「判定できなかった」を含むよう広げる）。同一性は散文で確かめる
- `/start-issue`「5c. 承認」は、承認を記録した直後にこのスクリプトを呼ぶ。exit 0 でなければ、出力に従って記録を直す
- 見出しの無い計画は不成立になる（#821 の再現をテストで固定する）
- PR 前ゲートに承認の判定は足さない
