# 計画 — issue #1493 工程の継ぎ目に契約を置き、計画の承認をリスクに応じて変える

## 目的と受け入れ条件

目的: implement → PR の継ぎ目に持ち主と本文の契約を置き、issue → 着手の継ぎ目で「検討:」「保留」を取りこぼさず、計画の承認を「人にしか答えられない問いが残るか」で分ける。

受け入れ条件（issue #1493 から）:

- A1 `/implement` の手順だけで PR 作成まで到達できる。PR 本文の節がテンプレートと一致する
- A2 「検討:」「保留」の issue を `/implement` に渡すと、計画や実装に入る前に止まって問う
- A3 3 基準のどれも立たない計画は、人に問わずに自己承認の記録が残り、`/implement` の入口判定を通る。自己承認の記録が自分の他の記録（「（裁定）」の印・変更ファイルの `SPEC.md`・発火した `/persistence-check`）と矛盾する計画は、入口判定を通らない（3 基準の判定そのものは自己申告で、機械では確かめない。D1）
- A4 `npm run governance:check` が通る

## 設計の決定（未解決の疑問への答え）

- D1（Q1）承認の記録は `/start-issue` が書き、`/implement` は形を確かめるだけにする（1c-B の「承認を自分で記録してはならない」は残す）。節の見出しを `## 人間レビュー` から `## 承認` へ改め、次のどちらか 1 件を置く
  - 人間承認: `- [x] 承認済み — <YYYY-MM-DD> / 問い: "<逐語>" / 回答: "<逐語>"`（従来どおり）
  - 自己承認: `- [x] 自己承認 — <YYYY-MM-DD> / 仕様変更: なし — <根拠> / 戻せない変更: なし — <根拠> / 人の裁定: なし`
  - `/implement`「1a」は、自己承認なら次を機械で確かめる。どれかが崩れたら承認不成立（fail-closed）: 3 項目がすべて「なし」／未確定欄に「（裁定）」の項目が無い／計画の変更ファイルの一覧に `SPEC.md` が無い（あれば仕様変更の徴候。「仕様変更: なし」と矛盾する）／`## セルフレビュー` の「check スキル」の行に `/persistence-check` が無い（あれば戻せない変更の徴候）
  - そのため `/start-issue`「5b」の記録欄に「check スキル: <5a で実行したもの、または なし>」の行を足す
  - 保証の範囲: 機械で確かめるのは、記録どうしの矛盾（自己申告と、`SPEC.md` の掲載・`/persistence-check` の発火）までである。3 基準の判定そのものの正しさは自己申告で、機械では確かめない
  - 1a の「エージェント自身の判断を承認の代わりにしない」は、「`/implement` 自身の判断」へ主体を狭める（自己承認の記録は `/start-issue` が 5c の基準で書く）
- D2（Q2）人の裁定が要る未確定事項は、行頭に「（裁定）」を付ける（`- [ ] （裁定）<事項> — <問い方>`）。解消して `- [x]` にしても印は残す。印が 1 件でもあれば「人の裁定: あり」であり、人間承認へ回す。承認の問いに裁定を含めてよい
- D3（Q3）自己承認のとき、`/start-issue` は Step 6（workspace のコミットと push）のあと、Skill ツールで `/implement` を呼ぶ。人間承認のときは従来どおり、承認を得てから Step 6 へ進む（`/implement` の起動は承認の回答が指示していればそれに従い、なければ案内して止まる）
- D4（Q4）`/implement` に「Step 5 — PR を作る」を Step 4 の後に足す。Step 4 の最後のツール実行のあとに `workspace/` の外を動かさない（hook (4) の照合）。本文ファイルはリポジトリの外（一時ディレクトリ）に Write で書く。push → `gh pr create --title … --body-file …`（`git push … && gh pr create …` の鎖にリダイレクトを挟まない）。PR を作るときの機械的な条件は `.claude/hooks/pre-bash.mjs` の冒頭を指し、写さない。マージはしない（`/merge-pr` はユーザーが起動する）。`allowed-tools` に `Bash(gh *)` を足す
- D5（Q5）テンプレートの節。直近の PR の節名は割れている（`workspace/research.md`「敵対的調査（3b）の反映」）ので、実践の写しではなく次を選ぶ: 冒頭の合意行（該当時。条件の正本は `.claude/rules/safety-nets.md` のフロントマターの `paths` と規範文書）／対応 Issue（`Closes #<N>` か「なし — <理由>」。マージのときの `--closes` と一致させる）／概要（何を・なぜ）／変更／検証／残したもの（採らなかった案・⚠️・範囲外。無ければ節ごと省く）。コメント（`<!-- -->`）で各節に書くことを一言添える。`/implement` Step 5 はテンプレートを Read して節に従い本文ファイルを書く（`--body-file` の経路でテンプレートが本文に入るかに依存しない）
- D6（Q6）`/implement`「出力」に `### PR` の欄（URL、または停止したなら「未到達」）を足す
- D7（Q7）`/deps-update`「Step 4」は「本文はテンプレートの節に従う。更新一覧は『変更』節に載せ、major bump は ⚠ で明示する」とする
- D8 判定 3 基準の正本は `/start-issue`「5c」に置く。① 仕様変更 = `AGENTS.md`「開発ワークフロー」の 1 の判定（`SPEC.md` の記述を変えるか）② 戻せない変更 = `AGENTS.md`「条件別チェック」の永続形式・識別子/キー形式の行に当たるか ③ 人の裁定 = D2 の印。セーフティネットの計画も同じ基準で判定する（マージ前の合意は残る）。`/implement`・`/plan-review` は 5c を指す
- D9 `/plan-review`「リスク判定」に、高リスクは独立レビューの要否を決めるもので、承認の主体（人間か自己か）は決めないことを 1 文で足す。同 Step 3 末尾の「人間の承認へ渡す」を「承認（`/start-issue`「5c. 承認」）へ渡す」に直す。Step 1 末尾の「調査や裁定が要るなら、未確定欄へ追加する」に、人の裁定が要る項目には「（裁定）」の印を付けることを足す（付け忘れると自己承認をすり抜ける）
- D10 見出しを改める: `/start-issue`「Step 5 — 計画検証と人間レビュー」→「Step 5 — 計画検証と承認」、「5c. 人間の注釈と承認」→「5c. 承認」、plan.md の `## 人間レビュー` → `## 承認`。旧名を `git grep` で数え、現役の文書の参照（`/implement` 1c-B が「5c. 人間の注釈と承認」を名指している）を同じ変更で直す。`docs/superpowers/`・`docs/design/` の過去の記録は直さない。旧見出しの計画は 1a で不成立（聞き直し）になるが、2026-11-21 に全 worktree の作業ツリーと `refs/heads`・`refs/remotes/origin` の全ブランチを数え、承認済みの `workspace/plan.md` を持つものは 0 件だった（このブランチの承認待ちの 1 件だけ）。旧見出しを受け付ける移行措置は置かない
- D11「検討:」「保留」の判定は、計画なしの経路（1b の「計画が無く…」の 2 行）にだけ効かせる。計画ありの経路では `/start-issue`「Step 1」で済んでいる。`$ARGUMENTS` が issue 番号を含むときは `gh issue view` でタイトルを読む。散文だけで issue が無いときは判定の対象外。停止は新しい種「1c-D（検討・保留の issue）: 判定を自分では行わず、止まって `/start-issue <N>` へ渡すと報告する（判定の本文は `/start-issue`「Step 1」が持つ）」とし、1c の「停止は 3 種」は種の数を書かない言い方へ直す（「出力」の `1c-A/B/C` も同じ）
- D12 カテゴリ D の目視を `-PostToPr` で人へ委ねる場合（`/implement` 3b）、`-PostToPr` は PR が在って初めて使えるので、Step 5 で PR を作ったあとに行う。Step 5 にその 1 行を置き、3b の該当文から Step 5 を指す
- D13 自己承認でも、高リスクなら #1300 へ試行の行をコメントする（試行が記録するのは独立レビューであり、承認の主体ではない）。5c の文言を「承認（人間・自己）を記録したあと」にする
- D14 `/start-issue` の `description`（「人間の承認までを行い」）を、承認（人間または自己）へ直す。自己承認のときは `/implement` を呼ぶことも反映する

## 不変条件と異常系

- `/implement` は承認を記録しない（1c-B）。自己承認でも、記録の主体は `/start-issue`
- 承認の判定は fail-closed: `## 承認` 節が無い・2 形式のどちらでもない・自己承認なのに「あり」がある・「（裁定）」の印がある、のいずれも不成立
- 自己承認の記録は、承認より前に計画が変わったら書き直す（3 基準の判定は計画の内容に依存する）
- `/merge-pr` はユーザー起動のまま。マージの自動化を入れない
- `gh pr create` は `--body-file` で本文を渡す（heredoc は hook が拒む）
