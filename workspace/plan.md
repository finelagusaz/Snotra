# plan — #921 SPEC §4.9「入力と選択」の新設と §6.3 からの一本化

## 目的

「入力欄への文字入力は選択を 1 行目へ戻す」を **§4 に 1 度だけ**書き、§6.3 の重複を畳む。あわせて §4.8「マウス操作」に誤配置されているキーボードの 1 行（↑↓）を新節へ移す。**挙動は一切変えない**（`SPEC.md` と `search_state.rs` のコメントのみ）。

## 受け入れ条件（issue より）

1. §4 の記述が実装と一致する（通常検索の打鍵で選択が 1 行目へ戻ること）
2. §4 と §6.3 の間で同じ事実を二重に書かない
3. 挙動は変えない（as-built の明文化）
4. ツール選択中は打鍵が届かないことを、書く場合は §18.5 の既存記述と二重にしない

## 確定済みの判断（人間裁定・2026-08-04）

- **置き場所**: §4.9「入力と選択」を新設し、`SPEC.md:208`（↑↓）も移設する

- **AC 4 は「書かない」ことで満たす**: ツール選択中はそもそも文字入力が届かない（`interactive(false)` で `changed()` 不発火）ため、§4.9 に例外として書かない。§18.5「ツール選択中の入力は無効化」が既に所有している

**文言の制約（逸脱したら書き直す）**

- **候補行に触れない。** 選択のリセットは同期・無条件だが、候補行の差し替えは results（debounce）と folder（同期）で非対称であり、一歩でも触れると実装より強い主張になる（#838 の High 指摘と同型）
- **修飾句「全検索モード・フォルダ展開共通」は荷重を負っている。** §4.9 は「§4 検索システム」配下ゆえ、「通常検索では…」と限定すると §6.3 の削除が**事実の消失**になり AC 1 と AC 2 が衝突する（独立導出の要対処 3）。この修飾句が folder 側も覆うことが、削除を成立させている
- **入力が届かない状態（ツール選択中・launching 中）を書かない。** どちらもそもそも文字入力が発生しないため §4.9 の主張は falsify されない。既存の所有者は §18.5（ツール選択中の入力は無効化）と §19.6（`SPEC.md:1052`「打鍵は入力欄の無効化で抑止する」）で、書けば二重記述になる（AC 4）

- **挙動不変**: `src-tauri/src/**` に**実行に影響する差分を入れない**。証拠は 2 段

## テスト方針と検証コマンド

**新規テストは追加しない。**理由は 2 つあり、どちらも実測に基づく。
