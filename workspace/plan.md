# 実装計画 — #738 ドラッグ後の main をバー矩形で作業領域内へ復帰させる

## 目的

`main` 窓の**バー高ぶんの矩形**が作業領域の外にあるとき、**ドラッグを終えた時点で内側へ復帰する**ようにする。

**これは仕様変更である**（`AGENTS.md` ワークフロー 1）。現行 `SPEC.md` はドラッグでの持ち出しについて何も書いておらず、新しい保証を足す。「fix」というコミット種別は SPEC 同期を免除しない。

## 不変条件（前提条件つき・全称を張らない）

> **main が可視で、かつポインタが押されていないフレームにおいて、バー矩形は「そのバー矩形が乗るモニター」の作業領域の内側にある。ただしバー矩形が作業領域より大きい場合は左上寄せに留まる。**

前提を 3 つ明示する（`AGENTS.md`「全称表現は前提条件とセットで書く」）。**どれも実装より強い主張をしないために要る**。

1. **「ポインタが押されていないフレーム」** — ドラッグ中は拘束しない（後述「なぜ毎フレームではないか」）。OS の move loop 中は egui のフレームが来ない可能性があり、そこを拘束するには `WM_MOVING` のフックが要る。**採らない**（下記「却下した案」）
2. **「フレームにおいて」** — 状態変化がフレームを起こさない事象（タスクバーの移動・モニター構成変更で**作業領域だけが縮む**場合）では復帰しない。次回 show の `position_on_target_monitor` が直す
3. **「作業領域より大きい場合は左上寄せ」** — `window_width` に上限は無く（`snotra-core/src/config.rs:Config::validate` に幅の検証は無い・設定 UI は 1200 まで許す）、低解像度 × 高 DPI では窓幅が作業領域幅を超えうる。`WorkArea::clamp` は左上寄せする既存挙動（テスト `clamp_window_wider_than_work_area_aligns_to_left` が固定）

クランプの材料は **`bar_height`（論理 px）であって実高ではない**。実高を使うと toast が消えて窓が縮んだとき位置が戻らず、hide 時の `read_placement_relative` がそのずれを永続化する（#755/#801 で実際に起きた失敗）。これは `show_egui_main` が 1 手目で既に適用している導出と**同一**である（#877 が幅について採った治療法と同型・#878 が求める構造）。

## 設計上の要石 2 つ（codex の敵対的レビューで判明）

### 要石 1 — 基準モニターは**バー矩形の中心**から決める。窓の矩形から決めてはならない

`MonitorFromWindow`（＝既存の `monitor::window_monitor_work_area`）は**ウィンドウ全体の矩形**の重なりでモニターを選ぶ。

**失敗する筋**: 上下に隣接するモニターで、バーを上側モニターの下端付近に置く。status 行 + toast 行が出て実ウィンドウの大部分が下側モニターへ伸びると、`MonitorFromWindow` は**下側**を返す。クランプ先が下側モニターへ切り替わり、**行が出ただけでバーが下側モニターへ飛ぶ**——#904 の裁定「バーの位置はユーザーが決め、行の出没では動かさない」を、本修正自身が破る。

**ゆえに `window_monitor_work_area` を使わない。** バー矩形の中心点を `MonitorFromPoint(..., MONITOR_DEFAULTTONEAREST)` へ渡す新関数を足す。バー矩形は行の出没で変わらないので、基準モニターも変わらない。

### 要石 2 — ドラッグ中はクランプしない。**毎フレームでは封鎖が起きる**

**失敗する筋**: 横並びの作業領域 A=`0..1920`、B=`1920..3840`、窓幅 600px。A から右へドラッグすると、左端が `1320..1620` の区間ではまだ A の重なりが優勢である。毎フレームのクランプはそのつど `x=1320` へ引き戻すため、**B が優勢になる `x>1620` へ到達できない**——通常速度のモニター間移動が事実上封鎖される。

これは issue コメント 1 でユーザーが挙げた懸念（「ディスプレイ間移動で邪魔になったりしないか」）そのものである。**「ゴムバンドでも受け入れ条件を満たす」という初版計画の判定は誤りだった。**

**ゆえにポインタが押されている間はクランプしない。** ドラッグ中は自由に動かせ、離した時点で復帰する。副産物として、幅を広げたときに窓が別モニターへ飛ぶ筋（下記「却下した案」の 3 番目）も同時に消える。

## 却下した案

| 案 | 却下理由 |
|---|---|
| 毎フレーム無条件にクランプ | 要石 2。モニター間移動が封鎖される |
| `Moved` リスナーでクランプ | OS の move loop 中に連続発火し、要石 2 と同じ封鎖を起こす。加えて `set_position` が `Moved` を再発火する |
| `WM_MOVING` をフックして移動矩形自体を拘束（真に「常に内側」を保証する唯一の手段） | main 窓の wndproc は tao の所有であり、サブクラス化が要る。`src-tauri/CLAUDE.md`「ある窓の show / hide / topmost のいずれか 1 つが tao を迂回したら残り 2 つも迂回側へ寄せる」が示す混在の危険と同じ性格の介入になる。**得るものは「ドラッグ中も画面外へ出せない」だけで、ユーザーの要求（「持っていこうとしても復帰する」）は復帰で満たされる** |
| 幅変更フレームでもクランプする | 横並びモニターで幅 300px→1200px と広げると、新しい矩形の重なりが隣モニター優勢になり、窓が**左ではなく右へ飛ぶ**。要石 2 の対処（ポインタ非押下時のみ）だけでは防げないため、**幅の live-read による位置変更は行わない**（クランプはポインタの状態遷移でのみ意味を持つ） |

## 受け入れ条件

1. バー矩形が作業領域の外にある状態でドラッグを終えると、**上下左右いずれの方向でも**内側へ復帰する（前提: バー矩形が作業領域に収まる大きさであること）
2. **status 行・toast 行の出没では位置が動かない** — #904 の人間裁定を壊さない。**上下に並んだモニターで下側へ伸びる場合を含む**（要石 1）
3. **モニター間のドラッグ移動が妨げられない**（要石 2）
4. ドラッグ中に窓が振動しない
5. **前提条件によって外に残る状態から、ユーザーが自力で作業領域内へ戻せる**（人間裁定・2026-08-04）。手段は 3 つあり、いずれかが常に使える:
   - バーが掴める位置にある → ドラッグして離せば復帰する（受け入れ条件 1）
   - バーが掴めない → ホットキーで hide → show すれば `position_on_target_monitor` が復帰させる
   - 窓が作業領域より広い（前提条件 3）→ 設定で `appearance.window_width` を狭めれば掴める大きさへ戻る
6. `SPEC.md` §8.2 に新しい保証が**前提条件つきで**明記され、status/toast 伸長による下端はみ出し（受容残余・#904 で明記済み）との関係が読める
7. `cargo test` green・`clippy -D warnings` clean

## 単位の落とし穴 — outer と inner を取り違えない

**`WorkArea::clamp` の `win_h` は物理の *outer* 高さ、`bar_height` は論理の *content* 高さである。** `show_egui_main` がこの差を踏まないのは、`set_size` の後に `position_on_target_monitor` が `outer_size()` を**読み戻す**ため、非クライアント分を OS が供給するからである。**フレームループ経路にその読み戻しは無い。**

`decorations: false` ゆえ差分は 0 の見込みだが、**見込みに賭けない**。`outer_size()` と `inner_size()` を両方読み、その差を足す:

```
chrome_h = outer_size().height - inner_size().height   // 現在の高さでも差分は正しく取れる
win_h    = bar_rect_height_phys(bar_height, scale) + chrome_h
win_w    = outer_size().width                          // 幅は導出しない
```

測って「0 だった」で済ませると、装飾を足す将来の変更で**静かに数 px 外れる**——#878 が言う「目視でしか捕まらない」クラスそのものになる。

### `set_position` と `Moved` の関係（初版の分析を訂正）

初版計画は「`set_position` が `Moved` リスナーを**その場で同期実行**する」と書いたが、**これは誤りである**。`RedrawRequested` ハンドラが tao の runner を借用している最中のため、`EventLoopRunner::send_event` は `Moved` を**バッファし、`update()` の終了後に配送する**（`tao-0.35.3` の `event_loop/runner.rs`）。`app.listen` の `emit_filter` が同期実行されるのは、tao の `WindowEvent` が配送された**後**の段である。

帰結は 3 つ。

1. **同一フレーム内の再入は起きない** — engine lock のデッドロックを心配する必要は無い（初版が挙げた根拠は不要だったが、結論「安全」は変わらない）
2. **results の同フレーム追従は `Moved` 経由ではない** — `set_position` は `SetWindowPos` を同期で撃つので、直後の `drive_results_window` が `outer_position()` から**新しい位置**を読む。**クランプを drive の前に置く根拠はこちらである**（初版の根拠は差し替え）
3. **`Moved` は次のイベント配送で届き、results を再度同じ位置へ置く** — 同値上書きで無害（`position_results_below_main` の doc が記録する既存の性質）
