# Research: コメントのガイドラインを策定する (issue #557)

## issue の要約

- **ペイン**: コメントのフォーマットが決まっておらず長文メモが書かれている。コメントと実装をそろえるコストが高い
- **あるべき姿**: Rustdoc / TSDoc に対応（フォーマット・粒度をそろえる）。コメントにはコードから読み取れない「なぜ」を書く
- **備考**: ガイドラインは「どうあるべきか」のブレストから始める
- **ユーザー合意済みの方針**（AskUserQuestion で確認）:
  - 成果物は **docs/ に独立文書**（`docs/comment-guidelines.md`）。AGENTS.md / CLAUDE.md からは参照リンクのみ
  - スコープは**策定のみ**。既存コメントの書き直しは別 issue

## issue の論点への回答（ブレストの種）

issue のペイン「長文メモ」について: 調査の結果、長文メモの大半は**高価値な歴史記録**（実測値・却下案・不変条件）であり、排除すべきものではない。ペインの本質は「長い」ことではなく「**フォーマット・粒度が不揃いで、どこまで書くべきか判断基準がない**」こと。ガイドラインの主要論点:

1. **配置基準**: 何をコメントに書き、何を docs/ や CLAUDE.md へ送るか（→ 既存の「リファクタを生き延びるか」基準を継承）
2. **rustdoc/TSDoc の様式**: `///` vs `//`、`//!` の使い所、TSDoc タグの範囲、`.tsx` の扱い
3. **定型ラベルの標準化**: 保守注意/不変条件/# Why/回帰テスト由来の追認と一覧化
4. **issue 参照フォーマット**: `#NNN` の書き方・実測値の記録様式
5. **言語（日英）の使い分け基準**: 現状の分布を追認するか、統一するか
6. **書かないもの**: 未実装計画（YAGNI・ui/CLAUDE.md:159）、コードの逐語訳、レビュー向け説明

## 未解決の疑問

- 言語（日英）の方針は「あるべき論」が一意に決まらない（現状追認 = 混在許容 vs 日本語統一）。plan では**現状追認 + 領域別の推奨**を提案し、plan-review / ユーザーレビューで判断を仰ぐ
- `cargo doc` / TypeDoc 等の生成ツール運用は issue に要求がなく、development-principles.md L29 が「生成より参照」を既定としているため**スコープ外**とする
