# research — #1140 見出しが同じまま本文が変わった参照に、検知も報告も無い

## issue の要約

`G-heading-refs` が保証するのは「ラベルが見出しに着地するか」だけで、**見出しの名前が変わらないまま本文が入れ替わっても緑のままである**。生きた層で着地している正準形の参照 271 件のうち 81 件（30%）が「参照が書かれたあとに指し先の節が変更された」状態にあり、検査は一度も鳴っていない。

**要求（2026-08-19 にユーザーが選択）**: 節の中身が変わったことを、**PostToolUse hook で編集直後に**報告する。合否は出さない。

## 再利用できる既存パターン

- **reminder は gate ではない**（`isSourceFileWrite` の doc）。判定の SSOT を hook に再実装せず、低頻度シグナルで気づきを増やすだけに留める。`Write` に絞ったのは「既存ファイルの Edit まで拾うと沈黙 = 合格を壊す頻度になる」ため——**頻度が設計変数として明示されている前例がある**
- **合否を持たない計器**の前例は `ADR-retire-area-budget`（面積）。`scripts/governance/instrument.mjs` が `checks/` の外に在ることで「検査ではない」を構造で担保している
- 逆引きに要る部品（アンカー抽出・正規化・対象解決・走査行）は #1141 で 3 本の腕まで揃っており、**新規に書くのは逆引き索引と節の行範囲だけ**

## 技術的制約（実測）

### 費用

逆引き索引の構築は **約 190 ms**（3 回測定: 181 / 198 / 199 ms。走査 251 ファイル・参照 267 件・鍵 121 個）。編集ごとに走る hook としては無視できない量である。

### 騒がしさ

依存を持つ節は **116 個**。1 節あたりの依存件数は **中央 1 件・52% が 1 件・最大 19 件**（`AGENTS.md`「条件別チェック（トリガー → 参照先）」）。

発火頻度（`.md` を触った直近 80 コミットに対する近似。節の境界と索引は現在の木のもの）:

| | 発火した割合 | 1 回あたりの件数（中央 / 最大） |
|---|---|---|
| 全 hunk | **46%**（37/80） | 3 / 41 |
| 純粋な追記（旧側 0 行）を外す | **25%**（20/80） | 10 / 31 |

hunk の内訳は純追記 166・削除書き換えあり 407。**純追記を外すと発火は約半分になるが、1 回あたりの件数は増える**——低件数の発火が純追記側に偏っていたためである。

### 契約上の制約

- **`.md` の沈黙は今日「何も走らなかった」を意味する**（ルート `CLAUDE.md`「フック」・#497）。ここへ初めて出力を入れると、**沈黙が「依存は無い」と読まれうる**。reminder の不在に意味を持たせない書き方が要る
- `.claude/hooks/` は `scripts/` を **1 つも import していない**（実測: hooks 間の相互 import のみ）。依存の向きを新設するかどうかが設計判断になる
- 発火するのは `.md` の編集だけである——正準形の対象は `<path>.md` か `/skill-name`（`.claude/skills/<name>/SKILL.md` へ解決）であり、いずれも `.md` に着地する

## 未解決の疑問

1. **基準をどこに取るか。** `git diff HEAD -- <file>`（未コミットの差分）か、PostToolUse payload の `tool_input`（Edit は `old_string`/`new_string` を持つが Write は持たない）か
2. **判定をどこに置くか。** (i) hook が `scripts/governance/lib.mjs` を import する／(ii) hook が `node scripts/<新スクリプト>` を subprocess で呼ぶ／(iii) hook に再実装する（**(iii) は `isSourceFileWrite` の doc が DRY を理由に明示的に却下している形**）
3. **純追記を外すか。** 参照は「見出しが指す内容」に依存しており、行が**足された**だけで既存の参照が偽になるとは限らない。ただし表への行追加は「トリガーが増えた」ことを意味し、依存側が読み直す価値はありうる
4. **出力量の上限。** 中央 10 件（純追記を外した場合）を全部並べるか、件数 + 上位数件 + 全件を見るコマンドに留めるか
5. **190 ms を毎回払うか。** 編集されたファイルが「そもそも参照の対象になっているか」を先に安く判定して、なっていなければ索引を組まずに抜けられるか
6. `sectionOf`（lib.mjs の共有の口）が本件の節の切り出しに使えるか。プロトタイプは独自の `ANCHOR_LINE` を使ったが、フェンスのマスクを通す `sectionOf` の方が正しい可能性がある

## 敵対的調査（3b）の所見と採否

出力: `workspace/adversarial-1140.txt`（`general-purpose` / sonnet 1 体）

| 争点 | 裁定 | 採否 |
|---|---|---|
| 1. 索引構築は約 190 ms | **壊れた** | **採用**。`makeSnapshot(root)` は**引数 1 個**で、プロトタイプが渡していた `git ls-files` の結果は黙って無視されていた（一次証拠で確認済み）。母集団は walk 由来だが結果は `governance-check` の出力と一致するので**実害は無く、誤っていたのは説明の方**。決定的なのは費用の再定義——**壁時計は 380〜409 ms**（node 起動込み）。node 起動だけで **109〜130 ms**（自分で再実測） |
| 2. 依存節 116・中央 1・最大 19 | **小さく壊れた** | **採用**。前方一致による過大カウントは 121 鍵中 3 鍵（2.5%）。分布は動かない |
| 3. 発火 46% / 25% | **最も強く壊れた** | **採用**。現在の索引を過去へ当てる前方汚染。**別方法（blame 時刻での門）で自分で再測し、全 hunk 46→41%・件数 309→211 が一致**。レビュアが ⚠️ で残した純追記除外版も測った（下表） |
| 4. hooks は scripts を import しない | **壊せなかった** | 4 経路（import / subprocess / 設定 JSON / 文字列）を独立確認 |
| 5. 発火は `.md` 編集だけ | **壊せなかった** | `resolveRefTarget` が必ず `.md` へ解決する構造 |

**機序の裁定**: レビュアの「hook を subprocess 化する案では実質 2 倍」は所見として採るが、根拠は自分で測り直した（node 起動 109〜130 ms + 索引 156 ms）。

### 発火頻度（補正込み・上限と下限の幅で読む）

| 条件 | 発火 | 件数計 | 中央 | 最大 |
|---|---|---|---|---|
| 全 hunk / 補正なし（上限） | 37/80 (46%) | 309 | 3 | 41 |
| 全 hunk / 補正あり（下限） | 33/80 (41%) | 211 | 3 | 29 |
| 純追記を外す / 補正なし（上限） | 20/80 (25%) | 233 | 10 | 31 |
| 純追記を外す / 補正あり（下限） | 19/80 (24%) | 156 | 9 | 21 |

補正は「参照行の blame 時刻がコミット時刻より後なら、その時点に存在しなかったとして数えない」。blame は**最後に触った時刻**なので、書き換えられた古い参照を落とす——ゆえに下限である。

**純追記を外すと発火はほぼ半減する**（41〜46% → 24〜25%）。件数は 26% しか減らないので、**消えるのは小さな発火ばかり**である。

### レビュアが ⚠️ で残し、こちらも未解決のもの

- **フェンスマスク**: プロトタイプの節切り出し（独自 `ANCHOR_LINE`）は `sectionOf` のフェンスマスクを通していない。実チェックが使う `collectAnchors` も通していないので両者は整合するが、`sectionOf` を使った場合に節の範囲が変わるかは未測定 → 計画の未確定欄へ送る
- **射程外の宣言**: 「参照**そのもの**（正準形の記述）が書き換えられた」場合は、対象文書の中身の変化ではないので本件は扱わない
