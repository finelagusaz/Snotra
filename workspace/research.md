# 調査 — #1321 merge:pr の事後検証の待ち

## issue の要約

PR #1313 のマージ（道具の初の実地使用・2026-10-31）で、道具は exit 3 を返した。直後に手で引き直すと、すべて意図どおりだった。

- #1304 の closedAt は mergedAt の +1 秒、#1312 は +3 秒
- `merged:` の検索は PR を返した
- `closed:` の検索は宣言した 2 件だけを返した

原因は、事後検証の待ちが 1 経路にしか掛かっていないことである。

## 関連ファイル・シンボル（実在確認済み）

`scripts/merge-pr.mjs`:

- `SEARCH_RETRIES = [5_000, 10_000]`（:110）。事後検証の待ちと、マージ直後に状態を引き直す前の待ち（:240 の `SEARCH_RETRIES[0]`）の 2 か所で使っている
- 事後検証のブロック（:255〜:296）の並び
  1. **宣言した issue の状態**: `gh issue view` で番号ごとに引く。`CLOSED` でなければ findings に積み、**先へ進む**
  2. **検算**: `merged:>=` の検索に当の PR が現れるか。現れなければ **PostError を投げる**ので、(3) は走らない
  3. **`closed:>=` の検索**: 宣言した同リポジトリの issue が現れるまで、`SEARCH_RETRIES` で待つ（**待ちはここだけ**）

PR #1313 では、1 が #1312 を OPEN と積み、2 が投げ、3 は一度も走らなかった。出力の 2 件はこれと一致する。

`scripts/merge-pr.test.mjs`:

- 「索引の遅延: 宣言した issue が後から現れれば 0」「再試行しても現れなければ 3」は、3 の待ちだけを測っている
- 偽の実行器の `sleep` は no-op で、`issue list` は呼ばれた回数で応答を変えられる（`fake` の関数形）

## 再利用できる既存パターン

- 3 のループの形（`for (attempt) { 引く → 揃えば break → 尽きたら PostError → sleep }`）を、1〜3 をまとめた 1 回分の観測に広げる
- テストの、呼ばれた回数で応答を変える形（`"issue list": (n) => ...`）

## 技術的制約

- 終了コードの意味（0 / 1 / 2 / 3）は変えない
- 待ちは事後検証の中だけに足す。マージ前の検査には待ちを足さない
- 宣言外の close（undeclared）は「待てば揃う」ものではなく所見である。待ちの判定に入れると、宣言外があるたびに再試行が尽きるまで待つことになる。**最後の観測で 1 回だけ判定する**
- `SEARCH_LIMIT` の到達は待っても解消しない。即座に打ち切る（いまどおり）
- 待ちの総量は、マージ 1 回ごとに人が待つ時間になる。今回の実測は close の反映が 3 秒。索引の反映は手で引き直した時点（およそ 30 秒後）には済んでいたが、何秒かかったかは測っていない
