# research — #1070 パスクエリ `c:\` の裾（max / p90）が 1 フレームを超え続ける

## issue の要約

`#1067` は `c:\` の **p50** を支配していた tie-break（`PathStore::cmp_paths`）を実測で名指しし、
PR #1069（整列している範囲を `sorted_prefix_len` として保つ）で p50 を 1 フレーム
（16,700 µs）の内側へ入れて閉じた。**残った裾は未達のまま送られている。**

- 受け入れ条件は `#1067` から**逐語で引き継ぐ数値ゲート**: **実運用点で `c:\` の max が 16,700 µs を下回る**
- 判定条件も引き継ぐ: 実運用点で測る / 同一セッション・同一機・drift 対照つき /
  `\zzz-no-such-path\`・`\program files\`・`users` が退行しない / **検索結果が集合・順序とも 1 件も変わらない**
- **裾の帰属は一度も測られていない。** `#1067` の ablation は p50 の分解であり、しかも #1069 の適用**前**である

## ユーザーの仮説（本サイクルの出発点・2026-08-13 の依頼）

> `c:\` が対象になっているのはインデックスの作成対象に `c:\` 配下が指定されているから。
> ドライブレターが変わっても同じだろうし、`c:\workspace` 配下のみが条件に入っていても、
> パフォーマンスの問題は起きるのではないか。

**この仮説は「支配変数はクエリの字面ではなくマッチ件数である」と言い換えられる。** 実 config の
`[[paths.scan]]` は `C:\`（`extensions = [".txt"]` / `include_folders = true`）を含むので、
索引 312,108 件の**ほぼ全件が `c:\` で始まる**。ゆえに `c:\` は「索引の全件にマッチする最短のクエリ」
であって、`c:\` という文字列に固有の性質は無い。根が `D:\` なら `d:\` が、根が `C:\workspace` なら
`c:\workspace\` が同じ位置に立つ。

**この仮説が確からしいことは、既存の 3 行が既に支持している**（下の実測 §1）。同じ実運用点で

| 行 | マッチ件数 | p50 |
|---|---:|---:|
| `c:\` | 312,208（全件） | 15,484〜15,769 |
| `c:\users` | 96,482 | 11,495〜11,859 |
| `\zzz-no-such-path\` | 0 | 10,353〜10,500 |

**コストはクエリの字面ではなくマッチ件数に対して単調である。**
しかも `str::find` は一致で打ち切るため、**走査そのものは `c:\` のほうが `zzz` より速い**
（`c:\` は各キーの 0 バイト目で当たる）。ゆえに差 5,000 µs は per-hit コストの**下限**である。

**設計上の帰結（本 issue の制約）**: **改修はクエリの字面・ドライブレター・scan 根の形に
一切依存してはならない。** `c:\` を特別扱いする形は、根が変わった瞬間に効かなくなる。

**仮説が言っていないこと**（ここは分けて扱う）: 「根を狭めても改善しない」は**成り立たない**。
コストは `全件走査の床（∝ 索引件数 N）+ マッチ件数に比例する分` の形なので、根を
`C:\workspace` に狭めれば N が減って床ごと下がる。仮説の射程は「**同じ索引規模なら、
どの字面が高いかが変わるだけで問題は消えない**」である。

## 何が裾を作りうるか（候補と、それぞれを名指す測定）

**共通の枠組み**: 1 フレームのコスト = 全件走査の床（マッチ件数に依らず必ず払う）
＋ **マッチ 1 件ごとに払う仕事** × マッチ件数。`c:\` はマッチ件数 = 索引全件なので、
per-hit の仕事が 312,208 倍に増幅されて裾へ出る。候補はすべてこの per-hit 側にある。

### C1: incremental cache 用の全一致 index 収集（`local_matches`）— **最有力**

`search.rs` の rayon fold は、マッチした全エントリについて `local_matches.push(i)` を無条件で
行い、reduce で `a_matches.extend(b_matches)` と併合し、`IncrementalCache::update` へ渡す。
`c:\` では **312,208 個の `usize`（2.4 MiB）** を毎打鍵で組み立てている。

**この収集はパスクエリでは原理的に使われない。** 読み手は `IncrementalCache::can_reuse` ただ
1 つで、その述語に `!plan.has_path_sep` が入っている（`snotra-core/CLAUDE.md`
「incremental cache とパスクエリの非互換」）。次のクエリ `Q'` が再利用するには
`norm(Q').starts_with(norm(Q))` が要り、`norm(Q)` が区切りを含む以上 `Q'` も区切りを含む。

**安全性の論証は正規化の詳細に依存させない形で書く**: 収集をやめると `prev_candidates` が
空になり、`can_reuse` の `!self.prev_candidates.is_empty()` が落ちて**全件走査へ倒れるだけ**である。
全件走査は常に正しい（候補集合の上位集合）。**ゆえに検索結果は集合・順序とも不変**であり、
`¥` や `nucleo_normalize` の挙動を永久に固定する必要が無い。

裾を作る機序として整合する: 16 worker それぞれの `Vec` が倍々で伸びる再確保と、
reduce の木で走る数 MiB の memcpy は、**アロケータの当たり外れが直接コストに乗る**形である。

- **p50 での額**: #1067 の ablation で `M_idx` = **2,821 µs**（ただし **#1069 適用前・p50 の分解**）
- **名指す測定**: 同じ変異（`local_matches.push(i)` を殺す）を #1069 適用後に当て、**max / p90 で読む**。
  2,821 は判断材料にならない
- **射程**: 条件は `plan.has_path_sep` のみ。クエリの字面にも根の形にも依存しない（上の設計制約を満たす）

### C2: top-k の tie 比較（`TopK::push` → `ScoredEntry::cmp`）

`c:\` は**全件が同じ score（`3000 - 0`）で並ぶ**。`push` は満杯の heap に対して
`scored.cmp(&worst)` を必ず 1 回走らせ、score と `last_launched` が同値ゆえ**毎回
`lower_name` の文字列比較まで落ちる**（さらに同値なら `cmp_paths`）。312,208 回である。

`#1067` の `M_topk` は 11,674 µs で、うち `M_cmp`（第 4 キー）が 7,714 だった。**#1069 が
削ったのは後者だけ**なので、残り ≒ 3,900 µs がここに残っている勘定になる（引き算ゆえ推定）。

- **名指す測定**: `top_k.push(scored)` を殺す変異（`M_topk`）を #1069 適用後に当て max で読む
- **注意**: これは**結果を消す変異**であり計器としてしか使えない（製品の候補にはならない）。
  ここが支配項だったとき採れる形は別途要る

### C3: rayon の task 分割の揺れ

`with_min_len(MIN_PAR_CANDIDATES)` と 16 worker の chunk 境界で、worker ごとの `PathCursor` の
鎖が冷える。**署名は「0 件行（`zzz`）も同じだけ動く」こと**——per-hit ではないので `c:\` に
固有には出ない。

- **名指す測定**: baseline の `zzz` 行の裾（max 12,871〜13,590 に対し p50 10,353〜10,500 で
  **+2,400〜3,100**）。**`c:\` の裾（p50 → max で +7,800〜9,500）はこれより明らかに大きい**ので、
  分割の揺れだけでは説明できない。**ただし `zzz` 行の +2,400〜3,100 は `c:\` の裾にも乗っている**

### C4: 他プロセスの割り込み・機体の drift

- **名指す測定**: 同一セッション内の A′ 対照（#1067 の drift 帯は 995 µs = +4.4%）。
  3 回の実行間の揺れ（`c:\` max で 14.7%）はこの帯より大きいので、**drift だけでは
  説明できない**が、**ゲートの判定はこの揺れを織り込んだ形（3 回とも下回る）で書く**

### C5: `result_limit`（**候補ではない・既に却下されている**）

36 構成の掃きで最大の梃子だったが、`docs/adr/ADR-sorted-prefix-over-reflagging.md`「却下 2」が
**機能変更である**（200 行はすべて UI へ渡りスクロールで到達できる）と裁定済み。
**再訪しない。** 本 issue で触れるなら、それはユーザー決定を要する別の話である。

## 再利用できる既存パターン

- **ablation は製品コードに 1 行も残さない**（#1067 の手順）: 変異を 1 つずつ当てて測り
  `git checkout` で戻す。A / A′ の drift 対照を同じ実行で採る
- **結果不変の証明は実 index 全件の突き合わせ**（`sorted_prefix_fast_path_changes_nothing_over_real_index`
  の型）: 集合ではなく `(name, path)` の**列を順序ごと**比べる。件数一致では足りない
- **非空虚検査を持たせる**: 「その経路を 1 回も通らないまま緑」を潰す

## 技術的制約

- **計器（`measure_path_query_frame_cost_at_operating_point`）は変えない。** 変えると
  baseline §1 と比較できなくなる（`fixing-instrument-invalidates-ab-comparison` の型）
- **`index.bin` を書き換えうる。** 製品レベルの計器は `load_or_scan_with_stats` を通る。
  現在は v7 なので昇格は走らない（実測: `%APPDATA%\Snotra\index.bin` 17,323,918 B・2026-08-11）
- **max は 3 回で 14.7% 揺れる。** 1 回の実行を判定に使わない
- **`show_hidden_system` を振らない**（cache-miss で 22〜30 秒の全走査＋ `index.bin` 上書き）
- **`search.rs` の incremental に触るので `can_reuse`（read）と `update`（write）を対で見る**
  （`.claude/rules/snotra-core-search.md`）

## 実測 §2 — 裾の帰属（ablation・2026-08-13・同一機・同一セッション）

変異を 1 つずつ当てて測り `git checkout` で戻した。**製品コードには 1 行も残していない**
（`git status` で確認済み）。同じ計器・同じ実運用点の腕（`substring` + PATH マージ）の
`c:\` 行だけを並べる。単位 µs。

| 変異 | 実行数 | p50 | p90 | p99 | **max** |
|---|---:|---|---|---|---|
| **A**（baseline・§1） | 3 | 15484〜15769 | 17772〜18921 | 20437〜23309 | **21742〜24943** |
| **A′**（変異を戻した drift 対照） | 1 | 15322 | 19143 | 24732 | **26558** |
| **X1** = パスクエリでは `local_matches` を集めない（**C1**） | 3 | **12639〜13688** | **15588〜15946** | 17543〜19298 | **18290〜19992** |
| **X2** = X1 + `top_k.push` も殺す（**C2 の天井**・結果が消える） | 3 | 8792〜9333 | 10661〜11425 | 12310〜15308 | **13080〜17335** |
| **X3** = X1 + candidate index の `Vec` を実体化しない（**C6**） | 2 | 12510〜13550 | 15137〜15437 | 16512〜18377 | 16927〜18991 |
| **X4** = X1 + fold の task 粒度を 24 分割へ（**C3**） | 2 | 12304〜12732 | 14699〜15236 | 16471〜19776 | 17707〜24238 |

**読めること 5 つ。**

1. **p50 は 3% しか揺れないが、max は 4 回の A / A′ で 21,742〜26,558（±20%）揺れる。**
   **受け入れ条件が乗っている統計量が、最も不安定な統計量である。**
2. **C1 は本物である。** p50 −2,000〜−2,900 / p90 −2,200〜−3,300 / max −3,000〜−6,600。
   **p90 は 3 回とも 1 フレームの内側へ入る**（15,588〜15,946 < 16,700）。
   **⚠ 対照行の判定はこのブロックでは確定できない**——baseline を別ブロックで先に取ったため、
   機体の暖まりが A 側だけ有利に働いている（詳細は下の「敵対的調査」命題 6）。
   **確定は計画 Phase 3 の交互測定で行う。**
3. **C1 だけでは max のゲートに届かない**（18,290〜19,992・不足 1,600〜3,300）。
4. **残る支配項は top-k 挿入（C2）である。** X1 → X2 で p50 −3,300〜−4,900 / max −4,000〜−5,500。
   **ただし X2 は結果を消す変異であり、製品案ではない**（→ 下の「C2 に実装形が無い理由」）。
5. **C3 と C6 は測って却下した。** C6（candidate index の `Vec` を作らない）は p50 も max も
   X1 と区別できない。C3（task 粒度を粗く）は min を下げるが**対照行が退行する**
   （`\program files\` の p50 が 10,4xx → 13,743・`zzz` の max が 13,0xx → 15,218）
   ——負荷分散が崩れて裾が伸びる向きである。

### C2 について検討した 3 手はどれも成立しない（コードから導いた・測定ではない）

**「実装形が無い」とは書かない**——それは全称否定であり、**探索した範囲を超えている**
（敵対的調査 命題 3 が壊した）。ここで裁定できるのは、下の 3 手が成立しないことだけである。
**未探索の 2 案**（`select_nth_unstable_by` によるバッチ選択・比較キーを 1 語へ詰める多段比較）は
`ScoredEntry::Ord` を変えないので**結果を保てる形でありうる**が、**未測定**であり、
本サイクルでは踏み込まない（ADR へ再訪条件つきで残す）。

`c:\` は**全件が同じ score（`3000 - 0`）で並び、`last_launched` もほぼ全件 0** なので、
`ScoredEntry::cmp` は**毎回 `lower_name` の比較まで落ちる**。top-200 の中身は
「312,208 件の `lower_name` のうち辞書順で最小の 200 件」そのものであり、
**これは定義上、全件を比較しないと決まらない。**

- **score の下限で枝刈り**（`scored.score < worst_score` で即棄却）— 全件が同点なので発火しない
- **k を小さくする** — `result_limit` は `docs/adr/ADR-sorted-prefix-over-reflagging.md`「却下 2」で
  **機能変更**と裁定済み（200 行はすべて UI へ渡りスクロールで到達できる）
- **tie-break の規則を変える** — 検索結果の順序が変わる＝受け入れ条件「1 件も変わらない」に反する

**ゆえに、本サイクルで検討・実測した手段では「実運用点で `c:\` の max < 16,700」に届かない。**
しかも **X2（C1 + C2 を両方殺し、検索結果が空になる天井）ですら max は 13,080〜17,335 で、
3 回中 1 回は 16,700 を超えている**——**削るものを全部削っても、測定分散だけでゲートを割りうる。**
per-hit コストの削減だけでは足りず、ゲートを額面どおり満たすには測定分散そのもの
（rayon のスケジューリングの揺れ・機体の drift）への対処も要ることになる。
