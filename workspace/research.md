# 調査 — issue #1552

## issue の要約

`/implement`「1a. workspace/plan.md の由来を確かめる」が「機械判定」と呼んでいる 2 つ（未確定ゼロ・承認の形）を、スクリプトにする。

- 判定する関数と CLI を `scripts/` に置き、`npm run plan:check` から呼ぶ
- 呼ぶ場所は 2 つ。`/implement` の Step 1 の入口（破る前に止める）と、`/start-issue`「5c. 承認」で承認を記録した直後（書式の誤りを、書いたその場で見つける）
- 見出しの無い計画が件数ゼロとして通る fail-open の先例がある（#821）。これをテストで再現する
- 範囲外: PR 前ゲートに承認の判定は足さない

## 関連するファイル・シンボル

- `.claude/skills/implement/SKILL.md`
  - 「1a. workspace/plan.md の由来を確かめる」: 同一性・未確定ゼロ（機械判定）・承認（機械判定）の 3 つ。自己承認の追加条件 4 つもここにある。判定の正本はいまこの節にある
  - 「1b. 分岐」: 3 つが立てば Step 2、同一性は立つが未確定ゼロか承認が立たなければ 1c-B
  - 「守ること」: 同一性と承認の行は「散文＋証跡」、未確定ゼロの行は「機構で気づく」（PR 前ゲート）
  - frontmatter の `allowed-tools` に `Bash(npm *)` がある
- `.claude/skills/start-issue/SKILL.md`
  - 「5c. 承認」: 人間承認・自己承認の行の形。末尾の段落に「`/implement`「1a」は、この記録が計画の他の記録と矛盾しないことを機械で確かめる（照合する記録の正本は 1a である）」とある
  - 「Step 4」: 未確定欄と承認欄の雛形（コードフェンスの中に `## 未確定（実装前に潰す）` と `## 承認` がある）
  - frontmatter の `allowed-tools` は `Bash(git *)`・`Bash(gh *)` だけで、npm が無い
- `package.json` の `scripts`: node のツールは `node scripts/<name>.mjs` の形（`prose:sweep`・`merge:pr`・`race:boundaries`・`verify:tree`）
- `docs/build-commands.md`: ツールの npm script の一覧（`race:boundaries`・`prose:sweep`・`merge:pr` の行があるフェンス）と、ツールごとの注意の箇条
- `scripts/governance/checks/G-build-commands.mjs`: `docs/build-commands.md` に書いた npm script の実在を照合する
- `.claude/hooks/pre-bash.mjs` の `countUnchecked`: ファイル全体の `- [ ]` を数える（PR 前ゲート）。節に限る数え方とは別物

## 再利用できる既存のパターン

- ツールの形: `scripts/race-boundaries.mjs`・`scripts/prose-sweep.mjs`・`scripts/merge-pr.mjs`。冒頭に契約（終了コード・SSOT）を書き、shebang を置かない（CRLF 化で vitest が落ちる・PR #592）。純関数を export し、`scripts/<name>.test.mjs` が vitest で検証する
- 終了コード: 使用法の誤りは exit 2、判定の結果は 0 / 1（`merge-pr.mjs`・`prose-sweep.mjs` と同じ分け方）
- 理由を全件出す: `merge-pr.mjs` の exit 1 は止めた理由を全件並べる

## 技術的な制約

- 判定は 1a の文言に一致させる（いまの正本は 1a。移したあとはスクリプトが正本になる）
  - 未確定ゼロ: `## 未確定（実装前に潰す）` で始まる見出し行が存在し、その節（次の同レベル見出しまで）に `- [ ]` が無い。見出しが無ければ不成立
  - 承認: `## 承認` 見出しがあり、その節に人間承認の行（`- [x] 承認済み — <日付> / 問い: "…" / 回答: "…"`）か自己承認の行（`- [x] 自己承認 — <日付> / 仕様変更: なし — … / 戻せない変更: なし — … / 人の裁定: なし`）が 1 件ある
  - 自己承認の追加条件: 3 項目がすべて「なし」／未確定欄に「（裁定）」の印の付いた項目が無い／`## 変更するファイル` で始まる見出しの節があり、その節に `SPEC.md` が無い／`## セルフレビュー` に「check スキル」の行があり、その行に `/persistence-check` が無い（節や行が無ければ不成立）
- 計画はコードフェンスを含みうる（雛形を引用すると、フェンスの中に `## 承認` などが現れる）。フェンスの中の行を見出しや項目として数えると、判定が誤る
- `/start-issue` の `allowed-tools` に npm が無い。呼ぶなら足す
- 同一性は判断が要るので、スクリプトにしない（散文に残す）
- これはセーフティネット（`.claude/skills/**`・`scripts/**`）の変更である。マージはユーザーと合意してから

## 敵対的調査（3b）の採否

出典: `workspace/adversarial-1552.txt`。委譲先は `git log --all -- workspace/plan.md` の 831 版を試作の判定器で測った。

- F1 採る — `## 変更するファイル` の節で `SPEC.md` を部分文字列で探すと、#1524 の計画（`f7526bba` ほか 3 版）の散文の行「`SPEC.md` は変えない。」で誤って不成立になる（`git show f7526bba:workspace/plan.md` で確かめた）。数えるのは、節の中のリスト項目（`-`・`*`・`1.`）のうち、最初のコードスパンが `SPEC.md` の行だけにする
- F2 採る — `## 承認時の前提（明示する）` のような見出しがある。承認節は、レベル 2 で `承認` と完全に一致する見出し（末尾の空白は許す）だけにする。未確定欄は 1a のとおり、レベル 2 の前方一致（`## 未確定（実装前に潰す）— ラウンド N` が実在する）
- F3 採る — 未チェックの数え方を PR 前ゲート（`.claude/hooks/pre-bash.mjs` の `countUnchecked` の正規表現。行頭・字下げ可・`-`/`*`）にそろえる。行の途中の「`- [ ]`」という言及は数えない
- F4 採る — 判定の正本を指し合っている（1a は「正本は 5c」、5c は「正本は 1a」）。判定の述語を持つ散文は、implement の 1a・1b の表・1c-B・「守ること」、start-issue の 5c 末尾・Step 6・引き渡し契約にある。スクリプトを判定の正本にし、これらはスクリプトの結果を指す形へ直す（行の形の定義は 5c に残す）
- U1 一部採る — `allowed-tools` は事前許可の列で、制限ではないと読める（`docs/superpowers/specs/2026-07-26-skill-workflow-boundary-design.md` の F4）。足すのは無害なので、`/start-issue` に `Bash(npm run plan:check *)` を足すが、「足さないと動かない」とは書かない
- U2 採る（fail-closed のまま） — 「check スキル」の行の `/persistence-check` は部分文字列で見る。否定文で書かれても不成立になるが、文言で「行から外す」と案内する。実データでは 0 件
- U3 採る — 「（裁定）」は、未確定欄のリスト項目でチェックボックスの直後に置いた印だけを数える（start-issue Step 4「行頭に印を付ける」）。本文中の言及は数えない

壊せなかった項目（G-build-commands が文書の npm script の実在を照合すること、フェンスの中の見出しは歴史上 0 件であること、承認行の記号が 110 版で一貫していること、「で始まる」と節の境界）は、本文の記述のまま。フェンスへの対応は、雛形を引用する今後の計画のためにテストで担保する。
