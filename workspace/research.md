# 調査: コードコメントを要点中心に簡潔化する（issue #1185）

## issue の要約

コードコメントを**減らす**のではなく、**現在のコードを理解・変更するために必要な情報へ圧縮する**。
証拠（実測値）・歴史（事故史）・却下案の詳細は、それぞれの正本（`PERFORMANCE.md` / issue・
`RETROSPECTIVE.md` / ADR・`docs/`）へ分離する。

完了条件は 6 つ。規約（`docs/comment-guidelines.md`）の改訂 3 件、既存コメントの整理 1 件、
失われていないことのレビュー 1 件、既存ルールから参照できる状態にする 1 件。

非目標: 行数の機械的削減・hard limit の導入・一括書き直し・知見そのものを捨てること。

## 技術的制約（実測）

### 1. 規約は既に「短く」を部分的に持っており、既存コメントがそれに違反している

`rustdoc の様式`: **「`//!` はモジュール冒頭の責務宣言: モジュールの役割と設計方針を数行で」**。
`index_tree.rs` の `//!` は **35 行**。つまり完了条件の一部は**新しい基準の追加ではなく既存基準の
適用**である。新基準を足す前に、既存基準がどこまで届いているかを見る必要がある。

### 2. 削ると規約自身の根拠が消えるコメントが対象内に在る

`docs/comment-guidelines.md` は `IndexTree::file_key_into` の doc を**模範例として名指している**
（「頻度は数を添えられないなら根拠に使わない」の唯一の実例。「実データで根は約 200 件（0.06%）」）。
このシンボルは **`index_tree.rs`＝整理対象ファイル**に在る。

**同型の事故が既に 2 回起きている**——規約が名指した模範例が消えた形（`Engine::new_from_cache` を
#984 が削除／test fixture が #996 で対象ごと消滅）。**どちらも機構は緑だった。**

⇒ **シンボルごとに「外から名指されていないか」を先に測る手順が計画に要る。**

### 3. 外からの名指しの母集団（実測）

対象 6 シンボルはすべて `PERFORMANCE.md` と `snotra-core/CLAUDE.md` から名指されている。
`CachedMasks` はさらに ADR 2 本・`persistence-check` スキルからも。

`snotra-core/CLAUDE.md:10` は**全モジュール一括で** `//!` を責務の正本に指名している
（「各モジュールの責務宣言は各ファイルの `//!`（module doc）を正本とする」）。
⇒ **`//!` の圧縮では責務宣言そのものを残さねばならない**（削れるのは責務以外の層）。

### 4. 機械検査の射程（どこまでが緑で守られるか）

| 機構 | 対象 3 ファイルへの射程 | 実測 |
|---|---|---|
| G-heading-refs | **及ぶ**——`headingRefSourceDocs` は `f.endsWith(".rs")` で**全 `.rs`** を走査元にし、対象 3 ファイルには正準形の見出し参照が **19 件**在る（indexer 11 / index_tree 4 / build 4） | ripgrep とリテラル grep の 2 方法が一致 |
| G-stale-identifiers | **及ばない**（走査元は `.claude/{skills,rules,agents}/*.md` と `docs/**.md`＋固定 4 パス。`.rs` は入らない） | `staleIdentifierDocs` / `staleIdentifierGuideDocs` / `STALE_EXTRA_DOCS` を読んだ |
| `cargo doc`（intra-doc link） | **及ぶ**（`broken_intra_doc_links` が deny・**CI でのみ発火**） | 規約と `docs/build-commands.md` |

⇒ **コメント内の「参照先の実在」は G-heading-refs が守っている。** 一方で「規約の模範例が
消えた」「正本の宣言が消えた」は**どの機構も見ない**——`G-stale-identifiers` が見るのは
識別子が現行語彙に在るかだけなので、**関数名が残れば doc の中身が変わっても緑**である
（敵対枠の実測）。過去 2 事故（名指し対象が消えた形）より、**対象は残るが中身が変わる形の
ほうが無防備**である。

⚠ **この行を測るとき計器が壊れた。** bash の `grep -E` に日本語を含む**否定文字クラス**
（`[^`]` / `[^」]`）を渡すと、多バイト文字に対してバイト単位で動き**一致が静かに 0 件になる**。
初稿はこれで「0 件・G-heading-refs は及ばない」と書いていた。既知の `awk length` のバイト
問題と同族だが、**こちらは長さではなく一致そのものが落ちる**。リテラル照合と ripgrep の
2 方法で裁定した。

⇒ **ただし `docs/comment-guidelines.md` 自身は G-stale-identifiers の走査元に入る**——規約へ
書く識別子は実在が照合される。

### 5. 機械検査を足す案は既に却下されている

`ADR-comment-guideline-delivery-by-pointer` の「却下 3: 行またぎコードスパンの検知器」
「**却下 4: 散文の数え上げを検出する検知器**」。issue の非目標（hard limit を導入しない）とも
一致する。⇒ **本件で `governance:check` へ検査を新設しない。**

### 6. 規約自身が肥大の実例である

「第一原則」の「書かないもの」の 1 箇条が入れ子の下位箇条を伴って約 15 行あり、条項自身の
腐敗史（#977 / #984 / #989 / #732）を本文に抱えている。**issue が問題としている形が、規約本文に
そのまま現れている。** 完了条件 1「短く保つ基準を追加する」を素直に実施すると**さらに伸びる**。

### 7. 規約と issue が正面から衝突する条項が 3 つある

| 箇所 | 現在の文言 |
|---|---|
| 第一原則「書く価値があるもの」 | **過去の事故**（実測値・再現条件・issue 番号つきの経緯） |
| 歴史メモの様式 | **設計判断・事故の記録は長くてよい** |
| rustdoc の様式 | **長さ自体は問題ではない**（→「歴史メモの様式」） |

⇒ 改訂の中心はこの 3 つ。**判定基準そのもの**（「この情報が消えたら、将来の変更者が同じ失敗を
繰り返すか？」）は issue と矛盾しないので**残す**。変えるのは**証拠の置き場**である。

## 未解決の疑問

1. **「現在の設計判断を支えている値」の判定をどう書くか。** ハイブリッド方針の分水嶺であり、
   実装者が追加判断せず実行できる粒度で計画に書く必要がある
2. **`PERFORMANCE.md` へ着地させる値の出所が既に失われている場合の扱い**（#1032 の 40〜95 ms が
   その形）。ハイブリッドなら「支えていない」側へ倒れるはずだが、境界の実例で確かめる
3. **規約の肥大をこの PR で扱うか**。制約 6 は issue の射程外に見えるが、完了条件 1 を満たすと
   悪化する。「足す」ではなく「置き換える」形にできるか
4. ~~`.claude/rules/comments.md` が router のみである以上、完了条件 6 は既に満たされている
   可能性がある~~ → **解消。** router はポインタのみで 5 節を正準形で名指しており、完了条件 6 は
   **ほぼ満たされている**。残る作業は、改訂で節名を変えたときに router 側を同時に直すことだけ
   （G-heading-refs が捕まえる）
5. **正本候補どうしが既に食い違っている場合の扱い**（敵対枠が 2 件発見・下記）。ハイブリッド
   方針は「コード側の値を `PERFORMANCE.md` へ寄せる」を前提にするが、両方に**違う値**が在る
   ケースを想定していない

### 採らなかった所見（事実部分の誤り）

**P1 の事実主張「対象 3 ファイルには正準形参照が現状 0 件」は偽である。** 敵対枠は
**私が故障と診断したのと同じ bash の否定文字クラスのパターン**を使っており、故障を継承した。
リテラル照合と ripgrep の 2 方法がともに **19 件**を返す（上の制約 4）。

**ただし P1 の結論（`.rs` は構造的に除外されていない）は正しく、採用した。**
——`AGENTS.md`「検証の作法（全タスク共通）」の「所見が正しくても機序の説明は独立に誤りうる」
の逆向きの形である: **事実が誤っていても結論が正しいことがある。** 採ったのは結論であって
数え上げではない。
