=== M-2 [Medium] helper 化で新設された誤用経路 — 字下げアンカーが #1108 の欠陥を沈黙で再生する ===

場所: src-tauri/src/indexing.rs:200-226（top_level_fn_body）

根本原因: 終端を「列 0 の }」に定めたのに、**アンカーが列 0 で始まることを誰も検査しない**。
字下げされたアンカー（たとえば mod tests 内の関数）を渡すと、最初に見つかる列 0 の } は
mod tests 自身の閉じ括弧（EOF 直前）になり、母集団が assert リテラルを飲み込む。
terminated は true になるので assert(terminated) は発火しない。

実測（scratchpad/anchorprobe.rs — 実ファイル src-tauri/src/indexing.rs を include_str!）:
  anchor = "fn top_level_fn_body_is_line_ending_agnostic("（字下げ・mod tests 内）
  -> terminated=true で通過。母集団 = 3225 bytes
  -> 母集団は mod tests の assert リテラルを飲み込んだか:
       try_begin_index_build( = true / invalidate_icon_cache( = true
つまり #1108 が塞いだはずの「探す 2 文字列が必ず真になる」状態が、helper の引数経由で
そのまま構築できる。旧インライン実装にはこの affordance が無かった（母集団の切り出しが
呼び出し側に無かったため）。helper 化が新たに開けた面である。

同じ節に束ねる: **assert(terminated) 自身に恒久的な検知器が無い。** 受け入れ条件 2
（終端が見つからなければ赤くなる）を測る回帰テストが差分に無い。plan.md Phase 2 の
TDD は使い捨ての find("\n}\n") 実装に対して 1 回発火させただけで、**今この行を消しても
すべて緑である**（M1a/M3/M4 のどれも terminated 側を通らない — 私の probe でも
発火したのは canary と invalidate_icon_cache の assert だけだった）。
なお indexing.rs 単体では terminated=false は実質到達不能である（mod tests の閉じ括弧が
必ず列 0 にあるため）。だからこそ fixture で測るしかない。

修正例（どちらも #[cfg(test)] 内で閉じる。production は触らない）:
  (1) アンカーの列を検査する
      let (before, after) = src
          .split_once(anchor)
          .unwrap_or_else(|| panic!("{anchor} が見つからない（改名したらこの検査も直す）"));
      assert!(
          before.is_empty() || before.ends_with(0xA as char),
          "{anchor} が列 0 で始まっていない——この helper の終端（列 0 の `}}`）は
           トップレベル関数を前提とする"
      );
      副産物: アンカー文字列が doc コメント等でより手前に現れた場合も赤になる。
  (2) #[should_panic(expected = ...)] の fixture を 2 本足す
      - 終端なし: "pub fn target() {\n    marker();\n"      -> assert(terminated) が発火
      - 字下げアンカー: "mod m {\n    fn target() {\n        marker();\n    }\n}\n"
        + anchor "fn target(" -> (1) を入れれば発火

偽にする手順: top_level_fn_body に anchor = "fn top_level_fn_body_is_line_ending_agnostic("
（字下げされたアンカー）と canary = "let lf =" を与えて実ファイル src-tauri/src/indexing.rs を
食わせ、terminated=false で落ちるか、あるいは返った母集団が "try_begin_index_build(" と
"invalidate_icon_cache(" のどちらも含まないなら、私の指摘は誤り。

## R2-4 [Low・回答] before.ends_with(LF) は意図した集合を過不足なく切るか（ご質問 2）
--------------------------------------------------------------------------

結論: **現行の呼び出しに対しては過不足ない。** 実装上の残余が 2 方向あり、どちらも
今日は無害だが、性格が違うので分けて書く。

(A) 誤って落ちる側 — BOM。**実測した。**
  scratchpad/bom で測ったところ `include_str!` は BOM を**保持する**
  （先頭 4 バイト = [239, 187, 191, 112]）。アンカーがファイル先頭にある BOM 付きファイルでは
  before = "\u{feff}" となり、is_empty=false / ends_with(LF)=false で**誤発火する**。
  ただし現状は無害である: (1) 追跡下の *.rs 全件を走査して BOM は **0 件**、

  belt-and-braces を望むなら before.trim_start_matches("\u{feff}").is_empty() で覆える。
  **今の差分の欠陥ではないので修正を求めない**（記録として置く）。

(B) 誤って通る側 — assert が切るのは「行頭か」であって「宣言か」ではない。
  列 0 から始まる行なら、それが /* */ ブロックコメントの中でも raw string の中でも通る。

    pub fn start_index_build(app) — 旧実装のメモ

  この場合 before は LF で終わるので assert は黙り、母集団がコメントから始まる。

doc の主張の検算: 「（doc 中にアンカー文字列が先行出現した場合もここで落ちる）」は
**真である** —— /// ・//! ・// のいずれもスラッシュが行頭を占めるので、アンカーが
列 0 に来ることはありえない。上の (B) はブロックコメントと raw string の話であって
doc コメントの話ではないので、この括弧書きは実装より強くない。

   期待する字下げ、そして**アンカー述語の形**である——列 0 側は「行頭に何も無いこと」を、
