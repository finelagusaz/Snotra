### 4.6 #900 への含意

**5 年後の #900 の `clippy.toml` を脅かすのは「誰も触らないうちに腐る」ではなく、次の 2 つである。**

1. **#894 型の淘汰。** 判定基準は「捕捉実績」と「保守費」。#900 の予想捕捉は
   「`ctx.set_visuals` へ戻す変更」であり、それは 11 日で 1 回起きた種類の事故なので
   `G-config-reachability`（捕捉 0）よりは分が良い。**だが淘汰の決め手は捕捉 0 だけではなく
   「検査が固定した表自身が腐る」だった**——#900 の 9 件表は egui 0.35.0 の API 表面へ固定した表であり、
   **同じ形をしている**（→ 要-H2）。
2. **`G-workspace-lints` が射程外と宣言した領域に落ちること。** `git blame -L 290,320 scripts/governance-check.mjs`
   → **:290〜:320 は全行 `ca8afae`（誕生時）**。すなわち clippy カテゴリの除外は**後から狭められたのではなく
   生まれつき**で、その理由は逐語でこうである:
   > 見るのは `rustdoc` カテゴリだけである。`[workspace.lints.clippy]` 等が降格されてもこの検査は鳴らない
   > （**clippy は `cargo clippy ... -- -D warnings` がコマンドライン側で昇格させており、workspace テーブルが担っていない**）。

   **この除外理由は #900 には当たらない。** `disallowed-methods` は lint レベルではなく設定値であり、
   **`-D warnings` は解決に失敗したパスを昇格させない**（`research.md` 測定 7 / レビュー §5-R1 の実測: EXIT=0）。
   つまり #900 は、**既存の唯一の lint 実効性検査が「担われている」と明示的に想定して除外した領域の外に、
   新しい lint ガバナンス面を 1 枚増やす**（→ 要-H1）。

## 計画を変えるべき発見

### 要-H1 ⚠ **R8 / 未確定 2 の「clippy.toml の生存に検知手段は無い＝受容残余」は、この repo の先例と正面から食い違う**

`plan.md` は 3 か所で `clippy.toml` 自身の生存を受容残余に置く（不変条件表・沈黙経路・未確定 2）。
だが歴史は次を示す:

1. **同じ失敗クラスは一度実現している**（#706・4.3）。「lint 設定が特定 crate に黙って適用されない」形で、
   実害つきで、CI 緑のまま。
2. **repo はそれを受容しなかった**——`G-workspace-lints` + members カナリアを置いた（`ca8afae` / `de06e58`）。
3. **その回の振り返りが規則を明文化している**: 「**カナリアで守るのは沈黙する経路だけでよい**」（`fd5826e`）。
   #900 の要-3 は沈黙経路が**2 本**あることを実測している——規則の適用対象そのものである。
4. **既存の唯一の lint 実効性検査は、#900 の領域を「clippy はコマンドラインが担っている」という理由で
   生まれつき射程外にしている**（`ca8afae` の :303-305・4.6-2）。**その理由は `disallowed-methods` には当たらない。**

**ただし #706 と #900 は失敗の機序が違い、その違いがそのまま「何が覆えて何が覆えないか」を決める。**
#706 の沈黙は**追跡された manifest の opt-in 欠落**——members × テーブル位置という**列挙できる述語**だったので、
`G-workspace-lints` は 6 形すべてを故障注入できた。#900 の沈黙は**文字列が解決しなくなること**で、
解決を判定できるのは clippy だけである。ゆえに沈黙経路 3 本を並べると、**覆える経路と覆えない経路が分かれる**:

| 沈黙経路（要-3 / R8 の実測） | 最安の検知手段 | 覆うか |
|---|---|---|
| `clippy.toml` の消失・`disallowed-methods` の空配列化（**R8**） | `governance-check.test.mjs` に `de06e58` 型のカナリア 1 本（実ファイルを fail-closed で読み、9 件以上あることを固定し、失敗メッセージが更新先を名指しする） | **○**（Rust のパス解決を要しない。ファイルの存在と件数だけ） |
| メソッド名・型名の書き損じ（**要-3a**・`-D warnings` 下でも EXIT=0） | CI で clippy の stderr を `does not refer to a reachable function` で grep して落とす（**独立レビュー §5-R1 が既に名指ししている手**） | **○**（ただし CI の配線が 1 本増える） |
| crate 名の書き損じ・egui 依存の消滅（**要-3b**・**診断そのものが出ない**） | どちらも覆わない。**Phase 2 の 9 件注入を打ち直すことだけが検知点である** | **×** → **要-H2** |

**ゆえに主張はこう分かれる**——「カナリアを置けば沈黙経路が塞がる」は**偽**である（最悪の 1 本が残る）。
だが**現在の計画は R8 を「誰にも止められない」として受容しており、その 1 本は最安の型で実際に覆える**。
そして残る要-3b は、計画の外にある別の手（要-H2）でしか覆えない。

**私は「G 検査を 1 本足せ」とは主張しない**——#894 の淘汰基準（捕捉 0 の検査は保守費で負ける）は
新設 G 検査に不利であり、それも歴史の事実である。**求めるのは 2 つだけ**:

- (a) **R8 に対する `de06e58` 型のカナリア案を、却下した代替案として明示的に評価すること**（採否は問わない）。
  現在の未確定 2 が却下しているのは「`safety-nets.md` の `paths` へ足すか」だけで、**カナリア案は検討されていない**。
  評価にあたっては上表のとおり **「これは R8 しか覆わない」ことを前提に置くこと**——
  「沈黙経路が塞がる」と読んで採ると、`4f13054` の「範囲の過大評価がそのまま判断の入力になる」を踏む。
- (b) 置かないと決めるなら、**#706 / #820 の先例から離れる理由を `clippy.toml` のコメントに 1 文で残すこと**。

### 要-H2 ⚠ **egui のバージョンを動かしたとき 9 件表を測り直せ、と言う面がどこにも無い**

- `Cargo.toml:11` は **`egui = "=0.35.0"`（完全一致ピン）**。設定は `b59f1fe`（2026-07-22）の 1 回だけで、
  **この repo に egui のバージョン更新の歴史は 0 件**（`git log -L` で当該行を追跡・実測）。
  つまり 9 件表は **API 変更に対して一度も曝されたことがない**。
- 完全一致ピンゆえ `cargo update` では動かず、**バージョン更新は人が `Cargo.toml` を書き換える操作**になる。
- `/deps-update` の SKILL.md は「clippy 警告・型エラー・軽い API 追従はこのスキルで直す」と言うが、
  **解決しなくなったパスは警告でも型エラーでもない**（要-3 の実測: `-D warnings` 下で EXIT=0、
  crate 名側なら診断ゼロ）。**このスキルは原理的に捕まえられない。**
- `plan.md` の「触らない」は `docs/build-commands.md` と `.claude/rules/safety-nets.md` を除外し、
  未確定 2 が rules の `paths` を却下した。**結果として、egui を上げる人へ再測定を告げる面が repo に 1 枚も無い。**
- **これは `G-config-reachability` を殺した機序そのものである**（#894 逐語: 「検査が固定した表自身が
  実装に追随せず腐った」・#819）。**番人が番される側に回る**形。
- 先例のある最安の形は `AGENTS.md` 条件別チェックの
  「撤去条件を**その成果物自身の doc へ書く**」（#872 の `repro-pester-flake.ps1` の `.NOTES` が実際に撤去を駆動した）。
  → **`clippy.toml` のコメントに「egui のピンを動かしたら Phase 2 の 9 件注入を打ち直す。
  パスが解決しなくなっても CI は緑である」を 1 行**。計画は既にこのコメントを「判断の正本」と定めているので、
  置き場所は増えない。

### 要-H3 ⚠ **`reason` が `#[allow]` を名指しする点だけを落とす（条件つき文言そのものは維持してよい）**

**これは 要-2 と競合しない。** 要-2 が求めているのは **条件つきの枠づけ**
（「使ってはならない」ではなく「**callback 内からは当該 pass に届かない**」）であり、
それは `EguiView::setup` という欠陥を持たない地点が構造として在ることの正しい反映である。
私が落とせと言うのは **「逃げ道の名指し」1 点だけ**で、条件つき枠づけには触れない。

`plan.md` Phase 1 の当該文:

> 条件つき文言なら回避が要るときに **`#[allow]` + 理由コメントという正しい逃げ道が診断から読める**。

repo の実測（`30bbf1d` / #775・5.2）が有害と記録したのは、まさに**この形**である——
一般論としての「条件つき文言」ではなく、**「どの経路なら検出されないか」を診断文に書くこと**:

> **要件ではなく検出範囲を教えると、読者は検出範囲を最適化する。**
> 具体例は「`\` はこの hook の**別判定**に当たります」という付記で、これは
> 「**別判定に当たらない `\` を選べばよい**」という読み方を作った。**削除して要件そのものを書く形に変えた**。

**切り分け**（否定の知識を捨てずに衝突を解く）:

- **`clippy.toml` のファイル冒頭コメント**に 否定の知識（含めなかった 4 群・`options_mut` の素通り・
  沈黙経路・R7 の遮蔽・`#[allow]` で抜けられること）を残すのは**維持**。
  これは実装者・保守者が読む面であり、repo は `ADR-*` でこの種の記録を強く支持している。
- **`reason` 文字列**（＝**違反者が診断として読む面**）は、**条件つき枠づけのまま、`#[allow]` の名指しを落とす**。
  例: 「root `Ui` が pass 冒頭で `Arc<Style>` を掴むため、**`run_ui` の中では** `ui.visuals_mut()` を使う（#751 / PR #901）」。
  「`run_ui` の中では」が要-2 の求める条件つきを保ち、`setup` からの正当な書き込みを排除しない。
- **`#[allow]` の案内を落としても失うものは無い**——clippy 自身が help 行で
  `to override -D warnings add #[allow(clippy::disallowed_methods)]` を出す（独立レビュー §5-R3 の実測）。
  repo 側で重ねる必要が無く、重ねた分だけ #775 の形に近づく。
