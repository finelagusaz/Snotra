2. L-1 の修正は過剰に剥がしていないか（実リポジトリでの実測）
=============================================================

修正後の述語:

    const stripLead = (line) => line.replace(/^\s*(?:(?:\/\/[!/]?|#|\*|>|-)\s*)*/, "");

繰り返し群の**内側**へ `\s*` を入れたので、`> - 「` / `/// - 「` のように記号が
空白で隔たる形も剥がせるようになった。過剰かどうかを 2 方向で測った。

2.1 走査母集団の全行で、新旧の読みを突き合わせる
------------------------------------------------
判定に効くのは「剥がした結果が `「` で始まるか」という述語だけなので、そこを見た。

    走査母集団        : 260 ファイル
    走査行数          : 65,199 行
    剥がし結果が違う行: 3,251 行
    **述語（`「` で始まるか）が反転する行: 52 行**

反転する 52 行はすべて同じ形である——**`- **「…` / `> **「…` のように、箇条書きや
引用の記号の後に強調（`**`）が来て、その内側が `「` で始まる行**。旧述語は `- ` まで
しか剥がせず「`「` で始まらない」と読み、新述語は `- **` まで剥がして「始まる」と読む。
所在は `docs/development-principles.md`・`.claude/rules/safety-nets.md`・`AGENTS.md`・
`CLAUDE.md`・`docs/comment-guidelines.md`・各 SKILL.md など、規範文書に集中している。

2.2 それが実際に偽陽性になるか（必要条件の突き合わせ）
------------------------------------------------------
偽陽性の必要条件は「**形 A の候補行（対象綴りで終わる行）の直後**が、新述語でだけ
`「` 始まりと読まれる行であること」。両方を数えて交差を取った。

    形 A の候補行                      : **21 件**（evidence の「折れうる位置 21 件」と一致）
    述語が反転する行                    : 52 件
    **そのうち候補行の直後に在るもの    : 0 件**  ← 新たな偽陽性は **0 件**

候補行 21 件の直後行を全件目視した（すべて `old=false new=false`）。内訳は
空行 6 件、`- ` で始まる普通の箇条書き 13 件、`3. ` 等の番号付き 2 件で、
`「` で始まるものは新旧どちらの読みでも 1 件も無い。

2.3 合成の敵対ケース（構造的に剥がしすぎないか）
------------------------------------------------
実リポジトリに今日在るかどうかと独立に、剥がしすぎで壊れうる形を 13 件当てた。

    OK  期待 0 / 実測 0  表の区切り行 `|---|---|`
    OK  期待 0 / 実測 0  表の行（`「` を含むセル）
    OK  期待 0 / 実測 0  水平線 `---`
    OK  期待 0 / 実測 0  setext 下線 `===`
    OK  期待 0 / 実測 0  本文が `-` で始まる散文（`「` でない）
    OK  期待 0 / 実測 0  `-- 通常の本文`（既存の負例テストと同じ形）
    OK  期待 1 / 実測 1  箇条書き + 強調で始まる `「`（**新たに拾う形**）
    OK  期待 1 / 実測 1  blockquote + 箇条書き `> - 「`
    OK  期待 1 / 実測 1  rustdoc + 箇条書き `/// - 「`
    OK  期待 0 / 実測 0  コードフェンス内（`.md` の走査が落とす）
    OK  期待 0 / 実測 0  非コメント行（`.mjs` の走査が落とす）
    OK  期待 0 / 実測 0  空行が挟まる
    OK  期待 0 / 実測 0  `*/` で閉じる行
    期待と食い違い: 0 件

表の区切り行が無事なのは `|` が剥がし対象に入っていないためで、水平線・setext は
剥がした後に `「` が残らないためである。**構造的な剥がしすぎは見つからなかった。**

2.4 判定
--------
**過剰剥がしは今日 0 件。ただし「安全」ではない、という指摘は正しい。**
リスクの所在を名指しておく:

  反転した 52 行と、形 A の候補行 21 件は**同じファイルに同居している**
  （少なくとも `AGENTS.md`・`.claude/rules/safety-nets.md`・
  `docs/development-principles.md` の 3 枚）。とくに `AGENTS.md:13-17` は
  **各項が `` `<path>.md` `` で終わる箇条書き**であり、同じリストへ
  `- **「…」** …` の項を 1 つ足せば、その瞬間に赤が出る。

  ただし**この偽陽性クラスは今回の修正が新設したものではない**。旧述語でも
  `- 「…」ではない項目` は赤になり、既存テストがそれを**負例ではなく期待動作として
  固定している**（`"行頭記号の落としすぎを起こさない"` の `toHaveLength(1)`）。
  修正が広げたのは同じクラスの適用範囲（`- 「` → `- **「`）であって、
  新しい失敗の種類ではない。**沈黙側の誤りを塞ぐために騒音側のクラスを少し広げた**
  という設計判断であり、commit message の「見逃しは沈黙側なので塞ぐ側へ倒す」と
  整合している。所見としては挙げるが、修正を求めない。
