### 所見（Info、問題ではなく確認事項）
- **`[index-load]` 出力のバイト不変性**: 確認した。フォーマット文字列リテラルは無変更
  （`"[index-load] cache_hit={} total={}ms hash={}ms cache_load={}ms scan={}ms sort={}ms cache_save={}ms"`）。
  変わったのは埋め込み式のみ（`s.hash_ms` → `s.hash.as_millis()` 等）で、`u128` の値と
  `Duration::as_millis()` の値は同じ丸め（生成時に既に ms 精度だった #1027 以前と異なり、
  今回は ns 精度の Duration を表示時に `as_millis()` で切り捨てる）。**出力される数値自体は
  ロード処理の実測時間に依存するため diff からは「表示形式が同一」しか保証できないが、
  s.total.as_millis() は変更前から Duration のままだったため式の形は一貫している。** 実際に
  `cargo run` して行を確認してはいないが、コード上の保証（フォーマット文字列不変・式が単に
  `.as_millis()` を後付けしただけ）で十分と判断する。⚠️ 実機での目視確認はしていない
  （カテゴリ D 非該当と判定したため）。
- **`tests/memory_footprint.rs` の残余算式**: `cache_save_is_internal = s.cache_hit` は変更前と同一の
  述語（変更なし）。`attributed` の組み立ては
  `s.hash + s.cache_load + s.scan + s.sort + if cache_save_is_internal { Duration::ZERO } else { s.cache_save }`
  で、旧版の `saturating_sub` の被減数の組み立て（`s.hash_ms + s.cache_load_ms + s.scan_ms + s.sort_ms
  + if ... { 0 } else { s.cache_save_ms }`）と同型——除外の条件・対象は完全に一致。**唯一の違いは
  丸めのタイミング**（旧: 各フェーズをそれぞれ ms に丸めてから整数和 → 整数引き算 saturating_sub、
  新: Duration のまま ns 精度で和 → 引き算 → 1 回だけ ms に丸め、符号つき f64）。commit message の
  主張（残余が旧は丸め屑を吸っていた・新は符号つきで負が見える）は算式を読んで妥当と確認した。
  `delta_ms` の実装 `(total.as_nanos() as f64 - attributed.as_nanos() as f64) / 1_000_000.0` は
  doc の主張（ns→f64 ms 変換、符号を保持）どおり。
- **`upgrade_save: Option<Duration>` の Some/None 生成点**: grep で確認、3 箇所すべて変更前と同じ
  分岐に位置する。
  1. `upgrade_legacy_cache_in` 内: `let upgrade_save = Some(save_started.elapsed());` （Some を作る
     唯一の行、doc の主張どおり）

     そのまま返す（1 の Some を経由）
  3. `finish_legacy_read` の `LegacyUpgrade::Skip` 枝: `upgrade_save: None`（変更前から None）
  4. `load_cache_in` の現行版（v7）早期リターン: `upgrade_save: None`（変更前から None）

### 変異 1: cache-hit 枝の配線 `cache_save: result.upgrade_save.unwrap_or(Duration::ZERO)`
→ `cache_save: Duration::ZERO` に置換

**結果: 落ちた（予測どおり）。**
```
--- clippy: 失敗 (exit 101) ---
snotra-core\src\indexer.rs:1149:5: error: field `upgrade_save` is never read
--- core-test: 失敗 (exit 101) ---
failures:
    indexer::tests::load_or_scan_with_stats_reports_upgrade_save_in_cache_save
test result: FAILED. 604 passed; 1 failed; 11 ignored
```
指示どおりの検知器（`load_or_scan_with_stats_reports_upgrade_save_in_cache_save`）がまさに
落ちた。副作用として `LoadCacheResult::upgrade_save` が「配線先を失って未読になる」ため
clippy の dead-code 検査も同時に落ちる（配線を捨てる退行はこの経路でも検出される、という
追加の発見）。

### 変異 2: `upgrade_legacy_cache_in` の `let upgrade_save = Some(save_started.elapsed());`
→ `let upgrade_save = None;`

**結果: 落ちた（予測どおり）。2 つの検知器が同時に落ちた。**
```
--- core-test: 失敗 (exit 101) ---
failures:
    indexer::tests::load_cache_reports_upgrade_save_only_when_it_upgrades_a_legacy_format
    indexer::tests::load_or_scan_with_stats_reports_upgrade_save_in_cache_save
test result: FAILED. 603 passed; 2 failed; 11 ignored
```
`LoadCacheResult` レベルの検知器（前者）と、`LoadOrScanStats` レベルまで配線を追う検知器
（後者）の両方が独立に落ちる——commit message の主張（「最終レビュー Important 1 の実際の
欠陥はこの配線が壊れていたことであり、`upgrade_save` 単体の検知器はこの配線を落とす退行では
落ちない」）とは違う変異（今回は Some を作る側そのものを壊した）なので both が落ちるのは
一貫している。

### 変異 3: `snotra-core/tests/memory_footprint.rs` の `delta_ms` を saturating 相当へ変更
`(total.as_nanos() as f64 - attributed.as_nanos() as f64) / 1_000_000.0`
→ `total.saturating_sub(attributed).as_nanos() as f64 / 1_000_000.0`

**結果: 何も落ちなかった（予測どおり「検知器は無い」）。**
```
cargo test -p snotra-core → 605 passed; 0 failed; 11 ignored（変異前と同数）
```
`delta_ms` の消費者は `measure_real_index_footprint`（`#[ignore]`、手元 release 実行専用の
計測ハーネス）内の `println!` 1 箇所だけであり、その値に対する `assert` は存在しない。
通常の `cargo test` では実行されず（ignored のまま）、コンパイルも通り clippy も通る
（`saturating_sub` は `Duration` の正当な API）。**この変更に検知器は無い、と明記する。**
これは PERFORMANCE.md への注記（残余 0〜1ms は旧意味論の値、現在の基準にしない）で人間の
判断に委ねられている領域であり、機構的な検査は存在しない。commit message の「残余（本 PR
では塞がない）」の記述と整合する。

### 変異 4: `LoadOrScanStats` 構築点（`load_or_scan_with_stats_in` の cache-miss 枝）で
`scan: scan_took, sort: sort_took` → `scan: sort_took, sort: scan_took`（scan と sort を入れ替え）
