### 3-1. 実装の正しさ

#### `enable()` の `unsafe` — `std::slice::from_raw_parts` の健全性【判定: 今日は健全】

```rust
let value = wide(&command_line_for(&exe));   // Vec<u16>（ローカル）
...
let bytes = unsafe { std::slice::from_raw_parts(value.as_ptr() as *const u8, value.len() * 2) };
let status = unsafe { RegSetValueExW(key.key(), ..., REG_SZ, Some(bytes)) };
```

4 つの要件を 1 つずつ確かめた:

- **アラインメント**: `*const u16`（align 2）→ `*const u8`（align 1）。**下げる向きなので常に妥当。** OK
- **長さ**: `Vec<u16>` の連続領域は `len() * 2` バイト。**過剰読みは無い**（`capacity` ではなく
  `len` を使っている点も正しい）。OK
- **REG_SZ の `cbData` に null 終端が含まれるか**: `wide()` が `chain(once(0))` で終端を足すので
  `value.len()` は終端を含み、`len() * 2` はその 2 バイトを含む。**Win32 の REG_SZ は cbData に
  終端を含めることを要求する**ので正しい。OK（終端を落とすと `Run` 値が壊れる形の誤りだが、
  ここは正しい）
- **寿命**: `value` は `bytes` より先に宣言され、`RegSetValueExW` の呼び出し時点で生存し、
  ムーブも変更（＝再確保）もされない。**今日の並びでは健全。** OK

**⚠️ ただし構造上の残余がある（下の R-1）。**

#### `is_enabled()` が読み取り失敗を `false` へ畳むこと【判定: 誤る向きは安全側だけ】

想定外の入力で「逆に倒れる」経路を探した。倒れない:

- `Run` キーが開けない（権限・不在）→ `false`。安全側（未登録と表示）
- 値が存在するが型が違う（REG_EXPAND_SZ / REG_DWORD）→ `RegQueryValueExW` は
  ERROR_SUCCESS を返すので `true`。**意味論「`Run` 値が存在する」と一致**しており矛盾しない
- 値が存在してデータが空 → `true`。同上
- **`true` を返しつつ実際には値が無い経路は見つからなかった。** `RegQueryValueExW` が
  不在の値へ ERROR_SUCCESS を返す条件が無いため

`lpData = None` かつ `lpcbData = None` で存在確認する呼び方も Win32 の契約どおり。

#### `path_env.rs` — ガードを `unsafe` ブロックの外へ出したことによる挙動変化【判定: 無い】

差分が**消した行が持っていた不変条件**を名指しして、再確立地点を探す向きで見た:

| 消した行の不変条件 | 再確立地点 | 判定 |
|---|---|---|
| `RegOpenKeyExW(HKEY_CURRENT_USER, "Environment", Some(0), KEY_READ, ..)` | `win_registry::open_hkcu` に逐語で移設 | OK |
| 失敗時に early return（`.ok().ok()?`） | `open_hkcu` が `None` を返し、呼び出し側の `?` が同じ位置で return | OK |
| 成功時にのみガードを構築 | `open_hkcu` の `Some(RegKeyGuard(raw_key))` | OK |
| ガードが最後の使用より後に Drop される | **スコープが「unsafe ブロック末」から「関数末」へ延びた**（L87 → L89）。最後の使用は L49 なので、**寿命は伸びる向きにしか変わっていない**。短くなる経路は無い | OK |
| ブロック内の early return（L43 の `buf_size == 0`、L57 の 2 回目の `?`）でも閉じる | ガードは外側スコープなので**それらの return でも Drop する**（従来と同じ） | OK |

**use-after-free も二重クローズも早期 return の取りこぼしも導入されていない。**
L88 のコメント「key は RegKeyGuard の Drop で自動クローズ」も現在も真。

**R-1【`unsafe` の構造的残余】`from_raw_parts` の返す寿命が `value` に縛られていない**

### R-2（`Registry(0)` = ERROR_SUCCESS を診断として見せる）→ **解消**

見つけたときの道具は「型と経路を辿る」だったので、同じ形で 2 段に測った。

(a) **型**: `open_hkcu` は `Result<RegKeyGuard, WIN32_ERROR>` を返し、`Err` を作る枝は
    `if status.is_err() { return Err(status); }` の 1 本だけである。
    `windows` crate の実装を一次証拠で確認した:
      C:/Users/<user>/.cargo/registry/src/.../windows-0.61.3/src/extensions/Win32/Foundation/WIN32_ERROR.rs
        pub const fn is_ok(self) -> bool { self.0 == 0 }
        pub const fn is_err(self) -> bool { !self.is_ok() }
      （0.62.2 も同一）
    → **`is_err()` ⟺ `self.0 != 0`**。ゆえに `Err(status)` は**必ず非ゼロを載せる**。

(b) **経路**: `open_run_key` が `.map_err(|status| AutostartError::Registry(status.0))` で
    そのコードを載せる。`Registry` の構築点を全部数え直した:

        ./snotra-core/src/autostart.rs:199   return Err(...Registry(status.0));         ← RegDeleteValueW 失敗
        ./snotra-settings/src/tabs/general.rs:62   Err(...Registry(code)) => {           ← 消費側

## 2-4. 修正差分のレビュー（3 観点）

### 実装の正しさ

呼び出し側が名指しした 3 点を、1 つずつ測った。

**(1) `open_hkcu` の戻り型変更が `path_env.rs` の早期 return とガードの寿命を変えていないか
    → 変えていない。**

  差分は 1 行:  `...open_hkcu(w!("Environment"), KEY_READ)?`
             → `...open_hkcu(w!("Environment"), KEY_READ).ok()?`

  消した行の不変条件を名指しして再確立地点を探す向きで見た:
  - **束縛位置**: `let key = ...` は変更前後とも L27（`unsafe` ブロックの**外**・L29 の直前）。動いていない
  - **早期 return**: `Result` に `.ok()` を掛けて `Option` へ落とし、同じ `?` が同じ位置で
    `None` を返す。**開き失敗時に関数を抜ける挙動は同一**
  - **ガードの寿命**: `.ok()` は `Ok(guard)` を `Some(guard)` へ**ムーブ**するだけで
    `Drop` を走らせない（`Err` のときは `T` が存在しない）。`key` は関数末（L89）まで生き、
    最後の使用は L49 の 2 回目の `RegQueryValueExW`。**使用より後に落ちる関係は不変**
  - **ブロック内の early return**（L43 の `buf_size == 0`、L57 の 2 回目の `?`）でも
    `key` は外側スコープゆえ Drop する。**不変**
  - L88 のコメント「key は RegKeyGuard の Drop で自動クローズ」も**今も真**
  → use-after-free も二重クローズも早期 return の取りこぼしも導入されていない。
    `cargo test -p snotra-core` の 611 件が緑であることは傍証にすぎず、
    根拠は上の 5 項目の対応づけである。

**(2) `as_bytes` の `size_of_val` が元の `value.len() * 2` と同じ長さを返すか
    → 返す。null 終端も含む。**（2-3 の実測表が一次証拠。5 ケース全一致）
  REG_SZ の `cbData` が終端を含む必要がある件も、`wide()` が `chain(once(0))` で
  終端を足し `size_of_val` がそれを数えることを実測で確認した（`nul_included=true`）。

**(3) `is_enabled` の `let Ok(key) = ... else` が `let Some(key) = ... else` から
    意味を変えていないか → 変えていない。**
  - **成功時**: どちらも中身を `key` へ束縛する。同一
  - **失敗時**: どちらも `else` 節へ入り `return false`。`Result` 版は `Err` のペイロード
    （`AutostartError`）を捨てるが、この型は `Drop` を持たない（`#[derive(Debug, Clone,
    PartialEq, Eq)]` のみ）ので**破棄の副作用も無い**
  - **失敗する条件の集合**: `open_run_key` が `Err` を返すのは `open_hkcu` が `Err` を
    返すときだけで、それは `RegOpenKeyExW` が失敗したとき。**変更前に `None` を返していた
    条件と同一**（`open_hkcu` の失敗判定は `.ok().ok()?` から
    `if status.is_err() { return Err(status) }` へ書き換わったが、`WIN32_ERROR::ok()` も
    `self.0 == 0` で分岐するので**同じ述語**である）
  → 「読み取り失敗は `false`」の意味論は保たれている。

## 2-7. 追補 — §2-1 W-2 の全称を測り直した

§2-1 の W-2 で「**非 Windows で Rust をビルドする経路は CI に存在しない**」と全称で書いたが、

出荷前に測り直した（`AGENTS.md`「何が増えたら/変わったらこの文は偽になるか」）。

**測り方**: 全 workflow の `cargo` の出現を 1 件残らず列挙し、それぞれが属する job の
`runs-on` を突き合わせた。

  create-release.yml:63 `build-release`           `uses: ./.github/workflows/release.yml`
                                                  （workflow_call。その唯一の job が windows-latest）
  ※ smoke.yml:78-82 / ci.yml:141-157 の `cargo`・`rustup` はコメント（どちらも windows job 内）

**ubuntu ジョブ 4 つの `run:` を全部読んだ**:
  ci.yml `node-check`(ubuntu)       : `npm ci` / `npm test`
  ci.yml `governance-check`(ubuntu) : `npm ci` / `node scripts/governance-check.mjs` / L118 の多行 run
