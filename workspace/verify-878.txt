--- 変異の強さの判定 ---

**強すぎない。** 変異版はビルドが通り（clippy -D warnings も PostToolUse hook 経由で沈黙）、
cargo test も落ちず、外から測る窓の寸法も変わらない。赤にしたのは当該検出器だけである。

**高さの食い違いだけで発火することを確認した**: show_w == frame_w == 768（幅側 inset_w は
正しいまま）で、show_h 54 と frame_h 64 の 10 px 差だけで赤になっている。この 10 px は
FrameGeom::inset_h の doc が「DPI 125% の環境で実測 10 物理 px」と記録した値そのもので、
注入がその数値を独立に再測した形になる（この機体の実測値: scale=1.25 / bar 43.2 論理 →
54 物理 / inset_w=18 / inset_h=10 / 幅 600 論理 → 750+18=768 物理）。

**ただし「やや弱い」側面がある（下の M1 と同じ論点）。** 検出器の**高さ軸**は
  show 側:  bar_rect_height_phys(bar, geom.scale) + geom.inset_h   （derive_bar_rect_phys）
  frame 側: bar_rect_height_phys(bar, geom.scale) + geom.inset_h   （read_bar_anchor）
という**逐語で同じ式の 2 回評価**である。ゆえに高さ軸が捕まえられるのは
derive_bar_rect_phys 側にだけ在る誤り（今回の変異はまさにこれ）であって、共有部
（read_frame_geom が読む inset_h そのもの、logical_to_phys の丸め規則）の誤りは両側が同じだけ
ずれるので沈黙する。**現実（OS の実測値）と突き合わせているのは幅軸だけ**である
（frame 側の width_phys は read_bar_anchor が読んだ GetWindowRect の外形幅）。
今回の注入は「検出器が守れる範囲の内側」を確かに撃ち抜いたが、検出器の射程そのものを
測ったわけではない。

3. 「挙動は変えない」の裁定（一次資料 + 実測）
================================================================================

問い: derive_bar_rect_phys の式が、変更前の `set_size(width, bar_height)` 直後の
outer_size() と同じ値を与えるか。

(a) dpi 0.1.2 の丸め規則 — 一致する
    ~/.cargo/registry/src/*/dpi-0.1.2/src/lib.rs
      impl Pixel for i32 { fn from_f64(f: f64) -> Self { round(f) as i32 } }   （u32 も同じ）
      /// Round f to the closest integer, rounding away from `0.0`
      fn round(f: f64) -> f64 { f.round() }
    layout::logical_to_phys の `.round()` と同一（0 から遠ざかる丸め）。新設のユニットテスト
    logical_to_phys_rounds_half_away_from_zero が .trunc()／銀行家丸めを 0.5 の 3 例で落とす。

(b) tao 0.35.3 の set_inner_size（windows） — 式が逐語で一致する
    platform_impl/windows/window.rs:273-313
      desired = size.to_physical::<i32>(scale_factor)              // = round(logical * scale)
      if window_flags.undecorated_with_shadows() {
          desired_w += (window_rect − client_rect).width           // = FrameGeom::inset_w
          desired_h += (window_rect − client_rect).height          // = FrameGeom::inset_h
      }
      util::set_inner_size_physical(...)
    util.rs:91-118 → adjust_window_rect は is_decorated=false のとき style から WS_CAPTION /
    WS_SIZEBOX を落とすので調整は実質恒等、そのまま
      SetWindowPos(cx=desired_w, cy=desired_h,
                   SWP_ASYNCWINDOWPOS|SWP_NOZORDER|SWP_NOREPOSITION|SWP_NOMOVE|SWP_NOACTIVATE)
    ⇒ その後の GetWindowRect（= outer_size()）は round(logical*scale) + inset を返す。
    これは derive_bar_rect_phys の式そのものである。**旧経路と新経路は同じ値を与える。**
    - undecorated_with_shadows() = MARKER_UNDECORATED_SHADOW && !MARKER_DECORATIONS。main 窓は
      decorations(false) + tauri 既定の shadow ゆえ真（実測でも真: 下の (d)）。
    - SWP_NOMOVE が立っていることを確認した ⇒ src-tauri/CLAUDE.md の「set_size は位置を
      動かさない（tao の util::set_inner_size_physical が SWP_NOMOVE を立てる）」は正しい。
    - SWP_ASYNCWINDOWPOS も立っているが、MSDN のとおり効くのは呼び出しスレッドと窓の所有
      スレッドが別の入力キューに属するときだけ ⇒ view.rs:1294-1296 の記述は正しい。

(c) inset を読む時刻の違い — 影響しない
    旧: 1 手目の set_size の**後**に outer_size() を読む（inset は tao 自身が set_size の中で
        window_rect−client_rect として読んだもの）。
    新: set_size より**前**に read_frame_geom が同じ差を読む。
    非クライアント分は style + DPI から決まる量（AdjustWindowRectExForDpi の入力が style/DPI/
    menu だけ）でサイズに依存しないため、読む時刻の差は値を変えない。

(d) 実測による裏づけ — 幅軸が現実と一致し続けている
    check_show_bar_rect の**幅軸は導出値 vs OS 実測値**の突き合わせであり、clean 2 回・
    mutant 1 回・revert 1 回のすべての show で show_w == frame_w == 768 だった。
    768 = logical_to_phys(600, 1.25) + inset_w(18) = 750 + 18。すなわち
    「set_size(LogicalSize) の後に GetWindowRect が返す値 == 導出式」が実機で成立している。

(e) 変わらないもの
    - egui_show:done の payload は {ms, height} のまま（height は実高）。smoke の
      「payload height 86」断言は 3 回とも同じ値。
    - 位置決めの基準モニター（カーソル/プライマリ）・クランプの算術（WorkArea::clamp）は不変。
    - scale の出所は新旧とも「窓の現在の scale_factor()」。ターゲットモニターの DPI が違う
      場合の扱いは変わっていない（既存の性質。下の ⚠️ W2）。

M1. 検出器の「受容する残余が 2 つある」という**数え上げが不足している**
    所在: window_coordinator.rs:797-799（check_show_bar_rect の doc）と
          docs/adr/ADR-show-path-derives-bar-rect.md:29「検出器の死角」
    doc は退行として「非クライアント分の落とし・scale の取り違え・丸め規則の食い違い」を
    捕まえると宣言し、その隣で残余を **2 つ**（show と初フレームの間の config 変更／DPI 変更）
    と数えている。しかし高さ軸は §2 で示したとおり**同じ式の 2 回評価**であり、3 つ目の死角が

    inset_h は幅軸の対象外である）。
    AGENTS.md「保証を宣言する文の隣に、保証されていない数や一覧を置かない」および
    「数え上げは偽になる時点が確定している」に当たる形。**直し方は数を 3 へ直すことではなく、
    列挙をやめて「高さ軸は導出の 2 回評価であり、現実と突き合わせているのは幅軸である」という
    機構の記述へ倒すこと**だと考える（採否は主エージェントの判断）。
    なお、これは「検出器が弱い」という指摘ではない——この PR が持ち込みうる退行

-------- ⚠️ 確信の持てない所見: 3 件 --------

⚠️ W1. 非 Windows ビルドで show_bar_width_phys / show_bar_height_phys が dead_code になりうる
    EguiShellState の新フィールド 2 本は、**書き込みが show_egui_main の #[cfg(windows)] ブロック、
    読み出しが #[cfg(windows)] 版 check_show_bar_rect だけ**である。#[cfg(not(windows))] 版の
    check_show_bar_rect は空スタブでフィールドを読まない。ゆえに非 Windows ターゲットでは
    「field is never read」が出て、-D warnings 下では赤になる可能性がある。
    EguiShellState の既存フィールド（hide_pending / reset_pending / show_read_indexing /
    show_read_toast / show_applied_height_bits）はいずれも cfg なしの view.rs から読まれており、
    **この非対称は本差分が初めて持ち込んだもの**である。
    **測れていない**: この環境にも CI にも非 Windows の Rust ビルドが無い（ci.yml の
    node-check は ubuntu だが npm のみ、rust-check は windows）。windows crate 依存のため
    クロスチェックも現実的でない。ゆえに「起きる」と断定はできず、**誰も通さない経路である**
    という事実のほうが本体かもしれない。フィールドに #[cfg(windows)] を付けるだけで消える。

⚠️ W2. scale はターゲットモニターではなく「窓が今いるモニター」のものである
    derive_bar_rect_phys は set_position より**前**に window.scale_factor() を読み、その物理値を
    **別モニターの作業領域**へクランプしうる（follow_cursor_monitor で DPI の違うモニターへ
    出すとき）。**旧経路も同じ**（1 手目の set_size は self.scale_factor() を使い、
    outer_size() はその結果を返す）なので**退行ではなく既存の性質**であり、本差分の所見として
    は弱い。ただし ADR の死角の列挙にも入っていない。実害は「DPI をまたぐ初回 show で
    クランプ材料が最大 25% ずれうる」で、次のフレームのクランプが直す。確信が持てないのは
    実機（複数 DPI）で測っていないためである。
